# TEI Product Value

## この文書の目的

TEI（鼎／テイ）は、単に画面やテーブルを速く作るためのローコード基盤ではありません。

業務システムを含むソフトウェアには、長い運用と開発の中で蓄積されたDomainの意味、例外、制約、既存資産、Infrastructure上の判断があります。実装技術、生成AI、担当者、実行環境が変わっても、それらを失わず、必要に応じて実現方法を選び直し、別Applicationへ再利用できることにTEIの中心的な価値があります。

この文書では、個別機能や現在の実装状況より上位にある、TEIが守るべき価値を定めます。

## 一文で表す価値

**TEIは、ソフトウェアと業務の意味を技術から独立して保ち、生成AIがその意味から継続的にApplicationを構築・変更し、必要に応じてAIエージェントが業務遂行にも利用でき、人間が高密度なProjectionから理解・判断・再利用できる基盤を目指します。**

この価値の中心にあるのは、**業務の意味の正本（single source of truth、以下SSOT）を一つに保ち、画面・コード・DB・文書・AIの出力をすべてそこから導かれるものとして扱うこと**です。以下の1〜8はこのSSOTを守るための性質であり、次節はSSOTが誰にどんな価値をもたらすかを述べます。

## 意味のSSOTが生む事業価値と社会価値

### 背景 — 正本は放っておくと失われる

業務の意味は、最初は要件定義書や担当者の頭の中にあります。開発が進むと、同じ意味がコード、テーブル定義、画面、テスト、運用手順、Excelの設計書へ少しずつ違う形で写されます。数年たつと、どれが正しいのかを誰も言えなくなり、「今のコードの振る舞いが仕様」という状態になります。

生成AIはこの流れを加速させます。AIはコードや文書を大量に速く作れますが、作られたものが増えるほど、それらの間の食い違いも増えます。正本が無いまま生成量だけが増えると、人が確かめるべき範囲は際限なく広がります。

### 防ぎたい損失

SSOTが無いときに組織と社会が払っている損失を、TEIは次のように捉えます。

| 損失 | 起きていること |
| --- | --- |
| 仕様の再発見 | 変更のたびに、コード・DB・関係者への聞き取りから「本来の意味」を掘り起こし直す |
| 刷新時の意味の喪失 | 技術を入れ替えるとき、例外処理や業務上の判断が移行の途中で落ちる |
| 属人化 | 意味を知っている担当者が異動・退職すると、システムを安全に変えられなくなる |
| 技術への閉じ込め | 意味が特定の製品・言語・ベンダーの形式にしか存在せず、選び直す交渉力を失う |
| AI生成物の検証不能 | AIが作ったものが何に基づき、何を壊し得るかを確かめられず、使える範囲が狭まる |
| 説明不能 | 「なぜこう動いたのか」「誰が承認したのか」「実際に何が起きたのか」を後から示せない |

### 事業価値 — 業務システムを持つ組織にとって

1. **変更の単位コストを下げる。** 影響範囲を業務の意味から辿れるため、変更のたびの調査と回帰確認が縮みます。同じ規則を画面・API・AIエージェントがそれぞれ持ち直さないので、一か所の変更が全体へ伝わります。
2. **刷新と移行のリスクを下げる。** 意味を作り直さずに実現方法だけを選び直せるため、段階的な移行と既存資産（SQL、既存の認証仕様など）の温存ができます。一括置換に賭ける必要が減ります。
3. **知識資産が複利で効く。** 一つのApplicationで確立したData、Relation、制約、Contractは、次のApplicationで同じidentityのまま再利用できます。作るほど次が速く、安全になります。
4. **AI活用の上限を引き上げる。** AIへ正確な文脈（何を意味し、何を壊してはいけないか）を渡し、人の承認を「小さい意味の差分」に絞れるため、AIに任せられる範囲が広がります。
5. **技術選択の自由を保つ。** 意味が特定の技術から独立しているので、Provider・UI技術・AI基盤を、その時点で最も適したものへ選び直せます。

### 社会価値 — 組織の外へ及ぶもの

1. **社会を支える業務システムを継続できる。** 行政、医療、物流、金融、製造などのシステムは数十年使われ、担い手の不足と世代交代の中で保守されます。意味を人から切り離して引き継げることは、これらのサービスを止めずに変え続けるための前提です。
2. **自動化とAIに説明責任を持たせる。** AIや自動処理が業務を行う時代には、「何を根拠に、誰の承認で、何を実行し、実世界で何が起きたか」を追えることが、利用者と社会からの信頼の条件になります。TEIは提案と承認、命令と観測、分からない状態を分けて保持します。
3. **権限の暗黙の拡大を防ぐ。** AIが業務知識を読めることを、実行してよいことと同一視しません。安全なAI利用の土台になります。
4. **知識を特定の組織・個人・ベンダーに閉じ込めない。** 業務の意味を移植可能な形で持つことで、組織の再編や委託先の交代、他組織との連携でも知識が失われにくくなります。
5. **同じ意味の作り直しという社会的な無駄を減らす。** 刷新のたびに要件を掘り起こし直す労力を、新しい価値を作る側へ回せます。

### 具体例（Referenceから）

例はRequirementやCanonical meaningではなく、価値の働き方を示すためのものです。

- `order_entry`では、受注確定の前に守る業務Validationを一つの正本として持ち、Application Driverと第一Web Targetが同じ規則を使います。画面側へ規則を書き写していません（Gate C: Semantic Conformance）。
- 第二Application `repair_intake` は、`order_entry`で使っていた顧客の意味（`customer.customer`）と顧客照会のContractを、コピーではなく同じidentityのまま参照して組み立てられました。既存の意味を作り直さずに次のApplicationへ再利用した最初の実例です。
- 受注確定のCommandが受け付けられたことと、外部の状態が実際に変わったことを、別の結果として保持します。「受け付けた」を「完了した」と読み替えません。

### 価値の確かめ方

TEIは、価値を画面数やコード生成量では測りません。外部の研究や他製品の数値を、TEI自身で確かめないまま目標値にすることもしません（RQ-022）。代わりに、次のような観測できる事実で価値を確かめます。

- 一つの業務規則を変えるとき、人が手で直す必要がある場所の数
- 画面・API・AIエージェントの間で、同じ規則の食い違いが生じないこと
- 別Applicationで再利用した意味について、元のidentity・前提・差分を追跡できること
- 実行・承認・観測について、後から根拠を示せること
- 分からない状態が、成功や安全として扱われていないこと

どこまで確かめられているかの現在地は[`docs/status.md`](../../docs/status.md)が正本です。

### まだ主張しないこと

- 費用削減や生産性向上の数値的な効果は、まだ測定していません。
- 社会価値は目指す方向であり、公共性の高い実システムで実証したものではありません。
- 現在の実証は小規模なReference Application（`order_entry`、`repair_intake`等）に限られます。

## 1. 業務の意味を失わない

TEIが最も優先するのは、画面、DB、プログラム、クラウド構成より手前にある「何を意味しているのか」を保つことです。

受注、顧客、契約、請求、承認、履歴、状態遷移といった業務概念は、特定のテーブルや画面と同一ではありません。実装上の都合で意味を縮めたり、逆に実装詳細を業務概念そのものとして固定したりしないことを重視します。

そのため、Canonicalな意味、authoring source、実現方法、実行結果、観測結果を同一視せず、相互に追跡できる形で分けて扱います。

## 2. 実現方法を閉じない

業務上の意味が保たれているなら、その実現方法は必要に応じて選び直せるべきです。

TEIは、特定のDB、UI技術、プログラミング言語、クラウド、workflow engine、AI agent基盤だけで世界を閉じません。SQLやGoなど、その領域で既に成熟しているnativeな技術を無理に独自DSLへ移し替えることもしません。

Provider、Capability、Binding、Projection、Adapterといった境界を通じて、同じ意味を複数の技術へ結び付けられることを価値とします。

## 3. 現実の業務複雑性を削らない

既存の業務システムは、教科書どおりの単純なCRUDだけではありません。

一つのApplicationが複数Databaseを利用すること、Databaseごとに障害境界やtransaction境界が異なること、システム固有の認証・認可・有効期限・失敗回数制御があること、既存SQLや固有処理をそのまま移行しなければならないことがあります。

TEIは、こうした事情を「理想形に合わない例外」として排除するのではなく、業務システムの現実として受け入れます。

標準化できるところは標準化しつつ、標準に入らない部分をCapabilityやcustom implementationへ逃がし、全体の意味と追跡性を失わないことを重視します。

## 4. 厳格さを利用者の負担にしない

業務システムでは、曖昧さを残してはいけない境界があります。型、関係、依存、権限、transaction、release、実行対象などは、必要なところでは厳格でなければなりません。

一方、その厳格さを、人が大量の設定や二重管理を続ける負担へ転嫁してはいけません。

TEIは、内部規則を厳密に保ちながら、Editorと生成AIが不足や矛盾を見つけ、既存の知識や選択履歴を再利用し、必要なときだけ控えめに確認することで、実用上はできるだけ軽く扱える状態を目指します。

同じ質問を繰り返す、既に選んだ内容を再入力させる、機械が導出できる情報を人に二重管理させる、といった負担は避けます。

## 5. 「実行した」と「実際にそうなった」を分ける

外部システムへ命令を送ったことと、外部世界が期待どおり変化したことは同じではありません。

TEIは、実行要求、acknowledgement、Observation、Evidence、reconciliationを分離します。状態が分からない場合は、都合よく成功や失敗へ丸めず、「分からない」という状態を保持します。

この姿勢は、deployment、database migration、外部process、将来のAI支援実行にも共通します。

## 6. 設計知識を実行可能な資産へ変える

設計書は、コードを書いた後に説明のためだけに残る文書ではなく、実装・検証・生成・実行へつながる基準である方が望ましいと考えます。

TEIでは、設計内容を一つの画面形式やDSL形式へ固定せず、同じCanonicalな意味を、詳細設計書ビュー、表、グラフ、UI、自然言語、実行用IRなどへProjectionできることを目指します。

これにより、設計と実装が別々に陳腐化する状態を減らします。

## 6.1 構造化された設計知識から実装を導けること

TEIの価値は、ApplicationにUIや業務ロジックがある場合だけに生じるものではありません。

あるソフトウェアについて、

- どの情報を持つか
- 何と何が関係するか
- どの状態を取り得るか
- どの制約を守るか
- 何を入力し、何へ変換するか
- どのCapabilityへ接続するか

を、図・表・グラフ・モデル等で高密度に整理し、その同じ設計資産からValidation・生成・実行・文書を導きたい場合、TEIの適用価値は高くなります。

これは「図を正本にする」ことではありません。図表はCanonicalな意味を読み書きするProjectionまたはauthoring surfaceであり、同じ意味を別形式へ切り替えられることを重視します。

したがってTEI適用判断では、**Application Planeの大きさ**と同時に、**設計知識を構造化して外在化し、そこから実装を導きたい度合い**を独立した軸として見るべきです。

## 6.2 生成AIが継続的にApplicationを構築・変更できること

TEIは、生成AIが一度だけコードを生成するための入力形式ではありません。

生成AIが実装作業の大部分を担う開発形態では、重要なのは「コードを書けること」よりも、

- 何を意味するApplicationか
- 何が既存知識として再利用できるか
- どこが今回の変更対象か
- 何を壊してはいけないか
- どの実装がderivedで再生成可能か
- どこがnative assetで慎重に扱うべきか
- 変更後に何を検証すればよいか

を機械可読な形で継続的に取り出せることです。

TEIでは、生成AIがRepository全体を毎回読み直して暗黙知を再構成するのではなく、Canonical meaning、Source、Pattern、Policy、Capability、Binding、Evidence、Decision history等から必要なcontextを取得し、変更を構成できる状態を目指します。

コードは重要な実行資産ですが、Application知識の唯一の容器にはしません。生成・再生成可能な実装はderived realizationとして扱い、native codeにしか存在しない重要な意味はSource Indexや明示的なContractへ接続します。

また、Applicationは完成して終わるものではありません。運用、制度、利用者要求、Provider、Targetの変化に応じて継続的に変更されます。TEIは、AIが過去の判断と現在の意味を読み直し、局所的な変更を安全に積み重ねられる基盤であることを重視します。

## 6.3 人間の認知効率を最大化すること

生成AIが実装を担うほど、人間にとって希少になるのはcoding throughputではなく、**複雑なApplicationを理解し、重要な判断へ注意を配分する認知帯域**です。

TEIは、人間へ大量のgenerated codeを読ませることを主要な確認方法にはしません。

同じCanonical meaningを、

- 高密度な表
- graph
- flow
- UI Projection
- dependency / impact view
- semantic diff
- diagnostic
- Evidence / provenance
- natural language

へ切り替え、目的に応じて必要な情報だけを圧縮して見られることを重視します。

人間が確認すべき対象も、全面的な実装詳細ではなく、

- 何が変わったか
- なぜ変わったか
- 何に影響するか
- どこが未確定か
- どの例外があるか
- 何をAIが判断し、何を人間が承認したか
- どのEvidenceから再確認できるか

へ寄せます。

TEIにおけるEditor / Projectionの価値は、単なるvisual authoringではなく、**人間が少ない認知負荷で大きなソフトウェア構造を理解・判断できること**にあります。

## 6.4 Domain・Infrastructure知識を移植可能な資産にすること

継続的なApplication開発では、一つのシステムで得た知識を次のシステムでも再利用できることが重要です。

TEIでは再利用対象をsource codeだけに限定しません。

- Domain type / relation / constraint
- Business Procedure / Pattern
- Policy / Variation
- Validation
- Capability contract
- Authorization rule
- Database contract / mapping
- deployment / runtime bindingの知識
- Provider固有の制約や適合条件
- 過去のDecision / Evidence

などを、実装技術と適切に分離したうえで再利用・移植できる状態を目指します。

再利用とは、別Applicationへ無条件にcopyすることではありません。元の意味、前提、依存、適用条件、Variation、Evidenceを追跡でき、移植先との差分を明示して再適用できることを重視します。

これによりTEIは、一つのApplicationを作る道具だけでなく、**Application開発を重ねるほどDomain知識とInfrastructure知識が蓄積し、次のApplicationへ移植しやすくなる基盤**になります。

## 6.5 AIエージェントが業務知識を読んで直接仕事を遂行できること

TEI成果物の利用者は、人間とApplication builderだけに限定しません。

場合によってはAIエージェントが、

- Business Procedure
- Business Action
- Data / Relation
- Policy / Constraint
- Semantic Capability
- Authorization
- Runtime Binding
- Evidence requirement

を読み、許可された範囲で業務を直接遂行できます。

この場合、従来のUIは業務遂行の唯一の入口ではありません。

```text
TEI business / system knowledge
        ↓
AI agent understanding / planning
        ↓
authorized Capability / Business Action
        ↓
Command
        ↓
Observation / Evidence
        ↓
business result / unresolved
```

ただし、TEIを読めること自体は実行権限を意味しません。AIエージェントのautonomy、Capability invocation authority、Resource access、side-effect authorityは独立して制御します。

また、AIが業務を行ったことと、業務上期待された結果が実世界で成立したことも分けます。Command、acknowledgement、Observation、Evidence、reconciliationの境界は、人間や通常Applicationが実行主体の場合と同様に維持します。

このためTEI成果物は、**Applicationの設計資料**であると同時に、**人間・Application・AIエージェントが共有して利用できる運用可能な知識基盤**であることを目指します。

## 7. 認知機能を、曖昧さの解消と設計支援へ使う

TEIが扱う業務上の意味は厳格である必要がありますが、そこへ至る入力は必ずしも厳格ではありません。既存のExcel設計書、自然言語、ソースコード、命名揺れ、古い仕様書、運用上の例外などには、人間なら文脈から判断できても、単純な規則だけでは確定しにくい部分があります。

TEIでは、こうした曖昧な境界へ、生成AIだけでなく、規則、embedding、分類器、ローカル軽量モデル、外部の認知基盤など、性質の異なる認知手段を利用できることを重視します。

ただし、認知結果とCanonicalな意味は同じではありません。

```text
cognitive observation / mapping candidate
  != canonical business meaning
  != accepted binding
```

たとえば「顧客番号」と「CUST_ID」が同じ業務概念らしいと認知系が判断しても、それだけでCanonical modelを書き換えません。既存の制約、Evidence、利用者の判断、検証可能な規則と照合し、採用された対応だけを明示的な意味へ昇格させます。

AIや認知系が担える範囲が将来広がっても、この境界は維持します。人間が逐次すべてを入力することを前提にはしませんが、**どの認知から、どの根拠で、何が正式なモデルへ採用されたかを追えること**を優先します。

## 8. SUI・SEI・EKIとの境界

TEIは、SUI Sensemaking、SEI Cognition、EKI Fabricと組み合わせて利用できますが、それらをTEI内部の必須moduleとはみなしません。

- **SUI Sensemaking** は、未整理な材料から関係・仮説・構造・統合を形成し、意味を成熟させるsensemaking lifecycleを主に扱います。SUIで安定してきた意味構造はTEIへのformalization candidateになり得ますが、自動的にTEIのCanonical meaningへ昇格しません。
- **SEI Cognition** は、認知・問い・不確実性・根拠・判断・Capability・Provenanceの継続性を主に扱います。TEIは曖昧なmapping、候補探索、例外検知などでSEIのCapabilityを利用できますが、SEIのDecisionやRecommendationをTEIのCanonical modelや実行権限と同一視しません。
- **EKI Fabric** は、異質で一時的な計算資源を安全に利用し、計算をどこで実行するかを主に扱います。TEIのValidation、Generation、Simulation、認知処理等をEKI上で実行できても、計算配置は業務上の意味の正本にはなりません。
- **TEI** は、十分に明確化された業務上の意味をCanonicalなformal modelとして保持し、検証・実装・実行可能な形へ接続する責務を持ちます。

この関係を固定pipelineにはしません。TEI単独でも成立し、必要なときだけ隣接Productや他のOSS・Providerを利用できることを重視します。

## 価値が衝突したときの優先順位

設計上の価値が衝突した場合は、原則として次の順に守ります。

1. 業務上の意味を失わないこと
2. 誤った確定や暗黙の権限拡大を避け、追跡・検証できること
3. 現実の業務要件や既存資産を無理に削らないこと
4. 実現方法を将来選び直せること
5. 利用者の二重管理や不要な操作を減らすこと
6. 自動化や開発速度を高めること
7. 個別実装を簡単にすること

下位の都合で上位の価値を損なう場合は、実装側を見直します。

## TEIが目指さないもの

TEIは、次の状態を目的にはしません。

- すべての業務資産を独自DSLへ移し替えること
- 特定のUI、DB、クラウド、workflow engineへ利用者を閉じ込めること
- 生成AIやAIエージェントへ、TEIを読めることや自律度の高さだけを理由に強い本番権限を与えること
- 「簡単に見えること」のために業務上の例外や不確実性を隠すこと
- 派生物を正本へ格上げし、どこがauthoritativeなのか分からなくすること
- 画面数やコード生成量そのものをプロダクト価値とすること
- generated codeや特定agentの会話履歴を、Application知識の唯一の正本にすること
- AIエージェント専用Knowledge Storeを、Canonical meaningの第二の正本として恒久化すること

## 変更を評価するための問い

大きな設計変更では、少なくとも次を確認します。

- 業務上の意味は、変更前より明確になっているか
- 特定技術の都合がCanonicalな意味へ混入していないか
- nativeな資産をnativeなまま扱えるか
- 既存システムの複雑性を不当に切り捨てていないか
- source、meaning、realization、execution、observationを追跡できるか
- 分からない状態を、誤って一致・成功・安全とみなしていないか
- 厳格な規則のために、人へ不要な二重管理を要求していないか
- AIの提案と、採用済みの決定を区別できるか
- AIエージェントが業務Actorになる場合、理解・自律度・実行権限・Resource権限・観測Evidenceを分離できるか
- 人がgenerated codeを読まなくても、意味・差分・影響・例外・Evidenceを十分に理解できるProjectionがあるか
- Domain / Infrastructure知識を別Applicationへ移植するとき、前提・Variation・Evidenceまで追跡できるか
- 将来別のProviderやTargetへ移るとき、業務の意味を作り直さずに済むか
- 業務の意味のSSOTを一つに保ったまま実現しているか。派生物の側に、意味の第二の置き場を作っていないか
- 利用組織の損失（仕様の再発見、刷新時の意味の喪失、属人化、技術への閉じ込め）を減らす方向か
- AIや自動化が関わる場合、根拠・承認・実行・観測を後から第三者へ説明できるか

これらに答えられない変更は、機能として便利でもTEIの中心価値から外れている可能性があります。
