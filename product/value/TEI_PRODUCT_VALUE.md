# TEI Product Value

## この文書の目的

TEI（鼎／テイ）は、単に画面やテーブルを速く作るためのローコード基盤ではありません。

業務システムを含むソフトウェアには、長い運用と開発の中で蓄積されたDomainの意味、例外、制約、既存資産、Infrastructure上の判断があります。実装技術、生成AI、担当者、実行環境が変わっても、それらを失わず、必要に応じて実現方法を選び直し、別Applicationへ再利用できることにTEIの中心的な価値があります。

この文書では、個別機能や現在の実装状況より上位にある、TEIが守るべき価値を定めます。あわせて、その価値が、日々業務システムに関わる個人、業務システムを持つ組織、そのシステムに支えられる社会のそれぞれに何をもたらすかを定めます。

## 一文で表す価値

TEIは、ソフトウェアと業務の意味を特定のデータモデルや実装技術から独立して保ち、必要な意味体系を後から拡張・合成できるようにすることで、生成AIによる継続的なApplication開発、AIエージェントによる業務遂行、人間による高密度なProjectionからの理解・判断・再利用を同じ基盤上で支えることを目指します。

この価値を支える中核は二つあります。一つは、同じ業務上の関心事について正式に受理された意味の正本（single source of truth、以下SSOT）を一つに保つことです。画面、コード、Database、文書、AIの出力等は、その意味から生成・投影される場合と、既存のnative assetとして利用される場合があります。いずれの場合も、どの意味を実現・説明しているかをSource / Evidenceとともに追跡でき、同じ意味を複数の正本から推測で統合しません。もう一つは、その意味を表すモデル体系そのものを固定せず、新しい概念を後から既存の意味と整合する形で追加できることです。個別のデータモデルやworkflow体系ではなく、意味を識別し、関係付け、拡張し、合成し、検証するための共通機構をTEIのCoreに置きます。

ここでSSOTとは、意味の正本が一つであることを指し、すべての物理artifactをTEIが生成し直すことや、authoritative source fileが物理的に一つであることを求めるものではありません。異なる関心事を別のnative sourceが所有することは許容します。問題になるのは、同じ意味をTEIの宣言と既存codeが独立に定義し、実行時にheuristicでmergeしなければならない状態です（RQ-003、RQ-004）。既存のcode、DB、文書から意味を立ち上げる途中では、関係がまだ分からない資産を無理に正本へ取り込まず、Observed Actual、Desired Candidate、Accepted Canonical、Unresolved / Conflictを分けて、未解決を明示したまま説明できる範囲を増やします。

## TEIのコア価値 — 固定モデルではなく、意味を拡張・合成できること

TEIでは、データモデルもシステム開発における一つの表現形として扱います。Data、Function / Interaction、Business Procedure、UI、Policy等のどれか一つを、他のすべてが従う特権的な上位モデルにはしません。Canonical meaningは、それらを横断して関係付ける基準であり、特定の表現形式そのものではありません。

Coreの役割は、将来必要になる業務概念を先回りして網羅することではありません。新しい概念が現れたとき、PluginやDSL等から、そのidentity、適用範囲、既存概念との関係、制約、Validation、ProjectionやCapabilityへの接続を宣言し、既存の意味体系へ追加できる共通機構を提供することです。拡張同士が衝突する場合は、暗黙の上書きで処理せず、明示的な選択またはUnresolvedとして扱います。

この拡張性は、実装上の便利さだけではなくTEIのProduct Valueそのものです。再利用可能な抽象を一度定義すれば、その後のApplicationでは同じ概念、規則、変換、検証を再利用できます。Application固有のコードは、既存の抽象では表せない差分へ寄せられます。TEIが目指す生産性の源泉は、生成コード量ではなく、再利用可能な意味と機械的に導出できる範囲を増やし、固有実装と再判断を減らすことにあります。

生成AIにとっても、この構造が実装のレールになります。AIへ自由な実装空間をそのまま渡すのではなく、利用可能な意味概念、適用条件、依存、制約、Validation、Capabilityを機械可読に渡し、既存概念の探索、合成、決定論的な変換・検証、不足部分だけのProposalという順に進められるようにします。これにより、AIが同じ設計論点を毎回議論し直したり、暗黙の前提から異なる実装を作ったりする余地を減らします。誤りが起きないと仮定するのではなく、曖昧さをUnresolvedとして残し、機械的に確定できる範囲を増やすことで、誤りが入り込む余地を構造的に狭めます（RQ-015、RQ-031〜033）。

## 意味のSSOTが生む価値 — 個人・組織・社会

### 背景 — 正本は放っておくと失われる

業務の意味は、最初は要件定義書や担当者の頭の中にあります。開発が進むと、同じ意味がコード、テーブル定義、画面、テスト、運用手順、Excelの設計書へ少しずつ違う形で写されます。数年たつと、どれが正しいのかを誰も言えなくなり、「今のコードの振る舞いが仕様」という状態になります。

生成AIはこの流れを加速させます。AIはコードや文書を大量に速く作れますが、作られたものが増えるほど、それらの間の食い違いも増えます。正本が無いまま生成量だけが増えると、人が確かめるべき範囲は際限なく広がります。

### 三つの層と、そのつながり

SSOTの価値は、次の三つの層で現れます。

- **個人** — 業務を知る人、システムを変更する人、変更を承認する人、仕事を引き継ぐ人。価値は日々の仕事の中で生まれます。
- **組織** — 業務システムを持ち、変更・刷新・委託先の交代・AI活用を判断する組織。価値は資産として蓄積します。
- **社会** — その業務システムに支えられる利用者、取引先、監査する第三者、公共サービス。価値は組織の外へ及びます。

三つの層は独立していません。次の図のように、個人の一回の判断が組織の資産になり、組織の資産が社会への説明責任を支えます。

```text
個人  一人の判断や知識を、根拠つきの意味の差分として一度だけ残す
        ↓ 同じidentityのまま蓄積され、次の変更・次のApplicationで再利用される
組織  担当者・委託先・技術が替わっても、変更・刷新・AI活用の土台が残る
        ↓ 根拠・承認・実行・観測を、組織の外の人も辿れる
社会  長く使われる業務システムを止めずに変え続け、自動化とAIに説明責任を持たせる
```

この流れは、上の段の失敗を下の段で補えません。個人が中身を確かめられないまま承認していれば、組織に残る記録は形だけになり、社会への説明責任も名目になります。組織が監査の仕組みを整えても、個人の段で意味と根拠が残っていなければ、説明に使えるものがありません。このためTEIは、どの層の価値も、他の層の副産物としては扱いません。

### 防ぎたい損失

SSOTが無いときに払われている損失を、TEIは次のように捉えます。同じ損失でも、最初に負担を受ける人と、最後に影響が及ぶ範囲は異なります。

| 損失 | 起きていること | 主に負う人 |
| --- | --- | --- |
| 仕様の再発見 | 変更のたびに、コード・DB・関係者への聞き取りから「本来の意味」を掘り起こし直す | 調べる担当者。積み重なると組織の変更コストになる |
| 二重管理と繰り返しの確認 | 同じ意味を複数の場所へ手で入力し、同じ質問に何度も答える | 日々入力・確認する担当者 |
| 属人化 | 意味を知っている担当者が異動・退職すると、システムを安全に変えられなくなる | 休みにくく異動しにくい本人と、その人に依存する組織 |
| 形だけの承認 | 大量の生成物や大きすぎる差分を、中身を確かめられないまま承認する | 責任だけを負う承認者と、人による確認を信頼の根拠にする社会 |
| AI生成物の検証不能 | AIが作ったものが何に基づき、何を壊し得るかを確かめられず、使える範囲が狭まる | AI活用を判断する組織 |
| 刷新時の意味の喪失 | 技術を入れ替えるとき、例外処理や業務上の判断が移行の途中で落ちる | 組織と、そのシステムの利用者 |
| 技術への閉じ込め | 意味が特定の製品・言語・ベンダーの形式にしか存在せず、選び直す交渉力を失う | 組織 |
| 説明不能 | 「なぜこう動いたのか」「誰が承認したのか」「実際に何が起きたのか」を後から示せない | 組織と、説明を求める利用者・社会 |

### 個人にとっての価値 — 業務を知る人、変更する人、承認する人、引き継ぐ人

1. **調べ直しから判断へ時間を移せる。** 変更の前に、コード・DB・関係者の記憶から意味を掘り起こす作業が減ります。変更に必要な意味・決定・影響・未解決点へ機械的に辿れるため（RQ-027）、人は「何を変えるべきか」「例外をどう扱うか」という判断に時間を使えます。
2. **知っていることが、本人がいなくても働く。** 業務を知る人の判断は、誰が・何を根拠に決めたかと一緒に、意味として残すことを目指します。現在残るのは、Shared Acceptance Boundaryを通した変更の受理だけで、`.tei/decisions/`に記録されます（RQ-027。Variationを表す形はまだ無く、RQ-016の提案と決定の記録はDesign Onlyです）。本人は「その人にしか直せない」状態から離れ、休暇・異動・新しい仕事を選びやすくなります。
3. **承認が、中身のある判断になる。** 承認する人は、生成コードの全量ではなく、意味差分・影響・例外・未解決点・権限変更を見て判断し、必要なときだけ実装詳細へ掘り下げます（RQ-010、RQ-028）。中身を確かめられないまま責任だけを負う状態を避けます。
4. **分からないと言える。** 情報が足りないときは、推測で埋めずにunresolved（未確定）として保持できます（原則P11。Database等の外部状態の比較ではRQ-006、承認時に未解決点を示す面ではRQ-010 / RQ-028）。推測で埋めた値の責任を、個人が黙って抱え込まずに済みます。
5. **同じことを二度しなくてよい。** 一度答えた確認や一度選んだ内容を理由と共に再利用し、機械が導出できる情報を人が二重に管理しない状態を目指します（RQ-016、RQ-017）。確認と退けた提案を記録する形はまだ無く（ISSUE-000074は評価待ち）、現在は実現していません。
6. **新しく来た人が、早く安全に参加できる。** 新しい担当者も、別のAI modelやagentも、過去の会話履歴や特定の人への聞き取りに頼らず、高密度なProjectionから全体・変更対象・例外へ入れることを目指します（RQ-010、RQ-011、RQ-027）。機械側のPreviewと索引はありますが、人が読む面はまだありません（RQ-010はDesign Only）。

### 組織にとっての価値 — 業務システムを持つ組織の事業価値

1. **変更の単位コストを下げる。** 影響範囲を業務の意味から辿れるため、変更のたびの調査と回帰確認が縮むことを目指します。同じ規則を画面・API・AIエージェントがそれぞれ持ち直さない構造を目指しており、成り立てば一か所の変更が全体へ伝わります（RQ-003、RQ-013、RQ-026、RQ-027）。ただし現在は、どの規則を評価するかの選択がTarget側にあり、この点は成り立っていません（後述の具体例）。AIエージェントがこの規則を使う経路も、製品側にはまだありません。
2. **刷新と移行のリスクを下げる。** 意味を作り直さずに実現方法だけを選び直せるため、段階的な移行と既存資産（SQL、既存の認証仕様など）の温存ができます。一括置換に賭ける必要が減ることを目指します（RQ-001、RQ-004、RQ-008、RQ-009）。実際の移行や刷新での確認はまだありません。
3. **知識資産が複利で効く。** 一つのApplicationで確立した顧客のSemantic（Data）は、次のApplicationで同じidentityのまま参照して再利用できます。照会のContractも、互換範囲（`master_data.customer ^2`）の条件つきで再利用できます。Application固有のPattern、Business Relation、datasource aliasの結び付けは、移植先が自分で持ちます（RQ-029）。作るほど次が速く、安全になることを目指しますが、速さと安全性の向上はまだ測定していません。
4. **AI活用の上限を引き上げる。** AIへ正確な文脈（何を意味し、何を壊してはいけないか）を渡し、人の承認を「小さい意味の差分」に絞れるため、AIに任せられる範囲が広がることを目指します。AIが作った内容は、AIを介さず正本から同じ結果を再現して確かめます（RQ-015、RQ-021、RQ-028）。範囲がどれだけ広がるかは測定していません。
5. **技術選択の自由を保つ。** 意味が特定の技術から独立しているので、Provider・UI技術・AI基盤を、その時点で最も適したものへ選び直せる構造を目指します（RQ-001、RQ-007、RQ-008、RQ-013）。第二Targetでの確認はまだで（ISSUE-000026）、現在の実証は第一Web Targetに限られます。
6. **説明できる組織でいられる。** 障害対応、監査、委託先との責任分界の場面で、「何を根拠に、誰の承認で、何を実行し、何が観測されたか」を、担当者の記憶ではなく記録から示せることを目指します（RQ-016、RQ-018、RQ-021、RQ-027）。決定記録はShared Acceptance Boundaryを通った変更に限られ、消去・偽造しても意味とrevisionが変わらないEvidenceです。監査で改ざん耐性を求められる記録には、まだなっていません。

### 社会にとっての価値 — 組織の外へ及ぶもの

1. **社会を支える業務システムを継続できる。** 行政、医療、物流、金融、製造などには、数十年使われ、担い手の世代交代の中で保守されるシステムがあります。意味を人から切り離して引き継げることは、これらのサービスを止めずに変え続けるための前提になると考えます（RQ-001、RQ-027、RQ-029）。これは目指す方向であり、公共性の高いシステムでの確認はありません。
2. **自動化とAIに説明責任を持たせる。** AIや自動処理が業務を行う時代には、「何を根拠に、誰の承認で、何を実行し、実世界で何が起きたか」を追えることが、利用者と社会からの信頼の条件になります。TEIは提案と承認、命令と観測、分からない状態を分けて保持することを目指します（RQ-016、RQ-018、RQ-021、原則P11。AIエージェントの業務遂行はRQ-030）。Referenceでは、変更の受理と決定の記録、Commandと観測の分離まで確かめています。しかしAIエージェントが業務を遂行する経路は、製品側にまだありません（RQ-030はDesign Only）。
3. **人による監督を、名目にしない。** AIが関わる業務では、「人が確認した」ことが信頼の根拠として求められます。しかし、人が確かめきれない量や形で承認を求めれば、その確認は名目になります。TEIは、人が判断できる大きさと形（意味の差分、影響、例外）で承認を求めることで、人による監督を実質的なものに保つことを目指します（RQ-010、RQ-028）。承認に十分な面の条件はISSUE-000071で案を検討している段階で、実際の利用者での確認はまだありません。
4. **権限の暗黙の拡大を防ぐ。** AIが業務知識を読めることを、実行してよいことと同一視しません。安全なAI利用の土台になります（RQ-019、RQ-030）。
5. **知識を特定の組織・個人・ベンダーに閉じ込めない。** 業務の意味を移植可能な形で持つことで、組織の再編や委託先の交代、他組織との連携でも知識が失われにくくなります。ただし、移植できることは公開することではありません。機密、個人情報、secret、権限の境界を保ったまま、意味を持ち運べることを指します（RQ-019、RQ-029）。
6. **同じ意味の作り直しという社会的な無駄を減らす。** 刷新のたびに要件を掘り起こし直す労力を、新しい価値を作る側へ回せるようになることを目指します（RQ-029）。

### 層の間で価値が衝突するとき

ある層の価値を高めようとして、別の層の価値を損なうことがあります。

- 組織が生成量や承認件数で個人の仕事を測ると、人は中身を確かめずに承認を急ぐようになります。個人にとっての中身のある承認も、社会にとっての実質的な監督も失われます。
- 知識の移植性を高めようとして機密や権限の境界を緩めると、組織と社会の信頼を損ないます。
- 個人が手元のメモやAIとの会話にだけ判断を残すと、その人には便利でも、組織の資産になりません。判断は正本と決定の記録へ残します。
- 画面側へ業務規則を書き写すと短期の開発は速く見えますが、意味の第二の置き場ができ、後から組織の変更コストを押し上げます。

TEIは、一つの層の価値を、別の層の損失で買わないことを基本とします。それでも判断に迷う場合は、後述の「価値が衝突したときの優先順位」に従います。

### 具体例（Referenceから）

例はRequirementやCanonical meaningではなく、価値の働き方を示すためのものです。いずれも小規模なReference上の事実であり、本番運用での効果を示すものではありません。

- **組織 — 規則を書き写さない。** `order_entry`では、受注確定の前に守る業務Validationの内容を一つの正本として持ち、Driverのscenarioと第一Web Targetが同じ定義を読んで評価します。画面側へ規則の内容を書き写していません（Gate Cのexact revision `T = 0ba87a4e…`で取得したFunctional Evidence。Validation not-satisfiedの経路）。ただし、**どの規則を評価するか**の選択は、以前は第一Web Targetのコードとscenario testに一覧として書かれており、規則を一件足しても、その一覧を直さない限り画面からの実行では評価されませんでした。2026-10-06に、この選択をApplicationの`uses validation`宣言（`order_entry`の正本）へ移し、Driverがそこから選ぶようにしました（[ADR-0029](../../plan/adr/0029-application-validation-selection-from-canonical-declaration.md)、[ISSUE-000073](../../plan/issue/000073-derive-validation-selection-from-canonical.md)）。これで、規則の追加は正本の変更（Validationの定義とApplicationの宣言）で届きます。ただし、操作ごとに評価対象を変える仕組みと、Business Procedureが別に持つ同じValidationの参照との関係は、まだ決めていません。また、これは`order_entry`というReferenceでの確認で、他のTarget・API・AIエージェントの経路では確かめていません。
- **組織 — Domainの意味を再利用する。** 第二Application `repair_intake` は、`order_entry`で使っていた顧客の意味（`customer.customer`）と顧客照会のContractを、コピーではなく同じidentityのまま参照して組み立てられました。既存の意味を作り直さずに次のApplicationへ再利用した最初の実例です。ただし、顧客のSemanticは同じidentityでの参照ですが、Contractと照会Queryは互換範囲（`master_data.customer ^2`）の条件つきの再利用です。`order_entry`のPatternは引き継がず、`repair_intake`が自分のPattern（`repair_intake.customer_reference`）を持ちます。
- **組織 — Infrastructureの知識も再利用する。** `repair_intake`の顧客マスタは、各Environmentへ1行ずつ結び付けを足すだけで既存の`master_data`インスタンスへつながり、Driverで実行する段階では、Queryを実行するための新しいEnvironment sourceは不要でした。`order_entry`のために書かれた既存のContract Query executor binding（Queryを実行する実装への結び付け）が、Applicationではなく「Environment・Database・Contract・Query」の組で識別されていたため、そのまま使えたからです。ただしこれはdevelopmentでの確認で、使ったExecutorはtest doubleです。実Databaseへの接続を示すものではありません。また、productionにはContract Query executor bindingが一件も無く、productionでは実行できません（`order_entry`でも同じで、Referenceの範囲として意図的かどうかは未判定です）。各Environmentへ足した1行ずつのbindingも、`repair_intake`のために新しく受理したものです。
- **個人 — 承認の対象を小さくする。** `repair_intake`の追加は、生成AIが作ったProposal（変更候補）を、file・CLI・Studio・AIのどの入口からの候補も同じ検査を通すShared Acceptance Boundary（共有の受入境界）で検査し、別の生成AIによる独立レビューを経てから、Repository ownerが明示的に受理しました。受理の対象は、生成コードの全量ではなく、3 source（741 bytes）の意味の差分でした。ただし、受理した人が意味差分を読んで判断できたかは検証していません。記録に残るのは、独立レビューの完了と残る停止条件を提示された上での明示的な回答までです。人向けの面は未実装で、RQ-028はPartial Evidenceです。また、Shared Acceptance Boundaryが実証したのは受け取る側で、Studio UIとAIによる候補生成の入口はまだ含みません。
- **社会 — 受理を権限と読み替えない。** 続けて受理した環境への結び付け（Environment binding）は、Permission grantやResource bindingを与えていません。「結び付けた」を「接続・実行してよい」と読み替えず、実行権限は未解決として残しています。
- **社会 — 受け付けたことと完了を分ける。** `order_entry`のReference Scenarioでは、受注確定のCommandが受け付けられたことと、外部の状態が実際に変わったことを、別の結果として保持します。「受け付けた」を「完了した」と読み替えません。

### 価値の確かめ方

TEIは、価値を測定値で確かめることを、今は主張しません。変更に伴う手直しの箇所数、削減率、作業時間、費用のような指標は、問題領域の知見が十分に蓄積されるまで、価値の判断に使わず、研究にとどめます（RQ-022）。

理由は、こうした数が要件ごとに意味を変えるためです。手直しの量は、業務要件の変更内容に左右されます。全体へ横串で同じ修正を入れるだけで済む変更と、ロジックの深い部分に及ぶ変更とでは、同じ「一か所」でも負担の意味がまるで違います。一つの数に畳むと、価値を示すどころか誤読の元になります。外部の研究や他製品の数値を、TEI自身で確かめないまま目標値にすることもしません。画面数やコード生成量も、価値の尺度にはしません。

代わりに、**積み上げた実務的な機能の量と、その有機的な関係性、実用性**で価値を確かめます。

- **量:** 実務の業務シナリオを通せる機能が、どの範囲まで揃っているか。
- **関係性:** それらの機能が、同じ意味・同じidentityでつながっているか。意味を一つ作れば、複数の機能・複数のApplicationから、写し直しなしに使われ、元へ辿れるか。
- **実用性:** 実務に近いシナリオを、実際に最初から最後まで通せるか。

この確かめ方は、数を出すためのものではなく、実際に動くものを作って見せることを先に置きます。MVP（最小限の実用的な製品）やプロトタイプで、実務シナリオを通し、通せた機能と、その間の関係を記録として積み上げます。測定は、その積み重ねから問題領域の知見が蓄積したあとの研究課題です。最初の実証の候補は[ISSUE-000075](../../plan/issue/000075-practical-scenario-mvp-demonstration.md)に整理しています（owner判断待ち）。

これと並ぶ強い確認方法として、成熟した既存の業務システムReference Modelを一式でTEIへ転写し、sourceにある意味を黙って落とさず、表現できるもの・nativeなまま残すもの・未解決のものを説明できるかを確かめます。小さい自作例では現れにくい規模、cross-reference、暗黙前提、実装依存を同時に圧迫できるためです。最初のbenchmarkは[ISSUE-000078](../../plan/issue/000078-reference-model-transfer-gate.md)で扱います。外部のmodel体系をTEIの仕様や正本へするのではなく、TEI自身のRequirementを反証可能な形で試す材料として使います。

実証で確かめる性質は、層ごとに次のとおりです。いずれも「できたか、できないか」「示されたか、示されないか」で確かめる性質で、数の大小ではありません。

- 個人
  - 新しい担当者や別のAIが、過去の会話履歴や特定の人への聞き取りなしに、変更に必要な意味・決定・影響・未解決点へ到達できること
  - 承認の対象が、生成コードの全量ではなく、意味差分・影響・例外・未解決点として示されていたこと
  - 一度答えた確認が、理由なく繰り返されないこと
- **組織**
  - 画面・API・AIエージェントの間で、同じ規則の食い違いが生じない構造であること
  - 別Applicationで再利用した意味とInfrastructure知識について、元のidentity・前提・差分を追跡できること
- 社会
  - 実行・承認・観測の根拠を、AIを介さず正本から第三者が再現できること
  - 分からない状態が、成功や安全として扱われていないこと
  - 業務知識を読めることが、実行権限へ変わっていないこと

研究にとどめている測定の課題は、[ISSUE-000072](../../plan/issue/000072-rule-change-hand-edit-count.md)に置いています。どこまで確かめられているかの現在地は[`docs/status.md`](../../docs/status.md)、Requirementごとの実証状況は[`plan/PRODUCT_REQUIREMENT_GAP_AUDIT.md`](../../plan/PRODUCT_REQUIREMENT_GAP_AUDIT.md)が正本です。各項目を担うIssueは[Issue一覧の「Product Valueの確かめ方と担当」](../../plan/issue/README.md)にまとめています。

### まだ主張しないこと

- 費用削減や生産性向上の数値的な効果は、測定しておらず、測定に基づく価値判断も留保しています（上記「価値の確かめ方」）。
- 積み上げた機能は小規模なReferenceの範囲にとどまり、実務で必要な機能の網羅は主張しません。実務シナリオを通すMVP的な実証は、これから積み上げる段階です。
- 個人にとっての価値の多くは、人が意味を読み、承認する面（Editor / Review Surface、RQ-010 / RQ-028）の出来に依存します。この面を実際の利用者で確かめた実証はまだなく、認知負荷がどれだけ減るかも測定していません。
- 社会価値は目指す方向であり、公共性の高い実システムで実証したものではありません。
- 現在の実証は小規模なReference Application（`order_entry`、`repair_intake`等）に限られます。
- 具体例にある独立レビューは別の生成AI（GPT-5.6 Sol）によるもので、人による独立レビューではありません。Proposalの作成者とレビュー者はどちらも生成AIです。
- Gate CのVisual Fidelityは単一のAI評価者による評価で、人の確認も別の評価者による再評価もありません（[`docs/status.md`](../../docs/status.md)、ISSUE-000058）。「社会」の層で述べる、第三者が根拠を再現できることの根拠には、この評価を数えません。
- 要求ごとの実証には偏りがあります。2026-09-21の再監査では、RQ-010、RQ-015、RQ-016、RQ-030がDesign Only、RQ-027、RQ-028、RQ-029がPartial Evidenceでした。2026-10-03に追加したRQ-031〜RQ-033は、追加時点ではDesign Onlyです。最新の状況は[`plan/PRODUCT_REQUIREMENT_GAP_AUDIT.md`](../../plan/PRODUCT_REQUIREMENT_GAP_AUDIT.md)を参照してください。特に、AIエージェントがTEI成果物を読んで業務を遂行する経路、答えた確認や退けた提案の記録、再利用時のVariationの表現は、製品側にまだありません。
- 決定記録（`.tei/decisions/`）は、Shared Acceptance Boundaryを通った変更に限られます。また、消去・偽造しても意味とrevisionが変わらないEvidenceであり、監査に耐える記録とは主張しません。
- 第一Web Target以外のTarget、`repair_intake`の顧客照会を、PostgreSQL以外の実Database Provider（第一Referenceの既存資産ではOracle）へ接続した実行、productionでの実行、別Repository・別組織への知識の移植は確かめていません。
- 「担い手が替わっても続く」ことは、実際の引継ぎ、刷新、委託先の交代では確かめていません。確認したのは、Reference内で会話履歴なしに機械側から意味・決定・影響へ到達できることの一部です。

## 1. 業務の意味を失わない

TEIが最も優先するのは、画面、DB、プログラム、クラウド構成より手前にある「何を意味しているのか」を保つことです。

受注、顧客、契約、請求、承認、履歴、状態遷移といった業務概念は、特定のテーブルや画面と同一ではありません。実装上の都合で意味を縮めたり、逆に実装詳細を業務概念そのものとして固定したりしないことを重視します。

そのため、Canonicalな意味、authoring source、実現方法、実行結果、観測結果を同一視せず、相互に追跡できる形で分けて扱います。

## 2. 実現方法を閉じない

業務上の意味が保たれているなら、その実現方法は必要に応じて選び直せるべきです。

TEIは、特定のDB、UI技術、プログラミング言語、クラウド、workflow engine、AI agent基盤だけで世界を閉じません。SQLやGoなど、その領域で既に成熟しているnativeな技術を無理に独自DSLへ移し替えることもしません。

Provider、Capability、Binding、Projection、Adapterといった境界を通じて、同じ意味を複数の技術へ結び付けられることを価値とします。

## 3. 現実の業務複雑性を削らない

既存の業務システムは、教科書どおりの単純なCRUDだけではありません。

一つのApplicationが複数Databaseを利用すること、Databaseごとに障害境界やtransaction境界が異なること、システム固有の認証・認可・有効期限・失敗回数制御があること、既存SQLや固有処理をそのまま移行しなければならないことがあります。

TEIは、こうした事情を「理想形に合わない例外」として排除するのではなく、業務システムの現実として受け入れます。

標準化できるところは標準化しつつ、標準に入らない部分をCapabilityやcustom implementationへ逃がし、全体の意味と追跡性を失わないことを重視します。

## 4. 厳格さを利用者の負担にしない

業務システムでは、曖昧さを残してはいけない境界があります。型、関係、依存、権限、transaction、release、実行対象などは、必要なところでは厳格でなければなりません。

一方、その厳格さを、人が大量の設定や二重管理を続ける負担へ転嫁してはいけません。

TEIは、内部規則を厳密に保ちながら、Editorと生成AIが不足や矛盾を見つけ、既存の知識や選択履歴を再利用し、必要なときだけ控えめに確認することで、実用上はできるだけ軽く扱える状態を目指します。

同じ質問を繰り返す、既に選んだ内容を再入力させる、機械が導出できる情報を人に二重管理させる、といった負担は避けます。

## 5. 「実行した」と「実際にそうなった」を分ける

外部システムへ命令を送ったことと、外部世界が期待どおり変化したことは同じではありません。

TEIは、実行要求、acknowledgement、Observation、Evidence、reconciliationを分離します。状態が分からない場合は、都合よく成功や失敗へ丸めず、「分からない」という状態を保持します。

この姿勢は、deployment、database migration、外部process、将来のAI支援実行にも共通します。

## 6. 設計知識を実行可能な資産へ変える

設計書は、コードを書いた後に説明のためだけに残る文書ではなく、実装・検証・生成・実行へつながる基準である方が望ましいと考えます。

TEIでは、設計内容を一つの画面形式やDSL形式へ固定せず、同じCanonicalな意味を、詳細設計書ビュー、表、グラフ、UI、自然言語、実行用IRなどへProjectionできることを目指します。

これにより、設計と実装が別々に陳腐化する状態を減らします。

## 6.1 構造化された設計知識から実装を導けること

TEIの価値は、ApplicationにUIや業務ロジックがある場合だけに生じるものではありません。

あるソフトウェアについて、

- どの情報を持つか
- 何と何が関係するか
- どの状態を取り得るか
- どの制約を守るか
- 何を入力し、何へ変換するか
- どのCapabilityへ接続するか

を、図・表・グラフ・モデル等で高密度に整理し、その同じ設計資産からValidation・生成・実行・文書を導きたい場合、TEIの適用価値は高くなります。

これは「図を正本にする」ことではありません。図表はCanonicalな意味を読み書きするProjectionまたはauthoring surfaceであり、同じ意味を別形式へ切り替えられることを重視します。

ここでいう構造化は、データモデルへ限定しません。Data、Function / Interaction、Business Procedure等は、それぞれ異なる観点から意味を構造化する表現です。将来別の観点が必要になった場合も、既存のどれかへ無理に押し込むのではなく、意味論的な拡張として追加し、他の表現と相互に検証できることを重視します（RQ-026、RQ-031、RQ-032）。

したがってTEI適用判断では、Application Planeの大きさと同時に、設計知識を構造化して外在化し、そこから実装を導きたい度合いを独立した軸として見るべきです。

## 6.2 生成AIが継続的にApplicationを構築・変更できること

TEIは、生成AIが一度だけコードを生成するための入力形式ではありません。

生成AIが実装作業の大部分を担う開発形態では、重要なのは「コードを書けること」よりも、

- 何を意味するApplicationか
- 何が既存知識として再利用できるか
- どこが今回の変更対象か
- 何を壊してはいけないか
- どの実装がderivedで再生成可能か
- どこがnative assetで慎重に扱うべきか
- 変更後に何を検証すればよいか

を機械可読な形で継続的に取り出せることです。

TEIでは、生成AIがRepository全体を毎回読み直して暗黙知を再構成するのではなく、Canonical meaning、Source、Pattern、Policy、Capability、Binding、Evidence、Decision history等から必要なcontextを取得し、変更を構成できる状態を目指します。

コードは重要な実行資産ですが、Application知識の唯一の容器にはしません。生成・再生成可能な実装はderived realizationとして扱い、native codeにしか存在しない重要な意味はSource Indexや明示的なContractへ接続します。

また、Applicationは完成して終わるものではありません。運用、制度、利用者要求、Provider、Targetの変化に応じて継続的に変更されます。TEIは、AIが過去の判断と現在の意味を読み直し、局所的な変更を安全に積み重ねられる基盤であることを重視します。

## 6.3 人間の認知効率を最大化すること

生成AIが実装を担うほど、人間にとって希少になるのはcoding throughputではなく、複雑なApplicationを理解し、重要な判断へ注意を配分する認知帯域です。

TEIは、人間へ大量のgenerated codeを読ませることを主要な確認方法にはしません。

同じCanonical meaningを、

- 高密度な表
- graph
- flow
- UI Projection
- dependency / impact view
- semantic diff
- diagnostic
- Evidence / provenance
- natural language

へ切り替え、目的に応じて必要な情報だけを圧縮して見られることを重視します。

人間が確認すべき対象も、全面的な実装詳細ではなく、

- 何が変わったか
- なぜ変わったか
- 何に影響するか
- どこが未確定か
- どの例外があるか
- 何をAIが判断し、何を人間が承認したか
- どのEvidenceから再確認できるか

へ寄せます。

TEIにおけるEditor / Projectionの価値は、単なるvisual authoringではなく、人間が少ない認知負荷で大きなソフトウェア構造を理解・判断できることにあります。

## 6.4 Domain・Infrastructure知識を移植可能な資産にすること

継続的なApplication開発では、一つのシステムで得た知識を次のシステムでも再利用できることが重要です。

TEIでは再利用対象をsource codeだけに限定しません。

- Domain type / relation / constraint
- Business Procedure / Pattern
- Policy / Variation
- Validation
- Capability contract
- Authorization rule
- Database contract / mapping
- deployment / runtime bindingの知識
- Provider固有の制約や適合条件
- 過去のDecision / Evidence

などを、実装技術と適切に分離したうえで再利用・移植できる状態を目指します。

再利用とは、別Applicationへ無条件にcopyすることではありません。元の意味、前提、依存、適用条件、Variation、Evidenceを追跡でき、移植先との差分を明示して再適用できることを重視します。

これによりTEIは、一つのApplicationを作る道具だけでなく、Application開発を重ねるほどDomain知識とInfrastructure知識が蓄積し、次のApplicationへ移植しやすくなる基盤になります。

## 6.5 AIエージェントが業務知識を読んで直接仕事を遂行できること

TEI成果物の利用者は、人間とApplication builderだけに限定しません。

場合によってはAIエージェントが、

- Business Procedure
- Business Action
- Data / Relation
- Policy / Constraint
- Semantic Capability
- Authorization
- Runtime Binding
- Evidence requirement

を読み、許可された範囲で業務を直接遂行できます。

この場合、従来のUIは業務遂行の唯一の入口ではありません。

```text
TEI business / system knowledge
        ↓
AI agent understanding / planning
        ↓
authorized Capability / Business Action
        ↓
Command
        ↓
Observation / Evidence
        ↓
business result / unresolved
```

ただし、TEIを読めること自体は実行権限を意味しません。AIエージェントのautonomy、Capability invocation authority、Resource access、side-effect authorityは独立して制御します。

また、AIが業務を行ったことと、業務上期待された結果が実世界で成立したことも分けます。Command、acknowledgement、Observation、Evidence、reconciliationの境界は、人間や通常Applicationが実行主体の場合と同様に維持します。

このためTEI成果物は、Applicationの設計資料であると同時に、人間・Application・AIエージェントが共有して利用できる運用可能な知識基盤であることを目指します。

## 7. 認知機能を、曖昧さの解消と設計支援へ使う

TEIが扱う業務上の意味は厳格である必要がありますが、そこへ至る入力は必ずしも厳格ではありません。既存のExcel設計書、自然言語、ソースコード、命名揺れ、古い仕様書、運用上の例外などには、人間なら文脈から判断できても、単純な規則だけでは確定しにくい部分があります。

TEIでは、こうした曖昧な境界へ、生成AIだけでなく、規則、embedding、分類器、ローカル軽量モデル、外部の認知基盤など、性質の異なる認知手段を利用できることを重視します。

ただし、認知結果とCanonicalな意味は同じではありません。

```text
cognitive observation / mapping candidate
  != canonical business meaning
  != accepted binding
```

たとえば「顧客番号」と「CUST_ID」が同じ業務概念らしいと認知系が判断しても、それだけでCanonical modelを書き換えません。既存の制約、Evidence、利用者の判断、検証可能な規則と照合し、採用された対応だけを明示的な意味へ昇格させます。

AIや認知系が担える範囲が将来広がっても、この境界は維持します。人間が逐次すべてを入力することを前提にはしませんが、どの認知から、どの根拠で、何が正式なモデルへ採用されたかを追えることを優先します。

## 8. SUI・SEI・EKIとの境界

TEIは、SUI Sensemaking、SEI Cognition、EKI Fabricと組み合わせて利用できますが、それらをTEI内部の必須moduleとはみなしません。

- SUI Sensemaking は、未整理な材料から関係・仮説・構造・統合を形成し、意味を成熟させるsensemaking lifecycleを主に扱います。SUIで安定してきた意味構造はTEIへのformalization candidateになり得ますが、自動的にTEIのCanonical meaningへ昇格しません。
- SEI Cognition は、認知・問い・不確実性・根拠・判断・Capability・Provenanceの継続性を主に扱います。TEIは曖昧なmapping、候補探索、例外検知などでSEIのCapabilityを利用できますが、SEIのDecisionやRecommendationをTEIのCanonical modelや実行権限と同一視しません。
- EKI Fabric は、異質で一時的な計算資源を安全に利用し、計算をどこで実行するかを主に扱います。TEIのValidation、Generation、Simulation、認知処理等をEKI上で実行できても、計算配置は業務上の意味の正本にはなりません。
- TEI は、十分に明確化された業務上の意味をCanonicalなformal modelとして保持し、検証・実装・実行可能な形へ接続する責務を持ちます。

この関係を固定pipelineにはしません。TEI単独でも成立し、必要なときだけ隣接Productや他のOSS・Providerを利用できることを重視します。

### SEIが提案する「統合の頂点」との関係（2026-09-27追記・評価待ち）

SEI側では、hat47xの製品群に対するSEIの役割を「統合の頂点」として定義し直す提案が出ています（`hat47x/sei-cognition:plan/adr/ADR-0035-family-integration-apex-and-control-meaning-boundary.md@041c3fa`、提案中）。この提案とそこから参照される文書は、SEIの`develop/v0.2.0`にあり、`main`には未統合です。提案の番号は、統合前はADR-0032でした。SEIの役割の定義はSEIが正本であり、SEI側で採否が決まるまで、TEIではこの小節を評価待ちとして扱います。

提案は「頂点」を三つの意味に限って採ります。観測・決定・権限のような最も一般的な概念を持ち、各製品に固有の意味をそこへ翻訳できるという抽象の頂点。製品やモデルや組織が入れ替わった後も読める、製品群の中で最も長く残る記録を持つという時間の頂点。製品をまたいだ判断の経緯を、時間をさかのぼって組み立て直せる唯一の場所という統合の頂点です。統合は任意の合流であり、製品はSEIへ記録を送ってもよいが、送らなくても成り立つ、とされています。逆に、他製品へ命令する指揮の頂点、他製品の意味やdataの正本を持つ所有の頂点、SEIが止まると製品群が止まる可用性の頂点は採りません。

TEIから見ると、この定義は本節の境界と矛盾しません。TEIが守る線は次のとおりで、いずれも本節、ADR-0022、ADR-0028から導かれるものです。SEIの提案の採否に関係なく維持します。

- 業務の意味の正本はTEIに残ります。 TEIに関してSEIが持つのは、TEIの記録（受理の記録、Authorization、Commandの結果、Observation等）への参照と、製品間の対応表だけです。対応表はTEIの記録を翻訳しますが、TEIの意味を書き換えません。
- SEIのRecommendationは、TEIのAuthorizationになりません。 SEIからTEIへの信号は依頼（SEIの語でAction Intent）であり、実行するかどうかはTEIが自らのAuthorization、Capability、Resourceの境界で判断します。SEIの記録が委任や判断の経緯を示していても、それは権限の証拠への参照であって、権限そのものではありません。
- 必須の依存はどちら向きにもありません。 TEIのDriverとShared Acceptance Boundaryは、SEIが止まっていても単独で完結します。受理の記録等をSEIへ写すことは任意です。SEI側の提案は、こうした局所で完結するループを神経系の比喩で「反射弓」と呼びますが、これは比喩であり、TEIの型や要求の根拠にはしません。

TEI側の具体的な受け止め方（SEI Change 2の再開、受理記録をSEIの判断の記憶へ写す候補、MCPの扱い）は[ISSUE-000070](../../plan/issue/000070-sei-reference-adoption-change2-resumption.md)、AI Business Actorへの委任をSEIから参照する候補は[Actor Context Projections §11.1](../../plan/ACTOR_CONTEXT_PROJECTIONS_2026-09.md)に置いています。どちらも評価待ちです。


## 技術調査を利用者の価値へつなぐ（2026-10-09、実証前）

技術調査で有望な方式が見つかっても、それだけでは利用者の価値は増えません。既存の価値を、利用者が経験する場面と検証できる結果に言い換えてから、実装の優先順位を判断します。具体的な調査根拠と実証案は[技術リサーチ統合方針](../../plan/TECH_RESEARCH_INTEGRATION_2026-10.md)にまとめます。

**第一の価値は、実装する前に問題のある仕様へ気づけることです。** 受注画面で顧客を編集したいという要求が出たとき、既存の顧客マスタが参照専用であるなら、その矛盾をプログラム生成後ではなく、業務規則・参照関係・権限・未解決点を確認する段階で示せる必要があります。見落としだけでなく、根拠のない警告で確認負担を増やすことも避けます。これは「業務の意味を失わない」「厳格さを利用者の負担にしない」という価値の具体例です。

**第二の価値は、画面が見えるだけでなく、業務として使えることです。** ある入力欄が表示されたという事実、意図した操作を実行できること、権限がない操作を拒否できること、外部の状態が期待どおり変わったことは、それぞれ確認が必要です。画面の外観や生成コードの量ではなく、業務上の結果に結び付く操作を実証します。これは「設計知識を実行可能な資産へ変える」「実行したことと実際にそうなったことを分ける」という価値の具体例です。

**第三の価値は、採用技術を替えても利用者の判断をやり直さずに済むことです。** Web、デスクトップ、携帯端末、異なる実行物の形式やHostへ展開するとき、元の業務意味・受理済みの判断・権限条件は保ち、技術固有の差を明らかにします。標準機能もプラグインを通じて交換できる設計を目指しますが、プラグインが存在するだけで可搬性や性能が証明されたとは扱いません。これは「実現方法を閉じない」価値の具体例です。

これらの価値を確かめる際は、単純な生成速度や正答率だけに頼りません。少なくとも、重要な仕様の見落とし、誤警告、人間の確認時間、Sourceへ戻る手間、業務操作の成立・拒否・未観測、Targetごとの差を分けて記録します。いずれも**測定方法の候補**であり、改善幅や製品としての成立を現時点で主張するものではありません。

初期の実証候補は、既存の受注業務Referenceを使った仕様レビュー、操作の実証、実行物の可搬性比較です。新しいモデル、コンパイラ、画面基盤の採用を先に約束せず、既存Issueと受入境界の中で、最小の実証ができるかを先に見極めます。候補の実施や次の段階への昇格は、既存計画の承認と実証結果に従います。

## 価値が衝突したときの優先順位

設計上の価値が衝突した場合は、原則として次の順に守ります。

1. 業務上の意味を失わないこと
2. 誤った確定や暗黙の権限拡大を避け、追跡・検証できること
3. 現実の業務要件や既存資産を無理に削らないこと
4. 実現方法を将来選び直せること
5. 利用者の二重管理や不要な操作を減らすこと
6. 自動化や開発速度を高めること
7. 個別実装を簡単にすること

下位の都合で上位の価値を損なう場合は、実装側を見直します。

## TEIが目指さないもの

TEIは、次の状態を目的にはしません。

- すべての業務資産を独自DSLへ移し替えること
- 特定のUI、DB、クラウド、workflow engineへ利用者を閉じ込めること
- 生成AIやAIエージェントへ、TEIを読めることや自律度の高さだけを理由に強い本番権限を与えること
- 「簡単に見えること」のために業務上の例外や不確実性を隠すこと
- 派生物を正本へ格上げし、どこがauthoritativeなのか分からなくすること
- 画面数やコード生成量そのものをプロダクト価値とすること
- generated codeや特定agentの会話履歴を、Application知識の唯一の正本にすること
- AIエージェント専用Knowledge Storeを、Canonical meaningの第二の正本として恒久化すること
- Decision・承認・Evidenceの記録を、個人の作業量を数えて評価・監視する道具にすること。記録は、意味と判断を説明し再現するためにあります

## 変更を評価するための問い

大きな設計変更では、少なくとも次を確認します。

- 業務上の意味は、変更前より明確になっているか
- 特定技術の都合がCanonicalな意味へ混入していないか
- nativeな資産をnativeなまま扱えるか
- 既存システムの複雑性を不当に切り捨てていないか
- source、meaning、realization、execution、observationを追跡できるか
- 分からない状態を、誤って一致・成功・安全とみなしていないか
- 厳格な規則のために、人へ不要な二重管理を要求していないか
- AIの提案と、採用済みの決定を区別できるか
- AIエージェントが業務Actorになる場合、理解・自律度・実行権限・Resource権限・観測Evidenceを分離できるか
- 人がgenerated codeを読まなくても、意味・差分・影響・例外・Evidenceを十分に理解できるProjectionがあるか
- Domain / Infrastructure知識を別Applicationへ移植するとき、前提・Variation・Evidenceまで追跡できるか
- 将来別のProviderやTargetへ移るとき、業務の意味を作り直さずに済むか
- 業務の意味のSSOTを一つに保ったまま実現しているか。派生物の側に、意味の第二の置き場を作っていないか
- 防ぎたい損失（仕様の再発見、二重管理、属人化、形だけの承認、刷新時の意味の喪失、技術への閉じ込め等）を減らす方向か
- 人に求める確認・承認は、人が判断できる大きさと形の意味上の判断に絞られているか。承認を形だけにしていないか
- AIや自動化が関わる場合、根拠・承認・実行・観測を後から第三者へ説明できるか
- 個人・組織・社会のどれか一つの価値を、別の層の損失で買っていないか

これらに答えられない変更は、機能として便利でもTEIの中心価値から外れている可能性があります。
