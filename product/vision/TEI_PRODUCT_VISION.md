# TEIの将来像

## 目指す姿

TEI（鼎／テイ）が十分に成熟したとき、ソフトウェア開発は「人が設計書を書く工程」「人がコードへ翻訳する工程」「実装後に人が設計書を追従させる工程」に分断されません。

ソフトウェアと領域固有の知識を表す構造化された定義を基準として保ち、人が図表から理解し、生成AIと協調して設計を進め、その定義から実装や検証を行える状態を目指します。対象は業務システムに限りません。知識と技術を分けて管理することが有効な分野で、同じ設計の足場を活用できることを目指します。必要に応じて、AIエージェントもその知識を業務や他の分野の活動に利用できます。

ドメイン知識は、案件固有のデータモデルを含む形で表します。データ、機能や操作、業務手順など、異なる観点から表した意味を関係付け、個別のモデルを共通の型へ押し込まずに扱います。将来必要になる概念は、拡張機能や定義言語を通じて既存の意味へつなげます。

TEIの中核は、意味を識別し、関係付け、検証する共通の仕組みを担います。プラグインは、分野固有の概念や、データベース、画面、実行環境などの技術別機能を、中核の決まりに沿って追加します。中核を小さく保ちながら機能を組み合わせられるため、技術の提供元による開発を待つだけでなく、案件に合わせた拡張を用意できます。仕様と実装を生成AIが読み取れる形に整え、人と生成AIが拡張を設計し、検証できることを目指します。

人が保つ定義は、機械的に安全に導き直せない意味に絞ります。画面や一覧、関係図、実行用の情報などは、その定義から組み立てます。人の確認、実行結果、外部の状態から得た事実は、意味を担う層へ戻し、変更候補として確かめてから受け入れます。生成AIや認知機能は調査、候補の提示、検証を支えますが、それだけで業務上の意味を確定しません。

検証シナリオも一つの定義から扱い、そこからコマンドラインを含む複数の実行・検査経路を導ける状態を目指します。これにより、人や生成AIが手軽な経路でシナリオの実行可能性を確かめ、同じシナリオを他の経路の検査にも役立てられます。

**ドメイン知識を一度構造化すれば、人の理解と判断、生成AIとの協調設計、実装と検証、別のシステムや分野への知識の再利用に役立てられること。**

これがTEIの長期的なプロダクト像です。

## 担い手が替わっても続く知識とソフトウェア — 個人・組織・社会から見たTEI

成熟したTEIの価値は、一つのアプリケーションを新しく作る場面だけでなく、長い年月の中で担い手・技術・利用形態が替わる場面にも現れます。

たとえば、10年使われている受注システムで、次のことが同時に起きたとします。

- 業務を最もよく知る担当者が異動する
- 画面の技術を刷新する
- 問い合わせ対応の一部をAIエージェントへ任せる

TEIが成熟していれば、それぞれの層で次のようになります。

- **個人** — これまでの判断と根拠が設計情報に残るため、後任者は全体、例外、未解決の点をたどって引き継げます。生成AIも同じ情報を使って作業を進めます。
- **組織** — 画面を刷新するときも、同じ業務上の意味から新しい実行先を組み立てます。業務規則や例外を引き継げたか、準拠性を確かめます。
- **社会** — AIエージェントは、明示された業務上の操作と実行機能を使い、許可された範囲で動きます。利用者や監査を担う人に、処理の根拠、承認、実行、観測の記録を示せます。

この例が示すのは、担い手や技術が替わっても、業務の意味と判断の根拠を引き継ぎ、システムを育てられる姿です。TEIが大切にする価値は[製品価値の文書](../value/TEI_PRODUCT_VALUE.md)にまとめています。

## 開発者から見たTEI

開発者は、業務システム全体を必要な情報量で見渡し、定義を編集できる画面を使います。

同じ正本となる意味を、用途に応じて次のように示せます。

- 詳細設計書に近い高密度な表形式
- データ間の関係を追うグラフ
- 状態や処理の流れ
- 実際の画面に近い表示
- データベースの設計・操作画面
- 自然言語による説明
- 入力元、診断結果、検証根拠をたどる画面

表示形式は正本ではなく、同じ意味を目的に合った形で読み書きするためのものです。用途に合わせて別の見方へ切り替えられます。

## 人間から見たTEI

人の主な仕事は、すべてのコードを書くことから、分野固有の知識、制約、例外、優先順位、変更の影響、検証根拠を理解し、必要な判断を行うことへ移っていきます。

TEIは、同じ意味を詳しい表、関係図、処理の流れ、画面、変更差分、影響範囲、診断結果、検証根拠など、目的に合う形で示します。

人間は用途に応じて、

- 全体構造を見る
- 一つの変更だけを見る
- 影響範囲だけを見る
- 未解決の点や例外だけを見る
- AIが変更した差分と理由を見る
- 元の検証根拠をたどる

ことができます。

そのためTEIの編集画面は、コードを書く道具にとどまらず、人がAIと大規模なソフトウェアを共同で理解し、管理するための場になります。

## 生成AIによる設計支援から見たTEI

生成AIは、TEIの知識を読み取り、設計の変更案を作り、検証を支える開発の担い手になります。

新規開発でも既存アプリケーションの変更でも、生成AIはリポジトリ全体のコードを書き換える前に、TEI内の知識や正本となる意味を調べます。

```text
既存の業務部品
  ↓
既存のプラグインや定義言語による意味の拡張
  ↓
既存の意味パターン
  ↓
既存の方針や選択肢
  ↓
組み合わせ
  ↓
実行機能
  ↓
不足部分だけ個別に実装
```

TEIへ入る情報が、最初から整理された形とは限りません。既存設計書の項目との対応、名前の揺れ、自然言語とモデルの対応、例外らしい箇所を読み解くために、規則、埋め込み表現、分類器、小型のローカルモデル、外部の認知基盤を使い分けられるようにします。

認知系は、データモデル上の不自然な1:N関係、関数従属性、履歴管理、認証・認可、監査、状態遷移など、業務システムで典型的に見落とされやすい論点を検査できます。能力が高まれば、候補提示だけでなく、一定範囲の探索・変換・検証をまとめて担うこともできます。

認知機能の結果は、正本となる意味と区別します。どの入力と根拠から何が提案され、どの検証を経て正式なモデルへ採用されたかをたどれるようにします。会話の状態や提供元固有の内部表現を、暗黙の正本として扱いません。

生成AIは、既に回答された問い、過去の選択、類似システムの知識、機械的に導ける情報を再利用し、必要な場面で人に確認します。

AIによる開発支援は、毎回ソースコードからリポジトリ全体の役割を推測する代わりに、変更要求から関係する知識、依存関係、設計判断、再利用できる型、実行機能、既存の技術資産、検証根拠をたどり、変更の影響を把握してから作業します。

AIモデルやエージェントが交代しても、アプリケーションの理解を引き継げます。長い文脈や会話の記憶も役立てながら、設計知識はリポジトリ内で管理します。

## AIエージェントから見たTEI

AIエージェントは、TEIの設計知識を読み取り、業務を進めるためにも利用できます。

業務手順、操作、データ、制約、方針、実行機能、認可、対応付け、検証根拠の要件を整理しておけば、AIエージェントはそれらを業務に必要な知識として読み取れます。

たとえば、

```text
業務手順
  ↓
現在の業務上の操作
  ↓
必要なデータ / 制約
  ↓
利用できる実行機能
  ↓
認可 / 資源の確認
  ↓
命令 / 外部への操作
  ↓
観測 / 検証根拠
  ↓
次の操作 / 完了 / 未解決の点
```

という経路です。

業務上の操作や実行機能が明示されていれば、AIエージェントは画面操作をまねるだけでなく、その境界を通じて必要な処理を進められます。

設計知識を読めることと、操作を実行する権限は別に管理します。書き込み、実行機能の呼び出し、秘密情報やネットワーク、ファイルへのアクセス、外部状態を変える操作には、それぞれ明示的な権限が必要です。

業務手順には、人の判断、物理的な作業、外部組織との調整も含まれます。AIエージェントが自分で進められる範囲と、人へ引き継ぐ箇所を判断できる状態を目指します。

## 周辺製品との連携

TEIは、意味探索を担うSUI Sensemaking、認知・判断の継続性を担うSEI Cognition、分散実行を担うEKI Fabricと連携できます。

連携する製品や機能は、用途に応じて選べます。SUIから形式化候補を受け取る場合も、SEIの認知機能を使う場合も、EKIへ計算を委ねる場合も、TEIは正本となる意味、対応付け、検証、検証根拠の境界を保ちます。

周辺製品の分野固有の知識は、それぞれの製品で管理します。必要な情報を明示的な契約と接続部でやり取りし、互いの内部モデルに依存せず連携できる状態を目指します。

## 自作OSS群から見たTEI

TEIは、業務システムに加え、画面、操作、分野固有の処理、検証、利用開始から終了までを持つ自作の公開ソフトウェアに、**アプリケーション実装層**として活用できることを目指します。

各製品の価値、分野固有の知識、検証根拠は、それぞれのリポジトリで管理します。TEIは、それらをアプリケーションの実装、表示形式、実行先、実行機能へつなぐ共通基盤を担います。

SUI Sensemakingを参照事例として使い、TEIを幅広いソフトウェアに適用できるか確かめます。SUIには空間的な作業面、複雑な操作、確認と承認、安全上の境界、AIや認知機能が関わります。単純なデータの登録・参照・更新・削除を超える開発で、TEIが役立つかを調べられます。

不足が見つかった場合は、次の順で対応します。

1. TEIの既存モデルや再利用できる型、表示形式、実行機能で表す。
2. 複数の利用先で使えるプラグインや接続部、実行機能としてまとめる。
3. 技術固有の資産や個別の実装として接続する。
4. 複数のアプリケーションに共通する意味上の不足が見つかった場合に、中核や製品要求への追加を検討する。

スケジュール管理、処理の実行、通信手順、隔離環境、モデルの実行環境、認知アルゴリズムなどの基盤は、それぞれの製品や技術を生かします。SEI CognitionやEKI Fabricの管理画面、設定、表示、業務機能にはTEIを使い、専門的な処理には各製品固有の実装を活用できます。

SUI Sensemakingでの確認では、TEIの利用範囲よりも、**同じ意味を変更する際に、個別の実装、検証、同期にかかる手間を減らせるか**を見ます。自作の公開ソフトウェアで使うことで、TEIが実際の開発基盤として役立つかを確かめます。

## TEIを適用する範囲を考える二つの観点

TEIを使う範囲は、画面や業務処理の有無だけで決まりません。

もう一つ重要なのは、

> **そのソフトウェアの意味、関係、制約、状態、変換を図、表、グラフ、モデルなどで整理し、同じ設計情報から実装を導きたいか**

という軸です。

ここでは、アプリケーション機能の広さと、設計情報を構造化する価値を別々に見ます。

### アプリケーション機能の広さ

高いほど、次の共通化価値が大きくなります。

- 画面や操作
- 分野固有の規則
- 検証
- 業務手順
- 表示形式
- 認可と受け入れ
- 実行先での実現

### 設計情報を構造化する価値

高いほど、実装より前に次を外在化して保持する価値が大きくなります。

- データと型
- 関係
- 状態と遷移
- 規則と制約
- 入力と出力
- 変換
- 実行機能
- 依存関係
- 権限
- 配備先と実行時の対応付け

この観点は、図を描くかどうかだけを問うものではありません。**実装の知識をコードだけに閉じず、複数の図表や自然な文章から同じ設計情報を読み書きできる状態が役立つか**を見ます。

画面をほとんど持たないコマンドラインの道具やサービスでも、定義、関係、変換、制約を設計情報として管理し、そこから検証や実装を導く場合は、TEIを活用できます。

一方、価値の中心が特殊な描画、数値計算、コンパイラ、認知アルゴリズムなどの専門処理にある場合、TEIは画面や設定など周辺の機能を担い、専門処理は既存の技術を生かす構成が考えられます。

### 二つの観点で見た適用例

| | 設計情報を構造化する価値が高い | 設計情報を構造化する価値が低い |
|---|---|---|
| **アプリケーション機能が広い** | 意味、検証、表示、実行先までTEIで組み立てる | 画面や設定など周辺機能にTEIを使い、専門処理には既存技術を生かす |
| **アプリケーション機能が限られる** | 画面のないサービスでも、設計や検証にTEIを使う | TEIを使う範囲を個別に見極める |

この整理だけで導入を決めるわけではありません。性能、安全性、機器の制約、既存資産、移行費用、製品価値を合わせて判断します。

### 図表と正本となる意味の関係

図、表、グラフは設計情報を作成し、理解するための手段です。見た目だけで意味を決めず、同じ意味を別の表示形式でも読み書きできるようにします。

```text
図 / 表 / グラフ / 自然な文章
        ↓ 作成・確認
正本となる意味
        ↓
検証 / 模擬実行 / 実現 / 生成
```

同じ意味を複数の表示形式で編集し、検証できることがTEIの価値です。

図表で整理した情報からアプリケーションを作りたいという要求は、TEIを活用できる場面の一つです。図表の形式を一つに定める必要はありません。

## 既存システムから見たTEI

TEIは、新規開発だけを前提にしません。

既存システムには、固有の認証テーブル、独特な状態管理、長年使われたSQL、複数のデータベース、外部処理、帳票、運用手順などがあります。

TEIでは、既存の仕様や資産を保ちながら、知識との関係を整理し、必要な箇所から実現方法を見直せるようにします。

移行範囲を段階的に広げ、既存の仕様を引き継ぎながら、共通部品や実行機能を取り入れられることを目指します。

## 実行先から見たTEI

TEIは、ウェブ画面に限らず、複数の実行先を同じ上位設計から扱える構造を目指します。

画面や操作の意味を実行先に依存させず、次の環境へ結び付けられるようにします。

- ウェブ
- デスクトップ
- モバイル
- API
- MCP
- 音声操作

新しい実行先は、中核を書き換えずに、独立した接続部やパッケージ、準拠性の確認を通じて追加できることを目指します。

データベースや外部の実行環境も、製品固有の知識を中核へ取り込まず、提供元との境界を通じて接続します。

## 実行・検証基盤の役割

実行・検証基盤は、完成したアプリケーションを動かすだけでなく、設計中の内容を確かめる場としても使います。

設計途中でも、データ、業務規則、画面、処理、権限、データベースとの契約などの整合性を、隔離した環境で動かして確かめられるようにします。

人が設計書を読んで確認するだけでなく、「この設計を動かすと何が起きるか」を早い段階で検証できる状態を目指します。

## 厳密さと使いやすさを両立する

TEIの内部では、意味、型、依存、権限、実行境界を厳格に扱います。

利用者が扱う画面には、必要な情報と確認事項を整理して示します。

- 自動で導出できるものは自動で導出する
- 一度確認した内容は履歴として再利用する
- 変更したいときは、後から選択経緯まで追って変更できる
- 問題の可能性が高い箇所を知らせる
- 必要な人が詳細を確かめられるようにする

内部の規則を厳密に保ちながら、日々の作業を進めやすい状態を目指します。

## 成熟したTEIで可能になること

最終的には、次のような開発の流れを一続きにしたいと考えます。

1. 業務上の要求や既存システムを読み解く
2. 既存の業務部品やパターンを再利用する
3. 編集画面で意味と関係を整理する
4. 生成AIが抜けや食い違いを調べる
5. 実行・検証基盤で設計を動かして確かめる
6. ウェブやデスクトップなどの実行先へ結び付ける
7. データベースや外部機能へ接続する
8. 実行・配備する
9. 実際の状態を観測し、検証根拠を残す
10. 実装方式を変更しても、業務上の意味と履歴を保つ

この流れを既存技術や公開ソフトウェアと組み合わせ、特定の製品や実装技術に閉じない形で実現することがTEIの将来像です。
