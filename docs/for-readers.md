# はじめてTEIを知る方へ

TEI（鼎／テイ）は、業務システムを「画面とデータベースを素早く作る道具」だけとして捉えず、**業務上の意味を長く保ちながら、実装技術を入れ替えやすくするための基盤**を目指している実験的なプロジェクトです。

まだ完成した製品ではありません。現在は、後から変更しにくい設計境界をGoのコードとテストで確かめています。

## 何が問題なのか

業務システムには、画面に見えている項目より多くの意味があります。

たとえば「受注」には、単に受注テーブルがあるだけでなく、次のような事情があります。

- どの番号を業務上の識別子とするか
- どの状態からどの状態へ変わってよいか
- いつの時点の情報を履歴として残すか
- 顧客マスタや在庫など、別のデータベースをどう参照するか
- 古いアプリケーションと新しいデータベース構造を一時的に共存させられるか
- 本番へ変更命令を出したあと、実際に変更されたことをどう確認するか

従来は、こうした意味が画面定義、SQL、Java / Go等のコード、DB制約、運用手順書、担当者の知識へ分散しがちでした。

TEIは、その分散を一つの巨大な独自言語へ押し込めるのではなく、**意味・実装・配備・観測を分離したまま相互に追跡できる状態**を目指します。

## 具体的にはどう違うのか

### アプリケーションとデータベースを別々に考える

一つのアプリケーションが複数のデータベースを使うことを普通に扱います。

```text
受注Application
├─ 販売DB       読み書き
└─ 顧客マスタDB 読み取り
```

TEIでは、アプリケーションが「どのようなデータベースの機能・構造を必要とするか」を **データベースの利用契約（Database Contract）** として要求します。

その要求を、開発・検証・本番など各環境に存在する具体的なデータベースへ結び付ける操作を **対応付け（Binding）** と呼びます。

このため、アプリケーション側の配布版（Release）と、データベース側の配布版を一対一に固定しません。

### SQLや既存コードを捨てない

TEIには独自の記述形式がありますが、SQLをすべて独自DSLへ変換したり、Goの実装を隠したりすることを目的にしていません。

SQLがもっとも自然ならSQLを正本として扱い、その意味を必要な範囲で解析します。既存技術を残したまま、上位の意味との接続を明示する方向です。

### 「命令した」と「起きた」を分ける

たとえばデータベースの構造変更を実行するコマンドが正常終了しても、それだけで「本番DBは期待した状態になった」とは限りません。

TEIの配備・実行モデルでは、おおむね次のように分けます。

```text
変更を要求する
    ↓
Executorが受理する
    ↓
外部状態をObservationする
    ↓
必要なEvidenceを確認する
    ↓
次のActionへ進む
```

ここで「観測（Observation）」は外部で実際に起きたことを確かめる行為、「検証根拠（Evidence）」は次へ進む判断を支える資料や事実です。

これにより、再試行や障害復旧で「同じ副作用を二重実行してよいか」を曖昧にしにくくします。

## 誰にとって、何がよくなるのか

受注入力の規則をいちばんよく知っている担当者が、来月異動することになったとします。規則は画面、SQL、DB制約、その人の頭の中に、少しずつ違う形で残っています。後任は変更のたびに、コードを読み、関係者に聞いて回って「本来の意味」を掘り起こし直します。担当者本人も、代わりに直せる人がいないため、休みにくく異動しにくくなります。

もう一つの場面は、生成AIが作った大きな変更の承認を頼まれた人です。生成物の全量を確かめる時間はなく、中身を理解しないまま責任だけを負って承認することになりがちです。生成AIとの関係は次の節で扱います。

TEIが防ごうとしているのは、この二つに共通する損失、つまり**業務の意味の正本が失われ、人が確かめきれない食い違いが増えていくこと**です。そこでTEIは、業務の意味の正本（single source of truth、以下SSOT）を一つに保ち、画面・コード・DB・AIの出力をそこから導かれるものとして扱うことを目指します。

期待する効果は、次の三つの層に分けて考えています。いずれも目指している方向で、実現済みの効果ではありません。

- 個人（業務を知る人、変更する人、承認する人、引き継ぐ人）: 変更の前に意味を調べ直す時間を減らし、判断に時間を使えるようにすることを目指します。知っていることが本人不在でも働くようにし、承認する人が生成コードの全量ではなく「意味の差分・影響・例外・未解決点」を見て判断できるようにします。分からないことは推測で埋めず、未確定として残します。
- 組織（業務システムを持つ組織）: 担当者・委託先・技術が替わっても、変更や刷新の土台が残ることを目指します。一つのアプリケーションで確立した意味を、別のアプリケーションでも同じ識別情報のまま再利用できるようにします。障害や監査の場面では、何を根拠に誰が承認したかを、担当者の記憶ではなく記録から示せる状態を目指します。
- 社会（そのシステムに支えられる利用者、取引先、監査する第三者）: 数十年使われる業務システムを、止めずに変え続けやすくすることを目指します。AIや自動処理についても、根拠・承認・実行・観測を辿れるようにして、説明責任を持たせやすくします。

三つの層は独立しておらず、一つの層の価値を別の層の損失で買わないことを基本にしています。層ごとの損失の一覧、具体例、価値の確かめ方は、ここへ複製せず[TEI Product Value](../product/value/TEI_PRODUCT_VALUE.md)に任せます。

### まだ主張していないこと

- 確かめているのは、小規模なReference Application（TEIの設計を試すために作った小さな業務アプリ。`order_entry`、`repair_intake`等）だけです。公共性の高い実システムや本番運用での効果は示していません。
- 費用削減や生産性向上は測定していません。
- 承認する人が意味を読む画面（Review Surface）は、実際の利用者で確かめていません。認知負荷がどれだけ減るかも測定していません。
- 実装済みの範囲は[現在の実装状況](status.md)が正本です。ここに書いた価値は、目指している方向を含みます。

## 生成AIとはどう関係するのか

生成AIがコードを書けるようになるほど、「毎回大量のコードを生成する」だけでは、長期保守で同じ意味が何度も別実装される可能性があります。

TEIでは、AIがまず次のような既存知識を探せる状態を目指します。

1. 既存の業務概念や再利用部品（Domain Component）
2. 繰り返し現れる意味のパターン（Semantic Pattern）
3. 既存の規則や選択肢（Policy / Variation）
4. 既存部品の組み合わせ
5. 宣言的なルール
6. 外部機能を呼び出すためのCapability
7. それでも足りない部分だけの個別実装

つまり、AIに渡す再利用単位をコード片だけでなく、**意味と契約の単位まで引き上げる**ことを狙っています。

AIが常に本番環境の操作を判断したり、自動的に強い権限を持ったりすることを前提にはしていません。実行時の規則・権限・採用した実現方法は、明示的で追跡可能な形へ固定することを重視します。

## TEIは何ではないのか

現時点のTEIは、次のものではありません。

- 今すぐ業務アプリをGUIだけで完成できる市販ローコード製品
- すべてのSQLや既存コードを独自形式へ置換するプラットフォーム
- すべての業務を一つのWorkflow Engineへ従属させる仕組み
- KubernetesやVault等を内製し直す基盤
- AIへ自動的に本番変更権限を与える仕組み

外部製品や既存実装は外部機能やその提供元（Capability / Provider）として利用でき、必要なら交換できることを重視しています。

## なぜ最初からEditorを作らないのか

見栄えのよい編集画面を先に作ると、その画面で表現しやすい概念が、そのまま中核の設計になりがちです。

TEIでは先に、アプリケーション、データベース、SQL等のQuery、Release、Deployment、Plugin、実行時のResource authorityといった境界を、実行可能なコードで検証しています。

編集画面はその上に載る「編集・表示の方法」の一つと考え、意味の唯一の所有者にはしません。

## 現在どこまで来ているか

現在は、業務上の意味を定義してから、アプリケーションやデータベースのReleaseへつなぎ、本番変更の実行・観測・障害復旧、さらにPluginの権限やHost交代時の安全性まで、途中で意味が切れないかを一つの縦方向のシナリオとして確かめています。

技術的には、おおむね次の流れです。

```text
Semantic definition
  ↓
Application / Database contract
  ↓
Query / Persistence / Migration
  ↓
Application / Database / Solution Release
  ↓
Deployment Run
  ↓
Executor / Observation / Evidence
  ↓
Plugin permission / Resource lease
  ↓
Host takeover / fencing / runtime reattach
```

これは「これらの機能が完成製品として揃った」という意味ではありません。完成したGUIやproduction adapterより前に、この縦方向の意味と安全境界が途中で崩れないことを確かめている段階です。
