# 既存認証仕様への接続アダプターの準拠確認

## 目的

この準拠確認では、既存システムの認証状態や規則を変えずに、意味上の機能である`security.authenticate`から利用できることを確かめます。

既存の認証用データ構造を、TEI標準の利用者定義へ作り替えることはしません。既存の記録と規則は接続部の内部で扱い、アプリケーションやドライバーからは共通の機能契約を通して利用します。

対象は課題#68とADR-0019です。業務上の結果と実行エラーは、課題#77とADR-0020で定めた`capabilityinvoke`の共通境界で区別します。

## 既存利用者記録の扱い

第1版の参照用接続部では、既存システムが保持している場合がある次の情報を扱えます。

- ログイン識別子
- 認証された主体に対応する識別情報
- 認証情報への参照
- 無効化状態
- 有効期間
- ログインの失敗回数
- ロックの期限
- 組織コード
- ロールコード

この型はTEI標準の利用者定義ではありません。既存のデータ構造やAPIから得た情報を、認証用の接続部へ渡すためのものです。

既存の利用者記録に、検証で使う認証情報の値そのものは保存しません。保持するのは参照先だけです。

## 認証情報の検証境界

認証情報の検証は`CredentialVerifier`に分けます。

```text
runtime input
  login ID
  presented credential
        │
        ▼
Legacy Authentication Adapter
        │
        ├─ UserStore ──> legacy user metadata
        │
        └─ CredentialVerifier
             credential reference
             + presented credential
```

提示された認証情報は実行時に検証器へ渡します。意味の正本となる全体モデル、入力元索引、業務結果には複製しません。

参照用テストにも、正しい秘密情報の値は記録しません。検証器の成功・失敗を外部から指定し、情報の受渡しと判定結果が区別されることを確かめます。

## 正常な業務結果

次の`denied`は、認証の判断を正常に終えたうえで、利用を拒否したことを示す業務結果です。

| 条件 | 業務結果 |
| --- | --- |
| 利用者が見つからない | `denied / credential_mismatch` |
| 認証情報が一致しない | `denied / credential_mismatch` |
| 無効化済み | `denied / account_disabled` |
| 有効期間前 | `denied / not_yet_valid` |
| 有効期間切れ | `denied / expired` |
| ロック中 | `denied / account_locked` |
| 既存システム固有の規則を満たさない | `denied / <legacy reason>` |

参照実装では、利用者が見つからない場合も、認証情報が一致しない場合も、同じ拒否理由を返します。認証結果から利用者の存在を推測されにくくするためです。

認証に成功した場合は`authenticated`を返します。結果のデータに含めるのは、認証された主体の識別情報だけです。

## 実行エラー

次の状態は、業務上の認証拒否としては扱いません。

- 既存の利用者情報の保存先へ接続できない
- 認証情報の検証器を実行できない
- 既存の規則の評価を完了できない
- 既存の利用者記録に主体の識別情報がない
- 既存の利用者記録に認証情報への参照がない
- `security.authenticate`以外の機能を誤ってこの接続部へ渡す
- 接続部の入力型が契約と一致しない

これらの障害を`denied`に変換すると、認証の判断を終えて拒否した場合と、判断自体を完了できなかった場合を区別できません。

そのため、これらの障害は`capabilityinvoke.Invoke`からGoの`error`として返し、正常に完了した認証拒否と区別します。

## 既存システム固有の規則

項目どうしの対応付けだけでは表せない既存の条件を、TEI共通の規則へ無理に置き換えることはしません。

`LegacyRule`は、既存の利用者情報と評価時刻を受け取り、次のいずれかの結果を返します。

- 正常に評価でき、許可または拒否を判断できた
- 評価処理そのものを完了できなかった

規則の評価を正常に完了して拒否した場合は`denied`を返します。規則の評価そのものを完了できなかった場合は、実行エラーを返します。

参照実装の準拠確認では、組織コード、ロールコード、ログイン失敗回数が、既存の情報として規則の評価に渡されることも確かめます。

## この段階で固定しないこと

この準拠確認だけで、次の事項を確定することはしません。

- TEI標準の利用者データ構造
- `std.auth.*`の標準Capability
- 本番用のパスワードのハッシュ化方式
- LDAP、IdP、OIDCなどの製品選択
- 認証情報の更新方式
- 認可の規則
- ログイン画面
- 汎用的な認証エラーの分類体系

一つの認証用接続部で得た結果だけを根拠に、これらを共通仕様へ一般化することはしません。

## 次の接続段階

次の検証では、この接続部を参照用作業領域に定義した機能の対応付けへ接続します。既存の項目との対応を追跡できることと、秘密情報が結果に混入しないことを、リポジトリ内の検証根拠で確かめます。

その後、`security.authorize`を`order_entry`の参照、編集、確定の各操作へ接続し、判定段階Aを再評価します。
