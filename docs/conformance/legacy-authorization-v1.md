# 既存認可仕様への接続の準拠確認

## 目的

この準拠確認では、既存システムの組織やロール、個別の規則をTEI共通のアクセス制御モデルへ作り替えず、第1版の参照用アプリケーション`order_entry`の認可判断に利用できることを確かめます。

認証は利用者などの主体を確認する処理であり、認可はその主体に操作を許すか判断する処理です。認証で得た主体の識別子は認可へ渡しますが、アプリケーションやドライバーが組織コードやロールコードを直接読み取り、独自に判断することはしません。

## 意味上の実行機能

第1版の参照実装では、`security.authorize`に必要最小限の次の契約を使います。

```text
subject
+ action
+ resource
    ↓
security.authorize
    ├─ allowed
    └─ denied
```

`allowed`と`denied`はいずれも、認可の判断を正常に完了した場合の業務結果です。

既存の利用者情報へ接続できない場合や規則を評価できない場合は、業務上の拒否を示す`denied`ではなく実行エラーとして扱います。

## 操作と対象

最初の参照例では、`order_entry`に必要な三つの操作に対象を絞ります。

| 操作 | 対象 | アプリケーション上の意味 |
| --- | --- | --- |
| `browse` | `order_entry.recent_orders` | 受注一覧を参照する |
| `edit` | `order_entry.order_record` | 受注recordを編集する |
| `execute` | `order_entry.submit_order` | 受注確定Commandを実行する |

操作対象はウェブ画面の名前やURLではなく、既存のアプリケーションの型に付けた識別子で特定します。

`order_entry.submit_order`は既存の命令型の機能で、`sales.order.submit`へ接続されています。認可規則に同じ機能名を重複して記述する必要はありません。

## 既存規則の試験用データ

`reference/legacy-auth/authorization.json`は、既存システム固有の認可表を模した参照用データです。

現在の例では、次の既存の情報をそのまま使います。

- 組織コード
- ロールコード
- 操作
- 対象の資源
- 許可または拒否の効果

このデータはTEI標準のロールモデルではありません。既存の仕様を変更せずに、意味上の機能へ接続できることを確かめるための試験用データです。

`ORDER_EDITOR`と`ORDER_VIEWER`も標準のロール名ではなく、この参照例に含まれる既存システム固有の値です。

## 対象者と既存利用者の対応

認証が返した主体の識別情報を使い、`FixtureStore.FindBySubject`で既存の利用者記録を再取得します。

```text
Authenticated Subject
        ↓
security.authorize
        ↓
SubjectStore
        ↓
legacy user metadata
        ↓
legacy authorization rule
```

アプリケーションやドライバーには組織・ロールの情報を直接公開せず、認可規則を重複して実装させません。

## 明示的な接続

`order_entry`では、認証と同じ既存のGoによる接続定義の形式を使います。

```tei
realize security.authorize with custom go
```

対応付けを識別する値は次のとおりです。

```text
order_entry/security.authorize
```

入力元索引から、記述元のファイルである

```text
applications/order-entry/realizations/authorize.tei
```

へ戻れることを準拠確認で確かめます。

認可を実現するためだけに、新しい接続定義の形式を追加することはしません。

## 参照実装で確かめる判断

編集者については、次の操作が`allowed`となることを確認します。

- 受注一覧の参照
- 受注recordの編集
- 受注確定Commandの実行

閲覧者については、次の結果を確認します。

- 受注一覧の参照 → `allowed`
- 受注recordの編集 → `denied`
- 受注確定Commandの実行 → `denied`

未知の主体や、既存の認可規則に一致しない操作は`denied / not_authorized`とします。

これは参照実装に必要な最小限の結果の表現です。認証と認可の一例だけで、拒否理由の分類を標準仕様として固定しません。

## 実行エラーとの境界

次の場合は、`denied`として扱いません。

- 主体の情報を取得する保存先を利用できない
- 既存の認可規則を評価できない
- `security.authorize`以外の機能を誤って接続部へ渡す
- 主体・操作・対象の情報が不足している
- 接続部の入力が契約に違反している

これらは操作を拒否した結果ではなく、認可の判断自体を完了できなかった状態です。プルリクエスト #141 で導入した、機能に共通する実行エラーの扱いを適用します。

## プラグイン・実行環境の権限との分離

ここでいう認可とは、アプリケーションの利用者が業務上の操作を実行してよいかを判断することです。

別プロセスのプラグインがデータベースや外部資源へアクセスしてよいかを制御する、実行時の利用許可とは異なります。この参照例でも、両者を同じ規則や機能へまとめません。

## この段階で固定しないこと

- TEI標準の利用者・ロール・許可のデータ構造
- `std.auth.*`への標準化
- 汎用的な役割・属性に基づく認可規則の言語
- Webの画面遷移を守る仕組みやボタン表示
- HTTPの状態コードへの変換
- 本番用の認可方針を評価する仕組み
- プラグインの実行時の利用許可との統合

これらは複数のアプリケーションや実行先で必要性を確認した後に検討します。

## 判定段階Aとの関係

この参照例では、少なくとも次の情報をドライバーへ渡せる状態を目指します。

- 認証された主体の識別情報
- 認可機能の識別子
- アプリケーションで扱う操作と対象
- 既存の組織・ロール・規則との接続境界
- `allowed / denied`という業務結果
- 実行エラーとの区別
- 対応付けと既存の試験用データの出所

この段階の変更後は、`security.authenticate`の識別子を変えずに、既存の認証方式への接続部を交換できるか確認します。その結果を示す検証根拠がそろってから、課題 #68 と判定段階Aを再確認します。
