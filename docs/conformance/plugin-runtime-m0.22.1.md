# M0.22.1 プラグインと実行環境の境界の準拠確認

この文書は、M0.22.1で実装したプラグインと実行環境の境界について、試験で直接確かめた範囲を整理したものです。

ここでいう準拠確認は、本番環境での安全性や可用性を広く保証するものではありません。参照実装がTEIの設計上の境界条件に従っているか、コードと試験から追跡できる状態を指します。

## 読み方

プラグインと実行環境に関する似た用語でも、役割はそれぞれ異なります。M0.22.1では、少なくとも次の区別を保ちます。

- **プラグインと配布一式（Plugin / Bundle）**：機能（Capability）を配布し、利用する実装を選ぶための単位
- **権限の付与（Permission Grant）**：環境（Environment）が機能に与える論理的な権限
- **資源の対応付けと利用権（Resource Binding / Lease）**：論理的な権限を実行時の具体的な資源に結び付けるホスト側の仕組み
- **監督役の所有権（Supervisor Ownership）**：どのホストが現在その呼び出し（Invocation）を監督できるかを表す所有権
- **排他制御トークン（Fencing Token）**：古いホストからの操作を拒否するための世代番号
- **永続的な呼び出し識別情報（Durable Invocation Handle）**：外部の実行環境へ再接続するために保存する最小限の識別情報

これらを一つの大きな実行状態にまとめません。たとえば、資源の利用権（Resource Lease）を取得したことと、外部の実行環境へ再接続できたことは別の事実です。

## プラグインの解決先を固定する

環境で使うプラグインは、実行するたびに最新版を選び直しません。プラグインの実装固定情報（Plugin Lock）で版と選択結果を固定します。

選択結果の解決は主に`internal/plugin/lock.go`と`internal/plugin/resolve.go`が担います。主な準拠確認の試験は`internal/plugin/lock_test.go`と`internal/plugin/resolve_test.go`です。

現在の試験では、少なくとも次の点を確認しています。

- 実装固定情報を作成した後に互換性のある新版が追加されても、既存の固定情報が自動的に新版へ切り替わらないこと
- 定義情報が実装固定情報の作成時から変わっていれば、その不一致を検出すること
- 環境が要求する機能と、プラグイン一覧にある提供実装の対応が曖昧なまま実行へ進まないこと

プラグインの実装固定情報は、提供元の信頼性を完全に保証する仕組みではありません。実行する予定だったプラグインと、選択時の定義情報・方針の組合せを固定し、後から追跡できるようにする仕組みです。

## 別プロセスのプラグインは独立した信頼境界として扱う

`internal/plugin/runtime/model.go`では、同一プロセス内での実行と、別プロセスでの実行を区別します。

別プロセスで動くプラグインは、ホスト側で隔離環境、成果物の検証、実行許可、資源との対応付けが整うまで実行を開始しないことを重視しています。主な試験は`internal/plugin/runtime/model_test.go`と`host_sandbox_test.go`にあります。

特に、次の順序を保つことが重要です。

1. プラグインと機能の提供実装を決定する
2. 成果物と実行環境の前提条件を確認する
3. 隔離環境を準備できることを確認する
4. 権限と資源の対応付けを検証する
5. 必要な資源の利用権を取得する
6. ホスト側の実行環境との境界を構成して呼び出す

成果物の検証や隔離環境の事前確認が失敗した場合、秘密情報やネットワークの接続先を先に渡してはいけません。

## 権限と資源の貸出しを必要最小限にする

権限（Permission）は、「この機能は秘密情報を読む」「この接続先へ通信する」といった論理的な許可です。秘密情報を参照するハンドルや具体的な接続先は、ホストの資源仲介機構（Resource Broker）が資源の対応付け（Resource Binding）から解決します。

この仕組みの主な実装は`internal/resource/`と`internal/plugin/runtime/host_sandbox.go`にあります。

試験では次を確認しています。

- 機能に必要な権限を環境が明示的に付与していなければ拒否すること
- 資源の利用権に、要求していない資源や、種類の異なる具体的な資源情報を混ぜられないこと
- 秘密情報、ネットワーク、ファイルシステムの具体的な値を、論理的な権限と資源IDから分離すること
- 呼び出しが失敗した場合も資源の利用権を解放すること
- 利用権の取消しが時間切れになった場合、その失敗を無視して成功と扱わないこと

また、`resource.Record`は永続化する記録用の型であり、ホストで解決した秘密情報のハンドル、ネットワーク接続先、マウント元やマウント先のパスは保持しません。M0.22.1では、この境界を直列化の試験でも直接確かめます。

ここで守るのは、TEIが秘密情報の値を解析しないということだけではありません。ホスト固有の具体的な資源情報を、意味の正本となる定義や永続化した実行記録へ持ち込まないことも含みます。

## 更新と再読込みを別の操作にする

資源の利用権（Resource Lease）には有効期限があります。ただし、期限を延長することと、参照する具体的な資源情報を取得し直すことは別の操作です。

- **更新（Renew）**：利用権の有効期間を延長する
- **再読込み（Refresh）**：明示的に`refresh=live`と指定された対応付けについて、具体的な資源情報を取得し直す

この区別は `internal/resource/` と `internal/plugin/runtime/lease.go`、`host_sandbox.go` 周辺で実装しています。

試験では、更新だけでは資源の意味や具体的な参照内容が変わらないこと、再読込みは許可された対応付けだけに作用すること、どちらかに失敗した場合は安全側に倒して拒否することを確認しています。

ホスト側で利用権を監督する仕組みは、有効期限の延長や資源情報の再取得をプラグイン自身の責任にはしません。プラグインが長時間動作する間も、利用権の管理はホスト側で行います。

## 監督役の所有権と世代管理

ホストが停止・再起動した場合、以前のホストと新しいホストが同じ呼び出しを同時に監督してはいけません。

`internal/resource/ownership.go`と`internal/plugin/runtime/supervisor.go`の周辺では、監督役の所有権、定期的な生存通知、単調に増加する排他制御トークンを使って、この境界を表しています。

テストでは、次を直接確認しています。

- 所有権が有効な間は、別のホストが無断で監督を引き継げないこと
- 所有権の期限が切れた後の引継ぎでは、排他制御トークンの世代番号が単調に増えること
- 以前の所有者による権限確認・生存通知・解放の操作を拒否すること
- 資源仲介機構も、古い排他制御トークンによる更新・再読込み・解放を拒否すること
- 所有権の生存通知を維持できなければ、ホスト側の実行を安全側に倒して停止すること

資源の利用権の改訂版と、監督役の世代を示す排他制御トークンは、別々の履歴を表します。資源の更新回数と監督役の世代交代の回数を混同してはいけません。

## 永続化する実行識別子と実行環境への再接続

M0.22.1では、監督役のホストが交代した後も外部の実行環境へ再接続できるよう、永続化する呼び出し識別情報（Durable Invocation Handle）を導入しています。主な実装は`internal/plugin/runtime/invocation_recovery.go`です。

永続的な呼び出し識別情報には、少なくとも次の内容を保持します。

- 呼び出し・実行・操作・要求の識別子
- 環境
- プラグインの識別情報と機能
- 定義情報の照合値
- プラグインの実装固定情報の照合値
- 実行方針の照合値
- 成果物の照合値
- 実行環境の種類と実行ハンドル
- 資源の利用権のID
- 監督役の所有者と排他制御トークン
- 最後に観測した実行環境の状態

再接続する前に、保存済みの識別情報と現在の環境計画が同じ実行を指しているかを確認します。外部の実行環境にはまだアクセスしません。M0.22.1の準拠確認のテストでは、環境、Plugin Lock、プラグインの識別情報、定義情報、成果物の照合値、実行方針の違いを拒否し、その段階では実行状態の観測も行わないことを直接確認します。

保存済みの識別情報に古い排他制御トークンが使われた場合や、同じトークンを別の管理主体が持ち込んだ場合も、実行環境へアクセスする前に拒否します。

## 実行環境の状態を推測しない

再接続時に避けるべきなのは、「処理が見つからないので再実行する」という自動的なやり直しです。外部システムへの変更が、既に行われている可能性があるためです。

現在の復旧結果は、実行環境で観測した状態に応じて次のように扱います。

- `running` / `starting`：再接続を試みる
- `succeeded`：既に成功して終了した状態として扱う
- `failed`：既に失敗して終了した状態として扱う
- `missing`：実行環境が失われた状態として扱い、自動的には再実行しない
- `unknown`：未解決として、引き続き観測を待つ

さらに、最初の観測で`running`だった実行環境が、再接続時に`missing`へ変わっていても、自動的に再実行してはいけません。

これらの分岐は `internal/plugin/runtime/invocation_recovery_test.go` で直接固定します。

## 実行状態不明時の世代管理権限

M0.22.1の監査で見つかった`RuntimeUnknown`時の扱いについては、Issue #9とADR-0005で判断を記録しました。

永続的な呼び出し識別情報では、監督役の所有権を管理する保存先で現在の調停権を持つ世代と、外部の実行環境が権限を伴う操作を通じて実際に受理した世代を区別します。

- `SupervisorOwnerID` / `FencingToken`：永続的な管理機構で保持する監督役の権限
- `RuntimeFencingToken`：実行環境側で受理済みと確認できた最後の世代

基本的に守る条件は`RuntimeFencingToken <= FencingToken`です。該当する項目がない既存の識別情報では、実行環境側の世代を`FencingToken`から推測せず、0を不明な状態として扱います。

`RuntimeUnknown`を観測した場合、新しい監督役の所有者と排他制御トークンは保存しますが、`RuntimeFencingToken`は進めません。再接続も行わず、配備の操作は未解決のまま残します。その後の観測で同じ実行環境が`running`または`starting`に戻り、権限を伴う再接続が成功した場合に限り、`RuntimeFencingToken`を現在の監督役の世代へ進めます。

この区別により、資源仲介機構の側では新しい世代への引継ぎが済んでいても、実行環境側の排他制御は未確立という状態を永続的に記録できます。その間に実行環境の完全な操作権限があるとは判断せず、実行環境の状態を変更する操作や自動再実行には進みません。

準拠確認の試験では、状態が不明な場合は監督役の世代だけが進むこと、後の再接続で実行環境側の世代が追いつくこと、実行環境側の世代が監督役の世代を超える識別情報を拒否することを確かめます。また、終了または消失の状態を権限なしで観測しただけでは、実行環境側の世代を進めないことも直接確認します。設計理由は [ADR-0005](../../plan/adr/0005-supervisor-and-runtime-fencing-authority.md) に記録しています。

## この文書が保証しないもの

M0.22.1のテストが成功していても、次の項目を本番運用できる品質で実現したと主張するものではありません。

- 分散環境向けの監督役の所有権を管理する保存先について、実運用に必要な品質
- Kubernetes、Vault、Cloud IAMなどの本番環境向け接続部品
- OSレベルで完全に隔離された実行環境
- ネットワークやファイルシステムの隔離を、すべての実行先で実現すること
- 秘密情報を管理する仕組み自体の安全性
- 外部の実行環境の耐障害性
- 高可用性、災害対策、性能、長期運用性
- ソフトウェアの供給経路全体の署名・証明

参照実装の目的は、これらの製品をすべて内製することではありません。外部の実装と接続する際にも守るべき意味上の境界を、あらかじめ明らかにすることです。

## 変更時に確認する点

プラグインや実行環境を変更するときは、テストの合否だけでなく、次の順序で確認します。

1. どの権限や識別情報を変更するのか
2. 永続化する情報とホスト内にだけ置く情報の境界は変わるか
3. 古いホストからの操作や二重実行を拒否するための排他制御は弱くならないか
4. 実行環境の消失・状態不明を、成功や再実行へ短絡していないか
5. 現行の準拠確認試験のどの前提が変わるか

意味上の判断を変える場合は、テストを先に作って既成事実にするのではなく、IssueとADRに判断を記録してから実装します。
