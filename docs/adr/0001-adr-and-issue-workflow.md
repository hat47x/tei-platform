# ADR-0001: 設計判断と実行作業をADRとIssueに分ける

- 状態: 採用
- 日付: 2026-08-30
- 関連Issue: #1, #2

## 背景

TEIの開発では、意味モデル、Database lifecycle、Deployment、Plugin / Runtime境界など、後から広い範囲へ影響する判断が増えています。一方で、実装、検証、文書改善、調査といった日々の作業も並行して進みます。

これらを会話履歴だけで管理すると、「いま何を作業しているのか」と「なぜこの設計になっているのか」が混ざりやすくなります。さらに、複数の生成AIへ作業を分ける場合、各作業者が過去の会話をすべて読まなければ安全に着手できない状態は避ける必要があります。

## 判断

TEIでは、長く残す設計判断をADR、実行する作業をGitHub Issueとして分けて管理します。

ADRには、少なくとも次を残します。

- どのような背景や問題があったか
- 何を判断したか
- 他の案と比べて、なぜその判断を採ったか
- その判断によって何が良くなり、何を引き受けることになるか

Issueには、少なくとも次を残します。

- 作業の目的
- 対象範囲
- 今回は行わないこと
- 完了条件

生成AIがIssueを担当する場合も、既存ADRと矛盾する設計変更を暗黙に混ぜません。作業中に設計判断の変更が必要だと分かった場合は、その変更を実装へ紛れ込ませず、Issueへ論点を戻し、必要なら新しいADRとして扱います。

## この方式を採る理由

Issueだけでも作業履歴は残せますが、Issueは完了後に閉じられ、将来の設計判断を調べる入口としては不安定です。逆にADRだけでは、細かな実装や調査の進行管理には重すぎます。

両者を分けることで、作業の流れと設計の理由を、それぞれに適した寿命で残せます。

## 影響

良い影響として、別の生成AIや人間の開発者が、会話履歴をすべて知らなくても作業の背景へ到達しやすくなります。また、設計変更が通常の修正へ紛れ込むことを減らせます。

一方で、すべての判断をADRにすると文書が増えすぎます。そのため、局所的で容易に戻せる判断や、単なる実装手順はADRにしません。将来の作業者が「なぜこうなっているのか」を知る必要がある判断に絞ります。

## 補足

文章は定型を埋めることより、後から読んで判断の流れが自然に分かることを優先します。特に生成AIが作成するADRでは、不自然な直訳調や抽象語の羅列を避けます。
