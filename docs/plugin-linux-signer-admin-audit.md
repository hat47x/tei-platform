# Linux署名鍵管理：認可・監査のHost契約（設計案）

対象はIssue #1370 / #1251です。既存の `LinuxHostSignerTrust.Allow/Revoke` はHostが信頼する鍵を変更する低水準機構であり、呼び出し元の認可や永続監査は行いません。この文書では管理経路の要求を明確にしますが、認可・監査が実装済みであることを示すものではありません。

## 境界と基本原則

- **プラグインの実行経路から鍵の変更操作を公開しない。** Hostの管理経路で、操作要求の発信元、認証された主体、管理対象のHost/テナント、対象署名参照、操作種別（登録・交換・失効）を確定する。
- **要求に記載されたactorやtenantを信頼しない。** Hostが検証済みの認証コンテキストから値を取り出し、権限判定と監査の両方に渡す。
- **デフォルト拒否。** 権限判定が失敗した場合は、鍵集合を変更しない。監査記録の保存に失敗した場合も、原則として変更を開始しない。
- **鍵の素材と証拠を分離。** 公開鍵はHostの信頼ストアに保持する。署名証拠やプラグインのマニフェストに記載された自己申告は信頼しない。監査イベントには公開鍵の生データを載せず、SHA-256指紋を記録する。
- **複数Hostは別要件。** 現行のメモリ内`LinuxHostSignerTrust`には、Host間同期・永続化・再起動時の復元機能がない。

## 管理操作の受入契約

1. 認証済み主体・操作権限・Host/テナントの範囲・対象署名参照を検証し、操作前に権限判定を完了する。認証主体が不明な場合、署名参照が対象外の場合、権限が不足する場合は拒否する。
2. `Allow`の登録と交換を区別し、`Revoke`では存在しない参照を変更成功として報告しない。同じ鍵を再登録した場合も世代を更新する。
3. 成功イベントは、操作ID、Host ID、認証済み主体ID、対象参照、操作種別、旧世代、新世代、旧/新公開鍵指紋、時刻、結果、理由コードを含む。失敗イベントは秘密情報を含まない理由コードを記録する。
4. 権限判定と監査の失敗を検出可能にし、少なくとも管理者へエラーを返す。監査記録が欠落している状態で、成功したと応答しない。
5. 更新後に既存の署名済み固定実行内容が旧世代を使って新たに起動しないことを確認する。起動済みプロセスを停止するかどうかは、別の運用ポリシーで扱う。
6. 管理操作と監査の整合性は単一Host内でも明確化する。イベントの書込み後に更新が失敗しても、成功したと誤記録しない。監査と鍵更新のトランザクション、または保留/確定イベントの二段階記録を選択し、クラッシュ復旧時の不整合を検出する。

## 推奨インターフェース（未実装）

```go
type SignerAdminRequest struct {
    OperationID string
    HostID      string
    SignerRef   string
    Operation   string // register | rotate | revoke
    PublicKey   []byte // revokeでは空
}

type SignerAdminAuthorizer interface {
    AuthorizeSignerChange(ctx context.Context, principal VerifiedPrincipal, req SignerAdminRequest) error
}

type SignerAdminAuditSink interface {
    RecordSignerChange(ctx context.Context, event SignerAdminAuditEvent) error
}
```

`VerifiedPrincipal`は外部要求に含めず、Hostの認証層が生成する。監査Sinkのイベント順序、耐障害性、改ざん検知、保持期間は、実運用に応じて選択できるものとする。失効後の新規起動の禁止は、既存のHost内信頼集合に委ねる。管理APIから子プロセスを直接起動しない。

## 最小実装の切り分け

- **A. Host管理アダプタ**：認証済み主体と対象範囲の検証、拒否時の非変更試験、権限テーブルの外部注入。
- **B. 監査イベント**：成功・拒否・監査障害・重複操作IDを記録する型とSink。公開鍵指紋のみ保持。
- **C. 永続化・復旧**：Hostの鍵世代と失効状態を保存する。クラッシュ後に古い承認が復活しないようにする。複数Host間の伝播は、後続の別Issueで扱う。
- **D. 故障注入試験**：認可失敗、監査失敗、更新失敗、再起動、同時失効・起動、同一操作の再送を検証する。

## 並行開発との境界

PR #1599で導入されたHost内の起動開始ガード、およびPR #1601で進行中の世代別の実行中プロセス管理には手を加えない。管理API・監査Sinkはそれらの上位に追加する。既存`Allow/Revoke`をただちに破壊的変更することはしない。まずHostの管理経路を通じた利用を実装・試験し、その後に低水準APIの外部公開制限を検討する。


## 段階B：監査付き管理アダプタの参照実装

`internal/plugin/runtime/process_signer_audited_admin_linux.go`には、Hostが認可した署名鍵管理と監査先を組み合わせる`LinuxSignerAuditedAdmin`を用意しました。`LinuxSignerAuditSink`が設定されていない場合、操作を拒否します。許可された鍵登録・失効は、**変更前の準備記録が成功した場合にだけ**実行され、変更後には、実施結果を別の記録として残します。監査イベントに記録するのは、操作ID、Host ID、認証済み主体、署名参照、操作、変更前後の観測世代、公開鍵のSHA-256指紋、段階、結果コード、時刻です。公開鍵そのものや秘密鍵は含めません。

- 権限が拒否された場合は`denied`、事前準備は`prepared`、変更成功は`applied`、失効対象なしは`unchanged`、中断・操作失敗は`failed`として区別します。
- 事前の監査記録の保存に失敗した場合、鍵は変更しません。変更後の結果記録が失敗した場合は`ErrLinuxSignerAuditOutcomeUnrecorded`を返します。**鍵の変更が既に成立している場合があり、エラーをロールバック成功と解釈してはいけません。**
- `LinuxSignerAuditSink`が成功と応答した場合は、Hostが選んだ永続的な監査先への書込みが完了したことを意味する契約です。参照用のインメモリ監査先では、永続性を検証できません。

```sh
go test -count=1 -run '^TestLinuxSignerAuditedAdmin' ./internal/plugin/runtime
```

**依然として未実装の要件：** 監査と鍵更新は単一の永続トランザクションではありません。`prepared`だけが残った場合、実際の鍵状態と照合して復旧する仕組みが必要です。アダプタ自身の同時操作は直列化しています。一方、別のアダプタや低水準の`Trust.Allow/Revoke`から行われる変更は防ぎません。管理操作IDの重複排除、主体の真正性の取得、Host/テナントの権限設計、監査記録の保全、クラッシュ復旧、複数Host間の同期待ちは、後続の課題として残ります。
