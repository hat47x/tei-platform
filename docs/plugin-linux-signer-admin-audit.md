# Linux署名鍵管理：認可・監査のHost契約（設計案）

対象：Issue #1370 / #1251。既存の `LinuxHostSignerTrust.Allow/Revoke` は、Hostが信頼する鍵を変更する低水準機構であり、呼び出し元の認可や永続監査は行わない。この文書は管理経路の要求を明確にするもので、認可・監査が実装済みであることを意味しない。

## 境界と基本原則

- **プラグインの実行経路から鍵の変更操作を公開しない。** 操作要求の発信元、認証された主体、管理対象のHost/テナント、対象署名参照、操作種別（登録・交換・失効）をHostの管理経路が確定する。
- **要求に記載されたactorやtenantを信頼しない。** Hostが検証済みの認証コンテキストから取り出し、権限判定と監査へ同じ値を渡す。
- **デフォルト拒否。** 権限判定に失敗した場合、鍵集合は変更しない。監査記録の保存に失敗した場合も、原則として変更を開始しない。
- **鍵の素材と証拠を分離。** 公開鍵はHostの信頼ストアに保持し、署名証拠やプラグインのマニフェストからの自己申告を信頼しない。監査イベントには公開鍵の生データを載せず、SHA-256指紋を記録する。
- **複数Hostは別要件。** 現状のメモリ内`LinuxHostSignerTrust`はHost間同期・永続化・再起動時の復元を提供しない。

## 管理操作の受入契約

1. 認証済み主体・操作権限・Host/テナントの範囲・対象署名参照を検証し、操作前に権限判定を完了する。認証主体不明、対象外の署名参照、権限不足は拒否。
2. `Allow`の登録と交換を区別し、`Revoke`では存在しない参照を変更成功として報告しない。同じ鍵の再登録でも世代は更新する。
3. 成功イベントは、操作ID、Host ID、認証済み主体ID、対象参照、操作種別、旧世代、新世代、旧/新公開鍵指紋、時刻、結果、理由コードを含む。失敗イベントは秘密情報を含まない理由コードを記録する。
4. 権限判定と監査の失敗を検出可能にし、少なくとも管理者へエラーを返す。監査記録の欠落を隠して成功応答しない。
5. 更新後に既存の署名済み固定実行内容が旧世代を使って新たに起動しないことを確認する。起動済みプロセスの停止は別の運用ポリシーとする。
6. 管理操作と監査の整合性は単一Host内でも明確化する。イベント書込み後に更新が失敗した場合は、成功として誤記録しない。監査と鍵更新のトランザクション、または保留/確定イベントの二段階記録を選択し、クラッシュ復旧時の不整合を検出する。

## 推奨インターフェース（未実装）

```go
type SignerAdminRequest struct {
    OperationID string
    HostID      string
    SignerRef   string
    Operation   string // register | rotate | revoke
    PublicKey   []byte // revokeでは空
}

type SignerAdminAuthorizer interface {
    AuthorizeSignerChange(ctx context.Context, principal VerifiedPrincipal, req SignerAdminRequest) error
}

type SignerAdminAuditSink interface {
    RecordSignerChange(ctx context.Context, event SignerAdminAuditEvent) error
}
```

`VerifiedPrincipal`は外部要求に含めず、Hostの認証層が生成する。監査Sinkは、イベント順序、耐障害性、改ざん検知、保持期間を実運用に応じて選択可能とする。失効後の新規起動禁止は既存のHost内信頼集合に委ね、管理APIから直接子プロセスを起動しない。

## 最小実装の切り分け

- **A. Host管理アダプタ**：認証済み主体と対象範囲の検証、拒否時の非変更試験、権限テーブルの外部注入。
- **B. 監査イベント**：成功・拒否・監査障害・重複操作IDを記録する型とSink。公開鍵指紋のみ保持。
- **C. 永続化・復旧**：Hostの鍵世代と失効状態を保存し、クラッシュ後に古い承認を復活させない。複数Hostの伝播はその後の別Issueで扱う。
- **D. 故障注入試験**：認可失敗、監査失敗、更新失敗、再起動、同時失効・起動、同一操作の再送を検証する。

## 並行開発との境界

PR #1599で導入されたHost内の起動開始ガードと、PR #1601で進行中の世代別の実行中プロセス管理は変更しない。管理API・監査Sinkはそれらの上位に追加する。既存`Allow/Revoke`をただちに破壊的変更せず、まずHostの管理経路を通じた利用を実装・試験してから、低水準APIの外部公開制限を検討する。


## 段階B：監査付き管理アダプタの参照実装

`internal/plugin/runtime/process_signer_audited_admin_linux.go`には、Hostが認可した署名鍵管理に監査先を組み合わせる`LinuxSignerAuditedAdmin`を用意しました。`LinuxSignerAuditSink`が未設定の場合は操作を拒否します。許可された鍵登録・失効は、**変更前の準備記録が成功した場合にだけ**実行され、変更後に実施結果を別の記録として残します。監査イベントには操作ID、Host ID、認証済み主体、署名参照、操作、変更前後の観測世代、公開鍵のSHA-256指紋、段階、結果コード、時刻を含みます。公開鍵そのものや秘密鍵は含めません。

- 権限が拒否された場合は`denied`、事前準備は`prepared`、変更成功は`applied`、失効対象なしは`unchanged`、中断・操作失敗は`failed`として区別します。
- 事前の監査記録を保存できなければ、鍵は変更しません。変更後の結果記録が失敗した場合は`ErrLinuxSignerAuditOutcomeUnrecorded`を返します。**鍵の変更が既に成立している場合があり、エラーをロールバック成功と解釈してはいけません。**
- `LinuxSignerAuditSink`の成功応答は、Hostが選んだ永続的な監査先への書込み完了を意味する契約です。参照用のインメモリ監査先は永続性の検証には使用できません。

```sh
go test -count=1 -run '^TestLinuxSignerAuditedAdmin' ./internal/plugin/runtime
```

**依然として未実装の要件：** 監査と鍵更新は単一の永続トランザクションではありません。`prepared`だけが残った場合、実際の鍵状態と照合して復旧する仕組みが必要です。アダプタ自身の同時操作は直列化していますが、別のアダプタや低水準の`Trust.Allow/Revoke`から行われる変更までは防ぎません。管理操作IDの永続的な重複排除、主体の真正性の取得、Host/テナントの権限設計、監査記録の保全、クラッシュ復旧、複数Host間の同期待ちは後続の課題です。


## 段階C：管理操作IDの一意予約

`LinuxSignerAuditedAdmin`は、Hostが提供する`LinuxSignerOperationLedger`を必須の依存として受け取ります。鍵を変更する操作では、**権限を確認した後、監査準備記録を残す前**に`(HostID, OperationID)`を一意に予約します。予約に失敗したり、既に同じIDが使用されていたりする場合は、鍵を変更しません。

- **再送の拒否**：同じ操作IDが登録、交換、失効のいずれに再利用されても`ErrLinuxSignerOperationReplay`として拒否します。同じIDで公開鍵を変えても、別の操作へ変えても再実行しません。
- **保存障害時の拒否**：一意予約の結果を確認できなければ`ErrLinuxSignerOperationReservationUnavailable`を返し、鍵変更と準備監査を実施しません。保存先のエラー文字列は上位へ転送しません。
- **予約後の失敗**：監査の準備記録が失敗した場合も、結果記録に失敗した場合も、予約は自動で解放しません。別の操作IDで改めて操作する前に、`prepared`などの監査イベントと現在の鍵状態を照合して原因・結果を確認する必要があります。
- **無権限要求**：認可に失敗した要求は操作IDを予約しません。権限のない要求によって、正規の管理者が使う操作IDを先取りできない構成です。
- **実行時の前提**：永続的な一意制約、原子的な予約、障害後も失われない保存を`LinuxSignerOperationLedger`のHost実装が保証しなければなりません。今回の試験用インメモリ実装は、その性質を**実証しません**。

```sh
go test -count=1 -run '^TestLinuxSignerOperationReservation|^TestLinuxSignerAuditedAdmin' ./internal/plugin/runtime
```

**成立範囲に関する注意**：同じHost管理の永続Ledgerを共有する経路について、同一IDによる鍵変更を高々一回に制限する契約です。低水準の`LinuxHostSignerTrust.Allow/Revoke`を直接呼ぶ経路、Ledgerを共有しないHost、別々のHost IDの操作、Ledgerが耐久性を保証しない実装には、この保護が自動的には適用されません。成功した操作の結果を再送に応答として再現する仕組みは設けず、重複要求は拒否して既存結果の照合を求めます。

今後は、実際の永続Ledgerアダプタと再起動・クラッシュ障害注入を用い、予約・監査・鍵状態を再照合する復旧手順を検証します。


## 段階D：ローカルファイルによる永続操作予約（参照実装）

`LinuxFileSignerOperationLedger`は、Linux上のホスト管理ディレクトリに対して、`LinuxSignerOperationLedger`の永続的な一意予約を実装したものです。

利用前にホスト側で、信頼できる親ディレクトリの下へ専用ディレクトリを作成してください。ディレクトリの最終要素はシンボリックリンク不可、実効ユーザーの所有で、他ユーザーに読取・書込・実行権限を与えない設定（原則0700）が必要です。操作の記録ファイルは0600で作成されます。

1. `HostID`と`OperationID`から、一意なJSON文字列のSHA-256ハッシュを計算してファイル名とします。操作主体・参照名・公開鍵の指紋・操作種別はレコード内容として保存します。
2. ディレクトリのファイル記述子を保持し、`openat(O_CREAT|O_EXCL|O_NOFOLLOW)`で予約ファイルを新規作成します。既存ファイルがあれば、要求が同一内容かどうかに関係なく重複として拒否します。異なる管理アダプタ・別プロセスで同じディレクトリを共有しても、一意なファイル名に対する排他作成を利用します。
3. レコードの書込み、ファイルの`fsync`、ファイルのクローズ、ディレクトリの`fsync`が成功した場合にだけ「予約成功」を返します。失敗した場合は予約ファイルを削除せず、再実行を安全側で止めます。
4. 再起動後は同じディレクトリを開き直せます。予約ファイルを消したり上書きしたりするAPIは用意しません。

```go
ledger, err := runtime.NewLinuxFileSignerOperationLedger("/var/lib/tei/signer-operations")
if err != nil { return err }
defer ledger.Close()
admin.Operations = ledger
```

```sh
go test -count=1 -run '^TestLinuxFileSignerOperationLedger' ./internal/plugin/runtime
```

**運用上の境界**：この参照実装は**信頼できる単一Linuxホストと、排他作成・同期書込みが機能するローカルファイルシステム**を前提とします。親ディレクトリの改変防止、ファイルシステムの耐障害性、バックアップ、ストレージ障害への対応は運用者の責務です。ネットワークファイルシステムの排他操作や複数ホストの分散合意は保証しません。保存された予約ファイルを誤って消せば、予約に基づく再送防止が成立しません。

同じディレクトリを閉じて開き直す試験は行いますが、**実際の電源断と再起動、ストレージの同期保証を検証する試験ではありません**。同時予約・不正な権限の拒否・管理アダプタでの再送防止も検証します。鍵の永続化、監査結果と現在の鍵状態の復旧照合、監査先との一貫したトランザクションは未実装です。


## 段階D：Linuxファイル台帳の参照実装

`LinuxFileSignerOperationLedger`は、Hostが管理する既存の専用ディレクトリへ、操作ごとに排他的なファイル作成（`O_CREATE|O_EXCL`）を行い、ファイルとディレクトリの`fsync`が成功してから初めて一意予約を成立と報告します。名前には`SHA-256(HostID + NUL + OperationID)`を用い、ファイルには復旧のための操作情報を記録します。公開鍵・秘密鍵のバイト列は保存しません。

- 保存先はHostと同じ実効UIDが所有する既存の絶対パスの専用ディレクトリで、モードは`0700`、シンボリックリンク自体は拒否します。親ディレクトリを含むパス全体もHostが管理し、同一UIDの敵対者や任意書込みを排除する必要があります。
- 同じHost・同じ操作IDの予約ファイルが存在すれば、新しいLedgerインスタンスからの再送でも失敗扱いとし、上位では`ErrLinuxSignerOperationReplay`として鍵変更を拒否します。破損した予約ファイルも自動削除・再利用はしません。
- 途中で書込み、同期、クローズ、キャンセルに失敗した場合もファイルを消さず、原則として保存障害を返します。保留状態は運用者による照合対象です。
- テストでは別インスタンスからの再送と並列予約、安全でないディレクトリ、変更された権限、キャンセル、監査付き管理アダプタとの結合を確認します。

```sh
go test -count=1 -run '^TestLinuxFileSignerOperationLedger' ./internal/plugin/runtime
```

**保証の制約：** ローカルファイルシステムでの排他作成と同期に依存します。NFS等の分散ファイルシステム、ホスト間の任意の共同保存、ディレクトリの親パスを差し替えられる環境、同じUIDの攻撃者が存在する場合の防御は対象外です。ファイル台帳を備えたことは、鍵集合そのものの永続化や監査と鍵更新の原子的な確定、再起動時の鍵状態復元を意味しません。複数Host間にまたがる一意性には、それを保証する別の永続ストアが必要です。
