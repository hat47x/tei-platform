# TEI 文書品質ガイド

この文書は、TEIの技術文書・要件文書・設計文書・Issue・ADRを、**正確さを落とさず、より多くの人が理解し、レビューし、参画できる状態にするための執筆ガイド**です。

TEIは、業務のモデル化、データ設計、実行基盤、セキュリティ、配備、AIによる認知処理、適合性の確認までを、一連の意味のつながりとして扱う製品です。そのため、前提知識が多くなりがちです。その難しさを、そのまま読者の負担にしてはいけません。

目標は、内容を単純化することではなく、**文書側で背景・前提・因果・具体例を丁寧に引き受けることで、同じ内容へ参画するために必要な技術・業務知識を実質的に一段階下げること**です。

このガイドは、Product RequirementやArchitectureの第二正本ではありません。文書の意味・配置・正本性は[`../AGENTS.md`](../AGENTS.md)と各正本文書に従います。

## 1. 基本原則

### 1.1 読者の知識不足を前提にしすぎない

「この程度は知っているはず」として説明を省くと、設計そのものよりも用語や暗黙前提の解読に時間が使われます。

ただし、すべてを教科書のように説明すると、本来の設計判断が埋もれてしまいます。

TEIでは、本文を読むために必要な前提だけを、必要な場所で短く補います。

たとえば`fencing token`という語を使う場合、最初から分散システムの教科書を説明する必要はありません。しかし、少なくとも次の一文があれば、読者は設計意図を追えます。

> fencing tokenは、古い所有者があとから操作を続けても拒否できるように、所有権の世代を単調増加する番号で識別する仕組みです。

専門語を減らすことが目的ではありません。**専門語を、意味を失わず理解できる形で導入すること**が目的です。

### 1.2 詳細より先に、なぜ必要かを書く

新しい概念や仕組みを説明するときは、原則として次の順で書きます。

```text
背景
  ↓
困っていること / 防ぎたい失敗
  ↓
守る原則
  ↓
必要な能力
  ↓
具体例
  ↓
設計・方式
  ↓
未解決 / 非主張範囲
```

たとえば`Durable Invocation Handle`を説明する場合、構造体のfieldから始めません。

先に、次の問題を示します。

> 外部processへ処理を依頼したあとHostが停止した場合、処理がまだ動いているのか、すでに終わったのか、存在しないのかを区別できないと、安全な引継ぎができません。

その後で「このためにDurable Invocation Handleを持つ」と説明します。

### 1.3 「何であるか」と同じくらい「なぜそうするか」を書く

仕様の列挙だけでは、変更時に何を守るべきか判断できません。

重要なRequirement、Architecture境界、ADRには、可能な範囲で次を含めます。

- 何を要求するか
- 何を防ぐためか
- 満たさないと何が起きるか
- どの代替案があり、なぜ現在の案を選ぶか
- どこまでは決めておらず、今後のReferenceで判断するか

設計理由を残すことで、将来の実装者が「文面だけを守って目的を壊す」ことを避けます。

### 1.4 自然な日本語を優先する

英語の概念を語順までそのまま持ち込んだ文章は書きません。

悪い例は次のとおりです。

> Candidate retrievalはqualificationの前段に位置し、authorityを所有しないderived mechanismである。

よりよい例は次のとおりです。

> Candidate retrieval（候補探索）は、適用可能性を判定する前に「確認すべき候補」を絞るための仕組みです。候補を出すだけで、業務上の正しさや採否を決める権限は持ちません。

英語名がRepository内の正式名称であれば消す必要はありません。**日本語で意味を説明したうえで、必要な英語名を併記する**ことを基本とします。

### 1.5 正確さを保ったまま、認知負荷を下げる

わかりやすくするために、重要な境界をぼかしてはいけません。

たとえば、

```text
Proposal != Decision
Decision != Execution Authority
Observation != Evidence
Similarity != Applicability
```

のような区別は、簡略化のために一つの「AI判断」や「確認結果」へまとめません。

代わりに、具体例で違いを説明します。

## 2. 読者を一段下から迎える

文書を書くときは、その内容を実装できる人だけを想定しません。

たとえば、ある機能の実装に次の知識が必要だとします。

- Go
- distributed systems
- SQL / Database
- OAuth / SAML
- domain modeling

文書の読者要件まで同じにすると、レビューできる人が極端に減ります。

文書では、主担当より一段浅い知識の人でも、目的・境界・判断理由・主要な失敗例を説明できる状態を目指します。

これは、初心者向けに精度を落とすことではありません。

```text
実装できる
        ↑
設計判断を検証できる
        ↑
境界と理由を説明できる  ← 文書でここまで引き上げる
        ↑
用語を聞いたことがある
```

専門家だけが暗黙に補える情報を文書へ出すことで、レビュー可能な範囲を広げます。

## 3. 文書の入口で明らかにすること

長い文書では、最初の数段落で迷子を作らないようにします。

文書の内容に応じて、冒頭で次の点を明らかにします。

- この文書は何を説明・決定するのか
- 誰が読むと役立つのか
- 何が前提か
- 何はこの文書の対象外か
- 現在は採用済みか、評価中か、計画段階か
- 読後に何が判断できるようになるか

たとえばRequirement Draftであれば、次のような入口が望まれます。

> この文書は、実装方式を決めるための設計書ではありません。まず、Productとして何をできる必要があるかを整理します。特定のLLMや検索アルゴリズムは、その要求を満たす候補として後段で比較します。

この一文だけでも、読者は詳細方式を採用済みと誤解しにくくなります。

## 4. 専門用語の導入

### 4.1 初出で短く意味を添える

TEI固有語や、一般には意味が揺れる語は、初出で短く説明します。

例は次のとおりです。

- **正本となる意味（Canonical）** — 特定の画面やデータベース製品に依存しない、TEIが基準として扱う意味表現
- **用途別の表現（Projection）** — 正本となる意味を、画面・表・図などの用途に合わせて表したもの
- **対応付け（Binding）** — 抽象的な要求を、具体的な実装や資源へ結び付けること
- **検証根拠（Evidence）** — 次の段階へ進む判断のために確認した事実と資料

同じ文書内で何度も定義し直す必要はありません。

### 4.2 略語だけで進めない

`PAS`、`RQ`、`ADR`、`IR`、`CSP`、`SAT`、`SMT`等を使う場合、初出か近い入口で正式名称または役割を示します。

ただし、一般的な`SQL`や`HTTP`まで毎回展開する必要はありません。読者層と文書目的に応じて判断します。

### 4.3 英語と日本語の役割を分ける

リポジトリに保存する識別子や正式名称は、必要な英語表記を維持して構いません。

本文では、英語を並べるだけで意味を表現しない状態を避けます。

```text
悪い:
local contractionでcandidate frontierをqualificationする

良い:
ローカル処理で候補を段階的に絞り込み（contraction）、
適用条件を満たすかを確認したうえで、比較対象として残す候補群を作ります。
```

### 4.4 `yomiyasu`による推敲

日本語文書の執筆・更新では、内容を確定した後に全文を読み直します。文の主張、話題ごとの重み、断定・推量の強さ、依頼や説明などの文の働きを変えずに、主語と述語、文のつながり、不自然な英語の挿入を整えます。英語の概念名より日本語の意味を先に書き、必要な場合だけ原語を添えます。

実際の識別子、API、コマンド、構造化データの列挙値、規格・製品の正式名称、参照URLは翻訳しません。過去の判断や検証結果についても、読みやすさのために状態を格上げしません。機械的な文体検査は見直し候補として使い、警告を消すためだけの言い換えは避けます。

## 5. 具体例を「飾り」ではなく設計検証に使う

TEIは抽象境界が多いため、短い具体例を積極的に使います。

次の場面では、とくに具体例を優先します。

- 複数概念の違いを説明するとき
- なぜ境界を分けるか説明するとき
- Requirementの必要性を示すとき
- 不採用案の問題を示すとき
- stale / unknown / conflict等の例外状態を説明するとき

### 5.1 一つの例を縦に通す

可能なら、同じ受注・顧客・明細等のReferenceを使い続けます。

たとえば「顧客マスタはread-only」という一つの事実から、次を説明できます。

```text
Business meaning
  顧客は受注時に参照する

Application
  customer datasourceを使う

Database Contract
  readを要求する

Binding
  master_dataへ結び付ける

Design proposal
  顧客更新案はconstraint違反で除外する

Test
  write操作が拒否されることを確認する
```

異なる例を次々に出すより、意味の連続性を追いやすくなります。

### 5.2 失敗例を書く

正常系だけでは、境界の必要性がわからないことがあります。

たとえば`Observation != Evidence`なら、

> migration commandが成功したが、接続先が想定と違っていた

という失敗例を示すと、なぜ外部状態の確認が必要か理解しやすくなります。

## 6. 図は「箱を増やす」より「因果を見せる」

図を使う場合は、概念名を大量に配置するより、情報がどう流れ、どこで責務が変わるかを示します。

```text
Authoritative Source
        ↓ parse / normalize
Canonical Meaning
        ↓ derive
Projection / Runtime
        ↓ observe
Evidence
        ↓ propose
Shared Acceptance Boundary
        ↓ accepted only
Authoritative Source
```

読者が図だけを見ても、

- 何が入力か
- 何が派生物か
- どこで判断するか
- どこへ逆流してはいけないか

を説明できることが望まれます。

図を本文の代わりにしません。図の前後で「何を見る図か」を文章で説明します。

## 7. Requirementの書き方

Requirementは一文の命令だけにしないことを推奨します。

重要なRequirementには、次の項目をそろえます。

```text
要求
なぜ必要か
満たさない場合の失敗
確認方法 / Reference
非要求・保留事項
```

例は次のとおりです。

> **要求**: Derived cognitive indexは削除・再生成可能でなければならない。
>
> **理由**: indexを唯一の意味保存先にすると、algorithm変更や破損時にCanonical meaningを復元できなくなるため。
>
> **確認**: indexを削除し、同じrevisionから再生成して同じ意味参照へ戻れることをReferenceで確かめる。
>
> **非要求**: 同じ内部bit表現まで再現することは要求しない。

この形式をすべての小さなRequirementへ機械的に強制する必要はありません。意味境界が難しい箇所で使います。

## 8. ADRの書き方

ADRでは、結果だけでなく選択肢を残します。

最低限、次の点を追えるようにします。

- 何が問題だったか
- 何を守りたいか
- 採用した案
- 有力だった代替案
- 代替案を採用しなかった理由
- この判断で新しく発生する制約
- 後から判断を見直す条件

「Aを採用する」で終わるADRは、将来Bへ変えるべきか判断しにくくなります。

## 9. Plan Issueの書き方

Issueは実装TODOの羅列ではなく、**どの不確実性を減らす作業か**を示します。

冒頭で次を説明します。

- 背景
- 対応するProduct Requirement
- 現時点で何がわからないか
- このIssueで何を明らかにするか
- 完了すると次に何が判断できるか

作業項目は、その後に書きます。

これにより、個別PRが増えても「なぜこの作業をしているのか」を失いにくくします。

## 10. API・データモデル・内部構造の説明

型やfieldの一覧だけでは利用場面が見えません。

APIやdata structureを説明する場合は、少なくとも一つの利用シナリオを添えます。

```text
利用者が何をしたいか
  ↓
どの入力が来るか
  ↓
どの構造へ変換するか
  ↓
どの境界で検証するか
  ↓
何を返すか / 保存するか
```

その後にfieldやmethodを説明すると、構造が必要な理由を追いやすくなります。

内部実装の都合だけで存在するfieldと、Product meaningを持つfieldも分けて書きます。

## 11. Security文書の書き方

Securityは機構名の一覧では理解しにくいため、原則として次の順で説明します。

```text
守る対象
  ↓
想定する誤操作 / 攻撃 / 障害
  ↓
起きる影響
  ↓
防御境界
  ↓
実装されている仕組み
  ↓
残る限界 / Host側責務
```

たとえばfencingなら、

1. 古いHostが操作を継続する可能性がある
2. 新旧Hostが同じResourceを操作すると二重実行や破壊が起きる
3. 世代番号をResource操作へ伝播する
4. staleな世代の操作をBroker / runtime側で拒否する
5. ただしBroker外のResourceまで自動保護されるわけではない

という順で説明します。

「fencingを実装した」だけより、保証範囲が明確になります。

## 12. Evidence・評価結果の書き方

数字や`PASS`を出すだけでは、何を証明したかわかりません。

Evidenceには、可能な範囲で次を添えます。

- 何を確かめるための試験か
- どのrevision / fixture / external assetを使ったか
- 何が観測されたか
- そこから何を言ってよいか
- 何までは言えないか

特にsynthetic fixture、mock、isolated test、real external asset、本番相当環境を混同しません。

## 13. 「未解決」を品質の低さとみなさない

上流工程では、確定していないことを確定したように書く方が危険です。

文書では、次を明示して構いません。

- unknown
- unresolved
- candidate
- evaluation pending
- Evidence不足
- second Reference待ち

ただし「未解決」と書くだけで放置せず、**何がわかれば判断できるか**をできる範囲で添えます。

## 14. 読み進める順序を設計する

TEIでは文書数が増えるため、一文書の読みやすさだけでなく、文書間の導線も品質です。

原則として、

```text
初心者向け説明
  ↓
Productの目的・原則
  ↓
Requirement
  ↓
Architecture / Design
  ↓
Issue / ADR
  ↓
Reference / Evidence
  ↓
実装詳細
```

のように、必要に応じて深く潜れる構造にします。

詳細文書からしか根幹の趣旨を復元できない状態を避けます。

また、上位文書へ下位の詳細をすべて複製しません。上位では意味を説明し、下位へリンクします。

## 15. レビュー時の確認項目

文書PRでは、誤字脱字だけでなく次を確認します。

- 冒頭だけで文書の役割と状態がわかるか
- 背景を知らない読者が「なぜ必要か」を追えるか
- 用語が説明なしに連続していないか
- 日本語として自然に読めるか
- 箇条書きだけで判断理由が消えていないか
- 具体例が少なく、抽象語だけになっていないか
- Requirementの未達時に何が困るか説明できるか
- 採用案以外の有力な選択肢が隠れていないか
- 図は因果や責務境界を示しているか
- implementation / Evidence / Product claimを混同していないか
- 未解決事項を暗黙に確定していないか
- その文書を読んだ人が、次に読むべき文書を見つけられるか

## 16. 文書品質の目標

TEIの文書品質は、文章が整っているだけでは足りません。

良い文書は、読者が次の問いへ答えられる状態を作ります。

1. 何の問題を解こうとしているか
2. なぜこの境界が必要か
3. 何が正本で、何が派生物か
4. どこまで成立していて、どこから未検証か
5. 他にどんな選択肢があったか
6. 何を変更すると、どこへ影響するか
7. 自分はどの程度の知識があればレビューや実装へ参加できるか

最終的には、TEIそのものが高度であっても、**高度であることと、説明が難解であることを同一視しない**ことを文書文化として定着させます。
