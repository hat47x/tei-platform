# TEI仕様書の共通様式：概要から詳細契約へ

この文書は、TEIの機能・契約・構成に関する**設計文書を読みやすく整理するための執筆ガイド**です。新しい製品要求や実装契約、意味モデルの正本を作るものではありません。既存文書の配置と判断の正本は、[文書案内](README.md)、[文書品質ガイド](documentation-quality.md)、[開発規則](../AGENTS.md)を優先します。

## まず結論を読めるようにする

読者が必要な深さを選べるよう、説明を次の三段階で整理します。**三つのファイルや重複した仕様を必ず作るという意味ではありません。** 小さな仕様は一文書内の見出しで十分です。

| 深さ | 読者の問い | 書くこと | 書かないこと |
| --- | --- | --- | --- |
| 概観 | 何を、なぜ実現するのか | 目的、使いどころ、対象外、現在の状態 | 詳細な型の羅列 |
| 利用例・構造説明 | どのように振る舞うか | 一貫した利用例、図・表、通常時と失敗時の流れ | 概念名だけの図 |
| 詳細契約 | 境界で何を保証するか | 入出力、状態、制約、例外、互換性、反例、検証条件 | 未検証を実証済みとみなす記述 |

推奨する読み順は「問題 → 解決したいこと → 小さな使用例 → 責務と構造 → 正確な契約 → 負例と検証」です。すべての章を機械的に埋めるのではなく、読者が迷う部分を具体的に書きます。概要だけを読んでも核心が分かり、実装担当者は同じ文書から詳細に到達できることを目標とします。

## 文書の役割と正本を分ける

| 何を記述するか | 既存の置き場所・正本 | この様式との関係 |
| --- | --- | --- |
| 製品価値と設計原則 | `product/` | 引用・参照する |
| 製品要求 | `requirements/` | 要求を別の場所で再定義しない |
| 採用した設計判断 | `plan/adr/` | 判断理由・代替案はADRへ |
| 複数Issueをまたぐ設計・未採用の案 | `plan/design/` | この様式とテンプレートを適用できる |
| 実装に対応した利用・構成説明 | `docs/` | 実装と検証された範囲を示す |
| 現行の実装状態 | `docs/status.md` | 現況は参照し、第二の状態表を作らない |
| 実装・試験・外部観測 | ソース、試験、`plan/evidence/`、Gate記録 | 対象版を特定して参照する |

文書の冒頭では「本書が何を定義するか」「何を定義しないか」「現在は提案か採用済みか」を短く示します。**仕様の採否、コードの存在、テスト合格、実環境の確認は別の軸**です。たとえば「採用済み・実装未確認」も成り立ちます。章の題名やファイル拡張子、AIによる説明生成だけで意味受理や実行権限を得たことにはしません。

## 最小の共通ヘッダー

複数の担当者やAIハーネスが読む設計文書では、可能な範囲で最初に次を示します。既存識別子があれば使い、新しい全社共通ID登録簿をこのために設けません。

| 項目 | 意味 |
| --- | --- |
| 目的・対象読者 | 何の問題を扱い、誰が何を判断できるか |
| 状態 | 提案、採用済み、評価中など、**設計判断の状態** |
| 対象範囲・対象外 | システム、機能、利用条件。隣接担当との境界 |
| 参照する正本 | RQ、ADR、対応Issue、既存契約・モデルへのリンク |
| 実装・検証の位置 | 現在の版を確認する場所。未実施は未実施と書く |
| 未解決の判断 | 何が判明すれば決められるか |

## 詳細契約の書き分け

説明文は自然な日本語を基本とし、正確さが必要な部分だけ表、コード、図、数式、実行可能なSchemaへ切り替えます。

- **型と値**：値域、単位・精度、Identity、多重度、順序、NULL・欠損・未取得・非開示の差を必要な範囲で定義する。
- **振る舞い**：事前条件、入力、処理、事後条件、失敗、時間・競合、再試行を区別する。
- **作用と権限**：提案・意味受理・操作要求・外部実行・観測を混同しない。実装範囲外の権限を推定しない。
- **互換性**：旧Source、移行前後の意味、読取り・書戻し・生成先で保存すべき情報を記す。
- **検証**：正常例と独立した負例、ExpectedとActual、実施した版・環境、判定できない範囲を分ける。

規範的な条項は、原則として**一つの条件・一つの期待結果**を記し、曖昧な副詞より観測可能な事象で述べます。表や図で重要な意味を定義した場合、文章と二重の手編集正本を作らず、片方を参照・投影にします。機械可読な契約がすでに正本なら仕様書では説明とリンクを優先します。

### 小さな例：外部参照を取得できない場合

以下は**説明のための仮想例**であり、TEIの採用済み契約や現行実装の挙動を追加で確定するものではありません。

> 外部資料が取得できなくても、保存済みの内容と現在確認できた内容を区別し、取得不能だけを「内容の変更なし」の証拠にしない。

| 条件 | 期待する扱いの例 | 確認すべき反例 |
| --- | --- | --- |
| 参照先が取得でき、版・内容を照合できる | 照合範囲を示す | 同じURLというだけで内容一致と判定しない |
| 参照先を取得できない | 取得不能とその時点を示す | キャッシュがあるだけで最新と断定しない |
| 取得内容が前回から変わる | 影響する情報の再評価を検討する | 変更を無条件で受理済みの意味に反映しない |

詳細契約の正本は、対応する設計・受入記録を確認します。この例から新しい列挙型や状態遷移を作りません。

## 仕様の種類ごとに必要な深さを選ぶ

| 種類 | 推奨テンプレート | 厳密化すべき部分 |
| --- | --- | --- |
| 利用者の操作・業務機能・GUI | [機能仕様](spec-templates/feature-spec.md) | 主体・操作・例外・三視点・受入 |
| DSL・意味型・データ・プラグイン・API | [契約仕様](spec-templates/contract-spec.md) | 値域・状態・エラー・権限・互換性 |
| サブシステム・Target・実行境界 | [構成仕様](spec-templates/architecture-spec.md) | 責務・依存方向・実行時相互作用・品質 |

要求の採否は要求の正本で、設計判断はADRで管理します。これらの既存様式を上記テンプレートで上書きしません。Markdown上の型付きモデル定義・テスト表を実際に解釈・編集する機能は[Issue #2621](https://github.com/hat47x/tei-platform/issues/2621)、識別子参照の実在検査は[Issue #2309](https://github.com/hat47x/tei-platform/issues/2309)の担当です。**この文書は読み手向けの記述様式であり、Parser、Formatter、Writer、追加の判定Gateを実装しません。**

## レビューと段階的導入

新規仕様で試し、既存の長大な仕様書は一括変換しません。最初は一つの機能仕様と一つの契約仕様を同じ独立Expectedで照合し、どの読者が何を見落としたかを確認します。

1. 概要だけで目的・対象外・状態・次の参照先を説明できるか。
2. 例を読んだ人が、主体・入力・出力・失敗時の動作を再現できるか。
3. 詳細契約に、NULL・未取得・権限・競合など**当該機能に関係する**境界が欠けていないか。
4. 正本、提案、採用、実装、テスト、実環境の証拠を混同していないか。
5. RQ・ADR・Issue・テスト・証拠のリンクが辿れ、リンク先の版・確認範囲が分かるか。
6. 文書の説明と機械可読契約の差分があれば、どちらが正本か判断できるか。

AIのレビューは観点を増やす補助です。AIが仕様を自然に説明できたこと自体は、Ownerによる意味受理や実装の適合を示しません。

## 参考にした公開様式

- [Rust RFC Template](https://github.com/rust-lang/rfcs/blob/main/0000-template.md)：Guide-level / Reference-levelの説明を分ける考え方。
- [arc42](https://arc42.org/overview/)：システム構成・実行時の動作・品質・判断の整理。
- [Diátaxis](https://diataxis.fr/)：説明、手順、参照資料、学習資料の役割分担。
- [Kubernetes KEP Template](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md)：機能変更の目標・試験・移行への導線。
- [MADR](https://adr.github.io/madr/)：設計判断の背景・選択肢・影響。
- [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)：要求の明確さ・検証可能性の参考。

これらは参考にした**記述方式**であり、TEIが規格適合・認証を得たことを示しません。判断や要求の内容は、それぞれのTEIの正本で定めます。
