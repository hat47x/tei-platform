# 開発知識の蓄積と自律開発

[AGENTS.md](../AGENTS.md)から参照する。開発の途中で得た知見を、次の担当が再利用できる形に育てるための規約と索引である。個々の作業の履歴や製品仕様の第二の正本は作らない。

## 1. 知見を残す責務

すべての担当は、一つの実装・設計・レビューの区切り、障害の解決時、他担当への引継ぎ時に、今回得た知見が次の作業にも役立つかを確認する。特に、繰り返す障害、予想外の仕様・環境制約、利用者の操作で見つけた不足、人や他のエージェントからの訂正、再利用可能な実装・検証手順を対象とする。何もなければ追記しなくてよい。

| 知見の種類 | 更新先 |
| --- | --- |
| 製品の要求・設計判断 | 該当する要求、ADR、設計文書。未決は既存Issueへ |
| コードの利用条件、型・API・既存機構 | 対象ディレクトリのREADME、コード、契約試験 |
| ビルド・試験・障害切り分け | 対象のREADME、検証スクリプト、[作業ガイド](agent-development-guide.md) |
| 繰り返す専門作業 | 該当する既存Skill。公開前のSkillは許可された非公開作業資料側 |
| 担当間の依存・引継ぎ | 対象Issue/PR、DSHのセッション参照。次の判断に必要な情報だけ残す |
| 複数領域に共通する開発上の教訓 | 本文書の索引（§4）。詳細は既存の適切な正本へ |
| 個別の実行記録・CIログ | PR・CI。長期的な知識として複製しない |

既存文書を検索し、最も具体的な正本を一つ選んで更新する。再利用可能な知見だけを短くまとめ、索引からたどれるようにする。既存の参照経路で十分なら索引も増やさない。公開・非公開の境界を守り、未公開資料の内容や外部送出を許可されていない情報は公開側へ転記しない。

## 2. 知見を確かめ、更新する

- 記載するのは、適用場面、観測された事実、再利用する判断・手順、根拠（Issue/PR、commit、実行可能な試験または該当仕様）、適用限界。実行環境依存なら確認したバージョンも示す。
- 仮説や単発の観測を全担当への規則にしない。再現・既存契約との照合・必要な独立レビューにより確かめる。事実が不足する場合は候補として対象Issueへ戻す。
- 再発すると影響が大きい問題は、文章だけでなく既存の回帰試験、静的検査、型、診断、CIへ反映する。診断は原因と次の対処をたどれるようにする。対処を無理に全域へ一般化しない。
- 確認できる可逆な開発規約・手順・Skillの改善は、[ADR-0035](../plan/adr/0035-autonomy-levels-and-verification-packets.md)のA2/A3に従い、通常のPRと検証で自律的に更新・統合する。人の逐次承認を要件にしない。権限拡大、検査の無効化、未受理の業務意味や外部効果の承認を知識の更新で代替しない。
- 仕様・コード・環境が変わったときは関連知識も確認する。古い手順は現在の正本へ更新・統合・削除し、履歴はGitに任せる。矛盾は放置せず対象担当へ渡す。

実装フィードバック・仕様整備レーンは、他の担当が発見した共通課題、重複した知見、古い参照を作業選定時に確認し、必要に応じて担当と協調して整理する。専任の承認者にはならず、各実装担当も自分の作業範囲で更新してよい。

## 3. 長時間開発を止めない作業循環

1. 開始・再開時に、現在のゴール、最新main、対象Issue/PR、担当範囲、関連セッションと直近の知見を読む。環境と対象の基本動作を既存のコマンドで確認する。
2. 未達のゴールから、利用者に届く小さな実装・設計単位を選ぶ。他担当の障害を解消するもの、既に得られた成果を接続するものを優先する。受入条件、独立Expected、変更範囲は着手時に確かめる。
3. 実装→実行→観測→修正を繰り返す。実際の利用経路で確認し、必要な場合は別ロールへ独立レビューを委任する。テストを通すために要求や期待値を都合よく書き換えない。
4. 失敗時はまず再現条件を限定し、既存の知識・診断・代替手段を調べる。同じ失敗を独立に2回試して改善しないときは[既存の委任・エスカレーション手順](../tools/reference-external-role-dispatcher/AGENT_ROLE_AND_STEP_CODE_OPERATIONS.md)に従う。設計の難所は適切なロールへ渡し、応答を待つ間は依存しない作業を進める。
5. 区切りのよい変更をcommitし、Issue/PRに到達点、未達、次の作業、依存、検証・対象版を残す。中断やコンテキスト圧縮後もこれらから再開する。DSHの他セッション参照は補助とし、チャット履歴だけに知識を閉じ込めない。
6. §1–2に従って再利用できる知見を還元し、必要な検証を通して統合する。ゴールが未達で、独立した作業が残る間は、次の単位へ進む。

人に戻すのは、既存の権限・方針では決められない事項やADR-0035の人による確認が必要な効果に限定する。問題のある部分だけ保留し、可逆な調査、設計候補、隔離した試験、別の作業は進める。人に問い合わせる際は、観測事実、選択肢、推奨案、判断しない場合の影響をまとめる。A3の条件を満たさない統合は行わない。

## 5. 運用の改善

実装フィードバック担当は、同じ失敗・重複開発・人への問い合わせが繰り返される箇所から優先して、知識・Skill・既存検査の改善を行う。リンク切れや陳腐化を見つけた場合も、小さなPRで修正する。反復的な検査は既存CIへ組み込めるか検討する。現時点では専用サービス、追加の必須台帳、全PRへの一律の知識更新チェックを設けない。

評価は文書数や報告件数ではなく、同じ問題の再発、再開時の調査、不要な問い合わせ、重複した変更の減少と、実際に完了する利用者の仕事によって行う。計測が必要な場合は既存Issue/PR/CIから取得できる情報を優先する。
