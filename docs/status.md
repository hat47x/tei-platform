# TEIの実装状況

- 整理日: 2026-11-13（更新のたびに更新する。過去の内容はgit履歴を正本とする）
- 開発段階: **参照実装を使った実験と検証**
- 品質に関する注意: **生成AIを用いて開発中であり、コード・設計・安全性の体系的な人的確認は未実施**です。本番利用を想定していません。

TEIは、分野固有の知識と実装技術を分けて管理するローコード開発基盤を目指しています。現在は業務システムを主な参照事例とし、コマンドラインと参照用作業領域を使って、設計・実装・実行・観測の関係を確かめています。現時点では、完成した製品、画面編集機能、汎用の実行基盤は提供していません。全体像は[README](../README.md)、価値と対象範囲は[製品が大切にする価値](../product/value/TEI_PRODUCT_VALUE.md)と[製品要求](../requirements/TEI_PRODUCT_REQUIREMENTS.md)を参照してください。

2件・参照実装2件・`DeploymentExecutor` アダプタ1件で、**製品が `composition.Coordinator` を通らずに Runtime へ入る経路はいまのところ0件**です（[記録](../plan/evidence/UNPINNED_ADAPTER_SURVEY_2026-11-09/README.md)、旧記録は[RUNTIME_UNPINNED_PATH_PURPOSES_2026-11-08](../plan/evidence/RUNTIME_UNPINNED_PATH_PURPOSES_2026-11-08/README.md)）。ただしピン留めなしの `Registry.Invoke` を呼ぶ `ObservationProvider`／`EvidenceProvider` アダプタは**宣言だけで構築0件**であり、**使えば Coordinator を通らない**点は変わっていません。配備実行でも同じ形で、環境の deployment-executor Binding C-1 は `routing.RouteCommand`・`routing.Router.Dispatch`・`routing.ValidateResult` だけで Binding から実行まで繋がり（[参照](../tools/reference-binding-to-execution/README.md)、v1 で入場前拒否と入場後不確定を分離）、C-2 は `BindHostApplicationEnvironmentRoute`・`NewSelectedCoordinator`・`NewSelectedServiceCarrierInvoker` を順に呼んでHost世代をピン留めした Service 要求を運び（[参照](../tools/reference-service-carrier-connect/README.md)、v1）、C-3 は `RouteCommand` の解決結果を `BuildPlan` の plan が認めるかと `SupportsAction` を確かめます（[参照](../tools/reference-executor-id-resolution/README.md)、v0。実行はしません）。**ただし C-3 には実行側の盲点があります。** `DeploymentExecutor` アダプタは `Plan` と直書きの `CapabilityID` しか持たず、`Environment` を持たないため **Binding を照合できません**。`routing.RouteCommand` も `ValidateResult` も一度も呼ばず、非試験の4つの構築箇所はどれも `Dispatch` を経由せず `adapter.Execute` アダプタを変えずに呼出し側で一致を確かめる形も参照として試してあります（[記録](../plan/evidence/BINDING_GUARDED_EXECUTOR_REFERENCE_2026-11-09/README.md)）。加えて、宣言から解決して既存の Router で実際に入るかを `ObservationProviders` と `EvidenceProviders` で試し（[観測](../tools/reference-observation-router-connect/README.md)、[証拠](../tools/reference-evidence-router-connect/README.md)）、digest が変わったとき旧いピン留めが残るかを `generation.Router` で確かめました（[参照](../tools/reference-digest-change-reuse/README.md)）。**いずれも新しい解決器や選択の仕組みを作らずに動きましたが、これは「繋げられる」ことの証明であって、「繋ぐべき」ことの証明ではありません。** 判断材料の第12節が定めた受入条件 CON-12a〜d（解決と入場の分離・選択されていないProviderを実行しない・識別子が変わったら旧Bindingを再利用しない・部分的成功を保持する）は、**参照実装の範囲で確認済み**です。ただし Provider はすべて合成で、**Grant epoch `routing.ValidateResult` の同一性検査が到達不能でした（[観測](../plan/evidence/ADAPTER_IDENTITY_MASKING_2026-11-09/README.md)、[配備実行](../plan/evidence/EXECUTOR_ADAPTER_IDENTITY_2026-11-09/README.md)）。空のときだけ補う形へ修正し、修正前へ戻すと回帰試験が失敗することを実測しています。また `Router.Dispatch` が「実行するが帰属は判定しない」契約を doc コメントと試験で固定しました。 製品の通常CLI・Studio・本番Hostへの接続は未実証で、判断は[判断材料](../plan/workstreams/COMPOSITION_CONNECT_POINT_BRIEF_2026-11.md)のまま Gate と本節の Owner が持ちます。
