# TEIの製品品質を横断して考える

状態：**横断的な設計基準。検証根拠をもとに評価する方針**

関連する文書と課題は次のとおりです。

- `requirements/TEI_PRODUCT_REQUIREMENTS.md` — 製品要求の正本
- `plan/evidence/PRODUCT_QUALITY_EVIDENCE_PLAN_2026-09.md` — 段階的な実証計画
- `plan/evidence/PRODUCT_REQUIREMENT_GAP_AUDIT.md` — 要求ごとの達成状況
- `plan/UPSTREAM_ACCEPTANCE_SCENARIO_TRACEABILITY.md` — 製品の受け入れシナリオとの対応
- GitHub Issue #565

## 1. 位置づけ

TEIの製品品質は、意味モデルから切り離した「非機能の層」だけで評価するものではありません。

既存の設計で定めた次の境界が、実行先・提供元・実行環境・設計・編集環境・AI支援でも一貫して守られるかを確認するための観点です。

- 業務上の意味と、技術的な実現方法の分離
- 正本となる入力元と、そこから生成した成果物の分離
- 明示的な対応付けと権限
- 期待状態・実際の状態・差分・未解決状態の区別
- 業務結果・実行エラー・観測結果の分離
- 参照事例・準拠確認・検証根拠に基づく再現性
- 利用許可・資源・秘密情報の境界
- 実行先の条件を踏まえた性能
- データ・機能・業務の各視点からの相互確認

そのため、本書では番号付きの製品要求、意味の正本に含まれる要素の種類、判定段階、実行環境の個別機構を新設しません。

## 2. なぜ分野をまたいだ品質の検証が必要か

要求が適切でも、実装ごとに品質を個別評価するだけでは、次のような誤った結論に至るおそれがあります。

```text
データベースでは安全
  ≠ 実行先でも安全

意味の準拠性検査に合格
  ≠ 利用者が操作・復旧できる

応答時間 = 80ms
  ≠ 測定条件を示さず「高速」と主張できる

ログが多い
  ≠ 業務上の意味に沿って診断できる

AIによる検索の正確さが高い
  ≠ 意味の正しさが確認された
```

このような誤認を防ぐため、意味・変更・実行・操作・検証根拠を共通の観点から確認します。

## 3. 品質を確かめる八つの観点

### 3.1 意味の品質

主な問いは次のとおりです。

- 表示方法・実行先・提供元の都合で、正本の意味が変わっていないか。
- 生成した成果物が第二の正本になっていないか。
- 観測が不十分な状態を、`no diff`や成功とみなしていないか。
- 対象の識別が、最初に一致したものを採用するなど、偶然の探索順序に依存していないか。

主に対応する製品要求：

- RQ-001 / 002 / 003 / 006 / 011 / 017 / 018 / 021 / 026

### 3.2 変更の品質

主な問いは次のとおりです。

- 意味が変わらない変更、互換性を保つ変更、互換性を損なう変更、破壊的な変更、未解決の変更を区別できるか。
- 変更を適用する前に、影響範囲と前提条件を説明できるか。
- 計画した後で実際の状態が変わった場合、古い観測結果を根拠に破壊的な操作を実行していないか。
- 再試行、代替処理、CASCADEなどによって、操作の対象範囲が暗黙に広がっていないか。
- 元に戻せない変更について、復旧上の制約を隠していないか。

主に対応する製品要求：

- RQ-002 / 006 / 017 / 020 / 021 / 022

### 3.3 実行の品質

主な問いは次のとおりです。

- 業務上の結果、名前を持つ処理の結末、実行エラー、観測結果を区別できるか。
- 依存先の利用不能、機能低下、時間切れ、状態不明を、成功として扱っていないか。
- 再実行、監督役の交代、再試行によって、同じ外部変更を二重に起こさないか。
- 失敗が、アプリケーション・対応付け・機能・提供元・実行環境のどの境界で起きたか追跡できるか。

主に対応する製品要求：

- RQ-018 / 019 / 020 / 021 / 022

### 3.4 操作の品質

主な問いは次のとおりです。

- 情報量の多い表示が、操作しにくさや理解しにくさにつながっていないか。
- 実行先、ホスト、入力方法に合わせて、主要な利用場面の操作を完了できるか。
- 検証エラー、処理エラー、利用不能な状態から、利用者が操作を立て直せるか。
- 利用しやすさを、見た目の再現度や画面画像の類似度だけで評価していないか。

主に対応する製品要求：

- RQ-010 / 011 / 013 / 021 / 024

### 3.5 性能と資源利用の品質

主な問いは次のとおりです。

- 応答時間・処理量・メモリ使用量・外部サービスの費用などを、実行先・ホスト・提供元・処理負荷の条件とともに記録しているか。
- 平均値だけを示し、処理時間の長い例、初回起動、大量データなど重要な条件を隠していないか。
- 一つの実行先で決めた判定基準を、別の実行先へ無条件に適用していないか。

主に対応する製品要求：

- RQ-021 / 022 / 023 / 024

### 3.6 安全性と権限の品質

主な問いは次のとおりです。

- 業務主体、画面の便利さ、AIの自律性を、実行権限があることの根拠にしていないか。
- 秘密情報、認証情報、接続文字列、不要な物理的識別情報を診断結果や検証根拠へ複製していないか。
- 現在の利用許可と資源管理の境界を迂回する実行経路がないか。

主に対応する製品要求：

- RQ-003 / 008 / 019 / 020 / 021 / 022

### 3.7 保守性と発展のしやすさ

主な問いは次のとおりです。

- 一つの意味の変更に対して、複数の正本を人手で同期する必要が生じていないか。
- 提供元や実行先に固有の変更が、中核部分へ不要に波及していないか。
- 検証用ツール、計画、定義形式を増やすこと自体が、保守の負担になっていないか。
- 保守担当者が一人でも、要求・設計判断・参照事例・検証根拠を順に追跡できるか。

主に対応する製品要求：

- RQ-002 / 003 / 017 / 021 / 023

### 3.8 業務を漏れなく扱う品質

主な問いは次のとおりです。

- アプリケーションの機能だけで、業務全体を説明したことにしていないか。
- 手作業や外部で行われる仕事、業務主体、引き継ぎ、判断を漏らしていないか。
- データ・機能・業務の一つの視点だけを見て、矛盾を見落としていないか。

主に対応する製品要求：

- RQ-025 / 026

## 4. 品質の評価条件

### 4.1 定義

品質について単独の数値だけを残すと、測定した条件が分からなくなったときに、その数値が何を示すか判断できません。

品質についての重要な主張を次の情報と結び付ける考え方を、**Quality Envelope（品質の評価条件）**と呼びます。

```text
評価対象
+ 対象となる版・ビルドの識別情報
+ 実行先・ホスト・提供元・実行環境の条件
+ シナリオ・処理負荷・前提条件
+ 評価する品質特性
+ 測定方法・確認方法
+ 受入条件または判断理由
+ 検証根拠への参照
+ 評価した状態
```

Quality Envelopeは固定された定義形式ではありません。各領域に必要な項目を備え、検証根拠から再構成できる評価の単位です。

### 4.2 状態

少なくとも、次の状態を区別します。

- 観測済み・合格（`observed / passed`）
- 観測済み・不合格（`observed / failed`）
- 未解決（`unresolved`）
- 適用対象外（`not-applicable`）
- 未観測（`not-yet-observed`）

未観測の状態（`not observed`）を`passed`（合格）とみなしてはいけません。

### 4.3 意味の正本とは区別する

品質の評価条件では、次の制約を守ります。

- 業務上の意味を再定義しない
- 正本となる情報源へ暗黙に書き戻さない
- 運用時の計測情報から業務結果を逆に推測しない
- 性能などの測定結果から製品要求を自動生成しない
- 実行先に固有の品質を、すべての実行先に共通する意味として扱わない

## 5. 失敗や結果の種類を分ける

TEIでは、異なる性質のエラーや結果を一つにまとめません。

```text
業務上の結果
名前を持つ処理の結末
実行エラー
観測結果
開発者向けの診断
運用時の計測情報
```

これらは相互に関連付けられますが、同じ意味の情報ではありません。

例は次のとおりです。

```text
HTTP 200
process exit 0
DB commit success
span.status = OK
```

これらのいずれも、それだけで業務上の成功を証明するものではありません。

診断情報や運用記録には、必要な論理識別情報だけを残します。認証情報・パスワード・接続文字列の本文・秘密情報・不要な業務データを通常の記録へ複製しません。

## 6. 変更の安全性

変更の安全性は、データベースの移行に限った問題ではありません。

少なくとも、次のような変更が対象になります。

- 意味の正本となるソースの変更
- アプリケーションや対応付けの変更
- データベースで期待する状態の変更
- 生成物の更新
- 実行先や実行環境の設定変更
- 編集環境やAIから提案され、受理された変更

共通原則は次のとおりです。

```text
変更候補
  → 影響と互換性の確認
  → 必要に応じて現在の前提条件を確認
  → 明示的な受理
  → 変更の適用
  → 再読込み・観測・検証根拠の確認
```

外部の実際の状態に依存する破壊的な操作では、古い観測結果だけを実行許可の根拠にしません。情報の鮮度・版・対象の識別・管理主体など、必要な前提条件を適用直前に確認します。

一方、PostgreSQLに固有の安全機構を、すべての領域で使う共通の変更手順へ無条件に広げることもしません。

## 7. 操作性とアクセシビリティ

実行先に依存しないことは、すべての実行先で最小限の画面機能だけを提供することではありません。

同じアプリケーションの意味を保ちつつ、実行先ごとに適切な操作方法を提供します。主要な利用場面で実際に操作できたことは、検証根拠として記録します。

WebではWCAG 2.2などを検証可能な参考基準として使えます。ただし、デスクトップ・スマートフォン・API・MCP・音声操作に、Web固有の意味や制約を一律に課すことはしません。

画面の見た目に関する検証根拠だけで、操作の成立やアクセシビリティを合格とは判断しません。

## 8. 性能

RQ-024に従い、すべての実行先に共通する性能の合格基準値を先に固定することはしません。

まず参照例で基準となる値を測り、少なくとも次の条件を添えて記録します。

- 実行先とホスト
- 提供元と実行環境
- シナリオと処理負荷
- 起動直後か稼働が安定した後かなどの条件
- 対象となる版とビルドの識別情報

利用目的から必要性を説明できる段階で、受入れの判定基準を定めます。

## 9. AIと派生した認知支援

AI、連想に基づく検索、派生した認知支援では、候補の質と意味の正しさを区別します。

```text
候補の検索率・順位付け・応答時間
        ≠
業務上の適用可能性
        ≠
受理された判断
        ≠
実行権限
```

索引・埋め込み表現・FlyHashやHDCによる表現・処理履歴は派生情報です。これらを削除・再生成しても、意味の正本となるモデル全体が変わらないようにします。

認知方式の評価値もQuality Envelopeに関連付けられます。ただし、モデルの確信度や類似度を、意味の正しさを証明する検証根拠とは扱いません。

## 10. 運用時の計測情報

運用時の計測情報は、実行環境を観測して得られる派生情報です。

OpenTelemetryなどの共通の表現規則に対応付けることは、外部連携に役立ちます。ただし、TEIの意味の正本を、運用時の計測データ形式に合わせて変更することはしません。

必要な相関は次のように表します。

```text
TEIの論理的な識別子
   → 運用時の記録との対応付け
   → 処理の追跡記録・測定値・ログ
```

この対応関係によって、論理上の識別子と運用時の記録を結び付けます。

## 11. 外部の品質モデルの扱い

外部標準はTEIの製品要求に対する第二の正本とはせず、抜け漏れの確認や試験の参考基準として利用します。

- ISO/IEC 25010:2023：品質特性を監査する際の参考
- WCAG 2.2：Webの操作性とアクセシビリティの参考
- OpenTelemetry semantic conventions：運用時の計測情報を対応付ける際の参考
- NIST SSDF 1.1：安全な開発とソフトウェアの供給経路を管理する際の参考

明示的な採用判断とTEI自身の検証根拠がない限り、標準への準拠・認証取得・製品の完成を主張しません。

## 12. 既存の判定段階との関係

この製品品質の設計は、新たな判定段階を追加するものではありません。

- 判定段階B：既存の三つの必須検証根拠を増やさない
- 判定段階C：意味・機能・表示の検証根拠を分ける
- 最初の実行先：操作の成立、アクセシビリティ、性能、失敗時の動作を追加で観測する
- 編集環境・AI・二つ目の実行先：同じ品質評価条件の原則で比較する
- 本番運用：観測可能性、高可用性、ソフトウェアの供給経路などを、必要な検証根拠とともに拡充する

品質の計画策定や文書・コードの静的確認を、実際の環境で取得した検証根拠と同一視しません。

## 13. 先に固定しないもの

- 品質の評価条件を表す固定のスキーマ
- すべての品質をまとめた単一の評価点
- すべての実行先に共通する性能基準値
- すべての実行先に共通するアクセシビリティの確認項目
- OpenTelemetryを実行基盤の必須依存先とすること
- 汎用的な代替処理の実行機構
- 汎用的な再試行の方針
- 汎用的な移行・切戻し手順
- 品質特性ごとに新設する判定段階・受入シナリオ・課題群

これらを固定する必要があるかどうかは、参照事例と検証根拠に基づいて判断します。
