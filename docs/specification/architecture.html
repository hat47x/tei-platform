Workspaceとidentity

Workspaceの範囲はtei.workspace.yamlと管理rootで定めます。.teiだけが管理対象ではありません。標準名前空間はstd.*、生成物は.tei-generated/、派生索引等は.tei/です。業務IDにTEIの製品名を一律に付けません。

Canonical identityにはqualified logical keyを使い、file moveとlogical renameを区別します。同じ論理identityを保つfile移動は意味上の変更なしになり得ますが、Canonical IDの変更は明示的な意味変更です。全資産への手書きUUIDを必須にしません。

Source Indexはpath、fingerprint、range、roleからCanonical subjectへ辿る派生索引です。Semantic validationはDiagnostic＋Subjectを返し、Authoring側がsource上へ投影します。parse errorのために架空のCanonical identityを作りません。

参照：docs/architecture.md ／ requirements/TEI_PRODUCT_REQUIREMENTS.md

ApplicationとDatabaseをN:Mで扱う

一つのApplicationが複数DBを使い、一つのDBが複数ApplicationへContractを提供できます。Application ReleaseとDatabase Releaseは独立し、logical datasource、read／read-write、Environment Binding、transactionとfailureの境界を明示します。DBを跨ぐことから分散transactionを自動的に成立させません。

対象想定仕様
Persistence Mapping業務Dataとphysical table／column等の対応。Semantic Relationと物理FKを同一視しない。
Desired / Actual希望する物理構造と実観測を別に保持する。credentialや接続文字列をPhysical Schemaへ含めない。
Diff / Unresolved情報不足を「差分なし」や破壊的変更へ丸めない。比較scopeと未観測を残す。
Migration差分から候補を作り、明示採用してVersioned Migration／Database Releaseへ進む。観測だけでapplyしない。
Native QuerySQL-authoredならSQLが正本でQuery IRは派生。Graph-authoredとの二重正本を要求しない。
Provider方言、catalog読取、identifier比較、物理正規化、SQL生成はProvider側。Coreへ製品知識を増やし続けない。

PostgreSQLは深い実証対象です。Oracle等の既存外部資産は別のEvidenceとして扱います。real PostgreSQL fixtureの成功で既存Oracleとの互換性を主張しません。Partitionの親子構造とdrop誤判定は評価待ちの個別課題です。

参照：docs/architecture.md ／ plan/issue/000041-partition-schema-drift-semantics.md

Driverの実行結果を分ける

結果意味例・扱い
Business Result / named Outcome処理が契約どおり返した業務上の結末。成功や業務上の拒否。拒否を通信障害へ変換しない。
Execution Error契約を満たす実行・判定を完了できない。Binding欠落、Adapter障害、結果契約違反等。
ObservationCommandとは別のreadから得た結果。read identityとEvidence natureを保持。期待状態との一致判定はさらに別。
Developer Diagnostic設計・参照・実現の問題を開発者へ示す情報。Sourceへ戻れる。ユーザー向け業務結果へ混ぜない。

Command後のread境界は呼出側が選びます。payload、HTTP status、Capability名から推定しません。QueryのRaw resultと明示mapping後のMapped resultを分け、support column等の物理情報をSemantic rowへ漏らしません。

参照：plan/adr/0020-capability-business-outcome-boundary.md ／ plan/adr/0023-command-observation-explicit-read-boundary.md ／ internal/driver/observation.go

認証・認可・実行権限

認証はprincipalを確認し、認可は業務操作の許可を判断します。組織・membership・属性・関係・resourceの情報を明示的に接続し、固定のUser／Roleテーブルを移行要件にしません。既存のpassword方式、ロック、有効期限等はCapability契約とMappingを通じて保持できる方向です。

境界責務
Business actor業務上の担当・責任文脈。これだけでruntime権限を得ない。
Application Authentication / AuthorizationReferenceではsecurity.authenticate／security.authorizeというSemantic Capabilityで分ける。std.auth.*への即時標準化はしない。
Plugin Permission / Resource実装コードがsecret・network・filesystem等へアクセスできる範囲。利用者の認可とは別。
AI autonomy提案・自動化の度合い。高い自律性からwrite／invoke／Resource権限を暗黙付与しない。

参照：docs/security.md ／ plan/adr/0019-authentication-capability-boundary.md

Plugin・配備・回復

Capability単位でbuiltin、generated、Plugin、既存実装を差し替えます。Plugin Lockはversionとartifact identityを固定し、process実行ではPermission、Resource Broker／Lease、Supervisor、ownership／fencingを扱います。plain process launcherをOS sandboxとは呼びません。

配備ではRelease Definitionと実行履歴を分け、Release Graph、Durable Deployment Run、Executor Command、Observation、Reconcileへ接続します。takeover時はSupervisorの権限世代と、外部Runtimeが受理した世代を分けます。外部状態がunknown／missingなら、同じ副作用を無条件に再実行しません。

これらは研究実装の境界です。本番HA、耐久Store、cross-host回復、互換性保証、配布・署名・供給網の運用成熟は後続ロードマップで実証します。

参照：docs/architecture.md ／ docs/plugins.md ／ docs/status.md
