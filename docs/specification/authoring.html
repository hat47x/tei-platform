高密度な開発者向けStudio

Studio／Editorは開発者専用の設計環境です。Dataを一つ選び、そのFields、Relations、Rule、関連Pattern、手順、Source、Evidenceを局所的に追えることを重視します。全体graphを常時表示することより、検索・scope選択から必要な近傍へ入り、3階層以上の関係を分断せず確認できることが重要です。

表示できるようにすること
表・Matrix詳細設計を高密度に読み、参照、影響、CRUD根拠、unknownを比較する。
graph・flow関係、業務の情報流、状態・処理の構造を目的に応じて見る。
UI・自然言語利用者の理解や業務手順から設計の不足を見つける。
Database Workbench物理構造、Desired／Actual／Diffを調べ、元のMappingへ辿る。
Source・Diagnostic・Evidenceなぜその意味・診断・実証になったかを追い、変更箇所へ戻る。

各Projectionは意味を所有する第二の設計DBではありません。編集を許す表示であっても、変更候補を正本と共通受入境界へ返します。最終UI、パネル構造、部品体系はまだ固定していません。

parse／normalize／validate、architecture・policy検査、semantic diff、impact analysis、採用判断、reload／conformanceを変更種類に合わせて組み合わせます。一つの巨大APIにすることは要求しませんが、入口によって検査・権限が変わることは認めません。

PreviewとRejectは非変更操作です。候補のbaseModelRevisionが古い場合は、reject、rebase、regenerate、手動競合解消等を明示します。Patchは任意の入口であり、Patch-onlyや全資産へのStable UUID必須化へ戻しません。

既存知識の探索と再利用

最初に既存Domain Component、Semantic Pattern／Facet、Policy／Variationを探し、合成、宣言式・Rule、Capability呼出し、Custom実装の順に不足を埋める方向です。検索結果にはidentity、正本、依存、利用例、適用条件、Evidenceを結び付け、applicable／incompatible／unknownを分けます。

検索順位、embedding similarity、model confidenceは適合性の証拠ではありません。索引やAI knowledgeを削除・再生成しても意味を失わないことを確かめます。巨大なKnowledge Graphやvector DBの先行構築を開始条件にしません。

探索はISSUE-000047、変更の差分・依存解析は000039、第二Applicationへの組み立ては000040、提案採用は000027が担当します。同じ解析器やCanonical正本をAI側に作り直しません。Application固有のPatternは適用先が所有し、共有するData等は同じidentityを参照します。

参照：plan/issue/000047-knowledge-first-semantic-exploration.md ／ plan/issue/000039-business-change-rehearsal.md ／ plan/issue/000040-semantic-component-composition.md

AI支援の想定体験

AIは既存知識の探索、関係や制約の不自然さ、履歴・監査・認証・状態遷移の検討漏れを指摘し、比較可能な設計案やUI案を作ります。採用済みの事実、推論、提案、未解決を分け、参照したCanonical ID／Source／Evidenceへ戻れるようにします。

確認は必要な場合に控えめに行い、回答済みの質問を理由なく繰り返しません。選択と理由を辿り、後で変更し、提案を無視し、カテゴリを抑制できることが要求です。AI providerやchat-first UX、Proposalの最終schemaは未固定です。

HTMLモックやCustom UIの生成支援も、既存のApplication meaningへ結び付けます。自由生成を毎回の標準にせず、確定した構造から決定論的に作れる部分は通常の生成器へ渡します。AIだけがCanonicalや外部Capabilityを直接変更・呼出しする経路を作りません。

参照：requirements/TEI_PRODUCT_REQUIREMENTS.md ／ plan/adr/0022-ai-proposal-canonical-acceptance-boundary.md

Target・Host・Driverの区別

対象想定位置固定・未固定
GoParser、Resolver、Validator、Compiler、Runtime等の主要実装基盤。現行go.modはmodule tei、Go 1.23.2。業務意味をGo型へ固定しない。
Wails / WebViewdeveloper-facing Studioの外側のHost候補。CoreやCanonical PresentationへWails APIを持ち込まない。最終採用・バージョンをこの文書から固定しない。

第二Application Target第一と異なる条件で共通意味と差を圧力試験する。Gate C後に選択。Generated Wails Desktopを選ぶ場合もStudio Hostとは別実証。
Mobile / API / MCP / VUI上位設計を再利用できる拡張方向。全て対応済みとはしない。AdapterとConformanceで段階的に追加。

Target Capabilityは利用可能な表示・操作・device機能、Execution／Trust Profileはtransport、origin、session、Resource等の実行条件です。HostのMCP検査用interfaceと、業務ApplicationがMCPとして提供する操作も区別します。

Targetで確認する証拠と性能

同じ意味を使うことは、全Targetで同じ画面を描くことではありません。標準ProjectionとCustom UIを同じ上位意味へ接続し、Web固有の部品やレイアウトはTargetへ置きます。Universal widget DSLの最終体系を第一Targetだけで確定しません。

Evidence確認すること
Semantic同じHandover基線から業務意味・認可・結果契約を保つ。
Interaction / Functional利用者Scenarioとして操作が成立し、誤操作・拒否・障害も正しく扱う。
Visual Fidelity配置、可読性、操作可能性等の画面品質。これだけでSemantic合格にしない。
PerformanceTarget／Host／Driver／Providerと負荷・入力条件を添えて実測する。

短い応答が必要なタッチ業務端末とB2C Webを同じ固定閾値で扱いません。過去の「sub-second程度」という志向は利用場面の要望であり、現行の一律SLAではありません。測定条件と合否基準は各TargetのReferenceで具体化します。
