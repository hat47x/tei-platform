# X-TEA知見の受容要件（2026-11）

- 状態: **要求候補**。製品要求の正本は[TEI製品要求](TEI_PRODUCT_REQUIREMENTS.md)です。この文書は、X-TEAから回収した知見を受け止めるために、既存要求の受入条件を具体化し、新しい要求の候補を整理するものです。ここに書いた候補は、採用された要求ではありません。

- 計画: [X-TEA知見の移行計画](../plan/XTEA_LOWCODE_TRANSFER_PLAN_2026-11.md)

## 1. この文書の役割

X-TEAの知識目録には、現在のTEIの要求がすでに扱っているものと、まだ扱っていないものがあります。この文書は、次の三つを分けます。

1. **既存要求の具体化** — 要求はあるが、X-TEAの知見から受入条件を具体化できるもの。
2. **新しい要求の候補** — 現在の要求に受け皿がないもの。
3. **要求にしないもの** — 旧ツールの実装都合であり、TEIの約束にしないもの。

要求の追加・変更は、意味の受理に当たるため、人が判断します（[ADR-0035](../plan/adr/0035-autonomy-levels-and-verification-packets.md)のA4）。この文書はその判断材料です。

本文では、実行能力（Capability）を「能力」、正本から導出した表示・成果物（Projection）を「投影」と呼びます。受容は知識を受け止める設計上の行為、受理は意味を正本へ取り込む判断を指します。アプリケーションの型（Application Pattern）を「Pattern」、拡張を「Plugin」、設計・編集環境を「Studio」と呼びます。

### 2.3 既存要求との重複確認

候補が既存要求の言い換えになっていないかを確認します。

| 候補 | 対応する既存要求 | 既存が定めていること | 候補が加えること | 判定 |
| --- | --- | --- | --- | --- |
| RQ-C1 | RQ-014、RQ-031、RQ-032 | 標準Patternの再利用、Coreで特定体系を特権化しない、Plugin/DSLで意味を宣言 | パッケージの契約（種類、版、適合試験、取り外し）と、Coreの外で型を定義する条件 | 具体化（新しい契約） |
| RQ-C2 | RQ-032、RQ-018 | Pluginの意味宣言、CommandとObservationの分離 | 対話の位相・範囲・読み取り・使用能力・生成物・失敗の型付き宣言 | 具体化（新しい契約） |
| RQ-C3 | 直接対応なし（RQ-001、RQ-011が間接的） | 意味の技術非依存、複数の投影 | 暦・会計期間・税・通貨・採番の適用期間と評価時点 | 新規 |
| AC-1〜AC-11 | 各対象RQ | 要求の本文 | 受入条件と確認方法 | 具体化（要求本文を変えない） |

RQ-C1とRQ-C2は、既存要求が「何を守るか」を定めているのに対し、候補は「どの契約で表すか」を加えます。RQ-C3は、既存要求に対応する記述がないため、新規の候補とします。

## 3. 新しい要求の候補

以下は、現在の要求に対応する記述が見当たらないものです。番号は未確定で、`RQ-C1`〜`RQ-C3`と仮に呼びます。

### RQ-C1 対話の型を、Coreの列挙ではなく、契約を持つ交換可能なパッケージとして再利用できること

**要求.** 一覧・単票・親子・帳票・一括処理・起動処理のような頻出する対話の型を、Coreの要素種別を増やさずに、契約・版・適合試験を持つパッケージとして定義し、再利用できるようにします。パッケージは、既存のData・Relation・Query・Capabilityの型付き参照だけを組み合わせ、取り外しても受理済みの意味を変えません。

**なぜ必要か.** X-TEAの生産性は、8種の閉じた機能型から来ました。同じ生産性を、Coreに特定のモデル体系を固定せずに得るには、型をCoreの外で定義し、契約で交換できる必要があります。RQ-014は標準Patternの再利用を求めていますが、Patternの種類を誰がどの契約で追加できるかは定めていません。

**満たさない場合の失敗.** 機能型をCoreへ追加すると、TEIが特定のモデル体系を特権化し、別の業務分野の型を追加するたびにCore変更が必要になります。逆に、型を一切持たないと、案件ごとに一覧・単票・親子の組合せを再発明し、X-TEAが解いていた定型の再利用が失われます。

**確認方法.** 二つの独立したパッケージ（例：検索一覧、親子保守）を、同じCoreの意味に対して定義し、同じ適合試験の枠組みで比較します。パッケージを取り外したときに、受理済みの意味と他の投影が壊れないことを確認します。パッケージの追加がCoreの要素種別の追加を要求しないことを、変更の差分で確認します。

**非要求.** すべての業務をパッケージで表せることは要求しません。パッケージの市場や配布方式も要求しません。X-TEAの8型をそのまま再現することは要求しません。

### RQ-C2 対話の拡張点を、型付きの契機・範囲・効果を持つ宣言として表せること

**要求.** 定型の対話に、案件固有の検証・導出・参照入力の補助・連携を差し込むとき、正本には**宣言**だけを置き、本体は契約で束縛したPluginが供給できるようにします。宣言は、契機（読取前後、変更前後、削除前後）、範囲（行、レコード、項目）、読み取るデータ、使用する能力、生成する結果、失敗の種類を持ちます。宣言していない能力の呼出し、任意のSQL、任意の確定は許しません。

**なぜ必要か.** X-TEAのイベントとスクリプトは、定型の間に案件固有の処理を差し込む力を与えましたが、スクリプトAPIがSQL・確定・機能呼出しを同じ面に置いていました。RQ-032はPluginによる意味の宣言・合成を求めますが、対話のどの時点で何をしてよいかは定めていません。RQ-018は命令と観測を分けますが、対話の拡張点の効果は扱っていません。

**満たさない場合の失敗.** 任意スクリプトを正本へ入れると、宣言された効果と実際の効果が一致せず、権限・監査・再現の境界が失われます。逆に拡張点を一切持たないと、小さな案件差分のたびに生成器を分岐させ、生成器が増えます。

**確認方法.** 行レベルの検証、導出項目、参照入力の補助を、フック宣言と規則Pluginで表し、同じ入力に同じ結果を返すことを確認します。宣言していない能力を呼ぶフックが、検証時と実行時の両方で拒否されることを確認します。フックの失敗が、拒否・不明・未実行のいずれかとして観測できることを確認します。

**非要求.** 任意のJavaScriptや汎用プログラミング言語の埋込みは要求しません。フックの記述言語を一つに固定することも要求しません。フックが外部システムへ直接副作用を起こす権限を持つことは要求しません。

### RQ-C3 業務上の暦・会計期間・税・通貨・採番を、適用期間と評価時点を持つ宣言された意味として扱えること

**要求.** 業務上の暦（営業日、休日、年度・月度の開始、締め）、税（適用日、税区分、率、端数処理）、通貨（適用日、率の種類、換算の方向）、採番（対象、範囲、形式、連続性の保証）を、実行時関数の暗黙の呼出しではなく、適用期間と評価時点を持つ宣言として扱えるようにします。案件固有の規則は、Coreを変更せずに、データまたは提供元として差し替えられるようにします。

**なぜ必要か.** X-TEAの`Session`は、これらの計算を標準で提供し、生産性の大半を支えました。しかし規則がコードと標準表に埋まり、適用期間・端数処理・例外が意味として宣言されませんでした。TEIが同じ生産性を引き継ぐには、規則を意味として持ち、適用期間と評価時点で検証できる必要があります。

**満たさない場合の失敗.** 暦・税・通貨の規則が案件コードや実行時関数に埋まると、改正日の前後で結果が変わることを試験できず、年度替わりや税率改正のたびに個別の修正が必要になります。採番の連続性・欠番の扱いも、契約として宣言できません。

**確認方法.** 適用期間の境界（改正日、年度替わり）を含む入力で、同じ評価時点から同じ結果を返すことを確認します。案件固有の暦・税率を、Coreの変更なしに差し替えられることを確認します。採番の一意性・連続性・欠番の扱いを、契約として試験します。

**非要求.** すべての国の法制度へ対応することは要求しません。税・通貨の計算をCoreへ固定することは要求しません。最初から四つすべてを製品の約束にすることを要求せず、暦・会計期間から始める段階的な受容を許します。

## 4. 要求にしないもの

| 対象 | 理由 |
| --- | --- |
| X-TEAの8機能型と同じ型を製品が持つこと | 互換の再現は目的にしない。型はパッケージで表す |
| `.xead`/`.xeaf`の書式の読み書きを製品の約束にすること | 外部の書式。取込みは候補として扱う |
| 画面の座標・フォント・余白を正本で指定できること | 実行先を変えると再設計になる |
| 更新カウンタ列がすべての表にあること | 実現の一つであり、既存DBにない場合の縮退を宣言する |
| 任意SQLの実行を利用者へ公開すること | 意味の検証・認可・観測を迂回する |
| 旧Runtimeの画面・帳票の見た目を再現すること | 表示の忠実さは別の要求と検証で扱う |
| 手引書・参照モデルの内容を製品文書へ転載すること | 利用条件の確認は[#941](https://github.com/hat47x/tei-platform/issues/941) |

## 5. 採用の手順

1. この文書の候補を、[受容アーキテクチャ](../plan/design/XTEA_LOWCODE_RECEPTION_ARCHITECTURE_2026-11.md)の設計判断と照合する。
2. `RQ-C1`〜`RQ-C3`の採否と、既存要求へ追加する受入条件（AC-1〜AC-11）の範囲を、人が決める。
3. 採用する場合は、`TEI_PRODUCT_REQUIREMENTS.md`の該当箇所を変更し、この文書は根拠の記録として残す。要求本文をこの文書へ複製しない。
4. 受入条件は、[移行計画](../plan/XTEA_LOWCODE_TRANSFER_PLAN_2026-11.md)の作業パッケージと検証へ結び付ける。
