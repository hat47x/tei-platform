# TEI製品要求の読み方

この文書は、[`TEI_PRODUCT_REQUIREMENTS.md`](TEI_PRODUCT_REQUIREMENTS.md)に定めた製品要求を、全体の目的から個々の要求へ順に理解するための案内です。

製品要求の正本は`TEI_PRODUCT_REQUIREMENTS.md`です。この案内では要求を追加・変更しません。

`requirements/`には、製品が満たすべき要求を置きます。要求をどの順序で確かめ、どの受入シナリオや根拠へ結び付けるかは[開発計画](../plan/README.md)で管理します。要求本文を計画へ移さず、要求別の実証状況は[検証根拠の一覧](../plan/evidence/README.md)から確認してください。

TEIの要求は、業務モデル、データベース、実行先、実行環境、安全性、生成AI、業務手順など多岐にわたります。要求番号の順序だけでは相互の関係が分かりにくいため、ここでは何を守るための要求なのかに沿って整理します。

現在の要求では、主に業務システムを例に説明しています。TEIの適用先は業務システムだけではありません。分野固有の知識と技術を分けて管理することが役立つ、ほかの分野も対象とします。

## 1. まず一つの流れとして見る

TEIの要求は、おおむね次の一連の流れを守るためにあります。

```text
業務上の意味を定義・拡張する
        ↓
既存の知識・実装へ結び付ける
        ↓
アプリケーション、データベース、実行先へ具体化する
        ↓
明示された権限で実行する
        ↓
外部で実際に起きたことを観測する
        ↓
検証根拠をもとに設計や実装を改善する
```

この一連の流れで、意味、実装、権限、観測結果を区別することがTEIの基本です。

たとえば、次の四つは似ていますが別です。

```text
「受注を登録する」という業務上の意味
        !=
ウェブ画面で登録するという実現方法
        !=
その処理を実行できる権限
        !=
実際に外部データベースへ登録されたという観測結果
```

これらの区別を保つため、複数の要求が関係し合います。

これらの要求は、個人、組織、社会に提供する価値を、製品の機能によって支えるためのものです。目指す価値は[`TEI_PRODUCT_VALUE.md`](../product/value/TEI_PRODUCT_VALUE.md)で説明しています。

## 2. 要求群を九つのテーマで読む

### A. 意味を実装から守る — RQ-001〜004

この領域では、業務上の意味をファイルの場所、SQL、Go、データベース製品、画面などに固定しないことを要求します。

主な失敗例は、次のようなものです。

- ファイルを移動しただけで別の業務概念になってしまう
- 生成物がいつの間にか第二の正本になる
- SQLや既存Go実装をTEI利用のためだけに書き直す
- 複数の情報源から同じ意味を推測して統合し、どれを基準にすべきかわからなくなる

次の要求が対応します。

- **RQ-001** — 業務上の意味を実装技術から独立して保持する
- **RQ-002** — 記述元と正本となる意味を追跡する
- **RQ-003** — 暗黙の複数正本を作らない
- **RQ-004** — 既存形式の資産を元の形式のまま利用する

ここでいう正本は、特定の画面やデータベース製品に依存せず、TEIが基準として扱う意味です。

### B. アプリケーションと実装を安全に組み立てる — RQ-005〜009

業務システムでは、一つのアプリケーションが複数のデータベースや外部機能を利用し、既存システムと段階的に共存することがあります。

この領域では、アプリケーション、データベース、提供元、機能をそれぞれ扱い、必要に応じて組み合わせられることを求めます。

主な失敗例は次のとおりです。

- アプリケーションの配布版とデータベースの配布版を常に一対一に固定する
- 実際のデータベースの情報が不足している状態を「差分なし」と判断する
- PostgreSQLや特定クラウドの仕様が中核へ広がり続ける
- 標準認証へ移行できない既存システムをTEI対象外にしてしまう

次の要求が対応します。

- **RQ-005** — アプリケーションとデータベースを多対多で扱う
- **RQ-006** — 期待状態 / 実際の状態 / 差分 / 未解決を分ける
- **RQ-007** — 提供元固有知識を中核へ無制限に持ち込まない
- **RQ-008** — 機能ごとで実装を入れ替える
- **RQ-009** — 既存認証・認可仕様を保持した移行を可能にする

### C. 設計を多面的に見て、実装前に検証する — RQ-010〜014

TEIでは、設計を一つのフォームや図だけで表現しません。

同じ意味を表、関係図、流れ図、画面、自然言語などから確認し、実行可能な部分をドライバーで早期に試します。

主な失敗例は次のとおりです。

- 編集画面で表現できるものだけが中核の概念になる
- ウェブ画面の都合が正本となる意味を決める
- 実装が終わるまで設計矛盾に気づけない
- 検索や記録等の頻出構造を毎回ゼロから作る

次の要求が対応します。

- **RQ-010** — 高密度な編集画面
- **RQ-011** — 同じ意味を用途別に表す方法
- **RQ-012** — 実行役による設計検証
- **RQ-013** — 実行先に依存しない表示や操作
- **RQ-014** — アプリケーションの型の再利用

用途別の表現は、同じ意味を異なる形で示す方法です。読みやすさや編集しやすさを高めますが、それ自体を別の正本にはしません。

### D. AIを「自由な生成器」ではなく設計支援へ使う — RQ-015〜017

TEIでは、既存の知識を探索してから必要な部分を提案・生成する流れを基本とします。

まず既存の意味に関する資産、型、規則、機能を探して候補を絞ります。それでも不足する部分について、新しい提案を作ります。

主な失敗例は次のとおりです。

- 同じ業務上の意味をAIが毎回違うコードとして再生成する
- AI提案が確認を経ずに正本へ書き込まれる
- 過去に回答済みの確認を繰り返す
- AIの自律度に応じて、書き込み、秘密情報、ネットワークの権限まで広げる
- 同じ情報を意味モデル、生成ファイル、AIの記憶へ人が二重・三重管理する

次の要求が対応します。

- **RQ-015** — 既存知識を探索してから新規実装へ進む
- **RQ-016** — AIの確認提案を必要な範囲にとどめ、履歴を残す
- **RQ-017** — 人の二重管理を最小化する

現在検討している設計案の統合では、この要求群を次の流れへ発展させることを考えています。

```text
複数の設計候補を作る
        ↓
既存定義・制約・他ビューで候補を絞る
        ↓
必要な部分だけlocal LLMで比較・統合する
        ↓
人が意味上の選択を受理する
        ↓
実装・テストを可能な限り再生成する
```

ただし、正式な要求の追加・変更は、参照資料による検証根拠を得てから判断します。

### E. 実行・権限・観測を分ける — RQ-018〜020

設計が正しくても、実行時に権限が広がったり、副作用を二重実行したりすれば安全な業務基盤にはなりません。

主な失敗例は次のとおりです。

- 命令が受理されたことを、外部状態が変わった証拠にする
- 拡張機能が機能を知っているだけで実行権限も得る
- 秘密情報やネットワーク接続先を正本へ保存する
- 実行環境の引継ぎ後も古い実行環境が操作を続ける
- 外部プロセスの状態が不明だから同じ処理を自動再実行する

次の要求が対応します。

- **RQ-018** — 命令と観測を分ける
- **RQ-019** — 実行時の権限と資源を明示的に制約する
- **RQ-020** — 再実行・引継ぎ・不明を安全に扱う

安全性や実行環境の具体的な説明は[`../docs/security.md`](../docs/security.md)を参照してください。

### F. 実際の根拠に沿って製品について述べる — RQ-021〜026

この要求群では、TEI自身の設計や評価方法について定めます。

参照実装や実験が成功しても、それだけで本番運用に対応した製品とは言えません。また、業務手順、データ、機能など、いずれか一つの視点だけで業務全体を説明したことにもなりません。

主な失敗例は次のとおりです。

- 小さな試験用データで動いた結果を本番環境保証へ広げる
- 実験用の基盤の成功率をTEIのKPIへそのまま転記する
- 一つの実行先で速かったからすべての実行先へ同じ性能条件を課す
- アプリケーションの機能に現れない手作業や外部作業を業務モデルから消す
- データ、機能、業務の矛盾を別々の文書で見逃す

次の要求が対応します。

- **RQ-021** — 参照用資料と準拠確認で再現可能性を示す
- **RQ-022** — 完成製品と設計検証段階を区別する
- **RQ-023** — 一人でも維持可能な構造を保つ
- **RQ-024** — 性能要求を実行先ごとに検証可能にする
- **RQ-025** — 業務上の操作や手順をアプリケーションの機能から独立して扱う
- **RQ-026** — データ、機能と操作、業務手順を相互検証する

RQ-025 / RQ-026は、[`BUSINESS_SYSTEM_DESIGN_REQUIREMENTS.md`](BUSINESS_SYSTEM_DESIGN_REQUIREMENTS.md)で、もう一段具体的に解釈しています。

### G. 人とAIが長く一緒に開発し、業務を続ける — RQ-027〜030

生成AIが実装や業務の一部を担うようになると、一度作れるかだけでなく、数か月後に別のAIや担当者が安全に作業を引き継げるかが重要になります。

この領域では、アプリケーションの知識を会話履歴や特定の人の記憶へ閉じ込めず、人とAIが同じ正本から理解・承認・再利用・業務遂行を続けられることを要求します。

主な失敗例は次のとおりです。

- 前回のAIとの会話履歴が無いと、アプリケーションの意味や過去の決定を誰も再構成できない
- 人が生成コードの全量を読めないまま承認し、承認が形だけになる
- 別アプリケーションへ意味を複製した結果、元と先が黙って分岐する
- AIエージェントが業務手順を読めることを理由に、外部へ副作用を起こす権限まで持つ
- AIが命令を出したことを、業務が完了したことと読み替える

次の要求が対応します。

- **RQ-027** — AIが長期間にわたりアプリケーションへ再入場できる開発時の文脈を提供する
- **RQ-028** — 人間が実装詳細を全面的に読まずに変更を理解・承認できる
- **RQ-029** — 業務や基盤の知識を適用条件付きで再利用・移植する
- **RQ-030** — AIエージェントがTEI成果物を業務遂行の業務知識として利用する

この要求群は、個人の引継ぎや実質のある承認、組織の知識資産の再利用、人による監督や権限管理に関する社会的な価値につながります。RQ-030の業務遂行にも、RQ-018〜RQ-020で定める命令、観測、権限、不明状態の境界を適用します。この要求群の一部は、まだ要求段階にあり、価値が実証されたことを示すものではありません。RQ別の実証状況は[`PRODUCT_REQUIREMENT_GAP_AUDIT.md`](../plan/evidence/PRODUCT_REQUIREMENT_GAP_AUDIT.md)が正本です。

### H. 中核の語彙を拡張できるようにする — RQ-031〜033

TEIでは、データモデルも含め、現在あるモデル体系を将来のすべてのアプリケーションへ強制しません。中核が持つべきなのは業務概念の網羅ではなく、新しい意味を既存の意味と関係付け、衝突を検出し、複数の表現や実装へ接続できる共通機構です。

主な失敗例は次のとおりです。

- データモデルを唯一の上位モデルにし、行為・操作・手順等を無理に従属させる
- 拡張機能がコードは追加できても意味を宣言できず、編集画面やAIから不透明な固有実装になる
- 拡張の版、依存関係、互換範囲が分からず、同じ名前空間の意味が知らないうちに変わる
- 拡張同士の競合を読み込み順で黙って解決する
- AIが既存の意味拡張を発見できず、同じ概念や規則をアプリケーションごとに再実装する
- 情報不足や複数候補をAIが暗黙に一つへ決める

次の要求が対応します。

- **RQ-031** — 特定のモデル体系に中核で優先権を与えない
- **RQ-032** — 拡張機能や定義言語で意味の規則を宣言・合成する
- **RQ-033** — AIとツールが意味拡張を実装のレールとして利用する

この要求群は、実装の差し替えにとどまらず、意味体系そのものを後から追加し、既存の意味と矛盾なく扱える拡張性を求めます。生成AIは、その拡張を探索・合成・検証することで、毎回ゼロから設計判断をやり直す範囲を減らします。


### I. 開発環境を囲い込まない — RQ-034

生成AIを開発に使う場合も、作業環境をTEI専用の実行基盤に限りません。ChatGPTなどの対話型実行環境、Codex、Claude Code、一般的な統合開発環境、コマンドライン、自動確認の仕組みからリポジトリを扱える構成を目指します。

重視するのは、どのツールが編集したかをTEIへ細かく記録することではありません。各環境がソースを理解し、編集し、必要なビルドや試験まで行い、その結果をGitなどの標準的な経路で受け渡せることです。統合後は、元の対話やエージェントを必要とせず、正本となるソースから業務上の意味を再構築できなければなりません。

主な失敗例は次のとおりです。

- TEIを編集するために特定のエージェント連携機能や対話画面が必須になる
- AIがソースを編集する前に、すべての変更をTEI独自の提案形式へ変換しなければならない
- GitやCIが持つ作業状態をエージェントの作業記録や再開地点、検証状態等としてTEIへ二重管理する
- Gitで扱える変更にもTEI独自の変更記録を必須にする
- MCP経由の操作だけに特別な意味上の権限を与える
- 対話型の実行環境でMCPを使うという理由だけで、TEI専用のMCPサーバーを必須にする
- 開発環境のシェルやファイル操作の権限と、アプリケーション実行環境の権限を混同する

次の要求が対応します。

- **RQ-034** — 一般的な開発環境からTEIを改修・実行・検証できる

RQ-034はRQ-015やRQ-027を置き換えません。RQ-015はAIが何を参照して実装するか、RQ-027は後から再入場するための開発時の文脈を扱います。RQ-034は、それらを利用する開発環境を特定のエージェント製品やTEI専用の作業手順へ固定しないための境界です。対話環境側がMCPを利用する場合も、まず実行環境が持つシェル、ファイル操作、Gitの連携機能などからTEIのコマンドラインを呼べればよく、TEI固有MCPは追加価値が確認された場合の任意の連携方法です。

## 3. 一つの受注例で要求のつながりを見る

たとえば「顧客を選び、複数の明細を持つ受注を登録する」という業務を考えます。

```text
業務上の意味
  受注は明細を複数持つ
  顧客は既存のマスタから参照する
  数量は正の値とする
        ↓
アプリケーション
  記録 + 親子明細 + 参照
        ↓
データベース
  受注データベースは読み書き可能
  顧客マスタは読み取り専用
        ↓
実行先
  ウェブでは受注明細を編集できる
        ↓
実行環境
  認可された利用者だけが登録機能を使う
        ↓
観測
  登録後の実際の状態を必要に応じて確認
```

この一例でも、複数要求が関係します。

- 顧客マスタのファイル位置が変わっても顧客の意味を変えない — RQ-001 / 002
- 顧客マスタへ書き込みしない — RQ-005 / 019
- 読み取り専用のデータに編集画面を提案した場合は複数の観点で検出する — RQ-013 / 026
- 親子明細を既存型から再利用する — RQ-014
- AIは既存の受注や顧客の構造を探してから設計案を作る — RQ-015
- `quantity > 0`から失敗を確認する試験を導出する余地を持つ — RQ-015 / 017 / 021に接続する設計課題
- 命令の成功だけで登録完了としない — RQ-018

RQを単独のチェック項目として見るより、同じ業務シナリオの中でどの失敗を防ぐ要求かを見る方が、設計判断へつなげやすくなります。

## 4. 要求を読むときの注意

### 要求は実装方式を固定しない

たとえば「古くなったAIの提案を黙って適用しない」という要求があっても、特定の版を記録する仕組みや競合の解決方法を要求しているとは限りません。

製品要求では、まず守るべきことを定めます。具体的な方式は構成、設計判断記録、参照資料で比較します。

### 要求があることと、実装済みであることは別

```text
製品要求がある
  != 実装が完了している
  != 参照用資料による検証根拠が得られている
  != 本番利用できる
```

現在の実装範囲は[`../docs/status.md`](../docs/status.md)を参照してください。

### 「未解決」は要求違反とは限らない

上流設計では、情報が不足している場合に`不明`や`未解決`を保持することがあります。

根拠のない値で空欄を埋めるより、何がわかっていないかを明示する方が安全です。何を満たせば判断できるかは参照用や計画上の課題記録で具体化します。
