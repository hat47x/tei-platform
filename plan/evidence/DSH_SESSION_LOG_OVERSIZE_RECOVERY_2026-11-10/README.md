# 上限を戻すと凍っていたLogが1要求でまとめて届く（2026-11-09/10、#2515 H6-E2）

- 対象Issue: [#2515](https://github.com/hat47x/tei-platform/issues/2515)の`H6-E2`と`#2509`の経路網羅。機密境界の正本は[TAI #232](https://github.com/hat47x/tai-pleroma/issues/232)。
- 実行日: 2026-11-09〜10（Asia/Tokyo）
- 実行環境: Windows 11 Pro `10.0.26100`（AMD64）、DSH `0.2.2-rc.1`（`dsh --profile headless`）、Node `24.21.0`
- 状態: **ローカルMock Endpointのみ**。実Providerへの送出は**NOT RUN**。
- 先行記録: [上限を超える単一event](../DSH_SESSION_LOG_OVERSIZE_EVENT_2026-11-09/README.md)。本記録は、そこで未確定とした「**上限を戻した再実行で回復するか**」を埋める。

## 1. 何をしたか

1. **Run 1**: `maxBytes`を**4096**にし、**約8,000 bytesの`pwsh`出力**を1回、その後に小さな呼び出しを5回強制した（拡張が消える条件を再現する）。
2. **Run 2**: **同じSessionを再開**し、**上限を既定（8 MiB）に戻して**続けた。
3. 各要求で**`dsh_session_log` fieldの有無**と**水位（`afterSeq`→`throughSeq`）**を数えた。

## 2. 観測した結果

### Run 1（上限4096）: 拡張が消え、水位が止まる

| 要求 | 拡張 | event数 | 水位 |
| --- | --- | --- | --- |
| 001–003 | **あり** | 10/10/2 | `-1`→`9`→`11` |
| **004–010** | **なし** | — | — |

- 10要求のうち**拡張ありは3**、**なしは7**。**水位は`11`で凍った**。
- 送れたのは**22 event**、合計**606,472 bytes**。

### Run 2（上限を既定へ）: 凍っていた分が1要求で届く

| 要求 | 拡張 | event数 | 水位 |
| --- | --- | --- | --- |
| **011** | **あり** | **86** | **`11`→`97`** |
| 012 | あり | 8 | `97`→`105` |
| 013 | あり | 8 | `105`→`113` |
| 014 | あり | 11 | `113`→`124` |
| 015 | あり | 8 | `124`→`132` |

- **最初の1要求で86 eventが一度に届いた**。水位は**`11`から`97`へ一気に進んだ**。
- その後は通常の配送に戻った（8〜11 eventずつ）。
- Run 2の合計は**5要求・121 event・535,264 bytes**。

### 合計

| 実行 | 要求数 | 拡張あり | 送出event | 合計bytes |
| --- | --- | --- | --- | --- |
| Run 1（4096） | 10 | 3 | 22 | 606,472 |
| Run 2（既定） | 5 | **5** | **121** | 535,264 |

- **Run 2だけでRun 1の5.5倍のeventが届いた**。**Run 1で止まっていた分が失われていない**ことが分かる。

## 3. この記録が示すこと

- **上限を戻せば回復する**。凍っていた分は**失われず、1要求のburstとして戻る**。
- したがって**`maxBytes`は恒久的な抑止ではない**。単一eventが上限を超えて拡張が消えた場合も同じで、**設定を戻せばまとめて送出される**。
- **止まっている間もLogは記録され続けている**（Run 2で86 eventが戻ったことがその証拠）。
- 機密の観点では、**「上限を小さくして止めた」状態は、上限を戻した瞬間に一括で外へ出る**。

## 4. この記録が示さないこと

- **Telemetry（OTel）・UI・別flag**での検知（[停滞の可視性](../DSH_SESSION_LOG_STALL_VISIBILITY_2026-11-09/README.md)は3面で警告が出ないことを確認済みだが、本記録の形が他の面に出るかは未確認）。
- **burst の上限**（86 event が1要求に収まったが、それ以上で分割されるか）。
- `maxRequestBytes`（Telemetry側、既定4,000,000）との関係。
- **他版で同じ挙動になるか**（この版の観測であって契約ではない）。
- `H6-E2`の合否、機密Profile適合、Owner受理、#1119のGate。

## 5. 生データ

| ファイル | 内容 |
| --- | --- |
| `recovery.json` | `sessionId`、`run1`（overlay・要約・10要求のbyte数/SHA-256/拡張の有無/event数/水位/最大event bytes）、`run2`（overlay・要約・5要求の同項目）、`recovered`・`burstEventCount` |

生の要求bodyはコミットしていない。**合成のみ**（`BIGEVENT_START`/`x`の繰り返し/`BIGEVENT_END`・`SMALL_EVENT_TAIL`）。

再現する場合の要点:

```sh
# Run 1: maxBytes 4096 で大きい結果を出し、その後も呼び出しを続ける
python mock_provider_bigevent2.py 8799 <record-dir> 8000
dsh --profile headless --patch <maxBytes 4096> ... --json "Big then several small."
# Run 2: 同じ Session ID で、上限を既定に戻して再開する
dsh --profile headless --session-id <id> ... --json "Continue with the default cap."
```

- **Run 2 は Run 1 と同じ作業ディレクトリで実行する**。別ディレクトリだと`session ... was recorded in ...`で拒否される。
- 判定は**`dsh_session_log` fieldの有無**と**水位の前進**で行う。

## 6. `H6-E2`への含意（判断はしない）

`maxBytes`を小さくしても**送出は止まるだけで、記録は残り、上限を戻せば一括で出る**。単一eventが上限を超える場合も同じである。したがって**「上限を下げておけば安全」という扱いはできない**。機密Profileで送出を抑えるなら、**上限値ではなく送出そのものを止める手段**と、**止まっていることを観測できる面**が必要になる。どの統制を採るかは#2515とTAI #232のOwner判断であり、本記録は判定しない。
