# 行スコープのフックが値の三状態を潰す問題（設計判断、2026-11-17）

## 対象

- `internal/hook/rows.go` の `narrowTo`・`Runner.Rows`
- `internal/semantic/validationeval/reading.go` の `ValueState`（`present`／`null`／`not-fetched`）と `Coverage`
- `internal/currencyrate/granularity.go`・`internal/businesscalendar/holiday_binding.go` など「行は呼出し側が渡す」既存の役割結合

## 見つけたこと

独立レビューが、行スコープのフック入口を配線したときに意味が後退する点を指摘した。

`hook.Runner.Rows` の型は `[]map[core.CanonicalID]string` である。`narrowTo` は宣言した `reads` のうち**行に無いキーを単に落とす**。

```go
func narrowTo(row map[core.CanonicalID]string, declared []core.CanonicalID) map[core.CanonicalID]string {
	out := map[core.CanonicalID]string{}
	for _, attribute := range declared {
		if value, ok := row[attribute]; ok {
			out[attribute] = value
		}
	}
	return out
}
```

したがって次の2つが**同じ結果**になる。

| 実際の意味 | 渡された行 | フックが見るもの |
| --- | --- | --- |
| その行は値を**持たない**（NULL） | `map[]`（キー無し） | 「読んでいない」 |
| その行について**読んでいない** | `map[]`（キー無し） | 「読んでいない」 |

一方、リポジトリには値の三状態を明示する既存の契約がある。

- `ValuePresent`: 読んだ、値がある
- `ValueNull`: 読んだ、値が無い
- `ValueNotFetched`: 読んでいない（空かどうかも不明）

`Coverage` も `complete`／`partial` を持ち、「一部の行しか読んでいない」ことを表せる。**行スコープの入口は、この区別を持ち込む前の型でできている。**

## なぜ問題か

行スコープのフックは「その行の値を見て判定する」ものなので、**NULL と未読を取り違えると判定が変わる**。

- 「値が無いから不成立」と「読んでいないから判定しない」は別の結論であり、`hook.NotSatisfied`（業務上の不成立）と `NotEvaluated`（前提が欠けて評価しない）に分かれるべきもの。
- 現状はどちらも「キーが無い」になるため、**不成立として拒否するか、未評価として飛ばすかを実装が選べない**。

これは D-9 の変種である。**宣言（`reads`）はあるが、その宣言が指す値の状態を表現できない。**

## 選択肢

### A. 行の型を `map[core.CanonicalID]ValueState` 相当へ変える

行を `map[core.CanonicalID]string` から、値と状態の対へ変える。`ValuePresent` のときだけ `Value` を持つ。

- **利点**: `validationeval` と同じ語彙を共有でき、NULL と未読を区別できる。`Coverage` も一緒に渡せる。
- **欠点**: `internal/hook` の公開型が変わる。`currencyrate`・`businesscalendar` などの既存の「行は呼出し側が渡す」役割結合は `map[string]string` を前提にしており、**それら全部に波及する**（または両方の型を受け取る overload を持つ）。
- **コスト**: 中〜大。移行は機械的だが広い。

### B. 行ごとに「読んだ属性の集合」を別に渡す

行の値は `map[string]string` のまま、`ReadAttributes []core.CanonicalID` を別に渡す。`narrowTo` は「宣言 ∧ 読んだ」だけを残し、それ以外は `NotEvaluated` として区別する。

- **利点**: 既存の行の型を変えない。波及が `internal/hook` と入口に限定される。
- **欠点**: 「NULL」は依然表現できない（空文字と区別できない）。未読だけが救われる。
- **コスト**: 小。

### C. 何もしない（現状維持）と明記する

行スコープのフックは「渡された行にある値だけを見る。無い属性は未読として扱う」と契約に書き、NULL を表現しない。

- **利点**: 変更ゼロ。入口を配線する時点で意味を偽らない（曖昧さを契約として明示する）。
- **欠点**: 業務上の「値が無い」を表現できないため、NULL を不成立にしたい規則が書けない。
- **コスト**: ゼロ。

## 既定案: C（現状維持を契約として明記）＋ 入口を配線する前に B を検討

理由:

1. **まだ入口に本番呼出し元が無い。** 行を供給するデータ源自体が未実装なので、いま型を変えても**検証できない**（試験の合成行しか存在しない）。
2. **B は A の部分集合的な改善**であり、データ源の設計（どの列をどう読むか）が決まれば、必要な情報が「未読かどうか」だけで足りるか判断できる。先に A へ広げると、`currencyrate` などへの波及を**根拠なく**確定させてしまう。
3. 現状の曖昧さは、**契約として明記すれば危険ではない**。危険なのは「区別できると思って書かれた規則」である。

覆す条件:

- 行を供給するデータ源ができ、**NULL を不成立として扱う規則**が必要になったら B を実装する。
- 複数の役割結合（為替・休日・採番）が同じ三状態を要求し始めたら A を検討する。
- 参照実行で「値が無い」と「読んでいない」を取り違えた**誤判定が観測**されたら、直ちに B（または A）。

## いま明記しておくこと

`Runner.Rows` の契約に次を書く（このPRで実施）。

- 行は `map[core.CanonicalID]string` であり、**キーが無いことは「値が無い」ではなく「読んでいない」**を意味する。
- したがって行スコープのフックは、**値の不在を業務上の不成立として扱えない**。不在は未評価として扱う。
- NULL を表現する必要が出たら、行の型を変える（上記 B または A）。

## 読み取れないこと

- 実データ源が行をどう供給するか（列の欠落を NULL として渡すか、そもそも渡さないか）。
- `Coverage`（全件読んだか一部か）を行スコープのフックへどう渡すか。現状は渡す口が無い。
- X-TEA の旧 Runtime が「値が無い」をどう扱っていたか（画面ごとの実装依存で、宣言として残っていない）。

## 位置付け

設計判断であり、実装は未了。**行の供給源が未実装のため、この問題は現時点で観測不能**である。契約の明記（C）のみ行い、B/A は覆す条件が満たされた時点で判断する。仮承認。
