# 溜まったLogは243 event・375KBでも1要求でまとめて届く（2026-11-09/10、#2515 H6-E2）

- 対象Issue: [#2515](https://github.com/hat47x/tei-platform/issues/2515)の`H6-E2`と`#2509`の経路網羅。機密境界の正本は[TAI #232](https://github.com/hat47x/tai-pleroma/issues/232)。
- 実行日: 2026-11-09〜10（Asia/Tokyo）
- 実行環境: Windows 11 Pro `10.0.26100`（AMD64）、DSH `0.2.2-rc.1`（`dsh --profile headless`）、Node `24.21.0`
- 状態: **ローカルMock Endpointのみ**。実Providerへの送出は**NOT RUN**。
- 先行記録: [上限を戻した回復](../DSH_SESSION_LOG_OVERSIZE_RECOVERY_2026-11-10/README.md)。本記録は、そこで未確定とした「**burstの上限**」に着手した結果である。

## 1. 何をしたか

1. **Run 1**: `maxBytes`を**256**にして、**30回の`pwsh`呼び出し**（各約1,500 bytesの出力）を強制した。この上限では**最初から拡張が付かない**ため、Logが溜まり続ける。
2. **Run 2**: **同じSessionを既定の上限（8 MiB）で再開**し、溜まった分がどう届くかを見た。

## 2. 観測した結果

### Run 1（上限256）: 32要求すべてで拡張なし

| 項目 | 値 |
| --- | --- |
| 要求数 | **32** |
| 拡張あり | **0** |
| 送出event | **0** |
| 合計bytes | 2,809,857 |

- **1件も送られていない**。Logは溜まる一方である。

### Run 2（既定の上限で再開）: 1要求で243 eventが届いた

| 要求 | 拡張 | event数 | 水位 | 要求bytes | 最大event |
| --- | --- | --- | --- | --- | --- |
| **033** | **あり** | **243** | **`-1`→`242`** | **375,623** | **21,297** |
| 034〜063 | あり | 8ずつ | 242→482 | 142,132〜224,510 | 2,928〜2,930 |

- **最初の1要求で243 event・375,623 bytesがまとめて届いた**。**分割されていない**。
- 水位は**`-1`から`242`へ一気に進んだ**（Run 1では一度も進んでいなかった）。
- その中に**21,297 bytesのevent**（`request/header`）が含まれる。**上限256を大きく超えるeventも、溜まった後なら一緒に送られる**。
- その後は**8 eventずつ**の通常配送に戻った（30要求で240 event）。

### 合計

| 実行 | 要求数 | 拡張あり | 送出event | 合計bytes |
| --- | --- | --- | --- | --- |
| Run 1（256） | 32 | **0** | **0** | 2,809,857 |
| Run 2（既定） | 31 | **31** | **483** | 5,875,069 |

- **Run 2だけで483 eventが届いた**。Run 1で1件も送られていなかった分が**すべて戻っている**。

## 3. この記録が示すこと

- **243 event・375,623 bytesのbacklogが1要求で届いた**。**この範囲では分割されない**。
- **Run 1で一度も送られなかった分が、Run 2で全部戻った**。**取りこぼしは無い**。
- **単一eventが上限を超えていても、溜まった後なら一緒に送られる**（21,297 bytesのeventが含まれた）。
- 機密の観点では、**「小さい上限で止めていた」間に溜まった分が、上限を戻した1要求でまとめて外へ出る**。

## 4. この記録が示さないこと

- **243 event・375KBを超える場合**。本記録はその範囲までしか試していない。**「上限が無い」とは言えない**。
- `maxRequestBytes`（Telemetry側、既定4,000,000）との関係。
- **Telemetry（OTel）・UI・別flag**での検知。
- **他版で同じ挙動になるか**（この版の観測であって契約ではない）。
- `H6-E2`の合否、機密Profile適合、Owner受理、#1119のGate。

## 5. 生データ

| ファイル | 内容 |
| --- | --- |
| `burst.json` | `sessionId`、`run1`／`run2`の要約、`burst`（要求ファイル・event数・bytes・水位・最大event・`split: false`）、63要求のbyte数・SHA-256・Tool数・メッセージ数・Session ID・拡張の有無・event数・水位・最大event bytes |

生の要求bodyはコミットしていない。**合成のみ**（`BK<n>_` + `y`の繰り返し）。

再現する場合の要点:

```sh
# Run 1: maxBytes 256 で 30 回の呼び出しを強制し、Logを溜める
python mock_provider_backlog.py 8799 <record-dir> 30 1500
dsh --profile headless --patch <maxBytes 256> ... --json "Build a large backlog."
# Run 2: 同じ Session ID・同じ作業ディレクトリで、既定の上限で再開する
dsh --profile headless --session-id <id> ... --json "Drain the backlog with the default cap."
```

- **上限256では最初から拡張が付かない**ため、Run 1は「1件も送らない」状態になる。
- **Run 2 は Run 1 と同じ作業ディレクトリ**で実行する（別ディレクトリは拒否される）。
- 判定は**1要求あたりのevent数**と**水位の進み方**で行う。

## 6. `H6-E2`への含意（判断はしない）

`maxBytes`を小さくして止めても、**溜まった分は上限を戻した1要求でまとめて出る**。本記録では**243 event・375,623 bytes**が1要求に収まり、**分割も取りこぼしも無かった**。したがって**「上限を下げておけば少しずつしか出ない」という扱いはできない**。機密Profileで送出量を抑えるなら、**上限値ではなく送出そのものを止める手段**と、**止まっていることを観測できる面**が必要になる。どの統制を採るかは#2515とTAI #232のOwner判断であり、本記録は判定しない。
