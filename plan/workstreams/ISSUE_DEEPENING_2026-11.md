## 3. 見つかった三つの構造問題

### 3.1 台帳の状態が本文に埋もれている

同じ課題の中で、「未完了」「統合済み」「再開済み」が本文の複数箇所に書かれ、どれが現在かを読者が判断できません。

- #993 は「当面の統合完了。Issueをクローズし、Publicリポジトリ化が完了するまで再開しない」と書きながら、オープンのままです。
- #1161 は「残存証拠確認のためopen」と書き、本文の大半は当時の未マージ前提の手順です。
- #69・#214 は本文の冒頭で、下の記述が履歴であり現在の状態ではないと断っています。訂正が必要になったこと自体が、状態の置き場所が本文しかないことの結果です。

`docs/status.md` が実装状況の正本であるという規則はありますが、課題からそこへ戻る導線が一様ではありません。この問題は #2309（文書中の識別子の実在検査）の範囲を広げた「課題の状態の実在検査」として扱うべきです。

### 3.2 製品の主張と実装がずれている（検証できる例）

`internal/knowledgecontext/data_design_candidate_review.go` は、データ設計の候補を確認する経路で、次の理由を返します。

```text
current-core-has-no-first-class-functional-dependency-authoring-contract
```

しかし `internal/syntax/semantic_business_rules.go`（2026-10-13、#1126）が `candidate-key` と `functional-dependency` の宣言を実装し、`internal/validation/semantic_business_rules.go` が検証を追加しています。この理由文は 2026-10-11 以降更新されていません。つまり、**中核が関数従属性の宣言を持たない**という主張は、現在の `main` では成り立ちません。

同じずれが `docs/status.md`（整理日 2026-10-31）にもあります。候補キー・関数従属性の宣言と検証は、実装状況の表に現れません。

これは「文書が古い」というより、**主張の真偽を機械で確かめる経路がない**という問題です。#2309 は文書中の識別子の実在を検査する課題ですが、対象を「識別子」から「否定の主張」へ広げる価値があります。少なくとも、コードに埋め込まれた `*-not-*` 形式の非主張は、実装の変更で偽になり得るため、定期的に再評価する対象です。

確認手順（誰でも10分で再確認できます）。

```sh
git log --diff-filter=A --date=short --format='%ad %h %s' -1 -- internal/syntax/semantic_business_rules.go
git log --date=short --format='%ad %h %s' -1 -- internal/knowledgecontext/data_design_candidate_review.go
grep -rn 'has-no-first-class-functional-dependency' internal/
grep -n '候補キー\|関数従属' docs/status.md
```

1行目が 2026-10-13（#1126）、2行目がそれより前であれば、非主張のほうが古いことになります。3行目で該当箇所、4行目で `docs/status.md` の記載の有無を確認できます。

## 4. 深掘り対象の選定

### 4.1 基準

1. 製品の中心価値（意味から実装・検証へ）にどれだけ効くか。
2. 意味の層に宣言がなく、実行時にコードへ逃げているか（未確立の程度）。
3. 他の課題がこれを待っているか（下流のブロック数）。
4. 複数の課題を一つの抽象に束ねられるか。
5. 合成の作業領域で反証できるか（検証可能性）。

### 4.2 選定した5件

| 課題 | 1 価値 | 2 未確立 | 3 下流 | 4 抽象化 | 5 検証 | 選定理由（要旨） |
| --- | --- | --- | --- | --- | --- | --- |
| #1127 標準CRUD・検索・保守画面 | 高 | 高 | 高（#1124・#1130・#1803） | 高 | 高 | データを定義しただけでは業務画面が出ない（一覧にも Query とパターンの宣言が要る）。最初の利用者価値がここで止まる |
| #1129 効果規則・仮想項目 | 高 | 中 | 高（#1130・#2144・#1803） | 高 | 高 | 実行時の規則は設計済みだが、宣言と診断が無い。所有者越境の診断は未実装のまま明記されている |
| #1130 一括・帳票・無人実行 | 高 | 高 | 中（#2144・#2146） | 高 | 高 | サンプルで動いたが意味に戻っていない。P-JOB-01 は設計文書だけで、基盤の宣言と同定がない |

5件に共通するのは、**意味の層に宣言がないため、実行時のコードか運用に逃げている**という点です。どれも「機能を足す」話ではなく、「すでにコードでやっていることを意味へ戻す」話です。この性格が、抽象化（一つの導出契約で束ねる）と検証（合成の作業領域で反証する）の両方に向いています。

### 6.1 最初の一歩（半日〜2日）

迷わず着手できるように、最初にやることを一つに絞ります。

1. `internal/operations/surface.go` に、操作面の型（`Operation`・`Gap`・`Surface`）と、`data` と `persist` から `list`・`read` を導出する関数を書く。百行程度で足ります。
2. `internal/operations/surface_test.go` に、`reference/workspace` を読み込んで `sales.order` の `list`・`read` が出ることを確かめる試験を書く。期待値は `data` と `persist` の宣言から手で数えます（実データを使わない）。
3. `persist` が無いデータに対しては、成功ではなく `missing-input` の gap を返すことだけを守る。ここを空の成功にすると、後の段で何も検出できなくなります。
4. 動いたら W5（CLI）を足し、`tei commands` に `operation surface` を出す。ここまでで、他の担当が同じ導出を再利用できるようになります。

つまずいたときの判断: 一件参照のキーが決まらないデータが多い場合は、`read` の導出を後回しにし、`list` だけで W1 を閉じます（期間や効果の設計は `read` に依存しません）。

### 7.5 TAIシリーズとの接続

TEIの出力は、TAI Pleromaをはじめとする周辺の製品から読まれます。今回の設計が、その読み取りに効く点を三つに絞って記します。

1. **機械可読で版を持つ。** 操作面（`tei.cli.operation-surface/v0`）と導出成果物は、`schemaVersion` と規則の版を持ちます。これは #2354 で整備中の CLI の出力エンベロープと同じ形であり、受け取る側が版で判断できます。TAIの参照接続は TEI の `validate` の結果を読む経路を持っており（[reference-tei-model](https://github.com/hat47x/tai-pleroma/blob/main/tools/reference-tei-model/README.md)）、出力の形が揃っていることが前提になります。
2. **決定的である。** 同じ受理済みの意味と同じ規則から同じ結果が出ます。受け取る側が照合値で同一性を確かめられ、キャッシュや差分比較ができます。TAIの CP-2・CP-3 が、TEIの検証結果を固定した版へ結び付ける作業と整合します。
3. **正本を共有しない。** 操作面も成果物も読み取り専用で、TAI側に第二の正本を作りません。TAIの設計方針（中央のHostや共通DBを作らない）と衝突しません。

逆に、今回の設計で**やらない**こと。TAI側の契約をTEIへ取り込むこと、TAIの状態をTEIが持つこと、製品間の共通スキーマを先に固定すること。必要になった時点で、それぞれの製品の課題として扱います。

シリーズ内の役割分担にも触れます。操作面の `autonomy` は、そのまま製品間の受け渡しの材料になります。

- `unattended` の操作は、EKIへの委任の候補になります（範囲・期限・権限はEKI側の契約が決めます）。
- `human-gated` の操作は、SEIに判断の記録を残す対象の候補になります。
- 読み取り専用の操作面と導出成果物は、SHO（MMI）が扱う文書の参照先を指す材料になります。

いずれも**候補**であり、接続は各製品の課題で決めます。TEI側でEKIの委任契約やSEIの判断記録を作らない、という境界は変えません。

### 11.3 選定: A

理由。

1. 一往復の「標準Function / UIの即時実行」に直接効く。5件のうち、いま実装で前へ進められる唯一の段である。
2. 判断段階が A2 で、意味を増やさずに完了できる。`update` と `retire` を無理に導出せず、**未解決として理由を返す**ことが設計どおりの結果になる。
3. B は A の後がよい。成果物は「操作面の未解決」を載せるため、A の gap が先に確定しているほうが中身が濃くなる。
4. C は A の結果を材料にする。`create` が動き、`update` の不足が具体化してからでないと、マイルストーンの到達条件を足す判断ができない。

### 11.4 ゴールの完了条件

- `create` が、保存の宣言・キー・検証から導出される（入力、前提、効果、自律区分つき）。
- `retire` が、状態遷移の意図があるのにライフサイクルの宣言が無い場合に未解決として出る。
- `update` は、PoCの仮説H1（期待状態の比較）で導出される。仮説を変えた場合は `plan/workstreams/POC_HYPOTHESES_2026-11.md` を先に更新する。
- 参照用作業領域と合成の作業領域の両方で、正例と負例の試験が通る。
- `go test ./internal/operations` と `go test ./tools/repository-plan-check` が通る。
- 設計文書の実装状況を更新し、CLI 公開と新しい宣言は行わない（A4のまま）。
