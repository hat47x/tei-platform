# PoCの仮説と、上流へ戻る条件（2026-11）

- 状態: **仮説（採用判断ではない）**。PoCとして、判断が要る箇所は「もっともらしい案」を選んで先へ進み、課題が顕在化した時点で上流へ戻って直します。
- 対象: [標準CRUDの導出](../design/DERIVED_CRUD_OPERATION_DESIGN_2026-11.md)、[設計成果物の導出](../design/DERIVED_DESIGN_ARTIFACTS_DESIGN_2026-11.md)、[操作面の導出](../design/OPERATION_SURFACE_DESIGN_2026-11.md)
- この文書の役割: どの判断を仮説で選んだか、なぜそう選んだか、何を観測すれば誤りだと分かるか、誤ったときにどこへ戻るかを一か所に残す。

## 1. 進め方

```text
判断が要る箇所を見つける
        ↓
もっともらしい案を仮説として選ぶ（この文書に残す）
        ↓
実装し、試験と観測で確かめる
        ↓
反証条件に触れたら、上流（意味モデル・要求・契約・設計）へ戻る
        ↓
原因を分解して解消し、同じ形の箇所へ横展開する
```

上流へ戻るときは、原因を「対象（何を扱っているか）」「関係（何と何が結び付いているか）」「境界（どこまでが一つの意味か）」の三つに分けて見る方法（利用者の指示にある三要素分析法のような上流の分解手法）を使えます。方法そのものをこの文書で定義しません。**重要なのは、症状が出た箇所だけを直さず、同じ判断をした他の箇所へ同じ修正を広げること**です。

## 3. 各仮説の詳細

### H1 — 同時更新は期待状態の比較を既定にする

- 実装: `update` を常に導出し、`concurrency: expected-state` を付ける。呼出し側はキーと、読んだときの値（またはその照合値）を送り、一致した場合だけ書く。
- 観測: 後勝ちで消えた更新の件数（0であるべき）、比較のための入力サイズ、`update` が失敗する理由の内訳（不一致・権限・検証）。
- 反証: 比較の入力が実用にならない大きさになる、または「版番号で衝突を検出したい」という業務が参照事例で出る。
- 戻り方: `persist` に `version` 属性を宣言できるようにし、`update` の `concurrency` を `version-attribute` に変える。既存の `expected-state` は残し、案件が選ぶ。横展開として、#1130 の一括更新の同時実行制御にも同じ選択肢を渡す。

### H2 — 表定義書は行指向のテキストで出す

- 実装: [`internal/artifact/tabledef.go`](../../internal/artifact/tabledef.go)。`table`・`data`・`column`・`primary-key`・`index` の行を、保存の宣言順と索引名順で出す。
- 観測: 生成物を使ったレビューで、変更点と未解決を指摘できたか。手作業の設計書との突き合わせに何回手直しが要ったか。
- 反証: レビュー担当が読めない、または既存の設計書の形式に変換する作業が定常的に発生する。
- 戻り方: 種別ごとの形式を[設計成果物の導出](../design/DERIVED_DESIGN_ARTIFACTS_DESIGN_2026-11.md) 3章で決め直し、変換器を実行先側に置く。

### H3 — 未解決は検証エラーにしない

- 実装: [`internal/operations/surface.go`](../../internal/operations/surface.go) の `gaps`、[`internal/artifact`](../../internal/artifact/artifact.go) の `Unresolved`。
- 観測: `validate` が通った作業領域で、実行できない操作がどれだけ残っているか。未解決を無視した実行が起きたか。
- 反証: 「validateが通った＝使える」と誤解する運用が参照事例で起きる。
- 戻り方: 診断の重大度（warning）として `validate` にも出し、`update`/`create` を実行できないことを起動前に示す。横展開として、成果物の `Unresolved` も同じ重大度で扱う。

## 4. 仮説を変えたときの手順

1. 反証条件に触れた観測を、Issue かこの文書へ記録する（日付・対象・観測値）。
2. 上流（意味モデル・要求・契約）のどこが原因かを分解する。症状の箇所だけを直さない。
3. 修正案を、影響する設計文書へ書く（この文書の表も更新する）。
4. 同じ判断を使っている他の箇所を列挙し、同じ修正を広げる。
5. 修正後、影響した試験と受入を再実行する。実行できない場合は、その制約と残る危険を記録する。

## 5. この文書の限界

- ここに書いたのは**選んだ案**であり、正しいと確認した結果ではありません。参照事例と試験で確かめた範囲だけを根拠にしています。
- H1〜H3 は、実装と試験が通ったことを「製品として妥当」の証拠にしません。実データ・実利用者の確認は別です。

## 6. 反証の記録

### 2026-11-01 — 「Driver Scenario で書き込みまで実行できる」は成り立たない

- 前提にしていたこと: `#1127` W7 で、一覧 → 参照 → 登録 → 更新を `tei scenario` の一回の実行で確かめられる。
- 観測: `internal/scenariotest/scenario.go` が受け付ける操作は `observe-synthetic-state`・`evaluate-validations`・`resolve-pattern` だけである（`cmd/tei/scenario.go` も同じ語彙を使う）。**書き込み（create・update）を表す操作がない。**
- 影響: #2485 の受入は、Scenario を拡張しない限り満たせない。Scenario を拡張することは、実行の語彙を増やす設計変更であり、A4（意味の受理）に当たる。
- 分解（対象・関係・境界）:
  - 対象: 実行の語彙（Scenario の操作）と、標準操作（create・update）。
  - 関係: Scenario は Driver の検証入口であり、標準操作は操作面の導出結果。両者の語彙が一致していない。
  - 境界: Scenario の語彙を増やすのは「実行の意味」の追加であり、操作面の導出（読み取り）とは別の判断。
- 解消の案:
  1. Scenario に `execute-command`（能力の呼出し）を足す。語彙の追加なので A4。
  2. 先に Go の結合試験で、標準操作の実行（期待状態の比較を含む）を確かめる。Scenario の拡張は後回しにする。
- 採った案: まず 2 で実行時の比較を確かめ、Scenario の拡張は #2485 の判断として残す。横展開として、他の Scenario を使う課題（#1130 の一括実行）も同じ語彙の制約を受けることを記録する。
### 2026-11-01 — 書き込みの実行は、既存の能力へ束縛する（H4）

- 前提にしていたこと: 標準操作（`create`・`update`）を、汎用の書込み経路で実行できる。
- 観測: Driver には読み取りの実行（browse・契約問い合わせ・見出し明細）と `InvokeCapability` はあるが、標準操作を直接実行する書込みの経路がない。標準操作の実行手段を新設すると、実行の意味を増やす設計変更（A4）になる。
- 仮説: **書き込みは、同じデータに同じ効果を宣言した既存の能力へ束縛して実行する。** 汎用の書込みエグゼキュータは作らない。
- 実装: 操作面の `create`・`update` に `binding`（能力の識別子）を持たせる。同じ効果・同じ対象の能力が複数ある場合は、識別子の順で一つに決める。能力が無い場合は `binding` を空にし、**導出はするが実行手段が無い**ことを表す。
- 観測: 束縛が付いた操作の割合、束縛が無いために実行できなかった操作の件数。
- 反証: 束縛が無い操作が大半を占め、データ定義だけでは実行できない状態が常態になる。または、案件が能力を書く負担を許容しない。
- 戻り方: 汎用の書込みエグゼキュータを設計する（A4）。その場合も、操作面の `binding` は「どの経路で実行するか」の表示として残す。
- 横展開: #1130 の一括実行も同じ束縛を使う。Scenario の語彙拡張（#2485）を決めるときも、この束縛を入力にする。
### 2026-11-02 — 束縛ありの書き込みを実行へ渡す契約（次段の設計メモ）

`internal/driver/invocation.go` の `InvokeCapability` は、束縛を解決してアダプタへ渡し、**業務上の拒否は `capabilityinvoke.BusinessResult` として返し、実行の失敗は `error` として返す**ことを、コメントで明示しています。この区別を、標準操作の書き込みにもそのまま使います。

- 入力: キーと、読んだときの値（期待状態）。能力の入力型は、書き込むデータを受け取るものでなければ束縛にしない（`capabilityAcceptsData`）。
- 拒否: 期待状態の不一致・権限外・検証違反は `BusinessResult` として返す。実行エラーに丸めない。
- 失敗: 束縛の解決失敗・アダプタ不在・結果の受領失敗は `error` として返す。
- 観測: 拒否の理由の内訳を実行の記録から読めるようにする（H1の観測指標）。

次の実装は、`internal/driver` の試験で、束縛ありの `sales.order.cancel` を偽のアダプタへ渡し、(1) 拒否が `BusinessResult` として返ること、(2) 束縛の解決失敗が `error` になることを固定する。

確認済みのAPI（2026-11-02）: 実体は `internal/semantic/capabilityinvoke`。`BusinessResult{Capability, Mode, Outcome, Payload}`、`Adapter.Invoke(ctx, capability, input)`、`Invoke(ctx, capability, adapter, input)` は返された結果が能力の `result` 契約に従うかを検査する。したがって偽のアダプタは、`sales.order.cancel` の出力契約（`sales.order`）に合う `Mode`・`Outcome`・`Payload` を返す必要がある。
### 2026-11-02 — 束縛ありの実行試験の型（次の実装手順）

既存の `internal/driver/final_gate_b_scenario_test.go` と同じ型で書けます。

1. `driver.NewResolver(world)` を作る（世界は作業領域から読み込む）。
2. `resolver.InvokeCapability(ctx, "ledger", "sales.order.cancel", アダプタ解決, 入力)` を呼ぶ。アダプタ解決は `bindingAdapterResolverFunc` と同じ形で、期待する束縛の識別子は `ledger/sales.order.cancel`。
3. `sales.order.cancel` は単一の `output` 契約なので、偽のアダプタは `BusinessResult{Capability: "sales.order.cancel", Mode: capabilityinvoke.ResultOutput, Payload: <sales.order の行>}` を返す。`Mode` が違えば `ValidateBusinessResult` が拒否する。
4. 期待状態の不一致を表す場合は、`error` ではなく `BusinessResult` として拒否を返し、`InvokeCapability` が `error` を返さないことを確かめる。
5. 束縛の解決に失敗する場合（実現を外す、アプリケーションを変える）は `error` になることを確かめる。

この型で書けば、H4（能力への束縛）とH1（拒否を業務結果として返す）を同時に確かめられます。
### 2026-11-02 — 束縛ありの実行が通った（範囲と限界）

- 通ったこと: 負例の作業領域の `sales.order.cancel` を、宣言済みの実現（`ledger/sales.order.cancel`）へ解決し、偽のアダプタへ渡して `BusinessResult` を受け取った。アダプタの解決失敗は `error` として返り、原因も保持された（`internal/driver/bound_write_test.go`）。
- 分かったこと: **単一 `output` 契約の能力は、拒否を業務結果として表せない。** `ValidateBusinessResult` は `Mode: output` を要求し、`Outcome` の指定を拒否する。拒否（期待状態の不一致・権限外・検証違反）を `BusinessResult` で返すには、書き込み能力に `outcomes` の宣言が要る。
- 意味: H1の「拒否を業務結果として返す」は、書き込み能力の `outcomes`（例: `rejected`・`conflict`）として宣言する形になる。能力の出力契約と、拒否の表現が結び付く。
- 次: 負例の作業領域の `sales.order.cancel` に `outcomes` を足し、拒否の `BusinessResult` が `error` にならないことを試験で固定する。
### 2026-11-02 — 拒否が業務結果として返り、行が変わらないことを観測した（H1の実証範囲）

- 実装: 負例の `sales.order.cancel` を `outcome cancelled sales.order` と `outcome conflict sales.order` の二つの結果に変え、拒否を `BusinessResult{Mode: outcome, Outcome: "conflict"}` として返す試験を追加した（`internal/driver/bound_write_test.go`）。
- 観測: 期待状態を持つ呼出しに対し、別の書き手が先に状態を変えていた場合、`InvokeCapability` は `error` を返さず、`conflict` の業務結果を返した。合成の保存領域では行の状態が変わっていないことを確かめた。
- 範囲の限界: 保存領域は試験内の合成であり、実データベース・実トランザクションでの確認ではない。並行する二つの実トランザクションの競合は確かめていない。
- 意味: H1の「期待状態の不一致を拒否として返す」は、能力の `outcomes` に拒否の結果を宣言する形で、実行の入口まで成立する。実DBでの検証は別の段階（#2483の残り）。
### 2026-11-02 — 実データベースでの競合検証の枠組み

- 追加: `tools/reference-expected-state-concurrency/`。実際のPostgreSQLで、期待状態の比較が後勝ちを防ぐことを確かめる。
- 観測（環境変数がある場合）: 先の書き手が確定した後、古い状態を読んだままの第二の書き手は 0 行しか更新できず、先の値が残る。読み直せば 1 行更新できる。
- 環境変数が無い場合はスキップし、成功として扱わない（`ok` はスキップを含むため、実行時は `-v` で確認する）。
- 限界: 一つの行、`READ COMMITTED`、二つのトランザクションを順に実行。真の同時実行と `SERIALIZABLE` の直列化異常は扱わない。
### 2026-11-02 — 成果物の整合検査は H3 の実証になる

- H3（未解決を検証エラーにしない）を、成果物の側で確かめる仕組みを追加した（`internal/artifact/consistency.go` の `CheckSet`）。
- 検査は、未解決を落とした成果物、完成の偽装、目録の欠落、入力の版の混在を **`Findings` として返す**。実行を止める検証エラーにはしない。
- 観測: 負例の作業領域で違反ゼロ、4通りの改変で違反を検出。一括生成の時点でも同じ検査を通す。
- 限界: 検査は成果物同士の矛盾を見るだけで、「意味として正しい」ことは保証しない。実データ・実利用者の確認は別。
### 2026-11-02 — 束縛は、書き込むデータを受け取る能力に限る（H4の追記）

- H4（書き込みは既存の能力へ束縛する）に、束縛の資格条件を足した: 能力が書き込むデータを入力に取る（または出力する）こと。`capabilityAcceptsData` が判定し、対象外の能力は束縛に選ばない。
- 理由: 同じ効果を宣言していても、別の対象を受け取る能力を束縛に選ぶと、実行したつもりで別の対象を更新する危険がある。
- 観測: 負例の作業領域では `sales.order.register`（create）と `sales.order.cancel`（update）が束縛され、データを受け取らない能力は選ばれないことを試験で固定。
- 限界: 能力の入力型の一致だけを見る。入力の必須性・個数・意味の妥当性は見ない。
