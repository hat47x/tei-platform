# ADR-0035: 自律開発を段階づけ、機械可読な作業票と変更範囲に応じた検証で人間の関与を減らす

- 状態: 採用（2026-11-07に改訂。A3の統合条件を機械確認へ寄せ、人の確認を外部効果だけに限定した）
- 日付: 2026-10-18
- 関連ADR: ADR-0001 / ADR-0022 / ADR-0031
- 関連Issue: #2017 / #1973 / #1189 / #1163 / #1119 / #2344
- 運用上の扱い: `AGENTS.md`のA0〜A4は、本ADRを根拠にする。状態を変えたときは、参照元の記述を同じ変更で確認する（[索引の手順](README.md)）。

## 背景

TEIの開発規約は、AGENTS.md、CONTRIBUTING.md、ADR、Issue、CIに分かれて書かれている。生成AIや自動化が作業するとき、どの変更をどこまで自律的に進めてよいかを、作業者ごとに判断している。変更範囲、危険度、必須の検証、証拠の形式、人へ戻す条件が機械可読でないため、次のばらつきが生じる。

- 変更範囲に対して過剰な検証を回す、または必要な検証を落とす。
- 検証した版と、統合する版が一致しているかを、後から確認しにくい。
- リポジトリ内の変更と、外部へ出る取り消せない効果の区別が崩れる。
- 生成AIの自己申告や、古い証拠を成功として扱う。

本ADRは、自律開発の段階と、その前提となる作業票、検証、証拠の扱いを定める。PoC工程では、リポジトリ内で完結する作業を機械確認だけで進め、人の確認を外部効果へ絞る。

## 問題

自律性を上げるほど、次の失敗の影響が大きくなる。

1. 変更してよい範囲を越えた編集。
2. 変更範囲に合わない検証、または検証の未実行。
3. 外部へ出る取り消せない効果を、リポジトリ内の変更と同じ自動化へ混ぜること。
4. 検証した版と統合した版の取り違え。
5. 失敗・未確認・環境不足を、成功として扱うこと。

## 判断

### 自律性を段階に分ける

作業を、次の段階に分ける。段階は変更の種類で決め、作業者の自信では決めない。

- `A0` 読み取り・分析のみ。Source、Workspace、外部状態を変更しない。
- `A1` 受理済み意味からの決定的な派生物。設計成果物、一覧、DDL候補などを出力する。意味の正本を変更しない。
- `A2` 隔離したbranchでのSource・コード・試験の変更。変更範囲に対応する検証を必須とする。
- `A3` 統合。作業票の範囲、検証、証拠が機械確認できれば進める。意味、契約、Authorityの変更を含む場合も、受理済みの検証経路と機械可読な記録で確認できれば同じ扱いにする。人の承認を前提にしない。
- `A4` 取り消せない外部効果。秘密情報・顧客データの外部送信、本番環境への配備、外部システムの削除や破壊的移行、第三者ライセンスの法的判断、対外公開。影響範囲と選択肢を書いたうえで人に確認する。

段階が上がるほど、機械確認の条件を増やす。段階を飛ばさない。`A4`に当たるか迷う場合は、当たらない形へ変更を分割する。分割できない場合は、既定案を選んで進み、選んだ理由と覆す条件を記録に残す。

### 作業票を機械可読にする

作業票は、少なくとも次を宣言する。

- 対象Issue、base revision、危険度、許可path、禁止path
- 必須の検証コマンドと、変更範囲から追加する検証
- 停止条件（未確認の依存、権威の変更、想定外の差分、検証環境の不在）
- 証拠の形式（exact head、コマンド、終了コード、出力digest、未検証範囲）
- 失敗時の扱い（rollback、再試行しない条件、人へ戻す条件）

作業票は、変更の許可証ではない。作業票の範囲内でも、外部効果を出す判断は別である。

### 機械的な受理の条件を限定する

機械的な受理は、次をすべて満たす場合だけ行う。

- 変更pathが許可範囲内にある。
- base revisionが現在の統合先と一致する。
- 必須の検証がすべて実行され、成功している。
- 停止条件に当たっていない。
- 証拠が、統合対象のexact headを指している。

意味、契約、Authorityの変更は、受理済みの検証経路と機械可読な記録で確認できれば受理してよい。確認できない場合は、成功として扱わない。不明な依存や未実行の検証を、空の成功へ変換しない。ただし、受理を保留することは作業全体の停止を意味しない。保留した範囲を記録して、他の範囲を進める。

### 人が確認する外部効果を残す

次は、リポジトリの外へ取り消せない効果を出すため、影響範囲と選択肢を書いたうえで人に確認する。

- 秘密情報、顧客データの外部送信。
- 本番環境への配備、外部システムの削除や破壊的移行。
- 第三者ライセンスの法的判断。
- 対外公開。

これらは、作業票の危険度を上げるのではなく、別の判断として扱う。`A4`に当たるか迷う場合は、当たらない形へ変更を分割する。分割できない場合は、既定案を選んで進み、選んだ理由と覆す条件を記録に残す。

業務上の意味の受理、権限の付与、Production HostのAuthorityは、このリポジトリの外にある製品・利用先の判断であり、PoCの開発作業を止める条件にはしない。開発の中で意味を変える場合は、ADRと要求の版を記録して進める。

### 証拠を版へ束縛する

証拠は、統合対象のexact head、実行したコマンド、終了コード、実行環境、未検証範囲を持つ。以前の実行の証拠を、現在の版へ自動的に流用しない。同じ版と同じ環境で再実行できるかを確かめる。

### 開発環境を特定製品に閉じない

作業票と検証は、Git、CLI、CI、通常のEditorから使える形式にする。特定のAgent製品、Chat UI、常駐Runtimeを必須にしない（ADR-0031）。Agent製品を使う場合も、成果物と証拠はリポジトリとCLIから再現できるようにする。

### 失敗と不明を分ける

検証の失敗、環境不足、未確認の依存、作業票の範囲外、権威の変更を、それぞれ別の状態として記録する。自動再試行は、再試行しても意味が変わらないと確認できる場合だけ行う。不明な状態では、影響する範囲だけを保留する。

## 代替案

- **すべての変更を人間が確認する**: 変更量が増えると確認が形骸化し、危険な変更と安全な変更の区別が失われる。
- **すべての変更を自動で統合する**: 外部効果の判断を迂回するため採用しない。リポジトリ内の変更と外部効果を分けて扱う。
- **CIの全項目を毎回必須にする**: 変更範囲と関係のない検証が増え、実行時間と失敗の切り分けが悪化する。
- **専用のAgent Runtimeを必須にする**: 開発環境を特定製品へ閉じ、ADR-0031に反する。

## 影響

- 作業票のschema、検証ランナー、証拠の形式を小さく実装する必要がある（#2017）。
- CIは既存workflowを再利用し、変更範囲に応じた選択を加える。新しい常駐serviceは作らない。
- PRの説明とレビューは、作業票と証拠を参照できるようにする。
- 段階の判定を誤ると、外部効果を安全と誤認する。段階の境界を試験で固定する。

## 検証

#2017で、作業票の検査、変更pathの範囲確認、検証コマンドの実行、証拠のJSON化を最小実装した。許可path外の変更、base不一致、必須検証の欠落、環境不足を拒否できることを確かめた。1つの実PRで使い、AGENTS.mdの規約と矛盾しないことを確認した。`A3`の範囲を機械確認へ寄せた改訂は2026-11-07に行い、以後のPRで運用する。効果が確認できない場合は、改訂部分を戻す。
