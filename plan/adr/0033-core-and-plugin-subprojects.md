# ADR-0033: コアとプラグインをサブプロジェクトとして管理する

- **状態**：採用（目標構成）。ソース移動や独立ビルドが完了したという意味ではない。
- **判断日**：2026年10月12日
- **実施課題**：[Issue #1251](https://github.com/hat47x/tei-platform/issues/1251)
- **関連**：[ADR-0032](0032-composition-kernel-replacement.md)、[ADR-0031](0031-tool-neutral-git-native-development.md)、[依存方向の検査案](../design/REPOSITORY_ARCHITECTURE_DEPENDENCY_GUARD_2026-10.md)、[プラグインの説明](../../docs/plugins.md)

## 背景

TEIは、標準機能もプラグインとして提供し、利用する機能と実行先に応じた成果物を構築することを目指す。現在の製品実装は単一のGoモジュール（`module tei`）にあり、`internal/` 以下に共通機構、プラグイン管理、実行先固有の処理が混在している。

今後、コアと標準プラグインの独立性を明確にし、生成AIを含む複数の開発者が変更の影響範囲を把握できるようにする必要がある。ただし、ソースの配置、論理的なプラグイン、Goモジュール、ビルド成果物、配備単位を一対一に固定すると、静的結合や実行先に応じた最適化を妨げる。

## 判断

### 1. コアとプラグインを管理上の基本単位とする

単一のGitリポジトリを維持し、コアは`core/`、製品として提供するプラグインは`plugins/<プラグイン名>/`を目標配置とする。両者をサブプロジェクトとして扱い、責務、参照すべき契約、ビルド入口、検証方法を個別に明らかにする。

`core/`は最小の合成基盤、公開契約、実行上の信頼境界を担当する。最小限のホスト機構を含むことは認めるが、具体的なデータベース、認証方式、画面技術、実行先の実装へコアを依存させない。コアの内部に複数の構築対象が存在してもよい。

`plugins/`は標準プラグインを含む製品実装を管理する。言語処理、生成器、認証、データベース接続、ブラウザ・デスクトップ・組み込み機器向けの実行機構など、実行先固有の処理も原則としてプラグインの責務とする。独立した`targets/`を製品ソースの恒久的な分類として設けない。最小ホストの起動入口や検証用の`cmd/`、`tools/`は、プラグインに強制移管しない。

コアの共通契約と、プラグインが提供する実装を分ける。既存の`internal/core/`がそのまま新しい`core/`全体を意味するわけではない。旧プラグイン構造を移すだけで新しい合成基盤の契約が成立したものとみなさず、ADR-0032の境界に従って移管対象を判断する。

### 2. 管理単位と生成物の境界を区別する

次は互いに異なる単位とする。

| 単位 | 意味 |
| --- | --- |
| サブプロジェクト | 責務とソースの変更・検証をまとめる管理上の単位 |
| 言語・ビルド単位 | Goパッケージやモジュール、TEIの構築定義など実際の構築入口 |
| 論理プラグイン | 提供する契約、実装、版などの識別単位 |
| ビルド入力 | 対象成果物の構築結果に影響するソース、依存物、生成器、設定の集合 |
| 成果物 | バイナリ、WebAssembly、生成コード、定義パッケージなど |
| 配備・実行単位 | プロセス、静的に結合したアプリケーション、ブラウザ内の機構など |

一つのサブプロジェクトから複数の成果物を生成してもよく、複数の論理プラグインを一つの成果物にまとめてもよい。実行先や配備方式が異なっても、契約とプラグインの識別情報を追跡できるようにする。

ビルド入力はディレクトリ全体やリポジトリ全体と同義にしない。実際に影響する入力を構築条件に応じて確定する。リポジトリの版は検証記録として残せるが、成果物の入力指紋と混同しない。具体的な入力追跡の検証は[Issue #1089](https://github.com/hat47x/tei-platform/issues/1089)と既存のセルフビルド課題を参照する。

### 3. Goモジュールの分割は必要になってから行う

サブプロジェクト化と`go.mod`の追加を同時には行わない。外部配布、依存ライブラリの独立更新、再利用、契約の安定性に利点があると実証された領域だけを、必要に応じて複数モジュールへ分ける。

現在の健全性検査は`GOWORK=off`かつルートからの`go test ./...`等を前提とする。入れ子のGoモジュールを追加する場合は、全サブモジュールの検査漏れを防ぐ手順を**先に**整備する。`go.work`の有無だけで検査できたと判断しない。

Go以外の言語やTEI自身の生成器を使うプラグインに、Goの構成規則を強制しない。検証可能なビルド入口と依存契約を共有する。

### 4. READMEとAGENTS.mdを混同しない

- リポジトリ全体の説明はルートの`README.md`、コアの案内は`core/README.md`、プラグイン群の案内は`plugins/README.md`、各プラグイン固有の説明はその配下の`README.md`に置く。
- `AGENTS.md`は開発エージェントへの指示に使う。構成案内や機能・契約の正本を記載する目的では増やさない。対象固有の実質的な指示が必要な場合だけ下位ファイルを検討する。
- 採用した判断はADR、現行の構成説明は`docs/architecture.md`、実装状況は`docs/status.md`に置く。同じ仕様の正本を複製しない。

### 5. 変更を段階的に進める

最初に責務と依存を調査し、必要なREADMEを整える。新規プラグインは目標配置を優先し、既存実装は公開契約と回帰試験が成立したものから順次移す。既存の`internal/`や単一Goモジュールは移行の間も利用できる。

分割の成否はディレクトリ数でなく、独立構築、契約準拠、依存方向、既存コアを変更せずに機能を追加できる範囲、実行先ごとの不要機能除外、ビルド入力の再現性で評価する。並行開発でも、サブプロジェクトとGitブランチを一対一に固定しない。

## 採らなかった方法

- **全ソースを一括移動する**：並行する変更と回帰試験に不要な負担を生む。
- **各プラグインにGoモジュールを必須とする**：Go以外の実装や、単一成果物への結合を扱いにくくする。
- **実行先を`targets/`へ恒久的に隔離する**：プラグイン中心の構成と責務が二重になる。
- **READMEの代わりに下位AGENTS.mdを配置する**：説明と開発指示の役割が混ざる。
- **リポジトリを直ちに分割する**：共通契約と変更範囲が定まる前の分割はかえって維持費を高める。

## 移行状態と次の確認

このADRは目標構成を決めるものであり、コアやプラグインの独立ビルド、Goモジュールの分割、既存ソースの移動が完了したことを示さない。実施順序と受入条件は[Issue #1251](https://github.com/hat47x/tei-platform/issues/1251)で管理する。
