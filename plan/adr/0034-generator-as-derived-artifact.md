# ADR-0034: 生成器を受理済み意味から導出する版付き成果物として扱い、生成AIによる生成器生成を同じ適合境界に置く

- 状態: 提案中
- 日付: 2026-10-18
- 関連ADR: ADR-0015 / ADR-0022 / ADR-0031 / ADR-0032 / ADR-0033
- 関連Issue: #2016 / #1975 / #1063 / #943 / #1370 / #951 / #1803

## 背景

TEIは、業務の意味を実装技術から分け、同じ意味から複数の実行先を組み立てることを目指している。X-TEAのModeler/Editorが、定義を実行時に解釈し、機能種別とテーブル定義の組合せでアプリケーションを組み立てていた仕事を、TEIでは意味の受理と生成器の選択へ置き換える。

生成AIを使うと、アプリケーションのコードをその場で生成できる。しかし、毎回コードを生成する方式は、同じ入力から同じ結果が得られず、生成の根拠、検証、再生成、対象の交換が難しい。TEIが目指す生産性は、コードを一度生成することではなく、**受理済みの意味から生成器を導出し、生成器を検証済みの成果物として再利用する**ことで得る。

本ADRは、この方向を設計判断の候補として記録する。実装済みでも採用済みでもない。

## 問題

次の失敗を防ぐ。

1. 生成AIが生成したコードを、検証した生成器の成果物と混同すること。
2. 対象ごとに生成器が増え、意味の変更が対象ごとに分岐すること。
3. 生成器の出所・入力契約・対象・適合結果が追えず、再生成や交換ができないこと。
4. 生成器を生成する生成器（メタ生成）が、第二の権威や無限後退を作ること。
5. 生成AIの自己申告や生成成功を、正しさや権限の証拠にすること。

## 判断

### 生成器を版付きの成果物として扱う

生成器は、少なくとも次を持つ成果物として識別する。

- 入力となる契約のidentityと版
- 対象Profile（実行環境、言語、配備形態、資源制約）
- 生成器のsource digestと生成手段（テンプレート、手書き、生成AI）
- 適合試験の版と結果、未検証の範囲
- 失効・撤回の条件

生成器のidentityは、生成物のidentityと分ける。生成物は、生成器と入力から再生成できる派生物であり、意味の正本ではない。

### 受理済み意味を権威とする

意味の受理は、生成器の選択や生成物の生成より前にある。生成器がどれだけ高機能でも、受理されていない意味を正本へ昇格させない。生成物の変更を意味へ戻す場合は、通常の変更案と受理境界を通す。

### 生成器候補を固定した適合試験で選抜する

テンプレート、手書き実装、生成AIが書いた実装は、同じ入力契約と同じ期待値fixtureで比較する。候補の由来は選抜の根拠にしない。生成AIが生成したという事実は、権限も正しさも与えない。

期待値fixtureは、候補を作る前に固定する。候補に合わせて期待値を書き換えない。適合しない候補を、生成器の側で吸収しない。

### 生成AIによる生成器生成を同じ境界に置く

生成AIが生成器を書く場合も、生成器は上の成果物として扱う。生成AIが生成器を生成するメタ生成も同じ境界に置く。メタ生成を許す場合も、次を守る。

- 入力契約、対象Profile、期待値fixtureを、生成の前に固定する。
- 生成された生成器のsource digestと、生成に使ったモデル・設定・文脈を記録する。
- 生成器の採用は、固定した適合試験の結果で決める。
- メタ生成の停止条件（これ以上生成器を生成しない基準）を、対象Profileごとに決める。

メタ生成を無制限に再帰させない。基準となる生成器と適合試験を先に固定し、その範囲を超える生成は新しい変更案として扱う。

### CoreとPluginの責務を分ける

Coreは、契約のidentity、意味の受理、適合試験の枠組み、成果物の来歴を扱う。対象固有の生成器、テンプレート、言語別の実装は、Pluginまたは案件側の成果物として扱う。Coreへ対象固有の生成器を埋め込まない。

### 配備Profileは意味を変えない

組込み、OS常駐、Web、SaaS、エンタープライズの違いは、Target Profileとして扱う。Profileは、資源、実行形態、更新、権限、観測の違いを宣言する。意味のidentity、Validation、拒否の種類は変えない。Profileごとに第二のモデルを作らない。

### 失効と再生成を追跡する

契約、対象Profile、適合試験、生成器のいずれかが変わったとき、どの生成器と生成物が失効するかを追えるようにする。失効した生成器を、現在の権威として使い続けない。再生成は、新しい適合試験の結果を必要とする。

## 代替案

- **毎回アプリを生成する**: 再現性と来歴を失うため採用しない。
- **手書きの生成器だけを使う**: 対象追加のたびに人手が必要になり、生成AIの生産性を活かせない。
- **一つの万能生成器ですべての対象を扱う**: 対象固有の制約をCoreへ押し込み、意味の分岐を招くため採用しない。
- **生成AIの自己評価で生成器を採用する**: 権威と証拠を混同するため採用しない。

## 影響

- 生成器のregistry、適合試験の版、receiptの形式が必要になる。既存の#951 / #943 / #1370で表現できる範囲を先に確かめ、新しい正本を増やさない。
- 設計成果物（#1803）は、生成器の入力と出力の一部として位置づけ直せる。
- 生成AIのモデル・設定・文脈を記録する必要がある。モデルの版が変わったときの再現性は別途検証する。
- 対象Profileの数だけ生成器が増えるため、保守コストと選抜の自動化が課題になる。

## 未決

- 生成器のreceiptを既存のArtifact/Build Evidenceへ載せるか、別の成果物とするか。
- 生成器の署名・信頼根を、どこまで必須にするか。
- メタ生成の停止条件を、誰がどの単位で承認するか。
- 生成AIのモデル版が変わったとき、過去の適合結果をどこまで再利用できるか。

## 検証

#2016で、1つの契約と1つの対象を使い、テンプレート、別実装、危険な実装の3候補を同じ期待値fixtureで比較する。生成器のdigest、入力契約、対象、試験版、結果を一つのreceiptに残し、危険な候補を負例で排除できるかを確かめる。このPoCで効果が確認できない場合、本ADRは採用しない。
