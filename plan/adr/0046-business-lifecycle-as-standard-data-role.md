# ADR-0046: 業務状態遷移を、標準データ上のLifecycle役割とOwner Actionのガードとして扱う

- 状態: 提案中
- 日付: 2026-11-04
- 統合元: [ADR-0024](0024-business-lifecycle-ownership.md) / [ADR-0025](0025-transition-evaluation-and-conflict-result.md)（いずれも提案中）
- 関連ADR: ADR-0019 / ADR-0020 / ADR-0044
- 関連Issue: #2619 / #2620 / #1129 / #1174 / #2500 / #2540

## 背景

ADR-0024は、業務Lifecycleを「Semantic namespaceが所有する新しい要素」としてCoreに追加する案だった。その後の#2619（Everything is Data）は、すべての定義体を標準データ構造と意味解釈部品で表し、型ごとの専用Editorや第二の意味正本を増やさない方針を掲げている。新しいCore要素の種類を足す方式は、この方針と競合する。

ADR-0025は、遷移の評価順序の先頭に`Authentication`を固定していた。[ADR-0044](0044-authentication-not-a-core-concern.md)は、認証を必要としない運用と、Pluginで認証する運用を、同一の意味モデルから選べることを求めている。

一方、両ADRの中核である「状態identityと物理コードを分ける」「遷移の評価順序を固定し、成立しなかった遷移を業務結果として返す」は、方向性に沿っており維持すべきである。本ADRは両案を統合する。

## 決定

1. **状態はCanonical IDで識別する。** 物理コード（`P`、`PENDING`等）との対応はRealization / Provider binding側に置く。型や名前の類似から推測しない（ADR-0024）。
2. **状態と遷移は、標準データ構造に「Lifecycle」の意味役割を付けて記述する。** 状態×遷移の表など、既存の標準構造を使い、専用のCore要素種別・専用Editorを作らない（#2619/#2620）。
3. **遷移の`requires`は既存Validationの参照に限る。** 新しい条件式言語を入れない。「誰が遷移できるか」は認可のCapabilityが所有し、Lifecycleには書かない（ADR-0024・ADR-0019）。
4. **評価順序を次のとおり固定する。** ［認証（認証Pluginを束縛した構成のみ）］→業務Validation→認可→現状態の明示read→from判定→条件付きOwner Action→別操作のObservation。認証の段が無い構成でも、認可は省かない（ADR-0025・ADR-0044決定4・5）。
5. **from判定の通過をCommit時点の保証にしない。** 状態条件と認可版は、Commitと同一の境界で検証する（ADR-0025・#1174）。
6. **成立しなかった遷移は業務結果として返す。** 状態コードの解決失敗・readの失敗はExecution Errorとし、「遷移できない」という業務結果と混同しない（ADR-0025・ADR-0020）。

## 統合元ADRの扱い

本ADRを採用した時点で、ADR-0024・0025を「置き換え済み」とする。両ADRは提案中であり、採用済みADRの書換え禁止規則には触れない。
