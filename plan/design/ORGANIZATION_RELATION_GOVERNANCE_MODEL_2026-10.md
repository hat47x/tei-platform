## 1. どんな仕事を可能にしたいか

部門と従業員の単純な管理から始め、兼務、複数雇用、複数の指揮命令系統、企業集団、異動履歴、代理行為、申請承認を、必要になった範囲だけ自然に追加したい。従来のデータモデルで十分な部分を再構築する必要はない。

目標は「組織図が描ける」ことではない。同じ受理済みの業務意味から、(a)時点別の組織図と配置表、(b)移動前後の差分、(c)責任・承認候補の根拠、(d)参照するQueryとテストデータ、(e)実行・監査への接続を導き、読める設計と実際の振る舞いの間に説明可能な橋を架ける。

- **組織の事実**：何が誰とどの関係で、いつ、どの範囲で成立したか。
- **業務上の解釈**：その関係が、担当・責任・判断条件へどう結び付くか。
- **実行上の許可**：現在のHost/Providerがその操作を許すか。
- **外部で起きた結果**：更新・発行・通知・承認が確定したか。不明なら不明のまま残す。

「組織関係を登録した」「ルールがTrueと評価された」「権限が確認された」「実際に承認が確定した」はそれぞれ別の証拠を要する。

## 2. 最小の意味構造と、後から導入する拡張

### 2.1 最小形

`組織`・`人物/従業員`・`上位組織`・`所属`が記述できれば、初期の単純な案件は成立する。最初から全案件に雇用履歴、組織版、二時点、代理権限の表を要求しない。

### 2.2 必要な場合に加える関係

| 概念 | 説明と区別する対象 |
| --- | --- |
| 企業集団・法人・組織単位 | グループ・法的主体・実務上の編成を分離。法人とテナントを同一視しない |
| 人物・雇用/在籍・配置 | 人の識別、雇用契約、ある部門・職位での勤務を分離。派遣/委託先の担当も表せる |
| 職位・業務上の役割 | 「部長職」や職位の在席者と、「申請を確認する人」など業務Actorを分ける |
| 組織間の型付き関係 | 人事上の上位、指揮命令、会計の集計、資源の帰属、プロジェクト参加等。各軸は独立した制約を持つ |
| 辞令・変更事由 | 関係の変更を束ねる命令、決定または通知。現行関係そのものではない |
| 外部参照・対応付け | 連携元システムの識別子、対応先、確認状況、根拠、参照元の版。名称・メール一致は同一人物の確定根拠ではない |
| 委任・代理の業務意味 | 代理人、受益/被代理者、行為、対象、制約、発効・取消。実際のGrant/認証とは別 |
| テナント・実行主体 | TEIの業務対象とHostの保護境界。所属しただけでテナントアクセスは生じない |

既存のData/Relation/Validation/Procedure/Actionと型付き参照を第一候補とし、ここで新しいCore種別や固定テーブル群を採用しない。組織固有の型付き拡張やTemplateを試し、既存表への対応付けでも同等の意味が保持できるか評価する。

### 2.4 組織Dataのアクセス：同一TEI世界内の通常利用を原則とする（2026-11-01 Owner明確化）

**組織管理モジュールはDataの意味・操作を提供する構成要素であり、それ自体がセキュリティ境界ではない。** 同じTEI基盤・同じ業務世界内では、部門、所属、職位、配置、組織関係の通常データは他のDataと同様に利用・参照・JOIN・集計・Function Contextへ引き渡せることを基本とする。組織管理用テーブルであるという理由だけで、専用のACL、行レベル認可、別DB、専用Gateway、機密Projection、OS隔離を標準義務として追加しない。

**保護は組織というDomainではなく、具体的なデータ項目と運用上の要請によって例外的に決まる。** 例えばマイナンバー、クレジットカード情報、契約や組織が特別な保護対象と指定した項目等を扱う場合は、その項目・格納先・処理・送信先の範囲で適切な分離・アクセス管理・暗号化等の方式を個別に検討する。氏名・所属・役職・組織図・社員数・関係経路の全てを一律に機密とみなさない。法制度や個別用途に伴う保護要件を否定する趣旨でもない。

**別問題を区別する**：①同一TEI世界の通常のData参照、②保護対象データの特例管理、③承認・支払・削除等の副作用に対するHost Authority、④別テナント/別運用主体/外部AIサービスへデータを渡す際のDelivery・境界契約。③④が必要な場合も、①の組織参照へ独立の認可レイヤーを自動付与しない。外部ハーネスへの接続方式や隔離Profileは別の要件であり、組織テーブルに必須の属性ではない。

### 2.3 関係型ごとの制約

各関係型は、少なくとも「主語と目的語の種類」「同一時点での多重度」「重複期間の可否」「循環・複数経路の可否」「適用する業務範囲」「連携元の責任」を宣言できることが望ましい。

- 人事上の親子階層には「ある子に同一時点で親が高々一つ、循環なし」という制約を選べる。
- プロジェクト参加は多対多を許し得るため、人事上の親の規則を流用しない。
- 予算配賦は複数帰属と比率合計制約を持ち得る。単純なparentの木では表現しない。
- 兼務を認めても「主務は一つ」とするかは案件の業務判断。主務の欠落または複数がいつ不正なのかを明示する。
- 同じ組織が別の組織軸へ現れても、階層上の継承と権限の継承は同一ではない。
- 同名の部門や改名は同一性の根拠にしない。統合・分割では新旧の識別・継承の判断を明示する。

## 3. 時間の四つの意味を混ぜない

| 時間・版 | 質問 | 保持/比較対象 |
| --- | --- | --- |
| **業務有効時点（valid time）** | 2027-04-01にどの所属が有効だったか | 関係の適用期間 |
| **記録時点（recorded time）** | 2027-04-05に何を知っていたか | 訂正前後の記録履歴 |
| **公開済み組織版（published revision）** | 利用側はどの整合した版を見ているか | 変更集合の公開境界、依存とcache |
| **判断・実行時点（decision/commit time）** | 操作時にどの権限・業務条件が有効か | 現行認証、Grant、取引状態、Effect Fence |

必要な場合の時間区間は原則 `[開始, 終了)` の半開区間を候補とする。「2027-04-01付」の日付とTimestampを混ぜず、業務暦・基準タイムゾーン・終端の開閉と遡及訂正規則を案件で確定する。NULLの開始/終了は「無期限」「不明」「欠落」のいずれかに推測しない。

「2027年4月1日現在の組織」と表示するときは、少なくとも有効日を示し、必要なら記録時点と公開版を表示する。未来の発効日つきで受理した変更と、まだ受理されていない計画案は、同一の正式な組織として表示しない。

**注意**：SQL Server等のsystem-versioned temporal tableは主にDB管理上の更新履歴を示す。これだけで発令日等の業務有効期間を表せるとは限らない。実装方式を業務時間の正本と混同しない。

### 3.1 履歴の再解釈と表示

同じ業務有効日でも、「当時知られていた状態」と「後日に訂正された現在の理解」は異なり得る。過年度集計を変更するか、監査用の当時認識を維持するかは業務により異なる。集計の結果に表示時点/利用した資料版を残す。

## 4. 外部組織データ：レコード取込と組織版公開を別に扱う

既存[取込設計](BUSINESS_DATA_IMPORT_DESIGN_2026-10.md)では行ごとの確定を既定候補としている。これを組織改編のために全案件で変更しない。

組織改編では次を分ける。

1. **取得**：連携元、抽出範囲、snapshot/delta、基準版、完全性、取得時点を記録。部分スナップショットの欠落を退職・廃止扱いしない。
2. **候補照合**：外部IDの名前空間、対応関係、由来、型、欠損/NULL、rename、split/merge、不明の関係を分類。全対象の集合完全性は個別行の検証とは別。
3. **検査・差分提示**：業務有効時点での循環、所属重複、主務条件、参照先欠落、部門閉鎖時の配属、影響する承認依存を検査。
4. **業務上の受理**：Ownerの正本決定により変更集合を採用。取り込んだだけでAccepted事実へ変換しない。
5. **組織版の公開**：同一境界のConsumerに公開される新しい整合版を切り替える。部分変更だけが可視化されるなら本段階の受入不成立。
6. **外部への反映と確認**：別システム、別テナント、IdP、データウェアハウスへ非同期転送する際は、送信済み、受領済み、相手先確定、不明を区別。分散した原子的確定を主張しない。

取込元の権威は項目・関係・法人・期間ごとに異なる可能性がある。単一の「このHRマスターを全部信用」ではなく、どの情報について誰がSource of Recordかを明示する。競合した二つの正本候補は、取り込んだ順や新しいTimestampだけでは決めない。

## 5. 動的ワークフロー：承認候補、業務判断、現在権限の別評価

「申請部門の現時点の上位組織の責任者」というように、固定の利用者IDではなく組織関係と規則から候補を求めることを目標とする。

評価を次に分ける。

```text
申請/対象Dataと受理済み業務規則
  -> 参照する組織軸・業務有効日・組織版の確定
  -> 責任の候補を導出（複数/0件/不明も表す）
  -> 排他制御・利益相反/職務分掌の業務条件
  -> 認証済みの実操作者と対象業務の対応
  -> 現在のHost Authority/委任/対象revision照合
  -> 更新の確定境界（#1174）
  -> 確定結果と独立観測
```

承認候補の存在、Inbox表示、実際のClaim、決裁実行は異なる。失効者を候補として表示しただけで実行許可としない。

### 5.1 進行中の案件と異動

少なくとも次の三方式を比較し、業務Ownerが案件ごとに選ぶ。

- **開始時固定**：申請開始時の規則と組織版で担当を定め、後続の現行認可は別に確認。
- **各作業時再評価**：承認作業ごとに規則と組織関係を評価。ただし既に確定した承認を無条件に巻き戻さない。
- **移行規則あり**：特定の異動イベントによって保留・再割当て・再申請・上位者判断へ移る。

候補が0件、多数、未確認、関係循環、秘匿された関係などの場合を区別する。説明できても実行に進めないケースを許す。BPMN/DMN/CMMNは表現/実行Adapterの比較候補に留める。

### 5.2 委任と代理の条件

実操作者、被代理者、委任の根拠（権限の保有者を含む）、行為、対象、テナント、目的、期限、取消・失効、認証強度と監査を結び付ける。

- 委任先が元の委任者より広い権限を取得することを認めない。対象/行為/期間/テナントの範囲を交差させて評価する。
- 再委任・代理の連鎖は既定で許可しない。許容する場合は深さ、同一性、循環、委任権限の根拠を明示する。
- 代理決裁を実施しても、元の本人が操作したという監査履歴に書き換えない。
- 申請者と承認者が一致する、代理人が自分の案件を承認するなど、職務分掌の禁止条件を代理経路でも検査する。
- 組織モデル内のDelegate関係はHostの有効なGrantを代替しない。Grant失効後に古いcacheで確定しない。

NIST ABACは主体/対象/行為/環境の属性による判断を整理する参考になる。Zanzibarの外部一貫性と因果順序は認可変更とデータ更新の鮮度競合を考える参考だが、TEIが同等の保証を既に持つことを意味しない。

## 6. SQL/CTE・テストデータとの横断：Queryは仮想的な関係を作る

組織階層の探索、期間結合、委任による承認候補解決はSQLでCTE、再帰、複数JOINを伴うことが多い。

TEIのSQL構造モデリング検討と接続し、Queryを物理DB依存の文字列としてだけでなく、**入力集合→有効関係の抽出→関係経路の評価→業務判断用の結果集合**として読むための投影を候補とする。

```text
[入力] 部門U-11、業務有効日2027-04-02、参照済み組織版R7
     │
     ▼
[仮想集合A] 有効な「人事管理」親子関係
     │  有効期間・参照版・組織軸に従い抽出
     ▼
[仮想集合B] 部門U-11からの上位組織経路
     │  再帰/循環/複数経路の診断
     ▼
[仮想集合C] 対象組織の責任職位と在任者
     │  期間・兼務条件・選定規則
     ▼
[結果] 承認候補集合（認可許可ではない）
```

- CTE/サブクエリの仮想表は、Canonicalな組織Dataの第二正本ではなくQuery Workbenchの派生表現とする。
- 各仮想集合に、対応する入力・期待出力の小Datasetと、Field lineage、根拠となるRelationを示す。
- 同じ名称の仮想表でもQuery scopeが異なれば別の対象とする。再帰は深さと停止条件を可視化。
- query/評価で渡す全関係集合の完全性が不明なら、「候補なし」と断定しない。Providerが対象集合の一部だけを返した場合に正しい判断だとみなさない。
- 部門・人員・関係経路・件数は同一TEI世界内では通常Dataとして扱う。**個別に保護指定されたデータ**または実際の別運用Tenant境界に該当する場合に限り、その範囲の開示制御を検討する。
- Queryの形と検証結果からRuntime実行許可を発行しない。必要な認可はProvider側で強制し、scope条件が押し下げ不能なら安全に拒否する（#1656/#1769）。

**注意**：この表示は新しいTEI構文やSQL/CTE共通ASTの確定ではなく、既存Contract Query、Data/Relation/Scenarioと結び付く派生Workbenchの要求候補。

| ORG-10 | マイナンバー等、明示的に保護指定された特殊データを組織Queryが参照する | 保護対象の項目・範囲にのみ必要な制御を適用し、通常の組織Relation/経路・件数は一律に秘匿しない |
| ORG-11 | 組織版R7で承認候補を計算後、R8へ改編 | 固定/再評価/移行の三方式を明示。業務Owner未決のときは確定しない |
| ORG-12 | 外部SaaSへ人事変更通知→通信断 | 受付/確定/不明を区別し、根拠なく再送・業務完了表示しない |

- `ORG-01〜04,09`は **Pure semantic評価**を先行。実DBや認可の成功とは別。
- `ORG-05,06,12`は取込/公開/外部効果のContractを検証してから、実Providerの独立readを必要とする。
- `ORG-07,08,11`は業務上の承認・委任と実行権限の負例。`ORG-10`は保護指定された個別データの特例。組織管理Data全体のACLを意味しない。合成評価のPASSだけで本番効果を保証しない。

### 7.3 同じ結果でも根拠が違う

「P2は承認できない」について、未所属、関係が不明、認証できない、Grant失効、自己承認の禁止、対象版が古い、Provider失敗は区別して保持する。組織Dataの通常参照は同一TEI世界内で開かれたままとし、特定データが保護対象に指定された場合に限り当該Scopeの開示制御を別に扱う。未解決は否定の事実と同じではない。

## 8. 人間向けの五つのProjection

1. **軸・時点付き組織図**：どの階層か、業務有効日、公開版、必要なら記録時点、循環や未解決箇所を表示。
2. **人物/職位/所属一覧**：本務、兼務、出向、職位、参照元と有効期間を区別。テナント実行権限は別欄で現行確認の状態を示す。
3. **組織変更の影響表**：変更対象・消滅/新設・配属移動・不整合・影響を受けるFunction/Procedure/Query/承認Rule、公開前後の件数。
4. **判断の理由表示**：対象申請、適用Rule版、組織軸・有効時点、たどったRelation、候補導出、業務拒否、現在の実行認可、実際の効果を別行にする。
5. **Query構造と小Dataset**：CTE/サブクエリの仮想集合、Field lineage、例示入力/期待出力、不完全なread-set、実行時の監査/公開制約を結び付ける。

どのProjectionも同じ受理済み意味への型付き参照を保つ。配置、色、表示順はPresentationであり、正本の別コピーではない。Sourceを更新する場合は既存のProposal→Preview→Validation→Acceptance→再投影を使う。

## 11. 継続検討：判定の完全性は「取得集合」「対象集合」「業務規則」の三つに分ける（2026-10-30）

本節は他チャットのSQL構造モデル・Lean集合完全性・変更Impactの議論を#2386に接続する設計候補。現行APIの確立済み能力や実行済み試験ではない。SQL構造Explainは[#2387](https://github.com/hat47x/tei-platform/issues/2387)が所有し、同Issueで確認された現行`DerivedIR`/`RelationalIR`を再利用する。複雑なCTE/再帰Queryのread-only説明によって、現行D2実行preflightの非対応Query拒否を解除しない。

### 11.1 具体的な失敗例：取得分だけの全件検査

業務対象の集合`L`に対して、Providerの返却`R`が真部分集合だったとする。例えば、全承認担当候補`L={P2,P3}`に対し、連携結果`R={P2}`。P2に自己承認違反がなくても、P3の利益相反や対象組織の追加関係については何も判断できない。`checkAll(R)`の成立だけでは`checkAll(L)`を主張できない。逆に`R`が空集合でも、必要集合が空とは限らない。

- **形式・部分取得の構造検査**：ある返却集合`R`の各要素が型・Relation・期間制約を満たすか。
- **対象範囲と取得の完全性**：対象スコープ、関係軸、業務有効日、recorded time、公開組織版、Page/Continuation、filter、Provider snapshotに対して`R=L`が保証されるか。必要な`L`は直接列挙できないこともあるため、APIの返却値だけで保証したことにはしない。完全性の証拠は、契約された取得範囲、paginationの完遂、同版read、Source/Providerの保証と照合に基づく。
- **業務規則の適用**：その完全集合へ適用したRuleの版、対象の属性、空集合とNULLの意味、業務Ownerの受理状態。
- **現在の実行権限**：業務意味の判断とは独立にHostによる認可と実行直前の再確認。

対象集合の意味を定められないときは、**Closed-world（指定範囲を完全とみなす）/Open-world（未取得を不在とみなさない）**の契約が未確定として残る。個別Providerの返却状況やSQLで`COUNT=0`を得たことだけからClosed-world契約を導入しない。

### 11.2 「候補なし」の意味を閉じたテストと実Providerで分ける（2026-10-31訂正）

通常の設計・テストでは、業務Ownerが受理した対象範囲・0件・NULL・不在の意味を定義し、**閉じた小fixtureに対する独立Expectationと正負試験**で検証する。すべての0件に数学的な不存在証明、全域のProvider完全性証明や新しいProof Engineを義務づけない（#2387で確認された2026-10-30の方針に合わせる）。

一方、**現実のProviderに部分取得・権限制限・ページ欠損等が判明していて、全業務対象に対する「候補なし」を主張する場合**は、以下を区別する。
1. 対象業務スコープ、利用する組織軸、適用時点・Rule版と、そのスコープの閉世界／開世界のOwner前提。
2. 実際の取得範囲、ページ・継続トークン、Snapshot/組織版、欠損・非開示が判定へ影響するかというProvider側の根拠。
3. 業務規則の期待値。特殊な保護対象データや別運用主体との境界がある場合に限り、その結果開示条件も別に記録する。

必要な範囲が未取得なら「**取得した範囲では候補なし**」と「**業務対象全体で候補なし**」は別の主張である。区別できないときは判定不能/未検証を示す。内部では正当な空集合、未取得、Provider障害を区別し、特例として保護対象が非開示ならその状態も別に記録する。新しい万能Boolean/Confidence/Review-stateをCoreへ採用しない。

### 11.3 Graph/Rule/Impact連携時の区別

組織モデルの関係変更から影響候補が出ても、Impactの候補列挙は**全変更先が列挙された**証明ではない。これまでのImpact討議では、非列挙の対象や経路を現APIが直接返すとは確認されていない。まずGraph/Rule/Validate診断をConsumerが局所的に照合し、評価範囲を含めて説明する。第二のRule正本、全経路Trace、完備性の保証を先に実装済み扱いしない。

## 12. 再評価の選別：組織・業務規則・委任の変化は独立した入力

承認判断の意味上の依存を概念的に次のように整理する。これは新しいトークン形式やSchemaの採用ではなく、最小の比較票である。

| 依存 | なぜ必要か | 変化した場合に失効するもの |
| --- | --- | --- |
| 申請対象Dataと業務版 | 対象金額・所属・申請状態等 | そのデータに依存する判断、既存の操作前提 |
| Organization scope/axis/valid/recorded/published revision | 所属/階層の経路と候補の根拠 | その組織関係を参照した候補・説明・シミュレーション結果 |
| Rule/Procedure revision | 候補の選択規則、除外条件、承認過程 | 当該Ruleに依存する**過去の現在性表示**。変更が業務上遡及適用されるかはOwner判断 |
| Delegation/Account/Host Authority epoch | 実操作者の有効Grant・失効 | 現行アクセス許可と未確定の操作。過去に確定した効果を自動抹消しない |
| Query source/IR coverage/Provider completeness | どの集合を実際に検査できたか | Queryの説明の完全性、対象集合の判断、再利用可能な結果 |
| Realization/Target Build | どの生成物・Providerを使ったか | 実行適合・観測の再現資格。業務意味が自動で変わるわけではない |

### 12.1 最小の変更シナリオ

- **A：組織だけが改編**。業務Ruleは不変でも、対象部門の上位関係がR7→R8に変わると候補の再導出が必要になる可能性がある。Ruleは再受理しないが旧候補をcurrentと呼ばない。
- **B：Ruleだけが変更**。部門・所属・Queryのbytesが同一でも、例えば「部門長のみ」→「部門長と管理本部長の二者承認」と改訂した場合は旧判断の現在性を再評価する。元の過去判断の記録は残す。すべての進行中申請を新ルールへ適用するかはOwnerが決める。
- **C：委任だけが失効**。業務上の所属と候補選定は変わらない可能性があるが、実行許可は失われる。受理済み組織意味を無理に変更する必要はない。
- **D：表示名だけが変更**。同一性を保持する単純なラベル変更なら業務判断まで無条件に無効化しない。ただしラベルから外部IDを推定する未受理Consumerがあれば別の問題として検査する。
- **E：Source/Rule版不変でProviderの返却が部分欠損**。取得対象のcoverageが変わったなら旧`PASS`を全件保証に再利用しない。

依存の完備性が確認できない場合は「関係が無いので影響なし」を断定しない。保守的に再検査へ回すか、未判定を明示する。部分グラフを完全な不変境界とみなさない。

## 13. 複数法人・複数テナント・複数の立場

人物の所属と、アカウントと、現在の実行時の立場は別々の対象である。次の例では、同じ人物P1が法人Aへ雇用され、法人Bの業務プロジェクトに兼務し、テナントTA・TBのどちらにもアカウント対応があり得る。

```text
人物P1
 ├─ 雇用関係: A社
 ├─ 本務: A社営業部
 ├─ 兼務: B社共同事業室
 ├─ TAにおけるアカウント対応: 検証済みか要確認
 └─ TBにおけるアカウント対応: 検証済みか要確認

個別Action
 ├─ 実操作者: 検証済みPrincipal（Hostが供給）
 ├─ 業務上の活動主体: A社営業部の職務／B社共同事業室の職務など
 ├─ 対象TenantとResource: Host/Providerで明示
 ├─ 代理/委任: あるなら別の根拠として扱う
 └─ 実行許可: Hostの現在Authorityによって別途判断
```

活動主体の選択は実行時権限を発行する操作ではない。**同一TEI世界内の組織Data参照**ではA社/B社の所属・在任・役職を通常のRelationとして横断利用できる。B社テナントが別の運用・Host保護境界である場合には、その外部側の実操作権限を別に確認する。業務上の活動主体を切り替えることも、現在のGrantを発行・失効する操作ではない。

Microsoft Entraのcross-tenant synchronizationは、他テナントのユーザーを作成・更新・削除するProvisioning機構であり、アクセス設定や組織の業務意味とは別に運用される。現行説明では同期のSource of Authorityはobject単位で、属性別の任意な双方向正本にはならない。この例はTEIでも`同期された`、`本人として確認された`、`業務上所属する`、`操作を許可される`を独立に示す必要性の根拠になる。

- https://learn.microsoft.com/en-us/entra/identity/multi-tenant-organizations/cross-tenant-synchronization-overview
- https://learn.microsoft.com/en-us/entra/external-id/cross-tenant-access-overview

動的な活動主体や組織スコープの選択は、通常の組織Dataへのアクセス制御とは独立に扱う。**別の配備・運用Tenantが実際に保護境界を持つ構成**ではHostがその境界で実行対象とGrantを検査し、Client自己申告のRole/Org/Tenantを許可根拠にしない（#1769）。同一TEI世界内の複数法人・組織を横断した候補表示・人数集計・存在検査には組織モジュール固有の機密扱いを課さない。個別保護対象が含まれる場合だけ開示範囲を別途検証する。

## 14. 人の作業を「候補→引受→実行→確定」として扱う

業務手順（#1125）に記したActorと、実際の担当者のLifecycleを分ける。CamundaのTask管理は候補グループと個人によるClaimを分ける参考事例だが、TEIではワークフローエンジンを標準必須にしない。

- **候補列挙**：組織関係や職務から担当可能な集合を求める。未確定・複数・0件も説明する。
- **割当/引受**：具体的な担当者が処理を引き受ける。複数候補が同時に選ぶ競合は既存Resource/Action版で制御する実現候補。
- **実行**：実操作者・代理・操作対象・職務分掌・Authorityを現在の時点で検証する。
- **確定と観測**：業務結果、実DB等で確定したEffect、手動確認、独立read、結果不明を区別する。

組織異動により引受者が失効したとき、(a)既存担当の継続、(b)割当を取り消して再選定、(c)職務責任者へ移譲、(d)保留して人が判断、を業務上の選択肢とする。勝手な自動再割当てはしない。

- https://docs.camunda.io/docs/8.9/apis-tools/frontend-development/task-applications/introduction-to-task-applications/
- https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/

## 16. 組織階層と集計：共通経路と二重計上（2026-10-30追補）

組織階層は単に担当責任者を見つけるためではなく、部門別実績、予算、原価配賦、月次集計の経路を決める。自己参照型の期間別階層と、同じ対象が複数経路から現れる部品表型を区別する知見に基づき、**階層経路の多重度と集計の重複**を独立した検査対象にする。

例えば`営業統括→事業部A→共通センターC`と`営業統括→事業部B→共通センターC`がともに有効な場合、`C`の実績10を単純な経路展開で二回数えると20になる。これは、二重計上が業務上正しいという配賦規則が存在しない限り、集計の正しい結果ではない。人事階層がツリーでも、兼務・機能横断や会計の階層を同じものとして用いるとこうした問題が起きる。

- 集計の軸、レベル、参照年月、対象Dataの業務識別、経路の重複、配賦比率・加重方式を区別する。
- 正しい意味が「一度だけ計上」「配賦率で分ける」「各経路に全額計上」のいずれかは業務Ownerが決める。
- `DISTINCT`や`GROUP BY`をSQLに自動で挿入するだけでは、配賦の業務意味は確定しない。
- 集計結果の0円/NULL/対象なし/対象未取得/未認可は別の根拠。Queryの行数が多いことも欠落の反証ではない。
- 原価の所属・部門の親は業務有効時点で選ぶ。階層のレベルは永久属性ではなく、軸・年月・公開版に対して再計算され得る。

**ORG-21（未実行）**：二経路から参照される共通センターCに実績10を置き、表示するQuery経路・合計・配賦規則の関係を説明。二重計上を既定で業務上正しいとしない。既存#2387のQuery演算説明、#1126のRelation、#1131のDatasetを再利用する。

## 17. 組織関係に条件を加える際の境界

OpenFGAのRelationship-Based Access Control、条件付き関係、実行時の条件式は、利用者・組織・資源の関係と用途/時点等の条件を組み合わせる実装候補として参考になる。ただし、TEIの`所属`や`業務上の責任`を認可用の関係Tupleへ全件転写することは目標ではない。

- 受理された組織モデルの**業務事実**と、認可Providerに登録された**権限関係**は別のライフサイクルを持つ。
- 条件式を実行時に変更可能な方式を採用する場合も、誰が条件を変更できるか、版の固定、入力の出所、式の対象範囲、機密の開示、監査、無限に拡がる権限を防ぐ仕組みが必要。
- 版・変更イベント・失効を越えて旧判断をcache再利用しない。DB直読・高い一貫性を要求しても、業務SourceとProviderの版の結合・実際のCommit保証は別の検査。
- TEIのModelerから条件を編集できるようにする場合は、変更候補→検証→Owner受理→Hostの正式配備・権限付与という境界を保つ。編集完了で即時Grant発行とはしない。

**ORG-22（未実行）**：組織R7・業務RuleB1のまま、認可側の委任がEpochA1→A2で失効したケース。旧認可結果の再使用を拒み、業務上の候補導出と認可失効を別行で説明。条件が未受理の場合に任意式を動的に実行しない。

## 19. 組織ドメインの最小直交概念と、基本Data/Relationへの表現（2026-10-30提案）

### 19.1 MECEの対象は「組織を構成するための概念空間」というメタレベルである（Owner指摘により修正）

旧案の「組織についての七つの問いを分ける」だけでは不十分だった。**MECEの直接の対象は個別の人物・法人・組織・業態の分類でも、その用途を尋ねる質問のリストでもない。組織を表現する概念を生成・合成・検証するためのメタレベルの概念空間**である。

- **TEIの基礎メタモデル**：Data、Relation、属性、検証・規則、Action/Procedure、参照、差分など、組織以外にも使う汎用構造。
- **組織のメタ概念空間（本節の主対象）**：存在の同一性、関係依存性、役割・地位、権能と義務、変化と継続性、制度/時間/適用範囲といった意味の異なる次元。組織ドメインの意味型がどこから生まれるのかを規定する。
- **業種・制度別Profile**：企業人事・連結企業集団・公共機関・学校・共同事業・プロジェクトなど、組織メタ概念を組み合わせて固有意味と制約を具体化。
- **案件のAccepted meaning**：特定の法人/組織/人物/職位/規則/関係の事例。業務Ownerが責任を持って受理する対象。

この区分は、Core、標準Plugin、案件テンプレート、具体的なデータモデルが直ちに四つの異なる保存形式を持つことを意味しない。同一の汎用構造で表し、概念をどの抽象階層で定義しているかを型付き参照で保持する。

### 19.2 メタ概念空間の検討観点（直交性・MECE成立は未検証）

以下は初期段階の検討観点である。§22で示した通り、すべてが数学的に独立した直交軸だと主張するものではない。意味の構成形式と、重ねて適用できる判別特性を分けて検証する。

**第一の要求**：異なる意味の判断を一つの曖昧な`organization`/`role`/`authority`へ混ぜない。**第二の要求**：同じ意味を別の軸で重複定義しない。**第三の要求**：あるドメインで必要な意味を表せないとき、どのメタ次元が不足したか反証可能に示す。

| メタ次元 | 定義し分けるもの | 意味上の対照例 | 実装時の扱い |
| --- | --- | --- | --- |
| **存在と同一性** | 個体/集合/地位/制度的対象の同一性をどの条件で保持するか | Person、Legal Entity、OrgUnit、Position、組織共同体 | Dataのidentity・分類、主体ごとの同一性原理。名称・DB PKで代用しない |
| **関係と依存性** | 関係の参加者、役割、独立性、存在依存、構成・参加・配置・支配などの意味 | 部門の上下/構成、人物の所属、雇用関係、職位への配置 | 型付きRelationと必要時の関係実体化。関係の多重度・循環・存続条件を独立指定 |
| **地位・役割・機能** | 対象そのもの、占める社会的地位、状況で担う役割を区別 | Person≠Position、在任≠責任、申請者と承認候補 | Contextを持つ型/Relation/Procedure。空席職位や兼務を表現 |
| **規範性** | 事実（is）、義務（ought）、権能（may decide）、禁止、実行時の許可（system may execute）を混同しない | 「部長である」≠「決裁権限がある」≠「Hostが現在実行を許す」 | Business Rule/ConstraintとHost Authorityを異なるOwnerで管理 |
| **変化と継続性** | 出来事、変更指示、状態遷移、同一性の継続・再識別を区別 | 任命、辞令、組織改編、統合/分割、改称 | Event/Change Set、前後のRelation、SourceとIdentity migrationを分ける |
| **文脈と適用範囲** | 業務有効時点、記録時点、制度・管轄、関係軸、モデル版、テナント/実行環境を別の座標として使う | 人事軸と会計軸、2027年の所属と2026年に知られていた所属 | Fact/Ruleへの限定子。TenantはHostの保護境界として独立 |

**注意**：これらは「六種類のオブジェクトの互いに排他的な集合」ではない。メタ概念空間の**意味軸**であり、一つの具体的事象は複数の軸に座標を持つ。例えば部長への就任は「地位」「人物と職位の関係」「就任イベント」「発効時点」「規則」を同時に使用する。この意味軸をMECEと呼べるかは、各軸の定義域と他の軸からの暗黙推論の禁止、さらに必要なドメイン事例の網羅性を確認してから判断する。

**別の横断次元**として、意味の出所・Source identity・受理/未受理・鮮度・説明可能性を管理する。これらは**知識・根拠の管理**であって、組織の存在論そのものへ新しい組織種別として混入させない。保護のための開示制御と現在Authorityも同様に組織意味の第二正本にしない。

#### 19.2.1 メタモデルの「分類」と「合成」を取り違えない

ある具体的な概念が複数の分類に入ることは正常である。例えば、企業は法人という法的地位を持つ組織であり、契約上の当事者であり、グループの構成員でもある。したがって`LegalEntity`と`Organization`を排他的な型にすると不自然になる。

逆に、**関係とその結果、役割と担い手、規範と事実、業務権能と実行時認可**は、同じ概念へ畳むと意味が失われる。これらが概念空間で異なる軸にあることを明示する。

必要時の`Assignment`実体化も「新たな基本メタカテゴリの追加」ではない。関係の具体的な発生を識別可能なDataとして表し、その参加者・有効期間・根拠をRelationと属性で結ぶ表現選択に過ぎない。

#### 19.2.2 目標とするMECEを形式的に検査する方法

- **対象の限定**：何を分類しているかをまず明記。モデルの記述要素、組織ドメインの意味概念、案件の実体/関係、証拠・権限、UI Projectionを混在させない。
- **軸ごとの値域**：各意味軸に対し、選択肢、値が未確定の場合、適用対象外の場合、複数値が認められる場合を型・制約で明示。未確定を適当な値で埋めない。
- **非重複性の反例検査**：一つの宣言から、異なるOwnerが競合する業務意味を推論できないか。例えば`headOf`から`approved=true`を直接生成しない。
- **網羅性の反例検査**：小規模/グループ/公的組織/マトリクス/異動のReferenceに、欠けた意味がないか。未表現なものを単に`その他`へ吸収するのでなく、メタ軸・語彙・案件規則・Host機能のどこが不足か診断。
- **最小性の検査**：あるメタ次元がなくても、全Referenceで同じ区別と制約が表現できるなら独立次元として必須化しない。逆に別次元から推論すると情報が失われるなら分離維持。
- **合成の閉包**：各次元を組み合わせたときに矛盾や暗黙の権限昇格を生まない。構成可能であることは無制限な組合せの業務上の妥当性を意味しない。

比較対象として[OntoUML/UFO](https://ontouml.readthedocs.io/en/latest/intro/ufo.html)の、対象の同一性・役割・関係の実体化、出来事、社会的な規範性を区別する基礎的な概念分析は有用。ただし、その分類体系・meta-classや推論機構をTEIへ採用する提案ではない。まずTEI既存基本構造との対応と必要十分性を検証する。

### 19.3 特に混同しやすい概念を分ける

- **法人（Legal Entity）**：法的責任や契約を負う主体。**組織単位**：業務編成上の単位。**企業集団・共同体**：法人間関係や協業をまとめる単位。ある対象が複数分類に該当してもよい。**テナント**は配備・保護上の区分であり、このいずれとも一対一とは限らない。
- **人物（Person）**：人の同一性。**雇用関係（Employment）**：契約・在籍の関係。**所属（Membership）**：ある組織との関係。**配置（Assignment）**：ある期間、どの職位や職務を担うか。自動的な相互推論は業務契約が必要。
- **職位（Position/Post）**：担当者が欠けても残り得る席。**在任者（Occupant）**：その席へ配置された人。**業務役割（Business Role）**：作業や責任の性質。**認可Role/Grant**：実行上の許可根拠。職位・役割・権限は異なる。
- **業務上の権能**：どの契約・規程・規則に基づき何を決める責任・権能があるか。**実行権限**：現在のHost/Providerが、本人/代理、対象、アクション、条件に照らして何を実行させるか。前者が真でも後者を自動で真にしない。
- **命令・変更イベント**：発令の根拠と一括変更の経緯。**現在の構造**：宣言により有効となった関係の集合。イベント記録を遡ることと、その時点の業務状態を取得することは同じ処理ではない。

### 19.4 必要なときだけ関係を実体化する

最小構成では`Person—memberOf→OrgUnit`という直接のRelationでよい。兼務、在任期間、発令、出向元・先、主務/副務、証拠、取消など複数の属性が関係自体に必要になったとき、関係を`Assignment`等のDataとして実体化し、Person・OrgUnit・Positionへの型付きRelationを張る。

概念の切替えは**「基本モデルを捨てて別モデルにする」**ことではない。基本Relationは、詳細関係から安全に導出できる場合のProjectionとして残せる。反対に、基本Relation一件から、存在しなかった任期・発令・兼務比率を推測して補完しない。

例（仕様として確定したDSL構文ではなく、人が理解するための概念表現）：

```text
法人：A社
組織：A社 / 営業部
職位：A社 / 営業部 / 部長（空席でも存続）

人物：P1
雇用：P1 -- A社
所属：P1 -- 営業部（主務、2027-04-01から）
在任：P1 -- 営業部長（2027-04-01から）
業務規則：申請者の所属部門の上位責任者を承認候補とする
実行権限：上記の関係とは別にHostで照合
```

これらの図・表・日本語DSL・SQL構造説明は同一のAccepted meaningを参照する。業務上の規則の見出しをModelerで編集するときも、Projection metadataへ第二正本を作らない。

### 19.5 組織ドメインの標準機能はPlugin/Profileとして構成する

TEI Coreは型付きData/Relation、識別・参照、Rule/Validation、Capability/Source/Acceptanceの公開契約を提供する。組織ドメイン固有の意味語彙、型付きRelation制約、表示・生成・シミュレーションの組合せは、標準Organization Pluginと仕様Template/Profileに置く**候補**。

- Organization Semantic Profile：法人、部門、職位、所属、雇用、配置、統制・配賦関係の意味分類と、各関係型の制約。
- Organization DSL Plugin：人が読める名称・簡潔な文法・ルール記述を既存Semanticへ解析する（#988）。DSLはTEI Coreの特別な言語ではない。
- Organization Projections：部門/複数軸の組織図、人物別配置一覧、職位の空席図、変更前後差分、責任・権能の根拠経路を同じ正本から投影（#1124/#1803）。
- Organization Reference Cases：意味の小Dataset/Scenarioを使い、循環、兼務、複数親、多重集計、取得欠落、遡及変更、代理拒否を各々独立に評価（#1131/#2387）。
- Organization Business Specification Templates：小規模/グループ企業/プロジェクト/公共組織などを組み立てる開始点（#998）。Template採用はProject意味の正式受理ではない。

上記は責務上の分類であり、五つの独立配布物・固定テーブル・Go module・実行時Plugin dependencyを義務づける案ではない。ADR-0033の管理上のサブプロジェクトと生成物/配備単位の区別を保つ。Go等のTEI開発ツールチェーンとは別に、.NET/Java/WASM等の生成物で組織意味を実現する際、TEI独自HostやGo Runtimeを必須にしない。

### 19.6 「権限」を一種類の関係で表すことは避ける

組織に関する「権限」は複数の問いへ分解される。

| 問い | 最小の意味 |
| --- | --- |
| **責任を負うか** | 業務・契約・規程上のAccountability / Obligation |
| **判断の権能があるか** | 承認・決裁・指図など業務上のDecision Right |
| **行為を代行できるか** | 意思と根拠のある委任・代理の適用条件 |
| **システムが実行を許すか** | Authentication、Tenant/Resource Scope、現在Grant、Effect Fence |

例えば「部長である」は職位・在任という業務事実だが、「予算決裁権がある」はその職位等に結び付く業務Rule/規程であり、「今日の基幹システムへ入れる」は現在の認可である。どれも一つの属性`isManager=true`の派生として同一視しない。

[W3C ODRL](https://www.w3.org/TR/odrl-model/)は許諾・禁止・義務・条件を区別する比較対象、[W3C PROV-O](https://www.w3.org/TR/prov-o/)は実施した行為と責任・代理・来歴を区別する比較対象。どちらも全契約をそのままTEIに採用するものではない。

| --- | --- | --- |

## 21. MECEメタ概念空間の反証可能性：独立性と必要十分性の試験案

**ORG-25（NOT RUN）**：組織意味の概念空間が、単なる用語リストや画面項目の直和ではなく、異なる意味次元の合成であることを固定fixtureで検査する。新しいTEI Core kindは作らず、既存Data/Relation/Rule/Scenarioで可能な説明と不足を比較する。

| 反例 | メタ概念空間で必要な区別 | 識別できなければどこが破綻するか |
| --- | --- | --- |
| A：営業部長の職位はあるが在任者は不在 | 同一性を持つ職位、人物との在任関係、文脈 | 単純な「人物.role=部長」だけでは空席を表現できない |
| B：A社は法人、B社の支配会社、共同事業の参加者である | 対象の分類、支配・参加など別の関係 | 法人と親会社と参加者を互いに排他的な型へ押し込むと同一対象の重複が起きる |
| C：P1が部長でも100万円超の承認権能を持たない | 地位/在任という事実、業務上の規範、Host実行認可 | 役職名から承認許可を自動生成してしまう |

| F：HRシステムの一行が業務上未確認の個人を指す | 外部ソース、識別候補、業務上の受理 | Sourceに記録があるだけで同一人物と判定してしまう |
| G：同じ共通部門が二本の組織経路に現れる | 関係型の多重度、業務集計の規則 | 構造上の多重経路と、決算上の二重計上の可否を混同する |

### 21.1 採否判断の記録形式

各反例について、少なくとも以下の列を埋める（未実行なら空欄・未判定を保持）：`必要な意味の区別`、`TEI既存構造での表現`、`Organization Profileの型/規則`、`正しいSource/受理`、`禁止したい推論`、`表示・Scenarioでの観測`、`なお不足する意味`。

- **独立性**：同じ意味を複数の根拠・Ruleに保持したために、変更後に一方だけ古くなるなら、メタ概念の分担を見直す。
- **最小性**：削除した概念が他の構成要素から損失なく表現できるなら、Profileの派生概念へ下げる。逆に空席・代理・関係の期間などが失われる場合は明示的な意味概念として保持する。
- **十分性**：説明しきれない反例を、未確定・不支持・権限上の非開示へ分類し、無理に万能な型へ吸収しない。
- **可読性**：Modeler/設計書では、選択した「法人」「配置」「職位」の各要素がどのメタ次元・基本Data/Relation/Ruleに対応し、どの業務制約で結び付くかを段階的に追えること。
- **後方互換**：直接所属を使う小規模モデルが詳細な雇用・在任モデルに進化するとき、追加していない属性や受理されていない権能を推測せず、既存の業務意味を保つ。

この試験は「完全にMECEである」と証明する方法ではない。概念の重複と欠落を発見するための**反証可能な圧力試験**であり、網羅性の範囲は代表Referenceと合意した業務ドメインに限定する。

## 22. メタ概念空間の二層分解：分類と判別軸を混同しない（2026-10-30追補、採用前）

### 22.1 以前の「六つの独立軸」に対する自己修正

§19.2の「存在/同一性」「関係/依存」「地位/役割」「規範性」「変化/継続性」「文脈/適用範囲」は重要な**設計上の関心**だが、厳密に独立で互いに重ならない軸だと証明したわけではない。例えば役割は関係への依存を持ち、規範には適用時点があり、イベントは対象と関係を変更する。従って**六分割そのものをMECEの証明としない**。

「MECE」の対象は引き続き**組織の意味を構成するメタ概念空間**だが、次の二層を分けて実証する。

1. **モデル記述上の主たる形式（構成文法）**：対象の定義、関係の定義、規則/制約の定義、出来事・遷移の定義を、**同じ宣言が複数の正本カテゴリに所属しないように**記述する候補。これは文書/モデル宣言の役割の分類であって、「現実の対象・事実・イベントが互いに排他的な存在分類をなす」という意味ではない。例えば発令イベントは独立した識別子を持つ対象としてもData化できる。
2. **各概念を評価する横断的なメタ特性**：同一性、存続条件、存在依存、部分全体、役割の一時性、関係の多重度、規範の種類、時点・版・制度の適用範囲など。これらは**複数同時に該当し得る**ので、MECEな一列の種別表にしない。

合成された業務ドメインの語彙（法人、部門、職位、雇用、所属、在任、決裁、出向、異動等）は、上述の形式と特性の**組合せ**として表す。この定義を案件のProject Accepted意味へ無承認で適用しない。

### 22.2 基本形式からの合成例（DSL構文を確定しない概念式）

| 業務概念 | 構成の概念式 | 識別・依存・規範の確認 |
| --- | --- | --- |
| 人物 | 対象の定義 + 人物の同一性条件 | 雇用先が変わっても人物の同一性を失わない |
| 職位 | 対象の定義 + 特定組織/制度への依存 | 在任者が0人でも職位は存続し得る |
| 所属 | 型付き関係（Agent, Organization） + 期間/出典等 | 人物・法人・雇用関係と別のID/成立条件を持つ場合がある |
| 配置 | 関係（Agent, Position, Organization, Validity 等）を必要時に実体化 | 兼務・空席・複数在任を、関係型ごとのConstraintで定義 |
| 決裁権能 | 規範的Rule + 対象/行為/条件/根拠/適用範囲 | 「役職あり」から規範が存在すると暗黙推論しない |
| 人事異動 | Change/Transition + Before/After関係集合 + 発効/記録時点 | 発令が存在することと、業務関係が公開・適用されたことは別 |
| テナント実行許可 | 現在のHost Authority + Principal/Target/Resource/Action + Effect Fence | 上記の業務事実や規範から自動でGrantを発行しない |

**補足**：「組織」「法人」「共同事業体」を基本形式の排他的な子種別として固定しない。複数の制度的役割や類型へ同一対象が属することを許し、その意味が成立する条件を区別する。

### 22.3 合成規則（新しい公開ABIの採用前の確認項目）

- **対象／関係**：関係は参加する対象の意味型、役割、数、期間と適用範囲を明示。多項関係は必要時にDataとして実体化可能。既存Relationの意味を推測で上書きしない。
- **対象／役割**：本質的な対象の分類と、関係の成立によって一時的に担う役割を区別。例えば「人物」が「従業員」「部長」「申請者」でなくなっても人物として存続し得る。
- **関係／規範**：所属・上位関係・在任が成立しても、決裁権能・業務義務・利益相反の例外は**別途明示されたRuleにのみ**従う。規則のSourceと発効、判断時点を保持する。
- **出来事／状態**：命令・承認された変更集合と、実際に適用・公開された関係状態は別。状態遷移前後の整合と再実行安全性を検証。
- **文脈の交差**：時点、組織軸、管轄/制度、法人、Tenant、規則版等は同じ種類のscopeではない。交差する条件の意味と優先順位を案件/Plugin Ruleで明示し、不明なら未判定とする。
- **出所／受理／実行**：Sourceからの推測、受理済み業務意味、現在Authority、外部で確定したEffectは異なる。証拠の形式的整合を意味受理や認可へ昇格させない。

OntoCleanのrigidity/identity/unity/dependenceは**concept classに対するメタ特性**を評価する知見として使う。UFO/OntoUMLのendurant/event/role/relation等の区別は合成規則への圧力試験に使う。全Ontologyの分類木や推論器、哲学的な永続性をTEI Coreに導入しない。

## 23. 「概念空間の正規化」と受入に必要な証拠（新設、未実行）

正規化の目的はテーブルの物理正規化ではなく、**意味の責任・宣言・導出の重複を検出すること**。モデル構成には「構成した意味を二重に書き込まず、原理的に導出できる部分はProjectionへ置く」という規律を設ける。

| 意味の重複・混同 | 誤った構成 | 正規化案 | 受入の判定 |
| --- | --- | --- | --- |
| 人物と雇用 | Personの識別を人事社員番号に固定 | Personの同一性とSource別Employment/External IDを区別 | 複数雇用/異なる人事IDで誤結合せず未解決を残せる |
| 職位と在任 | PositionにoccupantIdだけを埋込 | PositionとOccupancy Relation/Assignmentに分離 | 空席・兼務・在任交替時の同一性が保持される |
| 所属と権能 | `manager=true`→`canApprove=true` | 在任/業務上の選定Rule/業務権能を分離 | 規則だけ変えても本人・職位・所属が更新されない |
| 組織親子と会計帰属 | 全関係をparent列に格納 | 関係型/軸/配賦Ruleを分離 | 多経路と重複集計の意味が可視化される |
| 辞令と現在所属 | 発令登録時に即時全Consumerへ現行反映したと仮定 | Change Setの受理、業務有効、公開revisionを分離 | 公開前/後と外部未反映を混同しない |
| メタ定義と案件定義 | 標準PluginのRuleを案件Owner受理なく適用 | 標準Semantic Profile、Template候補、案件Acceptedを区別 | Plugin更新が案件意味を暗黙改訂しない |

### 23.1 合成における「必要十分」の評価手順

1. **既存Data/Relation等への低位表現**を、概念ごとに一例示す。対応不能なものだけを差分として報告。
2. **概念追加の必要性**：その新しい区別がない場合に失敗する実務Referenceと、誤推論または表現不能の負例を要求。
3. **重複排除**：同じ事実/規範を複数のPlugin/DSL/図/Sourceが正本として保持していないかを比較。表示上の同一要素の重複は許す。
4. **変更閉包と影響**：一つの関係/Ruleの改訂によって、どの導出表示/Simulationを無効化するか。既存Impactが網羅性を保証しなければ保守的に未判定とする。
5. **説明の可読性**：ModelerとSHOの双方で、具体的概念→構成メタ形式→基礎Data/Relation→根拠Rule→Scenario/Sourceへ段階的にナビゲート可能か。
6. **外部相互利用**：Organization Semantic Profileを他Plugin/外部製品が利用するとき、Capability契約と分類の意味を公開できるか。Obsidian等の特定製品APIを組織メタモデルへ固定しない。
7. **不要依存の除去**：Organization Profileを含まない生成物に、組織DSLのParser/Runtime、履歴・組織図の実装を必須化しない。実現先.NET/Java/WASMでは外部Hostに委譲し、TEI専用HostやGo Runtimeを必須にしない。

MECEは任意の世界全体に対する完全性を数学的に証明したとは主張せず、**合意した概念宇宙Uとモデル記述形式Fの範囲での全域性・非重複性**、および**メタ特性の矛盾回避と合成の十分性**を別の検査に分割する。

## 25. 組織メタモデルの保存則と片方向投影（2026-10-30：他チャット横断）

### 25.1 メタレベルの概念を組み合わせても守るべき保存則

前節の構成文法（対象、関係、規則、出来事）と判別特性は概念を構成する候補である。ただし、**形式の組合せができることと、業務意味を保てることを別に検査**する。概念空間の必要十分性は単に分類の網羅だけでは検査できない。

| 保存則 | 内容 | 禁止する誤推論 |
| --- | --- | --- |
| **同一性保存** | Person、Org、Position、Assignment、Eventなどは、それぞれ受理された同一性条件で識別 | 同名、社員番号一致、同じ物理PKから自動的に同一業務対象とする |
| **依存関係の向き** | ある在任・雇用・所属は参加者や制度に依存し得るが、人物/職位の存在が必ずしもその在任関係に依存するわけではない | 退職でPersonを消す、空席でPositionを消す |
| **事実と規範の分離** | Fact/Relationが成立しても、義務・決裁権能・禁止・許可には別の規範的根拠が要る | `holds(position)`→`approve=true` |
| **変更と状態の分離** | ChangeEventの登録・承認と、指定時点の関係・公開組織版・外部Provider状態は別 | 発令を登録しただけで全テナントに反映済みとする |
| **投影の情報損失の明示** | 詳細Relationから単純Relationへ投影できても、逆算で消えた期間・根拠・主務/副務を補えない | `memberOf`から実体化Assignmentを根拠付きで創作 |
| **集合・多重度の保存** | 関係経路の列挙、DB Queryのbag semantics、配賦規則を区別 | `DISTINCT`によって業務的な二重計上を正したと宣言 |
| **意味受理とAuthority分離** | Source／Candidate／Accepted Rule／Host Grant／実Effectを別状態とする | AI案/検証PASS/Source byte一致を決裁権能・実行許可へ昇格 |

### 25.2 単純Relationと詳細Relationの可逆性を先に判定

例えば`Assignment A1=(Person=P1,Position=M1,Org=D1,valid=[2027-04-01,2027-07-01),主務,Source=S1)`がある場合、**所属とみなす規則が正式に定義され、対象時点とスコープが一致し、取得集合が完全**なら、`memberOf(P1,D1)`を導出して表示できる。

`projection(detail)=simple`は成立し得るが、一般には`inverse(simple)=detail`は成立しない。逆方向には、職位M1、任期、主務/副務、辞令Source、独立なAssignment IDという情報が不足する。UIが直接所属を編集した場合に黙って任期付きAssignmentを生成しない。対応不能は「詳細未決の業務関係」または明示的な導出・入力候補として残し、Owner受理を必要とする。

この片方向性はW3C Organization Ontologyの直接`memberOf`・`Membership`・`Post`の使い分け、およびOntoUML/UFOのmaterial relationとRelatorを区別する議論と整合する。ただし、それらの外部OntologyをTEIの意味正本として採用するわけではない。

- https://www.w3.org/TR/vocab-org/
- https://ontouml.readthedocs.io/en/latest/classes/sortals/relator/index.html
- https://ontouml.readthedocs.io/en/init-ontouml/relationships/material/index.html

### 25.3 概念をなくす試験と、不要な導出を禁止する試験

**ORG-32（NOT RUN）**：同じ`memberOf(P1,D1)`を、(a)期間のみの所属と、(b)特定職位への任命/主務/発令に由来する所属へ投影する。投影結果が同じでも元の詳細が異なることを示し、逆方向の無根拠な再構成を拒否する。**比較票は両者のSource/identity/validity/Owner状態を別行にする**。

**ORG-33（NOT RUN）**：関係`employedBy(P1,A)`が消滅し、同一人物P1の別会社への関係が開始した場合、Personの同一性が保たれ、雇用・配置だけが変化することを検証。外部社員番号の再利用や失効をPersonの同一性規則にしない。

### 29.2 「候補の選択範囲」と「実行対象」の別の穴

#1174の2026-10-31更新で指摘された、Capabilityの抽象的Grantと個別業務対象への許可の不一致を、組織承認にも適用する。例えば`approve`というCapabilityへのGrantがあっても、具体的な`Q1`申請・所属D1・決裁金額に対する許可は自動では成立しない。Ruleの評価対象集合`L`、取得された集合`R`、実際にEffectされる対象`E`、Host Grant scopeを同一視しない。

- 意味上の`L`は案件のRule/選定条件で定義し、通常は閉じたDatasetで期待値を比較。明らかな部分取得があるときだけその限界を反映する。
- `R`の構造的に正しいパース/Query Lineageは`R=L`を保証しない。#2387のQueryのScope/Source occurrence誤結合リスクが解決されるまでは「Full」表示も根拠不足の可能性がある（静的仮説、実測未確認）。
- `E`は実際に更新される受注/申請等の**対象識別**とAuthority Scopeに対応させ、従来Capability Grantがその範囲を保証しているかを#1174のAdapter側で検査。組織の所属から認可Grantを自動生成しない。
- V（Owner業務Invariant）、K（Receipt/Commit）、O（独立業務状態）を別々の証拠として残す。Kが確定してもV/業務完了は未確認となり得る。

### 29.3 業務規則の改版を跨ぐ再送：過去のEffect≠現在の意味適合

## 31. 横断論点をP0-M・P0-Vの停止条件へ統合（2026-10-31追補）

本節は§29〜30で選んだ**二つのP0 Referenceを実行しやすくするための受入条件**であり、さらに別のORG Case IDや新しいTEI Core schemaを追加しない。2026-10-31の再照合mainは`1e8d3031aee7881bf6907f7774c9dba7a438e11e`、本書は旧mainからのDraft branch上にある。以下の静的観測は、確認したソースに限る。

### 31.1 「Domain」「型」「値域」を組織のメタ概念と混ぜない

他チャットでの命名決定に合わせ、**Domainは企業・組織・技術・自然現象等を含む意味の対象領域**として用いる。属性が取り得る単独の値集合を一般に`Domain`とだけ呼ぶのは避け、**Value Domain / 値域 / 値制約**とする。

| 異なる層 | 例 | 区別の根拠 |
| --- | --- | --- |
| Domain / 対象領域 | 組織・企業というドメイン | 意味・規則を調べる対象。Businessに限定しない |
| Meta concept / 概念形成の規則 | 同一性を持つ対象、地位、関係、規範、変化、文脈 | 個別の部門名・職位名に依存しない構成原理 |
| Semantic Type / 意味型 | 部門識別子、職位識別子、雇用先識別子 | 値表現が同じ文字列でも意味的に統合できるとは限らない |
| Value Domain / 値域・値制約 | 「主務/兼務」の許容値、適用日付範囲、社員番号の書式 | 許容値を検査する。識別・業務権能・適用制度をこれだけで確定しない |
| Instance / 事例 | A社、部署D1、職位M1、人物P1 | 受理されたモデル上の特定対象・関係 |
| Physical Representation | 社員番号列、DB型、UIのID/表示名 | 意味型・業務同一性の代替ではない |

**P0-M停止条件**：`DepartmentID`と`PositionID`がともに文字列として表現できても、それらを同じ意味型と認定する根拠にはならない。組織概念を「単一属性のValue Domainの一覧」に還元した、または意味型名から法的/組織的意味を推測した場合は、意味の合成が成立したとしない。意味型の統合・再編は既存#1806へ委ね、組織Profileの側で第二のType体系を作らない。

### 31.2 P0-M：同じ対象に対する異なる記述形式の合成を検査

比較対象を**同一Subject**に固定する。例えば、`Person P1`、`Org D1`、`Position M1`、`Occupancy A1`、`Rule B1`、`Request Q1`。以下は実装の新フィールド名ではなく、検査の意味条件。

1. **構成**：直接`memberOf(P1,D1)`と、根拠を持つ多項`Assignment`をData/Relationで記述。後者の意味を前者へ投影するとき、必要な時点、対象、関係型、集合完全性を明示する。
2. **情報損失**：詳細Assignment→単純Relationでは、根拠Source、職位、任期、主務/兼務比率、在任IDが失われ得ることを一覧化。逆向きで情報を補完しない。
3. **変化**：`M1`の在任者がP2→P3へ交替しても、職位の業務同一性が存続するという**案件仮説**を比較。別の制度では職位自体を廃止する可能性を残す。
4. **規範**：`B1`（部門長一人を候補）と`B2`（二者承認）を、Position/Occupancyとは独立に変更できるか。Rule変更をGrant更新や業務完了と同一視しない。
5. **表現**：組織図・表・DSL・SQL構造Explain・SHO文書は同一Source/Subjectへの投影。native SQLのQuery-IRや表現上のaliasからPerson/OrganizationのSemantic identityを創作しない。

**合格扱いの最小条件**：「保存された意味」「投影で失われた意味」「既存TEIで未表現の意味」「業務Ownerによる未受理」を別々に示せること。美しい組織図の生成、型の一致、byte一致だけでは不足。現行`internal/semantic/model.go`にはData/Relation、Type alias、業務キー/FDと限定Validationがあるが、これを組織Profileの完全な動的Rule evaluatorとは見なさない。

### 31.3 P0-V：業務時点の切替と、状態変更の競合は別

§29のQ1責任部門D1→D2という**同一Tx内の後続更新**による反例に加え、データが変わらなくても時点が変わる反例を同じP0-Vの補助条件とする。

`2027-06-30 23:59:59`では職位M1の在任者P2、`2027-07-01 00:00:01`ではP3であるとする。Q1の事前候補はP2だったとしても、「承認実行時の組織関係を使う」という**Owner受理済みのRuleがある場合に限り**、発効境界後のP2による確定を再検査する必要がある。逆に、「申請受付時点の候補を案件完了まで固定する」というRuleも選択肢として有効であり、TEIが勝手に前者を既定としない。

**四つの異なる時点/版を混ぜない**：業務上の適用時点、データが記録・訂正された時点、参照した組織/Ruleの公開Revision、実行時Grant/権限版。必ずしも一つの全域Revisionとして整列していない。跨Providerの完全に原子的な切替も前提としない。

| 補助条件 | 検査対象 | 停止条件 |
| --- | --- | --- |
| **後続Mutation** | `P(S_checked)` vs `P(S_committed)`、同一Q1の責任部門D1→D2 | 最終Post-ImageでB1の不変条件が保証できないのにCommit成功を業務上正しいとする |
| **業務有効日の切替** | 同一Q1でP2→P3、Ruleで定める評価時点と有効な組織版 | 申請日/検査時刻/Commit時刻のどれを採用するか未決のまま承認者を確定する |
| **Ruleのみ改版** | 組織R1不変、B1→B2、進行中案件への適用 | 古いB1の候補・ReceiptをB2適合として再利用する |
| **Grantのみ失効** | 組織/Rule不変、Host Grant A1→A2 | 業務上の候補を実行許可として扱う |
| **Provider部分取得** | 業務対象Lと返却R、対象scope/鮮度/完全性 | `checkAll(R)`の成功を`checkAll(L)`や「候補が存在しない」の証明にする |

組織関連Sourceが外部HR/IdPなら、DB内の`Q1`更新に同一Txを使っただけではSource read-setの鮮度/完全性を保証しない。逆に通常の0件/NULLをすべて「不存在の数学的証明問題」に置き換えない。**閉じたDatasetやProviderが保証する範囲内**での0件/NULLの業務意味はOwnerが規定し、通常の負例テストで確認する（#1131/#2387）。

### 31.4 Script/低水準経路ごとの保証範囲を明記する

他チャットで明確化したTEI Scriptの公開範囲を、この組織承認の最終状態チェックに反映する。

| 書込み経路 | 許容する設計方針 | Q1の組織/決裁不変条件について言えること |
| --- | --- | --- |
| **標準Function/Smart Data binding** | #1129で、Pure Rule・before-write・same-Tx・post-commitを区別する。既存Hostに必要な保証を委譲 | 最終Post-Imageでの業務不変条件を保持する設計/試験が必要。Bind/Evaluate成功だけでは未保証 |
| **開発者・管理者の信頼済み低水準Script** | 開発環境で開発物に広い制御権を認め、生SQLや低水準Tx利用を一律禁止しない | 低水準操作が標準FunctionのGuardを通ったとは推測しない。製品側が保証する検証範囲と、Script作者が責任を負う範囲を明示する |
| **利用者向けMacro/制限付きScript** | 明示されたCapability/Service ContractとScopeだけを公開する候補 | 委任された機能を使っても個別Q1の判断・Grantを独自発行しない。Guard迂回経路や低水準更新権を既定で公開しない |

**停止条件**：標準FunctionでP0-VがPASSしても、別の書込み経路でQ1責任部門を変更できる場合に、「全ての更新経路で組織Rule不変」と宣言しない。全経路で不変条件を保つ必要があるか、どの経路は作成者・運用者の責任とするかはOwner判断。開発環境の開発者権限と、配備後の本番Host Authorityを同じものとはしない。

### 31.5 証拠/状態の型を増やさず、受入票に区別を残す

実行状態は、(a)構造表現可能、(b)ルール評価可能、(c)最後のMutation後でも業務不変条件を保てる、(d)現在Authorityで実行可能、(e)確定した副作用を観測した、(f)Ownerが意味を受理した、に分ける。これらは**評価観点**であって、新しい`status` enumやReceipt schemaの提案ではない。

独立した`P(S_committed)`の検証根拠が不足すれば、既存の`effectcommit`でAuthority/Receipt/CAS/Commitが扱われていても、その成功を最終業務Invariantの証明としない。Receiptは当時確定した効果の記録であり、現在のB2/組織R2に再適合したことの証拠ではない。副作用と業務上の完了判定の差は既存#1174/#1129/#1119の記録へ委ねる。

### 32.1 P0-Mの観測同値・関係の導出可能性を明示する（2026-10-31、採用前）

**一つの技術的区別**：「詳細な関係をDataとして実体化できること」と「その関係が単純な所属を**意味的に含意すること**」は別。後者にはOwnerが受理した**導出規則**が要る。

最小の合成事例：
- `D1` は部門、`M1` はD1に置かれる職位、`P2` は人物、`A1` は`P2 occupies M1`という2027-06-30時点の配置。これだけでは、`memberOf(P2,D1)`の**業務上の意味**を確定しない。例えば外部委託者に在任・代行を認める組織では、職位占有から在籍所属を推論できるとは限らない。
- Owner受理済みの橋渡しRule `occupies(P,M) ∧ positionIn(M,D) ∧ eligibility(P,M,D,C) ⇒ memberOf(P,D,C)` が存在し、`C=(有効日,制度/組織軸,Rule版,Source/取得scope)`の必要条件を満たしたときだけ、当該Scopeでの単純Relationを**派生表示**できる。Ruleに存在しない条件を推測で追加しない。
- 複数の詳細配置`A1={P2,M1,D1,期間T1,根拠S1}`と`A2={P2,M2,D1,期間T2,根拠S2}`は同じ単純`memberOf(P2,D1)`へ投影され得る。したがって投影は一般に**多対一**であり、単純Relationから職位/期間/根拠/配置IDを逆構成できない。

ここでの受入は、案件が従来利用していた**承認済み観測集合Q**（例：指定時点の直接所属表示）に対する旧モデルと新モデルの観測値が一致する、という**限定された観測同値**とする。数学的に書けば`∀q∈Q, ∀c∈C_test: q(M_old,c)=q(M_new,c)`が対象である。`C_test`を代表fixtureに限定した評価なら**実世界の全時点/全業務での完全同値ではない**。新しい職位・在任・権能Queryまで旧単純モデルと等価とは主張しない。

**最小P0-Mの正負観測**：①受理済み橋渡しRuleと完全な合成Datasetで同じ所属を表示、②橋渡しRule不在なら派生所属を断定しない、③二つの詳細配置が同じ所属表示へ畳まれても逆構成を拒否、④期間終了・制度軸切替では対象文脈を再指定、⑤`DepartmentID`と`PositionID`の同じ基底文字列から同一対象を導出しない。評価不能・Source範囲不明は**検査票の未判定**として記録し、既存`Validation`へ未採用の新Outcome enumを追加しない。

### 32.2 P0-Vの最小依存閉包とOwner-write Coverage（既存#1129の保証責任を再利用）

#1129の[Data-attached Rule / Owner-write Coverage CV-2](https://github.com/hat47x/tei-platform/issues/1129#issuecomment-6535115011)を踏まえ、組織側が定義するのは**業務規範B1の評価に必要な意味依存集合**だけに絞る。これを既存Function/Providerに渡す契約上の入力候補とし、第二のRuntime/Enforcerは作らない。

`B1`（Q1の責任部門の有効な部門長在任者を候補とし、申請者本人を除く）の依存候補：
`Deps(B1)={Q1.responsibleOrg, Q1.applicant, PositionIn(M,D), Occupancy(P,M,valid), 受理された候補選定Rule版, Ruleが採る評価時点/組織軸, 取得集合の必要範囲}`。

- **評価時点が固定でない場合**、データが一切更新されなくても、業務有効日の境界を跨ぐだけで評価結果が変わり得る。時計・有効期間は「書込みの有無」と独立した影響要因。
- **間接的なEffect**：`Function approve(Q1)`の事前判定後、別の`Function transferResponsibility(Q1,D2)`や下位Capabilityが`Q1.responsibleOrg`を更新した場合、同Txであっても`B1(S_checked)`を`B1(S_final)`へ昇格させない。
- **無関係な更新**：たとえば`Q1.memo`だけ変更し、Ruleが参照する全依存・時点が変わらず、対象集合の同版完全性を確認できるなら、当該更新だけを理由にB1の無条件再評価を義務にしない。
- **依存不明**：Scriptや未解析SQLの間接更新範囲が解決できないとき、`Deps∩Writes=∅`を立証したことにはしない。未判定と記録し、保守的な実施方式は#1129 Owner/Providerが決める。

**判定の原理**：Owner Ruleが最終Post-Imageで真であることを要求する場合、必要な書込みの依存閉包と時間境界について、(a)最終関連Mutation後の再検査、(b)対象を守るProvider/DB制約・条件付き書込み、(c)関連Mutationが最終検査後に起こらないと保証できるOwner Actionなど、**実装が実証した方式**によって成立させる。これは概念上の代替方式であり、全アプリ・全Providerに既定の再検査/DB機構を課すものではない。

**Function-use Binding と Owner-write Enforcementを別行で記録**する：
- Function-use：利用者向け画面、Function内のプレビューや候補表示にB1を適用できたか。
- Owner-write：Owner管理下の**正当な書込み入口**（別Function/API/子Capability/間接更新を含む）から、保存対象とRule適用Scopeに対する最終の必須規範が保証されるか。

既存Providerが対象入口を保証できる範囲を実証することと、外部の未管理の生DB書込みが絶対に存在しないことの証明は別。Trusted Scriptの広い能力は許容し、どの更新経路が**covered / uncovered / unknown**かを受入票に残す（新公開status enumではない）。

**同じQ1を使う最小対照（いずれもNOT RUN）**：

| 比較 | Rule依存への変化 | P0で観測すべき判定 |
| --- | --- | --- |
| F1：候補評価後、Q1のメモのみ修正 | 既知の依存に交差なし | 不要な全Rule再評価なしに整合性を説明できるか |
| F2：候補評価後、別Functionが責任部署D1→D2を変更 | `Q1.responsibleOrg`が変わる | `P(S_final)`の再保証なしに承認を確定したなら不適合 |
| F3：関係・Rule版は不変だが、業務有効時点を跨ぐ | 時間依存が変わり得る | Ownerの評価時点規則が未決なら最終候補を確定しない |
| F4：非管理のTrusted Scriptが同じ対象を直接更新 | Providerが管理しない経路 | 標準FunctionのPASSを全書込み経路の保証と表示しない |

この行列は#1129 FS-1/Owner-write Coverage、#1174 Effect Fence/TS-CUT1、#1131 Scenarioを**参照する組織用の意味差分**に限定する。Commit/Receipt/rollbackの結果分類、新Validator/Function Hook API/Source Registry、Leanによる不存在証明を本Issueで設計・実装しない。

## 33. メタ概念空間を一般Data Facetと接続する（2026-11-01：スコープ拡張）

**発展の方向**：既存P0-M（組織の意味と関係投影）・P0-V（最終状態の必須規範）は、実証を始めるための**小さな検証単位**とする。一方、製品要件、標準Organization Profile、Issue、比較対象、適用分野の探索には人為的な上限を設けず、#2493/#2495のAI大量並列開発・メタ概念空間の方針と同期する。探索を縮小するためにP0を使わない。

### 33.1 TEIの一般メタ空間との関係

[TEI #2495](https://github.com/hat47x/tei-platform/issues/2495)では、プログラミング言語の単一型階層を基準にするのではなく、**何を指すか／どう構成されるか／数学的性質／量・単位・時空間／利用・観測／Targetへの実現**というメタレベルの質問を分離し、複数のfacetと多重上位概念を許す案が検討されている。組織メタモデルはこの一般構造の**Domain専門化**として位置づける。

| 一般メタ空間での関心 | 組織に固有の構成要素・facet | 絶対に同一視しないもの |
| --- | --- | --- |
| **対象の同一性** | Person, Legal Entity, Organizational Unit, Position, Collaboration, Agent | 社員番号＝Person ID、法人＝Tenant、ログインPrincipal＝自然人 |
| **構成・Relation** | membership, occupancy, employment, reporting, control, delegation, collaboration; n-ary assignment | SQL JOIN＝受理済み業務Relation、二経路＝二組織 |
| **位相・グラフ性質** | 人事階層の木、マトリクスDAG、提携ネットワーク、行為の承認依存グラフ | Tree型を独立な組織Core kindと固定、全グラフに同一循環制約 |
| **規範と意思決定** | accountability, obligation, prohibition, business decision right, conflict-of-interest | role/occupancy＝Host Grant、候補選定＝実行の許可 |
| **時間/制度の文脈** | valid time, recorded time, org axis, jurisdiction, policy revision, change event | 現在のシステム時計＝業務上の有効時点、同値の全域revision |
| **数量・集合** | FTE、兼務比率、予算配賦、multi-parent到達経路、集計grain | 割合の合計が1とは限らない、Relation bagの経路数＝組織数 |
| **認識・証拠** | Source identity、未確認Mapping、Ownerの規程受理、表示可能範囲 | 外部人事Sourceの取得＝事実の受理、証拠byte一致＝権限取得 |
| **物理実現** | RDB、JSON、Directory/SCIM、.NET/Java/WASM、組織図、SHO | 物理SchemaやWIT/MCPが組織意味の正本 |

多重上位概念は、`is-a`（必要な同一性・制約の包含）、`has-facet`（独立の観点）、`acts-as`（文脈上の役割）、`composed-of`、`represented-as`、`implemented-by`を区別した**意味付きエッジ**として検討する。例えば「法人Aが企業グループの一員であり、契約主体であり、共同事業の参加者でもある」ことは、同じ対象に複数facet/Relationが成立するという意味であって、自動的にGo/Javaのmultiple inheritanceや型変換を要求する意味ではない。

**MECEの検証対象**は各観点が担う意味の責務、構成に必要な情報、推論の許容条件。実際の対象が複数の意味facetを持つことは正常である。規範/組織構造/認可/証拠は複数段階で関係するが、一つの曖昧な`authority`へ畳まず独立の正本と責任を識別する。

### 33.2 ユーザー・AI・組織主体の「行為」を分解する

Organization Profileが対象にする`Agent`はPersonに限らない。法人、外部委託組織、明示的に承認されたサービス主体、AI Agentも業務上の行為の参加者になり得る。**Actorの分類と、実行のPrincipal/権限主体の同一性は別**に扱う。

| 問い | 参照概念 | 組織Profile側で必要な区別 |
| --- | --- | --- |
| 誰が実際に操作したか | Invoker / Runtime Principal | 認証・Hostによる証明を要する |
| 誰のために行ったか | Represented party / On-behalf-of | 被代理者・組織、関係の有効性 |
| 誰が判断の責任を持つか | Accountability holder / Decision Owner | 制度・規則に由来する業務意味 |
| 誰が作成・配置・呼出しを認めたか | Author / Publisher / Invoker policy | Source/承認版/対象/期間/委任元を分離 |
| 何をどこまで任されたか | Delegation / Service Contract scope | Action, Resource, Context, Expiry, Revocation、必要な職務分掌 |
| どの操作が実際に許可・確定されたか | Host Grant / Effect / Receipt / Observation | 現在Grant、個別対象、最後のMutation、実確定は別 |

「AIエージェントが部門の代理として購買候補を作る」「人がその候補を承認する」「外部Hostが購買を確定する」は三つの異なる出来事と責任。役割facetや組織規程は提案・判断候補を作れるが、Host Grant・Token・秘密・更新権を自己発行できない。実行Targetが異なるときは外部Hostの実保証を明示する。

### 33.3 メタ区別は標準構造の設計原理でありPlugin作者の記述義務ではない（2026-11-01 Owner明確化）

**メタレベルの分類・facet・構成文法は、主としてTEIの標準データ構造を設計・発展させるための内部的な整理**である。通常の案件設計者や標準/独自Plugin作者が`is-a`、`has-facet`、同一性保存則、Rigidity等のオントロジー概念を理解・宣言してからDataを利用する設計にはしない。Profileごとに専用の上位オントロジーや全facetアノテーション、特別なメタDSLを記述することも基本要件ではない。

**通常の開発者の作業**は、すでに利用しているTEIの標準Data/Field/TypeRef/Relation/Key/制約/Operation/Ruleの組み合わせを使って、必要な意味と関係を宣言すること。例えば「部署」「職位」「在任」「所属」「有効期間」を既存の標準構造へ定義する。背後のメタ整理は、これらの構造がなぜ同じ抽象で扱え、どう接続できるかを説明し、標準構造を拡張するときの重複や概念の衝突を避けるために使う。

**後から効いてくる効果**は、標準UI/Operation/Query/Studio/SHOなどの一般Consumerが、共通構造に既に定義されている情報を利用できる点にある。特定組織PluginがUIフレームワークの内部事情を知らなくても、標準構造に合致したモデルから一般画面・編集操作・可視化候補を構成できるようにする。次は**推奨候補であり、現時点で実装済みの動作を意味しない**。

| 標準Data側で得られる構造的事実 | 標準Consumerによる利用候補 | 推測で付加しない業務意味 |
| --- | --- | --- |
| Entity/Field/Key/Value Constraint | 一覧、単票、入力・選択・Validation表示 | フィールド名から権限や必須業務手順を創作 |
| Relationの1:N・N:M／参照先ID | 親子一覧、明細Block、関係選択、Graph表示 | JOINしただけで雇用/直属上司などの業務関係を受理 |
| 親子Relationとその軸／循環制約 | Tree/Graph、展開ナビゲーション、複数経路の可視化 | あらゆるParent関係を人事階層・権限継承と断定 |
| 期間・時点の明示的な型付き関係 | as-of検索、期間選択、Timeline/Gantt候補 | 任意の日付列を発令日・業務有効日へ自動認定 |
| Declared Operation/Ruleと必要なContext | 標準CRUD/Command UI、確認・結果表示 | UIから表示できることを実行認可やCommit成功と見なす |

**自動構成の範囲**：形状が十分に宣言されている場合は、一般UIの実装側がレイアウト・編集部品・ナビゲーション・入力検査の既定を導出する。形状から判別できない業務意味（例：どのRelationが正式な指揮命令系統か、どの時点が業務判断基準か）は明示的な元の業務Rule/意味定義で解決する。形状が不足すれば候補または未対応として表示し、勝手な決め打ちをしない。組織Pluginが明示的な専用UIを提供することも可能だが、基本機能の利用にそれを必須化しない。

**内部設計と開発体験の二段階を分離**：
- *標準構造の設計者*：メタレベルの区別を使ってData/Relation/Value/Context等の責務の重複・欠落・接続可能性を整える。
- *通常のPlugin/案件開発者*：整えられた標準構造へ必要なData/Relation/Ruleを定義する。メタオントロジーの学習・毎回の宣言を前提にしない。
- *標準Consumerの作者*：標準構造の契約を用いてUI等を組み立てる。業務意味の正本はモデル側に保持し、UI状態を第二正本にしない。

**最小評価候補（NOT RUN、既存#1127/#1124/#2495と共通）**：①専門的なメタfacet宣言ゼロの通常Data/Relationから一覧・単票・1:N明細を導出可能か、②Org上の関係を1:N→N:Mに変更してもPlugin側の専用UI実装を強制せず適切な表現候補になるか、③期間/親子の曖昧な構造に特定の指揮命令/発効規則を推測しないか、④通常の組織Dataの参照へ余分なアクセス制御を挿入しないか、⑤編集されたUI操作が実行時の元Subject/Relation/Ruleへ正しく対応するか。

**設計上の帰結**：今後一般メタ空間の研究が深まっても、通常のPlugin作者向けのAPIを新しいメタ語彙で肥大化させる必要はない。必要な区別はまず**標準構造の設計とConsumerの共通解釈に蓄積**し、現行構造で表現できない明白な反例が現れたときだけ、互換性と導出効果を比較して拡張を検討する。

### 33.4 トポロジーを超える意味的な可視化（2026-11-01 Owner追補・設計候補）

標準UIが将来利用するのは**グラフの隣接・多重度・木/DAG/循環だけではない**。同じグラフ構造の辺/節点でも、対象・関係の意味（役割、同一性、依存、期間、規範、由来）によって理解すべき内容と表示/操作のあり方が異なる。メタレベルの区別を標準Data構造に整える意義は、後から**意味を保った視覚文法とインタラクション**を選べることにある。

#### 意味の違いが可視化へ与える具体的な効果

| 標準構造/受理済み意味から識別できること | 同じトポロジーであっても必要な表示差 | 編集・照会に伴う注意 |
| --- | --- | --- |
| **恒常的な対象（Person）と一時的なRole/Occupancy** | Personの同一ノードと職位の別ノード、空席の職位、在任線の開始/終了を別々に表現 | 在任者の交替をPerson消滅・職位再生成とみなさない |
| **単純な所属と根拠を持つAssignment** | 単純線の上に、必要時だけ在任・辞令・期間・Sourceへ展開できる説明リンクを置く | 派生所属線への直接編集を黙って詳細Assignmentの正本変更にしない |
| **部品-全体、参加、所属、依存、指揮命令** | 同じA→Bの矢印でも関係の種類を線種・端点・ラベル・配置規則等で識別（具体表記はUI側で設計） | どの関係が権限/集計へ影響するかを線の向きだけから推測しない |
| **規範（義務・禁止・候補選定）と実際の行為/確定効果** | 規則・未確定の候補経路・実行済みEffectを視覚的に別の意味状態として追う | 「部長なので承認候補」と「承認した」を同一チェックマークにしない |
| **発効時点・記録時点・公開Revision** | 指定したas-of組織図、関係の期間、変更前後差分、訂正・遡及を可視化する | `as-of`の日付がどの時間軸か明確にし、両時点を混同しない |
| **直接Fact、Rule由来の派生、未確認Candidate** | 同じ場所に重なる要素でも、直接根拠／導出された関係／未受理提案を明確に識別し、根拠へ辿れる | Source/Ownerの受理状態を省略表示によって変更しない |
| **1人が複数関係経路に現れる、Queryがbagを返す** | Graph上の人物は同一IDを保持、関係経路は複数表示可能。集計grainに応じて1人または2経路と明示 | 人数カウントとpathカウントを混同しない |

#### 標準UIが利用する情報の深さは段階的でよい

- **L0: 構造のみ**：Field、Key、Relation、cardinality等から表・一覧・単票・親子Block・汎用Graphを生成する。通常のPlugin開発者はここから始められる。
- **L1: 型付き関係の意味**：Role、Association、composition、validityのような情報が**すでに標準構造に明示されている場合**に、適切なビューや操作の候補を選ぶ。型名や列名だけで意味種別を推測しない。
- **L2: ドメイン規則の明示的な意味**：Owner受理済みRule/Relation/Procedureに基づき、空席・兼務・承認候補・禁止・変更差分などの説明可能なViewを構成する。専門Pluginが持つRuleから取得できる範囲を利用し、Plugin作者へ一般メタ概念の手入力を強制しない。
- **L3: 出所・時間・判断・結果**：視点の用途に応じ、元の意味ID、直接/派生/候補、valid/recorded時点、Source、Rule版、Owner受理、独立のEffect観測を重ねる。ここでも出所・意味受理・実行許可は異なる。

L0〜L3は**表示/説明の増分的な能力レベルの分析用ラベル**であり、新しいCore enum、保存Schema、各Pluginの義務や実装済み機能ではない。すべてのViewで全情報を同時表示するのではなく、利用者の目的別に選択・展開・比較できる設計とする。

#### 可視化の設計原則と既存責務

参考知見：[Moody et al., *Visual syntax does matter* (2010)](https://link.springer.com/article/10.1007/s00766-010-0100-1)は、視覚的記法の**意味的な透明性、記号の識別性、複雑さの管理、図間統合、認知的適合**などを重視する。[Cheng (2011)](https://pubmed.ncbi.nlm.nih.gov/25164400/)は概念領域の基本構造を表現方式そのものへ符号化する意義を論じる。[OntoUMLの関係説明](https://ontouml.readthedocs.io/en/init-ontouml/relationships/intro.html)は形式的なrelationと、雇用等の独立した関係的根拠を伴うrelationを区別する。これらは**可視化研究の参照**であり、特定の図記号や外部Ontologyの自動採用ではない。

**表現の制約**：配色だけで意味を伝えず、ラベル/線種/位置/ツールチップ/キーボード操作や表形式でも識別可能にする。情報が多い場合には概要→関係→根拠→詳細の段階表示を可能にし、利用者と作業目的によってViewを切り替える。任意に多くの記号を作ればよいわけではない。

**Source of Truth**：Canvas、組織図、ER図、Gantt、SHO文書は同じ標準Data/Relation/RuleとAccepted Subjectを参照するProjection。視覚的操作から正本を編集するときは、変更できる元の関係・Rule・Sourceを特定し、派生・提案とAcceptedを区別する（#1124）。標準UIは意味の候補表示を補助できるが、存在しない業務規則を描画の都合で追加しない。

**実証候補（すべてNOT RUN）**：A）同じGraphトポロジーで、所属/雇用/在任の意味が異なるfixtureを用意し、表示・説明・編集先の混同を検出する。B）在任者交替でもPersonとPositionのIdentityが保たれる。C）派生所属と直接所属を可視化で区別し、派生線の編集は根拠の選択/差分確認へ導く。D）同一人物が二経路に現れる表示と1人集計を共に説明できる。E）L0の単純Dataモデルから通常の一覧/Blockが生成され、Plugin側へ追加メタ注釈を要求しない。F）図と表とSHOで同じ元Subjectへナビゲートできる。

責務：**#2495**は標準データ構造を設計するためのメタ概念整理、**#1127/#997**は一般的なUI/Operation候補と構成、**#1124**はStudio/Viewの編集・再投影、**#1803**は文書、**#2386**は組織ドメインでの具体的な意味差分・反例。図記号/ウィジェット/描画エンジンの別実装を本Issueに追加しない。

## 34. 組織標準Profile群：要求の広域探索と概念の再利用

現段階では**標準Organization Plugin/Profileの一つの大きな仕様を固定しない**。代わりに、**共通メタ概念空間＋交換可能な分野Profile＋Scope別Rule＋Conformance fixture**で、企業・公共機関・共同事業・非定型組織を扱えるかを広く検討する。各分野に専用Core型や独自Hostを設ける必要はない。

| Profile探索群（すべて候補） | 特有の構造的圧力 | 最小の比較・負例 |
| --- | --- | --- |
| **小規模事業・事業所** | 少人数、役割兼任、直接所属からの段階的発展 | 空席/複雑Ruleを使わないモデルへ不要な固定表を強制しない |
| **大規模企業・持株会社** | 多法人、子会社、連結、共同支配、管理責任 | 親会社であることから子会社の全Tenantアクセスを導かない |
| **人事・異動管理** | 雇用/在籍/配置/職位/辞令/改組/遡及訂正 | 旧在籍Sourceの部分取得を退職・削除扱いしない |
| **マトリクス・プロジェクト** | 複数報告経路、兼務/FTE、費用配賦、職務分掌 | 重複する経路から二重計上やGrant継承を暗黙決定しない |
| **行政・自治体・公共機関** | 法令/管轄、指定代理、会議体、議決・公示の発効 | 職務上の権能とシステム許可を一致させない |

| **医療・専門職協働** | 有資格者、部署横断、職務責任、例外対応 | 資格・所属の一致だけで患者記録アクセスを許可しない |
| **共同企業体・サプライチェーン** | 契約、協力会社、元請下請、依存/委託関係 | 契約上の代理を全取引・全情報へ一般化しない |
| **分散組織・地域活動・非営利** | 会員、選任、合議、ボランティア、場所と活動 | 労働者・従業員だけをAgentの前提にしない |

| **AIエージェント・サービス組織** | 非人間Actor、契約Provider、代理・委任、作業成果の検証 | Tool登録成功／AI提案を本人の受理・確定Effectとしない |
| **組織の施設・地理・勤務形態** | 多拠点、リモート、勤務時間帯・兼務場所 | Site=Org Unit、Location=権限Scopeを自動的に同一視しない |
| **継続する組織目的と成果** | 目標/制約、部門別負担、制度改訂、例外学習 | 目標の表明を現在の業務Ruleへ無承認で導入しない |

**機能拡張候補**：組織の差分可視化、基幹Sourceマッピング、職位・在任のas-of照会、複数軸集計/配賦、動的承認候補、代理/委任のリスク診断、規程の自然言語化、複数組織の連携仕様、AIとの協働位置付け、緊急時の変化対応シミュレーション。各機能はOwnerが受理した対象意味と、既存Capability・Targetの実能力を照合して提供する。

**探索と実証の両立**：上記は初期のPressure群であり、数・分野・Issueの固定上限ではない。多数の独立調査/PoCを並行してよい。一方、個別の実証結果を参照する際は`repo/issue/base/source/fixture/oracle/evidence/acceptance`を区別し、統合前の比較不能なPASSを寄せ集めて共通Profileの準拠を宣言しない。

## 36. Function Data Context・組織DSL・TAI/SEIとの接続条件

### 36.1 Function Data Contextには「組織のどの意味を表示・操作するか」を渡す

TEI #1127が検討する`Semantic Data/Relations → Function Data Context + Operation Intent → Pattern Matching → Capability Resolution → Presentation Plugin`の導出では、組織領域に次の入力が必要になり得る。

- **対象Context**：Person/Org/Position/AssignmentとそのID。複数1:NやN:M、同一Personが複数の配置に登場する場合も`Selected subject`を曖昧にしない。
- **Relation Context**：参照するRelation型、軸、人事/経理/事業、経路と集計grain、階層の循環規則。Query JOIN/SQL aliasは受理済み業務Relationの代わりにならない。
- **Temporal Context**：valid/recorded時点、公開されたOrg Rule revision、在任期間の判定基準。フィルタの`today`と業務基準日を混同しない。
- **Operation Intent**：一覧/単票/配置差分/候補選定/異動のプレビュー/受理/配備/実実行などを区別。表示中の行選択、Functionへ渡す値、実Effect対象IDを照合。
- **Conformance & exposure**：Functionが必要とするデータ集合の完全性・鮮度を明記。同一TEI世界内の組織Dataには通常の一覧・検索・集計を使う。特例データに限って閲覧制限されたProjectionの取得範囲と、業務上必要な全件の違いを表示する。
- **Target**：同一Accepted Subjectから標準Org Chart、配属表、階層図、監査票、SHO文書、AI CUI、外部HostのContractへ投影する。UI編集の逆写像は案件/Owner受理を要する。

**既存P0-Mへの追加停止条件**：一つの人物が複数職位/複数部門で現れるとき、UIの選択行と`Function Operation`対象が異なるIDにすり替わらない。同じ本人を2行に表示することと、二人の異なるPersonとして扱うことを区別する。

### 36.2 SEI/TAI/外部ハーネスは異なる責務を保つ

- **SEI**：組織が目指す価値・判断の仮説、未決、暗黙の期待、違和感・反証の管理。SEI [#677](https://github.com/hat47x/sei-cognition/issues/677)の組織意志・用途/適用範囲・改版後の再確認を参照する。
- **TEI**：Ownerが受理した組織の同一性・関係・規範・Business Procedure・Rule/Source binding、意味Simulation/生成物の契約。未受理SEI案を自動的に案件のCurrent Ruleにしない。
- **TAI**：Caseの目的・協働・再計画・成果を横断観測。TAI [#165](https://github.com/hat47x/tai-pleroma/issues/165)が対象とする企業・未知課題の自律活動を、TEIの組織意味と関係付ける。
- **EKI/外部Harness**：目的限定のTaskと既存Capabilityを呼ぶConsumer/Worker。結果生成/Tool listing/OperationID一致を「業務判断の採用」「現在権限」「実効果の完了」へ昇格しない。
- **SHO/SUI**：設計書・組織図・仮説と根拠の探索表示。表示の意味Subjectと出典へ遡れること、開示不能・未確認を保持することを確認する。

### 36.3 組織Dataは原則共有利用、個別保護対象だけ例外管理（2026-11-01 Owner訂正）

**基本方針**：同じTEI世界で利用する組織表・関係・配置・職位・組織図・件数は、ほかの通常Dataと同じように参照・編集・検索・Query・Function Data Contextで利用する。組織管理モジュールの存在をアクセス保護の根拠としない。専用ACL、部門別RBAC、RLS、保護用Gateway、匿名化Projection、別DB、OS隔離を組織標準Pluginの必須機能にしない。

**例外の対象**：マイナンバー、クレジットカード情報など、個別の法律・契約・運用要件に基づき保護が必要な項目やデータ集合。保護条件を組織全体ではなく**具体的な属性・レコード・保管・利用用途**に結び付ける。必要な分離・アクセス管理・暗号化・監査等は、当該情報を保持/利用する実際のData/Provider/Hostや既存Delivery機構の責務とし、Organization Domainだけで特殊扱いしない。マイナンバー等の取扱いは案件・法令に沿って別途設計/確認する。

**接続範囲の違い**：通常のTEI内共有アクセスと、独立した外部サービス・別テナント・別のOS/Host・外部AIへデータを転送することは異なる。接続先で実際に保護/分離条件があるときに限り、#2020やTAI [#232](https://github.com/hat47x/tai-pleroma/issues/232)のProfileを適用する。これは組織モジュール標準の閲覧制御ではなく、**境界を跨ぐ接続に固有の要求**である。外部ハーネスで通常データを利用する道も閉ざさない。

**検証の修正**：通常のOrg一覧が権限フィルタなしで正しく動くことを正例とし、個別保護指定したフィールドだけが当該保護仕様に従うことを例外の正負例とする。組織Relation全体が隠れる、承認候補の業務上の取得集合が無用なACLで欠落する、といった機能退行を不適合とする。実Hostの副作用認可（#1174）は従来どおり独立して評価する。

### 36.4 並列開発と検証へ橋渡しする

- **探索Lane**：外部SaaS/OSS/規格を調査し、新たな概念・Profile・業務要件・負例を幅広く収集する（#2493、TAI #233）。候補数の制限は設けない。
- **メタ構造Lane**：#2495の多重facet/typed edge・#2386の制度的意味・#1126のData/Relation表現を対照し、同じ意味を二重に実装しない。
- **Product Lane**：#1127のFunction Data Context、#988のDSL、#1131のScenario、#1124/#1803のModeler/SHOへ、同一受理SubjectのProjectionを渡す。
- **Host/Trust Lane（境界がある用途のみ）**：#2390外部Consumer、#1174実Effectの認可、#2020実際に別運用Tenant/Deliveryを設ける場合、TAI #232の特別な機密隔離要求。組織Dataの標準参照へ追加制御を課さない。
- **Qualification Lane**：各Issueの既存Fixture/Accepted meaning/実Target証拠を、Source revisionと手計算Oracle付きで照合する。新しい全体Gateやすべての標準Pluginに義務付けるCommon Hostを作らない。

**具体的な追加Pressure（新Org Case ID固定前の候補）**：AIが代理で申請作成し承認は人間に残す／グループ企業で兼務する同一Personが二Tenantへアクセスできない／市役所の委員会所属と決裁権能が別／大学研究者が複数機関に研究者として所属するが雇用は一箇所／マトリクスOrgで到達経路2本でも人数1／人事異動の有効日cut／保護指定された特殊情報が外部ハーネスへ不必要に渡らない／AIが提案した制度改正が未受理なら権能不変、など。これらを**認識候補、意味Contract、Host実行、実効果、Owner判断**のいずれで確かめるかを各Laneで明記する。

## 39. 意味に基づく標準可視化の結合試験：同一Person・多経路・在任・集計（2026-11-02横断追補）

**今回の新しい設計判断**：構造のTopologyと意味的な可視化は**対立概念ではなく、異なる情報源**である。標準Data/Relation/Key/Operationが明示する「同一性・関係の粒度・意味型・期間・根拠」と、利用目的・業務Ruleから決まる「何を数え、何を選択し、何を変更したいか」を、標準Consumerが用途に応じて合成する。Plugin作者が抽象Ontological Facetを毎回設定する方式にしない（§33.3〜33.4）。

### 39.1 観測は「同じ図を描けるか」より「何を主張する図か」

可視化・文書・集計は、同じ正本モデルからの**利用目的に相対的なProjection**である。同じ対象を示していても、組織図、人事在任表、FTE配賦チャート、承認候補図が主張する内容は異なる。

| 何を主張するか | 必要な元の意味 | 図の解釈に必須の区別 |
| --- | --- | --- |
| 所属する人物の一覧 | Personの同一性、対象の組織軸、時点、採用した所属Rule | 直接所属／配置から導出された所属、兼務と同一人物 |
| 職位の在任状況 | PositionとOccupancyの独立ID・有効期間 | 空席・交替、PersonとPositionの存続性 |
| 組織の人員数 | 何を1件と数えるか（Person／Membership／Assignment）、集合範囲 | Graphのノード数、経路数、Relation件数の混同 |
| 部門別FTE | 期間・比率・配賦先・配賦Rule・集計軸 | 重複所属の人数と加算可能なFTEは別Measure |
| 責任者/承認候補 | Role/Position/業務規範、候補選定の文脈、評価時点 | 候補・未確定・実行後Effect・現在Host Grantは別 |
| 組織改編前後 | Person/Position/Assignmentの同一性と時点別Revision | 表示から消えた節点や線＝削除済み業務対象、と推定しない |

一般Graphのnode/edge layoutだけではこれらの差を十分に定義できない。一方、Rule等が存在しない場合はL0の汎用Relation表示にとどまることも正当な結果である。

### 39.2 一つの合成Datasetと手計算Oracle（**NOT RUN**）

**業務意味はこのfixture内の明示的な仮定**。実企業や既存TEIの受理済みRuleを意味しない。日付はいずれも合成。

- Person：`P1, P2, P3`（Person subject IDは3件）。
- Org Unit：`D1, D2`（異なる部門）。同一TEI世界の通常Data。部門間の参照/集計に特別なアクセス保護は不要。
- 独立したMembership関係出現：`A1=(P1,D1)`, `A2=(P2,D1)`, `A3=(P2,D2)`, `A4=(P3,D2)`、いずれも当該fixtureで直接受理済みの関係と仮定。

## 42. 意味付き組織Viewの反応的更新と編集セッションの分離（2026-11-02：他チャット同期）

### 42.1 「図を再表示する」よりも「どの主張がいつ有効か」を識別する

同じPerson/Relationから構成するGraph/Table/Chartの更新は、一括の「Viewがstale」判定には還元できない。**Viewが表示しているClaimと、更新された入力の関連性**を先に確かめる。

- **表示情報の更新**：D2の名称変更ではD2のラベルは更新対象だが、Person数、Membership数、明示配賦FTEを無条件に失効させない。人数の値が偶然同じだったというだけで既知の依存性が無いとは言えない。Rule・選択・Source版・取得範囲・Value/Row成立条件に関する根拠が必要。
- **業務上のFactの変更**：Membership A2の有効期間変更はそのRelation、D1所属一覧、D1配賦FTEに影響するが、Person P2の同一性やD2側A3が変わると推測しない。D1の職位M1の在任は別の関係で、影響の規則が存在しない限り独立。
- **Ruleだけの変更**：直接Factを改訂せずに橋渡しRuleのrevだけ変わる場合、Rule由来の所属線の説明・表示資格が変わり得る。直接受理済みA1〜A4を自動更新・破棄しない。
- **時間と履歴**：有効時点（valid time）と「いつそう認識されたか」（recorded/known time）を区別。遡及訂正を現在のViewへ反映しても、「訂正前に何と認識されていたか」を表示する過去の問い合わせは独立に扱う。
- **Context Instance**：画面選択epoch、Definition/Instance ID、親AnchorとSource/Rule版は独立。古い応答の上書き、旧SelectionのAction昇格、別配置のDirty Patch混入を許さない。
- **取得の不完全さ**：画面に存在しないRelationshipや人物を「本当に存在しない」と推論しない。取得済み1件の存在は示せても、集合全体の人数・不存在・最終承認候補の証明には必要Scopeの完全性を照合する。
- **非単調な導出**：`NOT EXISTS`・LEFT JOIN未一致・Top-N・集計では新規行の追加で既存表示が消えたり変化する。差分更新は単純なappendではなく、必要に応じてretract/replaceや全再取得を使う。

これらは共通のReactive Engineの新設を意味しない。[#2582](https://github.com/hat47x/tei-platform/issues/2582)はClaim相対の再評価・通知、[#2506](https://github.com/hat47x/tei-platform/issues/2506)はContext/Result Sliceの所有。組織ドメインは、固有の正負反例と、その独立Oracleを供給する。

### 42.3 差分の種類と、保持すべきView資格

| Change / 条件 | 保持できるもの（条件付き） | 再評価/表示再投影すべきもの | 無根拠な誤処理 |

| 同じRelationの出現順変更 | 集合意味に依存する計数・主張 | row-order依存のView | row indexを業務Relation IDとして保存 |
| A2の遡及訂正 | Person同一性、A3/A4の既知独立Relation | D1当該期間の所属線・FTE、部門関係計数 | valid timeとknown timeの混同、直接/派生Lineの混同 |
| 配賦Rule/値だけ変更 | Relation出現件数・Person数（同一対象前提） | FTEと依存する表示/検証 | FTE変化を業務Entity新規作成とする |
| Ruleだけ改版 | 受理済み直接Membership（保存版はそのまま） | Rule由来の表示・候補・説明・利用資格 | Rule改版をDB上の直接関係の自動変更とする |

### 42.4 Editing Session・一体保存と、標準UIの意味的可視化を混同しない

2026-11-02の別チャットでは、[#2597](https://github.com/hat47x/tei-platform/issues/2597)と[Draft #2601](https://github.com/hat47x/tei-platform/pull/2601)で`Function Definition → Function Instance → Data Context → Editing Session → Save Intent → Action/Effect`が検討されている。組織Viewの例では次の区別が必要。

1. **Functionの二つの配置**：I1でP2のA3関係を編集していても、同一Function Definitionを持つI2のEditing SessionへA3の未保存Patchを渡さない。
2. **P2ノード／A3関係線の区別**：元Subject IDとRelation occurrence IDがそれぞれ異なる。A3のunlinkはP2のEntity deleteではない。
3. **再取得とDirty Patch**：A3の新しいSource結果が到着しても、P2/D2への未保存変更を無音で上書きしない。Revision・Anchor・Instance IDを照合し、競合・未解決・再確認の候補を提示する。
4. **複数変更のSave Intent**：D1所属変更とD2所属変更を同じ組織図から依頼しても、一体のDB Transactionとして保存されるとは限らない。実際のBusiness Action・Provider/Host Tx契約と、個別の結果・部分成功・不明を分ける。
5. **意味上の「組織改編を受理した」と実保存**：Ownerが組織改編案を受理したこと、画面で変更意図を生成したこと、Providerで更新が確定したこと、異動の業務有効日が到来したことは別イベント。UIは各状態を別に投影する。
6. **製品横断の正本**：Document/SHO/AI CUIへの構成Contextは元のAccepted Data/Relation/Ruleと出典・時点へ参照する。[#2516](https://github.com/hat47x/tei-platform/issues/2516)で利用目的別のConstruction Contextを構成する場合も第二の意味正本を作らない。

**組織Dataのアクセス**：同一TEI世界内の部門・配置・関係・集計は通常Dataとして自由に利用する。ここでいう編集時の「元データへの対応」「現在のEffect権限」「特殊保護対象の例外」「独立外部Harnessへの情報送出」は四つの別問題。組織管理モジュールだからという理由で専用ACL/RLSを付けない（§2.4/§36.3）。

## 43. 組織ViewからRequestへの根拠束縛：視覚的同一性と実操作の同一性を分ける（2026-11-02）

### 43.1 本節を追加した理由

他チャットの[TEI #2598](https://github.com/hat47x/tei-platform/issues/2598)では、View変更を型付きIntent候補として説明できても、**実Actionへ渡す際にそのCandidateがどのRead/選択/Action版/Request対象を根拠にしているか**は、別に確認を要すると整理された。同じグラフが描けること、同じIntent表記が残っていること、同じOperationIDやRequestHashを持つことは、**正しい業務関係の変更が実際に行われた証拠ではない**。

この区別を組織の最小反例に落とす。TEIの共通Contractへ新しい本体型や必須の全Facet注釈を追加する提案ではなく、既存Referenceの証拠同士を**同一版・同じ試行に属するか照合するための受入票**とする。

### 43.2 直接Relation A3を解除するときの根拠例

- **元の意味**：Person `P2`、組織`D2`、直接Membership occurrence `A3`。P2は別のD1向けMembership `A2`も持つ。A3解除とP2のEntity削除・A2解除は異なる。
- **Contextの読取根拠**（合成）：Function Instance `I1`、選択Anchor `D2`、selection epoch `7`、meaning revision `org-r7`、Query `membership-q1`、read snapshot `snap-3`、表示Occurrence `edge-display-3`。
- **View変更候補**：対象を`Person P2`ではなく`Membership A3`の`unlink`と解釈する。これが可能でも、**まだHost/Provider実行可能とは確定しない**。
- **Requestとの対応**：既存Business Actionと実対象・Relation role・Expected Revision・Scope・必要な現在性の照合が先に必要。候補A3に対して実PayloadがA2を更新するなら対象不一致。別WindowのI2のDirty PatchをI1へ移すのも対象文脈不一致。
- **実Effectと業務完了**：実Requestに対するHost/Providerの現行Grant、確定境界、実更新先、Receipt、独立Observation、業務完了条件は#1174/#1129/#1125の領域。候補の同定やPayload一致はそこでの受理を代行しない。

この経路の**標準UI上の意味**は、メタレベルの分類を利用者やPlugin開発者に要求することではなく、画面の「線を解除する」という操作が特定のRelation occurrenceへ向かうことを理解できる点にある。

## 44. 単一Sourceから複数Viewへの意味保存：専用オントロジー不要の標準可視化Pressure（2026-11-02）

### 44.1 今回の差分：計数/操作の反例から、複数Viewの同時導出へ

他チャットの#2495/#2497（メタ構造・Projection保存条件）、#2506/#2507（Function Data Context・Pattern）、#2593（Measure）、#2598/#2597（Intent→Request・Editing Session）、#2610（**人が読める業務設計**とHeadless/Effect/SHOの接続）を、**同じモデルから複数の表示を構成する**という一つの実証課題として結ぶ。

**[Draft #2596](https://github.com/hat47x/tei-platform/pull/2596) の `verify-projection.mjs`**は、単一の合成Organization Source `org-synthetic-r7` を入力として、Table・Graph・部門所属Tree/forest・ChartとPositionの時点照会をread-onlyに構成する。以下の事実を利用する。

| Sourceに明示したもの | Table | Graph | Tree/forest | Chart・Timeline |
| --- | --- | --- | --- | --- |
| Person `P1/P2/P3`、Membership `A1〜A4` | 4行、P2は2行、行ID≠Person ID | Personノード3件、Membership Edge4本、P2から2本 | P2は2つの異なるRelation出現を持つ葉として表示可能 | 世界全体のユニークPersonは3、所属出現4を別々に集計 |

**このReferenceで明示的に解決した問題**：Treeには単一親表示の需要があるが、P2のA2/A3という二つの所属から、**先に現れた行を『本務/主たる親』として暗黙選択する根拠はない**。したがって、単一親表示を要求しながら表示上の優先Relationが指定されなければ、両方の所属出現を保持して`unresolved`とする。表示目的の明示的Preferenceが`P2→A2`を選んだときだけA3を**非表示の関係として明示記録**し、Viewを**lossy/read-only**にする。このPreferenceは組織上の本務や指揮命令系統が業務的に受理されたという意味ではない。

**デザイン原則**：Graph/Treeの形が違っても、実体とRelationの元ID・時点・集計の粒度・直接/派生の根拠を一致させる。UserがTree上の表示出現を削除・移動しても、隠れたA3がSourceから消滅したと解釈しない。意味の選択根拠が足りなければ**図を単純化しないこと**も適切な標準UIの応答である。

### 44.2 標準Operationの現実の適用限界（GitHubの実候補コードとの照合）

2026-11-02の[PR #2587](https://github.com/hat47x/tei-platform/pull/2587)は、候補Head `dc2842d241082d6dee89343cfbd9294153d0d403` に`internal/operations/surface.go`（blob `e1024a56e060c2dda4e64343d4eaae647782f84b`）を含む。**これはmainへ統合済みという意味ではない**。同ファイルの`OperationSurface`は、一般的なData単位の`list/read/create/update`などを、SourceのData/Key・Persistence Mapping・既存Capability Effect Bindingに基づき**read-onlyに導出**する仕組みである。そこには`unlink(Membership A3)`のRelation occurrenceの一般導出・実行、Graph/Tree/Chart自動構成は確認できない。

- **この段階で標準化されている可能性のあるもの**：DataのSource/Keyと既存Capabilityの対応、read-onlyな操作候補/不足診断、明示Effect/Bindingに基づくcreate/update実行接続（詳細な成功資格は#2485がOwner）。
- **本Referenceで局所的に示したこと**：`select-relation(A3)`をTable/Graphという異なるViewから、同じ元Relation occurrenceへ対応させられること。Sourceの単なる同一表示行やPerson名だけを根拠にしないこと。
- **これから製品で実証すべきこと**：標準Data/Relation宣言と受理済みActionから、表示候補と`unlink`等の適用可能な操作を#2507/#2500が認識し、既存Capability/Driverへの対象Bindingを#2598で確認できるか。実Effect/Receiptは#1174へ委ねる。
- **拡張の判断方法**：現行標準構造・Pattern/Pluginで表現可能か先に確かめ、反例で不足が確定したときだけ必要な共通意味契約を整理する。全Pluginへ特別なMeta DSL/Facetの登録義務、新Common Host、別のQuery/Action Engineを設ける方向には進まない。

ここから、**標準UIが表示可能であること ≠ 業務上のRelation Actionを標準操作として持つこと ≠ 現在のHostで実行可能なこと**を明示する。開発者向けの通常のData/Relation/Rule宣言は簡潔なままでよい。TEI DSLの文字列表現・Table/Graph記法・モデル作成方法が異なっても、元のData構造と受理済み意味の正本を共有する。

## 45. Everything is Dataを組織可視化で具体化する：共有Source・明示Context・複数Projection（2026-11-02）

### 45.1 一体モデルと利用目的を分ける

11月2日の横断方針[#2619](https://github.com/hat47x/tei-platform/issues/2619)（Everything is Data）、#2620（標準構造＋Role）、#2621（Markdown/Studio）、#2622（Data Operations）によると、Data/Relation/Function/Rule/Script/Scenarioを**標準データ構造と意味Role**で扱い、Markdown表・Graphviz・関数/チェーン・Goa/MukuroL風の簡潔なDSL等を**Authoring上の構文糖衣**とする。

組織モデルでは次の五つを別の意味役割として保持する。

1. **Data/Relationの存在**：P2はA2(P2,D1)とA3(P2,D2)を持つ。Graphで双方を辿れる。
2. **Functionが宣言するRead footprint**：D1のMembershipからID/Person/Deptを取得する等、Relation path・親Anchor・Field/Grain/要求Scopeを明示する。**Data ModelにRelationがあるだけで、そのFunctionがA3まで自動取得するわけではない**。
3. **Providerの観測Result Slice**：`all-for-selected-department`は全件取得を**要求する宣言**。実Providerがpartial/unknownなら、全件の人数や不存在を確定しない。取得したP1の存在証人と未取得P2の不存在は別。
4. **表示目的のProjection**：同じContext/Scope/Source版からTable行とGraph EdgeへA1/A2等の元Relation ID・粒度・選択epoch・取得完全性を保持して投影する。部門別人数2と全体Persons数3、Membership件数4、FTE3.0は別Claim。
5. **編集Intent・実Request・Effect**：`select-relation(A3)`が得られたことは`unlink(A3)`の実行許可ではない。候補→実Request対象→Host/Providerの実EffectとReceipt、Ownerの意味受理をそれぞれ既存担当で評価する。

**Everything is Dataは、全Relationの暗黙Traversal・全件Fetch・業務意味の自動受理を意味しない。** 構文糖衣は増やせる一方、対象/時点/Scope/Rule/Operator版・現在のObservationが明示された範囲で標準UIを構成する。一般のPlugin作者にメタオントロジーの宣言作業を課さず、共通構造と専門Profileを組み合わせる方針を保持する。
