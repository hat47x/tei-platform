## 1. 結論

**規則は「宣言したOperator一つを、名前の付いた入力へ当てたもの」と定める。規則の種別は今ある六つで閉じ、今後は足さない。** 新しい規則はOperatorの宣言、実装、例の三つを足して作る。解析器、種別の列挙、評価器の分岐、読み手の境界は変えない。

この一点から、積み残していた判断が次のように決まる。

| 積み残していた判断 | 決めたこと | 節 |
| --- | --- | --- |
| 二つ以上の項目を受け取るOperatorの宣言 | 入力に名前、型、範囲、読むものを書く署名を採る | §3 |
| 行ごとに尋ねるか、関係の全行に一度尋ねるか | 規則の種別ではなく、署名の範囲から導く | §3、§5 |
| 値がないとき、読んでいないときの答え | 評価器が一か所で扱う。実装は値のある入力だけを受け取る | §5 |
| 全件かどうかの宣言 | Contract Queryの束縛に、どの関係の行をすべて返すかを書く。宣言だけでは揃っているとみなさず、実行したQueryの資格を照合できたときだけ揃っているとする | §6 |
| 暦日の保存と読取り | 読み手は`YYYY-MM-DD`の文字だけを受け取る。列の型が分かる場所で変換する | §7 |
| 入力と期待の表で意味を宣言する形 | 例の表の列を署名の入力名にする。読んでいない入力を含む例は、補った例と矛盾しないことを機械で確かめる | §8 |
| 式の入れ子、`let`、`it` | 入れない。必要になったら、途中の値に名前を付けた導出で深さを持たせる | §9 |
| 組織DSLの前提 | 組織のための言語は作らない。標準の定義と規則、共通の表示へ投資する | §10 |
| 移行候補の読み方 | 候補は意味へ寄与しない。採用は欄の単位で、既存の編集経路だけを通す。旧動作は例の表の根拠として残す | §11 |

この判断が正しいかは、§12の受入れ一件で確かめる。**標準にないOperatorを一つ足す変更が、宣言の文書、実装のファイル、その試験の三種類だけに収まること**である。収まらなければ、この判断は誤っている。

## 2. なぜ今決めるか

規則経路の文書は§7.4で「述語が固定の列挙である」ことを不足に挙げた。その後の追補は、不足を解かないまま規則を一件ずつ足した。mainの`semantic.Validation`は次の形になっている。

| 観測した事実（`internal/semantic/model.go`） | 何が起きているか |
| --- | --- |
| 種別が六つある（`positive`、`relation-unique`、`operator`、`not-after`、`no-overlap`、`required-if`） | 規則を一件足すたびに列挙が増える |
| `Compared`の欄が三通りの意味を持つ。比べる相手、期間の最終日、必須にする条件の項目 | 欄の意味を種別ごとに読み分けている |
| `IfPresent`、`GroupBy`、`OpenEnded`は、それぞれ一つの種別でだけ有効 | 種別に固有の欄が共通の構造に積もっている |
| 読み手の境界が四つある（数値、暦日、値の有無、関係のキー） | 読むものが変わるたびに境界が増える |
| 規則を行へ当てる入口は、種別ごとに尋ね方を決め、知らない種別を拒否する | 別のセッションが足した種別を読み手が知らず、試験で止めた（規則経路の文書§24の記録） |

一件を足す変更は、解析器、列挙、Validator、評価器、読み手、派生ツールへ同時に及ぶ。TEIが掲げる「分野が足すのはRoleとOperatorの宣言だけ」は、製品ではまだ成り立っていない。

積み残した判断のうち五つは、同じ問いの別の面である。**Operatorは、入力について何を宣言するのか。** 一件ずつ決めると、決めるたびに種別と境界がもう一つ増える。先に署名を決める。

`ValidationKind`には「汎用式言語やrule engineを先回りして導入しない」という注記がある。この判断はその線を越えない。式の入れ子は入れず、評価器も増やさない。既存の評価器の中で、種別ごとの分岐を署名の解釈一つへ置き換える。

## 3. 判断：Operatorの署名

Operatorの宣言は、入力ごとに次の四つを述べる。結果は当面、成立か不成立かの真偽に限る。

| 述べること | 取り得る値 | 決まること |
| --- | --- | --- |
| 名前 | 入力の名前 | 規則と例の表が入力を指す単位。診断が指す位置の単位 |
| 型 | 数値、暦日、文字、真偽、型を問わない | 読み手が値をどう読み、何を拒否するか（規則経路の文書§21「値の読み方」のとおり） |
| 範囲 | 一件の値／関係の行すべての値 | 尋ね方。行ごとか、行の集まりに一度か。全件の宣言が要るか |
| 読むもの | 値／値があるかどうか | 値がないことを、判定できない理由にするか、正当な入力にするか |

加えて、Operatorの全体について二つを述べられる。

- **値がないことの読み替え**。入力ごとに、値がないときに使える名前付きの読み方を宣言する。期間の最終日がないことを「終わりのない期間」と読む、などである。宣言のない読み替えは規則に書けない。
- **一部の行での反証**。行すべてを読む入力を持つOperatorが、見えた行の中の反例だけで不成立と言えるかを宣言する。一意と期間の重なりは言える。合計の上限のように、見えていない行で答えが変わるものは言えない。宣言がなければ言えないものとして扱う。

今ある六つの種別は、次の署名で書ける。新しい意味は足していない。

| 今の種別 | 入力（名前：型、範囲、読むもの） | 補足 |
| --- | --- | --- |
| `positive` | 値：数値、一件、値 | |
| `operator` | 値：数値、一件、値 | 今の`takes number`と同じ |
| `not-after` | 前：暦日、一件、値／後：暦日、一件、値 | `if present`は§4の規則側の指定 |
| `required-if` | 対象：問わない、一件、有無／条件：問わない、一件、有無 | |
| `relation-unique` | キー：問わない、行すべて、値 | 一部の行で反証できる |
| `no-overlap` | 開始：暦日、行すべて、値／終了：暦日、行すべて、値 | 終了は「終わりのない期間」と読み替えられる。一部の行で反証できる |

書き方は製品の今の宣言を広げる。`operator sales.non_negative: takes number`は、名前を省いた入力一つの宣言としてそのまま読める。入力を増やす書き方の字句は§12に決めた。優先するのは、宣言が持つ情報と、その情報から導かれる動作である。

単位付きの数量は、型の一つとして後から足せる位置に置いた。次元、尺度、換算の検査はこの判断に含めない。

## 4. 判断：規則の正規形

規則が持つのは次のものだけにする。

| 持つもの | 内容 |
| --- | --- |
| Operator | 宣言したOperatorのID。必ず一つ |
| 入力の割当て | 署名の入力ごとに、同じDataの項目一つ、または定数一つ |
| 入力ごとの指定 | 「値のある記録についてだけ述べる」（今の`if present`）か、Operatorが宣言した読み替えの名前。どちらもなければ指定なし |
| 範囲の区切り | 行すべてを読む入力があるときだけ書ける。どの項目の値が同じ行どうしを比べるか（今の`per`と`GroupBy`） |

「値のある記録についてだけ述べる」は、どのOperatorのどの入力にも同じ意味で使える。その入力に値がない記録は成立とする。これは今の`not-after`の`if present`と同じ答えで、種別に固有の欄を入力ごとの指定へ一般化したものである。

入力へ書けるのは項目か定数である。別のOperatorの呼出しは書けない（§9）。

### 保存した形は変えない

受理済みの定義、固定したGate版、内容の識別値に影響するので、`semantic.Validation`の保存形は今回変えない。三段で進める。

1. **読み替えを足す**。`Validation`から正規形を返す関数を一つ置く。五つの古い種別は、固定の表で標準のOperatorと入力の割当てへ写す。評価器、Validator、読み手、派生ツールは、この正規形だけを読むように改める。
2. **列挙を閉じる**。種別を足すと失敗する試験を置く。新しい規則は`operator`の種別で、入力の割当てを持つ形でだけ足せる。`operator`の種別には、入力の割当ての欄を足す。割当てのない既存の規則は、入力一つとして読む。
3. **保存形を揃える**。古い種別の保存形を正規形へ書き直すかは、別の判断にする。受理の経路と識別値の移行を伴うので、1と2が動いてから、必要が生じた時点で決める。行わなくても1と2の利点は得られる。

### 書き方

今ある言い回し（`is positive`、`is not after … if present`、`is required if …`など）は、標準のOperatorを呼ぶ決まった書き方として残す。読んだ結果は正規形になる。Workspaceが新しい言い回しを定義する仕組みは入れない。標準にないOperatorは、名前空間付きの名前と、入力名を添えた割当てで書く。字句は§12に決めた。条件は一つである。**既存の文書の読み方が変わらないこと。**

### 診断の位置

診断は「規則＋入力」を単位に位置を指す。規則経路の文書§7.4が挙げた「診断が欄を指せない」は、入力がそのまま単位になることで解ける。Source Indexへ足す単位はこれ一つにする。

## 5. 判断：評価の入口を一つにする

読み手の境界は一つにする。「あるDataの、これらの項目を、行の集まりとして読む」である。返すものは三つある。行、行ごと項目ごとの値の状態（値がある、値がない、読んでいない）、行の集まりがどこまで揃っているか（§6）。今の四つの境界は、この一つへ適合させる薄い変換として残し、呼ぶ側を順に移す。

値がない場合と読んでいない場合の扱いは、評価器が一か所で行う。Operatorの実装へは書かない。

| 入力の状態 | 読むものが「値」の入力 | 読むものが「有無」の入力 |
| --- | --- | --- |
| 読んでいない | 判定できない（読んでいない） | 「分からない」として実装へ渡す |
| 値がない、規則が「値のある記録についてだけ」と指定 | 成立 | ― |
| 値がない、規則が読み替えを指定 | 読み替えた値を実装へ渡す | ― |
| 値がない、指定なし | 判定できない（値がない） | 「ない」として実装へ渡す |
| 値がある | 型どおりに読んだ値を実装へ渡す | 「ある」として実装へ渡す |

理由が二つ重なるときは、読めば解ける理由（読んでいない）を、読んでも残る理由（値がない）より先に返す。規則経路の文書§17と§23の原則をそのまま使う。

**実装は、値の揃った入力だけを受け取る純粋な関数になる。** 判定できない場合の分岐を実装ごとに書かずに済み、書き漏らしも起きない。

有無を読む入力にだけ「分からない」を渡すのは、今の`required-if`の答えを保つためである。対象に値があれば、条件を読んでいなくても成立と言える。実装が「分からない」を受け取って答えを返すときは、**分からない入力をどう補っても同じ答えになる場合に限る**。この条件は§8の例の表で機械的に確かめる。

尋ね方は署名から導く。行すべてを読む入力が一つでもあれば、範囲の区切りごとに行の集まりへ一度尋ねる。なければ行ごとに尋ねる。行が一つもないとき、行ごとに尋ねる規則の答えは0個である。行ごとの答えはまとめない。どちらも今の動作と同じである。種別がなくなるので、「知らない種別を拒否する」分岐は要らなくなる。

## 6. 判断：全件かどうかは束縛に書く

行の集まりが関係の全行かどうかは、行からは分からない。今は呼出し側の引数で述べている。これをContract Queryの束縛へ移す。束縛はQueryが何を返すかを知っている唯一の定義だからである。

行すべてを読む規則は、範囲を関係で書いている（`is unique per sales.order.lines`）。受注一件の明細、という単位である。束縛の宣言も同じ単位で書く。

| 束縛の宣言 | 意味 | 例 |
| --- | --- | --- |
| ある関係の行をすべて返す | 入力で定まる親一件について、その関係の行は揃っている | 受注一件の明細すべて |
| 一部の行を返す | 揃っていると言えない | 検索結果、ページ |
| 書かない | 何も述べていない | ― |

「関係の全行か、一部か」の二択を、DB全体についての問いにしない点が要である。「受注ごとに明細番号が一意」は、受注一件の明細が揃っていれば判定できる。表の全行は要らない。

**宣言は「揃っている」の根拠にならない。**（2026年11月17日に改めた。初めの版は、宣言があれば揃っているとみなしていた。その実装[#5341](https://github.com/hat47x/tei-platform/pull/5341)の試験で、宣言したままQueryが明細を1行落とすと、実際には重なっている明細番号の一意が「成立」になることを確かめ、統合しなかった。）

束縛の`covers`は書いた人の宣言（Declared）である。SQLの中身からは一般に証明できない。そこで、揃っているかを次の二つに分ける。

| 区別 | 中身 | 判定への効き方 |
| --- | --- | --- |
| 宣言 | 束縛の`covers <関係>`／`covers some` | `validate`の照合と、結果への記録（どの束縛が何を宣言したか）だけに使う。それだけでは「揃っている」にしない |
| 資格 | 実行したQueryについて、対象の関係、親の範囲、追加の条件、ページ・件数の制限、時点を照合できたこと | これがあるときだけ「揃っている」とし、§5のとおりに判定する |

資格の確かめ方は、一般のSQL完全性の証明器を作らずに、狭いContract Queryから始める。照合できないQueryは「一部」として扱う（閉じる側へ倒す）。行の数、`LIMIT`がないこと、0行であること、宣言があることは、どれも資格にしない。

最初の資格の照合は、Queryを、Workspaceが関係をどう保存しているか（永続化の定義の`relation-storage`）と突き合わせる。次をすべて満たすときだけ「揃っている」とする（`driver.QualifyHeaderDetailCoverage`）。

| 照合すること | 参照Workspaceの受注明細では |
| --- | --- |
| 束縛が、パターンの読む関係について`covers`と書いている | `covers sales.order.lines` |
| SQLが読む表が、関係の行き先のDataを保存する表である | `public.order_lines` |
| SQLの条件が、関係を保存する列ごとの`列 = :パラメータ`だけで、`AND`でつながる | `order_id = :order_id` |
| そのパラメータが、realizationの入力と束縛の入力を経て、関係の保存がその列に入れる親の項目を受け取る | `order_id`は`sales.order.order_id`を受け取る |
| ほかに行を減らしうるものがない | `LIMIT`、`OFFSET`、`DISTINCT`、`GROUP BY`、結合、副問合せ、注釈、二つ目の文がない |

照合はSQLを一つの形だけ読む。`SELECT 列, … FROM 表 WHERE 列 = :パラメータ [AND …] [ORDER BY 列 [ASC|DESC], …] [;]`である。この形にないものは、意味が同じでも読まず「一部」にする。読む形を広げるときは、行を減らしうる書き方を一つずつ足し、その書き方で「成立」が出ない試験を先に置く。

`tei view -environment`は、結果に`coverage`（`complete`か`partial`）と`coverageDeclared`（束縛の宣言）を返す。`complete`には照合した定義を`coverageBasis`に、`partial`には最初に満たさなかったことを`coverageReason`に書く。

この照合が前提にしていることが二つある。表の中身が永続化の定義どおりであること（同じ名前の表が、別の意味の行を持っていないこと）と、一つの読取り専用のトランザクションの中で一つの文を実行すること（時点が一つであること）である。前者は確かめていない。

| 場面 | 動作 |
| --- | --- |
| 行すべてを読む規則を、その関係について宣言のない束縛の上で選んだ | `tei validate`の警告 |
| 資格がある | §5のとおりに判定する |
| 資格がない（宣言だけがある場合を含む） | 見えた行の中に反例があり、Operatorが一部の行で反証できると宣言していれば不成立。それ以外は判定できない |
| 呼出し側が実行時に述べる | 下げることだけできる（揃っている→一部）。上げることはできない |

試験には、宣言を残したまま行を落とすQueryで「成立」が出ないこと（判定できない、または見えた反例による不成立）を必ず置く。

親を持たないDataの全行にわたる規則（マスタ全体でコードが一意、など）は、今の規則の書き方に範囲の関係がないので、この判断の範囲に入れない。必要になった時点で、範囲の書き方と一緒に決める。

## 7. 判断：暦日

規則経路の文書§24は、日時の列を暦日として読むと、実行した機械の時間帯で答えが変わることを実際のDBで確かめた。読み手は値がどの型の列から来たかを見られない。そこで次のように決める。

- **読み手が暦日として受け取るのは、`YYYY-MM-DD`の文字だけにする。** 「0時ちょうどの日時をその日として読む」受け方はやめる。機械によって答えが変わると確かめた受け方を、既定に残さない。
- **変換は、列の型が分かる場所で行う。** DBの実行を担う側は、結果の列の型をドライバーから得られる。暦日の列は`YYYY-MM-DD`の文字にして行へ入れる。日時の列が暦日の項目へ返ってきたら、変換せずに誤りにする。SQL realizationが列の型を書かなくても、実行のたびにこの検査が及ぶ。
- **保存の型に暦日を足す。** Providerごとの対応（暦日の型を持つDBではその型、持たないDBでは書式を検査した文字）とDDLの生成は、DBの担当が決める。それまでは、暦日の項目を文字で保存する今の扱いを続ける。
- **日時から暦日を得ることは、時間帯を入力に取るOperatorとして明示する。** 暗黙には行わない。

## 8. 判断：例の表で意味を述べる

Operatorの意味は、宣言の近くに書いた例で述べる。今の例の表（入力は数値一つ）を、署名に合わせて広げる。

- 一件の値だけを読むOperatorは、一行が一例である。列は署名の入力名、期待、注記にする。空のセルは「値がない」、決まった語で「読んでいない」を書く。期待には、成立、不成立、判定できないを書ける。
- 行すべてを読むOperatorは、一表が一例である。既にある記録の例の表（期待を印に書く形）と同じ形にし、列を入力名にする。
- 実装を選ぶとき、すべての例と照合する。一つでも違う実装は、そのOperatorの実装として使わない。これは今の動作と同じである。

足す検査は一つである。**読んでいない入力を含む例が成立か不成立を期待するとき、その入力を補った例が表にあれば、期待が同じでなければならない。** 違えば宣言の誤りとして診断する。§5で実装に求めた条件を、宣言の側でも確かめることになる。

この表は、移行でも同じ役目を持つ（§11）。

### 最初の三入力Operatorで確かめること

最初の実装対象は `within(value, low, high)` とする。これは下限と上限を含む範囲の判定であり、三つの値が揃っている場合は `low <= value` かつ `value <= high` が成立するかを答える。数値は十進の原文を保ち、二進浮動小数点数への丸めで境界を判定しない。

- `(value, low, high) = (0, 0, 100)` と `(100, 0, 100)` は成立、`(101, 0, 100)` は不成立。入力名によって対応づけるため、Ruleに書く `low:` と `high:` の順序や、例の表の列順を変えても答えは変わらない。
- **`low > high` は範囲外の値ではなく、範囲の指定自体の誤り**とする。上下限を勝手に入れ替えず、不成立とも答えない。上下限が定数で宣言時に分かるならそのRuleを検証時に拒否する。実データから読み取った値で初めて分かるなら、当該行の評価エラーとして理由を報告する。値がない・読んでいないことによる「判定できない」とも区別する。新しい判定結果の種類は設けない。
- 署名の入力順序は契約の一部である。第1入力はRuleの主語から一度だけ与える。`value:` で再指定したら二重束縛として拒否する。`low:` と `high:` は名前で割り当て、入力不足・余分な名前・同名の重複をSource位置付きで拒否する。署名の順序そのものが変われば再検証が必要になる。
- 例の表では `1` と `1.0` を同じ数値として扱う。同一の入力組を別の表記で二度書いた場合は、期待が一致していても重複として拒否する。誤りの位置は該当セルへ戻す。
- 最初の実装では、値の揃った数値例を検証してから実装を選ぶ。空欄・未読・判定できない期待については、この節で決めた§8冒頭の契約を変更しない。まだ読めない場合は未対応として明示的に停止し、`0` や不成立で補わない。Operator例の合格から実Providerの読取資格やOwnerの業務意味の受理を推論しない。

次の製品変更は、既存のOperator署名、例の表、Ruleの入力束縛、実装選択、評価器を同じ変更単位で接続する。独立した期待と旧単入力の回帰試験を添え、`plan/NOW.md` に定めた受注初回変更の検収を優先する。

### 8.1 行集合の例を表で記述する（2026-11-25、実装に向けた設計案）

道⑤の残件である「一表が一例」を、既存の `tei.authoring/v1` の表とOperator実装選択へ接続する。次のコード変更は、値が揃った行集合の例をLoad・意味モデル・`CheckImplementationMatchesContract` の同じ経路に通す一件とする。新しい言語、例専用の評価器、別の実装選択機構は設けない。

#### 記述形式

行集合の期待は行ごとに書かず、記録の例の表と同じ `expecting` を印に用いる。例えば以下の宣言に対し、明細二行の集合を二通り示す。

```tei
operator sales.every_line_at_most:
  takes value: number of each row
  takes limit: number
  refutes on some rows
```

```markdown
<!-- tei: cases of sales.every_line_at_most expecting satisfied -->
| value | limit |
| --- | --- |
| 2 | 10 |
| 5 | 5 |

<!-- tei: cases of sales.every_line_at_most expecting not-satisfied -->
| value | limit |
| --- | --- |
| 2 | 10 |
| 5 | 4 |
```

- 従来の `cases of <operator>` と表内の `expect` 列は、一行が一例である従来のOperatorに限り、そのまま維持する。行集合では `cases of <operator> expecting <answer>` とし、列は署名の入力名だけにする。単一入力の行集合でも `value` 列を一件の値と解釈しない。
- 一つのOperatorに複数の行集合の例を置ける。同じOperatorへの従来形式の二表は引き続き拒否する。行集合形式と従来形式の混在も拒否する。例の数と表内の行数は別であり、同値の行が二つあっても消さない。
- 入力の列順は問わない。行の中で入力を対応付け、行の並びと多重性を保つ。 `limit` が属性参照でも定数でも、ここで述べるのは実装へ渡る行ごとの値である。定数の繰返しを省略する記法は足さない。
- 初回は数値が揃った非空の表を対象にする。空欄、未読、空集合、`undecided` の期待を扱えると装って受理しない。現行Markdown scannerは本文が一行もない表を拒否するため、空集合を表す記法の採否は別の変更で扱う。空集合をNULL一行とみなさない。

#### 意味モデルと実装選択

§15.3 の `OperatorCase` の拡張を使い、行集合は行の配列（各行は入力名から数値原文への対応）、期待は表に一つの明示的な値として持つ。旧 `Value`・`Inputs`・`Satisfied` の読取りとJSONを変えない。行集合では `Rows` と新しい期待欄だけを意味として解釈し、旧値欄や真の旧 `Satisfied` と併記した矛盾する構造は拒否する（旧JSON形式に由来するfalseは行集合の期待として読まない）。行集合の有無と期待の明示を検証し、ゼロ値だけで不成立を期待したことにしない。

現行 `internal/syntax/operator_cases_authoring.go` の表読取り、`internal/workspace/rule_authoring_markdown_loader.go` の `attachOperatorCases`、`internal/semantic/operator_case.go` の例の比較、`internal/validation/semantic_business_validation.go` の検査、`internal/semantic/validationeval/operator.go` の `CheckImplementationMatchesContract` を接続する。表の形は印で識別し、署名との一致は全Source読込み後に検査する。現在の「同じOperatorの二表を拒否する」制約は行集合形式だけ変更する。未宣言の列・不足した列・重複する列・不正値は、印、列名、セルの該当位置へ戻す。期待不一致は少なくとも対象Operatorと表の期待位置を特定できるようにする。

実装に渡す値は既存の `map[string][]NumberReading` とし、数値は既存の十進数読取りで厳密に変換する。 `NumberRows` を呼ぶために行を列へ写すだけで、実装を選び直したり、Providerを呼んだりしない。期待との照合に失敗した実装は、`tei validate` と実行時の双方で拒否する。数値の意味が同じで、入力名と行順・多重性が等しい二表は期待の一致にかかわらず重複として拒否する。列順の入替えは同一の例であり、行順を変えた例は別の試験として残せる。

この表が述べるのは**純粋なOperatorの入力と答え**である。実DBの `Coverage`、読取Attempt、業務主キー、Ruleによる読み替え、Ownerの受理を表から作らない。部分読取での `refutes on some rows` の効力は§15.2と実DB経路で引き続き検査する。

#### 次の実装の受入条件

| 入力・操作 | 独立した期待 |
| --- | --- |
| 上記二表と適合する実装を選ぶ | `tei validate` が通り、二表が二例として保持される |
| 二表目の期待だけを成立へ変える | 実装不一致として拒否。実データ読取りは行わない |
| 列を逆順にする | 同じ判定。別の入力へ値を取り違えない |
| 同じ数値の別表記で一表を重ねる | 重複を拒否（例：5と5.0）。同じ表内の同値行は保持 |
| 行集合形式に従来の期待列を加える／入力名を欠く／余分な列を置く | Source位置付きで拒否 |
| 従来の一行一例の表を読む | 旧JSON・判定・診断の回帰がない |

この一件が通った後、§8の三値の例へ広げる。空欄は `ValueNull`、明示語 `not-fetched` は `ValueNotFetched` として扱う案とし、欠けた列を未読の代用にしない。数値のある行、NULLのある行、未読のある行を同じ表に置けるようにする。Operator契約の例ではRule固有の読み替えを暗黙に実施しない。読み替え自体はRuleの例および製品読取経路で確かめる。

特に `every-at-most` では、比較可能な一行に反例があれば、他の行がNULLや未読でも反証は成立する。反例と未読行の順序を入れ替えた二例で同じ期待を固定する。現行mainの `operator_selection.go` は行走査中に最初のNULL・未読で `TriMaybe` を返すため、後の行に反例があると判定が順序に依存し得る（静読による指摘、未実行）。これは一般のOperatorすべてに可換性を要求するものではなく、当該Operatorの意味の検査である。不正なpresent-without-value等の入力契約違反は、既知の反例で隠さない。

#### 三値の例へ広げる際に先に揃える契約

値の状態を持つ行集合では、Operatorの関数が答える三値と、評価器が業務規則について返す三値を混同しない。前者は与えられた入力の組に関する答え、後者はその答えに実際の読取範囲と規則の指定を加味した答えである。例の表を使う実装選択では前者だけを確かめる。後者の反例は、既存のRuleの例と実DB試験に置く。

| 行集合の入力（value, limit） | every-at-most の答え |
| --- | --- |
| (2, 10), (5, 5) | TriYes |
| (2, 10), (5, 4) | TriNo |
| (NULL, 10), (5, 4) | TriNo |
| (5, 4), (NULL, 10) | TriNo |
| (未読, 10), (5, 4) | TriNo |
| (5, 4), (未読, 10) | TriNo |
| (未読, 10), (5, 5) | TriMaybe |
| (NULL, 10), (5, 5) | TriMaybe |

この期待は当該Operatorに固有のものである。未知の行があっても不成立と断定できるのは、比較可能な行の反例が未知の値をどう補っても消えないためである。比較の順序で答えを変えない。反例を含む行が読めなくなった場合、見えた行だけの関数の答えは変わり得るが、評価器は部分読取から規則全体の成立を導かない。逆に、正負を含む数値の合計が上限を超えないことを問うOperatorには、途中の合計を根拠に同じ判断を適用できない。一般のOperatorの実装適合を有限個の例だけで証明したとは扱わない。

**読み替えは例の表とは別に、入力束縛の契約として確定する必要がある。** §3〜§5では宣言が読み替えの候補を述べ、Ruleがそれを選ぶ。ただし現行mainの `readSubjectInput` は主語の宣言から直接読み替え、`readAssignedInput` は名前付き割当ての `or` を見る。さらに行集合側は後続入力にも宣言の読み替えを既定で適用する。このため同じ名前付き入力でも一件の規則と行集合の規則で、`or` を省いたときの意味が異なる可能性がある。また、一件側の `readAssignedInput` は読み取れなかった理由を検査せずに読み替えを呼ぶ箇所が残る。いずれもコードの静読による指摘であり実行結果ではない。

次の判断案では、主語については現行の明示的な宣言による読み替えを互換上維持し、後続の名前付き入力はRuleで選んだ読み替えだけを有効にする。どの入力であっても、確実に値がない場合に限り読み替える。未読・非開示・reader失敗から値を作らない。主語もRuleごとに選択するよう統一する案は、現在のSourceで意味が変わる範囲と移行方法を確認してから別途判断する。既存の `absent as` によって成立している規則を無告知で変えない。

| 入力の状態 | 名前付き入力の指定 | 期待する入力または結果 |
| --- | --- | --- |
| 数値5 | or zero | 5のまま |
| NULL | or zero（宣言・実装とも対応） | 数値0 |
| NULL | orなし（宣言のみ） | NULLのまま／一件では判定不能 |
| 未読 | or zero | 未読のまま／一件では判定不能 |
| reader失敗 | or zero | error |
| NULL | 宣言にないor名 | Source位置付きで拒否 |
| NULL | 宣言済みだが実装が読めない名前 | 既存の判定不能の理由を保持 |

後続の実装は、同じNULLの属性を使った一件・行集合の規則で上の違いを再現し、両者の束縛の意味を揃える。定数0を渡した試験は読み替えを通った証拠に数えない。反例と未読を混ぜた場合は、読み替えの有無とは独立に既知の反例を失わないことを確かめる。判定不能の理由が複数ある場合も、§5で定めた未読優先と、§15.2で定めた行内の理由をCoverageより先に返す条件を満たすか検査する。新しい結果分類は作らない。

本節は設計案であり、Parser・意味型・実装の変更や実行済みの証拠ではない。担当は #4359。優先順位は `plan/NOW.md` のままとする。

### 8.2 空の関係を一例として書く記法（2026年11月25日、決定）

8.1 は空集合を表す記法の採否を「別の変更で扱う」とした。本節がその決定である。**決定の対象は記法だけであり、評価の意味は 8.1 と §15 から変えない。**

**記法は、行集合の例の印に `over no rows` を置く。**

```markdown
<!-- tei: cases of sales.every_line_at_most expecting satisfied over no rows -->
| value | limit |
| --- | --- |
```

**本文0行を許すのは、印がこの句を持つときだけである。** 句のない本文0行は従来どおり拒否し、拒否の文言がこの句を名指す。理由は三つある。

- **空の表は、意図した空集合よりも書き忘れのほうが多い。** 句を必須にすれば、行を書き忘れた表は意味を持つ例にならず、書いた人へその場で返る。句なしの本文0行を空集合と読む案は、書き忘れを「一例」へ黙って昇格させる。
- **意味を表す語が印にあり、表の形から推測しない。** 8.1 が「空集合をNULL一行とみなさない」と定めたのと同じ理由で、空の関係と、値がない行1行を、字面で区別できる必要がある。
- **既存の表の読み方を変えない。** 句のない表は今と同じく本文1行以上を要求するので、既存の `cases of` と `expecting` の文書は影響を受けない。

**空の関係に対する答えは、`refutes on some rows` の有無で変わらない。** 読んだ行が0行なら反例も0件であり、`decideRowScoped` の表（§15.2）では答えは `TriYes`、Coverage が complete なら `satisfied` になる。`refutes on some rows` は「見えた反例をどう扱うか」の宣言であって、反例が1件も無い場合は適用先が無い。**この事実は製品経路の実DBで固定する**（`TestARowScopedRuleOverAnEmptyRelationIsSatisfied` が受注1003で既に固定している）。本節の変更は、その同じ答えを**例の表からも**書けるようにする。

**例の表が述べるのは純粋なOperatorの入力と答えである。** 空の関係の例も、実DBの Coverage・Read Attempt・業務主キー・Rule の読み替え・Owner の受理を作らない。8.1 の「表が述べるのは純粋なOperatorの入力と答え」をそのまま適用する。

**次のコード変更は、この句を `internal/syntax` の scanner・行集合の例の parser・`internal/workspace` の列検査・`internal/semantic/validationeval` の例の照合へ通し、句なしの本文0行の拒否を保つことである。** 期待は三つ——句ありの空集合が `tei validate` を通り、句なしの本文0行が句を名指して拒否され、空欄1行が空集合ではなく値がない行1行として読まれる。

本節は設計案であり、Parser・意味型・実装の変更や実行済みの証拠ではない。担当は #4359。優先順位は `plan/NOW.md` のままとする。

#### 8.4 型ごとの値を、実装へどの形で渡すか（2026年11月25日、決定）

§3 は入力の型を定め、§5 は「実装は、値の揃った入力だけを受け取る純粋な関数になる」と定め、§7 は暦日の読み手を定め、§8.3 は例の表の書き方を定めた。**しかし `OperatorImplementation` の関数は `*big.Rat` しか受けず、暦日・文字・真偽の値を実装へ渡す口が無い。** 型 `date`/`text`/`truth`/`any` の読者を足す次の変更は、その口を必要とする。本節がそれを決める。

**値は、型ごとの判別を持つ一つの型で渡す。**

```go
// OperatorValue is the value of one input, read according to the type the
// declaration gave. Exactly one of the fields is set, decided by the type.
type OperatorValue struct {
	Number *big.Rat      // type number
	Date   *CalendarDate // type date
	Text   *string       // type text
	Truth  *bool         // type truth
	Any    *AnyValue     // type any
}
```

**欄を入力ごとに増やすのではなく、値の型を一つにする理由は `any` である。** `any` は型を問わない入力なので、同じ入力が数値にも文字にもなりうる。数値の欄と文字の欄を別々に持つと呼び出し側が型を選ぶ判断をし、選び間違いが判定の誤りになる。一つの値に型の判別を持たせれば、読んだ型がそのまま実装へ届く。

**`any` の値は、読んだ型を保つ。** 数値として読んだ `100` と、文字として読んだ `"100"` は別の値であり、`AnyValue` はその区別を保つ。§8.3 が例の表で引用符の有無によって両者を区別したのと同じ区別を、実装へ渡す値でも保つ。**数値と文字を同じ値として扱わない。**

**既存の三つの欄は残す。** `Number`・`Numbers`・`NumberRows` はそのまま動く。数値だけの実装（`tei.number.within`・`tei.number.every-at-most`）は今の欄を使い続け、**その変更を要しない。** 型ごとの値を受ける欄を足すことで、既存の実装と試験に触れない。**同じ実装が数値の欄と型ごとの欄の両方を提供することは拒否する**——どちらの値で答えるかが曖昧になる。

**行集合の入力にも同じ値を使う。** 行ごとの値は `[]OperatorValue` であり、数値の `[]NumberReading` を別に持たない。行の状態（値がある・値がない・読んでいない）は今のとおり値とは別に運び、**型ごとの値は「値がある」行にだけ入る。**

**実装が型に合わない値を受け取ることはない。** 宣言が `number` なら実装は数値の欄だけを見、`text` なら文字の欄だけを見る。評価器は宣言の型で値を読み、その型の欄だけを埋める。埋まらない欄を見た実装は、**その値を読めなかったとして判定不能を返す**（誤った型として読むことはしない）。

**この節が変えないもの。** §5 の「値がない・読んでいないの扱いは評価器が一か所で行う」はそのままである。実装は値の揃った入力だけを受け取り、判定不能の分岐を実装ごとに書かない。新しい結果分類も作らない。

**次のコード変更は、この値を `internal/semantic/validationeval` に置き、`OperatorImplementation` に型ごとの欄を足し、`internal/semantic` の `OperatorInput` に `date`・`text`・`truth`・`any` を加え、§8.3 の記法を例の表の読込みへ通すことである。** 期待は五つ——四つの型語が受理され、`text` の例が引用符付きで読まれ、`any` の `100` と `"100"` が別の値として実装へ届き、型に合わないセルが拒否され、**既存の数値の二実装とその試験が変更なく通る**。



### 8.3 例の表で、数値以外の値を書く（2026年11月25日、決定）

§3 は入力の型を `number`・`date`・`text`・`truth`・`any` と定め、§7 は読み手が暦日として受け取るものを定めた。**しかし例の表が数値以外の値をどう書くかを、どの節も定めていない。** 型の読者を足す次の変更は、その記法を必要とする。本節がそれを決める。

**例の表のセルは、入力の型によって次のように書く。** 型は署名が持っているので、表が型を推測することはない。

| 入力の型 | セルに書くもの | 例 |
| --- | --- | --- |
| `number` | 十進の数字（§8.1 のまま） | `100`、`-0.01` |
| `date` | `YYYY-MM-DD` の文字 | `2026-04-01` |
| `text` | 二重引用符で囲んだ文字 | `"A-100"` |
| `truth` | 語 `true` または `false` | `true` |
| `any` | 上のどれか。引用符の有無で `text` と他の型を区別する | `100`、`true`、`"100"` |

**値がないことと読んでいないことは、型によらず同じ書き方を使う。** 空のセルは値がない行、語 `not-fetched` は読んでいない行である（§8.1）。**`text` の入力では、空のセルと `""`（空の文字列）は別のもの**である。前者は値がないことであり、後者は長さ0の文字列という値である。

**引用符を必須にする理由は、`text` と `any` の区別である。** `any` は型を問わない入力なので、`100` と `"100"` が同じ表に現れうる。**引用符の有無が型を決めれば、表の見た目だけでどちらかが分かる。** 引用符を省ける案は、`any` の2つの値を区別できない。

**書けるのは、その型の値として読めるものだけである。** 暦日として読めない文字、引用符の閉じていないセル、`true`/`false` 以外の真偽の語は、セルの位置を指して拒否する。**拒否は表の読込み時に行い、実装選択や実データ読取りの前で止める**（§8.1 の「実装を選ぶとき、すべての例と照合する」と同じ位置である）。

**この記法が変えるのは例の表の書き方だけである。** 規則の入力（`low: 0 high: sales.order_line.unit_price`）の書き方は §4 のままであり、定数の型は署名から決まる。**規則に引用符付きの文字定数を書くことは、この節の対象ではない**——§4 は入力を項目か定数と定めたが、定数の型ごとの字句は別に決める必要がある。**例の表だけを先に決める。**

**次のコード変更は、この記法を `internal/syntax` の行集合の例の表の読込みへ通し、`internal/semantic` の `OperatorInput` に `date`・`text`・`truth`・`any` を加え、`internal/semantic/validationeval` の例の照合が型ごとの値を実装へ渡すようにすることである。** 期待は四つ——四つの型語が `Source` 位置付きの拒否なく受理され、`text` の例が引用符付きで読まれ、`any` の `100` と `"100"` が別の値として読まれ、型に合わないセルが拒否される。

本節は設計案であり、Parser・意味型・実装の変更や実行済みの証拠ではない。担当は #4359。優先順位は `plan/NOW.md` のままとする。

### 8.5 `presence` 入力を、実装へどの形で渡すか（2026年11月28日、決定）

§3 は入力の型を `number`・`date`・`text`・`truth`・`any` と定め、`presence` を「値の有無を読む入力で、型を問わない」と定めた。§8.4 は型ごとの値を `semantic.OperatorValue` 一つに載せ、実装はその型の欄だけを見ると決めた。**しかし `presence` は値ではなく「値があるか」という状態であり、`OperatorValue` のどの欄にも載らない。** `ParseOperatorInputValue` は `presence` のセルを「値ではない」として拒否しており、`OperatorImplementation` にも `presence` を受ける欄が無い。`presence` の入力を持つ演算子を決める次の変更は、その口を必要とする。本節がそれを決める。

**`presence` の値は、`OperatorValue` に載せない。** `presence` は「値があるかないか」を問う入力であり、値そのものではない。`OperatorValue` の欄に `Presence bool` を足すと、同じ型の中に「値」と「値の有無」が混ざり、`Any` の `Type` が `presence` を持ちうることも含めて、§8.4 の「型ごとの判別」が二つの意味を持つ。**別の欄にする。**

**実装は `map[string]bool` を受け取る。** 欄は `Presence func(values map[string]bool) (bool, error)` である。`true` はその入力の属性が値を一つ持つこと、`false` は持たないことを表す。

**「読んでいない」は実装へ渡さない。** §5 の「値がない・読んでいないの扱いは評価器が一か所で行う」をそのまま適用する。`presence` の読みは三つの状態を持ち、評価器が次のように扱う。

| 読んだ状態 | 意味 | 扱い |
| --- | --- | --- |
| `ValuePresent` | 属性は値を一つ持つ | 実装へ `true` を渡す |
| `ValueNull` | 属性は値を一つも持たない | 実装へ `false` を渡す |
| `ValueNotFetched` | 誰も読んでいない | 実装を呼ばず、判定不能（`value-not-fetched`） |

**`ValueNull` が判定不能にならない点が、型ごとの値と違う。** 型ごとの入力では「値がない」ことは答えを決められないので判定不能にした（§5）。`presence` の入力では「値がない」こと自体が問いへの答えである。**「値がない」と「読んでいない」を混ぜない**という §5 の要求は、この表で満たしている。

**`presence` を受ける欄は、それだけで一つの形である。** 実装は `Presence` と他のどの欄（`Number`・`Numbers`・`NumberRows`・`Values`・`ValueRows`）も併せて提供しない。§8.4 と同じ理由である——どちらの値で答えるかが曖昧になる。**形の検査の二箇所を直す必要がある。** 一つは「提供する欄の数を数える」箇所へ `Presence` を足すこと。もう一つは `!rowScoped && !hasTyped` の分岐で、これは複数入力の宣言に多値の欄を要求する。`Presence` だけを提供する実装は多値の欄を持たないので、**この条件へ `hasPresence` を足さないと、新しい欄を見る前に拒否される。****行集合の `presence` は本節が決めない**（行ごとの有無をどう運ぶかは別の判断である）。宣言が `of each row` を付けた `presence` 入力を持つ演算子は、本節の変更では拒否する。

**例の表では、`presence` のセルに値の有無を書く。** `presence` は値を問わない入力なので、セルは値を書く場所ではなく**値があるかないかを書く場所**になる。セルに書くのは語 `present`（属性は値を一つ持つ）と語 `absent`（属性は値を一つも持たない）の二つであり、**この二語は §8.1 の一表一例で `presence` の入力を書く唯一の書き方である。** 空のセルは「値がない行」を意味し、入力の値ではないので、`presence` の「値がない」を空のセルで書くことはできない。

**この二語は `truth` の `true`/`false` と混ぜない。** 「属性が値を一つ持つ」と「その値が真である」は別の問いであり、片方から他方を答えることはしない（§3 の `presence` の定義）。`truth` の入力のセルに `present` を書くことも、`presence` の入力のセルに `true` を書くことも、**セルの位置を指して拒否する。**

**例は実装と照合する。** ある `presence` の演算子の実装が `present` に対して `not-satisfied` を答えるなら、その例と実装は食い違っており、**その実装はその演算子の実装ではない**（§8.1 の「実装を選ぶとき、すべての例と照合する」と同じ位置で拒否する）。**例を書かない代わりに実データで確かめる、という扱いにはしない**——`presence` は値ではなく有無を問うので、実データの読みだけでは「この演算子が何を意味するか」を著者が述べる場所が無くなる。

**この節が変えないもの。** §8.3 の型ごとのセルの書き方、§8.4 の `OperatorValue`・`Values`・`ValueRows` はそのままである。新しい結果分類も作らない。

**次のコード変更は、`internal/semantic/validationeval` の `OperatorImplementation` に `Presence func(values map[string]bool) (bool, error)` を足し、`refuseNonNumberInputs` から `presence` の拒否を外し、評価器の `Values` 経路で `StatefulPresenceSource.ReadPresence` を呼んで上の表どおりに値を埋め、形の検査に `Presence` を一つの形として数え、`presence` のセルの二語を例の照合へ通し、出荷実装を一つ足すことである。** 期待は六つ——`presence` の入力を持つ演算子の規則が `ValuePresent` の属性で `satisfied`／`not-satisfied` を返し、`ValueNull` が `false` として実装へ届き、`ValueNotFetched` が実装を呼ばずに判定不能になり、`Presence` と他の欄を併せて提供する実装が拒否され、`presence` のセルの `present` と `absent` が、それぞれ `true` と `false` として実装へ届き、**既存の型ごとの実装とその試験が変更なく通る**。

### 8.6 `presence` 入力の行集合形を、実装へどの形で渡すか（2026年11月28日、決定）

§8.5 は一件の `presence` 入力を `OperatorImplementation.Presence`（`map[string]bool`）へ渡すと決め、**`of each row` を付けた `presence` は本節が決めないとして拒否に残した。** 本節がその残りを決める。

**いまの状態。** `of each row` を付けた `presence` を持つ演算子は、形の検査（`internal/semantic/validationeval/operator.go`）で「no reader reads yet」として拒否されている。**行ごとの有無を読む口が無いためである**——一件の有無を読む `StatefulPresenceSource.ReadPresence` は在るが、関係のすべての行について同じ属性の有無を返す口は無い。

**読者の口を足す。** `StatefulPresenceRowSource` を足し、`ReadRelationPresence(relation, attribute core.CanonicalID) (PresenceRowsReading, error)` を要求する。`PresenceRowsReading` は `Coverage`（読んだ行が関係のすべてか）と、行ごとの `PresenceReading` の並び（読んだ順）を持つ。**行ごとの状態は `ValuePresent`・`ValueNull`・`ValueNotFetched` の三つで、一件の読者と同じ意味である。**

**実装の欄は、行集合の他の形と同じく `Tri` を返す。** `OperatorImplementation` に `PresenceRows func(rows map[string][]PresenceReading) (Tri, error)` を足す。**既存の `ValueRows` が `Tri` を返すのと同じ理由**であり、`refutes on some rows` を持つ宣言では反例の有無がそのまま `TriNo` になる。**新しい結果分類は作らない。**

**「読んでいない」行は、その行の理由として集め、実装を呼んだうえで合成規則へ渡す。** §5 の「値がない・読んでいないの扱いは評価器が一か所で行う」は、**行集合でも既存の数値・型ごとの行集合と同じ場所**（`decideRowScoped`）で行う。**実装を呼ばない、ではない。**

| 行の状態 | 意味 | 扱い |
| --- | --- | --- |
| `ValuePresent` | その行は値を一つ持つ | 実装へ `ValuePresent` として渡す |
| `ValueNull` | その行は値を一つも持たない | 実装へ `ValueNull` として渡す |
| `ValueNotFetched` | その行を誰も読んでいない | 実装へ渡し、**その行の理由（`value-not-fetched`）を合成規則へ渡す** |

**実装を呼ばないのは、`ValueNotFetched` の行があるからではなく、答えが決まったからではない。** 既存の行集合の合成規則（`decideRowScoped`）は、**見た反例（`TriNo`）を「他が不明でも規則を決める」ものとして扱う**（§6）。**未読の行があるからといって実装を呼ばないと、別の行で見つかった反例を捨てることになる。** したがって次の順で扱う。

1. 行の理由を読んだ順で集める（最初の `ValueNull` または `ValueNotFetched`）
2. **実装を呼ぶ**
3. **合成規則**で、`TriNo`（反例を見た）は理由に関わらず `not-satisfied`、`TriYes` は理由があれば判定不能、`TriMaybe` は理由をそのまま返す

**この合成規則は既存の行集合の型（数値・型ごと）と同じであり、新しいものを作らない。** 一件の `presence`（§8.5）が「`ValueNotFetched` で実装を呼ばず判定不能」としたのは、**一件には見るべき反例が他に無いから**である。**行集合では他の行が反例になりうるので、同じ扱いにしない。**

**一件の規則と違い、`ValueNull` の行は実装へ渡す。** 一件の `presence` でも `ValueNull` は「値がない」という答えとして `false` を渡した（§8.5）。行集合では行ごとの `true`/`false` を並べて渡すので、**`ValueNull` の行を `false` に畳むのは実装の仕事ではなく、値をそのまま渡すのが評価器の仕事**である。**実装は受け取った並びだけを見て `Tri` を返す。**

**`Coverage` は今までどおり扱う。** 読んだ行が関係のすべてでなければ、`TriYes`（反例が無い）は `satisfied` にしない（既存の行集合の規則と同じである）。**部分的に読んだ関係で「反例が無い」を全件の答えとして扱わない。**

**`presence` の行集合の欄は、それだけで一つの形である。** `Presence`（一件）・`PresenceRows`（行集合）と他の欄を併せて提供しない。宣言が `of each row` を付けたかどうかで、どちらの欄を使うかが決まる。

**行集合の例は、§8.1 の表で書く。** セルの語は `present`・`absent`・`not-fetched` の三つであり（§8.3 の「値がないことと読んでいないことは型によらず同じ書き方」）、`presence` の一件の例と同じ語を使う。**行集合の例は、実装と照合する**（§8.1 の「実装を選ぶとき、すべての例と照合する」）。

**この節が変えないもの。** §8.5 の一件の `presence`（`Presence`、`OperatorValue` に載せない、`ValueNotFetched` は判定不能）はそのままである。§8.4 の `ValueRows` とその他の型ごとの行集合もそのままである。**新しい結果分類も作らない。**

**次のコード変更は、`internal/semantic/validationeval` に `StatefulPresenceRowSource`・`PresenceRowsReading` を足し、`OperatorImplementation.PresenceRows` を足し、形の検査の「no reader reads yet」を外して `PresenceRows` を一つの形として数え、評価器の行集合経路で `ReadRelationPresence` を呼んで上の表どおりに判定し、`presence` の行集合の例を照合へ通し、出荷実装を一つ足すことである。** 期待は六つ——`of each row` を付けた `presence` の演算子の規則が実 PostgreSQL の行で `satisfied`／`not-satisfied` を返し、`ValueNull` の行が値なしとして実装へ届き、`ValueNotFetched` の行があるときも実装を呼び、見た反例があれば `not-satisfied`、無ければ判定不能になり、部分的に読んだ関係で反例が無いことが `satisfied` にならず、`present`/`absent`/`not-fetched` の行集合の例が実装と照合され、**既存の行集合の型ごとの実装とその試験が変更なく通る**。

## 9. 判断：式の入れ子は入れない

規則の入力は項目か定数に限る。`a + b > c`のような入れ子、`let`、`it`、パイプは入れない。

理由は三つある。入れ子を入れると、型の推論、途中の値がないときの伝わり方、診断の位置を、式の木の全体について決めることになる。それは汎用の式言語であり、今の停止線を越える。次に、実際に書かれた規則はどれも一段で書けている。最後に、記法の試作を四回レビューして反例が減らなかったのは、ほぼこの部分だった。

深さが要るときの方向だけを決めておく。**途中の値に名前を付けた導出として宣言し、規則はその名前を項目と同じように入力へ割り当てる。** 値を返すOperatorと導出の宣言を足すことになり、規則の正規形は変わらない。入れ子の式は、この導出へ展開する書き方として後から足せる。

見直す条件は具体的に置く。参照用の作業領域か移行の題材から、一段では書けない規則が三件集まり、どれも「その規則でしか使わないOperatorを作る」以外に書きようがないとき、導出を設計する。それまでは、一段で書けない規則はOperatorを宣言して書く。

## 10. 判断：組織のための言語は作らない

規則経路の文書§15は、所属の一覧を定義ではなく記録と判断した。この判断を前提として確定し、組織の扱いを次のように定める。

- **組織のための文法、解析器、意味モデルは作らない。** 組織は、標準の定義（組織単位、人、所属、委任といったDataと関係）、標準の規則、共通の表示の組合せとして提供する。
- **文書に書くのは、記録の形、規則、例である。** 誰がどこに属するかは記録であり、記録の置き場所に一つだけ置く。文書と記録の両方に同じものを置かない。
- **組織の規則は、§3の署名で書く。** 主所属の期間が重ならないことは、期間の重なりのOperatorを人ごとに区切って使う。終了日がないことは「終わりのない期間」の読み替えで書く。未定と不明の区別は記録の項目として持つ。
- **遡って訂正することは、Dataの項目と規則で表す。** 有効な時点と、認識した時点を別の項目にする。中核へ時間の仕組みを足さない。
- **認可は、組織の定義を読まない。** 判断の時点の記録をQueryで読む。所属を変えただけで責任や権限が移ることにはしない。
- **投資は共通の表示へ向ける。** 同じ所属をグラフ、表、期間の図で読み、一つの関係を選んで編集できること。これは組織に限らず使える能力である。

組織は、この文書の判断を試す二つ目の題材になる。人ごとの区切り、読み替え、束縛の「部署の所属をすべて返す」の宣言が、受注明細とは別の分野でそのまま使えるかを確かめる。最初に完成させるのは、所属一件の期間を変えて、三つの表示が同じ版を指すことである。

## 11. 判断：移行候補の読み方

既存の資産を解析して得た候補と、受理した定義を、次のように分ける。

- **候補は、作業領域の意味へ寄与しない。** 候補のファイルを置いただけでは、読込みの結果は変わらない。選んでいない文書を拒否する今の仕組みを保つ。
- **採用の単位は、定義一つの欄一つである。** 機能まるごとを推測で採用しない。すべてを手作業にも戻さない。
- **候補は、根拠の種類で三つに分ける。**

| 根拠の種類 | 例 | 進め方 |
| --- | --- | --- |
| 構造から得たもの | 表、項目、型、キー、参照 | 変換の候補にまとめる。人は一度の操作でまとめて採用できる |
| 動作を読んで得たもの | 初期値の計算、入力の検査、更新の条件 | 規則の候補と、旧動作を写した例の表の組にする。例が規則を支える範囲だけ採用する |
| 決められないもの | 動的に組み立てるSQL、外部への作用 | 未解決として残す。空欄を人に埋めさせず、どの根拠があればその欄を決められるかを示す |

- **採用の経路は一つである。** 採用は、設計文書への型付きの変更として、既存の編集と保存の経路を通す。保存後に読み直して確かめる。候補のための別の正本や別の採用の仕組みは作らない。
- **候補のIDは、定義の同一性にしない。** 再解析でIDが変わっても、定義は変わらない。出どころは、定義の近くへ来歴として残す。
- **旧動作との比較は、例の表に残す。** 例に根拠を付ける。「旧動作を観測した」か「仕様として定めた」かである。意図して変えた仕様は、旧動作の例と期待が違う例として書き、どの例を置き換えるかを示す。旧新の一致、互換の条件、意図した変更が、§8の例の表一つで管理できる。実行先を足しても同じ表を使える。

最初に完成させる一件は変えない。既存の照会一件から定義と新しい照会を作り、保存した単価が保たれることを、旧動作の例と比べて確かめる。

### 字句

書き方は次のとおりに決める。どれも今の文法を広げるもので、既存の文書の読み方は変えない。今の字句解析は、改行と字下げを区切りに使わず、読点（`,`）を字として受け付けない。数字は名前と同じ種類の字句として読む。そのため、区切りには決まった語と`名前:`だけを使い、読点は書かない。作業1と5で、既存の反例試験がすべて通ることを確かめてから入れる。通らない字句があれば、情報と動作（§3〜§6）を保ったまま字句だけを改める。

Operatorの宣言は、一行の形を残し、入力が二つ以上のときは字下げで並べる。

```tei
operator sales.non_negative: takes number

operator sales.within:
  takes value: number
  takes low: number
  takes high: number

operator std.not_overlapping:
  takes start: date of each row
  takes end: date of each row absent as open
  refutes on some rows

operator std.required_if:
  takes target: presence
  takes trigger: presence
```

一行の形は、`value`という名前の入力一つとして読む。型の語は`number`、`date`、`text`、`truth`、`any`。`presence`は値の有無を読む入力で、型を問わない。`of each row`は関係の行すべてを読む入力、`absent as <名前>`は値がないことの読み替え、`refutes on some rows`は一部の行での反証である。

規則は、今の`<項目> is <名前空間付きのOperator>`を広げる。主語の項目が最初の入力になり、残りは入力名を添えて書く。

```tei
rule sales.order_line.discount_in_range:
  sales.order_line.discount is sales.within low: 0 high: 100
```

入力へ書けるのは完全な項目のIDか定数である。次の入力は、名前の直後に`:`が続くことで見分ける。数の定数は数字で始まる字句（負の数は`-`で始まる字句）、文字の定数は引用符で囲んだ字句として読む。項目の後ろに`if present`、または`or <読み替えの名前>`を書ける。`per <関係>`と`for each <項目>`は、行すべてを読む入力があるときだけ書ける。今ある決まった言い回しは、同じ正規形へ読む。

束縛は、今のブロックへ一行足す。

```tei
header-detail-contract-query-binding {
    application order_entry
    pattern order_entry.order_lines
    contract sales_core.order_line
    query find_by_order
    input sales.order.order_id to order_id
    covers sales.order.lines
}
```

一部の行を返す束縛は`covers some`と書く。

## 13. 2026年11月19日：名前付き入力が製品で意味する範囲と、次の接続

§3〜§12で決めた署名と正規形は、これから作る文法の自由度を増やすためではなく、**業務で読める一つのRuleを、どの入力で、何を確かめるものとして評価するか**を固定するために使う。

現行コードを再確認した。 `internal/syntax/rule_authoring.go` は `takes amount: number` の名前と、規則に書かれた `name: value` の位置を読み取れる。しかし、`internal/semantic/model.go` の `Operator` は現時点で単一の `Input`／`InputName`／`AbsentAs` を保持し、`Validation` には複数の引数値を保持する欄がない。`internal/syntax/rule_authoring_validation.go` は、名前のない `takes number` を読取時の `value` と解釈する一方、規則が入力値を明示してもその値を捨てずに表現できるまで、製品の意味モデルへの入場を拒否する。これは設計上の失敗ではなく、**読める記法と、実際に扱える意味を区切る停止線**である。

### 13.1 最初の一件：単一入力の名前を付けても、読取先を増やさない

例えば次の記述では、`amount` は演算子の最初の入力の**名前**であり、規則に現れた `discount` とは別の数値を追加要求しない。

```tei
namespace sales

operator sales.non_negative: takes amount: number

rule sales.order_line.discount_non_negative:
  sales.order_line.discount is sales.non_negative
```

ここでは既存の意味モデルを使い、宣言の読み取り、型検査、Ruleの参照先、選択済み実装の一回の数値読取、実際の判定までを追える。一方、後ろに `amount: 0` を付けると、規則の主語がすでに与えた入力を二度割り当てることになるため、読込時に拒否する。**ただし、Operator宣言がRuleと別文書にある場合**、現行Readerはその場所で相手文書の名前付き入力一覧を参照せず、まず「入力値をMeaningへ保持できない」として拒否する。同一文書内の専用診断と文言が異なることを、受理漏れと取り違えない。

新しい製品回帰 `internal/workspace/tei_md_named_unary_operator_product_test.go` は、既存の別Markdown文書に置いたOperator宣言とRule、`Workspace.Load`／Source Index／`validationeval.EvaluateWithOperators` を用いてこの境界を検査する。文章だけを変更したときは意味を保ちながら古いSource Indexを失効させ、入力名自体を変更したときはOperator契約の変更を確認する。追加Go試験の実行結果は、exact HEADのCIを確認してから記録する。

### 13.2 次に実装することと、その順序

**第一段階の前提は、選択済みSource全体で署名を確定することである。** 現状の`RuleNamespace(file)`は同じ文書のOperator宣言だけから入力名を調べる。別文書の宣言を参照したRuleに入力値を明示すると、値を保持できないために拒否される。一方、`loadAuthoringMarkdown`はOperatorの例表を保留し、全Source読込後の`attachOperatorCases`で結び付けている。Ruleの入力も、この既存の読込経路に沿って後段で解決する。先に見つかった同名宣言へ暗黙に結び付ける別Registryや、値を落とした仮のValidationは作らない。

**後段解決の受入条件**：Ruleの主語・名前付き入力・参照した署名ID・原文byte位置・文書パスを解決前から保持する。選択済みの文書全体でOperator宣言が一意になった後にだけ入力を束縛し、宣言文書がRule文書より先でも後でも同じ結果にする。未選択の宣言で不足を補わず、同じIDの二重宣言、未知・重複・不足した入力名、主語の再束縛、型不一致は元のSource位置へ診断を返す。解決に失敗したとき、`mergeAuthoringMarkdown`が守る文書単位の受理・拒否を崩さず、Ruleの一部やOperator例だけがWorldに残った状態をLoad成功として返さない。

**回帰とSource資格は別々に照合する。** 旧`takes number`と`takes amount: number`の一入力経路、別文書の宣言・Rule・例表、宣言とRuleの文書順入替えを独立Expectedで検査する。宣言の原byteを変えずにファイルだけ移した場合は、意味が同じでもSource Index・Model Revisionを更新し、旧Indexを拒否する（[#5691](https://github.com/hat47x/tei-platform/pull/5691)）。この負例が通っても、三入力の意味保持・評価、Writer GrantやOwnerの意味受理が済んだことにはしない。

**第一段階：入力の意味を保持する。** `RuleInputAssignment` が保持している名前・値・原文位置を、既存`semantic.Validation`と`semantic.Operator`の意味として表せるようにする。入力の識別子、数値定数、参照するAttributeとその型、NULL／未取得、行ごとの読取範囲、評価時点を別に扱う。ここで新しいValidationKindや汎用式ASTを作らない。保存形を決めるときは、既存の `Function`／`Parameter` 等との再利用可能性も比較するが、モデル全体へ未確定の型を先に増やさない。

**第二段階：入力を必要とする実際の判定へ接続する。** 規則の主語と追加の入力を、宣言した署名の順序・役割で一回ずつ読取り、既存`validationeval.Decide`の結果と判定不能の理由へ接続する。宣言された入力以外を読まないこと、部分取得でも不成立が確定する場合を失わないこと、数値の精度や時点を暗黙に変更しないことを試験する。未対応のOperator実装は自動的に別方式へ置換しない。

**第三段階：独立した例で一つの実装を受理する。** 最初の題材は§12で固定した範囲判定（`value`、`low`、`high`）を維持する。入力のうち一つだけを変えた正例と負例、未取得、型不適合、重複束縛を同じ期待表で確認する。既存Operatorの契約例を通ることと、実Providerを呼んだこと、Ownerが業務意味を認めたことは分ける。

**第四段階：生成・製品利用へ接続する。** 成熟した一つのRuleに限り、解釈方式P／生成方式G／外部委譲Dの対応状況を説明し、実装の選択、実Call、実Builder入力、Artifact、通常CLIの独立Consumerを既存Ownerの受入へ渡す。StudioのStage1→Stage2セルフビルドの代用にはしない。

### 13.3 完了にしてはならないもの

次の五つは現段階で未達である。複数の名前付き入力を持つ正規形の製品受理、複数値を保持するMeaning、複数値での実評価、複数入力の実Provider読取、Ruleを再実装したGoの正式Builder・Consumer同一Attemptである。既存テストの一入力PASSや、宣言からの候補抽出だけでこれらを完了扱いにしない。

実装着手は§12のOwner（#4362、#1129と各Caller）へ戻し、原文→意味→実Read→判断の一辺ずつを確かめる。署名と評価を結ぶ差分が成立するまでは、Node View、組織モデル、Batch、BRMSのために別々のRule文法を増やさない。

## 14. 2026年11月21日：構文と実行をつなぐ「入力束縛の一巡」

この節は§13.2の実装順を補う**受入条件**であり、新たな実行系や構文の採用ではない。DSL・Clojure風のForm・中置式・Markdown表・Studioの編集フォームの検討を照合した結果、表記の違いを吸収する場所と、実データを読む場所を明確に分ける必要がある。どの表記から来た場合も、Ruleが何を読むかは、選択済みOperatorの署名と解決済みの入力束縛だけで決まる。

### 14.1 値を読む前に束縛を確定する

`sales.order_line.discount is sales.within low: 0 high: 100` を対象に、次の順序を守る。

1. **原文を読む。** Ruleの主語・Operator参照・名前付き割当てを、選択元文書と原byte範囲とともに候補として保持する。この時点で受理済みMeaningへ追加しない。
2. **選択済みSourceをそろえる。** 全Source読込後にOperator宣言を一意に解決する。宣言の出現順、Ruleとのファイル名順によって結果を変えない。同一IDの重複、未選択の宣言への依存は拒否する。
3. **署名の入力へ結び付ける。** 第1入力はRuleの主語だけが与える。残りは名前によって照合し、型を検査したうえで**署名の順に**並べる。不足・余分・重複・第1入力の再束縛は元の割当て位置へ診断を返す。定数とAttribute参照は区別したまま保持する。
4. **既存の読取境界へ渡す。** 値が必要になって初めて選択されたProvider／Scope／Attemptを使って読む。原文の記述順や表示形式から新たなReadやAuthorityを生まない。未取得・NULL・権限不足をゼロに置き換えない。
5. **既存の判断と例で確かめる。** Operatorの実装は署名に一致する一つだけを選ぶ。契約例と独立Expectedで照合し、業務上の不成立、判定不能、契約違反・実行エラーを区別する。

この手順の「束縛計画」は説明上の呼称であって、永続化する第二のMeaningや新しいRegistryを意味しない。現行の単一入力を表す`Input`／`InputName`／`AbsentAs`を複数入力表現へ移す場合も、**二種類の保存欄を同時に正本として解釈しない**。新旧の入力欄を矛盾した内容で併記するSource／意味表現は拒否し、旧`takes number`の評価結果とSource表現を回帰試験で守る。

### 14.2 読み取った範囲と判定の範囲を混同しない

`within`の最初の受入対象は**一つの行の三つの数値**である。ただし、三値が存在するだけでは判定可能とは限らない。参照する値は同じ業務対象・粒度に属し、同じRead Attempt／Snapshot、または明示的に整合を確認できる時点・取得条件に結び付いていなければならない。定数入力に実DBのSnapshotを要求するのではなく、**実際に読み取るAttribute間の整合性**を確かめる。複数Providerに共通Snapshotがあるとは推定しない。これを満たした行の範囲判定から、Relation全件についての成立を主張することもできない。Relation全件・集約・重複検査を行うOperatorでは、既存のQuery資格・Coverage・実Readの同一トランザクション／Snapshotの条件を別に満たす必要がある。

数値は原文の十進値を保持して厳密に比較する。`low > high`は定数なら検証時の誤り、実データで判明したなら当該評価の誤りとし、範囲外という不成立へ読み替えない。NULL・未取得・非開示・部分取得はそれぞれ根拠を保ち、計算できない理由を消さない。全入力がそろう前に、見えている一部の値だけから恣意的に成立を推定しない。

| B-06 | `low > high` | 宣言時に分かればRuleを拒否し、実データで初めて分かれば評価エラー |
| B-07 | NULL／未取得／partial／値0 | これらを同値にしない。行単位の答えとRelation全件の資格も分離する |
| B-08 | Sourceの説明文変更・別パスへの移動 | 意味が同じでも旧Source Index・Model Revisionを再利用しない |
| B-09 | 宣言の署名と選択実装／例表が不一致 | 別実装へ暗黙にfallbackせず、契約に従って拒否する |
| B-10 | 同じ行IDの`value`と`low`／`high`を異なるRead Attemptから取得 | 単に値が揃っただけでは同一時点の判定として受理しない。取得条件の整合を確かめられなければ判定不能とし、勝手に共通Snapshotを仮定しない |
| B-11 | 異なるAttribute参照が現時点では同じ数値を返す | 判定結果が等しくても、参照先のIdentity・依存関係・編集対象を同一視しない。変更後の再評価対象を取り違えない |
| B-12 | `low: 0 high: 100`の定数束縛と、同値を返すAttribute参照の束縛を比較 | 前者の論理的な読取要求はRule主語だけ、後者は主語と参照した属性。結果の一致をRead FootprintやProvider呼出の同値としない |

B-10〜12は、Function Data Contextの結果粒度・時点（#2506）と、Operatorの観測同値性（#988）を、このRuleで測定可能な形にしたものである。論理的な読取要求と物理的なSQL／Provider呼出回数は別に観測する。**判定値が等しいことは、依存先・読取経路・編集対象まで等しい証拠にはならない。**

各ExpectedはParser・Evaluatorから逆算せずに固定する。`1`と`1.0`は数値として等しく、三入力の例表では**数値組全体**で重複を検査する。現行の一数値・真偽値専用の`OperatorCase`に三入力を仮詰めしたり、「判定できない」を`false`で代用したりしない。対応前は明示的に未対応で停止する。

### 15.1 行集合入力の読みと設計

**結論**：既存の `StatefulSource` は拡張しない。`StatefulPeriodSource` と同じ形の、狭い能力interfaceを一つ足す。型は `NumberRowsReading{ Coverage Coverage; Rows []NumberReading }`、メソッドは `ReadRelationNumbers(relation, attribute core.CanonicalID) (NumberRowsReading, error)`。`NumberReading`・`Coverage`・`ReadAttempt` は既存をそのまま再利用する。新しいRegistryは作らない。

**根拠**：(a) `StatefulSource` へ増やすと `Row`・`legacySource` の全readerが実装を強いられ、`Row` は「一行に relation を訊かれた」と拒否する羽目になる（`ReadNumber`/`ReadDate` が Detail で拒否するのと対）。能力interfaceなら、実装しないreaderは型アサーションで検出でき、規則を**拒否**できる——`StatefulDateSource`/`StatefulPeriodSource` が既にこの形で、行化けした答えを出さない。(b) `PeriodRowsReading` は no-overlap 固有の固定形（`PeriodRow` が Start/End/Group）。`of each row` は任意の入力数を持つので、属性ごとの `ReadRelationNumbers` に一般化し、`NumberRowsReading` は「coverage + 各行の読み」という同一の形にそろえる。

**要件／条件**：`NumberRowsReading` は `Coverage` と `Rows []NumberReading` だけを持つ。`ReadRelationNumbers` は `Detail` にだけ実装し、`Row` では `ReadRelationKeys` と同じく拒否する。評価器は `ValidationOperator` 分岐で型アサーションにより発見し、読めなければ規則を拒否（error）とする。行集合入力が複数なら入力ごとに一度ずつ呼び、すべて同じ `Detail` の同一 attempt・同一 coverage から来る（B-10 は自動的に保たれる）。

### 15.2 `Coverage` と「一部の行での反証」の関係

**結論**：partial と反証の分岐は**評価器（`validationeval`）**に置く。`driver.Qualified`／coverage の決め方は変えない。三値 `tri` を再利用し、`no_overlap.go` から共有定義へ移して一意にする（重複排除であり新Registryではない）。operator の行関数は「見えた行」から `tri` を返し、評価器が `tri × Coverage × RefutesOnSomeRows` を `Decision` に写す。

| operator の `tri` | Coverage | RefutesOnSomeRows | 答え |
| --- | --- | --- | --- |
| triNo（見えた反例） | 問わない | 宣言あり | `not-satisfied` |
| triNo（見えた反例） | partial | 宣言なし | `undecided`（`relation-partially-read`） |
| triNo（見えた反例） | complete | 問わない | `not-satisfied`（全行を見たので宣言は無関係） |
| triYes | complete | 問わない | `satisfied` |
| triYes | partial | 問わない | `undecided`（`relation-partially-read`） |
| triMaybe（行内の未読・null） | 問わない | 問わない | 行内の理由（`value-null`/`value-not-fetched`）を coverage より先に報告 |

**根拠**：§6 の表（資格がなく、見えた行に反例があり、operator が一部の行で反証できると宣言していれば不成立、それ以外は判定できない）をそのまま実装にしたもの。`relation-unique`/`no-overlap` が既にこの厳密なロジックを持ち（`decideNoOverlap` の `overlapSeen→not-satisfied` と partial 順序）、`tri` はその中核である。次の答えを一つに絞る——partial・反例なしの答えは既存の `UndecidedRelationPartiallyRead` だけにし、新しい判定結果の種類は設けない（§8）。

**要件／条件**：既存の `Decide` 一経路・`Operators` 選択・`read_attempt.go` の B-10 判定は変えない（追加のみ）。coverage は `QualifyHeaderDetailCoverage` と物理表照合が決める現行のまま。`triMaybe` を coverage より先に返す順序は `decideNoOverlap` の `anyUnsure||dateMaybe` の順を踏襲する。

### 15.3 純粋関数の引数の形

**結論**：平坦な `Numbers map[string]*big.Rat` は拡張しない（行の状態を運べず、単入力の「値の揃った入力だけを受け取る」契約＝§5 を壊す）。`NamedImplementation` と `OperatorImplementation` に、行集合入力用の別フィールドを一つ足す。引数は `map[string][]NumberReading`（入力名→その入力の列の、各行の値と状態）。返りは三値（`tri` と同じ厳密性を持つ exported な判定型。`tri` を exported に昇進させ no-overlap と共用する）。`absent as` は**行単位**で、評価器が rule が名付けた mapping を `Absent` で読み替えてから行関数へ渡す（`readAssignedInput` の absent 処理の行版）。

**根拠**：no-overlap の判定は silent/unsure/stated の区別と `tri` の合成が必要で、値を剥いだ純粋関数では書けない。`NumberReading` は既に `State`（present/null/not-fetched）を持つので、行の状態は既存型で運べ、`PeriodRowsReading` が `[]PeriodRow`（各行が `DateReading` 二つ）であるのと対称である。§5 の表（値がある→実装へ、値なし＋読み替え→読み替え値、値なし指定なし→判定できない、未読→判定できない）は、行版にそのまま generalize して壊さない。

**要件／条件**：単入力（`Number`）・複数入力平坦（`Numbers`）の経路はそのまま。行関数は Source を持たない純粋関数（§3・§5）。例の表現——`semantic.OperatorCase` は `Value string`・`Inputs map[string]string`・`Satisfied bool` しかなく、N行×M入力の「一表が一例」（§8）を表せない。**最小拡張**として `Rows []map[string]string`（行の配列、各要素が入力名→値テキスト）と、例が「判定できない」を期待できるようにする三値の期待（`Satisfied bool` は残し、`undecided` 期待を書ける欄を足す）を追加する。既存の単値・入力別値の例の読み方は変えない。

### 15.4 規則の範囲の書き方

**結論**：範囲は新フィールドでなく**既存の `Validation.Relation`** に乗せる（`for each <属性>` は既存の `Validation.GroupBy`）。§12 の `per <関係>` をそのまま operator 規則へ適用する。`Relation`/`GroupBy` の意味を「関係の行の上で問われる規則」——`unique`・`no-overlap` に加え、行集合入力を持つ operator——へ広げるだけで、保存形は変えない（フィールドは既存・既に JSON 化）。reader の dispatch（`Detail.Decide`）は「その operator が `of each row` 入力を宣言するか、Kind が unique/no-overlap」なら Detail に一度訊き、それ以外は行ごと、に拡張する。

**根拠**：`RuleAuthoring.Scope` は `per <relation>` を、`Validation.Relation` は unique/no-overlap が既に使う。別 `Scope` 欄を足すと同一物の二重保存になり、§14.1 の「二種類の保存欄を同時に正本として解釈しない」に反する。subject 属性は第1入力の列で、`per <関係>` がその関係を名ぶる点は unique/no-overlap と同一である。

**要件／条件**：operator 規則が scope を書けるのは「その operator が `of each row` 入力を宣言するときだけ」。`of each row` を宣言する operator の規則は scope が必須（どの関係の行か決まらないため）。per-row operator（`of each row` なし）への scope は現行どおり拒否する。衝突しない——unique/no-overlap と同じフィールド・同じ dispatch・同じ読み方を共用する。

### 15.6 変換時の拒否を維持するか

**結論**：変換時の拒否は、評価経路（行読み取り＋行関数＋dispatch＋`tri × Coverage × RefutesOnSomeRows`）と `Detail.ReadRelationNumbers` が揃い、実DBの反例で通るまで**維持する**。そしてその経路を**同一変更で**外す。「意味へ取り込んだが判定できない」半端状態を作らないのはこちらである。

**根拠**：現在の拒否は load 時に Source 位置付き diagnostic を返し operator を meaning から落とすので、半端な受理が生まれない（安全）。意味へ先に取り込み評価時に未対応にすると、「受理したのに判定できない」が生まれる（避けるべき）。`OperatorInputDeclaration.OfEachRow` 等の欄は既に存在するので、取り込むのは schema 変更ではなく、拒否を外す**タイミング**の問題である。

**要件／条件**：不変条件を一つに置く——**宣言は (a) load 時に Source 位置付き diagnostic で拒否、または (b) meaning へ完全に運ばれ既存の一つの `Decide` で判定できる、のどちらか。「意味に入ったが黙って判定不能」は作らない。** 拒否を外す変更と、判定できるようにする変更を同一単位にする。

### 実装ワーカーが次に踏むべき一歩

`internal/semantic/validationeval` に `NumberRowsReading` と `ReadRelationNumbers`、`tri` の共有定義、`tri × Coverage × RefutesOnSomeRows → Decision` の写しの一箇所を、**SQLite の実 `Detail` に対する合成試験（反例つき）で先に固定する**。変換時の拒否は、この経路と `Detail.ReadRelationNumbers` が実DBの反例で通るまで維持する。

**一貫性（一文図式）**：`署名の of each row 入力 → Detail.ReadRelationNumbers(relation, attribute) が 1 読み取り（= 1 attempt）で []NumberReading を返す → operator の行関数は Source を持たず tri だけを返す → 評価器の一箇所が tri × Coverage × RefutesOnSomeRows を Decision に写す（反例は partial でも not-satisfied、それ以外は undecided）`。言い換えると——**1 行集合＝1 読み取り＝1 attempt。`of each row` の全入力は同じ `Detail` の同じ試行から読まれ、operator は純粋関数として `tri` だけを返し、`undecided` の理由と Coverage の結合は評価器の一箇所にしか置かない。**
