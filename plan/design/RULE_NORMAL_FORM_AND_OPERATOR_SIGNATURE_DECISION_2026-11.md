## 1. 結論

**規則は「宣言したOperator一つを、名前の付いた入力へ当てたもの」と定める。規則の種別は今ある六つで閉じ、今後は足さない。** 新しい規則はOperatorの宣言、実装、例の三つを足して作る。解析器、種別の列挙、評価器の分岐、読み手の境界は変えない。

この一点から、積み残していた判断が次のように決まる。

| 積み残していた判断 | 決めたこと | 節 |
| --- | --- | --- |
| 二つ以上の項目を受け取るOperatorの宣言 | 入力に名前、型、範囲、読むものを書く署名を採る | §3 |
| 行ごとに尋ねるか、関係の全行に一度尋ねるか | 規則の種別ではなく、署名の範囲から導く | §3、§5 |
| 値がないとき、読んでいないときの答え | 評価器が一か所で扱う。実装は値のある入力だけを受け取る | §5 |
| 全件かどうかの宣言 | Contract Queryの束縛に、どの関係の行をすべて返すかを書く。宣言だけでは揃っているとみなさず、実行したQueryの資格を照合できたときだけ揃っているとする | §6 |
| 暦日の保存と読取り | 読み手は`YYYY-MM-DD`の文字だけを受け取る。列の型が分かる場所で変換する | §7 |
| 入力と期待の表で意味を宣言する形 | 例の表の列を署名の入力名にする。読んでいない入力を含む例は、補った例と矛盾しないことを機械で確かめる | §8 |
| 式の入れ子、`let`、`it` | 入れない。必要になったら、途中の値に名前を付けた導出で深さを持たせる | §9 |
| 組織DSLの前提 | 組織のための言語は作らない。標準の定義と規則、共通の表示へ投資する | §10 |
| 移行候補の読み方 | 候補は意味へ寄与しない。採用は欄の単位で、既存の編集経路だけを通す。旧動作は例の表の根拠として残す | §11 |

この判断が正しいかは、§12の受入れ一件で確かめる。**標準にないOperatorを一つ足す変更が、宣言の文書、実装のファイル、その試験の三種類だけに収まること**である。収まらなければ、この判断は誤っている。

## 2. なぜ今決めるか

規則経路の文書は§7.4で「述語が固定の列挙である」ことを不足に挙げた。その後の追補は、不足を解かないまま規則を一件ずつ足した。mainの`semantic.Validation`は次の形になっている。

| 観測した事実（`internal/semantic/model.go`） | 何が起きているか |
| --- | --- |
| 種別が六つある（`positive`、`relation-unique`、`operator`、`not-after`、`no-overlap`、`required-if`） | 規則を一件足すたびに列挙が増える |
| `Compared`の欄が三通りの意味を持つ。比べる相手、期間の最終日、必須にする条件の項目 | 欄の意味を種別ごとに読み分けている |
| `IfPresent`、`GroupBy`、`OpenEnded`は、それぞれ一つの種別でだけ有効 | 種別に固有の欄が共通の構造に積もっている |
| 読み手の境界が四つある（数値、暦日、値の有無、関係のキー） | 読むものが変わるたびに境界が増える |
| 規則を行へ当てる入口は、種別ごとに尋ね方を決め、知らない種別を拒否する | 別のセッションが足した種別を読み手が知らず、試験で止めた（規則経路の文書§24の記録） |

一件を足す変更は、解析器、列挙、Validator、評価器、読み手、派生ツールへ同時に及ぶ。TEIが掲げる「分野が足すのはRoleとOperatorの宣言だけ」は、製品ではまだ成り立っていない。

積み残した判断のうち五つは、同じ問いの別の面である。**Operatorは、入力について何を宣言するのか。** 一件ずつ決めると、決めるたびに種別と境界がもう一つ増える。先に署名を決める。

`ValidationKind`には「汎用式言語やrule engineを先回りして導入しない」という注記がある。この判断はその線を越えない。式の入れ子は入れず、評価器も増やさない。既存の評価器の中で、種別ごとの分岐を署名の解釈一つへ置き換える。

## 3. 判断：Operatorの署名

Operatorの宣言は、入力ごとに次の四つを述べる。結果は当面、成立か不成立かの真偽に限る。

| 述べること | 取り得る値 | 決まること |
| --- | --- | --- |
| 名前 | 入力の名前 | 規則と例の表が入力を指す単位。診断が指す位置の単位 |
| 型 | 数値、暦日、文字、真偽、型を問わない | 読み手が値をどう読み、何を拒否するか（規則経路の文書§21「値の読み方」のとおり） |
| 範囲 | 一件の値／関係の行すべての値 | 尋ね方。行ごとか、行の集まりに一度か。全件の宣言が要るか |
| 読むもの | 値／値があるかどうか | 値がないことを、判定できない理由にするか、正当な入力にするか |

加えて、Operatorの全体について二つを述べられる。

- **値がないことの読み替え**。入力ごとに、値がないときに使える名前付きの読み方を宣言する。期間の最終日がないことを「終わりのない期間」と読む、などである。宣言のない読み替えは規則に書けない。
- **一部の行での反証**。行すべてを読む入力を持つOperatorが、見えた行の中の反例だけで不成立と言えるかを宣言する。一意と期間の重なりは言える。合計の上限のように、見えていない行で答えが変わるものは言えない。宣言がなければ言えないものとして扱う。

今ある六つの種別は、次の署名で書ける。新しい意味は足していない。

| 今の種別 | 入力（名前：型、範囲、読むもの） | 補足 |
| --- | --- | --- |
| `positive` | 値：数値、一件、値 | |
| `operator` | 値：数値、一件、値 | 今の`takes number`と同じ |
| `not-after` | 前：暦日、一件、値／後：暦日、一件、値 | `if present`は§4の規則側の指定 |
| `required-if` | 対象：問わない、一件、有無／条件：問わない、一件、有無 | |
| `relation-unique` | キー：問わない、行すべて、値 | 一部の行で反証できる |
| `no-overlap` | 開始：暦日、行すべて、値／終了：暦日、行すべて、値 | 終了は「終わりのない期間」と読み替えられる。一部の行で反証できる |

書き方は製品の今の宣言を広げる。`operator sales.non_negative: takes number`は、名前を省いた入力一つの宣言としてそのまま読める。入力を増やす書き方の字句は§12に決めた。優先するのは、宣言が持つ情報と、その情報から導かれる動作である。

単位付きの数量は、型の一つとして後から足せる位置に置いた。次元、尺度、換算の検査はこの判断に含めない。

## 4. 判断：規則の正規形

規則が持つのは次のものだけにする。

| 持つもの | 内容 |
| --- | --- |
| Operator | 宣言したOperatorのID。必ず一つ |
| 入力の割当て | 署名の入力ごとに、同じDataの項目一つ、または定数一つ |
| 入力ごとの指定 | 「値のある記録についてだけ述べる」（今の`if present`）か、Operatorが宣言した読み替えの名前。どちらもなければ指定なし |
| 範囲の区切り | 行すべてを読む入力があるときだけ書ける。どの項目の値が同じ行どうしを比べるか（今の`per`と`GroupBy`） |

「値のある記録についてだけ述べる」は、どのOperatorのどの入力にも同じ意味で使える。その入力に値がない記録は成立とする。これは今の`not-after`の`if present`と同じ答えで、種別に固有の欄を入力ごとの指定へ一般化したものである。

入力へ書けるのは項目か定数である。別のOperatorの呼出しは書けない（§9）。

### 保存した形は変えない

受理済みの定義、固定したGate版、内容の識別値に影響するので、`semantic.Validation`の保存形は今回変えない。三段で進める。

1. **読み替えを足す**。`Validation`から正規形を返す関数を一つ置く。五つの古い種別は、固定の表で標準のOperatorと入力の割当てへ写す。評価器、Validator、読み手、派生ツールは、この正規形だけを読むように改める。
2. **列挙を閉じる**。種別を足すと失敗する試験を置く。新しい規則は`operator`の種別で、入力の割当てを持つ形でだけ足せる。`operator`の種別には、入力の割当ての欄を足す。割当てのない既存の規則は、入力一つとして読む。
3. **保存形を揃える**。古い種別の保存形を正規形へ書き直すかは、別の判断にする。受理の経路と識別値の移行を伴うので、1と2が動いてから、必要が生じた時点で決める。行わなくても1と2の利点は得られる。

### 書き方

今ある言い回し（`is positive`、`is not after … if present`、`is required if …`など）は、標準のOperatorを呼ぶ決まった書き方として残す。読んだ結果は正規形になる。Workspaceが新しい言い回しを定義する仕組みは入れない。標準にないOperatorは、名前空間付きの名前と、入力名を添えた割当てで書く。字句は§12に決めた。条件は一つである。**既存の文書の読み方が変わらないこと。**

### 診断の位置

診断は「規則＋入力」を単位に位置を指す。規則経路の文書§7.4が挙げた「診断が欄を指せない」は、入力がそのまま単位になることで解ける。Source Indexへ足す単位はこれ一つにする。

## 5. 判断：評価の入口を一つにする

読み手の境界は一つにする。「あるDataの、これらの項目を、行の集まりとして読む」である。返すものは三つある。行、行ごと項目ごとの値の状態（値がある、値がない、読んでいない）、行の集まりがどこまで揃っているか（§6）。今の四つの境界は、この一つへ適合させる薄い変換として残し、呼ぶ側を順に移す。

値がない場合と読んでいない場合の扱いは、評価器が一か所で行う。Operatorの実装へは書かない。

| 入力の状態 | 読むものが「値」の入力 | 読むものが「有無」の入力 |
| --- | --- | --- |
| 読んでいない | 判定できない（読んでいない） | 「分からない」として実装へ渡す |
| 値がない、規則が「値のある記録についてだけ」と指定 | 成立 | ― |
| 値がない、規則が読み替えを指定 | 読み替えた値を実装へ渡す | ― |
| 値がない、指定なし | 判定できない（値がない） | 「ない」として実装へ渡す |
| 値がある | 型どおりに読んだ値を実装へ渡す | 「ある」として実装へ渡す |

理由が二つ重なるときは、読めば解ける理由（読んでいない）を、読んでも残る理由（値がない）より先に返す。規則経路の文書§17と§23の原則をそのまま使う。

**実装は、値の揃った入力だけを受け取る純粋な関数になる。** 判定できない場合の分岐を実装ごとに書かずに済み、書き漏らしも起きない。

有無を読む入力にだけ「分からない」を渡すのは、今の`required-if`の答えを保つためである。対象に値があれば、条件を読んでいなくても成立と言える。実装が「分からない」を受け取って答えを返すときは、**分からない入力をどう補っても同じ答えになる場合に限る**。この条件は§8の例の表で機械的に確かめる。

尋ね方は署名から導く。行すべてを読む入力が一つでもあれば、範囲の区切りごとに行の集まりへ一度尋ねる。なければ行ごとに尋ねる。行が一つもないとき、行ごとに尋ねる規則の答えは0個である。行ごとの答えはまとめない。どちらも今の動作と同じである。種別がなくなるので、「知らない種別を拒否する」分岐は要らなくなる。

## 6. 判断：全件かどうかは束縛に書く

行の集まりが関係の全行かどうかは、行からは分からない。今は呼出し側の引数で述べている。これをContract Queryの束縛へ移す。束縛はQueryが何を返すかを知っている唯一の定義だからである。

行すべてを読む規則は、範囲を関係で書いている（`is unique per sales.order.lines`）。受注一件の明細、という単位である。束縛の宣言も同じ単位で書く。

| 束縛の宣言 | 意味 | 例 |
| --- | --- | --- |
| ある関係の行をすべて返す | 入力で定まる親一件について、その関係の行は揃っている | 受注一件の明細すべて |
| 一部の行を返す | 揃っていると言えない | 検索結果、ページ |
| 書かない | 何も述べていない | ― |

「関係の全行か、一部か」の二択を、DB全体についての問いにしない点が要である。「受注ごとに明細番号が一意」は、受注一件の明細が揃っていれば判定できる。表の全行は要らない。

**宣言は「揃っている」の根拠にならない。**（2026年11月17日に改めた。初めの版は、宣言があれば揃っているとみなしていた。その実装[#5341](https://github.com/hat47x/tei-platform/pull/5341)の試験で、宣言したままQueryが明細を1行落とすと、実際には重なっている明細番号の一意が「成立」になることを確かめ、統合しなかった。）

束縛の`covers`は書いた人の宣言（Declared）である。SQLの中身からは一般に証明できない。そこで、揃っているかを次の二つに分ける。

| 区別 | 中身 | 判定への効き方 |
| --- | --- | --- |
| 宣言 | 束縛の`covers <関係>`／`covers some` | `validate`の照合と、結果への記録（どの束縛が何を宣言したか）だけに使う。それだけでは「揃っている」にしない |
| 資格 | 実行したQueryについて、対象の関係、親の範囲、追加の条件、ページ・件数の制限、時点を照合できたこと | これがあるときだけ「揃っている」とし、§5のとおりに判定する |

資格の確かめ方は、一般のSQL完全性の証明器を作らずに、狭いContract Queryから始める。照合できないQueryは「一部」として扱う（閉じる側へ倒す）。行の数、`LIMIT`がないこと、0行であること、宣言があることは、どれも資格にしない。

| 場面 | 動作 |
| --- | --- |
| 行すべてを読む規則を、その関係について宣言のない束縛の上で選んだ | `tei validate`の警告 |
| 資格がある | §5のとおりに判定する |
| 資格がない（宣言だけがある場合を含む） | 見えた行の中に反例があり、Operatorが一部の行で反証できると宣言していれば不成立。それ以外は判定できない |
| 呼出し側が実行時に述べる | 下げることだけできる（揃っている→一部）。上げることはできない |

試験には、宣言を残したまま行を落とすQueryで「成立」が出ないこと（判定できない、または見えた反例による不成立）を必ず置く。

親を持たないDataの全行にわたる規則（マスタ全体でコードが一意、など）は、今の規則の書き方に範囲の関係がないので、この判断の範囲に入れない。必要になった時点で、範囲の書き方と一緒に決める。

## 7. 判断：暦日

規則経路の文書§24は、日時の列を暦日として読むと、実行した機械の時間帯で答えが変わることを実際のDBで確かめた。読み手は値がどの型の列から来たかを見られない。そこで次のように決める。

- **読み手が暦日として受け取るのは、`YYYY-MM-DD`の文字だけにする。** 「0時ちょうどの日時をその日として読む」受け方はやめる。機械によって答えが変わると確かめた受け方を、既定に残さない。
- **変換は、列の型が分かる場所で行う。** DBの実行を担う側は、結果の列の型をドライバーから得られる。暦日の列は`YYYY-MM-DD`の文字にして行へ入れる。日時の列が暦日の項目へ返ってきたら、変換せずに誤りにする。SQL realizationが列の型を書かなくても、実行のたびにこの検査が及ぶ。
- **保存の型に暦日を足す。** Providerごとの対応（暦日の型を持つDBではその型、持たないDBでは書式を検査した文字）とDDLの生成は、DBの担当が決める。それまでは、暦日の項目を文字で保存する今の扱いを続ける。
- **日時から暦日を得ることは、時間帯を入力に取るOperatorとして明示する。** 暗黙には行わない。

## 8. 判断：例の表で意味を述べる

Operatorの意味は、宣言の近くに書いた例で述べる。今の例の表（入力は数値一つ）を、署名に合わせて広げる。

- 一件の値だけを読むOperatorは、一行が一例である。列は署名の入力名、期待、注記にする。空のセルは「値がない」、決まった語で「読んでいない」を書く。期待には、成立、不成立、判定できないを書ける。
- 行すべてを読むOperatorは、一表が一例である。既にある記録の例の表（期待を印に書く形）と同じ形にし、列を入力名にする。
- 実装を選ぶとき、すべての例と照合する。一つでも違う実装は、そのOperatorの実装として使わない。これは今の動作と同じである。

足す検査は一つである。**読んでいない入力を含む例が成立か不成立を期待するとき、その入力を補った例が表にあれば、期待が同じでなければならない。** 違えば宣言の誤りとして診断する。§5で実装に求めた条件を、宣言の側でも確かめることになる。

この表は、移行でも同じ役目を持つ（§11）。

## 9. 判断：式の入れ子は入れない

規則の入力は項目か定数に限る。`a + b > c`のような入れ子、`let`、`it`、パイプは入れない。

理由は三つある。入れ子を入れると、型の推論、途中の値がないときの伝わり方、診断の位置を、式の木の全体について決めることになる。それは汎用の式言語であり、今の停止線を越える。次に、実際に書かれた規則はどれも一段で書けている。最後に、記法の試作を四回レビューして反例が減らなかったのは、ほぼこの部分だった。

深さが要るときの方向だけを決めておく。**途中の値に名前を付けた導出として宣言し、規則はその名前を項目と同じように入力へ割り当てる。** 値を返すOperatorと導出の宣言を足すことになり、規則の正規形は変わらない。入れ子の式は、この導出へ展開する書き方として後から足せる。

見直す条件は具体的に置く。参照用の作業領域か移行の題材から、一段では書けない規則が三件集まり、どれも「その規則でしか使わないOperatorを作る」以外に書きようがないとき、導出を設計する。それまでは、一段で書けない規則はOperatorを宣言して書く。

## 10. 判断：組織のための言語は作らない

規則経路の文書§15は、所属の一覧を定義ではなく記録と判断した。この判断を前提として確定し、組織の扱いを次のように定める。

- **組織のための文法、解析器、意味モデルは作らない。** 組織は、標準の定義（組織単位、人、所属、委任といったDataと関係）、標準の規則、共通の表示の組合せとして提供する。
- **文書に書くのは、記録の形、規則、例である。** 誰がどこに属するかは記録であり、記録の置き場所に一つだけ置く。文書と記録の両方に同じものを置かない。
- **組織の規則は、§3の署名で書く。** 主所属の期間が重ならないことは、期間の重なりのOperatorを人ごとに区切って使う。終了日がないことは「終わりのない期間」の読み替えで書く。未定と不明の区別は記録の項目として持つ。
- **遡って訂正することは、Dataの項目と規則で表す。** 有効な時点と、認識した時点を別の項目にする。中核へ時間の仕組みを足さない。
- **認可は、組織の定義を読まない。** 判断の時点の記録をQueryで読む。所属を変えただけで責任や権限が移ることにはしない。
- **投資は共通の表示へ向ける。** 同じ所属をグラフ、表、期間の図で読み、一つの関係を選んで編集できること。これは組織に限らず使える能力である。

組織は、この文書の判断を試す二つ目の題材になる。人ごとの区切り、読み替え、束縛の「部署の所属をすべて返す」の宣言が、受注明細とは別の分野でそのまま使えるかを確かめる。最初に完成させるのは、所属一件の期間を変えて、三つの表示が同じ版を指すことである。

## 11. 判断：移行候補の読み方

既存の資産を解析して得た候補と、受理した定義を、次のように分ける。

- **候補は、作業領域の意味へ寄与しない。** 候補のファイルを置いただけでは、読込みの結果は変わらない。選んでいない文書を拒否する今の仕組みを保つ。
- **採用の単位は、定義一つの欄一つである。** 機能まるごとを推測で採用しない。すべてを手作業にも戻さない。
- **候補は、根拠の種類で三つに分ける。**

| 根拠の種類 | 例 | 進め方 |
| --- | --- | --- |
| 構造から得たもの | 表、項目、型、キー、参照 | 変換の候補にまとめる。人は一度の操作でまとめて採用できる |
| 動作を読んで得たもの | 初期値の計算、入力の検査、更新の条件 | 規則の候補と、旧動作を写した例の表の組にする。例が規則を支える範囲だけ採用する |
| 決められないもの | 動的に組み立てるSQL、外部への作用 | 未解決として残す。空欄を人に埋めさせず、どの根拠があればその欄を決められるかを示す |

- **採用の経路は一つである。** 採用は、設計文書への型付きの変更として、既存の編集と保存の経路を通す。保存後に読み直して確かめる。候補のための別の正本や別の採用の仕組みは作らない。
- **候補のIDは、定義の同一性にしない。** 再解析でIDが変わっても、定義は変わらない。出どころは、定義の近くへ来歴として残す。
- **旧動作との比較は、例の表に残す。** 例に根拠を付ける。「旧動作を観測した」か「仕様として定めた」かである。意図して変えた仕様は、旧動作の例と期待が違う例として書き、どの例を置き換えるかを示す。旧新の一致、互換の条件、意図した変更が、§8の例の表一つで管理できる。実行先を足しても同じ表を使える。

最初に完成させる一件は変えない。既存の照会一件から定義と新しい照会を作り、保存した単価が保たれることを、旧動作の例と比べて確かめる。

### 字句

書き方は次のとおりに決める。どれも今の文法を広げるもので、既存の文書の読み方は変えない。今の字句解析は、改行と字下げを区切りに使わず、読点（`,`）を字として受け付けない。数字は名前と同じ種類の字句として読む。そのため、区切りには決まった語と`名前:`だけを使い、読点は書かない。作業1と5で、既存の反例試験がすべて通ることを確かめてから入れる。通らない字句があれば、情報と動作（§3〜§6）を保ったまま字句だけを改める。

Operatorの宣言は、一行の形を残し、入力が二つ以上のときは字下げで並べる。

```tei
operator sales.non_negative: takes number

operator sales.within:
  takes value: number
  takes low: number
  takes high: number

operator std.not_overlapping:
  takes start: date of each row
  takes end: date of each row absent as open
  refutes on some rows

operator std.required_if:
  takes target: presence
  takes trigger: presence
```

一行の形は、`value`という名前の入力一つとして読む。型の語は`number`、`date`、`text`、`truth`、`any`。`presence`は値の有無を読む入力で、型を問わない。`of each row`は関係の行すべてを読む入力、`absent as <名前>`は値がないことの読み替え、`refutes on some rows`は一部の行での反証である。

規則は、今の`<項目> is <名前空間付きのOperator>`を広げる。主語の項目が最初の入力になり、残りは入力名を添えて書く。

```tei
rule sales.order_line.discount_in_range:
  sales.order_line.discount is sales.within low: 0 high: 100
```

入力へ書けるのは完全な項目のIDか定数である。次の入力は、名前の直後に`:`が続くことで見分ける。数の定数は数字で始まる字句（負の数は`-`で始まる字句）、文字の定数は引用符で囲んだ字句として読む。項目の後ろに`if present`、または`or <読み替えの名前>`を書ける。`per <関係>`と`for each <項目>`は、行すべてを読む入力があるときだけ書ける。今ある決まった言い回しは、同じ正規形へ読む。

束縛は、今のブロックへ一行足す。

```tei
header-detail-contract-query-binding {
    application order_entry
    pattern order_entry.order_lines
    contract sales_core.order_line
    query find_by_order
    input sales.order.order_id to order_id
    covers sales.order.lines
}
```

一部の行を返す束縛は`covers some`と書く。
