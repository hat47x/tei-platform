- 状態: **調査・引継ぎ用の設計案**。製品仕様、受理済み対応、実装完了、実環境受入ではない。
- 作成: 2026-10-17
- 追跡: [#1969](https://github.com/hat47x/tei-platform/issues/1969)
- 既存の入口: [#950](https://github.com/hat47x/tei-platform/issues/950)、[#1142](https://github.com/hat47x/tei-platform/issues/1142)、[#1802](https://github.com/hat47x/tei-platform/issues/1802)、[#1119](https://github.com/hat47x/tei-platform/issues/1119)
- 前提: 旧原典・検収Ledger・Script・モデル固有識別子は非公開の資料庫に保持する（[#941](https://github.com/hat47x/tei-platform/issues/941)）。本設計案は、公開可能な**判断方法**だけを扱う。

## 1. 解こうとする問題

原典モデルをTEIで再現しようとしたとき、「実装不可」には少なくとも三つの異なる意味が混じり得る。

1. 原典の要素が分からない、または原典とTEIの意味的な対応がまだ受理されていない。
2. 意味は表せるが、選んだ実行先・Provider・Hostで実現する能力や接続が足りない。
3. 必要な意味を、既存のTEI定義とプラグイン構成で表せない具体的な反例がある。

さらに、「実行していない」「原典の実挙動と比較できない」「公開できない」は、いずれも**製品機能が欠けている証拠ではない**。これらを一律に機能追加へ振り分けると、誤ったCore拡張、不要なIssue、未受理の業務意味の固定化が生じる。

この文書では、**原典側で止まった理由を製品側の責務へ渡すための照合方法**のみを整理する。形式化が必要になっても、まず既存Ledger／Issueの記載で運用する。新しい保存形式、状態型、受入Gateを制定しない。

## 2. 調査する一単位

対象は、旧ツールの機能名そのものではなく、**特定の業務上の仕事／意味をTEIで表現・実行しようとして止まった一経路**とする。

| 記録欄 | 記載内容 | 公開境界 |
| --- | --- | --- |
| 事象 | 匿名の追跡番号、要約、原典種別 | 公開可 |
| 元の根拠 | 原本digest、原典node/attribute/Function/Table/Script locator、版、静的／実測の別 | 具体的locatorは非公開 |
| 対応候補 | 提案されたTEI要素、対応の説明、承認の有無 | 未受理は未受理と記す。原本再構成情報は非公開 |
| 試行 | TEI revision、受理した定義、Target/Provider、開始条件、停止段階、診断 | 公開可能な合成例のみ公開 |
| 判定 | 既存で可能／制約付きで可能／要証拠／契約判断待ち／再現した不足／移植不要とする判断 | **断定の根拠**とOwnerを併記 |
| 次の行動 | 不足証拠、既存Owner Issue、必要なら最小の独自再現例 | 個別Issueへの引継ぎを優先 |

判定欄の表現はレビュー用の自然言語であり、TEI共通の列挙型を追加する提案ではない。「実装不可」は原則として**どの前提に対して不可能か**を添える。原典を未受理のまま製品要求として採用しない。

## 3. 停止位置による分類と引継ぎ

| 停止した段階 | まず検討する理由 | 主な既存担当 |

| 原典→意味候補 | Functionと画面・メニュー等の表現差、Table/Field/Keyの差、Scriptが持つ実際の効果の未特定 | source/model Owner、#950、#1120 |
| 候補→受理済み定義 | 意味同一性、業務上の制約、更新責任の未承認 | #267、関連するBusiness/Model Owner |
| 定義→実行計画 | Capability欠落、Plugin解決不能、必要Providerの未接続 | #1121、#1127、#1130 |
| Action→副作用確定 | Transaction境界、認可版、競合、拒否結果、保存後の結果照会 | #1129、#1174、#1708（個別論点に応じる） |

## 4. 代表的な未決事項の置き場所

以下は現状の資料から見える**調査対象の類型**である。いずれも「TEIの機能欠落が確定した」という意味ではない。

| 論点 | 分かっている範囲 | なお足りないもの | 引継ぎ |
| --- | --- | --- | --- |
| 元Function／TableとTEI候補 | 原典・実装間の静的対応候補や差異は存在する | source/model Ownerによる対応根拠と受理 | source/model Owner、#950 |
| 元のActionに対応する業務効果 | 合成Referenceには低位の拒否・副作用制御の一部がある | 原典との対応、Action/Event/効果の意味、正式Host接続 | #1129 |
| Validationの鮮度 | 複数入力・Snapshot・競合を扱う課題がある | 読取り集合の再評価と同一確定境界の採用判断 | #1708 |
| output-onlyの拒否 | 低位`StatusDenied`の実装根拠がある | Canonical業務結果への意味写像と正式呼出経路 | #1174ほか既存結果契約Owner |
| Authorityと回復 | CAS／rollback／receipt／replay等に参照実装がある | 実Host／Owner Authority／Providerの確定経路と実DB検証 | #1174 |
| 実保存と旧Driver比較 | 過去の固定Work根拠で正式production save caller・対象Windows GUI実行は未確認 | 同じ対象と前提での独立実行観測 | #940、#1142、#1163 |

旧Workの固定snapshot `518be565` の結論を、後日の`main`のコード閲覧だけで更新しない。既存の低位実装が見つかった場合でも、製品Hostがそれを呼んでいる証拠とは分ける。

## 5. 新規増強Issueへ進む場合

次を**説明できる範囲で**一つの機能不足を切り出す。説明できないときは調査未了として残す。

- 実現したい仕事の意味が、単なる旧画面／旧Scriptの互換要求ではなく、TEIの製品価値に結び付いていること。
- どの原典事実・業務Ownerの受理に由来するか。未受理なら仮説として扱い、確定要求にしない。
- 現行の既存機構、Plugin、Projection、Provider接続では足りないことを示す、公開可能な独自合成fixtureまたは再現可能な診断。
- 正常系と、誤って成功扱いしてはいけない負例。実DBや旧Driverの観測がまだない場合はその旨。
- 設計・契約の判断Ownerと、実装Ownerが同じか異なるか（不明なら未特定）。
- 他のIssueと重ならない変更範囲。既存契約に衝突するなら先にそのOwnerへ判断を戻す。

Issueを起票したという事実は、意味の受理、製品契約の採用、実装、試験、動作同等性のいずれの代わりにもならない。

## 6. 初回作業と確認範囲

1. 非公開の検収Ledgerと移植候補から、実際に進行が止まった経路を限定して取り出す。具体的な原典識別子は公開しない。
2. 停止位置と確定可能な事実、推測、証拠欠落を分け、既存担当へ照合を依頼する。
3. 公開側には匿名の事象と責務・不足する根拠だけを返す。原典から再構成可能なJSONや詳細なScriptは渡さない。
4. 既存の担当で解消可能なものは追記で済ませる。独立した不足が再現できた段階でのみ、最小要求を新規Issueにする。

**本案の確認範囲**: 公開Issue・設計資料、非公開検収README／静的調査記録の読取り。テスト実行、TEIのコード変更、原典Driver実行、実DB操作、Windows GUI操作、Ownerによる意味受理は行っていない。
