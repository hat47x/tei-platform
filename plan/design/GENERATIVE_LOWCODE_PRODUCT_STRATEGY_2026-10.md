# 生成AIネイティブなローコード開発基盤の製品戦略（2026-10）

- 状態: 提案・優先順位の整理（未採用）
- 日付: 2026-10-18
- 位置づけ: 複数のIssueとADRにまたがる製品戦略の仮説。設計判断はADR、作業条件はIssue、実装状況は`docs/status.md`を正本とする。
- 関連: #2016 / #2017 / #2018 / #2019 / #2020 / #2021 / #1803 / #1124 / #1125 / #1119 / #1802 / ADR-0034 / ADR-0035

## 1. この文書の役割

TEIが、X-TEAのModeler/Editor/Driverが担っていた仕事を引き継ぎながら、生成AI時代の開発基盤として何を目指すかを整理する。個別機能の仕様ではなく、**どの価値を先に作り、何で測り、どこで止めるか**を決めるための材料とする。

ここに書くのは仮説であり、採用済みの製品約束ではない。数値目標や市場規模は置かない。効果はIssueごとのPoCとベンチマークで確かめる。

## 2. 戦略を一文で表す

TEIは、業務の意味を正本として保ち、その意味から**生成器を導出・検証・再利用**することで、従来型のコーディングとローコードのどちらよりも、生成AIが扱いやすく、変更に強い開発基盤を目指す。

アプリケーションを毎回生成するのではない。生成の単位を生成器へ上げ、生成器を版付きの成果物として検証する。これにより、同じ意味から複数の実行先を組み立て、生成AIの生産性を再現可能な形で使う。

## 3. 価値の仮説

### 3.1 意味を正本にすると、生成AIの仕事が小さくなる

生成AIが扱う対象を、コード全体から、識別子・関係・制約・検証・手順へ狭める。意味の記述はコードより小さく、変更の影響を型付き参照で辿れる。生成AIは、既存の意味を検索し、変更案を作り、影響を示すことに集中できる。

### 3.2 定型設定の生産性を、意味の再利用へ拡張する

X-TEAは、機能種別とテーブル定義の組合せで、定型的な画面・帳票・バッチを高い生産性で作る。TEIは、この定型性を受理済み意味からの生成器の再利用として引き継ぐ。案件ごとに生成器を書き直すのではなく、契約と適合試験を共有し、差分だけを案件側へ置く。

### 3.3 設計情報の正規化が、変更と引継ぎを支える

設計情報を正規化し、同じ関心事を一か所に置く。名称、識別子、表示、実装、証拠を混ぜない。正規化された意味は、生成AIの文脈を減らし、人にとっても変更箇所と影響を追いやすくする。

### 3.4 業務知識と技術基盤を分けると、技術を選び直せる

業務上の概念、規則、例外、手順を、画面・DB・言語・配備から分ける。技術を交換しても、意味と検証を引き継ぐ。生成AIは、特定のフレームワークやベンダーに閉じずに、複数の実現を比較できる。

### 3.5 生成器を生成できると、対象追加のコストが下がる

生成AIに生成器を書かせ、固定した適合試験で選抜する。テンプレート、手書き、生成AIの実装を同じ期待値で比較する。生成器の出所ではなく、適合の証拠で選ぶ。これにより、組込みからエンタープライズまで、対象ごとの実装を小さく増やせる。

## 4. X-TEAから引き継ぐ仕事

X-TEAのModeler/Editor/Driverの思想から、TEIが引き継ぐのは画面や書式ではなく、設計者の仕事である。詳細な対応は[設計ツールの機能移植対応表](AUTHORING_TOOL_FEATURE_TRANSFER_MAP_2026-10.md)を正本とする。

| 引き継ぐ仕事 | TEIでの置き換え | 担当 |
| --- | --- | --- |
| データ・業務・機能の三要素を一つのモデルで扱う | 意味の正本と、複数のProjection | #1124 / #1125 / #1126 |
| 定型の機能を定義から組み立てる | 受理済み意味からの生成器・設計成果物 | #2016 / #1803 / #1127 |
| 設計書・一覧・DDLを出す | 決定的な派生物とmanifest | #1803 |
| 変更を版と影響で追う | 型付き参照、Semantic Diff、影響、再検証 | #1120 / #1143 / #1803 |
| 人が設計し、AIが案を出す | 提案と受理の分離、Shared Acceptance | ADR-0022 / #267 |
| 複数の実行形態を選ぶ | Target Profileと生成器の交換 | #2019 / #259 |

引き継がないものは、Swingの画面、`.xead`/`.xeaf`の書式、任意SQLの実行、旧Runtime固有の確定規約である。互換の再現を目的にしない。

## 5. 生成AI適合性の根拠（仮説）

TEIが従来型の開発やローコードより生成AIに適合する根拠は、次のように分解できる。いずれも未測定であり、#2018で比較する。

| 根拠 | 期待する効果 | 反証する観測 |
| --- | --- | --- |
| 意味の記述がコードより小さい | 文脈量が減り、変更案の精度が上がる | 文脈量が減らない、または精度が上がらない |
| 識別子と参照が安定している | 生成AIが対象を取り違えにくい | 同名別scopeの誤参照が減らない |
| 制約と検証が宣言されている | 生成案を機械的に検査できる | 検査通過率が従来と変わらない |
| 受理境界が明確である | 生成案の採用判断を分けられる | 自動受理の誤りが増える |
| 生成器を再利用できる | 対象追加・変更の手修正が減る | 生成器の保守コストが手書きを上回る |
| 証拠が版に束縛される | 再検証の範囲を限定できる | 再検証漏れや過剰検証が減らない |

「圧倒する」は目標であり、測定前の主張ではない。比較は、同じ業務変更、同じ評価集合、同じ環境で行う。

## 6. 適用範囲のスペクトル

TEIの意味モデルは変えず、Target ProfileとDelivery Profileを変える。

| 領域 | 主な制約 | 変えるもの | 変えないもの |
| --- | --- | --- | --- |
| 組込み・OS常駐 | 資源、起動、オフライン、更新 | 実行モデル、生成器、配備 | 意味のidentity、Validation、拒否の種類 |
| 端末・小規模 | 単一利用者、ローカルデータ | 認証、保存、配布 | 意味の正本、変更の受理 |
| SIer受託 | 顧客ごとの納品、権限、監査 | Delivery Profile、証拠の開示 | 意味の契約、生成器の適合 |
| 大規模SaaS | テナント分離、段階更新、監査 | 分離、権限、運用 | 意味の契約、変更の手順 |
| エンタープライズ基幹 | 既存DB、認証、移行、可用性 | Adapter、移行、配備 | 意味の正本、業務規則 |

個人・SIer・大規模SaaSの提供形態は#2020、組込みからエンタープライズまでの配備は#2019で扱う。

## 7. 生成器生成とメタ生成

生成器の生成は、次の順で小さく試す。

1. 受理済み契約と対象Profileを固定する。
2. 候補を作る前に、期待値fixtureと適合試験を固定する。
3. テンプレート、手書き、生成AIの候補を同じ試験で比較する。
4. 生成器のsource digest、入力契約、対象、試験版、結果をreceiptに残す。
5. 危険な候補を負例で排除する。
6. 採用した生成器を、失効条件とともに版管理する。

メタ生成（生成器を生成する生成器）は、基準となる生成器と適合試験を固定した範囲でだけ行う。無制限の再帰を許さない。詳細はADR-0034と#2016で扱う。

## 8. 軽量認知基盤の位置づけ

端末内・閉域・低資源の環境では、クラウドの大規模モデルを前提にできない。軽量な認知基盤は、候補生成、分類、診断、要約を担う。ただし、提案だけを出し、受理・権限・実行を決めない。

モデル名・版・設定・入力文脈・出力のfingerprintを記録し、モデルを差し替えても同じ期待値fixtureで比較できるようにする。能力外・不明・失敗を、空の提案や成功へ潰さない。詳細は#2021で扱う。

## 10. 測定と反証

各施策は、次の順で評価する。

1. Baseline: 現行の手作業・既存ツールで同じ変更を行い、時間、介入回数、変更範囲、再検証範囲を記録する。
2. 候補: TEIの新しい経路で同じ変更を行い、同じ指標を記録する。
3. 比較: 差がどの構造から生じたかを切り分ける。単なるコード量の削減を成果にしない。
4. 撤回: 効果が確認できない、保守コストが上回る、失敗の意味を潰す、第二の権威を必要とする場合は撤回する。

測定は#2018のベンチマークに集約し、個別IssueのPoCはその一部として再利用できる形にする。

## 11. リスクと境界

- 過剰な抽象化: 意味の記述が実装より複雑になると、生成AIにも人にも扱いにくい。#1973の「効果がなければ撤回」を適用する。
- 生成器の増殖: 対象ごとに生成器が増えると保守コストが上がる。共通契約と適合試験で選抜し、重複を許さない。
- AIの自己承認: 生成AIの自己申告を、受理・権限・適合の証拠にしない。ADR-0022と#267の境界を守る。
- ベンチマークの gaming: 評価集合を候補に合わせて変えない。結果の不確かさを記録する。
- ライセンスと外部資料: 参照モデル・手引書の内容を転載しない（#941）。外部の設計論は、出典の事実とTEIの判断を分けて記録する。
- 人間の判断: 意味の受理、権限、本番配備、秘密情報、ライセンスは自動化しない（ADR-0035）。
