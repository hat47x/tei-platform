# PostgreSQL提供元の制約出力の設計

- 状態: 設計案（評価待ち）。実装はしていない。
- 対象Issue: [#1803](https://github.com/hat47x/tei-platform/issues/1803)（DDL出力の入口。親: [#1802](https://github.com/hat47x/tei-platform/issues/1802)）
- 関連する設計判断: [ADR-0009](../adr/0009-unique-constraint-and-unique-index.md)、[ADR-0013](../adr/0013-offline-physical-realization-policy.md)、[ADR-0015](../adr/0015-provider-owned-migration-sql-rendering.md)
- 関連する設計: [意味の変更に伴う既存データの移行設計](SEMANTIC_CHANGE_DATA_EVOLUTION_DESIGN_2026-10.md)の5章（PostgreSQLでの安全な手順）

## 1. この文書の役割

DDL出力の入口（`tools/reference-ddl-entry`）を`reference/workspace`の`sales_core`に適用すると、PostgreSQLの提供元は二つの表を、どちらも出力できませんでした。理由は、どちらの表にも主キーがあり、提供元が主キーの出力を拒否するためです。

この文書は、その拒否を解消するために何が足りないかを確かめた結果と、段階的に解消する案をまとめます。SQLの組み立ては提供元の責務のままで（ADR-0015）、この文書は提供元の中で何を決めるかを扱います。

## 2. 現状（2026年10月18日の`main`で確認）

| 箇所 | 確認した内容 |
| --- | --- |
| `internal/database/providers/postgres/migration_sql.go` | 表の新規作成は`CREATE TABLE <表> ();`を出力し、列は後続の列の追加で出力する。主キーを持つ新規作成は、`until constraint identity is realizable`として拒否する。主キーの変更（`change-primary-key`）も同じ理由で拒否する |
| 同上 | 一意制約・外部キーの追加と削除（`add-unique-constraint`、`drop-unique-constraint`、`add-foreign-key`、`drop-foreign-key`）は、未対応の変更種別として拒否する |
| `internal/database/physical/model.go` | 主キーは`PrimaryKey []string`（列名の並び）で、制約の名前を持たない。一意制約と外部キーは任意の`Name`を持つ |
| `internal/database/providers/postgres/sql_catalog.go` | 主キーの観測は、列の並びだけを読む。制約の名前（`conname`）は読まない。一意制約と外部キーの観測は`conname`を読む |
| `internal/database/schemadiff/diff.go` | 差分は、主キーの変更（`change-primary-key`）と、一意制約・外部キーの追加と削除を、すでに区別して出す |

つまり、差分と観測の側は主キー・一意制約・外部キーを扱えますが、**出力の側（提供元のSQL組み立て）が主キーも、一意制約も、外部キーも出力できません**。「制約の識別」とは、制約の名前をどう決め、どう観測し、どう比べるかを指します。

## 3. 解決したいこと

- 新規作成用のDDLに、主キー、一意制約、外部キーを含められる。
- 制約の名前が、望む状態、実際の状態、差分、出力文のあいだで食い違わない。
- 既存の行を持つ表に主キーや制約を足す場合に、既存データが違反していないことを、実行前に確かめられる。

## 4. 案

### 4.1 段階

| 段階 | 内容 | 前提 |
| --- | --- | --- |
| P0 | 制約の名前の決め方を決める（4.2） | なし |
| P1 | 新規作成する表の主キーを出力する | P0 |
| P2 | 新規作成する表の一意制約を出力する | P1 |
| P3 | 外部キーを出力する。参照先の表が作られた後に出す | P1 |
| P4 | 既存の表への制約の追加を、既存データの検査つきで出力する | P1〜P3、移行設計の5章 |
| P5 | 主キーの変更を扱う | P4 |

P1〜P3は、空の表に対する新規作成だけを扱います。既存データがない前提なので、データの違反は起きません。P4からが、既存データとの両立の問題です。

### 4.2 制約の名前の決め方（P0で決めること）

選択肢を二つ挙げます。

- **案A**: 意味の側（物理対応）に任意の名前を持たせ、持たないときは、物理の実現の方針（ADR-0013）が決定的な名前を決める。一意制約と外部キーの現在の扱い（任意の`Name`）と揃う。
- **案B**: 名前を宣言させず、PostgreSQLの既定の名前（主キーは`<表>_pkey`）に任せる。観測は名前を読むが、比べるのは列の並びだけにする。

私の推奨は案Aです。理由は、制約の追加・削除を後から出力するとき、名前が決まっていないと、削除の文を書けないためです（`DROP CONSTRAINT`は名前が要ります）。案Bは新規作成だけなら足りますが、P4以降で名前の観測が必要になり、設計を二度やることになります。

案Aの場合に追加で決めること:

1. 名前を持たない場合の決定的な生成規則（表名、列名、制約の種類から作る）と、PostgreSQLの識別子の長さの制限（63バイト）を超えた場合の扱い。
2. 観測した名前と、望む名前が異なる場合を、差分としてどう扱うか。名前だけの違いを`ChangePrimaryKey`にするか、別の種類にするか。
3. 一意制約と外部キーの既存の`Name`との整合。

### 4.3 出力の順序と形（P1〜P3）

空の表への新規作成は、次の順に出します。

1. `CREATE TABLE <表> ();`（現状どおり）
2. 列の追加。主キーの列は`NOT NULL`で追加する。
3. `ALTER TABLE <表> ADD CONSTRAINT <名前> PRIMARY KEY (<列>);`
4. 一意制約の追加。
5. すべての表の作成の後に、外部キーの追加。参照先の主キーまたは一意制約が先に存在する必要があるため。

差分の側が出す変更の順序に依存せず、提供元が種類ごとに整列して出します。外部キーが互いを参照する循環があっても、最後にまとめて出せば成立します。

### 4.4 既存データの検査（P4）

既存の行を持つ表へ主キー・一意制約・外部キーを足す場合は、移行設計の5章に従い、実行前に次を数えます。値そのものは示しません。

- 主キーと一意制約: 重複する行と、主キーの列に空の値がある行の件数。
- 外部キー: 参照先に存在しない行の件数。

件数がゼロでなければ、補完・修正・例外の扱いの宣言なしに出力しません。観測の権限がない場合は、件数ゼロと扱わず`unresolved`にします（移行設計のDE-10）。

## 5. 効果仮説と観測（#1973）

- 従来の限界: 物理対応から、実用的な新規作成用のDDLを取り出せない。DDL出力の入口が`sales_core`で全表を拒否される。
- 効果（P1〜P3）: `reference/workspace`の`sales_core`で、両方の表のDDLが出力できる。
- 観測: 出力した文を、実データベース（PostgreSQL）で実行し、実際の状態を観測して、望む状態との差分がなくなることを確かめる（`schemadiff.Compare`が空になる）。合成データの試験だけで、実環境で動く証拠にしない。
- 撤回条件: 提供元がSQLを組み立てる方式（ADR-0015）では制約の出力が成り立たないと分かった場合は、この案を見直す。
- 未確認: 実データベースでの実行、名前の長さの制限を超える場合、循環する外部キー。

## 6. 受入シナリオと否定試験

| 番号 | 状況 | 期待する動作 |
| --- | --- | --- |
| PK-01 | 主キーを持つ表の新規作成 | `CREATE TABLE`、列、主キーの追加を出力する。実データベースで実行後、差分が空になる |
| PK-02 | 複合主キー | 列の順序を保つ |
| PK-03 | 名前が識別子の長さの制限を超える | 黙って切り詰めず、決定的な規則で短縮するか、`unresolved`にする |
| PK-04 | 主キーの列がNULLを許す定義 | 出力前に診断にする |
| UQ-01 | 一意制約を持つ表 | 一意制約として出力し、一意索引と区別する（ADR-0009） |
| FK-01 | 互いを参照する二つの表 | すべての表の作成後に外部キーを出力する |
| FK-02 | 参照先が主キーも一意制約も持たない | 診断にする |
| EX-01 | 既存の行に重複がある表へ主キーを追加 | 件数を示して止める。補完の宣言なしに出力しない |
| EX-02 | 観測の権限がない | `unresolved`。件数ゼロとしない |

## 7. 結論を出していない範囲

- 制約の名前の決め方（4.2の案A・案B）。
- 名前だけが異なる場合の差分の種類。
- PostgreSQL以外の提供元。現在、提供元のレンダリングはPostgreSQLだけが実装されている。
- 主キーの変更（P5）の安全な手順。
- 外部キーの検証を後から行う方式（`NOT VALID`の利用）。運用上のロックの特性が変わるため、移行設計の5章と合わせて判断する。
