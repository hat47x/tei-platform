# PostgreSQL提供元の制約出力の設計

- 状態: 設計案（評価待ち）。P1〜P4を実装した（P4は4.4）。P5は実装していない。
- 対象Issue: [#1803](https://github.com/hat47x/tei-platform/issues/1803)（DDL出力の入口。親: [#1802](https://github.com/hat47x/tei-platform/issues/1802)）
- 関連する設計判断: [ADR-0009](../adr/0009-unique-constraint-and-unique-index.md)、[ADR-0013](../adr/0013-offline-physical-realization-policy.md)、[ADR-0015](../adr/0015-provider-owned-migration-sql-rendering.md)
- 関連する設計: [意味の変更に伴う既存データの移行設計](SEMANTIC_CHANGE_DATA_EVOLUTION_DESIGN_2026-10.md)の5章（PostgreSQLでの安全な手順）

## 1. この文書の役割

DDL出力の入口（`tools/reference-ddl-entry`）を`reference/workspace`の`sales_core`に適用すると、PostgreSQLの提供元は二つの表を、どちらも出力できませんでした。理由は、どちらの表にも主キーがあり、提供元が主キーの出力を拒否するためです。

この文書は、その拒否を解消するために何が足りないかを確かめた結果と、段階的に解消する案をまとめます。SQLの組み立ては提供元の責務のままで（ADR-0015）、この文書は提供元の中で何を決めるかを扱います。

## 2. 現状（2026年10月18日の`main`で確認）

| 箇所 | 確認した内容 |
| --- | --- |
| `internal/database/providers/postgres/migration_sql.go` | 表の新規作成は`CREATE TABLE <表> ();`を出力し、列は後続の列の追加で出力する。主キーを持つ新規作成は、`until constraint identity is realizable`として拒否する。主キーの変更（`change-primary-key`）も同じ理由で拒否する |
| 同上 | 一意制約・外部キーの追加と削除（`add-unique-constraint`、`drop-unique-constraint`、`add-foreign-key`、`drop-foreign-key`）は、未対応の変更種別として拒否する |
| `internal/database/physical/model.go` | 主キーは`PrimaryKey []string`（列名の並び）で、制約の名前を持たない。一意制約と外部キーは任意の`Name`を持つ |
| `internal/database/providers/postgres/sql_catalog.go` | 主キーの観測は、列の並びだけを読む。制約の名前（`conname`）は読まない。一意制約と外部キーの観測は`conname`を読む |
| `internal/database/schemadiff/diff.go` | 差分は、主キーの変更（`change-primary-key`）と、一意制約・外部キーの追加と削除を、すでに区別して出す |

つまり、差分と観測の側は主キー・一意制約・外部キーを扱えますが、**出力の側（提供元のSQL組み立て）が主キーも、一意制約も、外部キーも出力できません**。「制約の識別」とは、制約の名前をどう決め、どう観測し、どう比べるかを指します。

## 3. 解決したいこと

- 新規作成用のDDLに、主キー、一意制約、外部キーを含められる。
- 制約の名前が、望む状態、実際の状態、差分、出力文のあいだで食い違わない。
- 既存の行を持つ表に主キーや制約を足す場合に、既存データが違反していないことを、実行前に確かめられる。

## 4. 案

### 4.1 段階

| 段階 | 内容 | 前提 |
| --- | --- | --- |
| P0 | 制約の名前の決め方を決める（4.2） | なし |
| P1 | 新規作成する表の主キーを出力する | P0 |
| P2 | 新規作成する表の一意制約を出力する | P1 |
| P3 | 外部キーを出力する。参照先の表が作られた後に出す | P1 |
| P4 | 既存の表への制約の追加を、既存データの検査つきで出力する | P1〜P3、移行設計の5章 |
| P5 | 主キーの変更を扱う | P4 |

P1〜P3は、空の表に対する新規作成だけを扱います。既存データがない前提なので、データの違反は起きません。P4からが、既存データとの両立の問題です。

### 4.2 制約の名前の決め方（P0で決めること）

選択肢を二つ挙げます。

- **案A**: 意味の側（物理対応）に任意の名前を持たせ、持たないときは、物理の実現の方針（ADR-0013）が決定的な名前を決める。一意制約と外部キーの現在の扱い（任意の`Name`）と揃う。
- **案B**: 名前を宣言させず、PostgreSQLの既定の名前（主キーは`<表>_pkey`）に任せる。観測は名前を読むが、比べるのは列の並びだけにする。

- **案C**: 主キーは名前を宣言せず（無名のまま）、削除や変更のときに、実際のデータベースのカタログから名前を観測して使う。一意制約と外部キーは、すでに任意の`Name`を持つので、案Aの扱いにする。

#### 先行事例からの根拠

公式文書とソースコードで確認した内容です（原文の保存先と行番号は調査記録にあります）。

- PostgreSQLは、名前を指定しなければシステムが名前を生成します（[CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html)）。主キーの名前は表名に`_pkey`を付けた形で、列に依存しません（`indexcmds.c`の`ChooseIndexName`）。ただし、生成した名前が既存の関係と衝突する場合は、ラベルに数字が付き、表名の側は63バイトに収まるよう切り詰められます（同`makeObjectName`、`ChooseRelationName`）。**既定の名前は、常に`<表>_pkey`とは限りません。**
- 識別子は既定で最大63バイトで、それより長い名前は切り詰められます（[字句構造](https://www.postgresql.org/docs/current/sql-syntax-lexical.html)）。
- 一つの表が持てる主キーは一つだけです（[制約](https://www.postgresql.org/docs/current/ddl-constraints.html)）。一意制約と外部キーは複数持てます。
- Alembicの文書は、`DROP CONSTRAINT`には名前が要ること、名前はカタログから調べられるが、PostgreSQLの内部の命名に頼ることには疑問があることを述べ、命名規約の辞書で全制約に名前を与える方法を示します（[Alembic](https://alembic.sqlalchemy.org/en/latest/naming.html)）。
- SQLAlchemyは、生成した名前が長すぎるとき、名前のmd5から作る4文字の接尾辞で決定的に切り詰めます。Djangoは表名、列名、ダイジェストから名前を作り、長ければ縮めます。Railsの外部キー名は、表と列から決定的に作る10文字の識別子で、任意の名前も指定できます。
- Djangoは、名前を持たずに列からカタログを調べて制約を探し、見つかった数が一つでなければ失敗させます。
- Atlasの記述言語では、主キーのブロックは名前を持たず、外部キーのブロックは名前（ラベル）を持ちます（[Atlas](https://atlasgo.io/atlas-schema/hcl)）。これは、現在のTEIの物理モデル（主キーは無名、一意制約と外部キーは任意の名前）と同じ形です。
- Atlasは制約の名前を比べ、違えば名前の変更（RENAME）を計画に出します。ORMのように制約に名前を付けない定義では、環境ごとに生成される名前が異なり、意味のない変更が出るため、名前の比較を省く設定（`rename_constraint = true`）を用意しています（[Atlas FAQ](https://atlasgo.io/faq/skip-constraint-rename)）。
- 実際の失敗例として、Gerritは、PostgreSQLの主キーの名前を「表名_pkey」と仮定していたため、表名を変えた後（主キーの名前は変わらない）に主キーを削除できず、移行が失敗しました。修正は、仮定をやめて、データベースのメタデータから名前を取得する方式でした（[Gerritのコミット](https://gerrit.googlesource.com/gerrit/+/477f8e296532c65d10dc27f6cff96462504c47f8%5E%21/)）。
- 名前を切り詰めた結果が別の名前と衝突すると、PostgreSQLはエラーにします（[pgsql-general, 2013](https://www.postgresql.org/message-id/20130110162334.GA24281%40momjian.us)）。

確認できなかったこと: 案Aと案Bを直接比べた原典。Liquibaseの変更の差分での名前の扱い。移行ツールが、切り詰めた名前の衝突で失敗した事例。

#### 推奨

**案Cを推奨します。** 理由は次のとおりです。

- 主キーは一つの表に一つだけなので、削除や変更の対象は名前なしで一意に特定できます。カタログから名前を観測すれば足り、名前の宣言は要りません。既定の名前が`<表>_pkey`と限らない事実（衝突時の数字、切り詰め、表名の変更後も主キーの名前は変わらないこと）にも影響されません。Gerritの失敗は、まさに「表名_pkey」と仮定した場合に起きた問題です。
- 名前の違いを差分にするかは、定義側が名前を与えるかで決まります（Atlas）。主キーを無名にすれば、名前の違いは差分になりません。一意制約と外部キーは名前を与えるので、名前の違いは差分になります。この扱いは、4.2の追加で決めることの2番目に当たります。
- 一意制約と外部キーは複数あるため、削除のときに名前が要ります。すでに任意の`Name`を持つので、案Aの規約で名前を決定的に与えるのが自然です（Alembic、Django、Railsの方式と同じ向きです）。
- 現在の物理モデルを変えずに済み、変更が小さいです。案Aを主キーにも広げる必要が、先行事例からは見えませんでした。

案Cの主キーで残る問題: 新規作成の主キーを出力するとき、名前を指定しないと、PostgreSQLの既定の名前になります。その名前が、後で観測した名前と一致することを、出力文を実データベースで実行して確かめます（5章の観測）。

一意制約と外部キー（案A）で追加で決めること:

1. 名前を持たない場合の決定的な生成規則（表名、列名、制約の種類から作る）と、PostgreSQLの識別子の長さの制限（63バイト）を超えた場合の扱い。
2. 観測した名前と、望む名前が異なる場合を、差分としてどう扱うか。名前だけの違いを`ChangePrimaryKey`にするか、別の種類にするか。
3. 一意制約と外部キーの既存の`Name`との整合。

#### 1番目の仮決め（#1803）

利用者の暫定承認を受けて、1番目を次のとおり仮に決めました。正式な採用ではありません。実装はPostgreSQLの実現の方針（`providers/postgres.RealizationPolicy`）にあり、`persistence.RealizeDesired`が、`Name`を持たない一意制約と外部キーに名前を付けます。望ましい物理の形が名前を持ち、提供元のレンダリングは常に`ADD CONSTRAINT <名前>`を出力します。名前を持たない一意制約・外部キーが届いた場合、レンダリングは拒否します。主キーは案Cのとおり無名のままです。

- 規則: 一意制約は`<表>_<列1>_<列2>..._key`、外部キーは`<表>_<列1>..._fkey`。表名はスキーマを含めず、列は宣言の順です。これはPostgreSQLの既定の名前と同じ形です。以前に名前なしで作ったデータベースでも、63バイト以内で、PostgreSQLが数字を付けていなければ、名前が一致します。PostgreSQL 16.15で、`ADD UNIQUE (pb, pa)`が`child_pb_pa_key`、`ADD FOREIGN KEY (pa, pb)`が`child_pa_pb_fkey`、多バイトの表名も`表テーブル_列_列二_key`となることを確かめました。
- 63バイトを超える場合: PostgreSQLの切り詰めに頼りません。名前全体をUTF-8の文字の境界で54バイト以内に切り、`_`と、切る前の名前全体のSHA-256の先頭8文字（16進の小文字）を付けます。**PostgreSQLの切り詰めとは意図的に異なります。** PostgreSQLは表と列の部分を切り、`_key`などを残します（例: `a_very_long_table_name_for_te_first_long_column_name_second_key`）。このため、長い名前では、以前に名前なしで作ったデータベースと名前が一致しません。
- 衝突: 生成した名前が、他の生成した名前や宣言された名前と衝突する場合、その表を`unresolved`として理由つきで返し、出力しません。PostgreSQLでは、一意制約は同じ名前の索引を伴うので、スキーマ内の関係の名前（表、索引、主キーの索引）と同じ名前空間にあります。制約の名前は、表ごとにも一意である必要があります。外部キーは関係ではないので、同じ表の制約の名前とだけ比べます。主キーの名前は`<表>_pkey`と予測して比べます。宣言された名前どうしの衝突は、この規則の対象外です。
- 他の提供元: Oracleの実現の方針は名前を付けません（未決定）。

2番目（名前だけの違い）は未決定です。現在の差分は制約を構造（列の並び、参照先）で比べ、名前を比べません。名前だけが異なっても差分は出ません。実データベースの試験では、名前をカタログから直接確かめています。

### 4.3 出力の順序と形（P1〜P3）

空の表への新規作成は、次の順に出します。

1. `CREATE TABLE <表> ();`（現状どおり）
2. 列の追加。主キーの列は`NOT NULL`で追加する。
3. `ALTER TABLE <表> ADD CONSTRAINT <名前> PRIMARY KEY (<列>);`
4. 一意制約の追加。
5. すべての表の作成の後に、外部キーの追加。参照先の主キーまたは一意制約が先に存在する必要があるため。

差分の側が出す変更の順序に依存せず、提供元が種類ごとに整列して出します。外部キーが互いを参照する循環があっても、最後にまとめて出せば成立します。

### 4.4 既存データの検査（P4）

既存の行を持つ表へ主キー・一意制約・外部キーを足す場合は、移行設計の5章に従い、実行前に次を数えます。値そのものは示しません。

- 主キーと一意制約: 重複する行と、主キーの列に空の値がある行の件数。
- 外部キー: 参照先に存在しない行の件数。

件数がゼロでなければ、補完・修正・例外の扱いの宣言なしに出力しません。観測の権限がない場合は、件数ゼロと扱わず`unresolved`にします（移行設計のDE-10）。

#### 実装した範囲（#1803、2026年10月25日）

P4を、表の削除の事前確認（`RenderMigrationSQLWithObservation`と`SchemaObservation`）と同じ形で実装しました。実装は`internal/database/providers/postgres/constraint_data.go`にあります。

- 対象: 同じ差分で作らない表への一意制約・外部キーの追加と、主キーを持たない表への主キーの追加（`change-primary-key`のうち変更前の主キーが空のもの）。既存の主キーの置き換えと削除はP5として拒否のままです。
- 観測: `Provider.ObserveConstraintData`が、差分の追加ごとに件数を数え、`SchemaObservation.ConstraintData`に入れます。数える内容は、主キーと一意制約では、NULLを含まない重複したキーの値の数と、その値を持つ行の数です。主キーでは、キーの列にNULLがある行の数も数えます。外部キーでは、キーの列がすべてNULLでなく、参照先に対応する行がない行の数を数えます（`MATCH SIMPLE`）。参照先の表を同じ差分で作る場合は、その表が空なので、キーの列がすべてNULLでない行を数えます。問い合わせは識別子を引用符で囲み、件数だけを返します。値は返しません。
- 観測できない場合: 数える手段を持たない読取り口や、権限がなく数えられなかった場合は、その追加を`Observed=false`とし、理由を残します。件数ゼロとはみなしません。
- 判定: `RenderMigrationSQLWithObservation`は、追加ごとに観測を照合します。観測がない、観測できなかった、別の差分の観測である場合は`existing-data-unobserved`、件数が一つでもゼロでない場合は`existing-data-violations`として、件数を示し、差分全体を拒否します（`ConstraintDataReadinessError`）。主キーの列が望む状態でNULLを許す場合も拒否します。観測を受け取らない`RenderMigrationSQL`は、既存の表への追加を常に拒否します。
- 出力: 判定を通った追加は、新規作成と同じく、主キー、一意制約、外部キーの順に`ALTER TABLE ... ADD ...`で出力します。適用の直前は、既存の`ApplyPostgresWithFreshObservation`が同じ判定で出力し直します。そのため、適用の直前に件数を数え直す場合は、渡す観測に`ObserveConstraintData`の結果を含める必要があります。含めなければ拒否されます。
- 実データベースの確認: PostgreSQL 16.15（`postgres:16`）で、行を持つ既存の表に対して次を確かめました（`tools/reference-ddl-entry/existing_realdb_test.go`）。違反がない場合は制約が追加され、実行後の差分が空になりました。重複、NULL、参照先のない行がある場合は、期待どおりの件数で拒否され、制約は作られませんでした。拒否の文に値は含まれません。数えない場合と、表を読む権限のない役割で観測した場合は、`existing-data-unobserved`になりました。

#### 未決

- 違反がある場合の扱い（補完、修正、例外）の宣言。この設計も移行設計も構文を決めていないため、件数がゼロでない追加は拒否のままです。
- 観測から適用までの間のデータの変化。適用時に数え直せば検出できますが、数え直しから`ALTER TABLE`までの間に書き込まれた行は、PostgreSQL自身の検査で失敗します。
- 重複の判定は、問い合わせの`GROUP BY`の等価で数えます。制約の索引の演算子クラスと等価の定義が異なる型では、件数が制約の判定と一致しない可能性があります。確かめていません。
- 大きな表での件数の問い合わせの所要時間と負荷。全件を走査します。
- 移行設計の5章が推奨する手順（一意性は`CONCURRENTLY`で作った索引から制約にする、外部キーは`NOT VALID`の後に`VALIDATE CONSTRAINT`）は使っていません。ロックの特性が変わるため、7章のとおり別に判断します。

## 5. 効果仮説と観測（#1973）

- 従来の限界: 物理対応から、実用的な新規作成用のDDLを取り出せない。DDL出力の入口が`sales_core`で全表を拒否される。
- 効果（P1〜P3）: `reference/workspace`の`sales_core`で、両方の表のDDLが出力できる。
- 観測: 出力した文を、実データベース（PostgreSQL）で実行し、実際の状態を観測して、望む状態との差分がなくなることを確かめる（`schemadiff.Compare`が空になる）。合成データの試験だけで、実環境で動く証拠にしない。
- 撤回条件: 提供元がSQLを組み立てる方式（ADR-0015）では制約の出力が成り立たないと分かった場合は、この案を見直す。
- 未確認: 実データベースでの実行、名前の長さの制限を超える場合、循環する外部キー。

## 6. 受入シナリオと否定試験

| 番号 | 状況 | 期待する動作 |
| --- | --- | --- |
| PK-01 | 主キーを持つ表の新規作成 | `CREATE TABLE`、列、主キーの追加を出力する。実データベースで実行後、差分が空になる |
| PK-02 | 複合主キー | 列の順序を保つ |
| PK-03 | 名前が識別子の長さの制限を超える | 黙って切り詰めず、決定的な規則で短縮するか、`unresolved`にする |
| PK-04 | 主キーの列がNULLを許す定義 | 出力前に診断にする |
| UQ-01 | 一意制約を持つ表 | 一意制約として出力し、一意索引と区別する（ADR-0009） |
| FK-01 | 互いを参照する二つの表 | すべての表の作成後に外部キーを出力する |
| FK-02 | 参照先が主キーも一意制約も持たない | 診断にする |
| EX-01 | 既存の行に重複がある表へ主キーを追加 | 件数を示して止める。補完の宣言なしに出力しない |
| EX-02 | 観測の権限がない | `unresolved`。件数ゼロとしない |

## 7. 結論を出していない範囲

- 制約の名前の決め方（4.2の案C）。一意制約と外部キーの生成規則は、PostgreSQLの既定の名前に合わせる規則で**仮決め**です（4.2の「1番目の仮決め」）。正式に採用するかは決めていません。
