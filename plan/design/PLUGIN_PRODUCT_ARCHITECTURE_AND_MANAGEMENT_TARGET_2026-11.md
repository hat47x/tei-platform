# Studioとビルド成果物を一体で拡張するプラグイン基盤の理想設計

2026年11月14日。将来の製品に必要な構成を先に定める設計案である。現行の型、Registry、Source配置、PoCの接続方式を上限にはしない。実装へ移す際は既存ADRとの整合と移行方法を判断するが、その確認を理由に理想形の検討を縮小しない。本書のフィールド名は概念上の契約案であり、既存APIの実装済み名称ではない。

## プラグインが拡張するのは開発の一部分ではない

TEIのプラグインは一つの機能を設計し、編集し、検証し、実装へ変換し、利用環境で動かすまでに必要な部品を、同じ契約と版の下で提供する。StudioのUIと、生成したアプリケーションのUI・実行機能を一体で拡張する。

例えばDBプラグインを選ぶと、Studioでは表・項目・キー・関係を設計し、Queryを書き、取得結果や更新単位を確認できる。Buildでは同じ定義からアクセス処理、必要なDDLや移行処理、画面の入出力との接続を作る。成果物には選んだDBへの接続と実行に必要な実装だけを組み込む。Studioの表示と、生成後に実行する処理を別々の製品へ手作業で設定し直すことを減らす。

統合するのは設計から利用までの契約と版である。Studio用Editor、設計検査、Generator、実行時サービスは別の成果物でよい。同じ論理パッケージが、それらの対応する契約、依存、入力と出力を説明できることが重要である。配布単位、実行プロセス、論理的なプラグインの識別を一対一に固定しない。

## 基本原則と採る構成

Coreには識別、参照、型付きのデータと操作、定義の版、拡張点を接続する最小の規律を置く。DB、認証、組織、描画、特定のUIライブラリやクラウドをCoreの必須実装にしない。標準機能も同じ拡張契約を通して提供し、標準だけが使える非公開の接続経路を常態化させない。

意味を表す定義、実装の選択、生成物、実行ごとの状態は分ける。意味定義を先に解釈し、その契約を満たすProviderとTargetを選ぶ。実装方式の都合から、設計上異なる値や関係を同じものとして扱わない。UI、DSL、API、CLI、MCPは同じ操作契約の異なる入口として接続する。

標準の選択は利用者がすぐ仕事を始められる構成にする。必要なプラグインを一件ずつ探して数十項目を手設定することを初期体験にしない。標準Profileから始め、案件の要件に応じてDB、認証方式、UI、媒体等を差し替える。追加した機能の設計UIと生成後の機能が、同じ選択へ追随する。

実装は宣言と目的に合う形式を選ぶ。CSS、Schema、辞書、図表、Templateだけで成立するプラグインに実行コードを要求しない。実行する場合も静的結合、Process、Wasm、外部サービス等を契約に応じて選ぶ。全プラグインを同じ言語、同じプロセス、常駐サービスへ固定しない。

## 提供物を段階ごとに明示する

プラグインが拡張点へ提供する部品をContributionと呼ぶ。各プラグインは必要な段階の部品と、それらの対応を宣言する。

| 段階 | 提供する部品の例 | 受け手 |
| --- | --- | --- |
| 設計の意味 | 型、値域、関係、制約、操作、状態、DSLの拡張 | 解析、型検査、標準データ構造 |
| Studio | Palette、Property Editor、図表、専用View、設定支援、診断、操作、ヘルプ | Studioの構成と編集操作 |
| 検査と変換 | 静的検査、意味変換、最適化、差分、移行変換 | Compiler、検証、変更影響 |
| 生成と構築 | Generator、Template、Target Binding、DDL、資産、Toolchain Adapter | Buildの工程と成果物 |
| 実行とUI | サービス、データアクセス、認証、UI部品、OS連携、外部接続 | 生成したアプリケーション |
| 試験と運用 | Fixture、独立した期待結果、Scenario、負荷試験、診断・観測、更新支援 | Studio、CLI、CI、実環境の運用 |

Contributionの基本情報には、識別、段階、接続先、入力と出力の契約、対応するTarget、実装またはデータの参照、必要な設定、依存、起動条件、作用、失敗・取消・資源の条件を持たせる。UIの表示位置だけを宣言し、必要な操作や意味定義が別途暗黙に存在する構成にはしない。

Contributionは明示した拡張点へ接続する。メニュー、Property Editor、検査器、Query Provider、生成工程等は、受け付ける入力、返す内容、複数提供時の選択・順序・合成を定義する。同名の登録や出力の衝突を、読み込み順による上書きで隠さない。案件側が明示的に置き換える場合は、置換対象と適用範囲を残す。

拡張点の数をCoreへ無制限に追加することも避ける。新しい分野のプラグインは既存の拡張契約から新しい拡張点を提供できる。利用者がそのProviderを選んだときに、配下の拡張を解釈・構成できるようにする。意味上の契約が互換であることと、実装のABIが互換であることは別に検証する。

## パッケージと版のモデル

| 概念 | 保持する内容 | 分ける理由 |
| --- | --- | --- |
| Package | namespace付きID、版、説明、供給元、利用条件、提供物一覧 | 利用者が選び、配布・更新する単位 |
| Contract | 意味、入出力、条件、版、適合試験 | 実装を変えても保つ約束 |
| Contribution | 段階、接続先、契約、実装・資産、依存 | 一つのPackageが複数の場所へ提供する部品 |
| Variant | Target、実行方式、対応能力、必要条件 | 同じ機能のWeb/Windows/Wasm等の違い |
| Artifact | 役割、形式、内容識別、取得先 | 一つのPackageと物理ファイルを分離する |
| Configuration | 型付きの設定と環境別の束縛。秘密は参照で扱う | 設計と実環境の値を混ぜない |
| Resolution | 要求、選択した実装、選択理由、依存の解決結果 | 再実行と変更の比較に使う |

Packageの版だけで全ての互換性を判断しない。意味契約、設定Schema、Source形式、UI拡張API、生成器、実行ABIには別の互換条件がある。Packageのminor更新でも、選択したTargetで必要な部品が欠けていれば利用できない。互換版の宣言と、実際に確認した組合せを対応付ける。

意味上の型は識別と意味の版を持ち、構造が同じという理由だけで同じ意味へ統合しない。構造上の互換は表現やABIの対応条件として使い、意味を変換する場合は対応規則を明示する。Lockには選択した契約とSchemaの識別を含め、StudioとGeneratorが互換でない定義を別々に使っている場合を検出する。

ContributionのScopeは、プラットフォーム、案件、Window、文書、アプリケーション、実行Context等の用途に応じて宣言する。例えば表示設定と実行中のSessionを同じグローバル状態へ置かず、複数案件や複数利用者の状態を混ぜない。最小のLanguageとSchemaのSeedを明示し、プラグインの宣言を読むために、その任意コードを先に実行しなければならない循環を避ける。

同じPackageの複数版はScopeと依存を分離できる場合に併存を認める。同じ文書の同じ意味要素を二つの互換でないSchemaで解釈するなど、分離できない場合は競合として扱う。全環境で一つの版しか使えない制約も、どの版でも無条件に同居できる制約も置かない。

## 管理方式を構成する役割

プラグイン管理は一つの万能Registryに全責務を集めない。検索するCatalog、取得したPackageを置くStore、案件の要求と解決結果、StudioのContribution構成、Buildの入力と成果物、実行時のProvider配置を分け、その対応を一貫して追跡する。これらを統括する管理UIと操作APIを用意する。

Catalogは公式、組織内、ローカル、案件同梱等を併用できる。Storeには取得したPackageと資産を内容識別で保存する。同じ版の内容が無通知に変わることを防ぎ、ネットワークへ接続しない構築でも固定した入力を利用できるようにする。Catalogに見つかること、端末へ取得したこと、案件で選んだこと、実際に使用したことを区別する。

依存の解決は案件の要求、Profile、Target、利用可能なCatalogと固定した版から決定論的に行う。結果は選択したProvider、Contribution、Variant、Artifact、設定の対応を含む。最新の互換版を選ぶ操作と、Lockから同じ構成を再現する操作を分ける。Buildの途中で、端末に偶然入っていた別の版へ切り替えない。

Providerは明示した選択とpinを優先し、指定がなければProfileの推奨を使う。複数の候補を一意に選べなければ、その理由と候補を返す。依存の探索順や取得順を選択理由にはしない。更新を要求したときだけ互換候補を再評価し、通常の再構築ではLockを使う。

依存には、意味上の参照、構築の順序、実行時の呼出し等の種類を持たせる。型の相互参照を、構築順序の循環と同じ理由で拒否しない。順序が必要な生成工程は実行可能な依存グラフにし、反復や相互初期化を許す場合は、その成立条件と終了条件を宣言する。

| 利用者が行うこと | 画面で説明する内容 |
| --- | --- |
| 探す | 機能、対象領域、媒体、Target、契約、利用条件、供給元、対応するStudioの版で検索する |
| 内容を調べる | Studioに追加するUI、設計できる要素、生成する機能、実行時の依存、設定例、Sample、既知の制約 |
| 案件へ加える | 標準Profileとの差分、依存の追加、必要な設定、選択できるProvider、対応しないTarget |
| 構成を比較する | 現在と候補の版、契約、生成工程、成果物、設定、移行、試験の差 |
| 更新する | 影響するSource・画面・Query・生成物、設定移行、再検証・再構築する範囲、戻せる範囲 |
| 無効化・削除する | 依存する機能、残るSource、代替Provider、失われる設計UI、保持するデータ |

管理画面の情報は同じ型付き操作からCLI/API/MCPにも提供する。表示名だけを使って対象を選ばせず、何をどの案件・Targetへ適用するかを確認できるようにする。通常の可逆な設定変更へ毎回多段階の承認を要求せず、具体的な変更と必要な影響だけを示す。

管理の操作契約は次の粒度を初期案とする。名称は説明用であり、現在のCLIやHTTP APIへそのまま追加済みという意味ではない。

| 操作 | 主な入力 | 返す内容と作用 |
| --- | --- | --- |
| Catalog検索 | 機能、契約、Target、供給元、利用条件、検索範囲 | 候補と対応条件。取得範囲と未確認を保持する |
| 選択理由の説明 | 案件、Profile、Target、要求 | 候補、選択理由、満たせない要求、競合の経路 |
| 変更案の作成 | 基準版、追加・更新・削除・選択の要求 | 変更前後の構成、取得、設定移行、Build・試験の影響。構成自体は変えない |
| 配布物の取得 | 変更案と固定したArtifact | 取得と内容の照合結果。取得だけでは有効化しない |
| 案件構成への適用 | 変更案、期待する基準版 | 新しい構成と解決結果。不一致時は部分適用しない |
| Studioへの構成 | 解決した版、Window・Workspace・文書等のScope | 各Contributionの利用状態と失敗。対象の編集中状態を保持する |
| 成果物の構築 | 固定した意味・構成・Target・構築入力 | 工程、成果物一式とSubjectの対応、試験・観測への参照 |
| 利用状態の照会 | Package、Contribution、Scope、Target、時点 | 選択、構築、配備、実利用の状態と根拠。古い観測を現在と断定しない |
| 切戻しの作成・適用 | 戻す構成と、Data・外部作用の状態 | 戻せる範囲、追加の移行・補償、適用した構成 |
| Storeからの削除 | 内容識別と利用参照 | 不要な取得物を除去する。案件Sourceや業務Dataは削除しない |

インストール済みという一つの表示で状態をまとめない。少なくとも取得済み、案件で選択済み、Studioへ構成済み、対象Targetの構築済み、配備済み、実行で利用中を説明する。開発環境で使えたという理由だけで、配布したアプリケーションでも同じ版が動いていると表示しない。

## 導入・更新・削除を一貫した変更にする

導入は必要なPackage・資産の取得と検査を済ませてから、案件の構成と解決結果を切り替える。取得途中の状態を有効な構成へ混ぜない。構成の基準版が他の編集で変わっていれば、差分を照合して適用する。未保存の設計や案件固有のCSSを、Pluginの更新で上書きしない。

更新では設計Schema、設定、生成コード、DB移行、利用画面への影響を区別する。Themeの値だけの変更は即時反映できても、意味定義やGeneratorの更新は再解析・再構築が必要になる。進行中の処理を新しい契約で読み替えず、旧版で終えるか、新版へ移すための対応を持つ。

切戻しはPackageの版を戻すことだけでは完了しない。DBや外部サービスへ適用済みの変更、保存データ、進行中の仕事を確認し、元の状態へ戻せる部分と、結果を打ち消す追加処理が必要な部分を区別する。設計UIからPluginを外しても、関連するSourceを削除しない。解釈できない定義を保持し、代替の導入や元へ戻す操作につなげる。

供給元と利用条件、内容識別、署名、必要な実行能力は別の情報として扱う。CSSだけのPackageへDBやファイルの実行能力を要求しない。任意コードが必要な拡張では、選んだHostやOSの境界で条件を満たす。宣言上の能力一覧を、実際の強制隔離の証明にはしない。

## 性能と故障時の振る舞い

起動時は必要な定義と索引を読み、重いEditorやProviderは利用時に起動する。案件で未選択の拡張が文字入力、参照検索、起動を比例して重くしないことを目標とする。Contributionごとの起動時間、CPU、メモリ、I/O、生成時間を測り、どの機能が遅延の原因かを管理画面から調べられるようにする。

一つの専用Viewの例外でStudio全体を失わないよう、表示の障害を領域ごとに扱う。外部実行の停止、Timeout、取消、部分出力を型付きの結果で返し、空の正常結果へ変えない。再起動できる拡張でも、編集中の内容や実行途中の作用を無条件に再送しない。

インクリメンタル処理は宣言した依存と実際の入力に基づいて設計する。同じ出力値が得られたという理由だけで、途中の変更がなかったとは推定しない。構成が変わったときに再解決する部分、再検査する部分、再生成・再構築する部分を分け、性能を上げるために意味の検査を無断で省略しない。

## 主要プラグインでこの構成を確かめる

| プラグイン | Studioへ組み込む機能 | 成果物へ組み込む機能 | 共通の定義 |
| --- | --- | --- | --- |
| 認証・Session | 方式選択、接続設定、ログイン画面、主体とRoleの対応、試験 | ログイン、Session、再認証、終了、API接続 | 認証契約、画面と処理の対応、対象環境の設定 |
| DB・Data Access | 表・項目・キー・関係、Query、結果確認、移行差分、性能表示 | 型付きアクセス、接続、Transaction、方言、Migration | データ・Query・更新単位・Providerの能力 |
| 組織・関係 | 組織図、配置表、所属、役職、時点、異動、責任の確認 | 時点別取得、担当候補、代理・承認への入力、履歴 | 人・組織・所属等の区別、関係と期間の規則 |
| テスト | 設計要素へのCase、試験データ、結果、差分、再現 | Target別Runner、Adapter、必要な観測点 | 対象、入力、独立Expected、環境、作用、評価基準 |

組織情報は通常のDataとして使えるようにし、組織プラグインを導入したという理由だけで全情報へACLや匿名化を追加しない。認証されたこと、組織上の関係があること、実操作の権限があることはそれぞれ別の意味として接続する。

試験用FixtureやStudioのEditorを、配布アプリケーションへ無条件に含めない。共通の定義から必要な部分を段階別に選ぶ。データを表示するUI、APIから呼ぶ操作、DBで実行する更新、試験で確認する結果が同じ意味要素へ対応することを検証する。

## 分野別ツールキットの探索を二つの利用先へ分ける（2026-11-14、候補評価）

標準的な業務アプリケーションの生産性に加え、特定分野の計算・表現を使いやすくすることも拡張方針の候補とする。ただし、**TEIで開発・生成するアプリケーションに組み込む機能**と、**TEI Studio自体で設計・分析・表示する機能**は同じPackageに収録できても、Contribution・依存・実行環境・受入を分ける。Studioだけで動く計算や描画を、生成Targetの実装済み機能とは呼ばない。専門家用ツールを作るためにStudioが必ずその分野の実行環境を内蔵する必要もない。

| 候補領域 | Studioでの用途 | 生成アプリケーションでの用途 | 先に確かめる意味・負例／既存Owner |
| --- | --- | --- | --- |
| 統計・科学計算（R/Mathematica等を参考にする） | 計算式、分布、推定法、誤差・可視化の選択と検算 | 選んだTargetへ純粋計算Operatorや利用するライブラリとのAdapterを生成 | 原実装の出典・許諾、算法/版、数値精度・丸め、欠測・種、独立Expected。同一数値でも単位/仮定が異なれば非同値。#2495/#2544/#2501 |
| WBS・PERT・スケジュール | 作業依存DAG、Calendar、制約、Critical Pathと遅延要因の編集・比較 | 工程計画・進捗/変更影響・期間計算・Gantt等の型付き表示 | Cycle、稼働日、複数開始条件、未確定所要時間、Resource制約を無視した最短日程を実受入にしない。#3791/#4133/#2507 |
| レポート・集計・SQL Window | Query、集計軸・粒度、期間窓、Chart/Tableの構成と試行 | DB方言別SQL/分析処理・帳票/Window Functionを生成 | ROWS/RANGEと順序、JOIN fanout、RLS/Limit、Stock/Flow、AVG再集計、NULL/partialを区別。#2593/#2387/#2586 |
| 熱力学・動的システム・数理論理 | 系・境界、変数、次元、拘束・保存則・解法を記述し実測と対照 | Solver/数値積分/制約検査のTarget実装または明示外部Provider呼出し | 温度点と温度差、保存則違反、単位不整合、発散/収束、境界・初期条件未設定を正常計算へ変えない。#2495/#2544/#3791 |

**共通の入口**は、標準Data/Function/Query/Relation/時系列・単位等の既存意味Contractへ、領域固有のOperator/描画/Targetを段階別Contributionとして接続すること。Expression表層（数式、Markdown、Graphviz、WBS等）の編集形式を保持しても、意味・入力型・演算の公理・Targetでの実精度は別に検証する。RやMathematicaのライブラリ・定義を参考にする場合、公開仕様/実行結果の比較と、コード/データ/教材の著作権・使用許諾を分離し、無許諾のソース移植を前提にしない。外部Rプロセスを全Targetに必須化せず、純粋Operator、Target用ライブラリ、必要時のみ明示Providerの三案を比較する。

**評価の入口は領域ごとに一件だけ**：公開可能な合成Fixtureと専門家が独立に固定する正例・反例で、(1) Core/標準Pluginで表現できる意味、(2) 領域固有の不足、(3) Studioで実選択・編集/Previewできた範囲、(4) 選択Targetで実生成/InvokeしたProvider・値・誤差、(5) 別Consumerの実受領、(6) 必要な許可/Source・使用条件と実行費用を別票に記録する。さらに、手書き実装と比較した設計・修正時間、生成物容量、実行時間、必要な手修正・検証工数を測定する。名称の人気、アルゴリズムの豊富さ、参考ImplementationのテストPASSだけで「キラーコンテンツ」や生産性改善を認定しない。

**最初の小さな圧力試験候補**は、WBS/PERTのDAGとCalendar・Critical Path、および期間Window集計とMeasureの再集計とする。Studioの既存図/表/Timeline、TEI Query、#2593の既存反例を使い、全方言・Resource leveling・複雑な科学Solverまで最初に実装しない。科学/統計、熱力学、バイオサイエンスは#3791/#2501へ候補と反例を供給し、明確な案件需要・独立Expected・適用Targetが得られた順に縦断実証する。各分野の探索は**P1以降の選択的な並行検討**であり、#4583の非Plugin Studio Stage1→Stage2と#2586の実Product ReadのP0を置き換えない。新Core型、Solver Host、万能可視化Engine、専用Registry/Runnerをここで採用しない。

## 参照する既存製品の考え方

[VS Code](https://code.visualstudio.com/api/get-started/extension-anatomy)は宣言するContributionと起動する実装を分ける。[Theia](https://theia-ide.org/docs/extensions/)は構築時に組み込む拡張と、実行時に追加する拡張等を分けている。[Backstage](https://backstage.io/docs/frontend-system/architecture/extensions/)は拡張の入出力と接続先を型付きで構成する。[Gradle](https://docs.gradle.org/current/userguide/plugin_basics.html)はプラグインから構築のTaskや設定を提供する。TEIはこれらを比較材料とし、設計の意味からStudio・Build・実行へ連続する契約を定める。各製品のAPIをそのままTEIの正本にはしない。

## PoCから理想形へ移す判断

既存の型へフィールドを足し続ける方法だけを選択肢にしない。必要な段階や依存を自然に表せない箇所は、理想形の契約へ置き換える。全面リプレースが単純で正確になる場合も比較する。継承するのは守るべき意味・振る舞い・検証例であり、現在のPackage配置やRegistryの実装そのものではない。

| 対象 | 理想形で必要なこと | 既存PoCとの比較で判断すること |
| --- | --- | --- |
| Plugin Definition | 段階別Contribution、契約、依存、Variant、資産を説明する | 現行形式の拡張で自然に表せるか、新しい形式へ移すか |
| 構成と管理 | Catalog、Store、要求、解決、Studio、Build、実配置をつなぐ | 現行Registryの再利用、Adapterでの移行、置換の費用と単純さ |
| Build | Plugin以外のアプリケーション、複数成果物、各Subjectとの対応を持つ | Plugin主語の現行BuildPlanを固定せず、中立な構築モデルへ移す |
| Studio | 宣言と型からの標準UI、目的別の専用UI、共通の編集と操作 | 固定登録を残す部分と、宣言から構成する部分 |
| 生成成果物 | 選んだ機能だけをTargetへ組み込み、Studioとの契約を保つ | 手作業の配線を生成へ置き換える範囲と既存コードの利用 |
| 試験 | 各段階とその接続を、独立した期待結果で判別する | 合成参照試験を残し、実Provider・実Targetの試験を追加する |

最初の実証は、DB、認証、組織、テストが一つの小さなアプリケーションを支える構成とする。Studioでの設定変更が、生成した画面・API・データ操作・試験へ届くことを確かめる。その後、ProviderとThemeをそれぞれ交換し、意味と入力・選択・保存の振る舞いを保てるかを比較する。

受入の反例には、Studioだけ新版・成果物は旧版、Bを選んだのにAを呼ぶ、UIで不可とした操作がAPIでは無検査、組織の所属変更で過去の結果まで書き変わる、異なるExpectedを実装に合わせて作り直す、途中更新で構成が混ざる、削除でSourceが失われる場合を含める。

### 実装計画と各段階の成果

| 段階 | 作るもの | 完了を判断する試験 |
| --- | --- | --- |
| 意味と拡張点の契約 | 段階別Contribution、型付き入出力、Scope、依存・版・Variantのモデル | データだけの拡張、複数段階の拡張、衝突、未対応Target、意味版の不整合を判別する |
| 管理の一巡 | ローカルCatalogとStore、要求とLock、変更案・適用、同じ操作のUI/CLI接続 | 導入、更新、途中失敗、同時変更、無効化、復旧で構成とSourceを保つ |
| DBの縦断実証 | Data/QueryのStudio UI、生成アクセス、標準画面とAPI、実Provider試験 | 一つの定義変更が表示・Query・更新へ届き、誤Providerやnullの誤変換を検出する |
| 認証・組織・テストの合成 | 設計UIと生成機能、状態・時点・対象への共通Binding | 旧Session、兼務、異動、別対象更新、UI/APIの不一致を独立Expectedで検出する |
| Targetと外観の交換 | Web/Desktop、Themeと部品、実行方式のVariant | 同じ仕事と編集状態を保つ。未対応の差は診断する |
| PoCの移行・置換 | 各旧経路の扱い、データとSourceの移行、不要な実装の整理 | 継承する既存Caseと新しい縦断試験を通し、恒久的な二重設定を残さない |

各段階の実装は理想形の契約を試すものであり、全ての機能を作り終えるまで一つも利用できない方式にはしない。一方、最初の短い経路で都合よく動くことを理由に、その経路の制約を恒久的な標準へ固定しない。

本書の到達点は、将来のプラグイン基盤を現行PoCより小さな能力へ閉じ込めず、何を統合し、何を分離し、どの具体例で設計を判定するかを定めることである。管理方式と代表的な縦断実証を先に固め、個別プラグインの実装へ展開する。
