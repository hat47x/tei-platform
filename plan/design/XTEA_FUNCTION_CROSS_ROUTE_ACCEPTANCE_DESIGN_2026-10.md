## 1. 解消する問題

X-TEA Driverの基本形は、画面からクライアント側の処理を起動し、DBをサーバー側に置く構成である。XF000も画面からScriptバッチを起動する機能であり、UIなしの常駐Workerや時刻起動の証拠ではない。TEIで画面に依存しない起動を実現することは追加の実現要求として扱う。旧SQL発行APIやSessionを、そのまま業務端末へ公開する設計にはしない。

CLI、Web、Desktopは業務操作の入口である。処理の配置は、同一プロセス、端末内の別プロセス、遠隔の提供元、複数拠点での分担から独立に選ぶ。TEI専用の常駐Hostを一律に要求しない。各環境への埋込みでも同じ業務契約と権限境界を保つ。

この分離によって、画面を閉じた後に遠隔処理を照会することや、別の入口から同じ要求を復旧することが可能になる。その成立は、入口の数ではなく、主体・要求・確定記録の連続性で観測する。追加の仕組みが有効でなければ、対応できた配置の参照実装に範囲を戻す。

## 3. 接続時に決める境界

### 3.1 主体と現在の権限

各入口は認証済みの外部主体を、発行元を含む信頼済みの対応付けによって業務主体へ解決する。`Subject`、メールアドレス、表示名、操作IDの一致だけで同じ主体と判定しない。同じ利用者が異なる認証方式を使う場合も、同じ業務主体へ解決されたことと現在の権限を個別に確認する。Tenantの所属や対象の範囲は、ブラウザやCLIが送った値を権限の根拠にしない。

操作を起動できる許可と、具体的な親・明細を読み書きできる許可は適用対象が異なる。`execute / Pattern ID`のGrantを`write / record ID`へ書き換えて転用しない。信頼された対応付けと既存の認可を使い、保存先で必要な範囲・認可版を確定時まで検査する。主体リンク変更、所属変更、失効、認可正本の障害はそれぞれ確認する。読取り・結果照会・帳票取得の権限も、更新権限から暗黙に導かない。

業務利用の認証接続にはSAMLを必須とする。認証方式の実装はプラグインや対象環境の認証基盤へ接続し、Coreへ固定しない。SUIのBFF・認証ブローカー構成は参考にできるが、Mock OAuth/JWTの試験と設定スクリプトの正常終了は実SAML往復の証拠ではない。SAMLの検証済み主体から業務主体への対応、署名・証明書・メタデータ、Entity ID/ACS、Audience/Recipient、有効期限、InResponseTo、再利用拒否を実IdPで確認する。CLI/Desktopへの認証復帰、セッション失効、CSRF等は各入口の実際の接続で検証する。SAML応答やブラウザCookieをCLI/Desktopの入力へコピーしない。

### 3.2 同一要求と新規実行

同じ引数での起動だけでは、再送・再開・新規実行を識別できない。新規の業務実行には新しい識別子を与え、同じ要求の照会・再送では既存の識別子と要求内容を保つ。実行試行の識別子を業務要求の識別子の代わりにしない。全件の二重起動を業務キーで禁じる場合は、案件の業務制約として別に宣言する。

要求の同一性には主体、Application/Capability、操作・対象範囲、対象版、入力内容を結び付ける。入口固有のHTTP形式や画面値をそのまま共通指紋にせず、同じ業務要求への正規化と型の照合を先に行う。既存`effectcommit.Request`へ渡すときはその指紋規則を使い、第二の冪等台帳を作らない。

現在状態が`submitted`であっても、自分の要求が確定した場合と他の要求が先に確定した場合は区別できない。更新データと同時に保存した要求に結び付く確定記録で結果を照合する。`not-recorded`は、その保存先で記録が見つからないことだけを表す。実行中の別処理や外部効果が存在しない証拠にしない。

### 3.3 取消要求と処理の寿命

呼出元の通信終了、取消要求の受付、実行停止、DB未確定、確定済み効果の補償を区別する。確認を断る操作と障害による停止も同じ結果にしない。CLI終了、ページ離脱、ウィンドウ終了の後に処理を継続するかは、操作の寿命と配置ごとに明示する。

`reference-capability-mutation-protocol`は確定意図の記録後に呼出元の取消しを切り離す。一方、`effectcommit`は渡されたContextでDB処理を行い、commitエラーを結果不明として返す。両者を合成する際は、誰がどのContextと期限で確定・照合を完遂するかを決める。通信の取消しを切り離しても権限は延長されず、保存先での現在の認可版照合を省略しない。

一括処理の取消しは、着手前・実行中・確定済みの項目に対して何を止めたかを記録する。部分確定が許容される業務でだけチャンク化する。XF310等の親子全体で一回の確定を必要とする操作を、実装都合で分割しない。

### 3.4 選択対象と帳票

対象集合は、明示選択、検索条件に一致する全件、固定した時点の集合を区別する。選択後にデータや権限が変わった場合、再検索で対象を黙って増減させず、確定前に再評価して競合・再確認・除外の規則に従う。対象や進捗に画面の行位置を使わない。

帳票では、対象範囲と取得時点、入力・テンプレート・Renderer・フォント等の必要な版、成果物の識別子とdigestを追跡する。digestは内容の同一性の手掛かりであり、業務上の正しさや開示権限ではない。保存済み成果物の再取得と、最新データからの再生成を分ける。サーバーの一時パスを利用者端末のパスとして渡さない。印刷先の受付も物理印刷の完了と区別する。

## 4. 最初の一連経路と失敗注入

同じ受理済みApplicationとScenario、規則版、業務入力、対象範囲、権限条件を基準に、検索→選択→親子編集→確定→別接続で再読取り→帳票生成・取得を比較する。テスト期待値は既存#1180のScenario正本へ戻し、本書の表を第二の実行DSLや生成物の手修正規則にしない。

| ID | 工程と共通する確認 | 失敗注入と合否 |
| --- | --- | --- |
| XR-01 | 正常経路。検索、親子の入力、検査、確定、独立した再読取り、帳票を同じ業務対象へ結ぶ | CLI/Web/Desktopを個別に実行し、同じ業務結果・保存値・帳票内容を確認する。入口固有の認証・操作・表示は別に確認する |
| XR-02 | 検索・親子読取り。行・項目の権限を検索・件数制限より先に適用 | 検索後に閲覧権限を失効。詳細・明細を返さない。別の親の明細混入も拒否する |
| XR-03 | 親子編集。対象ごとの版と削除意図を保持 | 明細1件を別接続で変更。全体確定が必要な操作は親と他明細も残さず競合にする。対象版を表せない提供元は#2096の能力不足として明示する |
| XR-04 | 更新前に主体リンクと具体的対象の権限を再確認 | 認可後・確定前にリンクまたは更新許可を失効。更新と確定記録を残さない。確定と失効が競合した場合は保存先で直列化された順序と結果を観測する |
| XR-05 | 同一要求の確定記録と再認可 | 確定後・応答前に通信を遮断。再接続または別入口から同じID・同じ要求を照会し、効果を増やさず回収する。同一ID・異内容は拒否し、他要求の先行確定を自分の成功にしない |
| XR-06 | CommandとObservationを別の結果として保持 | 確定後の読取りだけを失敗させる。更新を未実行へ戻さず、再読取りへ進む。復旧の主経路ではDBを初期化したりdraftへ戻したりしない |
| XR-07 | 取消しと確定境界 | 確定前の停止、確定意図の記録後、DB確定後を別々に注入。止めた範囲、確定済み範囲、不明、補償の要否を混同しない |
| XR-08 | 帳票生成と成果物取得を別々に認可 | 生成後に取得権限を失効。取得を拒否し、生成済み事実は維持する。親子の版混在や最新再生成を保存済み再取得として扱わない |
| XR-09 | 三入口で正規に認証した主体の対応付け | 異なる発行元の同名Subject、リンク変更、アカウント停止、結果照会権限失効を注入。操作IDを知っているだけでは結果を開示しない |

各入口の正常比較には分離した同等の試験データを使う。別入口からの復旧を確かめるXR-05/09では、同じ実行と保存済みの状態を引き継ぐ。独立した負例の準備で行った初期化と、復旧途中の初期化を区別して記録する。業務結果、実行エラー、確定状態、観測状態、公開してよい診断を残し、単一の成功フラグにまとめない。これらの軸の製品上の表現は既存契約との照合後に決め、新しいCore enumを本書だけで追加しない。

## 6. 採用・実装に進む条件

要求と既存ADRに反しない範囲で、最小の接続案を隔離ブランチで比較する。主体・所属の正本、操作許可と対象許可の対応、取消し後の調停責任、帳票の時点・保存期間・取得権限は、実際の案件と提供元に結び付けて判断する。Fixtureでこれらを決定済みとは扱わない。

XR-01からXR-09、実SAML、実権限正本、三入口の操作、PDF/印刷は本書ではNOT RUNである。過去のDB境界試験や固定GateのPASSを転用しない。採用済み意味の変更や権限付与は人の判断に戻し、実装・実環境確認の状態は`docs/status.md`と対象版付きの証拠で別に管理する。
