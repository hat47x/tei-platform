# TEIの多言語対応――意味モデルと表示資源を分離する設計

- **状態**：評価待ち（2026-10-12）。方式の提案と受入条件であり、実装・採用・全対象環境への対応を主張しない。
- **担当課題**：[多言語対応の意味契約 #1396](https://github.com/hat47x/tei-platform/issues/1396)
- **対象**：業務・データ・機能モデルの名称、画面、帳票、メッセージ、業務データの多言語表現、生成時の資源選択、翻訳支援。
- **対象外**：すべての文字列の即時翻訳、多言語入力の機械翻訳を伴う本番運用、すべての実行先への国際化ライブラリの同梱、プラグイン構成や意味モデルの新しい正本の作成。

本書は、多言語対応のためにTEIの設計情報を複製せず、同じ意味を日本語、英語などの異なる言語で扱えるようにするための設計候補をまとめる。現在の構成は[全体構成](../../docs/architecture.md)、現状は[実装状況](../../docs/status.md)を参照する。

## 1. どの問題を解くか

「受注確定」のボタンを英語で表示するために、受注処理そのものを英語の識別子で作り直す必要はない。逆に、画面の文字列を翻訳しただけで、英語版の帳票、数値や日時の書式、業務用語、原文変更後の再確認まで解決できたと扱ってもならない。

TEIでは、設計者が自然な日本語で定義した業務・データ・機能の意味を維持しながら、それらの表示や説明を言語ごとに切り替える。言語処理は標準プラグインの候補とし、固定された意味と資源から実行先に必要なものだけを生成する。

既存の[三視点の参照契約](CROSS_VIEW_TYPED_REFERENCE_CONTRACT_2026-10.md)は、論理識別子と表示名を分け、表示名の変更と意味上の改名を区別している。この前提を利用する。[案件構成設計](PROJECT_PLUGIN_COMPOSITION_DESIGN.md)、[配備構成設計](RUNTIME_TARGET_BINARY_COMPOSITION_DESIGN.md)、[ADR-0033](../adr/0033-core-and-plugin-subprojects.md)の依存・構築境界を増設しない。

## 2. 先に決める責務

| 対象 | 責務 | 正本・既存機構との関係 |
| --- | --- | --- |
| 業務・データ・機能の意味 | 論理識別子、型、規則、関連 | 既存の意味の正本。翻訳のために複製しない |
| 表示資源 | 名前、説明、通知、入力案内、帳票見出し | 論理参照に結び付く、独立した改訂・所有単位 |
| 地域別書式 | 数値、日時、通貨、並び順、複数形など | Unicode CLDR等の版を固定し、実装元を選択する |
| 翻訳支援 | 文脈提示、候補、確認、原文変更の検出 | 提案と受理を分ける。AIの出力で正本を直接変更しない |
| 資源の解決・配布 | 利用プラグイン、対象言語、利用箇所、実行先に応じた抽出 | 既存のプラグイン選択・構築・成果物の固定情報を使う |
| 業務データの多言語表現 | 商品説明、契約本文など実体として保存される文章 | データモデルの要件。画面資源の翻訳辞書へ移管しない |

同じ文字列「確定」が、受注の成立と入力途中の保存で同じ意味だとは限らない。画面で一致する語から一つの共通概念を推測しない。用語共通化は、明示的な業務上の意味と利用側の参照によって行う。

## 3. 言語と地域は別々に扱う

言語資源の識別にはBCP 47言語タグ（例：ja-JP、en-US、zh-Hant-TW）を使う。正規化規則とUnicode CLDRの版を明示する。言語を、国籍、タイムゾーン、通貨、法域と同じ設定項目にまとめない。

- **表示言語**：画面や説明に使う文章の言語。利用者の明示指定を優先する。
- **地域別書式**：日付、数字、通貨などの表し方。表示言語とは独立して指定できる。
- **タイムゾーン**：利用者または業務で選択した時刻の解釈・表示条件。保存時刻そのものとは別。
- **文章方向**：左書き・右書き、文字列の埋込み境界。言語タグだけを根拠に一律推定しない。
- **業務上の法域**：契約・税制などの適用条件。言語や端末所在地から暗黙に決めない。
- **データの原文言語**：各業務データが実際に記述された言語。画面言語とは別。

利用者・組織・アプリケーション・実行環境のどこが設定の正本を所有するかは、既存の設定／受理／権限の境界で扱う。ここで新しい優先順位管理機構を作らない。表示処理へ渡す解決済みの設定は、入力の出所と適用範囲を追跡できることを要件とする。

## 4. 表示資源の最小契約（案）

表示資源の識別子は単なる画面上の文字列でなく、所有プラグイン、意味上の参照先、表示箇所の役割で構成する。意味モデル内の表示名を削除することは初期条件としない。既存表示名を原文として参照するか、資源を別管理するかは、同じ値の第二の正本を生まない形で実証する。

次は検証のための概念例であり、新しい正式なYAML形式やプラグイン定義を採用したものではない。

~~~yaml
# 設計例：実際のTEIの定義形式ではない
owner: order-entry
subject:
  scope: sales
  kind: function
  id: submit-order
field: action-label
source:
  language: ja-JP
  text: 受注を確定
  revision: source-12
translations:
  en-US:
    text: Confirm order
    basedOn: source-12
    review: confirmed
  zh-Hant:
    text: 確認訂單
    basedOn: source-11
    review: needs-review
~~~~

参照先の主体は既存の識別子と名前空間を用いる。表示資源だけのメッセージには、意味上の対象との関連と資源内で安定した識別子を与える。単に表示語から識別子を生成したり、翻訳文そのものを識別子にしたりしない。

最小契約で確認する情報は次の通り。

1. 所有者と適用範囲：どの論理プラグインが資源を提供し、どの利用側に公開するか。
2. 安定した資源参照：既存の意味上の参照、表示箇所、または固有メッセージ識別子。
3. 原文の言語・版・翻訳対象可否：翻訳元が変わったことを検出できること。
4. 翻訳先の言語、表現、参照した原文の版、確認状態。
5. 動的メッセージなら名前付き引数と型、利用するMessageFormat機能の範囲。
6. 必要な場合だけ用途、原文の出所、用語参照、承認権限、配布上の制約。

翻訳の版を原文の版と混同しない。業務意味の版が変わらずに表示説明だけが改訂される場合もある。また原文の変更がなくても、新しい法令に合わせて翻訳文だけを訂正する場合がある。

## 5. 資源の所有、共有、上書き、衝突

資源は原則として各論理プラグインが所有する。共通用語は共通の意味を持つ参照資源として公開し、案件固有の文脈に応じて利用する。表記が似ているだけの語を自動共有しない。

- 同じ所有者・適用範囲・資源識別子・言語に、独立した正本が二つある場合は衝突として拒否する。
- 案件ごとの表現変更を許す場合は、対象と上書き元の識別子を明示し、プラグイン間の依存と選択結果に固定する。読込み順や偶然のファイル配置を優先順位に使わない。
- 案件独自の用語を標準用語へ統合する際は、実際の業務意味、既存の利用側、翻訳後の文法上の適合性を検証する。
- 資源がプラグインに所属しても、ランタイムに翻訳管理機構を同梱する義務はない。

既存の[機能契約 #951](https://github.com/hat47x/tei-platform/issues/951)、[構築・成果物 #943](https://github.com/hat47x/tei-platform/issues/943)の管理境界を利用する。専用の並行する機能解決器や依存固定ファイルを追加しない。

## 6. 言語資源の選択と代替

資源ごとに、どの言語版を使用したかを決定論的に示す。例えば要求がen-GBで、資源がenとja-JPにある場合、適用を明示した代替候補がenならそれを利用できる。一方、zh-Hantをzh-Hansへ勝手に置き換えるなど、意味や表記が大きく変わる代替を暗黙に行わない。

1. まず要求された言語に合う資源を探す。
2. 明示された代替方針の範囲で、許可されている言語版のみを試す。親言語候補を自動的に採用するかは案件の方針で選び、採用時は経路を記録する。
3. 原文へ戻すことが許可されていれば、原文を最後の候補にする。
4. 許容される資源がなければ、資源識別子・要求言語・欠落理由を診断として返す。

規約、法的同意文、危険な操作の警告などには、未承認の翻訳、原文への自動切替、代替言語による表示を禁止できる条件を設ける。禁止時に空文字や誤った別言語を表示して成功扱いしない。代替の有無と拒否理由は利用側へ構造化して返す。

翻訳文を利用者に提示したことが証拠となる場合、言語・資源版・書式データ版・必要な引数・提示時点の関係を追跡できることを要求する。機密情報や個人情報を翻訳ログへ無条件に複製しない。

## 7. メッセージ形式と実装の選択

動的メッセージの共通仕様にはUnicode MessageFormat 2（Unicode技術標準第35号第9部）を採用候補とする。複数形、数値、日付などは文字列の連結によって組み立てず、書式規則と翻訳文を使う。英語・日本語・アラビア語などを混在させる場合の文章方向も評価する。

ただし、仕様に準拠したすべての機能がGo、Web、組み込み機器で同じように利用できるとは限らない。Goの既存国際化ライブラリをMessageFormat 2の完全実装とみなさない。各実装元について、対応する仕様版、関数と選択処理、入力型、例外、CLDRの版を明示し、共通試験で一致を確認する。

実装の候補にはGoの言語処理ライブラリ、Webの国際化機能、軽量配布向けのICU4Xなどがある。ただしICU4Xを採用するためだけにGo中心の実装をRustへ移管するものではない。TEIの共通仕様は個別の実装言語・ライブラリに依存させない。

最低限、平文メッセージ、変数展開、複数形、日付・数値、右書き言語、名前付き引数の不足・型不一致、未対応関数を検証する。通常の画面にHTMLを埋め込む場合、メッセージ資源を安全なHTMLとみなさず、表示側で適切にエスケープする。

## 8. ビルド時の抽出と実行時の境界

既存の実行先別ビルド方式に従い、利用側の参照、固定されたプラグイン、対象言語、許可された代替経路、書式処理で必要な範囲を導出する。構築入力と生成物へ追跡情報を残す。

| 実行先 | 第一候補 | 注意 |
| --- | --- | --- |
| Web | 必要な言語資源の分割と遅延読込み | 言語変更中の表示整合、初期表示、キャッシュの版 |
| デスクトップ | 指定言語の同梱または更新資源の分離 | WebViewとGo間で同じ文言を保証する対象を限定 |
| サーバー | 呼出しごとの言語設定と固定された資源版 | 利用者間の設定混在を避ける |
| WASM・組み込み機器 | 使用資源の事前変換と固定、必要な書式データのみ同梱 | 未対応機能をビルド時に検出、必要ならビルドを停止 |

平文にまで実行時の解析器を強制しない。一方、引数を含むメッセージを単なる定数に置き換えて誤った表示を生成しない。外部から追加の言語資源を取得する構成では、署名、版、適用権限など既存の成果物受理条件を使う。

生成の途中で、資源の所有者、参照先の意味、変数型、必要な言語、MessageFormat機能、地域データ版を確定させ、利用先に応じた実装を選択する。表示機構が満たせない契約は明示的な不適合とする。

## 9. 翻訳と確認の作業

設計情報や用語の意味、利用画面の目的を参照して生成AIが翻訳候補を作成できる。ただし候補の提示と人間による確認は分ける。翻訳対象ではない値、識別子、機密情報を無条件に外部の翻訳サービスへ送らない。

初期状態は「原文」「翻訳候補」「確認済み」「要再確認」「利用不可」のように区別する。これらは言語資源の確認状態を示すもので、業務上の事実認定や実行権限そのものを表すものではない。人間の確認済み翻訳でも、後から原文が改訂されれば再確認が必要になる。

特に次の変更で影響を確認する。

- 原文だけが改訂された場合：参照していた原文の版に基づき、既存訳を再確認対象へ移す。
- 用語定義や関連する意味が変わった場合：依存関係が判明する範囲の翻訳に影響候補を示す。
- 翻訳文だけを改訂した場合：意味上の識別子を改名せず、翻訳の版と確認状態を更新する。
- AIが複数案を提案した場合：自動的に採用せず、確認するための候補として保持する。

既存の受理境界を置き換える承認機構を増やさない。説明の出所、参照版、確認者、用途を必要な範囲で残す。

## 10. 優先する受入試験

| 事例 | 期待する判定 |
| --- | --- |
| 同じ受注モデルを日本語と英語で表示 | 論理識別子と業務規則は不変 |
| 表示名だけを変更 | 表示依存に限って影響を追跡、識別子は不変 |
| 同じ「確定」という語が二つの操作にある | 語の一致から意味を同一視しない |
| 参照変数に不足、余剰、型の不一致がある | 構築時または表示時に不適合を通知 |
| 同一範囲・言語の資源を二つの提供元が供給 | 明示的な上書き契約がなければ衝突 |
| 英語訳が未確認で、重要な同意文に利用 | 未確認の版を表示しない |
| 原文の版が改訂された | 翻訳を要再確認として扱う |
| 言語と通貨・タイムゾーンが異なる | 数値・時刻の意味を保存し、指定書式で表示 |
| 右書きの文章と英数字を混在させる | 語順や表示境界が壊れない |
| 低資源の実行先に日本語のみ配布 | 他言語資源と未使用の解析器を必要以上に含めない |
| ビルド対象で使えない書式関数がある | 利用不能として停止し、静かに別処理へ置き換えない |
| 同じ仕様をGoとWebで処理 | 宣言した対応範囲で結果と失敗の分類が一致 |
| 法的な業務データが複数言語で存在 | 言語別の正本・版と画面資源を混同しない |

最初の縦断事例は既存の受注アプリケーションとする。業務・データ・機能の参照から日本語と英語の表示名を選び、数量付きのメッセージ、重要な警告、帳票の見出しを生成する。まず読み取り専用の参照例と負例を用意し、実際に不足する契約だけを実装へ昇格する。

## 11. 段階的な進め方

**E0：契約と検査表**　本書の区分に沿って、既存の意味参照、表示名、プラグイン資源、実行先の関係を整理する。新しい構文や権限はまだ導入しない。

**E1：単一アプリケーションの参照例**　日本語原文と英語訳を資源として持ち、読取り専用で表示候補を得る。重複、原文変更、未承認、欠落の診断を用意する。

**E2：二つの実装で確認**　WebとGoの実装を比較し、MessageFormatの対応部分について共通の正常・異常試験を実行する。利用可能な具体的なライブラリをここで選定する。

**E3：プラグインと配布成果物**　利用側の参照から必要な言語資源を抽出し、同じ意味からWeb向けの言語切替構成と軽量配布向けの日本語固定構成を作る。既存の構築・成果物の固定情報へ接続する。

**E4：翻訳支援と編集画面**　意味や用語を参照した翻訳案、確認、原文更新の影響を統合モデラーで扱う。AI提案は人間の確認を代替しない。

本書だけでE1～E4が成立したとは扱わない。関連する試験が動く版・実行手順・検証根拠を担当課題に記録する。全体健全性試験を一律の統合条件にせず、変更した範囲に必要な検証を選ぶ。

## 12. 標準仕様と参考資料

- [Unicode技術標準第35号第9部：MessageFormat](https://www.unicode.org/reports/tr35/tr35-messageFormat.html)：メッセージの構文、データモデル、処理、準拠条件。
- [Unicode CLDR／LDML](https://www.unicode.org/reports/tr35/tr35.html)：言語と地域に応じた書式など。
- [RFC 5646](https://www.rfc-editor.org/rfc/rfc5646)：言語タグ。[RFC 4647](https://www.rfc-editor.org/rfc/rfc4647)：言語の照合と選択。
- [W3C ITS 2.0](https://www.w3.org/TR/its20/)：翻訳対象、用語、説明、品質情報など。
- [OASIS XLIFF 2.1](https://docs.oasis-open.org/xliff/xliff-core/v2.1/os/xliff-core-v2.1-os.html)：翻訳支援ツールとの交換形式。
- [ICU4X](https://icu4x.unicode.org/)：資源制約のある実行先向けの地域別書式処理の参考。

標準仕様の採用判断と特定ライブラリへの依存追加は別の判断とする。実装段階では、採用する規格版とライブラリの機能・データ版を固定し、試験結果を残す。
