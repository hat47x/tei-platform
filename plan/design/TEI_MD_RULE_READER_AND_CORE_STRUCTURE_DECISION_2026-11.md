# `*.tei.md`の規則を製品で読む最初の経路と、中核構造の判断

- **状態**：提案。「実装したこと」はmainへ統合済みのGoコード（`091cb726d`）と、このPRの試験で確かめた。「判断」は採用前の設計案で、ADRではない。
- **関連**：[#4359](https://github.com/hat47x/tei-platform/issues/4359)（DSL構文）、[#2621](https://github.com/hat47x/tei-platform/issues/2621)（Markdown Authoring）、[#1018](https://github.com/hat47x/tei-platform/issues/1018)・[#988](https://github.com/hat47x/tei-platform/issues/988)（Language選択）、[#2619](https://github.com/hat47x/tei-platform/issues/2619)・[#2620](https://github.com/hat47x/tei-platform/issues/2620)（標準データ構造とRole）、[#4544](https://github.com/hat47x/tei-platform/issues/4544)（Generator自己記述）。
- **位置付け**：[自己記述設計](ROLE_BOOTSTRAP_AND_SELF_DESCRIPTION_2026-11.md)の§46.2と§47.5が「製品にLanguageの選択経路がない」と記した断点を、規則一件で実際に接続した。その実装でなぜその形を選んだか、同じ構造をどこまで広げられるかを記録する。新しい横断Issueや管理体系は作らない。

## 1. 結論

設計文書に書いた規則を、製品の`Workspace.Load`が読めるようにした。対象は数量の検査規則で、次の経路が一続きで動く。

```text
*.tei.mdの取得 → 読む領域の識別 → 解析 → 既存のsemantic.Validation → 既存Validator → Source Index → tei validateの診断
```

加えて、規則一件の型付きの変更を原文の一つのバイト範囲へ反映し、保存した文書を読み直すところまで確かめた。

この実装を通して、次の四つを判断した。理由と代替案は各節に書く。

| 判断 | 採った案 | 主な理由 |
| --- | --- | --- |
| どの言語で読むか | Workspaceのmanifestが言語の契約と版を選び、実行中の`tei`が実装を持つ。両者がちょうど一つに定まったときだけ読む | 拡張子や登録順で読み方が決まると、実装を足しただけで既存文書の意味が変わる |
| 文書のどこを読むか | `tei`と書いたコードフェンスだけ。書き損じに近い形は読み飛ばさず誤りにする | 見出しや通常の表を意味にすると、文章の手直しが定義の変更になる |
| 位置をどう得るか | 値と位置を一度の解析から得る。Source IndexはLoadが記録した範囲を使い、解析し直さない | 二度目の解析は別の読み方になり得る。`*.tei.md`は既存の文法では解析し直せない |
| 意味をどこへ置くか | 新しい意味モデルを作らず、既存のValidationへ変換する。文書は全部読めるか、何も寄与しないかのどちらかにする | 半分だけ読めた文書がもっともらしい意味を出すことを防ぐ |

中核構造については「標準データ構造・Role・Operator」の三部品を採る。ただしRoleの範囲、Operatorの範囲、自己記述の読み順の三点を改める（§7）。

## 2. 利用者から見た動き

### 書くもの

Workspaceのmanifestへ、文書を書く言語を一行足す。

```yaml
workspace: tei_md_rule
formatVersion: 1
sources:
  - semantic
languages:
  - tei.rule-authoring/v0
```

規則は`semantic/`の下の`*.tei.md`へ、説明と一緒に書く。

````markdown
# 受注明細の検査規則

## 数量は正の数にする

数量が0や負の数の明細は、出荷も請求もできません。入力の時点で止めます。

```tei
namespace sales

rule sales.order_line.quantity_positive:
  sales.order_line.quantity is positive
```

## 書き方の例

```text
rule sales.order_line.unit_price_positive:
  sales.order_line.unit_price is positive
```
````

定義として読まれるのは`tei`のフェンスだけである。`text`のフェンスに書いた例、見出し、本文は文書に残るが、定義にはならない。規則の書き方は[#4405](https://github.com/hat47x/tei-platform/pull/4405)でmainへ入った`rule`構文そのもので、文法は足していない。

### 起こること

`tei validate -workspace <dir>`を実行すると、規則は既存の`validation`宣言と同じ`semantic.Validation`になり、既存のValidatorが検査する。試験用の文書で存在しない属性を書いた場合の出力は次のとおりである。

```text
semantic/sales/order-line-rules.tei.md:13:6	error	UNKNOWN_SEMANTIC_VALIDATION_ATTRIBUTE	semantic validation sales.order_line.quantity_positive refers to unknown semantic attribute sales.order_line.quantty
```

行と列は文書全体での位置である。フェンスの中だけで数えた位置ではない。

| 書き方 | 結果 |
| --- | --- |
| manifestに`languages:`がないまま`*.tei.md`を置く | `TEI_MD_PARSER_UNBOUND`で止まる。従来と同じ |
| `tei.rule-authoring/v1`のように、この`tei`が持たない版を選ぶ | `TEI_LANGUAGE_UNAVAILABLE`で止まり、使える版を示す |
| フェンスを`TEI`や`tei-definition`と書く | 誤りにする。「読まれない定義」を残さない |
| `tei`のフェンスを4桁以上字下げする、引用（`>`）の中へ置く、閉じ忘れる | 誤りにする |
| `tei`のフェンスが一つもない`*.tei.md` | 誤りにする。何も定義しない文書を成功にしない |
| 同じ規則IDを、別の領域、別の文書、既存の`.tei`にも書く | 後から読んだ側の位置で誤りにし、先の宣言の場所を示す。読んだ順では選ばない |
| 属性を`quantity`のように修飾なしで書く | 誤りにする。近い名前や「文書内で唯一のData」からは補わない |

### 確かめ方

`Load`の結果は、どの文書をどの実装が読んだかを`AuthoringSources`に持つ。文書ごとに、読んだ領域の数と定義の数が入る。`ManagedFile.ReadByLoader`は`true`になり、「読まれないファイル」の警告は出ない。

## 3. 判断：言語の選択を二つに分ける

読み方を決める情報は二つある。文書が**どの言語の契約で書かれたか**と、その契約を**どの実装が読むか**である。前者はWorkspaceが決めることで、Gitで差分を確認できる場所に書く。後者は実行する`tei`の構成が決める。

今回はmanifestの`languages:`が前者を持ち、`tei`に組み込んだ実装の一覧が後者を持つ。選んだ言語ごとに実装がちょうど一つあり、文書を読むと主張する実装もちょうど一つのときだけ読む。足りなければ読まずに止まり、複数あれば選ばずに止まる。

| 案 | 利点 | 採らなかった理由 |
| --- | --- | --- |
| 拡張子`.tei.md`だけで読む | 設定が要らない | 版を表せない。実装を足すと既存文書の読み方が変わり得る |
| 文書の先頭で言語と版を宣言する | 文書だけで読み方が分かる | 文書ごとに同じ行を書くことになる。今は一つのWorkspaceで版を混在させる必要がない |
| manifestで選ぶ（採用） | 選択が一か所で、差分に残る。既存の`formatVersion`と同じ考え方 | — |
| Pluginの選択とLockから解決する | 外部のLanguage Pluginまで同じ経路になる | 組込みの実装一つのために、未接続のResolverを製品Loaderへつなぐことになる。外部実装が必要になった時点で、この経路を通す |

**見直す条件**：一つのWorkspaceで複数の版を同時に使う移行が必要になったら、文書ごとの宣言を足し、manifestとの一致を検査する。外部のLanguage Pluginを読むときは、組込みの一覧を広げず、既存のPlugin選択とLock（[#951](https://github.com/hat47x/tei-platform/issues/951)）から実装を受け取る。

**今回持たないもの**：契約と実装の内容識別値（fingerprint）は照合していない。組込みの実装は`tei`の実行ファイルそのものなので、照合する相手がまだない。実装のIDは読取りの記録に残る。

## 4. 判断：読む領域は`tei`フェンスだけにする

`*.tei.md`は普通のMarkdownとして読める文書である。その中で定義として読むのは、情報文字列がちょうど`tei`のコードフェンスに限る。フェンスの始まりと終わりはCommonMarkの条件で判定する。3個以上のバッククォートかチルダ、3桁までの字下げ、同じ文字で同じ長さ以上の閉じ、である。ほかのフェンスの中と、複数行のHTMLコメントの中にあるフェンスは読まない。記法の例を文書へ載せるときは、`text`など別の名前のフェンスを使う。

[Markdown-firstの設計](SEMANTIC_STRUCTURE_MAPPING_AND_DECLARATIVE_SYNTAX_VIEW_2026-11.md)は、見出し、入れ子のリスト、表も意味に使う方向を挙げている。今回それを採らなかった理由は、暗黙の構造ほど誤読に気づきにくいからである。見出しを一段動かす、表へ説明の列を足す、といった文章の手直しが、診断のないまま定義を変える。印を付けた領域だけを読む形なら、定義を変える編集は必ず領域の中で起きる。

一方で、読み飛ばしは別の危険を生む。`TEI`と大文字で書いたフェンスを「定義ではない」と扱えば、書いたつもりの規則が効かないまま文書は成功する。そこで、`tei`に近い名前のフェンス、字下げや引用の中の`tei`フェンス、閉じていない`tei`フェンス、後の記法の印に見える一行コメント（`<!-- tei: … -->`）は、すべて位置つきの誤りにする。

**見直す条件**：表や矢印で定義を書く必要が具体例で示されたら、領域の種類を足す。そのときも「印のある領域だけを読む」と「近い書き損じは誤りにする」は変えない。見出しへ意味を持たせる場合は、見出しに付けた明示の印に限る。

## 5. 判断：値と位置を一度の解析から得る

領域の中身は既存の`rule`解析（`ParseRuleAuthoringAnchored`）へそのまま渡す。渡す前に、領域より前のバイトを空白へ置き換え、改行だけを残した原文を作る。こうすると、解析が返すオフセット、行、列は、文書全体での値になる。位置を後から足し直す計算がなく、解析器にも手を入れていない。領域の終わりで原文を切るので、領域内の書きかけに対する誤りは、文書の末尾ではなく領域の中を指す。

Source Indexには変更が一つ要った。従来は意味定義のファイルを既存の文法で解析し直して位置を求めていた。`*.tei.md`はその文法では読めないうえ、二度目の解析は一度目と違う読み方になり得る。そこで`Load`が解析時の範囲を保持し、Source Indexはそれを使う。保持した範囲は、索引の検証でLoad時のバイト列と照合される。

| 案 | 採らなかった理由 |
| --- | --- |
| 領域を切り出して解析し、後からオフセットを足す | 行と列の補正が別の計算になり、CRLFやBOMで食い違う余地が残る |
| 字句解析器に開始位置を持たせる | 正しい方法だが、既存の解析器の全入口へ影響する。領域が多い大きな文書で、空白を作る費用が問題になったら移る |
| Source Index側で`*.tei.md`を解析し直す | 値と位置が別の解析に由来する |

## 6. 判断：既存の意味へ変換し、文書は全部か無かにする

規則は既存の`semantic.Validation`になる。`positive`と`unique … per …`は、既存の`validation`宣言の`positive`と`relation-unique`と同じ値を作る。試験では、同じ二つの規則を既存の文法で書いたWorkspaceと読み比べ、Validationが一致することを確かめた。Validator、評価器、診断コードには手を入れていない。

一つの文書に読めない領域、解決できない参照、既に宣言されたIDが一つでもあれば、その文書は何も寄与しない。検証用の読込み（`LoadForValidation`）では、文書内の問題をそれぞれの位置で集めて返す。

## 7. 中核構造の判断：三部品を採り、三点を改める

定義を「標準データ構造」「Role」「Operator」の組合せで書く方向（[#2619](https://github.com/hat47x/tei-platform/issues/2619)〜[#2621](https://github.com/hat47x/tei-platform/issues/2621)）は採る。分野ごとに文法と解析器を増やさずに済み、表や図との往復を共通の仕組みで持てるからである。今回の実装で、そのままでは足りない点が三つ分かった。

### 7.1 Roleは「読み方」だけを表す

Roleへ意味を詰め込むと、型やContractとの境が曖昧になる。次のように分ける。

| 概念 | 決めること | 例 | 決めないこと |
| --- | --- | --- | --- |
| Role | 標準データ構造を、どの種類の定義として読むか。持つ欄、同一性を決める欄、中へ書ける種類、参照先の範囲 | `rule`は対象と検査を持つ。`membership`は人、組織、期間を持つ | 値の計算、成立の判定、権限 |
| 型 | 欄や式が取り得る値の範囲 | Decimal、単位付きの数量、ある種類の定義への参照 | 定義の形 |
| Operator | 値から値を求める計算と、その入出力の型 | `positive`、`unique`、`convert` | 何を定義とみなすか |
| Contract | ある定義や実装が満たすべき条件 | 「Queryは宣言した入力だけを使う」「実装は丸めを最後に一度行う」 | 新しい部品。規則の集まりとして書く |

Contractを第四の部品にしない点が要である。Contractは「Roleで読んだ定義、または実装の観測結果を入力とする規則の集まり」として、同じ三部品で書ける。Traitも同じ扱いにする。複数のTraitを一つの定義へ適用することは、複数の規則の集まりが同じ定義を入力に取ることで表せる。

### 7.2 Operatorは計算に限り、作用は操作として分ける

計算、検証、変換は、どれも「型付きの入力から値を求める」ものとしてOperatorへ統一できる。検証は真偽を返す計算、変換は構造を返す計算である。外部への作用は統一しない。DBの更新や通知は、結果が「未適用・適用済み・不明」に分かれ、やり直しの扱いが計算と違う。作用は既存のCapabilityのような操作として宣言し、式の中からは呼ばない。

Operatorの契約には結果の型だけでなく**何を読む必要があるか**を含める。今回の二つの述語で、すでに違いが出ている。

| 種類 | 例 | 読む必要があるもの | 既存の評価器の入口 |
| --- | --- | --- | --- |
| 一つの値の計算 | `positive` | 属性一つの値 | `Number(attribute)` |
| 集まりの計算 | `unique … per …` | 関係の全件。途中までの取得では「成立」を言えない | `RelationKeys(relation, attribute)` |
| 構造の変換 | 定義から図やコードを作る | 定義そのもの | 評価器の外 |

同じ結果が返っても、読んだものが違えば同じ規則ではない。試験では、数量と明細番号がともに2のとき、対象を取り違えた規則も「成立」を返すことと、読取要求を照合すれば取り違えを検出できることを確かめた。

### 7.3 自己記述は二段で読み、循環を作らない

Roleの宣言もTEIの記法で書く。このとき「Roleを読むためのRole」を同じ読込みの中で解決しようとすると循環する。読み順を固定して断つ。

1. 種になる読み方は`tei`の実行ファイルが持つ。領域の検出、式の文法、`role`と`operator`の宣言の読み方である。
2. 一段目で、WorkspaceのRoleとOperatorの宣言だけを、種の読み方で読む。宣言の中で、Workspaceが宣言したRoleは使えない。
3. 二段目で、残りの定義を、一段目で得たRoleとOperatorで読む。

不動点を求める繰返しは行わない。セルフビルドでは、段Nの`tei`が種を持ち、段Nが読んだ定義から段N+1の`tei`を作る。今回の`languages:`と組込み実装はこの種を一言語ぶんだけ先に置いたものである。

### 7.4 今回の実装が示した不足

| 不足 | 今の状態 | 次に要るもの |
| --- | --- | --- |
| 述語が固定の列挙である | `positive`と`unique`を解析器が直接知っている | Operatorの宣言を読み、宣言にない名前、引数の個数や型の不一致を診断する経路（[#4362](https://github.com/hat47x/tei-platform/issues/4362)〜[#4366](https://github.com/hat47x/tei-platform/issues/4366)） |
| 診断が欄を指せない | 属性名の誤りでも、診断は規則のIDの位置を指す。Source Indexが定義の同一性しか持たないため | 「定義＋欄」を単位とする参照。Roleの欄がそのまま単位になる |
| どの行を読むかを書けない | 規則は属性を名指しするだけで、入力の束縛がない | 入力の宣言と、評価時のInstanceの照合 |
| NULL、未取得、部分取得を渡せない | 既存の評価器は数値と文字列の配列しか受け取らない | 取得状態と取得範囲を持つ入力。変換できない状態は評価へ渡さず止める |

## 8. 同じ構造をほかの分野へ使う

今回作った経路は規則に固有の部分と、ほかでも使う部分に分かれる。

| 部分 | 規則に固有か | ほかの分野での再利用 |
| --- | --- | --- |
| manifestでの言語の選択、実装の解決、未選択の拒否 | 固有でない | そのまま使う |
| `tei`フェンスの検出と近い書き損じの拒否 | 固有でない | そのまま使う。表や矢印の領域は種類を足す |
| 位置を保った解析、Load時の範囲をSource Indexへ渡す仕組み | 固有でない | そのまま使う |
| 文書単位の全部か無か、IDの重複の拒否 | 固有でない | そのまま使う |
| 規則の文法と、Validationへの変換 | 固有 | 分野ごとに、Roleの宣言と既存の意味型への変換を用意する |
| 型付きの変更を一つのバイト範囲へ反映する仕組み | 対象の欄の選び方だけ固有 | 欄の位置を持つ定義なら同じ形で使う |

分野ごとに足りない能力は次のとおりである。

| 分野 | 書きたい定義 | 足りない能力 |
| --- | --- | --- |
| 組織の所属 | 人、組織、主務か兼務か、開始日と終了日。同じ人と組織を期間違いで複数回結ぶ | 表の領域。IDを必須にする関係。終了日の「未定」と「不明」の区別。現行のMembershipにはPersonへの正式なLinkがなく、同じ所属の訂正前後を保存できない（[組織C1補遺](ORGANIZATION_C1_TEMPORAL_DECISION_CONFORMANCE_2026-11.md)§35）。記法より先に意味側を決める必要がある |
| 既存システムの移行候補 | 観測した事実と、それに対応すると考えるData・Function・Queryの候補。対応は0件から複数件まであり得る | 「候補」と「受理済みの定義」を別の種類として読む仕組み。候補は意味モデルへ入れず、根拠の参照を必須の欄にする。曖昧な一致から個別の対応を作らない規則は既にmainにある（#4850） |
| Generatorの定義 | 入力にする定義の種類、出力する成果物の役目と置き場所、使うToolchain | 構造を返すOperatorの契約。出力先の所有を宣言する欄と、衝突を書込み前に検出する検査。[#4544](https://github.com/hat47x/tei-platform/issues/4544)のG1が進行中なので、ここでは実装しない |

## 9. Pluginまわりの概念の整理

区別する理由が寿命、版、範囲のどれかにあるものだけを分ける。

| 概念 | 分ける理由 | 今回の対応物 |
| --- | --- | --- |
| Contract | 意味の版を持つ。実装が変わっても同じ | `tei.rule-authoring/v0` |
| Package | 配布の版を持つ。一つのPackageが複数の実装を含む | `tei`の実行ファイル |
| Instance | 設定と接続を持ち、実行中だけ存在する。同じ実装から複数作れる | 今回はない（設定を持たない） |
| Artifact | 生成や取得で得たバイト列。内容で識別する | 今回はない |
| Composition | ある用途のために選んだ組合せ。インストール済みの全候補とは別 | manifestの`languages:` |

ProviderとContributionは独立した管理対象にしない。Providerは「PackageがあるContractを実装している」という事実で、Packageの版に従う。Contributionはその事実に「設計時・構築時・実行時・試験のどこで使うか」を添えたものである。今回の組込み実装は「`tei`というPackageが、`tei.rule-authoring/v0`を設計時に読む」というContributionに当たる。

## 10. セルフビルドへの接続

セルフビルドの循環のうち、今回つながったのは最初の区間である。

```text
*.tei.md → 意味モデル（ここまで） → Generator → 生成部品 → Frontend → Desktop → 次のStudio
```

到達点は三つに分けて数える。DSLの自己記述（RoleとOperatorの宣言をTEIの記法で読む）、Generatorの自己構築（Generatorの定義から生成器を作る）、Studio Desktopの再構築（Stage1がStage2を作る）である。今回はどれにも達していない。達したのは「設計文書の規則が、選択した実装によって製品の意味モデルへ入る」ことである。

次の区間への接続は次のように考える。

- **Generator**：規則のValidationは既存の意味型なので、既存のGenerator選抜（[#4544](https://github.com/hat47x/tei-platform/issues/4544)、[#1121](https://github.com/hat47x/tei-platform/issues/1121)）がそのまま入力にできる。`*.tei.md`のために生成側を変える必要はない。
- **Build**：BuildIntentの対象をPluginに限らず、「入力の役目と出力の役目を持つ工程」として扱う方向（[横断Plugin設計](PLUGIN_ROLE_COMPOSITION_AND_STUDIO_REENTRY_2026-11.md)が「Studio Desktopを正式な非Plugin Build対象」としている）に賛成する。Desktopを架空のPluginにしない。工程の宣言は§7のRoleで読む定義の一種になる。
- **選択と実呼出しの照合**：実装の時点で、mainの`cmd/tei`がコンパイルできない状態だった。原因は、BuildPlanから得た選択Builderの内容識別値を子の起動へ渡す引数が、並行統合で落ちていたことである。変数だけを消して直すと、選んだBuilderと実際に起動した子の照合が行われなくなる。引数を復元した（`7085e2c18`、main統合済み）。「選択した」と「選択したものが呼ばれた」は別の検証事項であり、言語の実装についても試験で分けて確かめた。

## 11. 反証と試験

期待値は試験対象のコード以外から用意した。意味は既存の`validation`文法、位置は文書に対する`strings.Index`、読取要求は呼出しを記録するSourceである。

| 破綻し得る条件 | 確かめたこと | 結果 |
| --- | --- | --- |
| 同名だが異なるIDの定義 | `sales.…quantity_positive`と`purchase.…quantity_positive`を別の文書に書く | 別の対象として読み、Source Indexはそれぞれの文書の位置を指す |
| 同じIDの二重宣言 | 既存の`.tei`と`*.tei.md`、二つの`*.tei.md`、一つの文書の二つの領域 | 後から読んだ側の位置で止まる。読んだ順で選ばない |
| 異なる属性を読んでも同じ値になる | 対象を明細番号へ書き換え、両方の値を2にする | 結果は同じ「成立」。読取要求の照合で検出する |
| 0の扱い | 数量0を評価する | 不成立。値がない状態とは区別される |
| Unicode、CRLF、BOM | 日本語の本文の後ろの領域、CRLFの文書、BOM付きの文書 | オフセット、行、列が独立に求めた値と一致する |
| 古い位置への書込み | 編集案を、保存後の文書と、別の箇所が変わった文書へ適用する | どちらも拒否する。範囲の文字列が同じでも適用しない |
| 同じ文字列の複数出現 | 変更前の属性名を本文と引用例にも書く | 規則の中の一か所だけが変わる。範囲外のバイトは変わらない |
| 古いSource Index | 読込み後に本文だけを追記する | 古い索引は検証で失効する。定義が変わらなくても文書の識別値は変わる |
| 未選択の実装による解釈の変化 | 選んでいない実装を一覧へ足す。並び順も入れ替える | 呼ばれない。読んだ意味は変わらない |
| 選択と実呼出しの不一致 | Bを選んだときにAが読まないこと | Bだけが1回呼ばれ、読取りの記録もBを指す |
| 契約に合わない実装 | 持っていない版を選ぶ。同じ契約の実装が二つある | 止まる。近い版や先頭の実装へ代えない |
| 部分的な成功 | 一つの領域だけ参照を解決できない文書 | 文書全体が寄与しない |

検査が誤った実装を見分けられるかも確かめた。実装へ誤りを一つずつ入れ、試験が失敗するかを見た。

| 対象 | 入れた誤りの数 | 検出 | 検出しなかったもの |
| --- | --- | --- | --- |
| 領域の検出、解析、選択、読込み、Source Index | 18 | 17 | 1。問題のある文書でも読めた領域を採る誤り。この場合は`Load`自体が失敗して結果を返さないので、外から観測できない |
| 型付きの変更 | 2 | 2 | — |

入れた誤りは、改行を残さず行番号をずらす、フェンス名の大文字小文字を無視する、`text`のフェンスを読む、選択を無視して最初の実装で読む、版を照合しない、未選択でも読む、重複を検査しない、Load時の位置を使わない、対象の属性を取り違える、版を確かめずに編集を適用する、位置を文字列検索で決める、などである。この変異試験は実装時の版（`091cb726d`相当）に対して手元で実行した。再実行できるスクリプトはリポジトリへ入れていない。

### 確かめていないこと

- NULL、未取得、取得失敗、非開示の区別と、部分取得を完全な集合として扱う誤り。既存の評価器の入口がこれらを表せない。
- Decimalの丸め順序、単位、短絡評価。今回の規則には算術も複合式もない。
- UTF-16の位置との変換。Editorへ渡す側の仕事で、今回は扱っていない。
- 契約と実装の内容識別値の照合。
- 保存先での「版の確認と置換を不可分に行う」保証。型付きの変更は文書のバイト列に対する計画と適用までを実装した。ファイルへの条件付き書込みは既存のSource保存の経路へつなぐ必要がある。
- Generatorの出力先の衝突、古いArtifactの混入、再生成での手書きの消失、Stage1とStage2の構築関係。今回の経路の外である。
- 人による読みやすさの評価と、実装者から独立したレビュー。この文書と試験は実装者自身が用意した。

## 13. 追補：Operatorの宣言を読む経路（実装つき）

§7.4の一行目「述語が固定の列挙である」に対する最初の実装である。標準外のOperatorを一つ足すときに、解析器、列挙型、Validator、評価器を直さずに済むかを確かめた。

### 書くもの

Operatorは`tei`フェンスの中で宣言する。規則からは`is`の後ろに修飾名を書いて参照する。

````markdown
```tei
namespace sales

operator sales.non_negative: takes number

rule sales.order_line.discount_non_negative:
  sales.order_line.discount is sales.non_negative
```
````

`takes number`は、このOperatorが属性一つの数値を読むことを表す。宣言に書けるのは名前と読むものだけで、実装は書けない。組込みの`positive`と`unique`の書き方と意味は変えていない。

### 起こること

| 段階 | 動き |
| --- | --- |
| 解析 | `is`の後ろの修飾名をOperatorへの参照として読む。宣言済みかどうかはここでは決めない |
| 意味モデル | 宣言は`Namespace.Operators`に入る。規則は種類`operator`のValidationになり、どのOperatorかを`Operator`の欄に持つ |
| Validator | 宣言のないOperatorへの参照、数値を取るOperatorを文字列の属性へ使う規則、同じIDの二重宣言、属性など他の要素と同じIDの宣言を診断する |
| 評価 | `EvaluateWithOperators`へ、読み込んだ宣言と、選択した実装を渡す。宣言と実装がそれぞれちょうど一つあり、読むものが一致したときだけ判定する |
| Source Index | 宣言の位置を`semantic-operator`として記録する |

宣言を書いた文書と、それを使う規則を書いた文書の順序は問わない。属性への参照と同じく、Workspace全体が読めた後でValidatorが解決する。

### 判断

| 判断 | 採った案 | 理由 |
| --- | --- | --- |
| 種類の持ち方 | Validationの種類は`operator`を一つだけ足し、どのOperatorかはデータとして持つ | Operatorを足すたびに列挙型と各所の分岐を直す形をやめる。種類を足すのはこの一度だけである |
| 参照の書き方 | 修飾名は宣言済みOperator、修飾のない語は組込みの述語 | 修飾のない未知の語をOperatorとして読むと、`positiv`のような綴り違いが「未宣言のOperator」に変わり、誤りの場所が解析から検証へ遅れる |
| 読むものの決め方 | 宣言が決める。実装は値だけを受け取り、Sourceに触れない | 同じ結果でも読んだものが違えば同じ規則ではない（§7.2）。実装が別の属性や別の行を読めない形にすれば、読取要求は宣言から決まる |
| 実装の渡し方 | 評価の呼出し側が渡す。組込みの一覧は作らない | 実装の選択は構成の仕事である。今回は試験が実装を渡した。製品のシナリオ実行へ渡す経路は未接続である |
| 既存の二つの述語 | そのまま残す | 既存の定義、生成、指紋を変えない。標準のOperatorとして宣言し直すのは、取得状態を持つ入口を決めた後にする |

読み順を二段にする設計（§7.3）は、今回は必要にならなかった。`takes number`のOperatorは解析の仕方を変えないからである。Roleの宣言や、引数の形が解析に影響するOperatorを足すときに必要になる。

### 既存の反例試験が見つけた弱点

`rule sales.q: positive is a.b`のように語順を入れ替えた規則は、従来は解析で拒否されていた。修飾名をOperatorへの参照として読むようにした直後、この規則が「`positive`という対象に`a.b`というOperatorを使う規則」として受理された。既存の反例の試験（N-10）がこれを検出した。対処は二つである。述語の語を対象の位置に書いた規則を解析で拒否する。Operatorと属性が同じIDを持つことをValidatorで拒否する。後者がないと、属性とOperatorを入れ替えて書いた規則が、たまたま同名の宣言へ解決されてしまう。

### 反証

| 破綻し得る条件 | 結果 |
| --- | --- |
| 宣言がない、二重にある | 評価しない。Validatorも診断する |
| 実装がない、二つある、別のOperatorの実装しかない | 評価しない。成立とも不成立とも返さない |
| 実装が宣言と違う入力向けに書かれている | 評価しない |
| 値がない、取得に失敗した | 実装へ渡さない。0として扱わない。0を認めるOperatorなので、0で埋めると「成立」になる |
| 実装が受け取った値を書き換える | Sourceが持つ値は変わらない |
| 別の名前空間の同名のOperator | 別のOperatorとして読む。その実装では判定しない |
| 属性をOperatorの位置に書く | 未宣言のOperatorとして診断する |
| Operatorを含む原文の整形 | 拒否する。宣言や参照を落とした原文を返さない |
| Operatorを宣言しないWorkspace | 意味モデルの直列化にOperatorの項目が現れない |

独立した期待値は0・正・負の三つの数に対する「負でない」の定義である。0で組込みの`positive`と結果が分かれることを使い、宣言したOperatorが組込みの種類へ置き換えられていないことを確かめた。

実装へ誤りを20種入れ、試験がすべて検出することを確かめた。最初の実行で1種（整形が宣言を落とす誤り）が検出されず、試験を一つ足した。スクリプトはリポジトリへ入れていない。

### 足したもの、足していないもの

標準外のOperator `sales.non_negative`を足すために書いたのは、文書の中の宣言一行と、試験の中の関数一つである。解析器、列挙型、Validator、評価器のどのファイルにも、このOperatorの名前は現れない。

一方、仕組みそのものを入れるために、解析器、意味モデル、Validator、評価器、Loaderを一度ずつ変更した。次の種類の入力（関係の全件を読むOperatorなど）を足すときは、入力の語、Validatorの型の照合、評価器の読取りの三か所をもう一度変更する。この変更は入力の種類ごとに一度で、Operatorごとではない。

確かめていないことは次のとおりである。

- 製品のシナリオ実行（`tei scenario run`）は従来の`Evaluate`を呼ぶので、Operatorの規則は「評価できない」という誤りになる。選択した実装を渡す経路は作っていない。
- 実装の選択をPluginの選択とLockから受け取る経路。
- 生成（Goの検査コードの生成）はOperatorの規則を扱わない。
- 契約の版と内容識別値。宣言に版を書く場所がない。
- 関係の全件を読む入力、複数の引数、取得状態を持つ値。
- 独立したレビュー。

## 14. 追補：選択した実装をシナリオ実行へ渡す経路（実装つき）

§13で残した「`tei scenario run`はOperatorの規則を評価できない」に対する実装である。

### 書くもの

Operatorの宣言は文書に書く（§13）。どの実装で判定するかはWorkspaceのmanifestで選ぶ。

```yaml
implementations:
  - operator: sales.non_negative
    use: tei.number.non-negative
```

`use`に書くのは、実行する`tei`が持つ実装の名前である。現在の`tei`が持つのは、数値一つを調べる二つの実装である。

| 名前 | 成立する値 |
| --- | --- |
| `tei.number.non-negative` | 0以上 |
| `tei.number.non-zero` | 0以外 |

### 起こること

シナリオの`evaluate-validations`は、Applicationが`uses validation`で選んだ規則を評価する。規則が宣言済みOperatorを使う場合は、manifestが選んだ実装で判定し、実際に呼んだ実装の名前を証拠の`validationImplementations`へ規則ごとに記録する。組込みの`positive`と`unique`の規則にはこの記録が付かない。

| 状態 | 結果 |
| --- | --- |
| Operatorに実装を選んでいない | その手順は誤りで止まる。成立とも不成立とも記録しない |
| 選んだ名前の実装を`tei`が持たない | 誤りで止まり、選べる名前を示す |
| 同じ名前の実装が二つある、同じOperatorを二度選んでいる | 誤りで止まる。並び順では選ばない |
| 宣言のないOperatorへ実装を選んでいる | `Load`が`TEI_OPERATOR_IMPLEMENTATION_UNBOUND`で止まる |
| 判定したのに、選んだ実装が呼ばれていない | 誤りで止まる |

### 判断

| 判断 | 採った案 | 理由 |
| --- | --- | --- |
| 選択を書く場所 | Workspaceのmanifest | 言語の選択（§3）と同じく、選択は構成の仕事である。文書の宣言とは分ける |
| 選択と意味の関係 | 選択を変えても意味モデルは変わらない | 同じ文書を別の実装で試せる。試験で、実装を入れ替えた二つのWorkspaceの意味モデルが一致することを確かめた |
| 実装を持つかどうかを確かめる時点 | 評価のとき。`Load`は確かめない | 文書の検査や閲覧は、実装を持たない`tei`でも行える。持たない名前のまま判定することはない |
| 「選んだ」と「呼ばれた」 | 別に記録する | 選択の一覧に名前があることは、その実装が判定したことを示さない。呼出しのたびに記録し、記録がなければ結果を採らない |
| 組込みの実装の範囲 | 数値一つを調べる汎用の二つ | 業務の語（`sales.non_negative`）は文書の宣言が持ち、`tei`は業務を知らない汎用の検査だけを持つ |

### 反証

独立した期待値は0に対する「負でない」と「0でない」の定義である。0で二つの結果が分かれることを使い、選んだ実装が実際に判定していることを確かめた。

| 破綻し得る条件 | 結果 |
| --- | --- |
| 実装をBへ替えたのにAが判定する | 0に対する結果と、呼ばれた実装の記録の両方がBになる |
| 選んでいない実装が判定に関わる | 呼ばれない。選択を解決した時点では、どの実装も呼ばれない |
| 同じ名前の実装を一覧の前後どちらへ足しても | どちらの順でも止まり、足した実装は呼ばれない |
| 期待結果が誤っているシナリオ | 実際の結果と期待の不一致として報告する。期待へ合わせない |

実装へ誤りを12種入れ、試験がすべて検出することを確かめた。スクリプトはリポジトリへ入れていない。

### 確かめていないこと

- 生成済みのシナリオ実行コマンドは、意味モデルとPlugin Lockの識別値を固定するが、manifestの識別値は固定しない。実装の選択だけを変えた場合、古いコマンドは古いと判定されない。実行時には、その時点のmanifestの選択で判定し、呼んだ実装を記録する。
- 実装をPluginの選択とLockから受け取る経路。組込みの二つ以外の実装を足す方法はまだない。
- 実装が宣言の意図どおりかの照合。確かめているのは読むものの種類の一致だけである。宣言の近くに例と期待結果を書き、選んだ実装をその例で試す仕組みが要る。
- `tei scenario run`のコマンド全体を通した実行。試験は、コマンドが規則の評価に呼ぶ関数を、製品の`Load`で読んだWorkspaceに対して実行した。
- 独立したレビュー。

## 15. 追補：表の領域と、組織の題材での判断（実装つき）

§4の「表で定義を書く必要が示されたら、領域の種類を足す」と、§8の組織の行に対する実装と判断である。

### 判断：所属の一覧は定義ではなく記録である

組織の題材で最初に決める必要があったのは、表に何を書くかである。「誰がどの組織に、いつからいつまで属するか」を設計文書の表へ書く案は採らなかった。

TEIの意味モデルが持つのは、記録の形（Dataと項目）、規則、操作である。所属の一行一行は記録であり、参照用の組織Workspaceでも、DBに保存してQueryで読む対象になっている。これを設計文書の表にも書くと、同じ記録の置き場所が二つになる。人事異動のたびに設計文書を直すことになり、文書とDBのどちらが正しいかを決める規則が要る。

そこで、表の領域は次のように分けた。

| 表に書くもの | 扱い | 状態 |
| --- | --- | --- |
| 記録の形。Dataの項目定義表 | 定義として読み、既存の`semantic.Data`にする | 今回実装した |
| 例や試験の入力となる記録 | 定義ではない。規則やシナリオの入力と期待結果として読む | 未実装。印の形を別にする |
| 運用中の記録そのもの | 設計文書には書かない。DBやProviderが持つ | 対象外 |

「終了日の未定と不明の区別」も、記録の側の問題である。項目定義表で言えるのは「終了日は必須ではない」までで、値がないことの理由は表の記法では表せない。これは値の取得状態（§7.4の四行目）と同じ課題で、記録のモデルの側で決める。

### 書くもの

manifestで、表も読む言語を選ぶ。

```yaml
languages:
  - tei.authoring/v1
```

項目定義表は通常のMarkdownの表の直前に印を一行置いて書く。

```markdown
<!-- tei: data TransferRequest in organization -->
| attribute | type | required | display | description |
| --- | --- | --- | --- | --- |
| personId | std.identifier | yes | 対象者 | 所属を変える人 |
| allocation | std.decimal | yes | 配分 | 兼務のときの割合。主務だけなら1 |
| effectiveTo | std.datetime | no | 終了日 | 決まっていないときは値を持たない |
| reason | std.text | | 理由 | |
```

一行が一つの項目である。列は`attribute`と`type`が必須で、`required`、`display`、`description`は省ける。印のない表は、同じ形をしていても定義として読まない。同じ文書の`tei`フェンスに、この項目を対象にした規則を書ける。

### 起こること

表は既存の`data`宣言と同じ`semantic.Data`になる。DataのIDと項目のIDは、既存の文法と同じ規則で名前から導く。Validatorは既存のまま働き、未知の型は表の行の位置つきで診断される。Source Indexは、Dataを印の中の名前の位置、項目を`attribute`のセルの位置として記録する。

| 書き方 | 結果 |
| --- | --- |
| 空のセル（`required`、`display`、`description`） | 「書いていない」として読む。既存の宣言でその指定を省いたときと同じになる |
| 空のセル（`attribute`、`type`） | 誤りにする。既定の型で埋めない |
| `required`に`yes`と`no`以外を書く | 誤りにする |
| 見出しにない列、同じ列の重複 | 誤りにする。読まない列を残さない |
| 印と表の間に空行がある、区切り行がない、行が一つもない | 誤りにする |
| 行のセルの数が見出しと合わない | 誤りにする |
| セルの中に`\|`を書く | 誤りにする。縦棒を含む値は表の外に書く |
| `display`や`description`に二重引用符や逆斜線を書く | 誤りにする。既存の宣言で書けない値を作らない |
| 同じDataを既存の`.tei`や別の表でも宣言する | 後から読んだ側の位置で止まる |
| `tei.rule-authoring/v0`を選んだまま印を書く | 従来どおり誤りにする。読まない表を成功にしない |

### 判断

| 判断 | 採った案 | 理由 |
| --- | --- | --- |
| 印の形 | 表の直前の一行のHTMLコメント | 表をコードフェンスへ入れると、通常のMarkdown表示で表として描画されない |
| 読む表の決め方 | 印のある表だけ | 説明のための表を定義にしない（§4と同じ） |
| 意味の置き場所 | 既存の`semantic.Data` | 表のために新しい意味モデルを作らない。既存の宣言へ書き戻せる範囲だけを受理する |
| 言語の契約 | `tei.authoring/v1`を新しく置き、`tei.rule-authoring/v0`は残す | 既存の契約が読むものを変えない。v1はv0が読むものをすべて読む。試験で、フェンスだけの文書が両方で同じ意味モデルになることを確かめた |
| 二つの言語の併用 | できない。どちらか一つを選ぶ | 一つの文書を二つの実装が読むと、どちらの読みを採るかが決まらない |
| 関係と候補キー | 表では書かない | 項目の一覧は表が向く。関係は両端と多重度を持ち、一行に収まらない。既存の`.tei`か、後の矢印の書き方で書く |

名前の付け方には弱点が残る。`tei.rule-authoring`は規則の文法の名前から来ており、表まで読む契約の名前に合わない。そこで広い契約へ新しい名前を付けた。領域の種類ごとに実装を選べるようにする（§3の見直し条件）までは、この二つを使い分ける。

### 反証

独立した期待値は同じDataを既存の文法で書いた宣言である。表から読んだDataと、既存のLoaderが読んだDataが一致することを確かめた。

| 破綻し得る条件 | 結果 |
| --- | --- |
| 印のない表、通常の一行コメントの直後の表 | 定義にならない |
| 空のセルを値として読む | 読まない。`required`の空欄は必須にならず、`type`の空欄は既定の型にならない |
| `display`と`description`の取り違え | 既存の宣言との一致で検出する |
| 項目のIDをDataの下でなく名前空間の下に作る | 既存の宣言との一致で検出する |
| LF、CRLF、BOM | セルの位置が独立に求めた値と一致する |
| 表だけが誤っている文書 | 文書全体が寄与しない。同じ文書の規則も入らない |

実装へ誤りを20種入れた。最初の実行で1種を検出できず、通常の一行コメントを含む文書の試験が無いことが分かった。試験を一つ足し、20種すべての検出を確かめた。スクリプトはリポジトリへ入れていない。

### 確かめていないこと

- 例や試験の入力となる記録の表。組織の兼務と有効期間の例を、規則やQueryの期待結果へつなぐ経路はまだない。
- 所属から人への正式なLinkと、同じ所属の訂正前後の保存（§8）。意味の側の未解決で、今回は触れていない。
- 表で書いたDataを含むWorkspaceでの、Query、Persistence、生成。確かめたのは読込み、Validator、Source Indexまでである。
- 関係、候補キー、項目の`immutable`と`role`と`value`。表の列にしていない。
- 型付きの変更を表のセルへ反映する経路。セルの位置は持っているが、編集は実装していない。
- 人による読みやすさの評価と、独立したレビュー。
