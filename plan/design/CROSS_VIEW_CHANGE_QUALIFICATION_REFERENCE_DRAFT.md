# 視点をまたぐ変更の適格性確認 — 参照契約案

状態: **設計候補・未採用**。対象はIssue [#1143](https://github.com/hat47x/tei-platform/issues/1143)で検討中の変更確認です。製品の正規スキーマ、新しい正規モデルの種類、別個の受入機構は追加しません。

## 目的と責務の境界

一つの対象だけを見た知識の適格性確認や、`qualified-for-disclosure`を含むBuilder Reviewの引継ぎだけでは、業務・データ・機能の各視点にまたがる設計変更の整合性を証明できません。ここで検討するのは、既存のモデル上の根拠と検証器から、変更の適格性を読み取り専用で導く方法です。提案の昇格を保留することはできますが、この仕組み自体が変更を受理したり適用したりすることはありません。

既存の情報源と検証器が、それぞれの責務を引き続き担います。

- `internal/application/model.go`: `Application.DatabaseByAliasExact`、`DatabaseRequirement.Access`、`Pattern.ContractQuery`を定義します。参照や読取り契約が解決できても、編集権限があることにはなりません。
- `internal/driver/resolver.go`: `Resolver.ResolvePattern`がPatternの既存参照を解決します。`PatternResolution`の省略可能な値はPatternの種類に応じたもので、直ちに根拠不足を意味しません。
- `internal/validation/application_pattern.go`と`internal/validation/validation.go`: `ValidateApplicationPatterns`と`Validate`が正規モデル間の参照を検証します。`Diagnostic`だけでは根拠の由来や鮮度をすべて表せません。
- `internal/knowledgecontext/builder_review.go`: `BuildBuilderReviewPlan`は視点をまたぐ確認を計画に含めますが、確認が実施された証拠にはなりません。
- `internal/knowledgecontext/builder_review_handoff.go`: `ValidateBuilderReviewHandoff`は対象ごとの引継ぎを検査します。変更全体の整合性までは検証しません。
- `tools/reference-shared-acceptance/main.go`: `attach-qualification`と`propose-qualified-reference-pattern`が既存の接続口です。正規情報の変更は、明示的な`accept`を通じて行います。

## 最小限の投影案（スキーマ未確定）

| 項目 | 必要な情報 |
| --- | --- |
| 対象と操作 | 機能などの明示したモデル対象と、求める意味上の変更 |
| 基準 | 完全なWorld／準拠基準と、適用対象となる業務上の意味・入力元の版 |
| 影響対象と関係 | 種類と向きを持つ意味上の参照。逆向きのたどり方を、逆向きの権限や依存関係とみなさない |
| 根拠 | 入力元の識別、権威ある入力元の集合への所属、入力内容または照合値、版、適用範囲、時間的な適用条件 |
| 必須確認 | 確認を担う検証器、その適用条件、結果、根拠への参照、未解決の理由 |
| 結果 | `eligible-for-proposal`、`blocked-incompatible`、`blocked-unresolved`、`blocked-stale`のいずれか |
| 制約 | 認可、実行許可、受理済みの判断、推測した業務上の事実を表さない |

必須確認の不足や鮮度切れ、不整合があれば提案を先へ進めません。任意確認を省く際は理由を添えます。循環による結果の揺れは、処理範囲を限定し、出力順を固定して防ぎます。全体共通の業務手順・手順段階・引継ぎに新しい識別子は追加しません。

## 最初の参照シナリオ

1. 既存の受注登録にある顧客参照Patternと、明示的な読取り専用の基本情報契約から始めます。
2. 対象単位の知識の適格性確認が、参照の再利用については成功することを示します。
3. `enable-customer-edit`を要求します。読取り可能なデータ元、Patternの種類、問い合わせ契約の存在、観測された登録・更新・削除の事実から、書込み権限を推測しません。
4. 書込み機能の明示が欠けるか矛盾する場合は`blocked-incompatible`とします。権威ある業務上の担当者や手順が不明な場合は、別に`blocked-unresolved`とします。顧客保守の引継ぎを捏造しません。
5. 視点をまたぐ確認が欠けている場合、対象単位の引継ぎだけで変更全体を提案可能とはしません。
6. 既存のShared Acceptanceによる確認、期待照合値、明示的な受理・却下の境界を維持し、別の書込み経路を設けません。

受理済みの業務引継ぎには、明示条件付きの`order-entry.order-handling/BP-09 -> order-entry.follow-up/FU-00`がありますが、顧客保守の根拠ではありません。受理済みの登録・更新・削除の追跡も読取りのみで、`BP-00 -> R sales.order`、`BP-02 -> R customer.customer`、`BP-03 -> R sales.order_line`です。作成・更新・削除は推測しません。

## 反例を含む受入表

| 入力 | 期待する結果 |
| --- | --- |
| 読取り専用の参照契約による読取り | 読取りに適用。編集許可は導かない |
| 読取り専用契約での編集要求 | 不整合として保留 |
| 受理済みの業務上の責任がない編集要求 | 根拠不足として保留 |
| 視点をまたぐ根拠のない対象単位の引継ぎ | 根拠不足として保留 |
| 業務の入力元に変化がないままWorldだけが変わる | 根拠が古いため保留 |
| 業務の入力元または権威ある入力元の集合が変わる | 根拠が古いため保留 |
| 内容が同じでも管理対象の`Procedure.id`が重複する | 権威の競合として保留 |
| 対応する引継ぎを更新せず手順段階の名前を変える | 接続先が不正なため保留 |
| 影響調査で向きのある引継ぎを逆向きにたどる | 逆向きの意味上の権限を推測しない |
| モデル参照が循環する | 有限かつ決定的な診断を返す |

根拠の鮮度には入力元の内容、入力元集合、権威ある起点への所属、論理識別子の一意性、Worldと準拠基準の版を含めます。GitのHEADが一致するだけでは鮮度を証明できません。

## 実装へ進む順序

1. 業務手順の検査、参照データの正規化、準拠確認を担う既存のテストと関数を特定します。存在を確認していないパッケージや製品用ローダーを前提にしません。
2. `decodeQualificationInput`、`attachQualificationEvidence`、`proposeQualifiedReferencePattern`を調べ、既存の引継ぎ形式v1を変えずに提案段階を守る場所を選びます。
3. 既存の検証器と入力元の根拠を再利用する、読取り専用の投影処理を実装します。
4. 上の反例を含む参照データと、対象を絞ったGoテストを追加します。
5. 統合前に、信頼できるクリーンな作業場所で正確な変更版を対象に、リポジトリ健全性検査を実行します。この文書自体は検査記録ではありません。
