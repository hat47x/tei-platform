# 生成器契約が宣言する境界の設計（派生名・拡張点・書込み窓・能力の縮退）

- 状態: 評価待ち（未採用）
- 対応課題: [#2090](https://github.com/hat47x/tei-platform/issues/2090)（拡張点）、[#2092](https://github.com/hat47x/tei-platform/issues/2092)（書込み窓）、[#2094](https://github.com/hat47x/tei-platform/issues/2094)（派生名の衝突）、[#2096](https://github.com/hat47x/tei-platform/issues/2096)（能力不足の縮退）
- 関連課題: [#2016](https://github.com/hat47x/tei-platform/issues/2016)、[#1975](https://github.com/hat47x/tei-platform/issues/1975)、[#1180](https://github.com/hat47x/tei-platform/issues/1180)、[#1920](https://github.com/hat47x/tei-platform/issues/1920)、[#1935](https://github.com/hat47x/tei-platform/issues/1935)、[#2017](https://github.com/hat47x/tei-platform/issues/2017)、[#2091](https://github.com/hat47x/tei-platform/issues/2091)、[#2093](https://github.com/hat47x/tei-platform/issues/2093)
- 関連要求: RQ-001、RQ-008、RQ-015、RQ-016、RQ-019、RQ-021
- 関連する設計判断: [ADR-0022](../adr/0022-ai-proposal-canonical-acceptance-boundary.md)、[ADR-0033](../adr/0033-core-and-plugin-subprojects.md)、[ADR-0035](../adr/0035-autonomy-levels-and-verification-packets.md)
- 役割: 受理した意味から実装を生成する生成器が、生成物について何を約束し、どこを人やAIに書かせるかを、生成器の契約として宣言する設計候補
- 採用判断: 採用する場合は設計判断記録を作成し、そちらを正とする

## この文書の位置づけ

[#2016](https://github.com/hat47x/tei-platform/issues/2016)は、生成器そのものを版付きの成果物として扱い、同じ期待値で候補を比べる仮説を立てています。そこでは、生成器の入力契約、対象、適合試験を記録します。一方、生成器が**出力について**何を約束するかは、まだ一か所に定まっていません。

この文書は、その約束を四つに分けて扱います。四つはどれも「生成物と、生成物の外にあるもの（利用者の名前、手書きコード、AIの編集、既存データベース）との境界」です。担当課題は四つに分かれていますが、どれも生成器の契約に宣言し、生成と受理の前に検査する点で同じ仕組みに乗ります。

この文書は、意味の正本の変更規則を定めません。再利用元の定義の更新と適用先の差分は[再利用した知識の変動点と適用先差分の設計](KNOWLEDGE_VARIATION_DESIGN_2026-10.md)、既存データの移行は[意味の変更に伴う既存データの移行設計](SEMANTIC_CHANGE_DATA_EVOLUTION_DESIGN_2026-10.md)が扱います。

## 解決したい問題

受注の金額を計算する処理を例にします。受注の項目と導出規則は正本にあり、生成器がその計算のコードを生成します。案件では、得意先ごとの端数処理を手書きで足したいとします。

1. **手書きが消える。** 生成物を直接編集すると、次の再生成で消えます。生成クラスを継承して別の場所に置く方式（Generation Gap）を使えば消えませんが、生成器が基底の署名や呼び出し順を変えたとき、手書き側が壊れる、または黙って呼ばれなくなります。どちらも再生成の時点では分かりません。
2. **AIがどこでも書ける。** AIにこの端数処理を書かせると、端数処理の外（権限の判定、データ型、別の計算）まで変えることがあります。提案と受理を分けても（ADR-0022）、書込み先そのものは限られていないため、変更範囲は事後の差分でしか分かりません。
3. **名前がぶつかる。** 生成器は、項目名から表名・型名・API名を作ります。利用者が付けた名前と、生成器が接尾辞を付けて作った名前が一致すると、生成物が壊れるか、別の要素に黙って結び付きます。大文字小文字を区別しないデータベースやOSでは、区別する層で別だった名前が衝突します。
4. **能力が足りないのに動く。** 既存のデータベースの表に競合検出の列が無いと、更新操作を生成しても同時更新を検出できません。そのまま生成すると後勝ちで上書きされます。X-TEAでは、更新件数の確認や楽観ロックの列名が暗黙の既定になっており、更新件数が0件のときの扱いが機能の型ごとに違っていました。

どれも、生成の時点で生成器が分かっている情報（自分の出力の形、自分が付ける名前、自分が要求する能力）を宣言していれば、生成や受理の前に止められます。

## 現在の結論

1. 生成器の契約に、出力についての宣言を四つ持たせる。**派生名の規則**、**拡張点**、**書込み窓**、**要求する能力**である。宣言は機械可読にし、生成器のdigestと版に結び付ける（#2016の受領記録に含める）。
2. 拡張点と書込み窓は、同じ「書込み可能な領域」の宣言として表し、書く主体（人、AI）と必要な検証だけを変える。生成物のうち宣言された領域の外は、人もAIも直接編集しない。
3. 再生成のたびに、宣言された領域の契約が前回から変わったかを比べ、手書き・AIの内容が新しい契約に適合するかを検査する。適合しない場合は失敗とし、黙って効かなくしない。
4. 派生名の規則は、生成器とProviderの層ごとに正規化の規則（大文字小文字、区切り文字、接尾辞・接頭辞、最大長、予約語）を宣言し、意味の正本の受理前に全名前を照合する。
5. 操作ごとに要求する保証（競合検出、監査、トランザクション境界など）を宣言し、実現先の能力と照合する。不足があれば、操作を生成しない・拒否する・弱い保証を明示して受理する、のいずれかに決め、決めた結果を定義と検証根拠に残す。黙って成功させない。
6. 書込み窓の外の変更、窓の新設、能力不足の受理（弱い保証の明示）は、人の判断（ADR-0035のA4）へ戻す。

最初の適用先は、`order_entry`の導出規則の生成物とし、拡張点1つと書込み窓1つで試します。四つの宣言が既存の機構（#2016の受領記録、#1975の契約のみの生成、#1180の経路間比較）に接続できるかを確かめてから採用を判断します。

## 1. 用語

| 用語 | 内容 |
| --- | --- |
| 生成器の契約 | 生成器が入力として受け取る意味の範囲と、出力について約束する内容。#2016の「入力契約」に、本書の四つの宣言を加えたもの |
| 派生名 | 生成器やProviderが、正本の名前から作る名前（表名、型名、API名、メッセージ名など） |
| 書込み可能な領域 | 生成物のうち、生成器以外が内容を書いてよい箇所。名前、版、入出力、呼ばれる順序、書く主体、必要な検証を持つ |
| 拡張点 | 人が書く前提の書込み可能な領域 |
| 書込み窓 | AIが書く前提の書込み可能な領域。拡張点と同じ宣言に、AI向けの制約（検証、レビュー、証跡）を加えたもの |
| 要求する保証 | 生成した操作が成り立つために実現先に求める能力（競合検出、監査、トランザクション境界など） |
| 縮退 | 能力が足りないときに、生成する操作を減らす、拒否する、弱い保証を明示する、のいずれかを選ぶこと |

## 2. 派生名の規則（#2094）

生成器とProviderは、自分が作る派生名の規則を宣言します。

- 正規化: 大文字小文字の扱い、区切り文字（アンダースコア、ハイフン）を無視するか
- 付加: 生成器が内部で使う接尾辞・接頭辞（一覧用、条件用、明細用などの派生型）
- 制約: 最大長、使える文字、予約語、実行先のOSやデータベースの予約名

正本の受理前に、すべての名前と、その名前から作られる全派生名を、各層の正規化で比べます。衝突は、衝突した二つの要素の正本識別子と、どの層の規則で衝突したかを付けて報告します。名前を意味の正本とせず（P4）、この検査は識別子を変えません。改名（#1935）の後の名前にも同じ検査を当てます。

## 3. 書込み可能な領域（#2090、#2092）

### 3.1 宣言の内容

生成器は、書込み可能な領域ごとに次を宣言します。

- 名前と版
- 入出力（受け取る値、返す値、型）と、呼ばれる段階・順序
- 書く主体（人、AI、両方）
- 既定の実装（何も書かれていないときの動き）
- 必要な検証（単体試験、経路間比較、往復の一致など）

既定の実装を持たせることで、手書きもAIの編集も無い状態の生成物が、宣言どおりに動くことを確かめられます。

### 3.2 拡張点と書込み窓の違い

| 観点 | 拡張点（人） | 書込み窓（AI） |
| --- | --- | --- |
| 新設 | 生成器の版上げとして行う | 生成器の版上げ、または人の宣言で行う。AIは窓を自分で増やせない |
| 窓の外の変更が必要になったとき | 生成器の変更を依頼する | AIは止まって人に返す |
| 内容の検証 | 宣言された検証 | 宣言された検証に加え、AIの自己申告を証拠にしない（#2016）。証跡を作業票（#2017）の形式で残す |
| 本番系への適用 | 通常の受理 | レビューを必須にする |

### 3.3 全体生成との関係

AIに書込み窓を持たせず、生成器の契約に沿って全体を生成させる使い方もあります（#1975の契約のみからの生成）。この場合は、書込み範囲を構造で限れない代わりに、次を完了条件にします。

- 本番と分離した開発環境でだけ動かす
- 正本→実現先→正本の往復で差分が出ない（往復の一致）
- 反映前に変更前の状態を退避し、DDL・全件削除などの破壊的な操作は人の明示の承認まで実行しない

全体生成で作ったものを本番へ移した後の改修は、書込み窓に戻します。

### 3.4 再生成時の判定

再生成のたびに、前回の生成器の契約と今回の契約を、書込み可能な領域ごとに比べます。分類は[再利用した知識の変動点と適用先差分の設計](KNOWLEDGE_VARIATION_DESIGN_2026-10.md)の4章と同じ語を使います。

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| `unchanged` | 領域の宣言が変わっていない | 書かれた内容をそのまま使う |
| `applicable` | 宣言が変わったが、書かれた内容が新しい入出力と検証に適合する | 検証を再実行し、通れば使う |
| `conflict` | 入出力・順序・型が変わり、書かれた内容が適合しない。領域が削除された | 生成を止め、領域の識別子と変更点を報告する |
| `unresolved` | 前回の契約が取得できない、照合値が一致しない | 生成を止める |

削除された領域に書かれていた内容を、知らせないまま捨てません。宣言された領域の外で生成物が変更されていた場合も、上書きする前に検出して報告します。

## 4. 要求する保証と縮退（#2096）

生成器は、生成する操作ごとに要求する保証を宣言します。実現先（Provider、Target）は、自分が満たせる能力を宣言します。二つを照合し、不足があれば次のどれかに決めます。

1. 操作を生成しない（例: 競合検出の列が無い表には、更新・削除を生成しない）
2. 操作を拒否する（実行時ではなく、生成・受理の前に）
3. 弱い保証を明示して受理する（人の判断が要る）

どれになったかを、定義と検証根拠の両方に残します。縮退した経路を、縮退していない経路と同等とは認証しません（#1180の禁止する縮退）。能力の不足は、未確認ではなく確認した事実として記録します（P11）。

## 5. 既存設計との関係

| 既存 | 関係 |
| --- | --- |
| #2016 生成器生成 | 生成器の受領記録に、本書の四つの宣言を加える |
| #1975 契約のみからの生成 | 全体生成の完了条件（3.3節）を適用する |
| ADR-0022 AI提案と受理 | 書込み窓は受理の前段で書込み先を限る。受理の仕組みは変えない |
| #2017 作業票 | TEI自身の開発の作業票と、製品の中のAI編集の証跡で、形式を揃える |

| #1180 経路間の同等性 | 縮退した経路の扱いを揃える。業務アプリをAIへ公開する経路（#2093）も、同じ比較単位に乗せる |

## 6. 受入シナリオと否定試験

| 番号 | 内容 | 期待 |
| --- | --- | --- |
| G1 | 拡張点に手書きを置き、再生成を3回繰り返す | 手書きの内容と配置が変わらない |
| G2 | 拡張点の入力の型を変えて再生成する | `conflict`で止まり、領域の識別子が報告される |
| G3 | 生成物の宣言外の箇所を直接編集してから再生成する | 上書き前に検出して報告する |
| G4 | AIが書込み窓の外（権限の判定、データ型）を編集する | 受理前に拒否される |
| G5 | AIが窓を新設しようとする | 拒否され、人の宣言を求める |
| G6 | 大文字小文字だけが違う2つの名前、生成器の接尾辞と一致する名前、予約語、最大長超過 | 受理前に拒否され、衝突した2要素と層が報告される |
| G7 | 競合検出の列が無い表に更新操作を求める | 生成されない、または拒否される。縮退の結果が定義と検証根拠に残る |
| G8 | 全体生成で作った定義を、正本→実現先→正本と往復する | 差分が出ない |
| G9 | 拡張点も書込み窓も空のまま生成する | 既定の実装どおりに動く |

## 7. 結論を出していない範囲

- 書込み可能な領域の宣言を、どの言語の構造で表すか（継承、関数の差し替え、別プロセス）。特定の言語機構は採らない。
- 書込み窓の内側でも、意味・権限・Authorityを変える内容をどう判定するか。最初は人の判断へ戻す。
- 派生名の規則を、生成器とProviderのどちらが所有するか。両方が宣言し、照合はCoreが行う案を有力とするが、ADR-0033の境界との整合は未確認。
- 弱い保証を明示して受理した操作を、後で能力が満たされたときに戻す手順。
- 本書の宣言は、どれも実装・試験で確かめていない。四つの宣言を一つの契約にまとめることで、別々に作る場合より検査が減るかどうかは、最初の適用先で測る。
