## この文書の位置づけ

[#2016](https://github.com/hat47x/tei-platform/issues/2016)は、生成器そのものを版付きの成果物として扱い、同じ期待値で候補を比べる仮説を立てています。そこでは、生成器の入力契約、対象、適合試験を記録します。一方、生成器が**出力について**何を約束するかは、まだ一か所に定まっていません。

この文書は、その約束を四つに分けて扱います。四つはどれも「生成物と、生成物の外にあるもの（利用者の名前、手書きコード、AIの編集、既存データベース）との境界」です。担当課題は四つに分かれていますが、生成器の契約が要求と対象を宣言し、出力の公開・適用前に照合する点で共通しています。意味の受理、実現先への適合、Hostの実行受理は、それぞれの境界で確認します。

この文書は、意味の正本の変更規則を定めません。再利用元の定義の更新と適用先の差分は[再利用した知識の変動点と適用先差分の設計](KNOWLEDGE_VARIATION_DESIGN_2026-10.md)、既存データの移行は[意味の変更に伴う既存データの移行設計](SEMANTIC_CHANGE_DATA_EVOLUTION_DESIGN_2026-10.md)が扱います。

利用者が更新・再生成を続けられるかという評価と、要求・担当・受入候補の対応は[変更の継続性設計](CHANGE_CONTINUITY_DESIGN_2026-10.md)で扱います。本書は生成器の出力契約を具体化する候補であり、Sourceの編集範囲、意味の受理、実行権限を同じ宣言で代替しません。

## 解決したい問題

受注の金額を計算する処理を例にします。受注の項目と導出規則は正本にあり、生成器がその計算のコードを生成します。案件では、得意先ごとの端数処理を手書きで足したいとします。

1. **手書きが消える。** 生成物を直接編集すると、次の再生成で消えます。生成クラスを継承して別の場所に置く方式（Generation Gap）を使えば消えませんが、生成器が基底の署名や呼び出し順を変えたとき、手書き側が壊れる、または黙って呼ばれなくなります。どちらも再生成の時点では分かりません。
2. **AIがどこでも書ける。** AIにこの端数処理を書かせると、端数処理の外（権限の判定、データ型、別の計算）まで変えることがあります。提案と受理を分けても（ADR-0022）、書込み先そのものは限られていないため、変更範囲は事後の差分でしか分かりません。
3. **名前がぶつかる。** 生成器は、項目名から表名・型名・API名を作ります。利用者が付けた名前と、生成器が接尾辞を付けて作った名前が一致すると、生成物が壊れるか、別の要素に黙って結び付きます。大文字小文字を区別しないデータベースやOSでは、区別する層で別だった名前が衝突します。
4. **能力が足りないのに動く。** 版管理列だけを使う生成器が、その列を持たない表へ更新操作を出すと、想定した競合検出が働かず、後勝ちで上書きするおそれがあります。ただし、列の欠落だけで実現先全体の能力不足とは判断できません。同じ保証を満たす別の排他方式があるかは、ProviderとHostの契約・証拠で確認します。X-TEAでは、更新件数の確認や楽観ロックの列名が暗黙の既定になっており、更新件数が0件のときの扱いが機能の型ごとに違っていました。

生成器が、自分の出力の形、付ける名前、要求する能力を宣言すると、事前に照合する対象を固定できます。ただし、実現先の能力や現在の権限は宣言だけでは確定しません。必要な観測を含めて照合し、不足や未確認を公開・適用前に検出します。

## 現在の結論

1. 生成器の契約に、出力についての宣言を四つ持たせる。**派生名の規則**、**拡張点**、**書込み窓**、**要求する能力**である。宣言は機械可読にし、生成器のdigestと版に結び付ける（#2016の受領記録に含める）。
2. 生成物の拡張点と、その拡張実装をAIが編集する書込み窓は、同じ対象・契約の版・実行段階を指す場合に、宣言の共通部分を再利用する案とする。案件実装の所有とAIが編集を許される範囲は別に確認する。生成物外のSourceまで同じ領域へ限定せず、Source編集の制約は対象と操作で宣言する。
3. 再生成のたびに、宣言された領域の契約が前回から変わったかを比べ、手書き・AIの内容が新しい契約に適合するかを検査する。適合しない場合は失敗とし、黙って効かなくしない。
4. 派生名の規則は、生成器とProviderの層ごとに宣言する。選択した実現先について、出力の公開・適用前に全名前を照合する。対象未選択は未評価とし、一つの実現先での不適合を、全実現先に共通の意味の不正とはしない。
5. 操作ごとに要求する保証（競合検出、監査、トランザクション境界など）を宣言し、実現先の能力と照合する。不足または未確認の保証があれば、その操作を実行可能として公開・適用しない。操作を省く構成は対象範囲を明示し、保証を弱める案は別の変更候補として通常の受理へ戻す。承認だけで元の契約への適合にはしない。
6. 書込み窓の外の変更、窓の新設、別の保証を持つ契約への変更は、通常の受理境界（ADR-0022）へ戻す。窓内でも意味や権限が変わる場合は同じ境界を通す。編集範囲の宣言から実行・配備の権限を推測しない。開発作業としてはADR-0035のA3で進め、外部へ取り消せない効果を出す場合だけA4として人に確認する。

最初の適用先は、`order_entry`の導出規則の生成物とし、拡張点1つと書込み窓1つで試します。四つの宣言が既存の機構（#2016の受領記録、#1975の契約のみの生成、#1180の経路間比較）に接続できるかを確かめてから採用を判断します。

## 1. 用語

| 用語 | 内容 |
| --- | --- |
| 生成器の契約 | 生成器が入力として受け取る意味の範囲と、出力について約束する内容。#2016の「入力契約」に、本書の四つの宣言を加えたもの |
| 派生名 | 生成器やProviderが、正本の名前から作る名前（表名、型名、API名、メッセージ名など） |
| 書込み可能な領域 | 生成物のうち、生成器以外が内容を書いてよい箇所。名前、版、入出力、呼ばれる順序、書く主体、必要な検証を持つ |
| 拡張点 | 生成物へ案件固有の実装を結び付ける点。入出力、実行段階、契約の版と案件実装の所有者を追える。実装は人もAIも候補を作れる |
| 書込み窓 | AIが編集を許される対象と操作の範囲。生成物の拡張実装に限る場合は拡張点の情報を参照する。Source全体の編集制約や実行権限とは別に扱う |
| 要求する保証 | 生成した操作が成り立つために実現先に求める能力（競合検出、監査、トランザクション境界など） |
| 縮退 | 能力が足りないときに、生成する操作を減らす、拒否する、弱い保証を明示する、のいずれかを選ぶこと |

## 2. 派生名の規則（#2094）

生成器とProviderは、自分が作る派生名の規則を宣言します。

- 正規化: 大文字小文字の扱い、区切り文字（アンダースコア、ハイフン）を無視するか
- 付加: 生成器が内部で使う接尾辞・接頭辞（一覧用、条件用、明細用などの派生型）
- 制約: 最大長、使える文字、予約語、実行先のOSやデータベースの予約名

選択した実現先について、すべての名前と、その名前から作られる派生名を、各層の正規化で比べます。検査は出力を公開・適用する前に行い、意味変更と実現先を同時に提案する場合は、その提案の受理前にも診断します。実現先が未選択なら、その先での適合は未評価です。

衝突は、原因となる両要素の正本識別子と、実現先・規則の版を付けて報告します。予約語や最大長に対する単一要素の違反は、対象の識別子と違反した規則を示します。名前を意味の正本とせず（P4）、この検査は識別子を変えません。一つの実現先に適合しないという理由で、別の実現先でも有効な意味定義を一律に拒否しません。改名（#1935）の後の名前にも同じ検査を当てます。

## 3. 書込み可能な領域（#2090、#2092）

### 3.1 宣言の内容

生成器は、書込み可能な領域ごとに次を宣言します。

- 名前と版
- 入出力（受け取る値、返す値、型）と、呼ばれる段階・順序
- 書く主体（人、AI、両方）
- 既定の実装（何も書かれていないときの動き）
- 必要な検証（単体試験、経路間比較、往復の一致など）

既定の実装を持たせることで、手書きもAIの編集も無い状態の生成物が、宣言どおりに動くことを確かめられます。

### 3.2 拡張点と書込み窓の関係

| 観点 | 拡張点と案件実装 | AIが編集する書込み窓 |
| --- | --- | --- |
| 新設 | 生成器の版上げとして行う | 生成器の版上げ、または人の宣言で行う。AIは窓を自分で増やせない |
| 宣言した範囲の外の変更が必要になったとき | 別の拡張点または生成器の変更案を作る | AIは範囲外を変更せず、人の判断または別の変更案へ戻す |
| 内容の検証 | 宣言された検証 | 宣言された検証に加え、AIの自己申告を証拠にしない（#2016）。証跡を作業票（#2017）の形式で残す |
| 本番系への適用 | 意味の受理とHostの実行・配備権限を確認する | 同じ境界を使い、レビューも行う。窓の宣言だけで権限を得ない |

この表は生成器の出力を拡張する場合の比較です。生成物外の案件実装は明示的な結び付けと契約で扱い、生成器が上書きしません。Sourceを通常のGit経路で編集する場合は[ADR-0031](../adr/0031-tool-neutral-git-native-development.md)に従い、独自のProposal形式を必須にしません。製品内のAI編集については、基準の版と許す対象・操作を検査し、拡張点の名前だけで許可範囲を決めません。

### 3.3 全体生成との関係

生成器の契約に沿って実装全体の候補を作る使い方もあります（#1975の契約のみからの生成）。この場合も、隔離した候補の作業範囲と禁止する副作用を固定し、無制限の書込みを認めません。次を完了条件の候補とします。

- 本番と分離した開発環境でだけ動かす
- 定義を編集せずに開き直して保存した場合に、意味・識別子・案件拡張を保つ。書式や配置だけの差は別に確認する
- 反映前に変更前の状態を退避し、DDL・全件削除などの破壊的な操作は人の明示の承認まで実行しない

生成したコードやDDLから正本全体を復元できるとは仮定しません。逆変換を評価する場合は、対象形式と保持する情報を先に固定し、結果を観測または変更候補として扱います。派生物から正本を自動更新する経路は設けません。

全体生成で作ったものの改修では、その都度許可対象・操作・基準の版を固定します。限定した編集と構造全体の変更は、同じ意味の検証・受理へ接続し、検証の成功を本番への書込み権限とはしません。

### 3.4 再生成時の判定

再生成のたびに、前回の生成器の契約と今回の契約を、書込み可能な領域ごとに比べます。分類は[再利用した知識の変動点と適用先差分の設計](KNOWLEDGE_VARIATION_DESIGN_2026-10.md)の4章と同じ語を使います。

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| `unchanged` | 領域の宣言が変わっていない | 内容を保全する。依存・選抜結果・失効状態・実行条件を確認してから再利用する |
| `applicable` | 宣言が変わったが、書かれた内容が新しい入出力と検証に適合する | 検証を再実行し、通れば使う |
| `conflict` | 入出力・順序・型が変わり、書かれた内容が適合しない。領域が削除された | 生成を止め、領域の識別子と変更点を報告する |
| `unresolved` | 前回の契約が取得できない、照合値が一致しない | 生成を止める |

削除された領域に書かれていた内容を、知らせないまま捨てません。宣言された領域の外で生成物が変更されていた場合も、上書きする前に検出して報告します。

`unchanged`は無条件の実行許可ではありません。生成器が失効した場合は、過去の成果物・適合結果を履歴として保ち、現在の利用根拠から分けます。失効宣言、承認記録の対象一致、新候補の選抜、Hostの受理は[失効承認の設計案](GENERATOR_REVOCATION_APPROVAL_BOUNDARY_2026-10.md)の境界に従って別々に確認します。

## 4. 要求する保証と縮退（#2096）

生成器は、生成する操作ごとに要求する保証を宣言します。実現先（Provider、Target、Host）の能力を契約と観測条件に照らして確認し、不足と未確認を区別します。列の有無だけで保証の充足を判定しません。満たせない保証が残る場合は次のように扱います。

1. 操作を省く構成を選び、省いた操作と理由を示す。参照・登録も個別の必要条件を確認する
2. 同じ保証を満たす実装が無い、または確認できない場合は、実行可能な操作としての公開・適用を止める
3. 保証を弱める必要があれば、差分と影響を示した別の変更候補を作り、通常の受理へ戻す

どれになったかを、定義と検証根拠の両方に残します。能力を確認できなかった状態を、確認済みの不足に置き換えません。弱い保証の変更案が受理されても、元の契約へ適合したことにはしません。操作を省く構成も、元の全操作へ同等に到達できる経路とは認証しません（#1180）。

| 番号 | 内容 | 期待 |

| G2 | 拡張点の入力の型を変えて再生成する | `conflict`で止まり、領域の識別子が報告される |

| G5 | AIが窓を新設しようとする | 拒否され、人の宣言を求める |
| G6 | 選択した実現先の名前規則への衝突・予約語・最大長違反、別の実現先では有効な名前を与える | 対象と規則の版を診断し、その実現先への公開・適用を止める。対象未選択は未評価。別の実現先でも一律に拒否しない |
| G7 | 版管理列が無い構成に、保証を満たす別実装・不足・能力未確認を与える | 充足・不足・未確認を分ける。不足や未確認の操作を公開・適用しない。弱い保証への承認を元の契約への適合としない |
| G8 | 定義を無編集で開き直して保存する。別に、情報を失う実現先から逆変換を試みる | 無編集保存では意味・識別子・拡張を保つ。逆変換は損失と対象を示す候補とし、正本を自動更新しない |
| G9 | 拡張点も書込み窓も空のまま生成する | 既定の実装どおりに動く |
| G10 | 領域の宣言が同じまま、生成器を失効扱いにする | 内容を保全し、以前の適合結果を現在の利用根拠としない。承認記録の対象一致だけでHostの実行受理を成立させない |

## 7. 結論を出していない範囲

- 書込み可能な領域の宣言を、どの言語の構造で表すか（継承、関数の差し替え、別プロセス）。特定の言語機構は採らない。
- 書込み窓の内側でも、意味・権限・Authorityを変える内容をどう判定するか。機械で確認できる範囲は検証記録で受理し、確認できない範囲だけを既定案として記録して進める。
- 派生名の規則を、生成器とProviderのどちらが所有するか。両方が宣言し、照合はCoreが行う案を有力とするが、ADR-0033の境界との整合は未確認。
- 別の保証を持つ変更案を受理した後に、元の保証へ戻す際の変更・移行手順。
- 本書の宣言は、どれも実装・試験で確かめていない。四つの宣言を一つの契約にまとめることで、別々に作る場合より検査が減るかどうかは、最初の適用先で測る。

### 8.2 標準構造で表す「宣言・解決・観測・消費・受理」

新しい `Pipeline` 専用正本を作らず、既存の型付きRecord/Relation/Graph/Ref・BuildExecution/ArtifactSet/Subject Binding・Source Index・Selectionを再利用する。下表は**比較票の項目候補**であり、採用済みのAPI定義ではない。

| 段階 | 対象として保持するもの | この段階が証明しないこと |
| --- | --- | --- |
| Declared | Accepted Meaning、生成Intent、要求Capability、必要入力・依存・出力・Target・許された書込み範囲 | Providerの存在、全入力の確定 |
| Resolved | exact Generator/Builderと実装bytes・推移依存Pin、Source closure、Plan fingerprint | その実装がOS上で起動したこと |
| Observed | Attempt ID、実Process image/argv、読取/生成/リンクのうち実際に観測した辺、実Artifact member bytes | 観測されなかった工程の不存在、意味適合 |
| Consumed | 実Builder/Bundle/Runtime/Browserが受領したmember、役割、digest、対象Scopeと版 | Provider・Hostの現在権限、業務Effect |
| Accepted/Qualified | 独立Expected・適用版・反例の検証、Owner意味受理、現在の利用資格をそれぞれ参照 | 他Target、他Attempt、将来時点への自動継承 |

「図中になければ無い」は、質問で指定したScope/時点/Consumer/選択された実行経路について必要Source全集合と工程観測の被覆が**閉じたと証明できた場合だけ**の不在主張。未選択・未読込・未観測はunknown/unsupportedを維持する。フィルタや作図の成功を閉包の証明としない。

### 8.3 合成・最適化がグラフ形状を変える場合

宣言した論理Operationを、実BuilderのStepへ常に1対1に割り当てる必要はない。Fusion、部分評価、静的リンク、Pushdown、Cacheや並列化は論理グラフの辺数を変える。ただし、**対応付けの根拠がない消滅辺を最適化扱いにしない**。

1. 変換前のOperator入出力型・NULL/欠損/未取得・順序・多重度・単位・丸め・Effect・時点を契約として固定する。
2. 変換後の物理StepのSource/Artifact/Provider Pinを記録し、どの論理Operation群を実現したかの対応表を作る。多対一・一対多は許しても、未対応の要求は残す。
3. 独立Expectedと既知Mutantで比較する。結果値が偶然一致しても、外部Effect・順序・失敗時の部分成功、Receiptの同一性を省略しない。
4. Safety/Semantic Gate、Target/Physical Gate、実WorkloadのPerformance Gateを区別し、性能利得だけで意味保存を認定しない。正当化できない変換は採用せず元のPlanを使う。

これは汎用Optimizer新設の要求ではなく、[Plugin実現・最適化要件](PLUGIN_REALIZATION_AND_OPTIMIZATION_REQUIREMENTS_2026-11.md)で既に扱う最適化が生成・Build・図表の資格と衝突しないための検収接続である。
