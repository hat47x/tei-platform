# 実行相関と運用診断の設計

## この文書の位置づけ

[製品品質の構成](../../docs/product-quality-architecture.md)の10章は、運用時の計測情報を派生情報とし、「TEIの論理的な識別子 → 運用時の記録との対応付け → 処理の追跡記録・測定値・ログ」という相関を求めています。要求の不足監査も、実行先と本番環境を横断する診断の相関を残る不足に挙げています。しかし、どの識別子をどこで発行し、どの境界でどう受け渡すかを定めた設計はありません。

この文書はその空白を埋めます。製品品質の構成13章が定めるとおり、OpenTelemetryを実行基盤の必須依存先にはしません。TEIが定めるのは識別子、受渡しの規則、記録してよい内容、監査・計測・検証根拠の区別です。計測情報をどの形式で外部へ出すかは、プラグインが担います。

## 解決したい問題

Webの実行先で受注の確定が失敗したとします。運用者は少なくとも次を知る必要があります。

- どの受理済みの意味の版で動いていたか
- どのビルドの、どのプラグインの成果物が呼ばれたか
- データベースへの更新は確定したか、確定しなかったか、不明か
- 後続の観測で、実際の状態はどうだったか

現在の実装では、これらを一つの操作として結び付けられません。

| 場所 | 現状 |
| --- | --- |
| `internal/plugin/runtime/model.go`の`Request` | `RequestID`は呼出元が与える任意の文字列で、発行規則がない |
| 同ファイルの`InvocationProvenance` | プラグイン、ロック、成果物の照合値を持つが、アプリケーション、実行先、受理済みの意味の版、業務操作の識別子を持たない |
| `internal/driver/invocation.go`の`CapabilityInvocation` | 識別子を持たない |
| `internal/driver/observation.go`の`ObservationReadExecution` | 先行するコマンドへの参照を持たない。[ADR-0023](../adr/0023-command-observation-explicit-read-boundary.md)は観測の検証根拠に「先行Commandのidentity / run reference」を求めている |
| `reference/web-composition/go-host/host.go`の`AuditRecord` | 経路、操作、段階、状態、提供元だけを持ち、要求の識別子、時刻、主体の参照を持たない |
| ログ | 起動時に版を一回出力するだけで、要求ごとの記録はない |
| 標準エラー出力 | プラグインの実行環境は標準エラー出力をバイト数と照合値へ縮約する。一方、`internal/query/analyzer/client.go`は生の標準エラー出力をエラー文へ含めており、扱いが揃っていない |

識別子が層ごとに分断されているため、障害の調査は、時刻の近さやログ文字列の検索に頼ることになります。それでは、不明な結果を照会で解消する規則（RQ-020）も運用で使えません。

## 現在の結論

1. 識別子を二系統に分ける。業務操作の識別子は耐久性があり、冪等・競合・不明の解消・監査に使う。処理の追跡用の識別子（W3C Trace Contextの`trace-id`と`span-id`）は標本抽出で欠け得るものとして扱い、参照情報としてだけ記録する。
2. 受理済みの意味の版、実行先のビルド、プラグインのロック、実行方針の照合値は、プロセスごとの構成情報として一度だけ付与する。呼出しごとの記録には、呼出しごとに変わる識別子だけを持たせる。
3. 観測の記録は、先行する業務操作の識別子を必ず参照する。
4. 実行先の境界は信頼境界として扱う。外部から届いた追跡情報は親として採用せず、関連として結び付ける。プラグインのプロセスへは要求の封筒に入れて渡す。
5. 計測情報に入れてよい内容は許可した項目に限る。業務データの値、資格情報、主体の生の識別子は既定で含めない。
6. 監査記録、運用計測、検証根拠を別の記録として扱う。運用計測は検証根拠にならない。
7. 運用者向けの失敗は、安定した診断符号で表す。HTTPではRFC 9457の問題詳細形式へ写す。

## 1. 二系統の識別子

| 系統 | 識別子 | 発行する場所 | 用途 | 欠けたとき |
| --- | --- | --- | --- | --- |
| 業務操作 | 業務操作識別子、実行キー、効果識別子 | [業務副作用の設計](BUSINESS_EFFECT_LIFECYCLE_DESIGN_2026-10.md)の3章 | 冪等、競合、不明の解消、監査、観測との結び付け | 実行を止める。補完しない |
| 業務操作 | 耐久的な実行の識別子（`DurableInvocationHandle`、配備の`RunID`など） | 既存の実装 | 引継ぎと再接続（ADR-0005） | 既存の規則に従う |
| 追跡 | `trace-id`、`span-id` | 計測用プラグイン | 処理時間や呼出し関係の分析 | 欠けても業務処理は続ける |

規則は次のとおりです。

- 業務操作の識別子は、業務結果、実行エラー、観測、監査記録、効果記録に保存する。
- 追跡用の識別子は、業務操作の記録へ参照として書いてよい。ただし、冪等・競合・不明の解消の判定には使わない。
- 業務操作の識別子を、追跡用の識別子から作らない。逆も同じとする。

## 2. 相関の連鎖

```text
プロセスの構成情報（一度だけ付与）
  受理済みの意味の版 / 実行先のビルド / プラグインロック / 実行方針の照合値
        │
業務操作識別子 ─────────────────────────────── 監査記録
  │
  ├─ 実行キー → 呼出しの由来記録（InvocationProvenance）
  │               プラグインの成果物の照合値、資源の貸出しの識別子
  │                 → 提供元の受領記録
  │
  ├─ 効果識別子 → 効果記録 → 配送状態
  │
  └─ 観測（先行する業務操作識別子を参照）
```

一つの業務操作識別子から、受理済みの意味の版、呼び出した成果物、確定状態、確定後効果、観測結果へ機械的に辿れることを目標にします。

## 3. 構成情報

受理済みの意味の版や成果物の照合値は、処理の性質ではなくプロセスの構成です。呼出しごとに繰り返し記録すると、量が増えるうえに、呼出しごとに値が食い違う余地を作ります。

- プロセスの起動時に、次の値を構成情報として固定する。
  - 受理済みの意味の版（判定段階の記録で`R`と呼ぶもの、または共通受理の版）
  - 実行先のビルドの識別値（判定段階の記録で`T`と呼ぶもの）。Goでは`debug.ReadBuildInfo`の版情報と未コミット変更の有無を含める
  - プラグインロックと実行方針の照合値
  - 配備先の環境名
- プラグインのプロセスは、自身の識別子、版、成果物の照合値を自分の構成情報として報告する。呼出しの由来記録には、ロックのどの項目を解決したかを残す。
- OpenTelemetryへ写す場合、`service.name`、`service.version`、`service.instance.id`、`deployment.environment.name`は安定版の意味規約に合わせる。`vcs.ref.head.revision`（リリース候補）や`artifact.hash`（開発中）など成熟度の低い規約を使う場合は、使った規約の版を記録する。意味の版やロックの照合値には共通の規約がないため、名前空間付きの独自属性とする。属性名の接頭辞は採用時に決める。
- 構成情報には照合値と識別子だけを入れ、内容そのものは入れない。

## 4. 境界をまたぐ受渡し

### 4.1 実行先の境界

Web、コマンドライン、外部の呼出元から届いた要求は、信頼境界を越えてきたものとして扱います。

- 外部から届いた`traceparent`は、形式と長さを検査したうえで、新しい追跡の関連（OpenTelemetryのリンク）として結び付ける。親としては採用しない。
- 外部から届いた標本抽出の指示は採用しない。悪意のある呼出元が全件の記録を強制し、費用を増やせるためです。
- 業務操作識別子は、実行環境が発行するか、呼出元が指定した値を範囲付きで受け付ける（業務副作用の設計の3章）。追跡用の識別子からは作らない。

### 4.2 プラグインのプロセス

標準入出力でJSONを交換するプラグインには、追跡情報を要求の封筒の項目として渡します。

- `traceparent`と`tracestate`を、要求ごとの付帯情報の項目として加える。MCPの付帯情報（`params._meta`）で同じ名前の項目を使う仕様（SEP-414）と形を揃える。
- 環境変数`TRACEPARENT`による受渡しは、一回だけ起動して終了するプロセスに限る。長く動くプロセスでは起動時の一回しか読まれず、要求ごとの追跡情報を運べないうえ、同じ計算機上の他のプロセスから読める場合があるためです。
- 業務操作識別子と実行キーは、追跡情報とは別の項目で渡す。現在の`Request.RequestID`は発行規則のない文字列であるため、実行キーとの関係を定めるか、別の項目を設ける。どちらにするかは#1145の要求封筒の設計で決める。
- W3C Baggageは、信頼境界を越えて渡さない。必要な場合も許可した項目だけを渡す。

### 4.3 HTTPとMCP

- HTTPで提供元を呼ぶ場合は、`traceparent`ヘッダーを使う。業務操作識別子は追跡情報とは別のヘッダーで渡す。既存の参照実装には`X-TEI-Request-ID`がある。
- アプリケーションがMCPで業務操作を公開する場合は、`params._meta`の`traceparent`を受け付ける。扱いは4.1と同じとする。

## 5. 記録してよい内容

計測情報と運用ログには、許可した項目だけを入れます。禁止する項目を列挙する方式では、新しい項目が追加されたときに漏れるためです。

既定で記録してよい項目は次のとおりです。

- 実行能力、アプリケーション、問い合わせなど、定義の正本識別子（`sales.order`など）
- 業務操作識別子、実行キー、効果識別子
- 確定状態、業務結果の名前、診断符号
- プラグインの識別子、成果物の照合値
- 処理時間、件数

既定で記録しない項目は次のとおりです。

- 業務データの値（受注番号、顧客名、金額など）
- 資格情報、接続文字列、セッションの識別子、アクセストークン
- 主体の生の識別子。必要な場合は、[CLI C2の開示境界](CLI_C2_DISCLOSURE_BOUNDARY_DESIGN.md)と同じく参照（`principalRef`）を使う
- 値を埋め込んだSQL文。データベースの呼出しは、問い合わせの要約か、パラメーター化したSQL文だけを記録する
- 生の標準エラー出力

照合値（ハッシュ値）に置き換えれば記録してよいとはしません。値の種類が少ない場合、照合値から元の値を推測できるためです。[Capability Invocation Context設計](CAPABILITY_INVOCATION_CONTEXT_DESIGN.md)が指摘するとおり、照合値そのものが呼出元どうしの相関を可能にする場合もあります。

計測情報を外部へ出す前に、プロセスの中で許可した項目以外を取り除きます。収集基盤側の除去処理は二重の防御として使い、唯一の防御にはしません。

## 6. 監査記録・運用計測・検証根拠

| 記録 | 目的 | 欠けてよいか | 保存 |
| --- | --- | --- | --- |
| 監査記録 | 誰が何をいつどの権限で行ったかを後から確かめる | 欠けてはならない。標本抽出しない | 追記のみ、改ざん検知、論理的に分けた保存先、協定世界時の時刻 |
| 運用計測 | 性能や障害の傾向を調べる | 欠けてよい。標本抽出してよい | 計測用プラグインが決める |
| 検証根拠 | 判定段階や受入の判断を支える | 取得手順に従って欠けなく取得する | 対象の版、ビルドの照合値、意味の版、ロック、取得手順の版と結び付ける |

規則は次のとおりです。

- 監査記録は、計測情報の送出経路とは独立に書く。計測情報の標本抽出や送出の失敗で監査記録が欠けないようにする。
- 監査記録を必須とする操作で記録できなかった場合に操作を止めるかどうかは、操作の種類ごとに宣言する。CLI C2の開示境界は、監査が必要な送出で記録できない場合は送出しないと定めている。
- 運用計測を検証根拠として扱わない。運用計測は標本抽出や除去処理で内容が変わるためです。実行時の観測を検証根拠にする場合は、検証根拠の取得手順で、対象の版と取得条件を固定して取得し直す。
- 業務上の拒否は、計測情報では障害として扱わない。実行エラーだけを障害の状態とし、「不明」は独立した値で示す。

## 7. 運用者向けの診断

- 失敗は、安定した少数の診断符号で表す。[段階的な実行変換の設計](CRITICAL_LOWERING_CONTRACT_DESIGN.md)が挙げる候補（`unaccepted-meaning`、`contract-drift`、`missing-execution-context`、`authorization-denied`など）を起点にする。
- HTTPの応答では、RFC 9457の問題詳細形式に写す。`type`は診断符号ごとの固定のURI、`instance`は運用者だけが業務操作識別子へ引き当てられる不透明な値とする。`detail`には内部の構造やスタックトレースを含めない。
- 診断符号と、計測情報の`error.type`属性には同じ値を使う。
- 同じ問題を、外部向けの応答では存在の有無が推測できない表現にし、運用者向けの記録では詳しく残す。外部向けの表現は、既存の開示境界の規則に従う。

## 8. 既存の実装との差

採用する場合は、次の差を個別の変更として解消します。この文書の作成時点では、どれも変更していません。

1. 観測の記録に、先行する業務操作の識別子を加える（ADR-0023の要件との差）。
2. 実行能力の呼出しの記録に、業務操作識別子と実行キーを持たせる。
3. 呼出しの由来記録を、汎用の呼出し記録から辿れるようにする（要求の不足監査が指摘する差）。
4. Webの監査記録に、業務操作識別子、時刻、主体の参照、判断した方針の版を加える。
5. `internal/query/analyzer/client.go`が生の標準エラー出力をエラー文へ含める扱いを、プラグインの実行環境と同じ縮約の規則に揃えるか、編集支援用の内部処理として例外にする理由を記す。

## 9. 受入シナリオと否定試験

| 番号 | 状況 | 期待する動作 |
| --- | --- | --- |
| OC-01 | Webで受注を確定し、後で観測する | 業務操作識別子から、意味の版、ビルド、プラグインの成果物、確定状態、観測結果へ辿れる |
| OC-02 | 外部の呼出元が`traceparent`と全件記録の指示を送る | 新しい追跡を始めて関連として結び付け、標本抽出の指示は採用しない |
| OC-03 | 計測用プラグインを外す、または送出に失敗する | 業務処理と監査記録は変わらない |
| OC-04 | 業務データの値を含む項目を計測情報へ加えようとする | 許可した項目に無いため除去される |
| OC-05 | 確定の応答が失われる | 計測情報では「不明」として独立に示され、業務操作識別子で照会できる |
| OC-06 | 業務上の拒否を返す | 計測情報の障害状態にならない |
| OC-07 | 運用計測だけを根拠に判定段階の合格を記録しようとする | 検証根拠として受け付けない |
| OC-08 | 長く動くプラグインのプロセスへ、要求ごとに別の追跡情報を渡す | 要求の封筒の項目で区別される |

## 10. 結論を出していない範囲

- OpenTelemetryの採用、計測用プラグインの実装、収集基盤の構成は決めていません。
- 独自属性の接頭辞と名前は決めていません。
- 監査記録の保存先、保持期間、改ざん検知の方式は決めていません。
- 業務操作識別子を呼出元が指定する場合の範囲と形式は、[業務副作用の設計](BUSINESS_EFFECT_LIFECYCLE_DESIGN_2026-10.md)と#1145の要求封筒の設計に委ねます。
- 外部規格の状態は2026年10月12日の確認によります。W3C Trace Contextの第1版は勧告、第2版とW3C Baggageは勧告候補です。採用時に再確認します。
- 運用計測の仕組みが動いたことを、本番運用の観測可能性が成立した検証根拠として扱いません。
