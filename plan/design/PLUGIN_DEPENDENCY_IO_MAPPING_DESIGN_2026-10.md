## 現在の結論

1. 依存は「どの契約を必要とするか」だけでなく、「どの項目を、どの出どころから、どの変換で受け渡すか」で宣言する。起動順や実行順は、原則としてこの宣言から導出する。データの受け渡しを伴わない前後関係だけの依存は、理由を必須とする例外にする。
2. 受け渡すデータ項目は、名前の一致や文字列のパスではなく、契約が定める項目の識別子で扱う。型、多重度、欠損の区別、単位と精度、値が確定する時点、機密区分を項目の契約に含める。
3. 業務上の属性を契約の項目へ結び付ける対応付けは、業務の意味についての主張である。構成の設定値として扱わず、提案と受理の境界を通す。接続先や再試行回数のような技術的な調整値とは所有者を分ける。
4. 対応付けに使う変換は、副作用のない演算に限る。失敗、欠損、未確定を保存し、診断を出さずに別の値へ置き換えることはしない。外部参照や状態を伴う変換は、適合試験を持つ変換用の提供元として独立させる。
5. 値の出どころ（契約の既定値、提供元の既定値、構成、環境、呼出し、実行文脈）ごとに所有者と寿命を分ける。後から読み込んだ値を優先する規則は使わない。実行文脈の値は、利用側も対応付けも設定できない。
6. 必須の単一、任意の単一、集合という多重度と、提供元が無いときの振る舞いを、利用側の要求として宣言する。候補が複数あれば推測で選ばず、未解決とする。
7. 同じ論理的な対応付けを、静的な結合では生成した接続コードへ、動的な構成では実行世代の束縛へ具体化する。対応付けやパラメータを変えた場合は新しい世代として準備し、切り替える。
8. 項目の流れを、追跡、影響分析、試験の導出、未使用部分の除去、機密情報の流れの確認に活用する。契約の版が変わったときに、影響を受ける対応付けを機械的に特定できるようにする。

## 本書で使う用語

[名称と用語の指針](../../docs/naming.md)には、利用側、接続、対応付けなどの用語がまだ定義されていない。本書では次の意味で使う。方式を採用する段階で、指針への追加を判断する。

| 用語 | 意味 | 対応する英語の概念名 |
| --- | --- | --- |
| 利用側 | 契約を要求するプラグインや処理 | Consumer |
| 要求 | 利用側が必要とする契約と、その多重度、局所名、不在時の振る舞い | Consumer requirement |
| 局所名 | 同じ契約を別の目的で使うとき、利用側が要求を区別する名前 | requirement name |
| 接続 | 要求へ提供元を割り当てること | binding、wiring |
| 契約の項目 | 契約の要求、結果、失敗を構成する個々の値 | contract item |
| 対応付け | 出どころの値を契約の項目やパラメータへ結び付ける宣言 | mapping |
| 変換 | 対応付けの中で値に適用する演算 | transform |
| パラメータ | 提供元の準備時に確定し、実行世代の一部になる値 | parameter |
| 出どころ | 値を与える者。契約、提供元、構成、環境、上流の出力、呼出し、基盤のいずれか | value source |

| 文脈の受け口 | 契約が宣言し、基盤だけが値を与える項目 | context slot |

## 1. なぜ前後関係だけでは足りないか

受注を確定したら顧客へ通知を送る、という単純な例で考える。

前後関係だけで依存を表すと、「受注確定の処理は通知の提供元に依存する」と書くことになる。そこから分かるのは、通知の提供元を先に準備すること、提供元が無ければ受注確定の処理を有効にしないこと、の二点だけである。

実際に構成するには、次のことも決める必要がある。

- 宛先はどの属性か。受注先の顧客の連絡先か、担当営業か。受注に連絡先が登録されていない場合と、まだ取得できていない場合を同じに扱ってよいか。
- 本文に差し込む金額は、どの通貨と桁で渡すか。提供元が金額を最小単位の整数で受け取るなら、誰が換算するか。
- 宛先の個人情報を外部の配信事業者へ渡してよいか。記録用の提供元へ渡してよいか。
- 二重送信を防ぐための識別値を、どの属性から作るか。
- 配信事業者の接続先と秘密情報をどこで決め、誰が変更できるか。
- 送信者の表示名や再送回数の上限を、案件ごとに変えるのか、環境ごとに変えるのか。
- 通知の提供元が返す配信受付の識別子を、監査記録や後続の観測へどう渡すか。
- 誰の操作として送信したかは、利用側が渡す値ではなく、呼出しを実行する基盤が与える情報である。

これらは前後関係の宣言には現れず、各実装のコードや設定ファイルに散らばりやすい。散らばったままだと、次の失敗が起きる。

- 提供元を交換すると、気づかないうちに項目の意味が変わる。たとえば金額を最小単位で受け取る提供元へ交換し、100倍の金額を通知してしまう。
- 欠損を空文字や0に置き換え、本来は止めるべき送信を実行する。
- 個人情報を記録用の自由記述欄へ流し、閲覧権限の外へ漏らす。
- 利用側が実行者の情報を自分で詰めて渡し、権限の確認をすり抜ける。
- 同じ設定値を複数の場所に書き、読込み順で結果が変わる。
- 契約の版が変わったとき、影響を受ける接続箇所を探せない。

TEIは、標準機能も含めてプラグインを交換し、生成AIが構成案を作ることを前提にしている。そのため、これらを実装者の注意力に任せず、宣言して機械的に検査できる対象にする必要がある。

## 2. 現在の到達点と不足

### 2.1 すでにある仕組み

TEIには、名前から推測しない明示の対応付けが、特定の領域ごとにすでに作られている。本書の方式は、これらの仕組みを残したまま、その考え方をプラグイン間の受け渡しへ一般化する。

### 2.2 不足していること

1. 本番のプラグイン定義に、パラメータや設定の宣言が無い。値の型、既定値、設定できる場所を表せない。
2. 本番の要求と結果に型付きの形が無い。形は#951の参照実装にだけあり、試作の`Contract.Shape`は中身を持たない照合値である。
3. 利用側の値を提供元の項目へ渡す汎用の対応付け、既定値の扱い、変換が無い。対応付けは契約問い合わせ、業務上の結果、資源の参照など、領域ごとに個別に存在する。記述も揃っていない。たとえば`order_entry`の参照パターンでは`input ... -> id`、明細の束縛では`input ... to order_id`と、二つの書き方が使われている。
4. `requires`はパッケージと主版だけを表す。契約への要求、任意の依存、版の範囲を表せない。また現在の解決器は、先に解決した版を後から見直さずに使う。そのため、RQ-032が求める「探索の順序だけを理由に解決不能としない」を満たさない場合がある。
5. 文脈注入のReferenceはあるが、契約の発行権限、Provider適合、実行時の現在権限と結ぶ本番の接続は評価待ちである。
6. 任意のPluginの出力項目を別Pluginの入力項目へ接続し、変換・多重度・依存順序を一緒に検査する汎用の仕組みはない。契約問い合わせの行から次の入力を組み立てる既存経路と、構築成果物のグラフは、対象を限定した先例として扱う。
7. 業務上の属性を提供元の項目へ対応付ける仕組みは、契約問い合わせに限られる。

| SQL named parameterからPostgreSQL placeholderへ | [`BindNamedParameters`](../../internal/database/providers/postgres/query_parameters.go) | SQL文字列やコメント内を避けて`:name`を`$1`へ変換し、同じ名前は同じ位置を再利用する。使われない値・不足値を拒否する | これはProvider固有の通信・実行表現変換であり、業務上の意味対応付けへ混ぜない |
| 名前付きの業務結果 | [`semantic.Outcome`](../../internal/semantic/model.go)、[`workspace`での正規化](../../internal/workspace/loader.go) | Capabilityの結果名とpayload identityを宣言し、Workspace読込みでは結果名で整列する。列挙順を意味として使わない | 既知の結果を名付ける仕組みはあるが、利用側が結果ごとの対応や未対応結果を処理する汎用接続までは確認できない |
| UIの寄与 | [`UI構成キットのReference`](../../reference/ui-customization/composition/README.md) | 差し込み口に対する`provide / replace / decorate`を扱う。差し込み操作は構成の寄与であり、Pluginの型付き入出力契約とは区別されている | 寄与の選択とデータ項目の受け渡しは別の関係として保つ |
| 実行文脈 | [#1118の設計候補](CAPABILITY_INVOCATION_CONTEXT_DESIGN.md)、[文脈注入のReference](../../tools/reference-capability-invocation-context/README.md) | Referenceは要求と分離したHost由来のslotを下流へ渡す。機密slotの直接反射、任意の下流errorやpanicからの露出、終了済みの制御文脈を拒否する。契約要求の発行権限自体は検証しない | 合成Referenceの実装と、本番の契約・現在権限・適合の保証を区別する |

この棚卸しでは、対応付けの分類を直ちに崩す反例は見つからなかった。一方、現行コードは複数の明示対応を個別の所有層に置いており、すべてを一つの汎用Bindingへ統合してはいない。また、読んだfixtureと試験コードは局所的な値の流れを示すだけで、複数Plugin間での一般的な変換、多重度、任意依存の意味、動的世代切替までは実証しない。次のE2では既存型やCore enumを変更せず、これらの境界を保てる最小Referenceを別パッケージで試す。

## 3. 他のOSSから得た知見

2026-10-12に、プラグインや処理の段の間で依存と入出力を扱う19の方式を、各プロジェクトの公式文書で確認した。対象は、拡張機構（Backstage、JupyterLab、OSGi、WebAssemblyの部品モデル、VS Code、Eclipse、Cordis）と、データの流れを持つ仕組み（Gradle、Bazel、Tekton、Terraform、Crossplane、Dagster、CWL、AWS Step Functions、Camunda、NixOS、Helm、Pulumi）である。方式ごとの事実と確認した文書は[調査記録](../research/PLUGIN_DEPENDENCY_IO_OSS_SURVEY_2026-10.md)に置き、ここでは取り入れる点と避ける点だけを示す。方式の優劣を比べるものではない。

### 3.1 取り入れる共通の方式

調査した方式の多くに、次の共通点がある。

1. 受け渡す項目を型付きの識別子で表す。Backstageのデータの識別子、JupyterLabのトークン、Bazelの`provider`、WebAssemblyのインタフェースは、いずれも名前の一致ではなく宣言された識別子で接続する。本書の5.3節に対応する。
2. 受け口に多重度を宣言する。単一、任意、複数を区別し、複数の値があるときの扱いを決める。本書の9節に対応する。
3. 出力の参照から順序を導く。Gradle、Tekton、Terraform、Pulumi、CWLは、出力を入力へつなぐと順序が決まる。データを伴わない順序は別の記法で書き、例外として扱う。本書の8節に対応する。
4. 値の写しと変換を分ける。そのまま写す接続と、変換を伴う対応付けを区別し、変換は閉じた集合か制限された式に限る。本書の6節に対応する。
5. 値の出どころに強さの順を決め、同じ強さの衝突を誤りにする。本書の7.2節に対応する。
6. 構築時と実行時の依存を分ける。Bazelの`cfg`、Terraformの初期化時に確定する値がその例である。本書の4節と8.3節に対応する。
7. 秘密情報は参照として渡し、遅く解決する。Dagsterの環境変数、Camundaの秘密情報、Terraformの`ephemeral`がその例である。本書の7.3節に対応する。
8. 構成時に検査する。型の一致、参照の解決、循環を、実行より前に確かめる。実行時まで検査を延ばすと、Tektonの存在しない結果の参照のように、失敗が実行中に現れる。

### 3.2 TEIで避ける点

次は、調査した文書で注意点として説明されているか、仕組みから生じうる失敗である。各方式の目的や利用場面では妥当な選択であっても、TEIの前提では避ける。

- **読込み順や登録順で優先を決めること。** プラグインの追加や並べ替えで結果が変わる。
- **範囲の外から暗黙に値が入ること。** Helmの`global`や、Camundaのジョブ結果で出力の対応付けが無いときに結果全体が合流する挙動のように、宣言していない値が利用側へ届く。
- **文字列の経路で項目を指すこと。** 型と依存の情報が失われ、誤りが実行時まで分からない。
- **制限の無い式言語を対応付けに使うこと。** 実行時の上限が必要になり、静的な検査と具体化が難しくなる。
- **合わせ方の優先順位が文書や検査で定まっていないこと。** 取り込んだ値が既定値を置き換えるような予想外の結果が起きる。
- **データを伴わない順序制約を多用すること。** 計画が保守的になり、順序の理由が残らない。
- **宣言した契約を実行時や構成時に検査しないこと。** Eclipseのスキーマが開発ツールでしか使われない例、Tektonで宣言した結果の生成を事前に確かめない例がある。

### 3.3 TEIの前提による違い

次の点は、調査した方式の仕組みをそのまま当てはめられないため、TEIの前提から本書が補う部分である。

- **業務の意味の受理。** 調査した方式では、対応付けは構成や設定の一部である。TEIでは、業務上の属性を契約の項目へ結び付ける対応付けを業務の意味の主張として扱い、受理の境界を通す（6.3）。
- **暗黙の選択をしないこと。** OSGiのように版や識別番号で候補を選ぶ規則を持たず、一意に決まらなければ未解決とする（RQ-032）。
- **静的な結合と動的な構成の両立。** 同じ対応付けを、生成した接続コードと実行世代の束縛の両方へ具体化する（11節）。
- **偽装できない実行文脈。** 実行者などの情報は基盤だけが渡し、対応付けの行き先にできない（7.3）。
- **欠損、未確定、取得不能の区別。** CWLやCrossplaneの既定の扱いのように欠損を既定値や処理の省略へ変えることはせず、区別したまま受け渡す（5.2、6.4）。

## 4. 依存の種類を分ける

プラグイン間の関係を一種類の「依存」にまとめると、確定する時点、所有者、検査の方法が混ざる。次の種類を区別する。

| 種類 | 結ぶもの | 宣言する側 | 確定する時点 | 前後関係の扱い |
| --- | --- | --- | --- | --- |
| 契約依存 | 利用側の要求と、その契約を提供する提供元 | 利用側が要求を、提供元が提供を宣言する | 構成時に候補を決め、呼出し時に現在の権限を確認する | 提供元の準備完了が、利用側の準備完了の前提になる |
| 寄与 | 拡張点と、そこへ登録される複数の要素 | 拡張点の所有者が受け口を、寄与する側が登録を宣言する | 構成時 | 寄与の並び順は宣言から決める。読込み順は使わない |
| データ依存 | ある出力項目と、それを使う入力項目 | 対応付け | 経路は構成時、値は出力が確定する時点 | 出力を参照した時点で前後関係が生じる |
| パラメータ依存 | 提供元のパラメータと、その値の出どころ | 提供元が受け口を、構成や環境が値を宣言する | 構成時、配備時、または別の提供元の準備時 | 値の確定は、その値を使う提供元の準備より前に置く |
| 実行文脈 | 契約が宣言した文脈の受け口と、基盤が解決する値 | 契約が受け口を宣言し、基盤が値を与える | 呼出し時 | 利用側からは設定できない |
| 意味依存 | 演算子や意味拡張と、それが前提とする関係・制約 | 意味拡張 | 受理時 | 受理済みの意味集合として固定する |
| 構築依存 | 構築器や生成器と、その入力・出力 | 構築計画 | 構築時 | 実行時の依存へ持ち込まない |
| 配布依存 | 配布単位どうし | 配布一式 | 導入時 | 実行時の依存の唯一の表現にはしない |
| 明示的な順序制約 | データの受け渡しを伴わない前後関係 | 構成 | 構成時 | どの作用の順序を守るためかという理由を必須にする |

ADR-0032は、利用側の要求を契約で表し、パッケージ間の依存を配布上の制約に限ることを決めている。本書の分類は、その「利用側の要求」を、契約依存、寄与、データ依存、パラメータ依存、実行文脈に分解したものである。意味依存は[製品要求RQ-032](../../requirements/TEI_PRODUCT_REQUIREMENTS.md)と意味拡張の課題（ISSUE-000077）、構築依存は#1103と[プラグインの自己構築](PLUGIN_SELF_BUILD_PRODUCTION_CONTRACT_2026-10.md)が担当する。本書では、入出力の扱いが重なる部分だけを扱う。

RQ-032は、拡張が存在するだけで別の拡張の意味が暗黙に変わる方式を標準にしないこと、組合せに新しい意味が必要なら橋渡しの拡張として明示することを求めている。本書の対応付けも同じ立場をとる。二つのプラグインを接続するために意味の変換が必要なら、その変換を対応付けか変換用の提供元として表に出し、どちらかのプラグインの内部へ隠さない。

寄与は一般的な関係の種類として扱う。ただし、置換や装飾のような上書きの操作は、拡張点の所有者が定めたものだけを許す。UI構成キット（#997）の`extends / provide / replace / decorate`を、すべてのプラグインの上書き演算へ広げない。

## 5. 入出力の要素

### 5.1 契約の項目

#951の契約は、要求、結果、失敗の形を持ち、その全体を照合値で識別する。本書では、その形を構成する個々の値を**契約の項目**として識別できるようにする。項目の識別子は、契約の識別子と主版、契約内での経路から作る。たとえば`notify.message@1`の宛先は`notify.message@1/recipient`のように表す（書式は未決定）。

項目は、役割によって次に分かれる。

| 役割 | 値を与える者 | 例 |
| --- | --- | --- |
| 入力項目 | 利用側（対応付けを通す） | 宛先、本文の差し込み値 |
| 意味上の文脈 | 利用側。結果の意味に関わる | 対象の案件、基準時点 |
| 実行文脈の受け口 | 基盤だけ | 実行者、要求の期限 |
| 出力項目 | 提供元 | 配信受付の識別子 |
| 名前付きの結果 | 提供元 | 受付済み、宛先不正による拒否 |
| 実行時の失敗 | 提供元または基盤 | 接続不能、期限切れ |
| パラメータ | 構成、環境、または別の提供元の準備時の出力 | 送信者の表示名、接続先、再送回数の上限 |

意味上の文脈と実行文脈の区別は、#1118の「意味上の要求」「意味上の文脈」「実行文脈」の三分類に従う。名前付きの結果と実行時の失敗の区別は、[業務上の結果の設計](CAPABILITY_OUTCOME_V1_DESIGN.md)に従う。

パラメータは、呼出しごとの入力とは別のものとして扱う。パラメータは提供元の準備時に確定し、実行世代の一部になる。呼出しのたびに変わる値をパラメータにすると、同じ世代の中で振る舞いが変わり、追跡できなくなる。

### 5.2 項目の属性

各項目には、接続の可否を判定するために次の属性が必要になる。正本となる型や業務モデルから導出できる属性は導出し、手書きを求めない。手書きの項目を増やすより、正本の重複を減らすことを優先する。

| 属性 | 内容 | 欠けると起きる失敗 |
| --- | --- | --- |
| 型 | 文字列、整数、10進数、日時、識別子の参照、構造、列など | 形が合うだけで接続する |
| 多重度 | 一つ、任意、複数。複数なら集合か、重複を許す列か | 複数の値から一件を診断なしに選ぶ |
| 欠損の区別 | 値が空であること、項目が無いこと、取得できないこと、未確定であることの区別 | 欠損を空文字や0に置き換える |
| 単位と精度 | 通貨と桁、長さの単位、丸め方 | 金額の桁を取り違える |
| 確定する時点 | 構築時、構成時、配備時、準備時、呼出し時のどこで値が決まるか | まだ決まっていない値に依存した構成を作る |
| 鮮度 | いつ時点の値か、どれだけ古くてよいか | 古い観測を現在の値として使う |
| 同一性 | 何を識別するキーか、どの範囲で一意か | 別の範囲の識別子を混ぜる |
| 機密区分 | 個人情報、秘密情報、公開可など | 記録用の欄へ個人情報を流す |
| 既定値の所有者 | 契約、提供元、なし | 提供元ごとに既定値が違い、交換で意味が変わる |
| 由来の記録 | 値の出どころを観測記録へ残す必要があるか | 監査で値の出どころを示せない |

欠損の区別は、[DSL演算子の設計候補](DSL_OPERATOR_PLUGIN_COMPOSITION_DESIGN.md)が演算子に求める区別と同じものを、プラグイン間の受け渡しにも適用する。

### 5.3 項目の同一性と名前

項目の同一性は契約の中で決まる。業務上の属性の識別子（たとえば`sales.order.total_amount`）とは別のものである。

同じ名前でも意味が同じとは限らない。受注の`amount`が税込みの円の整数で、決済の提供元の`amount`が通貨の最小単位の整数であれば、名前が同じでも接続できない。逆に、名前が違っても同じ契約の同じ項目なら、対応付けは要らない。

そのため、名前の一致による自動接続はしない。生成AIや編集支援が名前や型の近さから対応付けの候補を出すことは認めるが、それは提案であり、受理の根拠にはしない。

## 6. 対応付けの方式

### 6.1 四つの置き場所

ある値を、別の契約の項目へ渡す方法は四つある。

| 置き場所 | 内容 | 使う場面 | 条件 |
| --- | --- | --- | --- |
| 同一契約の接続 | 利用側と提供元が同じ契約の項目を共有する。対応付けは不要 | 標準の契約をそのまま使う | 版の範囲が一致すること |
| 宣言的な対応付け | 出どころの値を、契約の入力項目へ結び付け、許可された変換を指定する | 業務上の属性を汎用の契約へ渡す。ある提供元の出力を次の入力へ渡す | 変換は副作用のない演算に限る |
| 変換用の提供元 | 契約Aを、契約Bを使って実装する独立した提供元 | 構造が大きく異なる。外部参照や状態を伴う | それ自身の適合試験を持つ |
| 提供元の内部 | 提供元が、外部製品のAPIの形へ値を変換する | 物理的な実現の詳細 | 契約の意味を変えないこと。追跡の対象外であることを明示する |

業務上の意味を持つ値の受け渡しは、提供元の内部に隠さず、宣言的な対応付けか変換用の提供元で表す。外部製品に固有の形式への変換は、提供元の内部で行う。境界を引く理由は、提供元を交換したときに意味が変わらないことを、対応付けと契約の照合だけで確かめられるようにするためである。

### 6.2 対応付けの記録に残すもの

一つの対応付けは、少なくとも次を持つ。

| 要素 | 内容 |
| --- | --- |
| 行き先 | 契約の入力項目、またはパラメータ |
| 出どころ | 業務上の属性、上流の出力項目、パラメータ、定数のいずれか |
| 変換 | 使う演算の識別子と版。変換しない場合は恒等であることを示す |
| 欠損時の扱い | 停止する、名前付きの結果として返す、契約が定める既定値を使う、のいずれか。指定が無ければ停止する |
| 機密区分の照合 | 出どころの区分を、行き先が受け付けるかどうか |
| 種類 | 意味の対応付けか、技術的な調整か |
| 受理の状態 | 提案、受理済み、無効化のいずれか |
| ソース上の位置 | 診断と追跡のための記述位置 |
| 照合値 | 上記の内容から算出した値。実行世代と観測記録から参照する |

出力の側でも、対応付けた項目だけを利用側へ渡す。提供元の結果全体を利用側の範囲へ暗黙に合流させることはしない。利用側が受け取る値を宣言した項目に限ると、提供元が出力項目を増やしても利用側に予期しない値が届かない。個人情報のような機密区分のある値が、必要のない処理へ流れることも防げる。

契約問い合わせの先例（2.1）と同じく、名前が同じ項目どうしでも対応付けを省略しない。省略を認めると、名前の一致による暗黙の接続と区別できなくなるからである。記述量を減らす必要がある場合は、記述を省略する代わりに、同一契約の接続（6.1）として扱えるよう契約を揃える。

### 6.3 意味の対応付けと技術的な調整を分ける

「通知の宛先は受注先の顧客の連絡先である」は業務上の判断である。この対応付けを変えると、誰に何が届くかが変わる。そのため、正本は案件の受理済みの意味の側に置き、[ADR-0022](../adr/0022-ai-proposal-canonical-acceptance-boundary.md)の提案と受理の境界を通す。

「再送の上限は3回」「接続の待ち時間は5秒」は技術的な調整である。業務の意味を変えない範囲で、構成や環境が所有する。

境界が曖昧な例として、通知の言語がある。顧客の言語属性から決めるなら意味の対応付けであり、全顧客に固定の言語を使うなら構成の値である。判定の規則は次のとおりとする。

- 値が業務上の属性から導かれる場合は、意味の対応付けとする。
- 値の違いが業務上の結果や利用者から見える内容を変える場合は、意味の対応付けとする。
- どちらでもない場合だけ、技術的な調整として構成や環境に置ける。

[案件構成の設計候補](PROJECT_PLUGIN_COMPOSITION_DESIGN.md)が定める「構成の選択、意味の受理、実行の許可は別」という原則を、対応付けにも適用する。構成プロファイルに意味の対応付けを書いて、受理済みの意味を上書きすることは認めない。

### 6.4 変換に許す演算

対応付けの変換には、既存の閉じた演算の集合を使い、対応付けのためだけに別の式言語を作らない。式言語を広げるほど、検査、静的な具体化、影響分析が難しくなるからである。候補は次の二つである。

- **構造の変換**：項目の選択、構造の組立て、列の各要素への適用など、値の意味を変えずに形だけを変える変換。既存の`internal/plugin/transform`の閉じた中間表現（`select-field`、`construct-object`、`map-array`など）が候補になる。ただし現在は構築器への入力のための仕組みであり、値が空であることと項目が無いことの区別を実行時のデータでどう扱うかは評価していない。
- **意味の変換**：丸め、単位の換算、値の導出など、値の意味に関わる変換。[DSL演算子の設計候補](DSL_OPERATOR_PLUGIN_COMPOSITION_DESIGN.md)の意味契約を持つ演算のうち、副作用のないものを使う。

どちらの集合を使うか、二つを一つにまとめるかは、E3（15節）の結果を見て決める。

許す変換の条件は次のとおりである。

- 副作用を持たない。外部の読取り、現在時刻の参照、乱数を使わない。現在時刻が必要なら、実行文脈か入力項目として受け取る。
- 失敗を明示する。丸めや桁あふれ、変換不能を、別の値で埋めずに失敗として返す。
- 欠損と未確定を保存する。未確定の値を変換した結果は未確定のままにする。
- 演算の版を固定する。演算の意味が変わったら、対応付けの照合値も変わる。

為替換算のように外部の値を使う変換は、この条件を満たさない。換算率を提供する契約の出力を入力に加えるか、換算を担う変換用の提供元を置く。

### 6.5 型の適合判定

出どころと行き先の型を照合した結果を、次の五つに分ける。

| 判定 | 例 | 扱い |
| --- | --- | --- |
| 同一 | 同じ契約の同じ項目 | 接続できる |
| 安全な拡大 | 精度を失わない整数から10進数への変換。必須の値を、任意を受け付ける項目へ渡す | 接続できる。判定結果を記録する |
| 条件付き | 10進数から整数への変換。任意の値を必須の項目へ渡す。長さに上限がある文字列へ渡す | 明示の変換と、失敗時・欠損時の扱いを要求する |
| 不適合 | 通貨や単位が違う金額。範囲の違う識別子 | 拒否する |
| 判定不能 | 型の情報や単位が欠けている | 未判定とし、接続できるとは扱わない |

判定不能を「制約なし」と推定しない。これは[AI向けの最小プラグイン規約](https://github.com/hat47x/tei-platform/pull/1233)が「未調査を制約なしと推定しない」としている原則と同じである。

## 7. パラメータと値の出どころ

### 7.1 出どころごとの所有者

| 出どころ | 所有者 | 寿命 | 例 | 照合値への影響 |
| --- | --- | --- | --- | --- |
| 契約の既定値 | 契約 | 契約の版 | 既定では再送しない | 変更は契約の変更として扱う |
| 提供元の既定値 | 提供元 | 提供元の版 | 内部の接続数 | 観測できる振る舞いを変えるなら開示を求める |
| 構成の値 | 案件 | 構成の版 | 送信者の表示名 | 構成の照合値に含める |
| 環境の値 | 環境 | 配備 | 接続先、秘密情報の参照 | 環境の束縛に含める。秘密情報の値は含めない |
| 別の提供元の準備時の出力 | その提供元 | 実行世代 | 適用済みの表の版、払い出された接続先 | 世代の束縛に含める |
| 呼出しの値 | 利用側 | 一回の呼出し | 宛先、本文の差し込み値 | 意味上の要求に含める |
| 実行文脈 | 基盤 | 一回の呼出し | 実行者、要求の期限 | 利用側からは設定できない |

業務の意味を変えるパラメータは、環境の値として置けない。#951が「環境の違いで受理済みの意味の妥当性を変えない」としているためである。たとえば金額の丸め方は、契約の項目の属性か意味の対応付けとして扱い、本番環境だけ別の丸め方にすることは認めない。

### 7.2 優先順位の決め方

構成ファイルの読込み順や、後から適用した差分が勝つ規則は使わない。プラグインの追加や読込み順の変更で、気づかないうちに値が変わるからである。代わりに次の規則を候補とする。

1. パラメータごとに、値を設定してよい出どころを契約または提供元が宣言する。たとえば秘密情報の参照は環境だけ、送信者の表示名は構成だけ、再送の上限は構成と環境、のように決める。
2. 出どころの間の強さは固定の順にする。契約の既定値、提供元の既定値、構成、環境の順に後者が強い。任意の数値で優先度を指定する仕組みは設けない。
3. 同じ出どころの中で同じパラメータに二つの値があれば、衝突として停止する。どちらかを選ばない。
4. 実際に使われた値が、どの出どころから来たかを記録する。「既定値をそのまま使った」と「既定値と同じ値を明示した」を区別できるようにする。

この規則では、ある環境だけ値を変える必要がある場合も、そのパラメータが環境からの設定を認めている限り表現できる。認めていないパラメータを環境から変えようとした場合は、設定の誤りとして診断する。

### 7.3 秘密情報と実行文脈

秘密情報のパラメータは、参照だけを受け付ける。値は実行時に資源の仲介役（Resource Broker）が解決する。構成、実装固定情報、対応付けの記録、診断、観測記録には値を含めない。

実行文脈の受け口は、#1118に従って契約が宣言する。対応付けの行き先に実行文脈の受け口を指定することは認めない。利用側の要求に実行文脈の値を含めることも認めない。静的に結合する場合も、実行文脈は基盤から渡す経路を残す。

## 8. 依存グラフと順序の導出

### 8.1 グラフを分ける

[Cordis由来の評価](CORDIS_CONTINUOUS_PLUGIN_UPDATE_EVALUATION_2026-10.md)は、所有関係と配置・契約依存を別のグラフにするとしている。入出力を加えると、次のグラフを区別することになる。

| グラフ | 節点 | 辺 | 用途 | 循環 |
| --- | --- | --- | --- | --- |
| 構成のグラフ | 提供元と利用側の要求 | 契約依存の束縛、準備時の出力からのパラメータ | 準備と起動の順序、撤去の影響範囲 | 拒否する（現在の試作と同じ） |
| データの流れ | 呼出しの段と項目 | 対応付け | 一回の呼出しの中の実行順序、値の追跡 | 拒否する。反復は契約の内部で表す |
| 寄与のグラフ | 拡張点と寄与 | 登録 | 集合の構築 | 拡張点が自分への寄与に依存する形は拒否する |
| 構築のグラフ | 構築の段 | 構築の入力と出力 | 構築の順序 | 拒否する。段階的な初期構築は別の段として表す |
| 所有のグラフ | 作用の範囲 | 親子 | 解放の順序 | 木に限る |

### 8.2 出力の参照から順序を導く

出力項目を参照する対応付けを書いた時点で、その出力を生む側が先、参照する側が後という順序が決まる。利用者が別途「後に実行する」と書く必要はない。

順序だけの制約は、データの受け渡しで表せないかをまず検討する。たとえば「表の移行を適用してから受付を始める」は、移行の提供元が準備時に「適用済みの表の版」を出力し、受付の提供元がその値をパラメータとして受け取る、と表せる。こう表すと、順序の理由が値として残り、適用済みの版が要求を満たすかも検査できる。

どうしても順序だけが必要な場合は、明示的な順序制約として書き、どの作用の順序を守るためかを理由として必須にする。順序制約は診断と影響分析の一覧に表示し、増え続けていないかを確認できるようにする。

順序は登録順に依存させない。現在の試作でも、提供元の識別子を整列してから評価している。[重要契約の段階的な具体化](CRITICAL_LOWERING_CONTRACT_DESIGN.md)でも、実行時の依存の順序を正規化し、登録順だけで計画の照合値が変わることを防いでいる。

### 8.3 確定する時点を照合する

値には確定する時点がある。構築時、構成時、配備時、準備時、呼出し時の順に後になる。ある時点で確定していなければならない値を、それより後に確定する出どころから受け取ることはできない。

たとえば、静的に結合する実行先で、構築時に決める必要のある設定を、別の提供元の準備時の出力から受け取ることはできない。この組合せは構成時に検出し、未解決として停止する。動的な構成へ暗黙に切り替えて解決しない。

## 9. 多重度・不在・競合

### 9.1 多重度

| 多重度 | 意味 | 提供元が無い場合 | 候補が複数ある場合 |
| --- | --- | --- | --- |
| 必須の単一 | ちょうど一つ | 利用側を不適格とする | 明示の選択が無ければ未解決とする |
| 任意の単一 | 0または1 | 利用側が宣言した振る舞いをとる | 明示の選択が無ければ未解決とする |
| 集合 | 0以上 | 空集合として渡す | すべてを渡す。並び順は宣言で決める |

現在の試作の`Dependency`は、必須の単一だけを表している。任意の単一と集合は、本書で追加を検討する範囲である。

### 9.2 任意の依存では不在時の振る舞いを宣言する

任意の依存では、「提供元が無いときに何をするか」を利用側の要求に書く。何も書かずに処理を飛ばすことは認めない。通知の例であれば、「通知できなかったことを観測記録に残し、受注確定は続ける」のように書く。

権限の確認、監査、検証など、安全に関わる要求は任意にできない。これらを任意として宣言した構成は、宣言の時点で拒否する。

### 9.3 利用側の局所名で区別する

同じ契約を別の目的で複数使う場合は、利用側の局所名で区別する。たとえば業務用のデータベースと監査用のデータベースは、どちらも同じデータベース契約を使うが、利用側の要求としては`business`と`audit`のように別の名前を持つ。どの提供元をどの局所名へ割り当てるかは、構成が決める。

この考え方は、現在の参照実装の`datasource`別名と同じである。`order_entry`では`sales`と`master`という別名が、環境ごとの具体的なデータベースの実体とは別に宣言されている。

### 9.4 集合の並び順と衝突

集合で受け取る寄与の並び順は、寄与が宣言した順序のキーか、構成の明示の並びで決める。同じ順序のキーを持つ寄与が二つあれば、衝突として診断する。読込み順や登録順で並べない。

[Webアプリケーション構成キットの設計候補](WEB_APPLICATION_COMPOSITION_DESIGN.md)は、HTTPの処理点に入力と出力、前後条件、効果を宣言させ、登録順の優先度に依存しない方針をとっている。集合の並び順の規則は、これを一般化したものである。

## 10. 版の変化と互換性

契約の版が変わったとき、影響を受ける対応付けと利用側を次のように判定する。

| 変化 | 利用側への影響 | 対応付けへの影響 |
| --- | --- | --- |
| 任意の入力項目の追加 | 互換 | 影響なし |
| 必須の入力項目の追加 | 非互換 | 既存の対応付けを不足として再検査する |
| 出力項目の追加 | 多くの場合は互換 | 参照していなければ影響なし |
| 名前付きの結果の種類の追加 | すべての種類を扱う利用側には非互換 | 結果ごとの分岐を持つ接続を再検査する |
| 型の拡大・縮小 | 向きによる | 型の適合判定をやり直す |
| 単位、精度、欠損の扱いの変更 | 非互換。別の意味として扱う | すべての対応付けを再検査する |
| 契約の既定値の変更 | 振る舞いが変わる | 既定値に頼っている接続を再検査する |
| 同一性を保った項目の改名 | 互換 | 表示だけを更新する |

再検査の結果は、案件構成の設計候補が定める`unchanged / applicable / conflict / unresolved`の分類で示す。自動で採用したことにはしない。

名前付きの結果の種類が増えることを互換とみなさない点に注意が必要である。新しい種類を知らない利用側は、それを別の結果として誤って扱うおそれがある。

## 11. 静的な結合と動的な構成での具体化

ADR-0032は、同じ契約を静的にも動的にも実現するとしている。対応付けも同じ論理的な宣言から、実行先に応じて具体化する。

- **静的な結合**：解決済みの接続と対応付けから、直接の呼出しと変換のコードを生成する。実行時に対応付けを解釈する機構、依存の監視、動的な読込みを成果物に含めない。生成したコードには、元の対応付けの照合値を記録する。参照されない出力項目を生む処理や、使われない提供元は、意味を変えない範囲で除去できる。
- **動的な構成**：実行世代の束縛に、提供元と成果物に加えて、対応付けとパラメータの照合値を含める。対応付けの変更は、新しい世代の準備、準備完了の確認、切替、旧世代の処理の完了待ちとして扱う。呼出し中の処理は、開始時の世代の対応付けで完了させる。
- **WebAssemblyの部品構成**：契約の項目をインタフェースの型として表し、ある部品の提供を別の部品の要求へ構成時に接続する方式を候補とする。外部の部品構成の仕組みを採用するかどうかは、実行先の評価で決める。
- **通信**：対応付けは意味上の値に対して行う。通信の符号化（#1145）とは分け、通信手段を変えても対応付けを変えない。

## 12. 対応付けの情報を活用する

対応付けを宣言として持つと、次の作業に使える。いずれも宣言から導出する派生情報であり、第二の正本にはしない。

| 活用 | 内容 |
| --- | --- |
| 影響分析 | 契約の版、業務上の属性、演算の版が変わったとき、影響を受ける対応付けと利用側を列挙する |
| 試験の導出 | 対応付けごとに、欠損、境界値、単位、機密区分の正負の試験を導出する。提供元を交換したときの回帰試験に使う |
| 機密情報の流れの確認 | 個人情報や秘密情報が、どの項目を通ってどの提供元へ届くかを一覧にし、受け付けない項目への流れを拒否する |
| 未使用部分の除去 | 静的な結合で、参照されない項目、提供元、変換を成果物から除く |
| 構成の一覧の生成 | パラメータの型、設定できる出どころ、既定値、実際の値の出どころを、正本から生成した一覧として示す |
| 生成AIの支援 | 型、単位、機密区分が合う対応付けの候補を提案する。提案は受理の根拠にしない |
| 観測と追跡 | 呼出しの観測記録に、どの世代とどの対応付けの照合値で動いたかを残す。機密区分のある値そのものは記録しない |

構成の一覧を正本から生成する案は、[AI向けの最小プラグイン規約](AI_NATIVE_PLUGIN_COMPOSITION_DESIGN_2026-10.md)の第8節でも検討している。

## 13. 概念例：受注確定の通知

次は、本書の要素を説明するための概念例である。現在のTEIで読み込める記述ではなく、記述構文の提案でもない。

通知の契約は、入力項目、実行文脈の受け口、出力項目、名前付きの結果、パラメータを宣言する。

```yaml
# 概念例：通知の契約
contract: notify.message@1
input:
  recipient:  { type: contact.address, required: true, classification: personal }
  template:   { type: template.ref, required: true }
  amount:     { type: money, required: false }
  dedupe_key: { type: text, required: true }
context_slots: [principal, deadline]
output:
  accepted_id: { type: text, determined: invocation }
outcomes: [accepted, recipient_rejected]
parameters:
  sender_name: { type: text, settable_by: [profile] }
  endpoint:    { type: resource.ref, settable_by: [environment] }
  api_key:     { type: secret.ref, settable_by: [environment] }
  max_retry:   { type: integer, default: 0, settable_by: [profile, environment] }
```

受注確定の処理は、利用側の局所名`customer_notice`で通知を要求し、意味の対応付けを宣言する。この部分は業務の意味なので、受理の対象になる。

```yaml
# 概念例：利用側の要求と意味の対応付け
requirement: customer_notice
contract: notify.message@^1
cardinality: optional
when_absent: record-and-continue
mapping:
  recipient:  sales.order.customer.contact_email
  template:   const(template.order_confirmed)
  amount:     sales.order.total_amount
  dedupe_key: derive(sales.order.id, "confirmed")
on_missing:
  recipient: outcome(not_notifiable)
```

構成と環境は、提供元の割当てと技術的な調整だけを持つ。

```yaml
# 概念例：構成と環境
binding:
  customer_notice: provider tei.notify.smtp
parameters:
  sender_name: "受注センター"
environment.production:
  endpoint: resource:mail.outbound
  api_key:  secret:mail.api_key
  max_retry: 3
```

監査の処理が`customer_notice`の`accepted_id`を参照すると、通知が先、監査が後というデータの流れが導出される。

この例で行う検査は次のとおりである。

- `recipient`は個人情報であり、通知の契約の宛先項目は個人情報を受け付けると宣言しているので接続できる。監査の自由記述欄へ宛先を流す対応付けは拒否する。
- `amount`は受注の金額と通知の金額がどちらも通貨付きの金額型なので、同一または安全な拡大として接続できる。金額を最小単位の整数で受け取る提供元へ交換した場合は、条件付きの判定になる。通貨の桁の規則を固定した換算の演算を明示しない限り、接続を拒否する。
- 連絡先が無い受注では、空文字を渡さず`not_notifiable`という結果にする。
- `principal`と`deadline`は基盤が渡す。利用側の対応付けには現れない。
- `max_retry`は構成では既定値の0のままで、本番環境だけ3にしている。このパラメータは環境からの設定を認めているので有効である。`sender_name`を環境で変えようとした場合は、設定の誤りとして診断する。
- 通知の提供元が無い構成でも、`when_absent`の宣言に従って受注確定は有効なままである。通知が監査の要求だった場合は任意にできないので、構成の時点で拒否する。

| 候補 | 位置付け・優先 | 少なくとも保持・検証すべき意味 | 先に使う実Consumer |

### 17.4 型付きパイプラインの可視性と限界

Source/Authoring Graph → Resolved/Lowered Graph → Targetの実行・観測という関連を同じ図に示しても、**それぞれ異なる証拠**として保持する。#2298（2026-11-03 UTCにmerge済み）§15の限定保証（`PlanClosed`、`EffectConfined`、`GraphTraceConformant`）を再定義せず、I/O Mapping側では次の対応に限定する。

- すべてのMapping Edgeはproducer slot/field、consumer slot/field、Contract identity/shape、TypeRef、Source/Accepted revisionの参照を**表示可能**にする。Name一致でEdgeを生成しない。
- Generator/変換は入力と出力に加え、宣言されたOperator/Provider、Stage、Loss（保持/明示変換/非可逆/未証明）、Error/Unknownを可視化する。隠れた変換、暗黙の欠損値補完、欠落Edgeの黙認をしない。
- Opaque Providerの内部を全展開できない場合はOpaque Nodeと許可Effectの境界を表示する。「図に存在しないから内部副作用も絶対ない」とは主張しない。強制できないEffectと未観測経路はUnresolvedである。
- Build-only dependencyとRuntime dependency、BusinessのRelation graphとService coeffect graphは別種類のEdgeとする。型の同一性から依存/実行順を推測しない。

### 17.6 二つの独立Consumerでの実証を一つの受入票に接続する（2026-11-06、設計候補）

**焦点**：既存の標準データ構造を使った非画面PipelineとTEIセルフビルドを、同じ*型付き辺の検査原理*で扱えるかを測る。これは新しい共通Pipeline Runtimeや固定 `std.dataset` / `tei.std.artifact` の採用ではない。既存Ownerは [#2620](https://github.com/hat47x/tei-platform/issues/2620)（標準構造・Role）、[#2827](https://github.com/hat47x/tei-platform/pull/2827)（ETL/ELT・MFT、Draft）、[#2831](https://github.com/hat47x/tei-platform/issues/2831)（Self-build P0）、[#1223](https://github.com/hat47x/tei-platform/issues/1223)（Composition I/O）を維持する。

| 二つのConsumer | 共通に表示・照合する辺 | それぞれ独立に必要な証拠 | 混同すると生じる誤認 |
| --- | --- | --- | --- |
| File/ETL：Source→Transform→Sink | 入出力Field/Shape、Semantic TypeRef、Multiplicity、NULL/Unknown、Producer、Operator/明示Adapter、Source Revision | 原バイト列・encoding/record boundary、Snapshot/Checkpoint、受取側の実byte確認、重複/partialと業務更正の扱い（#2542） | `std.binary`の一致を配送完了・Exactly-once・lossless変換へ昇格 |
| Self-build：Seed/Source→Builder→Artifact | 同じ型付きPort/Source依存、Build-only/Runtime Edge、Producer、Target、Artifact Role、変換の入力/出力 | 実消費Source closure、toolchain/engine、実command、exact output bytes/digest、stage1/2比較、未宣言工程の検出（#2831） | Artifact digestの一致をBuild Graph完全性・Seed Trust・実行権限へ昇格 |

**受入票に保持する最小列（新たなCanonical Schemaではない）**：Consumer/Target、型付きSource・SinkのContract/Field、TypeRef＋その定義を選んだSemantic Set、Cardinality/Null/Unknown、Value/Build/Effect Edge種別、選択Provider/Operator・版、Input/Outputの内容同一性、Source Closureの確認範囲、Independent Expected/Observed、現在のAuthority Owner、未確認事項。TypeRefと構造の検査を担う統合済み[#2584](https://github.com/hat47x/tei-platform/pull/2584)の**返す判定は合成された設計時候補のみ**。実際のE2EやProject Acceptanceを報告しない。

**横断する不成立条件**：Reference Workspaceの `validate=ok` だけでは未知Source root・未読込ファイルの不存在を証明しない（[#2823](https://github.com/hat47x/tei-platform/issues/2823)）。同じIDの文字列でも異なるAccepted意味版やScopeは同一視しない。Hash由来IDの文字種・長さの試作（[#2814](https://github.com/hat47x/tei-platform/issues/2814)）は、Semantic ID・Artifact digest・Checkpoint/Operation IDを自動的に兼用させる根拠ではない。`tei.std.*` の管理名前空間はRQ-008で採用済みだが、実装に残る `std.*` 型IDの暗黙移行は禁止する。

**反証順序**：まず既存E2aで `std.binary` / `std.text` / `std.json` と異種TypeRefを合成比較する（File relayとBuild metadataを模したfixtureであり実Consumerではない）。次に #2831 の **P0-SB-A**（宣言Graph対実消費）を先行し、並行して #2827/#2542 の既存File/Message試験結果を一つの受入票へ対応付ける。差分が「型の不足」なのか「Role/Scope/Effect/Source Closureの不足」なのかを独立診断できた場合だけ標準構造の追加を #2620へ返す。二つの用途で同じMeaningと保証を再利用できなければ新標準TypeKind化を撤回する。

**証拠状態**：2026-11-06時点のGitHub静的照合に基づく設計提案。共通テストハーネス／実ETL配送／TEI全体セルフビルド／本番のAcceptance・Authorityは、この追補だけでは**NOT RUN / NOT PROVEN**。既存CIや部分ReferenceのPASSを縦断PASSへ加算しない。


### 17.7 型付き辺と「閉包・不在・実効果」のClaim相対判定（2026-11-06、設計候補）

**新規の型体系ではなく受入票の判定規則。** [#2620](https://github.com/hat47x/tei-platform/issues/2620)のRole Required Shape/Source閉包、[#2831](https://github.com/hat47x/tei-platform/issues/2831)のセルフビルドP0-A0/A1、[Draft #2881](https://github.com/hat47x/tei-platform/pull/2881)のbounded absence、[Draft #2933](https://github.com/hat47x/tei-platform/pull/2933)の最適化時の契約保存を横断照合する。各担当のRole・Topology・Build・最適化用の第二検証器を本節で新設しない。

一つのConsumer/Target/Phase/Scope/Source revision/選択Generationを固定したうえで、必要に応じ次の**五つの異なる主張**を追跡する。

| Claim | 意味と必要な根拠 | 成功と取り違えないもの |
| --- | --- | --- |
| **Required** | ConsumerのContract/Role/Graphから独立して要求される型付きPort、依存、入力、Effect、Source集合。要求側の発行・適用範囲が必要 | PluginやFixtureが自己申告した `required=[]` |
| **Declared** | Source、計画、Manifestに明示されたNode/Edge/Input/Providerとその固定版 | 全宣言が実際に選択・実行されたという意味 |
| **Selected** | 解決されたContract/Provider/Instance/Builder/Operator/Artifact Roleとその正確な世代・対象 | 選択済み実装が実byteを読んだ／実Effectを行ったこと |
| **Consumed** | 既存Reader/実Build/実Provider等が実際に利用した入力・Artifact/Step・時点。観測能力と欠落範囲を注記 | 同じ出力Digestなら全消費Sourceも一致すること |
| **Observed / Disclosed** | 独立Read/Receipt/Trace/Studio Projectionで観測・開示できた内容、Reader coverage、Policy/Scopeと版 | 観測しなかった経路や隠れた副作用が「存在しない」こと |

**局所型検査の成立**は、選択済みSemantic定義の構造に対するTypeRef/Shape/Multiplicityの一致候補まで（E2a [#2584](https://github.com/hat47x/tei-platform/pull/2584)）。**閉包の成立**は、上表のRequired→Declared→Selected→Consumedを当該Claimの範囲で独立に照合し、未列挙・部分観測・動的ロード・opaque境界を明示する段階。**外部Effect/Authorityの成立**は、さらに実Targetの強制境界・結果/Receipt・必要な再認可で判定する段階である。これらを一つのboolean `valid` に畳まない。

- 宣言Graphの見た目・Tableの行数が一致しても、実Readerが未読込Sourceを見逃せば閉包未証明（[#2823](https://github.com/hat47x/tei-platform/issues/2823)）。逆にGraphにNodeが無くても、対象Scope/Reader/Phaseで閉包が確認されない限り「不存在」と表示しない。
- `std.binary`から`std.binary`へのTypeRef一致は、外部配送の4分割中3件ACK、Commit後の取消、Spool容量超過を成功へ変えない（Draft [#2827](https://github.com/hat47x/tei-platform/pull/2827)の既存DM/EF条件に委譲）。単なるTransport Batch、処理Chunk、業務的Atomic Batch、Execution Groupingの保証を継承させない。
- Build Graphに必要な型付きEdgeが揃っていても、一時的な`main.go`の二回Buildの成功から実`cmd/tei`・nested moduleの実入力閉包を推定しない（#2831）。Build stepの未宣言入力と可観測範囲外の動的工程はそれぞれfail/unknownとして区別する。
- Pushdown/Fusion/Cache/Batch/Provider交換の最適化は、TypeRefだけでなくNULL/順序/部分失敗/Unknown/Effect/Scope/対象時点を保ったことを別に検証する（Draft #2933）。宣言された論理契約が同じという事実を、物理結果・性能効果や現在のInvocation Authorityと混同しない。

**既存STケースへの追加判定（新Fixture IDは増やさない）**：ST-02はSemantic定義・Sourceの版変更による型候補と利用資格の失効、ST-03はETLのSelected/Consumed/ACK/Partialの別観測、ST-04は同型二InstanceのScope/Config/Grant分離、ST-09はArtifact digest一致でもBuilder/Attempt/Targetが異なる場合の再資格化をそれぞれ確認する。Graph/Tableの表示差は#2881、Role/Source closureは#2620、実Buildは#2831、実MFTは#2827/#2542に割り当てる。

**標準化判断の停止条件**：二つのConsumerで型付き辺の共通検査が成立しても、未充足がSource閉包・Role/Effect・Transfer receipt・Build provenanceで説明できるなら新しい標準TypeKind/専用DSL/第二Resolverを追加しない。独立して同じ**意味**の表現・変換・診断に欠損が再現されたときのみ#2620と#951へ最小契約差分を返す。Stage/Host/Studio/実DB/External ProviderのE2E、実際の閉包、Owner Acceptance、性能測定は本設計では**NOT RUN / NOT PROVEN**。


### 17.8 「型適合」「要求保証」「実行証拠」を別の判定にする（2026-11-06、実証引継ぎ）

**差分となる着想**：同じTypeRefの接続に成功した後でも、ProducerがConsumerの必要とする順序・配送・原子性・再現性などを提供するとは限らない。Pluginの継承/特殊化（例：Filesystem相当のByte保存とS3系Object保存）を、メソッド名・primitive・Capability名だけで置換可能とみなさない。既存[#951](https://github.com/hat47x/tei-platform/issues/951)の正式Contract、[#2933](https://github.com/hat47x/tei-platform/pull/2933)の最適化要件、[#2827](https://github.com/hat47x/tei-platform/pull/2827)の配送保証が各意味のOwnerであり、ここで独立した保証Registryを新設しない。

**診断の順序（新規プロダクトAPIではない）**：
1. **構造候補**：TypeRef/Name/Multiplicity/NULL/Shapeのうち試作が検査できる範囲を確認。存在しない型・選択されていないSourceは衝突と断定せずUnknownにする（[#2584](https://github.com/hat47x/tei-platform/pull/2584)）。
2. **必要な保証の充足**：Consumer側のRequired guaranteesと、選択されたProvider/Transform/Targetが**その対象と時点に対して**保証すると検証された条件を照合。未定義・不確実な意味（順序、欠損、外部ACK、Atomicity、idempotency、rollback等）は**未判定**であり、自動的なFallbackや暗黙Adapterを追加しない。
3. **実際の成立証拠**：Declared/Selectedだけでなく実Consumed/Observed、Source closure、正規のArtifact・ReceiptとIndependent Oracleを確認。TypeRef一致とProviderの仕様適合は、実行結果や現在の権限を代替しない。

要求保証を単純な真偽値へ畳まない。対象/Scope/Target/Phase/Source revision/Generation/OperationId/Attemptと、保証の根拠・確認できなかった範囲を記録し、要求が部分充足または不明ならCandidateをProduction-qualifiedに昇格しない。**Value-levelの互換、Stage/Build-levelの資格、Effect-levelの現在許可は異なる結論**として返す。

| ST-04 同型の二Plugin Instance | 同TypeRefでもInstanceは別 | 異なるScope/DataSource/Grantで選択の同一性を区別。NAS系とObject StoreのAtomic Rename/一式Publishを無条件継承させない | #951 / #1016 / Draft #2933 |

### 17.9 閉じた値域と設計特性の「意図・証拠・適合」を分離する（2026-11-06、設計候補）

他チャットで挙がったEnumのような閉じた値域・MECE区分・「強属性」を、単一の新しいSemantic TypeKindに詰め込まず、既存の[#2495](https://github.com/hat47x/tei-platform/issues/2495)（直交Facet）、[#2544](https://github.com/hat47x/tei-platform/issues/2544)（公理・演算の資格）、[#1126](https://github.com/hat47x/tei-platform/issues/1126)（候補キー・関数従属性）、[#958](https://github.com/hat47x/tei-platform/issues/958)（根拠と人間確認）、[#267](https://github.com/hat47x/tei-platform/issues/267)（受理）を利用して評価する。**「強属性」の原典における厳密な定義は未照合**なので、候補キー・決定属性と同義であると**断定せず**、資料・文脈に紐付く外部の意味分類候補に留める。

#### 値域に関する独立した問い

| 問い | 宣言として確認したいこと | 検証できる証拠と限界 |
| --- | --- | --- |
| 値域Closed | 値集合を特定版の列挙に限定するか、未知値・将来拡張を許すか | enum/oneof/CHECKの構文とTargetでの実制約。ただしアプリケーション全体のSource閉包を保証しない |
| Mutually Exclusive | 同時に所属可能な区分か、一個のtagを選ぶ構造か | tagged union・排他CHECK・独立Oracle。複数flagや期間重複は別契約 |
| Collectively Exhaustive | **何を全体集合とするか**（対象・Scope・時点）を明示し、どの実例もいずれかへ入るか | 分類規則と独立した対象集合。有限データで未出現値がないことは一般的な全件証明ではない |
| Identity / Determinance | 業務キー、一意制約、関数従属性、区分による条件付き制約を分ける | SchemaのUNIQUE/FK/FD、実データの反例、Ownerの意味判断。物理PK一致を業務IDの確定としない |
| Lifecycle / Effective time | 状態遷移・変更可能性・適用時点・無効化を区分から独立に扱う | 明示Ruleと実Targetの観測。Enumの定数集合だけで遷移可能性を推測しない |

「MECE」は閉じたEnum型の同義語ではない。**mutually exclusive** と **collectively exhaustive** は、分類対象の母集合・業務時点・Null/Unknown・複合分類の条件を明記した後、それぞれ検証する。Java等でEnumが有限でも、業務上の区分が完全かどうかや将来値の取扱いは自動決定できない。

#### 設定者・基盤の分担（候補）

| 判断する対象 | 設計者／Owner | 基盤の自動化・限界 |
| --- | --- | --- |
| 業務上の値域・分類の母集合／例外値 | 対象Scope・有効時点・未分類時の扱いを意図として宣言し、必要なら受理 | Java Enum、tagged union、SQL CHECK等の**構文上の有限値域**は抽出可能。ただし実装上のEnumを業務全体のClosed/MECEへ自動昇格しない |
| 区分の排他・網羅、状態遷移 | ビジネス上の条件や許される遷移を確認 | 静的Constraintと独立Oracleで反例を検査。データの現行サンプルに漏れがないだけでは全称命題の証明にならない |
| 識別性・強属性と呼ぶ特性 | Business Key/FD等に解釈できる場合は根拠と共に宣言。「強属性」の用語定義が未固定なら unresolved | UNIQUE/PK/FK/FD・実データ重複は**該当Targetの証拠**。DB PKを業務上の強さや正本Identityと同一視しない |
| 意図と実現の差分 | 誤検知・仕様変更・受理候補をレビュー | **violated**（具体的な反例）／**conformant-in-scope**（範囲・保証を限定して一致）／**unverified**（必要な閉包・Oracleがない）を別表示し、意図を勝手に書き換えない |

具体例として、業務モデルが「区分A/Bが常に排他的かつ網羅的」と要求するのにTargetの列が任意の文字列を受理する場合は、実Target上の制約が不足する**設計対実現の警告候補**とする。一方、制約が明示されていないという理由だけでは、実データに違反が存在すると断定しない。業務的なStatusの集合が未受理なら、Java Enumがあっても「業務的MECEを証明した」と報告しない。

#### 宣言意図と実態の差分提示（新しいTruth/Authority判定器ではない）

1. **Intended**：設計者が意味の正本に明示したClosed/Exclusive/Exhaustive/Identity等の条件、対象Scope/Source revision、受理状態。未採用の提案は受理済みと呼ばない。
2. **Observed / Inferred**：既存Parser・Constraint・Schema・Target Adapter・実データから判別できた事実、分析可能な範囲、反例・未読込Source・部分観測。列挙やSQL CHECKは**その実装面で確認できた制約**であって、業務意味を確定しない。
3. **Conformance**：同じSubject・Scope・Target・時点について、根拠付きで一致する場合だけ「範囲内適合」、明示反例がある場合は「不一致」、必要証拠が不足する場合は「未検証」。推定だけで人間のIntentやAccepted Meaningを書換えない。

次の既存ケースへの圧力とする（ここで第二の試験SSOTは作らない）。

- **ST-02 / ST-08**：同じ`std.code`・Ref／同じEnum名でも、値集合が変更・拡張され、Clientが旧全件性を仮定している場合は再資格化する。`std.*`→`tei.std.*`の改名を値域互換の証拠にしない。
- **ST-03**：CSV/JSON転送に未認識status/unknown/nullが含まれる場合、値を勝手に「その他」へ丸めず、Consumerが要求するclosednessとProvider側の実保証を別列に提示する。
- **ST-04**：二つのInstanceが同じTypeRefでも、Scope・effective-time・参照Master・業務キーの受理範囲が違えば同じ強さの区分/FDを使えると推測しない。
- **ST-09**：生成コード中のEnum構文があるだけで、元のBusiness classificationやSource全件性が保証されたとはしない。生成元の宣言・Target制約・実行観測を別に照合する。

**検証・撤回条件**：#2495の既存Facetと#1126のFD/Key／#2544の制約・証拠の関連付けで上記が表示・診断できれば追加TypeKindは不要。二つの異質Consumerで未表現の意味が同じ形で反復し、既存契約では欠落を明示できない場合だけ追加契約をOwnerへ提案。現時点では具体的なJava/SQL/DB/Studio実接合、正規の原典定義、Target完全性、A4意味受理は**NOT RUN / NOT PROVEN**。


### 17.10 既存コードからの意味抽出と異Targetへの再実現（2026-11-06、実証候補）

## 18. 大プラグイン主義：緩やかな公開・依存者責任・明示的保証（2026-11-07／調査・採用前）

### 18.1 設計論点と暫定的な結論

生成AIによって第三者Pluginの改修・互換性試験・Adapter作成のコストが下がり得るため、上流Pluginに全公開APIの列挙と安定保証を一律要求すると、拡張参加の障壁を不必要に高める懸念がある。反対に、技術的に到達可能な内部状態、秘密、未権限Resourceを無条件で実行可能にしてはならない。

**比較すべき既定案**は「原則として再利用・検査可能、互換性保証は上流の明示宣言、保証外利用と追随変更は下流の責任、物理EffectとDisclosureは現在Host/Policyが強制」である。これは第三者ライセンス、Publisherの契約発行権限、元Pluginの非公開コード／秘密への突破を許す意味ではない。

1. **技術的可視性**（Consumerから型・Contract/Role/Operator/公開SDKを参照できるか）と、**発見可能性**（許可されたCatalogへ載るか）、**契約上の安定保証**、**実呼出し可能性**、**Host Grant/Effect**を分ける。OpenをRuntime permissionと定義しない。
2. 既に配布・アクセス許可済みのContract/Role/Extension Pointは、公開者が個別の `export` を大量追加せずに、型・説明・利用条件を **Open / unpromised** としてConsumer側の発見・参照候補にできる。ただし**未発行・非公開・非開示Sourceを外部へ自動送出しない**。第三者に対するRelease/Registry登録自体はPublisherのRelease宣言に従う。
3. 上流は**保証したい契約だけ** Stable（保証Scope、互換性の意味、サポート期間/終了）を明示、破壊の可能性を示す Experimental/Deprecated、外部利用不可の Internal/Restrictedを最小の例外指定で示す。指定なしのOpenは「存在してよい／機械で読める」が「安定」「現在許可」「正式Provider Conformance」のどれも意味しない。
4. 上流が専用Service Contractを提供していない既存の到達可能APIに、下流が自分の**Consumer-owned Adapter/Requirement**を作ることを許す余地を評価する。ただし必要な可視性・公開ライセンス・Host入口が実在し、上流の禁止や境界を越えない場合だけ。下流の独自Contractに上流の公式保証を帰属させない。上流へ新しいStable Contractの採用を要求しない。
5. **互換性が破れても全Pluginを一律停止しない**：未依存Pluginは無影響、任意連携は機能単位でDegraded/Unavailable、必須依存は当該Function/Targetのみunsupported。実Targetの安全なError Boundaryの外で「自己責任」を理由にCrash/誤Effectを許さない。

### 18.2 公開度は3区分、使用資格は直交させる（暫定分類／新Core enumではない）

| 公開上の説明 | 上流Publisherがすること | 下流Consumerがすること | TEIの診断・資格 |
| --- | --- | --- | --- |
| Stable / Supported | 特定Contract identity・version・Semantic Profileと保証Scopeを明示。公開者がPromiseを変更する場合はBreakingを示す | 宣言した範囲内で利用し、実質的なEffect/Null等のConformanceを確認 | Promiseは独立Conformance/現在Grantの代替でない |
| Open / Unpromised（既定候補） | 既に公開したCapability・操作が参照可能なことを許し、**保守義務を自動負担しない**。個々の `export` 指定不要 | 具体的なInterface/Contract fingerprint・検証済みVersion/Artifactと追随Testを自分でPin。破壊時は自ら修正・上流へ任意提案 | 静的に存在しても実Call可能・Semantic互換とは限らない。任意依存のdegrade理由を説明 |
| Internal / Restricted | 実装内部、秘密/管理操作、再利用禁止、Scope制限を明示または既存Access Policyで保護 | 公開や実Grantを推測しない。上流実装を自己都合で外部露出しない | 読取・開示・呼出しは既存Provider/Host/Policy境界で拒否。AnnotationだけをSecurity Boundaryとしない |

**注意**：上記は上流が「外部向け利用を保証する度合い」に関する分類であり、配布物に含むバイト、Plugin ID、User/Tenant、組織所属、Authority、Receiver Disclosureの分類と同一視しない。Source/licenseが非公開の場合、未注釈ゆえにOpenと推定しない。「明示されなければOpen」は **Publisherが既に配布・可視化を許した範囲内** に限定する。

### 18.3 実際の依存の表現（既存標準Record/Relationを使う要求票、DSL文法未採用）

同じ上流Providerでも、利用側Functionは「どこまで保証されるか」を自分の要件として宣言できる。

| consumer/use-site | requires | 版要求 | 義務 | 利用する面 | 下流の責任 |
| --- | --- | --- | --- | --- | --- |
| `order.analytics` | `example.order.query` Contract | `>=1.4.0,<2` | required | Stable Contract: `search,get` | 意味適合とScope/Targetを再検証 |
| `order.analytics.extra` | `vendor.query.debug` Open API | `tested:3.2.1`（例） | optional | Open/unpromised、Publisher未保証 | 実APIのexact fingerprintをLock、破壊時にAdapter再生成、失敗時はその機能だけ停止 |
| `order.analytics.preview` | `example.render.table` | `^2.1`（例） | optional | 表示のみのExtension Point | 必要Shape/Grainを再検査し、非可逆編集不可 |

**版を最低5列に分離**：Contract semantic version／Contract revision-fingerprint／Provider implementation version／Bundle publication version／**実Resolved Lock（exact artifact・selected scope・Target）**。上流が公開保証をしないOpen APIではSemVer範囲に自動的な意味互換性を与えず、下流の `testedVersion / testedFingerprint`、互換試験と改版後の再生成記録を重視する。Providerを実行Targetで実際に選ぶのは#951/#1016の唯一の解決経路であり、「上流がOpenだから自動起動」はしない。

**選択規則の候補**：
- Stable契約：許容範囲のProviderを#951で選び、同一候補が複数なら明示Selectionを要求。ReferenceのScope/Source、Semantic Conformance、実Artifact、Host Grantを別に照合。
- Open依存：Consumer自身のCompatibility Testがまだ対象Revで未実行なら、**read-onlyで存在・形状をInspectできてもProduction実行資格はunverified**。安全なread-only previewに限りConsumerが明示的にexperimental modeを選べるか試す。Side-effectを伴う呼出しで実Grant/Effect境界を緩めない。
- Optional依存：不存在・未選択・非互換・失効のそれぞれを別理由で診断し、対象機能だけをdegradeする。直接・推移的Requiredを省略したOpen APIの「偶然見つかった」状態は、検証済みの解決結果に昇格させない。
- 複数Version共存：Consumerごとの名前空間/インスタンス/Build実装で可能な場合だけ許可。Go同一package pathの複数版を単一静的Linkで無条件許容しない。JS/NPM・Jenkins等も重複Class/グローバルSingletonが問題になるためTarget別に反証する。

**上流の明示的言及は保証限定でよい**。必要なのは、少なくとも「このContractはStableである／この拡張点はOpenだが非保証／この入口はInternalである」という説明であって、「全関数を利用させるための逐一export宣言」ではない。開発者体験では、Version差分・依存者一覧・影響関数・修復PR/Adapter/回帰Testの生成を優先する。
