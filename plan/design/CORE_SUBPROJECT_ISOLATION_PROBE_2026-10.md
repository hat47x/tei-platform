# 合成基盤を独立して構築するための確認（2026年10月）

- **状態**：局所的な検証手順。TEI全体の受入済み証拠ではない。
- **対象**：[Issue #1251](https://github.com/hat47x/tei-platform/issues/1251)、[ADR-0033](../adr/0033-core-and-plugin-subprojects.md)、[ADR-0032](../adr/0032-composition-kernel-replacement.md)
- **ソース確認の基準**：`main` `dbb74d860bfaf16f909f263f9a958c49a3322434`（2026年10月12日）

## 何を確認するか

`core/`へ実装を移動する前に、新しい合成基盤の候補である`internal/composition/`が、既存のリポジトリから切り離されても試験できるかを確認します。これはソースの独立性を確かめる実験であり、コアの公開契約や製品のビルド構成を決めるものではありません。

ソースを確認した時点では、`internal/composition/`直下の製品用Goファイル7件とテスト8件は、いずれもGo標準ライブラリ以外を直接参照していません。一方、`internal/core/`の製品コード2件と`internal/subject/`の1件もTEI内部パッケージを直接参照していません。`internal/permission/`は`internal/core/`に、`internal/semantic/`も`internal/core/`に依存しています。

これらは**確認したソースの直接import**に限る観測です。実行先別のビルドタグ、全利用者からの逆方向依存、生成物、配備、性能、実行権限を証明しません。

## 隔離試験の入口

信頼できるTEIリポジトリのクリーンなチェックアウトで、ルートから次を実行します。

```bash
tools/check-core-isolation.sh
```

この手順では、`internal/composition/`の内容だけをリポジトリ外の一時ディレクトリに複製します。一時的な最小`go.mod`を生成し、ネットワーク取得と既存の外部モジュールキャッシュを使わずに`go test -count=1 ./...`と`go vet ./...`を実行します。内部に別の`go.mod`や`go.work`があれば、対象が検査から外れないよう明示的に失敗します。確認が終わると一時領域を削除します。

これにより、その時点の合成基盤が外部モジュールやリポジトリ内の他のパッケージを必要とせずに試験できるかを直接調べます。

さらに、[別モジュールの利用者向け試験](../../reference/composition-kernel/testdata/external-consumer/consumer_test.go)を第二の一時Goモジュールで実行します。一時的な`replace`指定だけで合成基盤のコピーを読み込み、次を確認します。

- 別モジュールの利用者が公開されたGoの型と関数だけでProviderを登録・選択できる。
- Provider宣言の変更後、古い選択に基づく新規呼出しを拒否する。
- Hostが承認した新しい世代へ切り替え、処理中の旧世代を直ちに解放しない。
- Host側の権限拒否、新規呼出しの撤去、各世代の後始末を区別できる。

**この試験では合成基盤のコピーを一時モジュールの直下へ置き直します。** 現在の`tei/internal/composition`を別のGoモジュールから直接読み込めるという意味ではありません。Goの`internal/`には参照元の配置制約があるため、外部プラグインへGoパッケージを公開するなら、その公開契約を`internal/`の外に用意する必要があります。ただし、外部プラグインが通信契約を通じて接続する場合は、GoのAPI自体を配布する必要はありません。

この検証は、プラグイン実体の構築、製品の認可・署名検証、Webや組み込み向けのクロスビルド、再現可能なバイナリ生成を証明するものではありません。

既存の`tools/repository-architecture-check/`では、`internal/composition/`から他のTEI内部パッケージへの直接importを拒否する規則を追加します。これは現時点で成立している小さな境界を守るものです。将来、共通契約を取り込む必要が生じた場合は、その必要性と依存の向きを先に評価し、規則を更新します。

## 依存関係の追加調査（2026年10月12日）

公開GitHubの`main` `395481c408bde8731653f06b3dc2afda60200e7c`のGit treeと、そこに含まれるGoソースの内容を確認しました。

- `internal/`の製品用Goソース221件、`cmd/`の製品用Goソース13件の計234件を確認しました。
- 上記234件では、`tei/internal/composition`を直接importするファイルは0件でした。
- `internal/composition/`内の製品用ファイル7件、テスト8件には、外部ライブラリへのimport、ビルド条件を切り替える指示、`go:embed`の指定を確認できませんでした。
- 対照的に`tei/internal/core`は、データベース、プラグイン、検証、構文解析など多数の製品パッケージから直接参照されていました。

これはGitHub上の**ソース内容の静的調査**であり、`go list`を使ったコンパイル対象の依存グラフや、動作・本番接続を確認した結果ではありません。テストからの参照と`tools/`以下の利用状況も、この234件の集計には含みません。特に合成基盤への製品側の参照がないことは、製品実行経路への統合が未完了である可能性を示します。

したがって、`internal/composition/`のファイルをただ`core/`へ移動するのではなく、まず実際のConsumer/Providerを接続する縦断試験を設け、どの公開契約を通じて利用するかを確認する必要があります。

## プラグイン側の切り出しを阻む依存

代表例として、既存の処理実行プラグイン`tools/reference-process-plugin/main.go`を確認しました。このファイルは`tei/internal/plugin/runtime`と`tei/internal/deployment/executor`を直接参照しています。現在は同じGoモジュール内にあるため動作する構成ですが、実装だけを`plugins/`へ移しても、独立した契約と依存関係が成立するわけではありません。

一方、`examples/process-plugin/main.go`はプラグイン自身ではなく、その起動と呼出しを試す利用例です。こちらはさらに`tei/internal/core`、`tei/internal/deployment`、`tei/internal/plugin`などを参照しています。両者を区別せず一括でプラグインのソースとみなさないようにします。

先に、外部プラグインが参照する通信・呼出し契約と、ホスト内の実行権限・資源管理を分ける必要があります。契約の移行は[ADR-0032](../adr/0032-composition-kernel-replacement.md)および既存のプラグイン設計課題（[#951](https://github.com/hat47x/tei-platform/issues/951)、[#943](https://github.com/hat47x/tei-platform/issues/943)）に合わせます。今回、新しいプラグイン規約や外部公開APIを先取りして追加しません。

## 確認結果と残る条件

この変更の作成時点では、隔離スクリプトを使い、**合成した小さなGoパッケージ**で正常系と、外部依存を注入した失敗系を確認しました。 新たな別モジュールの利用者試験については、Goの一時モジュールを相対的な`replace`で接続し、外部からパッケージを読み込む仕組みだけを局所検証しました。**TEIの実ソースを使った追加試験の成功は未確認です。**後続の改修では、直下と下位ディレクトリの二つの模擬Goパッケージに対して両方のテストが実行されることを確認し、下位の`go.mod`を拒否することと、下位パッケージから存在しないTEI内部パッケージを参照した際に失敗することを確認しました（Go 1.23.2、Linux/amd64、`GO111MODULE=off`を呼び出し環境に設定した条件）。TEIの実ソース全体を取得した環境でスクリプトを実行した結果ではありません。

次に必要なことは次のとおりです。

1. 対象コミットのクリーンな全体チェックアウトで、隔離試験と通常の全体健全性検査の両方を実行し、実行環境と正確なコミットを記録する。
2. 全パッケージの依存関係と、コア候補が実際に参照される場所を`go list -deps -json`等で調べる。既存の[依存関係一覧ツール](../../tools/repository-dependency-report/)と[Issue #980](https://github.com/hat47x/tei-platform/issues/980)の成果を使い、重複した検査機構を増やさない。
3. 新しい合成基盤と最小ホストの責務を切り分け、契約の置き場所と移動が必要なソースを決める。
4. 少なくとも一つの実プラグインとの接続と回帰試験が成立してから、`core/`への移動や独立Goモジュールの必要性を判断する。

**隔離試験の成功を、TEIコア全体の独立ビルド完了とは呼びません。**
