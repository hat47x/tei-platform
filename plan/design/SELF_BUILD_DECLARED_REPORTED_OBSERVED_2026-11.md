# セルフビルドの記録を、宣言・申告・観測に分ける

状態: 設計判断と実測の記録（2026-11-17）。[#2831](https://github.com/hat47x/tei-platform/issues/2831)、[#2600](https://github.com/hat47x/tei-platform/issues/2600)。

この文書は、`tei self-build`でTEI自身を構築した実測から、構築の仕組みをどう組み立てるかを判断したものです。G4の判定ではありません。`qualified`は`false`のままです。実測の条件と生の値は[実測記録](../evidence/TEI_SELF_BUILD_OBSERVED_PIPELINE_2026-11-17.md)にあります。

入口の契約は[SB-C0の入口契約](SELF_BUILD_REENTRY_CONTRACT_SB0C_2026-11.md)が定めています。本文書はそれを置き換えず、§4.55・§4.56が残した問いに答えます。

## 1. 結論

1. **Buildの記録は三つに分ける。** 計画がBuildの前に述べたこと（宣言）、entryとbuilderがBuildについて述べたこと（申告）、Buildに参加しない観測器が見たこと（観測）です。これまでの検査は申告どうしの突合せで、Buildの内側から書いた記録だけでできていました。
2. **「図にない工程は無い」を言うのは観測である。** 申告の欄を増やしても、申告しない実行は見えません。実測では、entryの検査がすべて合格した試行で、宣言にない実行物が動き、二回目のBuildが一回目のstateを8,669回開いていました。
3. **entryは、自分が解決した計画をbuilderへ渡す。** これまでbuilderが受け取る計画は、呼び手が別の道具で作ったファイルでした。`-hand-over-plan`を足しました。
4. **Stage1のTEIがStage2を構築したことは、Stage2で動いた実行物のdigestで確かめる。** 三つの対象（CLI、builder、catalog作成ツール）で、Stage2の全1,663プロセスにStage0由来の実行物は一つもなく、三つともStage1とStage2のbyteが一致しました。残る外部起動は9プロセスです。
5. **再構築の判断には、宣言した入力ではなく、実際にコンパイルされる入力を使う。** 13種類の編集で、宣言に基づく鍵は7件を無駄に作り直し、コンパイル対象に基づく鍵は1件でした。誤った再利用はどちらも0件でした。
6. **未達がある。** Buildの宣言は今も試験が実行時に作っており、リポジトリに常設の宣言はありません。CLIをPluginとして宣言しています。Studio（Node、Wails、WebView2）は対象に入っていません。

## 2. 何が断絶していたか

`./cmd/tei`の全鎖（宣言→catalog→計画→Build→五条件）は2026-11-09に通っています（SB-C0 §4.50）。その全鎖を、試験の外で一工程ずつ再現して確かめました。

| # | 断絶 | 確かめ方 | 対処 |
| --- | --- | --- | --- |
| G1 | 宣言が、照合相手の実Buildから作られる。 全鎖の宣言は、試験が`go list -deps`の結果から実行時に書く。宣言と実行が一致するのは、構成上ほぼ自明である | `cli_self_build_full_chain_test.go`の`writeFullChainDeclaration` | 未対処（§6） |
| G2 | 計画は一工程しか述べない。 補助ツール4本のseedビルド、catalogの作成、builderの配置、計画の解決は、試験のコードにある | 全鎖をシェルで再現した | 一部対処（G3、§4） |
| G3 | builderが建てる計画は、entryの計画ではなかった。 計画ファイルは試験か別のresolverが書き、entryはfingerprintを比べるだけだった | 同上 | `-hand-over-plan` |
| G4 | 申告にない実行と読取りは、どの欄にも出ない | 観測器で全プロセスを追跡した | 観測器と照合（§3） |
| G5 | 名指した実行ファイルが、別の実行物へ切り替わる。 `-go`に名指したGoは1.25.14で、環境変数があるときだけ1.26.11へ自分で切り替わる。起動側は切り替わった後のGoで補助ツールをビルドし、builderは同じパスを1.25.14として起動した | 試行が失敗し、原因を追った | 計画でtoolchainを名指す（SB-C0 §4.56の既存機能）。名指さない計画では起こり得る |
| G6 | 失敗の理由が入口に届かない。 builderは`buildSucceeded: false`と理由を出して終了コード0で終わり、entryの報告には「成果物を読めない」だけが残った | G5の試行 | `childBuildError` |
| G7 | 宣言した入力の大半を、Buildは読まない。 宣言した1,672ファイルのうち、コンパイラが開いたのは487ファイルだった | 観測した読取りを集計した | 鍵を分ける（§5） |
| G8 | CLIをPluginとして宣言している。 subjectは`kind: "plugin"`、`id: "tei.command.tei"`。`BuildIntent`はPlugin以外を受け付けない | 宣言の中身 | 未対処（§6） |

G1・G2・G3は一つの問題の別の面です。**構築の手順が、TEIの読むデータではなく、試験やスクリプトのコードにある。** この形では、Stage1のTEIは手順を知らないので、Stage2を自分で進められません。

## 3. 観測を、Buildの外に置く

### 3.1 三つの方式

| 方式 | 記録を書く者 | 見えないもの |
| --- | --- | --- |
| A. 起動側が記録する | entry | childが内部で起動したもの、読んだもの |
| B. 工程が申告し、起動側が読み直す（現行） | builderとentry | 申告しない実行、申告と違う実行、申告の後の変化 |
| C. Buildに参加しない観測器が記録する（本文書） | 観測器 | 観測器が追えない呼出し（数えて記録する）、開いた後のbyte、木の外 |

現行のBは、穴が見つかるたびに欄を足してきました。builder照合（§4.56）、toolchainの観測、プロセスイメージ、stateの観測（§4.55）、隔離木の申告です。どれも一つの事実を、申告か、entryの読み直しで確かめます。

Cは、これらを一つの記録から導きます。

| 現行の欄 | 現行が確かめること | 観測から導けること |
| --- | --- | --- |
| `builderBinding` | 起動前に読んだファイルのdigest | 実際に動いたプログラムのdigest。起動後に別の実行物へ渡した場合も出る |
| `toolchainObservation` | builderが申告したパスにあるファイルのdigest | 動いたすべてのプログラムが、名指した閉包の下にあるか |
| `processImage` | 起動直後のパスの一致（linuxのみ、記録のみ） | 全プロセスについて同じこと |
| `stateSeparation`・`stateObservation` | 渡したディレクトリの前後のファイル数 | 一方のBuildが、他方のstateを開いたか |
| `childIsolation` | builderの申告 | Buildが読んだファイルが、宣言した範囲に収まるか |

### 3.2 反例

実対象で、builderに次のラッパーを据えました。二回目の起動の前に一回目のstateを二回目へコピーし、本物のbuilderへ処理を渡します。SB-C0 §4.55が「entryには見えない」とした構成です。

| 見る者 | 結果 |
| --- | --- |
| entry | `ok: true`、`l2b.claimed: true`、`reproduced`、`stateSeparation.basis: entry-post-hoc`、`stateObservation.kind: effect-observed`、`builderBinding: bound` |
| 観測器と照合 | `not-proven`。宣言にない実行が2件（本物のbuilder）、他方のstateへの読み書きが8,669件 |

二回目のBuildで動いたtoolchainのプログラムは、正常な試行の395に対して6でした。二回目はキャッシュの再生で、成果物の一致は独立した二回のBuildの結果ではありません。

同じ計画を、正しいbuilderで建てた試行では、宣言にない実行は0件、他方のstateへの読み書きは0件でした。

### 3.3 採った判断

- **観測器は、Buildの宣言や報告を読まない。** 照合は別の操作で、観測記録と宣言範囲を入力に取る。
- **宣言範囲の各項目に、誰の言明かを持たせる。** 計画、entryの報告、builderの申告、呼び手の指定を分ける。**builderの申告だけに基づく項目は、「範囲外は無い」の根拠にしない。** builderは任意のディレクトリをtoolchainとして申告できる。計画が名指すのはdigestで、パスを宣言済みとするのは、entryが一致を確かめた場合に限る。
- **追えない呼出しは数える。** 別のABIの呼出し、パスを追えない開き方、名前空間やrootの変更、追跡から外れる`clone`を見たら、記録にその数を残し、「範囲外は無い」とは言わない。
- **観測は防止ではない。** 宣言にない読取りを止めるのは境界（[#4486](https://github.com/hat47x/tei-platform/issues/4486) S2）の役目である。観測は、境界が効いたか、境界の無いホストで何が起きたかを確かめる。
- **既存の欄は外さない。** 観測はlinux/amd64でしか動かない。ほかのホストでは、現行の欄が唯一の記録である。

### 3.4 観測で見つかった、宣言にない読み書き

正しいbuilderの試行でも、照合は`not-proven`でした。残ったのは次の4種類です。

| 読み書き | 開いたもの | 分類 |
| --- | --- | --- |
| 二回目のBuildの隔離木 | builder、`go`、compiler | **報告の不足。** entryの報告は一回目の隔離木だけを載せる |
| 時刻帯のデータ | `go` | **環境から来る入力。** 計画は時刻帯を述べない |
| 共有の一時ディレクトリの一覧 | entry、builder | 同上 |
| 出力先の隣の一時ファイル | `go` | **宣言より広い書込み。** 出力として宣言したのは一つのパスである |

`go list`が起動する`go telemetry`は、toolchainの閉包の一員として範囲に入ります。計画にも報告にも現れない工程ですが、名指した閉包の中にあります。

## 4. Stage1がStage2を構築したことを確かめる

SB-C0 §4.4は、L3の証明に「stage1の生成物がstage2を駆動したこと」を求めています。2026-11-08の実測は、Stage2を駆動した`tei`がStage1の生成物であることを示しました。ただし計画はchildが解決し、builderはseedがビルドしたものでした。

今回は三点を変えました。

- **builderと、catalogを作るツールも、Buildの対象にした。** Stage2のbuilderはStage1が建てたものである。
- **計画は、各Stageの`tei`がin-processで解決し、builderへ渡した。**
- **Stage全体を観測した。** Stageが起動したすべてのプロセスについて、動いたプログラムのdigestを記録した。

判定は、観測記録とディスク上のファイルだけから行いました。entryの`ok`には依りません。

| 確かめたこと | 結果 |
| --- | --- |
| Stage2で動いたプログラムに、Stage0のdigestを持つものがあるか | 0件（全1,663プロセス） |
| Stage2の`tei`（3回）のdigest | すべてStage1の`tei` |
| Stage2のbuilder（6回）のdigestと起動元 | すべてStage1のbuilder。起動元はすべてStage1の`tei` |
| Stage1とStage2の成果物 | 三つともbyteが一致 |
| Stage2が開いた、前のStageのファイル | Stage1の`tei`とbuilderの成果物だけ。Stage0のファイルは0件。ただしこの観測記録には読めなかった停止が10件あり、その分だけ不確かである |
| 宣言 | 両Stageで同じファイル。Stageの間で書き換えていない |

**言えるのは次のことです。** この三つの対象について、Stage1が建てたTEIが、自分で計画を解決し、Stage1が建てたbuilderを起動して、Stage1と同じbyteの三つを建てた。その間、Stage0の実行物は動いていない。

**言えないことも残ります。**

- Stageの中で三つの対象を順に呼び、catalogを作り、builderを置くのは、今もシェルスクリプトである（`bash`、`mkdir`、`cp`、`sha256sum`の計9プロセス）。ここにあるのは、対象どうしの依存の順序と、成果物の受け渡しである
- 宣言は、Stage0の前に`go list`から作った（G1）
- Goのtoolchainは外部のseedである。TEIがGoのcompilerを建てたのではない
- linux/amd64、Go 1.26.11、1台、1回の実測である

## 5. 変更に対して、何を作り直すか

現行の計画は、宣言した入力すべてのdigestを含みます。`go-package`の入力はディレクトリ全体で、`_test.go`、README、testdataも入ります。

観測した読取りを集計すると、宣言した入力のうち、コンパイラ（`compile`・`asm`・`link`）が開いたのはファイル数で29%、byteで36%でした。残りの大半は`_test.go`です。`go`自身は一覧と条件判定のために`_test.go`の先頭も開きますが、成果物には入りません。

13種類の編集について、三つを比べました。宣言に基づく鍵（計画のfingerprint）、コンパイル対象に基づく鍵（`go list`が述べるコンパイル対象と`go.mod`・`go.sum`のdigest）、新しいstateで実際に作り直した成果物です。

| 編集 | 宣言の鍵 | コンパイル対象の鍵 | 成果物 |
| --- | --- | --- | --- |
| 試験ファイルを編集 | 変わる | 同じ | 同じ |
| パッケージ内のREADMEを編集 | 変わる | 同じ | 同じ |
| testdataを編集 | 変わる | 同じ | 同じ |
| 他OS向けのファイルを編集 | 変わる | 同じ | 同じ |
| 試験ファイルを追加 | 変わる | 同じ | 同じ |
| 他OS向けのファイルを追加 | 変わる | 同じ | 同じ |
| `go.mod`にコメントを追記 | 変わる | 変わる | 同じ |
| コンパイル対象の末尾にコメントを追記 | 変わる | 変わる | **変わる** |
| コンパイル対象の先頭にコメントを追記 | 変わる | 変わる | 変わる |
| コンパイル対象の文字列を変更 | 変わる | 変わる | 変わる |
| コンパイル対象のファイルを追加 | 変わる | 変わる | 変わる |
| 宣言の外の文書を編集 | 同じ | 同じ | 同じ |

| 鍵 | 誤った再利用 | 無駄な再構築 |
| --- | --- | --- |
| 宣言の鍵 | 0 | 7 |
| コンパイル対象の鍵 | 0 | 1 |

`go list`が述べるコンパイル対象は、観測した読取りと一致しました。toolchainの申告を、観測で確かめたことになります。

### 採った判断

- **宣言・計画・実消費を、別の役目として持つ。** 宣言は、Buildが読んでよい範囲の上限である。計画は、一回の試行で読む入力をdigestで固定する。実消費は、成果物を決めた入力である。**実消費 ⊆ 計画 ⊆ 宣言**を検査する。
- **作り直すかどうかは、実消費に基づく鍵で判断する。** 計画のfingerprintは「この試行が何を建てたか」の識別に使い続ける。鍵が同じなら、前の成果物を再利用してよい。そのとき作るのは新しいEvidenceであり、新しい成果物ではない。
- **実消費は、toolchainの申告から求め、観測で確かめる。** 毎回の追跡は要らない。追跡は、申告が正しいかを確かめるための検査である。
- **ファイルの追加に備える。** 前回読んだファイルのdigestだけを鍵にすると、パッケージへ新しいファイルを足したときに誤って再利用する。コンパイル対象の一覧そのものを鍵に含める。上の表では、ファイルの追加で鍵が変わっている。

### 反証された仮説

- **「コメントだけの変更なら成果物は同じで、作り直しを打ち切れる」は成り立たない。** コンパイル対象の末尾にコメントを足しただけで、成果物のbyteは変わった。入力が変われば成果物は変わる前提で扱う。

この節は鍵の比較までです。再利用する実装、現在資格の判定、待ち時間の測定（[#2600](https://github.com/hat47x/tei-platform/issues/2600) D0・D1）は行っていません。

## 6. 残っている判断

### 6.1 Graphは、宣言どうしの参照から導く

残った9プロセスの糊は、対象どうしの関係を知っています。builderは`tei`のBuildに要る。catalogはbuilderの成果物を指す。この関係は、今はスクリプトにあります。

三つの案を比べました。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| 対象ごとの宣言を、外の手順で順に呼ぶ（現行） | 関係は手順にある | 採らない。Stage1のTEIは手順を知らず、Stage2を自分で進められない |
| Graphを別のファイルに書く | 工程と矢印を宣言する | 採らない。宣言がすでに述べていること（どのbuilderの契約を使うか）を、矢印としてもう一度書くことになる。二か所を直す負担が生じる |
| **宣言が、ほかの対象の成果物を参照する** | builderの実体や入力として「対象Xの成果物」を名指す。Graphは参照をたどって導く | **採る** |

今のcatalogの宣言は、builderの実体を`"artifact": "builder"`というファイル名で指します。そこへ誰がファイルを置くかは、宣言の外にあります。これを「対象`builder`の成果物」という参照に替えると、置く工程は宣言から導けます。生成したTypeScriptをまとめる工程も、まとめた結果をGoへ埋め込む工程も、同じ形で書けます。

`tools/reference-build-execution-binding`には、解決済みの計画どうしを結ぶ`BuildGraph`があります。導いたGraphは、この型へ写せる見込みです。**実装していません。** 9プロセスが0になるかどうかで確かめます。

### 6.2 分類

| 不足 | 分類 | 根拠 |
| --- | --- | --- |
| 計画の受け渡し、失敗理由の伝達、観測と照合 | **既存の構造の組合せで解決した** | 型を足していない。`BuildPlan`、既存の報告、新しい参照ツール |
| 報告に二回目の隔離木と出力先が無い | **既存の構造の組合せで解決できる** | 報告の欄を足す。[#5202](https://github.com/hat47x/tei-platform/pull/5202)が同じファイルを変更中のため、今回は触れていない |
| Plugin以外の対象を宣言できない（G8） | **標準構造の拡張が要る** | `BuildIntent`のsubjectが`plugin`に固定されている。CLIやDesktopをPluginと偽らない |
| 宣言が、ほかの対象の成果物を参照できない（§6.1） | **標準構造の拡張が要る** | 入力とbuilderの実体に、参照の種類を足す |
| 常設の宣言が無い（G1） | **標準構造の拡張が要る** | 宣言を粗く安定に保つには、パッケージの列挙ではなく「このコマンドの閉包」と書ける入力の種類が要る。列挙は計画の段で、名指した道具に展開させる |
| Goのコマンドの実消費を求める | **Pluginで解決する** | 実消費の求め方はtoolchainごとに違う。Goでは`go list`、ほかのtoolchainでは別の方法になる。builderの契約の一部とする |
| ほかのOSでの観測 | **Pluginで解決する** | 追跡の方法はOSごとに違う。観測記録の形は共通にできる |

### 6.3 持ち主の判断

- **観測を、L2-bやG4の材料にどう数えるか。** 今回は記録を足しただけで、判定は変えていない。SB-C0 §4.56の決定2は、G4に数える試行を`host-boundary`に限った。観測で他方のstateへの読み書きが0件だった試行を同じ扱いにするかは、決めていない
- **toolchainの名指しを必須にするか。** 名指さない計画では、照合は「範囲外は無い」と言わない。G5はその実例である
- **時刻帯と一時ディレクトリを、宣言に載せるか、Buildから見えなくするか**
- **Plugin以外の対象の種類を、どう名付けるか**

- **TEI全体のセルフビルドの達成。** 確かめたのは、Goで書かれた三つのコマンドである。TEIの定義から生成した部品は、この三つに含まれていない
