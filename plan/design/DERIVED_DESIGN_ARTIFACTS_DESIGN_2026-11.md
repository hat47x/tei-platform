# 設計成果物の導出と、読める差分（設計候補）

- 状態: **提案中（未採用）**
- 対応課題: [#1803](https://github.com/hat47x/tei-platform/issues/1803)（設計書・一覧・DDLの導出出力）
- 関連: #1126（ER・関数従属性）、#1802（機能移植の対応表）、#2301・#2308（PostgreSQL の主キー変更・制約名）、#2016（生成器生成）、#1130（帳票の出力）、#1808（補助情報の置き場所）
- 正本: DDLの出力は[PostgreSQL制約出力の設計](POSTGRES_CONSTRAINT_RENDERING_DESIGN_2026-10.md)と[データベース方言プラグインの設計](DATABASE_DIALECT_PLUGIN_DESIGN_2026-10.md)が持つ。本稿は**設計者・レビュー者が読む成果物**の導出契約を足す。
- この文書の役割: 受理済みの意味から、人が読む成果物を決定的に導出し、その差分と未解決を読めるようにする。

## 1. 不足していること

TEIには、意味から実行物を作る経路（Lowering、生成器、DDL）がある。一方、**人が読む成果物**を意味から作る経路がない。

- 表定義書、機能定義書（画面イメージと入出力を含む）、主題領域・作業・機能・表の対応一覧（五種類）は、旧モデラーが出力していた。TEIには担当がない（[#1803](https://github.com/hat47x/tei-platform/issues/1803)、[機能移植の対応表](AUTHORING_TOOL_FEATURE_TRANSFER_MAP_2026-10.md)）。
- 帳票（#1130）は業務の出力であって、設計の成果物ではない。同じ「出力」でも読む相手が違う。
- DDLは、方言プラグインと制約出力の設計で部分的に扱われているが、成果物としての同一性（どの版の意味から、どの規則で、何が未解決か）を持っていない。

設計者が読む成果物がないと、レビューは設計ツールの画面に依存する。画面を閉じた後、何を根拠に承認したのかが残らない。

## 2. 導出成果物の契約

**導出成果物**（derived artifact）は、受理済みの意味から決定的に導出される、読むための成果物である。少なくとも次を持つ。

```text
artifact {
  kind            種別（table-definition / function-definition / cross-reference / ddl）
  inputRevision   入力の意味の版（受理済みの照合値）
  rule            {id, version, fingerprint}   導出規則の識別子と版
  generator       生成器の識別子（同じ規則でも実装が変わり得る）
  bytes           内容と、その照合値
  unresolved[]    未解決の一覧（空配列は「未解決がない」ことを意味する）
}
```

満たすべき条件。

1. **決定性。** 同じ `inputRevision` と `rule` からは、同じバイト列が出る。時刻、乱数、環境、ディレクトリの列挙順を内容に混ぜない。
2. **意味の差分。** 差分は、行の増減ではなく意味の変化として読める。名前の変更、型の変更、制約の追加、対応の欠落を区別する。
3. **未解決の非隠蔽。** 情報が足りない項目は、空欄や既定値で埋めず、`unresolved[]` に理由付きで載せる。空欄は「値が無い」、`unresolved` は「決まっていない」である。
4. **非昇格。** 成果物は意味の正本ではない。成果物を編集して意味を変える経路を作らない（編集は #1124 の受理経路を通す）。

読み手向けの文書（案内文・報告・対外説明）はSHO（MMI系）の担当であり、この成果物は**設計の確認**に限ります。体裁・配布・公開の判断はTEIが持ちません（[TAI上流への立ち戻り](../workstreams/TAI_UPSTREAM_ALIGNMENT_2026-11.md)）。

## 3. 種別ごとの内容

| 種別 | 入力 | 必ず載せる内容 | 未解決になりやすい点 |
| --- | --- | --- | --- |
| 表定義書 | `data`、`persist`、`candidate-key`、`functional-dependency`、`relation` | 表、列、型、必須、主キー・候補キー、外部キー、索引、業務上の識別子 | 業務上の識別子が未宣言、関数従属性が未宣言、物理型の対応が未決 |
| 機能定義書 | `application`、`pattern`、`capability`、`validation`、`authorization` | 機能の一覧、入出力、前提、業務結果、実行エラー、認可の要否 | 画面の項目が未確定（操作面の gap）、認可の対象が未宣言 |
| 対応一覧 | 主題領域・作業・機能・表の関係（#1126、#1125） | 五種類の対応と、対応の欠落 | 対応の根拠が無い（推測で埋めない） |
| DDL | `persist`、制約、方言 | CREATE／ALTER 文と、適用順序、制約名 | 提供元が出力できない制約（[#2301](https://github.com/hat47x/tei-platform/issues/2301)・[#2308](https://github.com/hat47x/tei-platform/issues/2308)） |

「対応一覧」は、対応が無いことを空欄で表さない。対応の欠落は、それ自体が設計上の発見である（#1126 の関数従属性の宣言が無い、#1125 の作業と機能の対応が無い）。

## 4. 可読性の受入

成果物の合否は、次の問いに**成果物だけ**で答えられることで判定する。

1. 前回の版から、何が変わったか。
2. その変更は、どの要求・どの意味の変更によるものか（`inputRevision` と差分から辿れること）。
3. 決まっていないことは何か。それは誰が決めるのか（`unresolved[]` に理由と担当の候補）。
4. この成果物を、意味を読まずに承認してよいか（よくない場合、どこを読むべきか）。

画面の見た目、PDFの体裁、フォントは判定に含めない。体裁は実行先の責務である。

W1 が前提。W2〜W4 は並行できる。W5 は W2 の後。

**実装状況（2026-11-01）。** W1（導出成果物の型と照合値）を [`internal/artifact/artifact.go`](../../internal/artifact/artifact.go) に追加しました。

- `Kind`・`InputRevision`・`Rule`（ID・版・照合値）・`Generator`・`Content`・`Digest`・`Unresolved` を持ちます。
- 同じ入力の版と同じ規則からは同じ照合値になります。内容、規則の版、入力の版のどれが変わっても照合値が変わります。
- 未解決はソートして照合値に含めます。順序の違いで別の成果物にしないためです。
- `Verify` は、保存された成果物の内容・規則・未解決が変わっていないことを確かめます。
- 識別情報が欠けた成果物は作りません（規則の版・照合値・生成器・入力の版は必須）。

W2（表定義書）も追加しました（[`internal/artifact/tabledef.go`](../../internal/artifact/tabledef.go)）。保存の対応と意味のデータから、`table`・`data`・`column`・`primary-key`・`unique`・`foreign-key`・`index` の行を、保存の宣言順・索引名順・外部キー名順で出します。外部キーは参照先の表名まで解決して出し、参照先が分からない場合は宣言の識別子をそのまま残します。列に写像されていない属性と、主キーが無い表は、空欄で埋めず `Unresolved` に載せます。形式は仮説H2（行指向のテキスト）で選んでいます（[PoCの仮説](../workstreams/POC_HYPOTHESES_2026-11.md)）。

機能定義書（W3）も追加しました（[`internal/artifact/functiondef.go`](../../internal/artifact/functiondef.go)）。`application`・`capability`・`input`・`output`／`outcome`・`effect`・`validation`・`pattern` を決定的に並べ、入力・結果・効果の欠落と、入口（pattern）の無いアプリケーションを未解決に載せます。

DDLとの整合（W5）は、表定義書の内容を `physical.SchemaSnapshot` に写し、既存の `schemadiff` で望ましいスキーマと突き合わせる形にしました（[`internal/artifact/ddlcheck.go`](../../internal/artifact/ddlcheck.go)）。差分は既存の語彙で返し、成果物側で黙って直しません。**索引は列名と一意性まで、外部キーは参照先の表と列まで対応**しました（属性から物理列名を解決）。キーの式・照合順序・述語は `persist` に宣言が無いため比較しません（推測して差分を出さないための制限）。

成果物一式の整合を検査する仕組み（`CheckSet`）も追加しました（[`internal/artifact/consistency.go`](../../internal/artifact/consistency.go)）。入力の版の一致、目録と成果物の対応、操作面の gap と未解決の対応、未解決があるのに完成と表示していないこと、成果物が自分の種類の規則を名乗っていること、読み手が頼る行（`table`・`application`・スキーマ版）を失っていないこと、操作が根拠（`basis`）と既知の自律区分を持つことを、**新しい意味を足さずに**確かめます。違反は対象と理由つきで返し、負例の作業領域では違反ゼロ、改変すると違反が出ることを試験で固定しました。### 整合検査の一覧

| 検査（Finding） | 何を守るか | 違反したときに読むこと |
| --- | --- | --- |
| `ARTIFACT_REVISION_MISMATCH` | 一式が同じ意味から作られていること | 別の版の意味で作った成果物が混ざっている |
| `MANIFEST_ENTRY_MISSING` | 目録がすべての成果物を載せていること | 目録を配ると、載っていない成果物が抜け落ちる |
| `SURFACE_GAP_UNRESOLVED_MISSING` | 導出できなかった操作が未解決として残ること | 操作が黙って欠落している |
| `COMPLETE_WITH_UNRESOLVED` | 「完成」の表示が未解決と矛盾しないこと | 未完成なのに完成として扱われる |
| `ARTIFACT_RULE_UNKNOWN` | 成果物が自分の種類の規則を名乗ること | どの規則で作ったかが狂っている |
| `ARTIFACT_CONTENT_INCOMPLETE` | 読み手が頼る行（`table`・`application`・スキーマ版）があること | 照合値は合うが読めない成果物 |
| `SURFACE_OPERATION_INCOMPLETE` | 操作が根拠と既知の自律区分を持つこと | 根拠不明の操作、未知の自律区分（ゲート無しと誤読される） |
| `ARTIFACT_DUPLICATE` | 同じ成果物が二重に混ざっていないこと | 目録や件数が実体と合わない |
| `MANIFEST_ENTRY_STALE` | 目録が実在しない成果物を載せていないこと | 目録だけが先行して更新されている |
| `MANIFEST_DIGEST_MISMATCH` | 目録の照合値が中身と一致すること | 目録だけが書き換えられている |
| `SURFACE_TARGET_UNREACHABLE` | 操作の対象が、アプリが到達できる保存の対応にあること | 操作面と保存の宣言が食い違っている（生成時に検査） |
| `PERIOD_PRECONDITION_UNKNOWN` | 期間の前提が、実在する期間を指すこと | 存在しない期間を前提にしている |
| `PERIOD_PRECONDITION_MISMATCH` | 期間の前提が、その操作の対象を統治する期間を指すこと | 別のデータの期間を前提にしている |

検査は**矛盾の検出**であり、成果物の正しさの証明ではありません。以後に成果物の種類を増やすときも、この検査を通します。一括生成（`RenderWorkspace`）は**生成時に検査を実行し**、結果を `Findings` として返します。違反がある場合も成果物は返しますが、「整合した一式」として読んではいけません。

標準操作の導出結果も成果物として束縛しました（[`internal/artifact/surface.go`](../../internal/artifact/surface.go)）。操作面の JSON を内容とし、**未解決（gap）をそのまま `Unresolved` に写します**。これで「同じ意味から同じ操作面」を照合値で確かめられ、設計書と同じ束縛で扱えます。負例の作業領域では、4件の gap が4件の未解決として目録に載ることを試験で固定しました。

作業領域からの一括生成（`RenderWorkspace`）も追加しました（[`internal/artifact/workspace.go`](../../internal/artifact/workspace.go)）。アプリケーションが到達できる保存の対応ごとに表定義書を作り、**`uses semantic` で宣言した名前空間の能力だけ**を機能定義書に載せ、操作面と合わせて目録にします（使っていない名前空間の能力を「提供している」と読ませないため）。入力の版は作業領域のモデル改訂を使うため、同じ意味から作った成果物だけが一つの目録に入ります。負例の作業領域（`ledger`）では表3件・機能1件と未解決が出て、目録は `complete=false` になることを試験で固定しました。

成果物の目録（manifest）も追加しました（[`internal/artifact/manifest.go`](../../internal/artifact/manifest.go)）。複数の成果物から、入力の版が揃っていることを確かめたうえで、種類・照合値・未解決の件数を決定的に並べます。各項目は**規則の識別子・版・指紋**も持ちます（何が作ったか、規則の中身が変わったかまで辿れる）。**未解決が一つでもあれば `complete=false`** とし、完成に見せません。入力の版が混ざる場合と、改変された成果物は受け付けません。

W6（CLI）の読み取りと書き出しを追加しました。`tei artifacts -workspace <root> -application <id>` が成果物一式（内容・照合値・未解決・目録・整合検査の `findings`）を JSON で出します。`-out <dir>` を付けると、成果物ごとに1ファイル（表は `table-<table>.md`、機能は `function-<app>.md`、操作面は `operation-surface.json`）と `manifest.json` を書き、目録を標準出力へ出します。同じ意味からは同じファイル名になり、同名で中身が違う場合は上書きせず停止します。未解決が残る場合は `complete: false`、整合検査の違反は `findings` に並びます。`-check` を付けると、整合検査の違反がある場合に終了コード 1 で止まります（CIで使う想定）。

対応一覧（W4）は、現在の意味モデルに主題領域・作業・機能の対応を表す宣言が無いため、受理済みの意味からは導出できません。意味を足すか（A4）、対応一覧を手で維持するかの判断待ちです（[#2482](https://github.com/hat47x/tei-platform/issues/2482)）。DDLとの整合（W5）とCLI（W6）は未着手です。

## 7. 停止条件

- 成果物から意味を書き戻す経路を作った場合は停止する。
- 未解決を空欄や既定値で埋めた場合は停止する。
- 生成に時刻・乱数・環境依存の値を混ぜた場合は停止する。
- 体裁（PDFの改ページ、フォント）を意味の層へ持ち込んだ場合は停止する。

## 8. 効果と撤回

- 効果: 設計のレビューが、ツールの画面ではなく成果物と差分でできる。承認の根拠が、`inputRevision` と規則の版で辿れる。未解決が一覧で見える。
- 観測: 成果物の生成回数、差分に現れた意味の変化の種類、`unresolved` の件数と解消までの日数、レビューで成果物だけを使って回答できた割合。
- 撤回: 参照作業領域で `unresolved` が常に空になり、差分も意味の変化を示さない場合は、成果物の導出をやめ、DDLだけに戻す。

## 9. 未決（Owner判断）

1. 成果物の保存先を、リポジトリ内の生成物とするか、実行のたびに生成するか。
2. `generator` を成果物の同一性に含めるか（同じ規則でも実装が変わればバイト列が変わり得る）。
3. #1130 の帳票の `output` と、この契約を統合するか。統合すると規則が一つになるが、業務の出力と設計の成果物で読む相手が違う。
