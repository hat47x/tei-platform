# データ導出規則の最小意味契約（検証案）

対象：#1637。問い合わせ適用は #1640、鮮度と確定値は #1641、更新・副作用は #1129 に委譲する。本書は採用前の設計案であり、製品機能の実装完了を意味しない。

## 分離する二つの対象

- **規則定義**：何を入力とし、どの型の結果をどう求めるか。規則ID、型付き入力参照、演算子と版、結果型、依存規則、純粋性を持つ。入力参照は物理列名ではなく意味上のIDを使う。
- **適用の結び付け**：規則IDを、意味属性、問い合わせ固有の結果、集合計算などの対象IDへ適用する。対象IDは規則IDと別に扱う。同名の列や属性を自動結合しない。

同じ規則を複数の対象へ適用できるが、対象の認可・NULL・評価文脈が同一だと推測しない。規則は保存値を暗黙に更新しない。既存の `semantic.Attribute`、`Relation`、#988 の演算子、#1120 の安定参照を利用し、新しいCanonical型や式言語を先に固定しない。

## 型付きの確認

`internal/semantic/derivationref` の参照実装は、規則の任意の型付き契約（`InputTypes`・`OutputType`）と、適用先の`TargetType`を検査する。型の不一致は`ErrType`、未対応の演算子は`ErrOperator`として区別し、名前や位置の一致で型を推測しない。

- 規則の型付き契約が揃っているとき、`multiply`は数値型（`decimal`・`integer`）の2入力と数値の結果型を要求する
- 適用先の`TargetType`が規則の`OutputType`と異なる場合は拒否する
- 一つの規則を複数の適用先へ結び付けられる。適用先を変えても規則は変わらない
- `InputTypes`・`OutputType`・`TargetType`は任意であり、指定しない既存の呼出しは従来どおり動く

これは参照用の宣言であり、Coreの型体系や新しい式言語を固定しない。

## 評価結果と診断の最小区別

| 状態 | 意味 | 期待する処理 |
| --- | --- | --- |
| 値 | 宣言した型に適合する結果 | 正常に返す |
| 正当なNULL | NULL方針により値がNULLとなる | 0に変換しない |
| 入力未取得 | 必要な入力が取得されていない | 参照先0件と区別して診断 |
| 参照先なし | 解決済みの関係に一致する対象がない | 関係の多重度とNULL方針に従う |
| 多重度違反 | 一件を要求した参照先が複数一致 | 任意の先頭行を採用しない |
| 評価不能 | 型、演算子、循環、実行能力などの不整合 | 値として偽装しない |

この表は評価上の区別を示すもので、単一の巨大な公開列挙型を要求しない。認可拒否は既存の実行権限の境界に従い、利用者に診断から秘匿情報を漏らさない。

## 最小受入例

| 入力 | 期待結果 |
| --- | --- |
| 数量2、単価300 | 600 |
| 数量0、単価300 | 0 |
| 数量NULL、NULL伝播を宣言 | NULL |
| 単価を未取得 | 入力未取得 |
| 一件参照に2件一致 | 多重度違反 |
| 規則A→B→A | 循環を拒否 |
| 未解決の演算子 | 評価不能 |
| 純粋な規則が外部書込みを要求 | 拒否 |

数値は浮動小数点の暗黙変換を避け、演算子契約の精度・丸め・通貨単位に従う。計算に使う規則・入力・評価文脈が固定されている場合に限り決定論性を検査する。

## 追補：Data Ruleの配置をFunction非従属と両立させる（2026-11-15、設計判断案）

本節は**既存#1637の適用先・#1129のTable lifecycle・#2622のData Operationsの分担を明確化**する設計案である。新しい式言語、Rule Engine、Schema、Registryを追加しない。以下はAuthoringと受入の方針であり、実Providerへの接続・Ownerの意味受理を示すものではない。

### 計算が依存する意味の範囲から配置先を選ぶ

「Data RuleかFunction Ruleか」を**SQLのテーブル数やUI部品の数だけで判別しない**。次を順に確かめる。

1. **何についての値・判断か**：特定Dataの属性、関係、制約か。利用者が要求する検索・集計結果か。業務上のイベント・責任・状態遷移か。最初に対象の意味と粒度を定める。
2. **値が変わる要因は何か**：同じData、同じ有効時点、同じ受理済み規則、同じ必要入力集合が揃ったとき、利用するFunction／画面／操作者／検索母集団が違っても意味上の値が同じか。異なるなら、何の違いに由来するかを明示する。
3. **どの依存を明示する必要があるか**：他のRelation、期間、集計母集団、外部情報源、取得完全性、Context、Ruleの版、現在の権限が必要なら隠さない。特に**複数行を読むから直ちにFunction Ruleとは限らない**。Dataに固有の関係集合から一意に定義できる値はData Rule候補になり得る。ただし部分取得を全件とみなさない。
4. **何を変えるか**：純粋導出、Validation、Draft変更、保存前の許容変更、業務状態遷移、実DB／外部Effectを区別する。「値が計算できる」と「実際に書き換えてよい」は別資格である。

| 候補 | 配置と理由 | 誤った配置 |
| --- | --- | --- |
| 受注明細の\`quantity × agreedUnitPrice\` | Dataの属性値に普遍的な純粋導出。Table Script／Data Ruleから同一#1637のRuleを参照 | フォーム・受注登録Function・帳票それぞれに式を複写 |
| 受注の明細合計（明細Relationの全件が必要） | 所属Relation、粒度、空集合、採用時点がData側に定まるならData Rule候補。完全性を満たすQuery/Providerが必要 | 画面の表示済み子行だけで永続合計を確定 |
| 「今月・自分の担当顧客」の売上 | 母集団、Actor、期間、現在AuthZがFunctionに固有。Function Context／Query | 顧客Dataの普遍的属性やTable Scriptへ隠して格納 |
| 承認済み注文だけの請求対象抽出 | 選択集合はFunction Context、承認状態の意味はBusiness、判定に使うRuleは共通化可 | 単一テーブルの表示項目・UIイベントで承認資格を確定 |
| 郵便番号の型、先頭ゼロ保持、必須 | Dataの型・値域・Constraint／項目拡張Facet。任意の式実行を要求しない | 型定義がないままTable Scriptで毎回文字列変換 |
| APIだけで完結する価格試算 | FunctionはData Modelを所有しなくてもよい。必要な型付き入力・共通Operator・外部Providerを明示 | Data Modelの新規作成をFunction存在の必須条件とする |

**原則**：純粋な規則の意味定義と、どこで／いつ適用するかのAttachmentを分ける。共有したいのはOperatorと受理済みの意味であり、画面・Table・Functionごとに式の第二正本を作らない。一つのRuleが複数の対象へ適用可能でも、時点・型・Scope・現在Grantの適合まで自動保証しない。

### 項目拡張定義とTable Scriptの一方向参照

まずは**項目拡張定義＝属性の宣言、Table Script／Data Rule＝Data局所の振る舞いの記述元**という整理を採る。項目には型・Facet・NULL・保存性・仮想属性という静的な性質を置き、計算式の本文と実行順序は別の場所へ複写しない。Studioが項目から式を開く場合は、解決済みRule IDとSource位置を通じて一次Scriptへ移動する。Field表示画面で式編集を可能にする場合でも、同じScript Sourceへ安全に書き戻せるときに限る。編集不可ならread-onlyにする。

ここでいう「Table」は**Dataの局所的なライフサイクルを表す利用者向けの見方**であり、物理RDBテーブルや専用Runtimeが必要という意味ではない。RDB/API/Document等のData Providerに同じ意味契約を投影する。仮想項目が名前を持っていても、Queryによる一時集計結果を必ず永続Data属性へ格納するわけではない。

### 規則の合成と衝突解決を順序依存にしない

Data RuleとFunction固有Ruleの双方が関係する場合は、安易に「Table Scriptを先、Function Scriptを後」で上書きしない。Ruleの適用先・結果スロット・Phase・前提・Read-set/Write-set・依存を比較し、競合があるときは同じ意味の参照へ統合するか、用途が異なることを明示して別出力へ分ける。別々のRuleが同じ結果スロットへ書く場合、排他的条件や合成規則が受理されない限り自動採用しない。依存循環・未取得値・粒度違い・失効したContextは既存診断へ渡す。

**読取側と保存側を混同しない**。Table Scriptによる導出値をQueryのFilter/Sort/Aggregate/Limitへ使う場合は#1640の計画順序が必要。純粋計算を行う行とその入力集合の取得が不完全な場合、再計算できるという理由だけで全件集計を成功にしない。業務上確定して保存された値は#1641の区別に従い、現在の入力・Rule版への変更で暗黙上書きしない。DB確定、通知、再実行は#1129/#1174のOperation/Effect/Receiptへ委譲する。

## 追補：規則の評価時点・取得範囲・Function Contextをまたぐ正しさ（2026-11-15）

既存のRule Definition／Attachmentの分離を、日常的な業務画面とデータ保存にまで適用するときの判定基準を整理する。**処理の配置は式の構文や参照テーブル数ではなく、何を対象とし、どの時点・母集団で意味が確定するかによって決める。** 業務FunctionはDataに従属せず、Dataに普遍的な規則はどのFunctionからも参照できる。

| 利用場面 | 参照できる入力・保証する意味 | Owner |
| --- | --- | --- |
| フォームの初期値 | 入力の候補をFunction開始／Draft生成時に求める。途中変更で自動再計算するとは限らない | Function Context／Presentation |
| 入力中の純粋導出 | 明示したDraftのField・Relation集合から計算し、UIで再表示する。DBの保存事実ではない | Data Rule／FunctionのDraft |
| 非保存属性の読取導出 | 指定したRead Scope／時点で求める。検索・整列・Limit前に必要な場合はQuery計画へ依存関係を渡す | #1637→#1640 |
| 保存前の再計算・検証 | 現在Grant・旧Version・対象Relation集合・old/newの差に基づき再評価する。UIで表示された金額を無条件に信用しない | #1129／#1174 |
| 取引時点に確定した値 | 採用した価格・税額・業務上の確定時点を保存事実として保持。現在マスターの更新で暗黙再計算しない | #1641／Function Action |
| 機能固有の期間別・担当者別集計 | Query結果の母集団・粒度・完全性・利用者・期間をFunction Data Contextに保持 | #2506／#2586／#2622 |

**関係をたどる値は三つに分ける。** (a)取得時点の値を保存したSnapshot、(b)参照先のEntity Keyを保存して現在の値を投影するRead、(c)今のRelation Pathを辿る非保存Projectionである。親の参照キーが同じでも中間Relationが変化すれば(c)は別のEntityへ到達し得る。(b)が保存する最終Entity Keyをいつ更新するかは別のAction／Rule条件で決める。Lookupの存在だけでSnapshotの自動同期や業務上の変更を起こさない。

**親子の入力中計算と保存時計算は共通Ruleを使っても、取得完全性と効果は異なる。** 入力中に変更していない既存子行、別タブの子行、削除予定の子行を含む変更集合の定義を固定し、当該集計に必要なRelation集合が揃っているかを確認する。保存前にはOwner Transactionの確定対象を再取得・再計算し、Versionと現在AuthZを検査する。Draft側での成功はDB Commitの成功でも、ファイル添付や外部Effectの原子性でもない。

**規則は利用目的ごとに許されるOperator/Functionの集合が異なり得る。** 計算・Initial Value・Business Guardが同じ式言語を使っても、Purpose・入力Kind・副作用許否・時間情報・再現性の制限を型付きで評価する。Guardで同じ述語を利用できることと、承認資格のGrantを得ることを混同しない。処理不能なPhase・循環依存・未取得集合を「別Phaseで試したら成功した」ことで隠さない。
