# 実装を持たない契約から案件別Providerを補完するPoC

- 状態：**評価待ち（未採用）**。製品API・形式・受理規則の決定ではなく、反証可能な設計仮説。
- 日付：2026年10月17日

- 既存責務：[Capability Contract #951](https://github.com/hat47x/tei-platform/issues/951)、[Composition Kernel #1223](https://github.com/hat47x/tei-platform/issues/1223)、[AIコード部分接続 #1448](https://github.com/hat47x/tei-platform/issues/1448)、[Build authoring #1109](https://github.com/hat47x/tei-platform/issues/1109)、[変換工程 #1063](https://github.com/hat47x/tei-platform/issues/1063)、[AI Proposal #267](https://github.com/hat47x/tei-platform/issues/267)
- 比較題材：[DB方言の検討案](DATABASE_DIALECT_PLUGIN_DESIGN_2026-10.md)。両文書とも、採用済みのDB Plugin製品仕様ではない。

## 1. 解きたい問題と仮説

従来、プラグインの「対応製品」を増やすには、その製品向けの実装を基盤側で用意してから配布する発想に寄りやすい。生成AIを利用できるなら、先に共有すべき資産は**製品別の実装一覧ではなく、満たすべき意味・失敗・制約と、その独立した検査方法**かもしれない。

仮説：**実装を持たない契約だけを配布しても有用**である。案件はその契約に適合する既存Providerを選んでもよいし、必要なTargetと製品版に対してのみ生成AI・人間が新しい実装を作ってもよい。基盤は契約、受理、検証、実行権限の所有者を変えずに、**対応範囲を案件側で拡張できる**。

これは「契約を書くと任意のDBが自動的に安全に動く」という主張ではない。未知の製品機能・OS・ドライバの特性、テストの欠落、権限・本番接続の不足は残り、未解決をそのまま表示する。

### この抽象が成立すれば変わること

- プラグイン実装が**ゼロ件**でも、要求・検証条件・対応不可の理由を共有できる。
- 新しいDB製品やRuntimeごとにTEI Coreへ製品名・固定列挙・例外分岐を足す必要が減る。
- 案件が作成した小さな実装を、**共有の独立した適合試験**で検査し、再利用可能な実装に育てられる。
- 実装の出自（手書き／AI生成／既存OSS）を実行権限の根拠にせず、**同じ契約と検証境界で比較**できる。

## 2. 一つの「プラグイン」に混ぜないもの

| 役割 | 所有するもの | 実装なしで存在できるか |
| --- | --- | --- |
| 契約資産（Contract Packという仮称） | 論理identity・版・指紋、操作・意味、入力／結果／拒否／Unknown、副作用・権限・適用範囲 | **できる** |
| 適合試験資産 | 独立した期待値、正負の例、境界条件、適用可能な製品版・Target、実行に要るfixture | **できる**。試験は存在しても未実行の場合がある |
| 実装候補 | Go/.NET/JVM/Wasm等での実装Source、依存・Target条件、選択したProvider | 任意。契約だけの配布には不要 |
| ビルド成果物 | 既存Builderが得た実行可能バイト列、digest、依存閉包、Build Evidence・Lock | **できない**。候補のままなら欠けてよい |
| 適合性・実行受理 | 実施した試験結果と適用範囲、Hostの現在のContract/Provider受理、Runtime権限 | 契約公開だけでは成立しない |

「契約資産」という用語は既存Contractに付随する配布・参照方法を説明する仮称であり、新しい登録簿、製品の永続schema、特権的な第三のAuthorityを提案しない。適合試験自体も**契約の意味の正本を持ち直さず**、承認された契約を検査するための資産とする。

### 未提供を失敗の一種類へ押し込まない

| 状況 | 利用者へ示すべき結果 | 次の対応 |
| --- | --- | --- |
| 契約や必要な意味そのものが未受理 | 意味未確定 | Source/Contract Ownerへ戻す。AIが勝手に確定しない |
| 契約は存在するが実装がない | 実現先不足 | 既存Provider探索、案件内生成の候補提示 |
| 候補はあるが適合試験未実行 | 未検証候補 | 試験を実施し、対象範囲を明示 |
| 適合試験が不合格 | 実装不適合 | 診断し修正または撤回。別意味へのフォールバック禁止 |
| 試験はPASSだがHost受理・権限がない | 実行不可 | 既存Authority/Acceptanceへ戻す |
| Target・DB実版が検証済み範囲と異なる | 適用範囲未確認 | 別版の実DB試験・Compatibility根拠が必要 |
| 実行の結果が不明 | Unknown | 成功・失敗へ推測で変換せず、既存Recovery/Observationへ引き渡す |

この区分は**診断の観点**であり、Coreに新しい列挙型を追加する指示ではない。

## 3. 案件が不足した実装を補完する経路

```text
既存の意味・契約（正本／明示した利用範囲）
             │
             ├── 既存Providerの有無と適合範囲を確認（#951）
             │         │
             │         └── 対応Providerがあれば既存経路へ
             │
             └── Provider不在（未実装を明示。業務意味の不一致ではない）
                       │
                案件/AIが実装候補を作成
                       │  出力はGit上の変更・依存・対象Target
                       ▼
                 既存BuilderとBuildPlan
                       │  Source/Builder/Artifactのidentityを固定
                       ▼
            独立した契約試験（正負）＋実対象環境の試験
                       │
              不合格 → 修正／撤回。未実施 → 未検証
                       │
                 適合した候補の証拠
                       │
            既存Host受理・Provider選択・実行時Authority
                       ▼
                    実際の呼出し
```

生成AIは候補を作る**開発手段**であって、Contract Publisher、Conformance Issuer、Host Authorityにはならない。生成器自体を必須常駐サービスにせず、AIを使わないGo/CLI/Git経路も残す。Runtimeの呼出し中に未確認のコードを即興で生成・実行する方式はPoC対象外。

既存成果物と同一のContractに適合すれば手書きProviderでもよく、「AI生成」を製品の特別なPlugin種別にしない。

## 4. 第一段階：SQLiteの狭い機能面による検証

最初からRDBの全SQL・DDL・Transaction移行を契約化しない。既存DB方言設計の**識別子引用とパラメータ束縛を中心とする読取り専用の小さな面**に限定し、既存のProvider境界に配置できるかを調べる。

契約と試験の例（**試験題材の例示であり、採用済みのSPI・Wire形式ではない**）：

- 引用する識別子：`customer`、引用符を含む`a"b`、予約語、空文字や不正入力。期待される識別子の引用結果を**独立した固定fixture**で明示する。
- 外部値：`' OR 1=1 --`、空文字、NULL、境界数値。SQL本文への文字列連結を禁止し、値が**パラメータとして束縛**されることを観測する。単なるSQLの文字列比較で安全性を証明しない。
- 結果：NULLの保存、列型の復元、行数と順序の条件、クエリ失敗と未実行の区別。対象となる読取り操作について独立した期待値を持つ。
- 条件：SQLiteの実版、ドライバ版、HostのTarget/実行方式、特権を持たない隔離fixtureを固定する。未対応の機能は`unsupported`として報告し、類似SQLに黙って置き換えない。
- 範囲：更新・Schema Migration、CAS、rollback/fencing、権限越境、並行性をこの小さな面の試験だけで保証しない。

### 確認ケース

| ID | 条件 | 期待する観測・反例 |
| --- | --- | --- |
| P0 | 契約＋試験のみ、Providerゼロ | 契約は読めるが、実行要求は実現不足で停止 |
| P1 | Provider候補を追加 | Core変更なし、同じ契約・試験で検査できる |
| P2 | 値のSQL直結を意図的に混入 | 独立fixtureで不合格。表面的なSQL文字列一致だけでは判定しない |
| P3 | 識別子引用、NULLやエラー処理を誤らせる | ケース別に不合格・未対応を区別 |
| P4 | 契約指紋・Provider artifact・DB版・Targetをずらす | 過去PASSを再利用せず停止／再検証 |
| P5 | 隔離された実SQLiteの読取り | 実DB結果と独立Observationを取得し、合成試験と分けて記録 |
| P6 | Hostの現在受理を撤回する | Contract試験がPASSでも新規実行を拒否 |
| P7 | 手書き・既存候補と生成候補を交換 | 同じ契約範囲で実際の動作・変更コスト・差分を比較 |

**P0〜P7は実施計画であり、現時点でPASSしたと主張しない。** とくにSQLiteの実バージョン・ドライバ・環境が決まるまで、実DBでの適合性は未検証とする。

## 5. 生成AIへ渡す最小限の仕事

AIへ渡すものは「TEI独自の巨大なPlugin manifest」ではなく、既存の正本を参照する**小さな作業入力**とする。次は必須schemaではない。

| 入力 | 意味 |
| --- | --- |
| 受理済みのContract参照とその版 | 改変してはならない外部条件 |
| 実現したい機能面・除外する機能面 | 大きなDB対応範囲の誤認を防ぐ |
| Target/製品版/ドライバ条件 | 実装を具体化するための環境制約 |
| 既存Adapter・Builderへの参照 | 重複Runtimeや独自Resolverの作成を防ぐ |
| 独立fixture／期待結果と試験の入口 | コードを動作で反証する |
| 許可するファイル変更範囲と権限 | 不用意なCore変更・本番DB接続を防ぐ |

AIの出力はSource候補・依存・未対応点・試験コマンド・実際に得た結果の参照で足りる。合否・実行済みと書かれていても、外側の実行証拠がない限り検証済みへ昇格しない。自動修正は独立fixtureが不合格の間のみ行い、実施回数や人手介入を計測する。

## 6. 検証の独立性と安全性

**テストを通ることと、必要な保証が網羅されていることは別。** 特に生成AIは、生成した実装に合わせてテストの期待値まで変更し得る。これを避けるため、PoCでは以下を分離する。

1. **契約・期待値の出所**：AIへ与える前に、契約側の管理者が正負の期待値を固定する。必要なら製品の一次資料と実DBから独立に検査する。
2. **候補実装とテスト改変**：生成AIは原則として実装のみ変更。試験を変更する必要が生じた場合は、契約変更提案として別に記録し、元の試験が通ると偽らない。
3. **合成環境と実Provider**：合成試験だけではSQL実行、ドライバ固有の束縛、Transaction、外部権限を証明できない。実SQLiteの隔離環境で必要範囲を観測する。
4. **契約の受理と実行権限**：Providerの自己申告・試験結果・Build digestは、それ自体で発行者権限やHost実行許可にならない。#951/#1174の責務を再利用する。
5. **失効・変更**：契約、依存、成果物、DB版、権限・Generationの変更で、旧い適合証拠が現在も適用できるか再照合する。完全性を証明できない依存は「変更なし」と断定しない。

## 7. 比較実験と採否

比較する方式：A. 既存Providerを再利用、B. 案件で人が実装、C. 案件でAIが実装・修復。B/Cは可能な範囲で同じ契約と独立試験を使う。既存Providerがない場合はAを「なし」と記録し、架空の比較値を作らない。

測定：契約＋試験の基盤側保守量、案件が変更したファイル数（とくにCore）、実現までの時間・修正反復、見つかった意味差・不合格、対象Targetごとの配備依存、後続の契約変更で再試験した範囲。**「AIによるコード生成成功」だけを成果としない。**

採用に値するのは、Providerがない場合でも要求を安全に表現でき、案件内生成で必要なProviderを**実DB上で限定的に利用できるまで**到達し、独立した試験とHost受理を混同せずにCore変更・人手・保守の削減が観測できた場合。

適合試験の作成／維持が製品別実装網羅より高コストで、しかも重要な差を検出できない場合、共通Contractの粒度を下げるか、手書きProvider中心へ戻す。実装を義務化しない価値は維持できても、追加の契約パッケージ方式は撤回してよい。

## 8. 既存設計との整合・未決

- #951はContractの意味とProvider適合、#1223はComposition/Generation、#1109/#943はBuilder/Artifact/Lock、#267はAI提案・受理、#1063は生成工程、#1448は生成コードの部分採用を担当。**本PoCは「実装ゼロから案件で補完する経路」を検証**し、それらの第二正本を持たない。
- [DB方言の検討案](DATABASE_DIALECT_PLUGIN_DESIGN_2026-10.md)にある`database.rdb`等の契約識別子、製品対応版の表現、方言の分割は**未採用**のまま。DB側の意味差を新しい抽象のために消さない。
- 言語/.NET/JVM/Wasm/Nativeの横断は、契約が物理成果物に依存しないか確かめる後続の比較題材。今回のPoCだけで全Runtime互換を主張しない。
- 原X-TEAのFunction/Table/ScriptとTEI候補の対応、`order_entry.submit_order`の正式な意味、production save caller、Windows GUI受入は、本PoCから推定・確定しない。

**未決事項**：契約と適合試験を実際にどの既存配布物へ格納するか、契約の部分適合とProvider探索の表現、実SQLiteの対象版と独立した期待値の出典、案件固有の候補を共有へ昇格する条件。まず実験して必要性を確かめ、型・構文・管理機構はその結果に基づき既存Ownerが判断する。
