# 標準GUIとCSS・スタイルプラグインの設計案

2026年11月14日。関連する既存課題は[UI構成キット #997](https://github.com/hat47x/tei-platform/issues/997)、[Web/React #1000](https://github.com/hat47x/tei-platform/issues/1000)、[構成Profile #1016](https://github.com/hat47x/tei-platform/issues/1016)、[Studio #1824](https://github.com/hat47x/tei-platform/issues/1824)である。本書はこれらへ返す具体案であり、全GUIの実装完了や採用済みADRを表さない。

## 目指す使い始めの状態

利用者がCSSを書かなくても、標準構成だけで社内システムとして使える画面を提供する。設計者はデータと操作を結び付け、一覧、単票、見出し明細などの構成を選べば、見出し、項目、入力支援、操作、診断が一貫した規則で並ぶ。外観の調整を利用開始までに必ず必要になる作業にはしない。

Desktopの初期構成はWailsの標準ウィンドウとOS連携を使う。WailsはHTML/CSS/JavaScriptをOSのWebViewへ表示する仕組みであり、TEIのフォームやデータ表のデザインシステムはTEIが提供する。[Wailsの説明](https://v3.wails.io/faq/)に従い、OSのメニュー・ダイアログとWeb領域のUIを分ける。現在のStudioはWails v3.0.0-beta.29に固定されており、この設計を理由に依存版を変更しない。

Studioの開発画面と、生成したアプリケーションの利用画面も分ける。Studioでは対象の探索、編集、参照、診断を組み合わせる。一般のアプリケーションでは仕事の手順に合う画面を選び、開発用の三ペインやJSON表示をそのまま標準画面として渡さない。両者でテーマ、入力部品、表、Focusや状態表示の規則を共用する。

## デザインを変更する四つの範囲

| 範囲 | 変更する内容 | 維持するもの |
| --- | --- | --- |
| Theme | 色、書体、文字サイズ、余白、角丸、表示密度 | 項目、操作、選択、編集中の値 |
| Component Skin | 表・入力欄・タブ等の見た目。公開したCSS変数・class・slotを使う | 部品の役割、型付きの値、イベント契約 |
| Layout / Screen Pattern | 一覧、単票、見出し明細、ナビゲーション、領域の配置 | 項目と操作の意味上のID。移動時の状態対応は別途定義する |
| UI Adapter | Web DOM、Desktop WebView、将来のNative/Canvas等の実現 | 表現と操作の契約。媒体固有の制約はAdapterが説明する |

CSSで実現できる変更には、新しい実行コードや独自の描画エンジンを要求しない。理想形では、スタイルプラグインも通常のPluginと同じ管理方式で、CSS、Token、画像や書体の資産、対応契約を提供する。管理方式は現行PoCのRegistryへ固定せず、設計時とビルド時に選択を一貫して解決できる構成を定める。CSSでは変更できない部品構造や動作だけを、LayoutやUI Adapterの拡張として扱う。

## 標準デザインの基本仕様

標準は低彩度の背景と読みやすい本文、控えめな枠線、一つの主アクセントで構成する。選択、Focus、実行中、成功、警告、失敗は役割を分け、色に加えて文言・形・操作状態で伝える。エラーを警告色へ変えても意味上の重大度は変えない。

本文・入力値は日本語を含むシステム書体で読みやすく表示し、標準の本文サイズは14〜16 CSS pxを目安とする。密度を変えても本文を過度に小さくしない。コンパクト表示では主に行間と余白を減らす。文字サイズや画面幅が変わると、フォームは項目群ごとに折り返し、長い表や図は専用のスクロール領域へ収める。

| 標準の構成 | 最低限提供するもの |
| --- | --- |
| アプリケーションの外枠 | 現在地、画面名、ナビゲーション、主操作、状態の表示。Desktopでは標準タイトルバーを既定とする |
| 一覧 | 検索条件、条件の解除、並び順、対象範囲、取得中・未取得・0件の区別、行選択、詳細への移動 |
| 単票 | 常に識別できる項目名、必須・読取専用・単位・入力例、項目別エラー、保存・取消、変更有無の表示 |
| 見出し明細 | 見出しと明細の関係、行追加・削除、選択行、集計、保存単位と途中入力の保持 |
| 対話と診断 | 確認が必要な操作の対象と結果、処理中の状態、再試行できる失敗、原因となる項目への移動 |
| 図表と文書 | 表示倍率、選択、読めるラベル、操作できる代替一覧。科学的な色尺度はブランド色と区別する |

Tabの順序は見た目の順序と一致させる。Focusを見失わせず、メニューやダイアログを閉じたら呼出し元へ戻す。IME変換中の入力を確定操作に使わず、テーマの切替だけで入力値を保存・再解釈しない。非同期応答と画面の資格管理は既存の処理を維持する。

通常文字のコントラスト4.5:1を基準に検査し、Focusと選択も個別に確認する。操作対象の大きさは[WCAGの対象サイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)を参照し、標準のDesktop入力部品は高さ32 CSS px以上を最初の目安とする。[文字コントラスト](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)の数値確認だけで、アクセシビリティ全体の適合とはしない。

## CSSとスタイル資産の接続

テーマの値は意味別のCSS変数として公開する。例えば`--tei-surface`は作業面、`--tei-text`は本文、`--tei-muted`は補足、`--tei-accent`と`--tei-on-accent`は主操作の背景と文字、`--tei-focus`はFocusを表す。値の配列をUI定義へ複写せず、部品が共通の変数を参照する。

最初の実装は`reference/tei-studio-workbench/theme.css`をTokenの定義元とし、`style.css`が配置と部品の見た目を組み立てる。Tokenは`tei.tokens`のCSS layerへ置くため、アプリケーションの通常のCSSから上書きできる。次の例はブランド色だけを変え、部品のSourceを変更しない。

```css
:root {
  --tei-accent: #5b21b6;
  --tei-on-accent: white;
}
```

Themeの切替と、利用者が選ぶ明暗・密度の切替は直交させる。最終的には標準、案件、利用者の設定を構成Profileの規則で解決し、同じ値を複数のスタイルプラグインが所有した場合の優先順位を明示する。読み込んだ順による偶然の後勝ちを、Plugin間の正式な合成規則にはしない。今回の実装には、このProfile解決や任意のプラグインを入れ替えるLoaderはまだ含めない。

スタイルプラグインの設計には対象UI契約の版、対応する部品と媒体、提供Token、必要なCSSと資産、対応する明暗・密度、代替Themeを持たせる。既存Plugin Definitionと構成Profileへの具体的な表現は#997/#1016で判断する。未知のTokenを無断で別の意味へ変換せず、未対応の部品や媒体を診断できるようにする。

CSSはDOM/WebViewの実現方式であり、NativeやCanvasへそのまま適用できるとはしない。色・寸法・文字等の共通TokenをAdapterが対応付け、固有の装飾は媒体別の資産へ分ける。OSのタイトルバーやファイルダイアログはCSSの切替対象から外し、WailsとOSの標準機能で扱う。

## 今回実装する範囲と確認方法

今回の範囲は既存Workbenchの固定色をTokenへ分離し、ライト・ダーク・システム追従と、標準・コンパクトの表示密度を切り替えることである。現在のモデル、Editorの実体、選択、未送信の入力を作り直さず、外観設定は利用者のローカル設定として保存する。保存できない環境でも切替は使える。既知の明暗・密度だけを受け付け、保存値をCSS URLや実行コードへ解釈しない。

実ブラウザーの試験入口は`cmd/tei-studio/test/appearance_browser_smoke.py`とする。WailsのServer版Hostへ接続し、テーマを変えたときのモデル・選択・入力の保持、追加Host呼出しがないこと、CSSだけの上書き、OS設定の変更、狭い画面、文字拡大、保存設定の不正値と保存不能を確かめる。Goの埋込み資産もSource側と同じ内容にそろえる。

この試験はDesktopの実WebView2や利用者の操作評価を代行しない。標準の業務画面、編集・保存を含むフォーム、全グリッド部品、IME・読み上げ、全Tokenの組合せ、第三者のスタイルプラグインは残る検証対象である。Graphの長いラベルが衝突する場合も、色の変更で解決済みとは扱わず、Graph部品側のレイアウト課題として残す。

## 実現する順序

1. 既存WorkbenchでToken・外観切替・状態保持の接続を実装し、現在の参照・診断を壊さないことを確認する。
2. 一覧、単票、見出し明細の標準サンプルを合成データで作り、標準デザインだけで利用できるかを検証する。Studioの成功を業務画面の完成に読み替えない。
3. 一つの案件用CSSを既存の構成Profileから選び、標準との差分だけを保持してBuildへ含める。標準へ戻す経路も検証する。
4. 同じサンプルで二つのスタイルプラグインを比較し、公開したToken・部品契約・互換版と、資産の固定を確認する。
5. WebとDesktopの実利用、キーボード・IME・読み上げ、長い日本語、200%表示、印刷・帳票への影響を確認し、標準デザインの受入を行う。

完成の判断は色を選べたことに加えて、初期画面が追加のデザイン作業なしで使え、外観を変えた後も同じ仕事を続けられることで行う。
