# 多言語プラグインの透過的適用と表示情報の合成

- **状態**：O0の設計案とO1参照実装の検証準備。プラグイン製品の採用済み機構ではない。
- **担当**：[課題 #1551](https://github.com/hat47x/tei-platform/issues/1551)
- **参照コード**：[多言語表示オーバーレイの参照実装](../../reference/multilingual-overlays/README.md)
- **関連**：[表示資源E1](MULTILINGUAL_SEMANTIC_RESOURCE_DESIGN_2026-10.md)、[業務データ・AI翻訳](MULTILINGUAL_BUSINESS_DATA_AND_AI_TRANSLATION_2026-10.md)

## 1. 目標と分離すべき責務

通常の業務プラグインが、後から追加される多言語プラグインの存在を知らなくても、標準のUIや帳票に表示される意味上の名称を多言語化できることを目指す。

ただし、文字列を無差別に置換することを目標にしない。意味上の対象を表す安定した識別子を優先して利用し、表示用の文言、業務レコード、メッセージ書式、認証・承認を分離する。多言語資源が通常プラグインの動作・権限・データモデルへ影響を与えることは許さない。

## 2. どの位置に多言語性を置くか

三つの配置を比較する。

| 配置 | 通常プラグインへの適用 | 判定 |
| --- | --- | --- |
| 各プラグイン内部の文字列辞書 | 既存プラグインの修正が必要 | 独自UIなどの例外として残す |
| DOMや描画結果への事後置換 | 文言や画面構造の変化に弱く意味を追跡できない | 基本方式には採用しない |
| **意味参照に結び付けた表示面の合成** | 正本となる通常プラグインに国際化コードを追加しなくてよい | **初期の第一候補** |

表示面の合成は、業務意味の正本に近いところで表示情報を定義するが、言語ごとの表示文そのものを型や関数の識別子へ含めない。意味の正本を読み替えることなく、利用する表示を差し替える。

### 定義体の概念例

次は試験で使う構造を説明する例であり、採用済みのTEI DSLやプラグインマニフェストではない。

```yaml
environment: env.sales
resolved:
  ordinaryPlugin: std.order-entry@1.2.0
  localePlugin: std.lang-en@1.0.0
surface:
  owner: std.order-entry@1.2.0
  target: { scope: sales, kind: function, id: sales.order.submit }
  field: display-name
  sourceLocale: ja-JP
languagePack:
  provider: std.lang-en@1.0.0
  targetPlugin: std.order-entry@1.2.0
  locale: en-US
  text: Confirm order
  basedOn: sha256:<照合された原文表示名のハッシュ>
  review: confirmed
grant:
  provider: std.lang-en@1.0.0
  targetPlugin: std.order-entry@1.2.0
  locale: en-US
  resource: { scope: sales, kind: function, id: sales.order.submit, field: display-name }
```

通常プラグインは、この追加の言語定義体を持たない。既存の意味参照と標準表示名をすでに持っていることが前提で、環境側の結合定義がそれらを参照する。固定文字列から識別子を自動生成したり、偶然同じ文字列が現れた箇所を一括変更したりしない。

## 3. プラグイン解決と表示資源合成の順序

1. 通常プラグインと多言語プラグインを既存の`plugin.Catalog`で解決する。どの版を利用するかは既存の`plugin.Lock`が管理する。
2. 受理された意味参照と、通常プラグインに所属する表示面の結合定義を取得する。
3. 確定した環境・アプリケーションの適用許可と翻訳資源を照合する。
4. 意味参照、表示名、原文の照合値、通常プラグインの正確な版、翻訳プラグインの版、対象言語を検証する。
5. 同じ表示面・言語に複数の提供元がある場合、具体的にどの提供元がどれを置換するか宣言されていない限り、競合として停止する。
6. 選ばれた翻訳を**既存のE1言語資源**に合成し、E1の言語選択、確認状態、原文改訂、明示的な代替言語、重要文言の禁止規則を適用する。
7. 結果を表示用の投影としてWeb／Desktop／CLIへ返す。元の意味モデルやプラグインの定義を書き換えない。

多言語プラグインが自分で`Grant`や`Override`を発行して、自分の翻訳を優先させる設計にはしない。採用されたアプリケーション／環境の既存の変更受理と権限規則が、結合定義の信頼の境界を担当する。

## 4. 既存プラグインの上書きをどう限定するか

第一段階で扱う対象は、型付き意味参照を持つ`modelref.Node.DisplayName`である。これは各プラグインの「標準表示名」のような情報を後付け翻訳する最小の事例となる。

上書き可能なのは**言語別の表示表現だけ**。業務関数、入力項目の型、権限、制約、プラグイン依存関係、DBの列や内容などは対象外である。

元の言語の表示名そのものをオーバーレイで上書きする方式は、原文の正本が二重化しやすいので初期段階では禁止する。これにより、原文が変わったときには表示名の照合値の不一致として訳文が失効する。

同じ資源の英語訳が二つ登録されたときは、先に読み込まれた翻訳を採用しない。環境の規約で、使用する多言語プラグインと置換対象を明示する。上書き元が別の版へ更新された場合は再審査できるよう、プラグインの正確な版を固定する。

## 5. 多言語対応を想定しない通常プラグインへの適用限界

型付きの意味モデルへ登録されている名称は、追加の翻訳資源を後から関連付けられる可能性が高い。これに対し、次の対象は参照を新たに設ける必要がある。

- 画面内の固定HTML、独自JavaScriptに直接書かれた文言、意味上の参照を持たないボタンや独自ウィジェット。
- 長い説明文、利用者向けのヘルプ、任意の書式を含む文章。
- 動的な日付、数量、複数形、変数展開を含むメッセージ（MessageFormat 2などの型付き書式処理を使う）。
- データベースから読み出す商品説明、契約条項、業務レコードごとに異なる正式な文章。

最後の項目は、後付けの表示文字列置換で実現すべきではない。データモデルに対して「翻訳に従属する文章」「各言語で独立した正式な文章」などの意味上の規約を宣言し、#1453の言語別版管理・データベース保存・受理経路へ接続する。

## 6. Web、Desktop、生成AIとの関係

標準UIに対しては、描画するテキストをキーで問い合わせられるようにする。Web標準のWeb Components／Lit、DesktopのWebViewであっても、表示の意味上のキーを維持できれば同じ翻訳資源を使える。Computer Useで見える表示文字列は翻訳しても、要素のプログラム上の識別子や操作の意味を翻訳文へ依存させない。

生成AIは、通常プラグインに不足している意味参照の候補を見つけたり、翻訳対象候補や用語集を作成できる。ただし、既存の正本へ識別子・意味・権限を書き込むための判断権限は持たせない。確認済みの意味参照と確定した翻訳元の版に対して、翻訳の変更候補を作る。多言語データのAI翻訳については#1453のD3a以降を再利用する。

対象言語の資源を配布時に抽出する場合、既存プラグインの固定情報、合成に用いた適用許可、原文と翻訳の版、必要な言語集合を入力として決定論的に導出する。実行先へ翻訳管理機構やAIサービスを常駐させることを必須としない。

## 7. 試験と段階

- **O0**：以上の構成と責務の決定候補。
- **O1**：既存の型付き意味参照・プラグインの選択済み集合・E1の資源選択を使う読み取り専用の合成と衝突検査。固定した受注例で実証。
- **O2**：実際の標準UI定義体とPlugin Lock／Editorへの接続。言語資源の提出、変更受理、実際の標準表示コンポーネントでの表示。
- **O3**：Web／Desktop／CLI向けの資源選択と配備、キャッシュ無効化、版固定、言語ごとの表示書式・アクセシビリティ、外部の多言語プラグインの認証・信頼の接続。

O1を実装できたことは、通常プラグインの**任意の文字列**を多言語化できることや、本番環境での安全な動的上書きが証明されたことを意味しない。受理・権限やロックへの接続がまだ成立していない箇所は、別の段階として残す。
