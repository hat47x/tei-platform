- 状態：検討案（採用前）。決定した内容はADRへ移す。実装済みの構成や実証済みの能力を示す文書ではない。
- 日付：2026年10月13日
- 関連：[ADR-0007](../adr/0007-database-driver-assembly.md)、[ADR-0013](../adr/0013-offline-physical-realization-policy.md)、[ADR-0015](../adr/0015-provider-owned-migration-sql-rendering.md)、[ADR-0032](../adr/0032-composition-kernel-replacement.md)、[ADR-0033](../adr/0033-core-and-plugin-subprojects.md)、[命名の指針](../../docs/naming.md)、[契約に基づく問い合わせの設計](DATABASE_CONTRACT_QUERY_V1_DESIGN.md)

## この文書の役割

複数のデータベース製品を扱うとき、製品に共通する関係データベース（RDB）としての扱いと、製品ごとの方言をどのプラグインに置くかを検討する。当面の対象はPostgreSQLとSQLiteの2製品とし、Oracleを特別扱いしない。

扱う範囲は、プラグインと契約の名前、方言として吸収する項目の一覧、製品の版の扱い、現行コードの仕分け、SQLiteを加えたときに契約へ生じる変更、実施の順序である。実装、ADRの採否、Goモジュールの分割は扱わない。

正本との関係は次のとおりである。

- 構成の目標はADR-0032とADR-0033が正本である。この文書はその範囲内で、データベースに固有の分割を提案する。
- 現行の構成は[全体構成](../../docs/architecture.md)、実装状況は[実装状況](../../docs/status.md)が正本である。
- 命名は[名称と用語の指針](../../docs/naming.md)が正本である。この文書の識別子は案であり、採用までは指針を変えない。

## 現在の案

1. プラグインは`tei.database.postgres`と`tei.database.sqlite`とする。パッケージ階層にRDBかどうかを含めない。
2. RDBであることは、共通の契約`database.rdb`を洗練して提供していることで確定する。共通の実装を配る必要が確認できた場合だけ、`tei.database.rdb`を別のプラグインとし、通常の依存で参照する。
3. 方言は、小さな機能面（以下「面」）の組合せとして表す。面ごとに、対応・未対応・対応する製品版の範囲を宣言し、未対応を黙って別の意味へ落とさない。
4. 製品の版は、プラグインの名前や版に含めず、環境が明示する値と、プラグインが宣言する対応範囲で扱う。
5. 順序は、SQLiteを既存の継ぎ目に当てて製品固有の前提を洗い出し、その差から契約を起こす。2製品がそろう前に抽象を固定しない。

## なぜ分けるのか

現行の構成では、製品に依存しない関係の処理（期待する物理構造の導出、差分、移行の計画、明示SQLの実行）が、製品の実装と同じ層に混ざっている。製品を増やすたびに、共通の層へ製品名の分岐を足す形になる。

```text
製品を足すと、共通の層に分岐が増える
  realization.PolicyFor   switch { postgres, oracle }
  migration.Render        switch { postgres }  ＋ PostgreSQL専用の削除ガード
  migration.postgres_apply  PostgreSQL専用
```

また、PostgreSQLだけを使う成果物に、SQLiteの方言を含めたくない。ADR-0033の「実行先ごとの不要機能除外」を満たすには、方言を独立して選べる必要がある。

## 識別子

[命名の指針](../../docs/naming.md)は、プラグイン（`tei.`で始まる）、機能（役割を示す名称のまま）、標準の意味名前空間（`std.*`）を分けている。この区別に従う。

| 区分 | 識別子（案） | 備考 |
| --- | --- | --- |
| 製品別プラグイン | `tei.database.postgres`、`tei.database.sqlite` | 現行の`tei.database.postgres`を維持する |
| 共通プラグイン | `tei.database.rdb`（必要な場合だけ） | 共通実装を配る単位。RDBであることの確定には使わない |
| 基底の契約 | `database` | 製品を問わない部分（提供者の識別、能力、観測） |
| RDBの契約 | `database.rdb` | `database`を洗練する。SQL、表、トランザクション、関係の差分 |
| 製品の機能 | `database.postgres`、`database.sqlite` | 現行の`database.postgres`を維持する。`database.rdb`に適合し、製品固有の拡張を持つ |

`std.*`は業務上の意味の型に使う名前空間であり、プラグインや契約の識別には使わない。

### 継承ではなく契約への適合として表す

ADR-0032は、固定の機能種別と、プラグインの配布単位どうしの`requires`を、実行時の依存の唯一の表現にしない。したがって、RDBであることをプラグインの継承では表さない。

- 製品プラグインが`database.rdb`を提供し、適合試験に通ることで、RDBとして扱う。
- 共通の実装を再利用するために`tei.database.rdb`が必要になった場合は、配布上の制約として`requires`で参照する。これは契約への適合とは別の軸である。
- 深い継承は採らない。共通の実装を共有することと、契約に適合することを混ぜない。

現行の合成の試作（`internal/composition`）には、契約が別の契約を洗練するという関係がなく、完全一致の依存だけを扱う。洗練の関係をどう表すか（洗練の関係を足すか、別の契約識別子と依存で表すか）は、ADR-0032のM2（契約中心の依存解決）で決める。この文書では決めない。

### 用語の衝突

- 「提供者（provider）」は、TEIでは製品の識別を指す（`postgres`、`sqlite`）。環境の`DatabaseInstance.Provider`がこれである。
- 「方言（dialect）」は、すでに`ProviderExpression.Dialect`が式の文法を表すために使っている。製品の識別とは別の概念である。
- Springでは、製品と方言がほぼ同じ意味で使われる。TEIでは、製品の識別と、文法・振る舞いの組合せを分けたまま使う。

## 方言を面に分ける

Springの`Dialect`は、一つの大きな基底ではなく、SQLの限定句、ロック句、識別子の処理、ID生成、型の変換などの小さな部品の組合せである。R2DBCでは、パラメータの記号の流儀と例外の翻訳も別の部品である。これをTEIの既存の考え方（能力フラグ、製品が所有する処理）に合わせる。

以下の表の「所有」は、既存のADRで決まっている所有者である。

| 面 | 内容 | 所有（根拠） |
| --- | --- | --- |
| 識別子の引用と比較 | 引用規則、大文字小文字の扱い | 製品（ADR-0014、ADR-0015）。ただし共通の差分処理は識別子を一律に小文字へ畳んでいる（後述） |
| 物理型の対応 | 保存型から製品の型への対応と、往復で値が変わらないことの宣言 | 製品（ADR-0013） |
| 索引の既定値と正規化 | 既定の方式、昇降順とNULL順の既定 | 製品（ADR-0013、ADR-0014） |
| 式の表現 | 作成者の式と、製品が復元した式の区別 | 製品（ADR-0012） |
| 移行SQLの描画 | 差分から文を作る。実行の単位（後述）を含む | 製品（ADR-0015） |
| 破壊的変更の事前条件 | 削除してよいかの確認 | 製品（ADR-0027） |
| パラメータの束縛 | 記号の流儀（`$n`、名前付き、`?`）と、書き換えの要否 | 製品 |
| エラーの分類 | 製品の固有コードから共通の分類への対応 | 製品。**現行コードには未実装** |
| カタログの観測 | 物理構造の読取り | 製品（ADR-0007） |
| 接続の初期化 | 接続ごとの設定（SQLiteの`foreign_keys`、`busy_timeout`など） | 製品。**新規** |
| 説明計画 | 実行計画の取得 | 製品。任意の面 |
| パーティションの観測 | 製品固有の拡張 | PostgreSQL（ADR-0026） |
| 能力フラグ | 上の各面の対応可否 | 契約の宣言。**対応する製品版の範囲を持たせる** |

製品の方言を、SQLの自動翻訳とは考えない。Contract Query（契約に基づく問い合わせ）のSQLは、対象と製品ごとに明示して書き、対応するSQLがなければ停止する現行の規則を維持する。標準のCRUD（[#1127](https://github.com/hat47x/tei-platform/issues/1127)）などでSQLを生成する場合、生成するSQL（限定句、生成キーの取得、競合時の更新など）が方言の面に加わるが、暗黙のSQL生成を禁じる#1127の範囲との関係を先に決める必要がある（未決事項）。

## 製品の版の扱い

現行では、`DatabaseInstance`は`ID`、`Definition`、`Provider`だけを持ち、製品の版を持たない。`Capabilities(ctx, instance)`は引数に実体を受け取るが、PostgreSQLの実装は固定の真偽値を返して引数を使っていない。式の正規化の版（`ExpressionNormalization.ProviderVersion`）は定義されているが、設定されない。

提案は次のとおりである。

1. 環境が、製品の版を明示して宣言する。版の自動判定は採らない（技術を推測しない方針）。
2. プラグインが、対応する製品の版の範囲を宣言する。能力フラグは、面ごとに版の範囲を持てる形にする。例：SQLiteの列の削除は3.35以降。
3. 実行時に観測した版は検証根拠として記録し、宣言と食い違えば停止する。
4. 製品のメジャー版を、プラグインのIDや版に含めない。プラグインの`compatibleMajor`は、プラグイン自身の互換性を表す別の軸である。

IDを分けるのは、保守する版が大きく異なり、一つのプラグインでは対応範囲を表せない場合に限る。その場合も、プラグインの版番号を製品の版と混ぜない別名を使う。この判断は、実際に必要になった時点で行う。

### 実行系の重複

- PostgreSQLの閲覧用Executor（`queryruntime/postgres/executor.go`）は、行の走査の処理（束縛、`QueryContext`、列取得、走査、値の安定化）を、同じ`postgres/runner.go`とほぼ同じ内容で再実装している。Oracleの`runner.go`にも同じ走査の処理がある。走査の処理は、製品に依存しない共通の部品にできる。
- 参照用と明細用の契約問い合わせ（`ExecuteReferenceContractQuery`、`ExecuteHeaderDetailContractQuery`）は、結果の検査の手順がほぼ同じである。
- 実行の配線（製品別の実行器の登録）は、現状は`tools/`の参照実装が手で組み立てている。

### 製品固有の面が共通の入口を持たないもの

`provider.Provider`の小さなSPIは、`ID`、`Capabilities`、`Introspect`だけを持つ。移行の描画、破壊的変更の事前条件、パラメータの束縛、観測は、共通の入口がなく、`migration`や`cmd/tei`などが製品の実装を直接参照している。

### 物理モデルのPostgreSQL寄りの項目

`physical`と`persistence`には、スキーマ、演算子クラス、索引の方式、`UniqueNullTreatment`（PostgreSQL 15の`NULLS NOT DISTINCT`）、索引の状態（有効・準備済み・使用中）、含む列、実体化ビューなど、製品によって意味が異なる項目がある。パーティションは、ADR-0026の判断どおり、共通のモデルには入れていない。

## SQLiteを加えたときの契約への影響

以下は、リポジトリの実装から導いた分析である。SQLiteの挙動は実機で検証しておらず、機能の導入版などは検証が必要である。

### 保存型の往復

SQLiteの型は動的で、型の宣言から決まる「型の親和性」だけが働く。十進数を数値型として宣言すると、浮動小数に変換されて値が変わる。したがって、保存型ごとに、値を失わない表現を契約として宣言し、試験で確かめる必要がある。

| 保存型 | 候補とする物理表現 | 注意 |
| --- | --- | --- |
| `int64` | `INTEGER` | 主キー列は別名の扱いになり、NULLが入りうる。`NOT NULL`を明示する |
| `varchar` | `TEXT` | 長さの上限が強制されない。必要なら`CHECK`で補う |
| `text` | `TEXT` | 照合の既定が二進比較。大文字小文字の無視は英字だけ |
| `datetime-tz` | UTC固定幅の`TEXT`、またはマイクロ秒の`INTEGER` | 型名`DATETIME`は数値の親和性になるため使わない。ドライバが時刻を書く形式は未確認 |
| `decimal` | 正規化した十進文字列の`TEXT` | 数値型の宣言は15桁を超えると値が変わる。算術と並べ替えには追加の手当てが要る |
| `json` | `TEXT`と`CHECK(json_valid(c))` | 書いた文字列のまま残る。PostgreSQLの`jsonb`のようなキー順の正規化はされない |

読取りの側では、`PRAGMA table_info`が返す型は宣言の文字列そのものである。複数の保存型を`TEXT`に畳むと、物理構造から元の保存型を逆引きできなくなる。型名の工夫、またはTEIが管理する別の記録で、判別できるようにする必要がある。

### 物理モデルの項目

意味がない、または縮む項目は、黙って無視せず、明示的に「未対応」として拒否する（PostgreSQLの描画が、未対応の変更を明示的に拒否する流儀と同じ）。

| 項目 | SQLiteでの扱い |
| --- | --- |
| 演算子クラス | 概念がない。未対応 |
| `UniqueNullTreatment`の`not-distinct` | 概念がない（常にNULLを区別する）。未対応 |
| 含む列（`INCLUDE`） | 概念がない。未対応 |
| 索引の方式 | `btree`のみ |
| 索引の状態 | 概念がない。常に有効として合成するか、観測なしとする |
| 実体化ビュー | 概念がない。未対応 |
| スキーマ名 | 同一データベース内の階層がない。`main`に正規化する規則が要る |
| 制約名 | 一意制約と外部キーの名前は保存されない。構造（列）で比較する |
| NULL順の既定 | SQLiteはNULLが最小値で、昇順で先頭。PostgreSQLの正規化と逆になるため、別の正規化が要る |

### 移行

- 表の作成で、列がゼロの`CREATE TABLE`は構文エラーになる。現行の「表の作成の後に列の追加が続く」モデルは、そのままでは成立しない。表の作成で列を持たせるか、SQLite側で畳み込む必要がある。
- 列の型や`NOT NULL`の変更、主キーの変更、外部キーや一意制約の追加・削除は、直接の`ALTER`ができず、表の作り直しが要る。
- 表の作り直しでは、`foreign_keys`の設定をトランザクションの外で切り替える必要がある。現行の`Realization.Statements []string`は文の平坦な列であり、「トランザクション内の文のまとまり」と「外に置く前後の文」を表せない。`Realization`の構造を拡張する必要がある。
- 作り直しは、データ量に比例した時間と書込みロックを要する。SQLiteは書込みを一つに絞るため、他の書込みが待たされる。破壊的変更の事前確認と、新しい観測に基づく再描画の確認（PostgreSQLの`postgres_apply`と同じ考え方）が要る。

### 式の比較

PostgreSQLは、カタログから正規化された式を得て、製品の版とともに比較できる。SQLiteには、式の正規化の権威がなく、テキストを抽出するだけである。式の索引や部分索引は、現行の規則では「未解決」になりやすく、未解決の差分は描画が拒否される。作成者の式どうしの文字列比較を許すか、未対応とするかを決める必要がある。

### 並行性と効果の確定

SQLiteは書込みが一つで、リポジトリの参照試験は`BEGIN IMMEDIATE`を使っている。`database/sql`の標準の開始では直接指定できず、ドライバ側の設定に頼るため、接続の初期化とトランザクションの開始方式が、方言の面（接続の初期化）に入る。外部キーの強制と待ち時間の設定も、接続ごとである。

### ドライバーと依存の規則

- 現行のリポジトリは、SQLiteの参照試験を`tei_sqlite_reference`と`cgo`のタグの下に置き、「TEI製品にcgoやSQLiteの依存を追加しない」としている。
- 製品としてSQLiteを第二のデータベースにするなら、この規則を解除するADRが要る。純粋なGoの実装を使えばcgoの規則とは衝突しないが、SQLiteへの依存を持たない規則とは衝突する。
- ADR-0007に従い、Providerは`*sql.DB`を受け取るだけにして、ドライバーの選択と登録は組立側の責務に残す。この形なら、SQLiteのProviderの試験を特定のビルドタグの下に置き、製品本体の`go.mod`への追加を切り離せる。

## 実施の順序（案）

各段階を小さなPRに分ける。段階は、結果を見て組み替える。

1. **この設計文書の合意。** 合意した内容をADRへ移す。
2. **製品に中立な処理の切り出し（挙動を変えない）。** 走査の処理を共通の部品へ移し、PostgreSQLの閲覧用Executorがそれを使う形にする。`migration.Render`のPostgreSQL固有の削除の事前条件を、製品の実装へ戻す。製品から方針への分岐を、列挙型の分岐から、登録に基づく解決へ置き換える準備をする。
3. **SQLiteの物理実現の方針。** 保存型の対応、未対応の項目の明示的な拒否、NULL順の正規化を、データベースなしで実装し、試験する。
4. **SQLiteのカタログと実行器。** ドライバーは組立側に置き、タグの下の参照実装として、観測・束縛・実行・往復を実測する。
5. **契約の導出。** 2製品の実装の差から、`database.rdb`の形（面と版の範囲）を起こし、2製品に同じ適合試験を適用する。データベースを要しない純粋な面は、DBなしで試験できる。
6. **規則の整理。** 依存の規則を解除するか、タグの下に残すかをADRで決める。ADR-0033に沿って、公開契約と回帰試験が成立したものから`plugins/`へ移す。

## 未決事項

## 根拠と、この文書から言えないこと

根拠は、`internal/database/`、`internal/driver/`、`internal/plugin/`、`internal/environment/`、`reference/effect-fence/`、`reference/multilingual-business-data/`の読取りと、既存のADRである。実行試験や実機での検証は行っておらず、SQLiteの挙動と導入版の記述は、実際の検証で確かめる必要がある。

この文書は、契約の最終形や識別子の採用を決めるものではない。PostgreSQLとSQLiteの2製品で試すまで、抽象化が適切に成立するかはわからない。Oracleは、契約が固まった後に同じ手順で加える。手元のOracleでの参照実装（[PR #1636](https://github.com/hat47x/tei-platform/pull/1636)）は、その入力として参照できるが、本文書の判断の根拠にはしていない。
