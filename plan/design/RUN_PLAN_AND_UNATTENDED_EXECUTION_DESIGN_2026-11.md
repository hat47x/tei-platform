- 配備の実行には、所有の記録（フェンシングトークン）、`lease-policy`（`max-lifetime`・`renew-before`・`revoke-timeout`・`renewal-failure fail-closed`）、試行の記録がある（[`reference/workspace/environments/production/environment.tei`](../../reference/workspace/environments/production/environment.tei)、`cmd/tei` の `deployment-*`）。
- 一括処理の意味上の規則（一括実行識別子、項目キー、チャンク、項目ごとの四状態、再開、取消）は副作用の設計8章にある。

不足。

- 一括処理を**意味の層で宣言する手段**がない。どの能力を、どの業務キーで、何回まで、どの順で走らせるかが、コードと運用に散っている。

- **無人で走らせてよいか**の判定が、宣言から導けない（操作面の設計8章の適用先がない）。
- 帳票・確認一覧などの**出力**が、どの実行のどの時点の結果かを主張できる契約がない。
- 所有記録の永続化（#2146）と、一括実行の排他の関係が未接続。

## 2. 宣言の候補

```tei
run-plan sales.monthly_close {
    operation sales.decide_close_date
    operation sales.import_shipment
    operation sales.close_period
    key sales.period
    concurrency singleton
    resume checkpoint
    output sales.close_statement
    autonomy unattended
}
```

| 要素 | 必須 | 意味 |
| --- | --- | --- |
| `operation` | 必須（複数可） | 順に実行する操作。操作は既存の `capability` か、操作面が導出した標準操作を指す |
| `key` | 必須 | 実行を業務上同定する入力項目。処理日付、対象月、取引先など。実行の識別子はここから決まる |
| `concurrency` | 任意 | `singleton`（同じ業務キーで同時に一つ）／`per-key`（キーごとに一つ）。既定は `singleton` |
| `resume` | 任意 | `checkpoint`（項目の進捗から再開する）／`none`（途中で止まったら次回は最初から。既定）。`none` の場合は出力の冪等を別に要求する |
| `output` | 任意 | 実行の結果として生成する出力（帳票・確認一覧）。読み取り専用の投影である |
| `autonomy` | 任意 | `unattended` を宣言する場合だけ書く。宣言が無ければ `attended`（操作面の設計8章） |

適用範囲は、**同じアプリケーションの内側で完結する実行**に限ります。範囲・期限・権限を持つ委任（他の組織・他の製品の実行環境へ処理を渡すこと）はEKIの担当であり、TEIは委任の必要性を判断しません（[TAI上流への立ち戻り](../workstreams/TAI_UPSTREAM_ALIGNMENT_2026-11.md)）。無人の実行の宣言も、TEIの内側の実行にだけ効きます。

宣言しないこと。

- 起動時刻の暦（営業日カレンダー）は書かない。暦は #1720（P-TIME-05）の担当であり、ここでは「いつ起動するか」を持たない。起動は Host と運用の責務である。
- スケジューラ、キュー、リトライ回数を持たない（副作用の設計11章が再試行方針を固定しないとしている）。
- 実行主体の資格情報を持たない。資源の解決は環境の宣言（`resource`／`grant`）が持つ。

## 3. 実行の同定

一つの実行は、次の組で同定する。

```text
runKey     = (plan の識別子, key の値)
attemptId  = runKey ごとに単調に増える試行の識別子
fenceEpoch = 所有の世代（リースの更新ごとに増える）
```

規則。

1. `runKey` が同じで、前回が**完了していない**場合は、再開（`resume checkpoint`）または拒否（`resume none`）のどちらかである。黙って新規実行にしない。
2. `runKey` が同じで、前回が**完了している**場合は、拒否する。再実行が必要なら、業務キーを変える（対象月を変える、訂正の実行として別の計画にする）か、明示の再実行の操作を作る。
3. `fenceEpoch` が現在の所有の世代と一致しない実行は、書込みを行わない（#2146）。古い担当が復帰しても、自分の世代でしか書けない。
4. 実行の記録（開始、試行、進捗、終了、出力）は、対象の業務データと同じ保存先に置ける場合だけ同一の確定境界に含める。置けない場合は、副作用の設計7章の「独立した外部効果」として扱い、原子性を主張しない。

## 4. 項目ごとの結果

一括の結果は、件数の集計ではなく、項目ごとの記録から導出する。項目の状態は副作用の設計8章の五つ（確定した／確定しなかった／不明／対象外として飛ばした／未着手）をそのまま使う。

- `不明` の項目は、再処理の前に照会で解消する。解消しないまま再処理しない。
- 集計（件数、金額、失敗の内訳）は、項目の記録から決定的に導出する。集計値を別に保存して正としない。
- 実行の途中で対象の集合が変わった場合、位置ではなく項目キーで再開する（8章）。

## 5. 出力（帳票・確認一覧）

出力は、実行の結果を読むための**読み取り専用の投影**である。

- 出力は、`(対象の時点, 規則の版, 実行の識別子)` を持つ。同じ三つからは同じバイト列が出ることを要求する（決定的であること）。
- 出力の再生成は、元の実行の記録から行う。再生成のたびに業務データを読み直して値を変えない。
- 出力に、その実行が確定した項目と、不明・失敗の項目を分けて載せる。失敗を 0 や空値に置き換えない。
- 出力の形式（PDF、CSV、HTML）は実行先の責務であり、意味の層は「何を載せるか」だけを決める。

## 6. 無人の実行

`autonomy unattended` を宣言できるのは、操作面の設計8章の条件をすべて満たす場合だけである。

1. 実行主体が環境に宣言されている（サービス主体）。
2. 権限が呼出しごとの人の判断に依存しない。
3. 冪等の識別子が宣言されている（効果規則の `idempotency-key`、または `runKey`）。
4. 人の判断・承認・例外判断の段階を含まない。

一つでも満たさない場合、宣言は診断で拒否し、`attended` として扱う。**「無人にしたい」という希望を宣言として受け付けない。**

無人実行の停止条件も宣言する。

- 失敗が既定の閾値を超えた場合に止める（閾値は運用が決める。意味の層は「止めることができる」ことだけを要求する）。
- 所有の更新に失敗した場合は `fail-closed`（`lease-policy` の既存の宣言を使う）。
- 未知の結果（`不明`）が残ったまま次の段階へ進まない。

## 9. 停止条件

- スケジューラやキューを新しく作り始めた場合は停止する。起動は Host の責務であり、意味の層は「何を、どの業務キーで」だけを持つ。
- 完了した実行の再実行を、既定で許可した場合は停止する。
- `不明` を失敗に丸めた場合は停止する。
- `autonomy unattended` を、条件を確かめずに受理した場合は停止する。

### P2 実行の同定と拒否規則（2026-11-03 追記）

実行の同定と、開始・再開・拒否の判定を実装しました（`internal/runlog`）。

```go
runKey    = RunKey(計画ID, キーの値)   // 区切りは unit separator（値にカンマが入っても偽造できない）
attempt   = 前回 + 1
fenceEpoch = 前回 + 1（再開のたびに増える）
```

| 前回 | `resume` | 判定 |
| --- | --- | --- |
| 無し | 任意 | `start`（attempt 1・fence 1） |
| 未完了 | `checkpoint` | `resume`（attempt/fence を +1） |
| 未完了 | `none` | **`refuse`** |
| 完了 | 任意 | **`refuse`**（業務キーを変えるか、明示の再実行の操作を作る） |

- `Owns` は現在の attempt と fenceEpoch が一致するときだけ真。古い担当は書けない。
- 記録は JSON Lines。壊れた行はエラーとして報告し、その行より前は返す。
- 実行の記録は受理済みの意味ではないので意味モデルには置かない。

**未着手**: 実際の実行ループへの接続、項目ごとの結果、無人実行の拒否試験、`autonomy unattended` の検証（操作面の自律区分との突き合わせ）。
### 実行ループ（2026-11-04 追記）

`execution.RunPlan` で、同定 → 判定 → 操作の順次実行 → 記録までをつなぎました。

- 判定が `refuse` のときは**何も実行せず**、判定を返す（エラーではない）。
- 実行する場合は `running` を記録してから操作を順に実行し、全部通れば `completed`、途中で止まれば `failed` を記録する。
- 操作の失敗は `StepResult` として返し、エラーにしない（どの項目で止まったかを残すため）。
- **`resume` はまだ実装していない**。項目ごとの進捗を記録していないため、再開すると黙って作業を繰り返すことになる。そのため再開の判定になった場合は**エラーで止める**（できていないことを、できたように見せない）。

**未着手**: 項目ごとの進捗の記録と再開、出力の生成、無人実行の拒否試験、期間・効果のガードを各操作の手前に置くこと。
### 項目ごとの進捗と再開（2026-11-04 追記）

`runlog.Record` に `steps`（この実行で終わった操作）を持たせ、**再開を実際に成立**させました。

- 操作が終わるたびに `running` と `steps` を追記する（途中で止まっても、どこまで終わったかが残る）。
- 再開の判定では、記録済みの `steps` を**飛ばして**残りから実行する。終わった操作は `StepResult{Detail: "already finished in an earlier attempt"}` として結果に残す（実行はしない）。
- 再試行のたびに `attempt` と `fenceEpoch` が増える。古い世代は `Owns` で書けない。

**未着手**: 出力の生成、無人実行の拒否試験、各操作の手前の期間・効果ガード、失敗した操作の再試行方針。
### 無人の実行の停止（2026-11-04 追記）

`autonomy unattended` の計画は、**前提が満たされているかを確かめられない限り実行しません**。

- `RunPlan` に `PreconditionFunc`（操作ごとに、満たされない理由を返す。空なら満たされている）を渡す。
- 無人で `PreconditionFunc` が nil の場合、理由は「確かめる手段が無い」として**止める**。人がいない状況では、確かめられないことを「たぶん大丈夫」に読み替えない。
- 止まった場合は `StepResult{Status: "blocked"}` と `runlog.Blocked` を記録する。**失敗（failed）とは別**で、何も実行していないことを表す。
- `attended` の計画は従来どおり（人がいるので、操作側の拒否に委ねる）。

**未着手**: 期間・効果の前提を実際に `PreconditionFunc` へ接続すること、無人実行の承認（誰が無人を許したか）の記録。
### 期間の前提との接続（2026-11-04 追記）

`execution.PeriodPreconditions(surface, states)` を追加し、操作面の期間の拒否をそのまま `PreconditionFunc` として渡せるようにしました。

- 期間が閉じていて能力が拒否される場合、その `Detail` が理由になる → 無人実行は**その操作の手前で止まる**。
- 期間が開いている、または期間を持たない能力は理由を返さない → 実行する。
- 期間の状態の出所は、期間と同じく呼び出し側（運用の記録・`periodstate.File`）が渡す。

これで「期間の宣言 → 操作面 → 束縛 → 無人実行の停止」が一本につながりました。
