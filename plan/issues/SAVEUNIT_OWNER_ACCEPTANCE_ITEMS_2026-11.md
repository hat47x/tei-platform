# 汎用保存機構（saveunit）：Owner受理が必要な事項と未対応表現

この文書は、`internal/saveunit` パッケージの実装により到達した現在地点を記録し、Ownerによる業務意味の受理が必要な事項や、未対応の表現を整理する。

## 受理済みの前提

- 保存単位（`SaveUnit`）は、Data Providerの違いを吸収する共通契約として設計している。
- フィールド変更は `Value` / `SetNull` / `Delete` / `Unchanged` の4状態で区別する。
- 保存順序はセマンティックモデルのリレーションから topological sort で導出する。
- トランザクション、ロールバック、楽観的排他、フックは共通契約の範囲内で提供する。

## Owner受理が必要な事項

1. **複合キーの変更语义**
   - 現在の実装は `EntityChange.Key` を文字列として扱い、変更前後の同一性は文字列比較で判定する。
   - 複合キーの構成要素が変更された場合（例: `order=ORD-1/line=1` → `order=ORD-1/line=2`）を「削除＋作成」と扱うか「更新」と扱うかはOwnerの業務意味に依存する。
   - 関連: #1126（Data/Relation）

2. **複合キー構成要素へのNULL代入**
   - `FieldChange.SetNull` は任意のフィールドに適用できるが、複合キーの構成要素を NULL にすることが业务的に許容されるかはOwnerが判断する必要がある。
   - 候補キーの一部が NULL になった場合の一意性確保の責任範囲も未確定。

3. **部分的な複合キー更新の可否**
   - 複合キーを構成する属性の一部だけを更新するパッチ（例: `order_id` だけ変えて `line_no` を変えない）が业务的に意味を持つかどうかはOwnerの受理を要する。
   - 現実装は这样的なパッチを受理し、キー文字列の変更として扱う。

4. **空集合置換と複合キー親子関係**
   - 親エンティティの複合キーが変わった場合、子エンティティのリレーションkeyも連動して変わるべきかどうかはOwnerの判断に依存する。
   - `OnDelete: cascade` と複合キーの組み合わせで、キー変更時に子を削除するか更新するかも未確定。

5. **Unchanged指定と複合キー**
   - `FieldChange.Unchanged` を複合キーの構成要素に指定した場合、そのフィールドを絶対に変更しないという保証が业务的に正しいかどうかはOwnerの受理を要する。
   - 楽観的排他制御のgeneration checkと複合キーのどちらを優先するかも未確定。

6. **フックの観測範囲と複合キー**
   - バリデーションフックやBefore/Afterフックが `EntityKey` として複合キー全体を受け取る設計だが、キー構成要素ごとに個別のhookを実行するべきかはOwnerの業務フロー依存である。

7. **外部サービス連携と複合キー**
   - DBトランザクション内で外部サービスを呼び出す場合、複合キーの一部変更で外部资源のkeyも変わる際の補償処理の責任範囲は未確定。

## 未対応の表現

1. **複合キーの型安全な表現**
   - 現在 `EntityChange.Key` は単一文字列であり、複合キーの構成要素を個別にバリデーションしたり、型安全に扱う仕組みを持たない。
   - 候補キー（`CandidateKeys`）の定義はセマンティックモデル側に存在するが、保存機構側では名称解決に利用していない。

2. **複合キー専用のSQL生成**
   - モデルに定義された候補キーから、INSERT/UPDATEの WHERE 句や MERGE 文を生成する機能は未実装である。
   - 現在の `saveunit` は Data Provider に依存しない抽象層であり、SQL固有の扱いは今後の拡張に委ねる。

3. **複合キー制約の実行時検査**
   - 複合キーの一意性制約や、参照整合性制約を実行時に検査する機構は未実装である。
   - 制約違反は `ConstraintViolation` エラー型で表現する設計だが、実際の検査ロジックは今後の拡張に委ねる。

4. **複合キーを含む楽観的排他**
   - 現在の楽観的排他はフックベースで実現しているが、複合キーの特定の構成要素だけが変わった場合の検出方法は未確定。
