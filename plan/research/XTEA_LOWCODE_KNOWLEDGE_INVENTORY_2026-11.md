## 3. 全体像

### 3.1 三つの成果物と四つの役割

X-TEAのローコードは、**設計モデル**、**実行仕様**、**解釈実行**の三つを分け、作者環境と実行環境を分業させています。

```text
設計モデル（.xead）
  業務・データ・機能の三視点、機能種別、入出力表
        │ Modelerで編集
        ▼
実行仕様（.xeaf）
  画面項目、列、絞り込み、ボタン、帳票句、イベントスクリプト
        │ Editorで編集。DBと照合
        ▼
解釈実行（Driver / Server）
  機能種別ごとの画面を組み立て、SQLを発行し、スクリプトを評価する
```

設計モデルは「何の機能か」を、実行仕様は「どう見せ、どう操作し、何を実行するか」を持ちます。両者は同じ要素IDで結ばれ、EditorはModelerの設計を取り込みます（`E:Editor.java L27311–27417` のImport、`E:Editor.java L27737–27786` の`.xeaf`保存）。Driverは実行仕様を読みます（`D:Session.java L448–487`。ファイルのほかURLも受け付けます）。

### 3.2 生産性の源

観察した生産性は、次の五つから生じていました。

1. **閉じた機能型**（8種）が、一覧・単票・ヘッダ明細・印刷・一括更新の定型を固定する。
2. **項目・列・絞り込み・ボタン・帳票句**を、コードではなく属性の組合せで宣言する。
3. **イベントとスクリプト**が、定型の間に案件固有の検証・導出・呼出しを差し込む。
4. **標準業務ライブラリ**（日付・年度・税・通貨・採番・利用者設定）が、どの案件でも要る処理を用意する。
5. **作者支援**（検査、差分、取込み、定義書・DDL・一覧の出力）が、設計と実装の往復を軽くする。

TEIが引き継ぐ価値があるのは、この五つが**何を可能にしたか**であり、Java Swingの画面や`.xead`/`.xeaf`の書式ではありません。

この抽出から、次の三つが分かります。

1. **共通部分が多い。** 表の結合、項目・列、キー、スクリプト、ボタン、固定条件、大きさは、ほぼ全型に共通します。型ごとの差は、複数性・編集性・出力形態に対応する部分に集中します。
2. **型固有部分は三つの家族に分かれる。** 一覧（XF100/110/300）、保守（XF200/310）、印刷（XF290/390）です。XF000はどれにも属さない起動処理です。
3. **型は直積の部分集合である。** 単票・一覧・見出し明細の三つの複数性、参照のみ・保守の二つの編集性、画面・印刷の二つの出力形態を考えると、8型はその一部の組合せに当たります。一覧の印刷や、単票の複数件保守などは存在しません。

この分解は、TEIが8型をそのまま列挙するのではなく、**複数性・編集性・出力形態の軸と、共通の対話契約**で受け止められる可能性を示します。軸の組合せで表せない型（XF000の起動処理、XF300の構造ツリー）は、別の家族として扱います。

## 5. 横断して見えた設計知見

以下は個別項目の要約ではなく、TEIの設計判断へ渡す一般化です。根拠は§4の各項目です。

1. **型を閉じると生産性が上がり、変更コストが実装へ移る。** 8種の機能型は定型を強力に支えたが、型の追加はDriverのクラス追加を伴った。TEIは型をCoreの列挙にせず、契約を持つ交換可能なパッケージにする必要がある。
2. **「何を表示するか」と「どう見せるか」を同じ属性に置くと、実行先を変えられない。** `FieldOptions`は幅・参照・改行・配置を一つに持ち、画面と帳票で再利用しにくい。
3. **イベントは強力だが、効果の境界を持たない。** スクリプトAPIがSQL・確定・機能呼出しを同じ面に置くため、宣言された効果と実際の効果が一致しない。
4. **取引の境界を画面に置くと、業務の完了と一致しない。** 画面を閉じる・確定する・取消すの意味が、業務上の完了と混ざる。
5. **失敗を件数へ潰すと、競合・不存在・多重一致を区別できない。** 更新件数1件の要求は、業務上の結果を一つのエラーへまとめる。
6. **取引の境界が画面の種類で変わる。** 閉じると確定する型と、操作ごとに確定する型が混在し、同じ「閉じる」が確定にも取消にもなる（D-8）。取引を業務の単位で宣言する必要がある。
7. **状態と結果を同じチャネルに置くと、呼出し側が文脈で意味を決める。** `RETURN_CODE`は画面モード・業務結果・取消・異常を兼ねる（I-10）。TEIは状態・結果・失敗を分ける必要がある。
8. **標準業務ライブラリは生産性の大半を占める。** 日付・年度・税・通貨・採番・利用者設定は、どの案件でも要る。これを案件コードへ書かせないことが、ローコードの実効性を決める。
9. **派生出力は、設計と実装の往復を軽くする。** DDL・設計書・行列・差分は、正本から再生成できるときに価値を持つ。出力を編集して戻す経路は、意味の同一性を壊しやすい。
10. **作者支援の検査は、意味の診断として再利用できる。** 未定義参照・未被呼出し・表の未使用・配置の重複は、TEIでもそのまま診断になる。
11. **機能定義が複数の提示形態を持てることは、X-TEAでも部分的に実現していた。** 機能定義は出力の種類（画面・帳票・Webページ・表）を宣言し、Driverはその一部（画面・帳票）を実行していた。TEIのTarget非依存の投影は、この延長にある。
12. **遠隔実行の境界をSQLに置くと、認可と型の境界が失われる。** `DBMethod`はSQL文字列をそのまま受け、`Service`はログイン後に機能IDを実行する。機能ごとの認可は、この境界では確認できない。TEIは操作・能力・提供元の契約を境界にする必要がある。

- 各機能型の全分岐、イベントの全組合せ、スクリプトAPIの全メソッドの実際の挙動は確認していません。
- 配布JAR（Modeler M50、Editor/Driver M36）と固定ソースの同一性は確認していません。過去の記録では差があるため、ソースの読解を配布版の動作と呼ばないようにします。
- 実DBでのSQL、トランザクション、更新競合、帳票出力の結果は確認していません。旧Runtimeの実測は[#940](https://github.com/hat47x/tei-platform/issues/940)が担当します。
- 参照モデルごとの機能型の使われ方、スクリプトの実例、帳票句の実例は、非公開の資料に依存するため、この文書へ転載していません。
- サーバ（`XeadServer`）はTEIの参考対象外とされています。ここでは遠隔実行の境界を学ぶ材料としてだけ扱い、移植対象にしていません。

## 付録A モデル要素の対応（抜粋）

設計モデルが持つ主な要素と、TEIで受け止める候補の層です。要素の意味は属性名と使われ方からの整理で、原典の定義文の転載ではありません。

| 要素 | 何を表すか | TEIの受容先（案） |
| --- | --- | --- |
| `System` | システム全体の設定（DB、メニュー、ログインスクリプト、フォント、PDF、SMTP、代理、変数、標準表） | 実行先・配備の設定、Plugin設定。意味の正本には置かない |
| `Subsystem` | 表と機能の所有境界、業務のまとまり | 所有・適用範囲の宣言。診断の単位 |
| `DataType` | 基本型、桁、小数、SQL表現 | 意味の型と、物理型への対応（Database Contract） |
| `Table` | 表の名前、別名、所属、DB、更新カウンタ、種別 | Data、物理スキーマへの対応、同時実行の契約 |
| `TableField` | 項目の別名、型、非NULL、既定値、更新禁止、属性種別、物理ID、表示指定 | Dataの属性、Validation、表示意図 |
| `TableKey` | 主キー・副キー・索引と構成項目 | 識別子・一意性・索引の宣言 |
| `Relationship` | 表間の関連（親子・参照・派生）、キーの対応、存在条件 | Relation、参照整合、条件付き関連の宣言 |
| `Function` | 機能の種別、所属、入出力表、引数、戻り、呼出し | Patternの組合せ、Capability、入出力の宣言 |
| `FunctionType` | 機能種別のコードと名前 | Patternパッケージの識別（Coreの列挙にしない） |
| `IOTable` | 機能が使う表と、作成・参照・更新・削除の意図 | 宣言された効果。実行時の実際と分ける |
| `IOPanel` / `IOSpool` / `IOWebPage` | 画面・帳票・Webページという出力の種類 | 投影の種類（表示プロファイル） |
| `Role` / `Task` / `Event` / `TaskAction` | 業務の主体、作業、契機、作業の操作 | 業務手順、実行主体、起動契機 |
| `TaskFunctionIO` | 作業の操作と機能の入出力の対応 | 業務と機能の対応（一対一にしない） |
| `DataflowNode` / `DataflowLine` | 業務の流れの要素と線、配置 | 業務手順の投影。配置は表示情報 |
| `SubjectArea` | 主題領域の区分 | 表示のまとまり、分類 |
| `Terms` | 用語と規則 | 用語集（意味の定義と名称の索引を分ける） |
| `Department` | 組織・部門 | 組織の意味（案件の拡張） |
| `Instance` | 項目ごとの例値、スライド順 | 設計検証用の例（正本の一部にしない） |
| `Menu` | メニューの構成 | ナビゲーションの投影 |
| `SubDB` | 追加のDB接続（読み取り専用） | データソースの宣言と読み取り専用の境界 |

この対応は、要素をそのままTEIの要素種別へ移すものではありません。**同じ仕事をどの層で受け止めるか**の候補です。
