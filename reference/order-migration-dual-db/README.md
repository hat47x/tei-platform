# 旧受注システムからの移行と並走、二つのDBをまたぐ引当(`order-migration-dual-db`)

移行担当者が、旧受注システムに残る受注残を、業務を止めずに新しい受注の主DBへ移し、受注残ごとに在庫の参照系DBへ引当を書き、並走、正本の切替、逆同期、巻戻しの訓練までを一つの移行作業として行う技術検証用サンプルです。確かめたいのは、参照系DBの停止や移行の処理の強制終了を挟んでも、旧と新の件数、合計、引当が一致し、一方のDBだけで確定した状態を成功にも失敗にも丸めないか、という点です。

- 状態: 設計案は提案段階で、このサンプルは新設です。工程1〜3は[`tools/reference-order-migration-dual-db`](../../tools/reference-order-migration-dual-db/README.md)に実装し、PostgreSQLの三つのインスタンスで工程1〜6の通しの検証を行いました。異種DBを前提とする要件(P-DB-03、P-DB-04)とP-DB-01は未成立です。
- 設計の正本: [技術検証用サンプルの統合設計 4.10節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#410-旧受注システムからの移行と並走二つのdbをまたぐ引当order-migration-dual-db新設)。技術検証用サンプルの位置づけ、物語、受け渡しの詳細はそちらを参照してください。
- 複合シナリオC1とC3は、このサンプルの通しの検証として行います([3.3節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#33-複合シナリオの対応))。

## DBの構成と当面の進め方

設計では、受注の主DBをPostgreSQL、在庫と単価を持つ参照系DBと旧受注システムのDBの代役をSQLiteとします。ただし、SQLiteの提供元はまだありません。そのため、SQLiteの提供元ができるまでは、PostgreSQLの二つのインスタンスで工程と失敗注入を先に組みます([7.6節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#76-サンプルの間の順序))。

この間、DBの種類が異なることを前提とする合否(方言の差による値の変化や並び順の差など)は、未成立として記録します。同じ種類のDB二つで通った結果を、異種のDBで成立した証拠にはしません。

工程1〜6の実装では、旧DBの代役もPostgreSQLとし、旧DB、主DB、参照系DBをPostgreSQLの三つのインスタンスに分けています。旧DBの変更記録は、設計が想定するトリガーではなく、PostgreSQLの論理デコーディングで取ります。選んだ理由と、捕捉できない変更の扱いは[実装のREADME](../../tools/reference-order-migration-dual-db/README.md#並走中の変更の反映工程4p-mig-02)にあります。

## 工程

| 工程 | 内容 | 前工程から受け取るもの | 使う既存資産 | 現状 |
| --- | --- | --- | --- | --- |
| 1 | 旧DBの観測と移行計画 | なし(最初の工程)。旧受注DBと、受注のデータ定義の複製 | [`tools/reference-order-migration-dual-db`](../../tools/reference-order-migration-dual-db/README.md)(このサンプル用に新設) | 実装済み。計画は件数、合計、月別合計、行ハッシュの照合値と区切り、品目コードの対応表を持つ。既知の差分として宣言するのは品目コードの変換だけで、方言の差は宣言していない(P-DB-03は未成立) |
| 2 | 全件の写しと、旧DBの変更記録の位置の対応づけ | 工程1の計画 | 同上 | 実装済み(同種のPostgreSQLで確認)。写しの前に論理レプリケーションのスロットを作り、その一貫点と写しの時点(snapshot)を計画の照合値に結び付けて記録する。写しとの対応はxidで決め、近似値のWALの位置は使わない |
| 3 | 区切りごとの移行と、二つのDBへの引当 | 工程2の写しと位置、工程1の計画 | 同上 | 実装済み(同種のPostgreSQLで確認)。P-MIG-01、P-TX-01、P-TX-03、P-DB-02の注入が通る。一対多の品目コードの受注残は保留する。P-DB-01は未着手 |
| 4 | 並走中の変更の反映、マスタの正本の切替、得意先の拡張 | 工程3の再開地点と、工程2以降の旧DBの変更記録 | 同上 | 実装済み(同種のPostgreSQLで確認)。論理デコーディングによる変更の反映(P-MIG-02)、得意先の項目ごとの正本と衝突の待ち行列、品目コードの一対多の保留(P-INT-03)、姓と名への分割と縮約の拒否(P-MIG-03)、請求システムへの冪等な送信と結果不明の照会(P-TX-02)の注入が通る |
| 5 | 照合と切替の関門 | 工程3・4の結果と、工程1の照合の規則 | 同上 | 実装済み(同種のPostgreSQLで確認)。宣言した既知の差分だけを除いて旧と新を照合し、差分、保留、待ち行列、引当の未確定が残れば切替を拒否する。方言の差の照合(P-DB-03、P-DB-04)は未成立 |
| 6 | 切替後の逆同期と巻戻しの訓練 | 工程5を通過した主DBと旧DB | 同上 | 実装済み(同種のPostgreSQLで確認)。切替後の新側の更新が逆同期で旧へ届き、巻戻しの訓練の後の照合で差分0件、欠落なし |

各工程が渡すもの(計画の照合値、写しの時点と変更記録の位置の組、区切りごとの再開地点、照合の結果など)は、4.10節の「工程と受け渡し」にあります。

## 通しの完了条件

通しの完了条件は、設計どおりの構成(主DBがPostgreSQL、旧DBと参照系DBがSQLite)では、どれもまだ成立していません。同種のPostgreSQLの三つのインスタンスで、条件ごとに次のところまで確かめました。

| 完了条件(下の一覧の順) | 同種のPostgreSQLで確かめたこと | 未成立のところ |
| --- | --- | --- |
| 計画の照合値の引継ぎ | 計画の照合値が、写しの記録、区切りの再開地点、効果記録、受注残、変更記録の処理の記録、関門の記録、逆同期の待ち行列と旧DBの受領、巻戻しの訓練の記録まで同じ値で引き継がれる。作り直した計画は、工程3の移行、状態の確認、照合と、工程5の関門で止まる | 異種DBの構成での確認 |
| 件数、引当、在庫残の一致 | 強制終了、参照系DBの停止、在庫不足、並走中の書込みを挟んでも、受注件数、明細、金額の合計、行ハッシュが旧DBと主DBで一致し、引当の件数と数量が主DBと参照系で一致し、二重の引当が残らない | 旧DBは在庫を持たないため、在庫残の旧と新の照合はしていない |
| 未確定の記録 | 一方のDBだけで確定した受注残を`undetermined:*`に分類し、成功にも失敗にも数えない。関門は未確定が残る間は切替を拒否する | 異種DBの構成での確認 |
| 既知の差分の扱い | 計画に宣言した既知の差分(品目コードの変換)だけを照合で除き、宣言のない差分(保留した受注、得意先の不一致)は関門で切替を止める | 方言の差(P-DB-03、P-DB-04)は宣言も確認もしていない |
| 逆同期と巻戻し | 切替後の新側の受注の追加、状態の変更、得意先の変更が逆同期で旧へ届き、逆同期の途中の強制終了でも重複しない。巻戻しの訓練の後の照合で差分0件、主DBにだけある受注残0件 | 異種DBの構成での確認 |

通しの検証は、GoとDockerがある環境で、リポジトリのルートから`python3 tools/verify-order-migration-dual-db.py`で実行します。手順と、確かめる内容の一覧は[`tools/reference-order-migration-dual-db`](../../tools/reference-order-migration-dual-db/README.md)にあります。

- 工程1の計画の照合値が、写し、再開地点、照合の結果、切替の関門、逆同期の記録まで同じ値で引き継がれる。計画を途中で作り直すと、照合が不一致として止まる。
- 参照系DBの停止と強制終了を挟んでも、受注件数、引当数量の合計、在庫残の合計が旧と新で一致し、二重の引当も宙に浮いた手順も残らない。
- 一方のDBだけで確定した受注残は「未確定」として記録され、成功にも失敗にも丸められない。
- 方言の差は、宣言した既知の差分だけが照合で除かれ、宣言のない差分は切替を止める。
- 切替後の新側の更新が逆同期で旧へ届き、巻戻しの後の照合でも差分が0件である。
- 合成の旧DBと同じ機械の上のDBで確かめた結果を、実際の旧システムや別の製品のDBで成立した証拠にしない。

## 部分工程の診断(互換入口)

該当なし。工程1〜6はこのサンプル用に新設した実装で担い、既存資産を部分診断として呼んでいません。設計文書は、棚卸しの後に追加された一部の資産を工程3の一つの境界を確かめる部分診断の候補に挙げています(4.10節「資産の処遇」)。いずれも二つのDBをまたぐ流れは持たないため、この段階では入口に載せません。

## 基盤への改善圧力

見出しだけを示します。現状、求める条件、確認方法は、4.10節の「基盤への改善圧力と現状」を参照してください。工程1〜6の実装で、基盤にないためサンプル側で最小限に作ったもの(区切りの再開地点、効果記録と受け手の重複排除、補償、参照先の停止時の方針、写しの時点と変更記録の対応、変更記録の取込みと逆同期、項目ごとの正本と衝突の待ち行列、コード変換表、拡張の段階と旧形式の書込み、外部への送信の冪等キーと結果不明の照会、切替の関門)は、[実装のREADMEの「基盤の不足」](../../tools/reference-order-migration-dual-db/README.md#基盤の不足)に記録しています。

- P-DB-03: 方言ごとの物理表現と往復の保証(プラグイン)
- P-TX-01、P-TX-03: DBごとの確定境界、効果記録による配送、補償の宣言(コア)
- P-MIG-01: 区切りの再開地点と照合の規則の宣言(コア)
- P-MIG-02: 全件の写しと変更記録の位置の対応、逆同期、正本の切替(実行時)
- P-DB-01、P-DB-02: 読取りの鮮度と、参照先の停止時の方針の宣言(データ)
- P-INT-03: マスタの項目ごとの正本と、コード変換表(データ)
- P-MIG-03、P-TX-02: 拡張の段階での旧形式の書込みと、外部への送信の冪等性(実行時)
- P-DB-04: 比較と並び順の意味の宣言(データ)
