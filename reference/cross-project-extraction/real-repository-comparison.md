# 異なる実リポジトリを比較した結果：共通化を急がない判断

- **位置づけ**: [#1067](https://github.com/hat47x/tei-platform/issues/1067)の読み取り専用の比較記録。2026-10-09時点のソースを確認した。共有プラグインの実装・採用・回帰テストの証拠ではない。
- **比較目的**: 生成AIが複数案件の実装を見たとき、コードや機能名の類似だけで共通化してよいかを判断する。まず、共通化を見送るべき例で境界を確かめる。
- **対象**: 同じ所有者の二つの実リポジトリ。ただし、その二つがTEIの独立した案件として動作することは未確認である。

## 読み取りから確認したこと

SUI側は、外部から取り込む文書を検査する。カード配列・カード辞書という入力の違いを吸収し、文書として扱える形に直したうえで検証する。問題は文書内のパス、利用者向けメッセージ、警告・エラーの重大度を伴って返す。カードに初期座標を与える処理など、取り込み形式の正規化も含まれる。

MMI側は、生成AIなどが提示した候補選択案を検査する。候補が渡された証拠の中に存在するか、候補の識別子と提案の構造が一致するかを調べる。正常な結果を `accepted-for-review` と表しても、それだけで事実認定や最終的な採用権限を与えない。

なおSUI側の同じファイルにある`validateView`は、表示情報の初期値を補う際、入力に生成日時がなければ現在時刻を使う。これは表示情報の取り込み処理としての選択であり、生成時DSLの純粋な決定論的変換へそのまま移せる性質ではない。MMI側の候補選択検証は提案内容の安定した識別子や照合を重視している。**同じ「検証」という名でも、時刻への依存や入力補完を含むかは別々に宣言すべきである。**

両者は「外部から渡された情報を無条件に採用しない」という原則を共有する。しかし、扱う対象、出力の働き、許容する正規化、診断の利用者、受理権限が異なる。

| 比較する観点 | SUI | MMI | 判定 |
| --- | --- | --- | --- |
| 入力 | 文書・表示の構造 | AIによる候補選択案と候補証拠 | 共通の入力型にはしない |
| 意味 | インポート可能な文書としての妥当性 | 選択候補が元の証拠に含まれること | 別契約 |
| 正規化 | 文書の取込形式を一部変換 | 提案の識別子と構造を厳格に照合 | 無条件にまとめない |
| 診断 | 場所、翻訳された表示文、警告・エラー | 検査段階、失敗コード、レビュー可否 | UI向け表示と意味診断を分ける |
| 採用権限 | 検査成功は別途の利用・保存を意味しない | `accepted-for-review` は採用確定ではない | 境界の原則のみ共有 |
| 時刻・副作用 | `validateView`の初期値生成は現在時刻を参照する | 候補選択の照合は渡された提案・証拠を対象とする | 生成時の純粋変換に一律統合しない |

### 現時点の判断

**両ファイルをそのまま共有のValidationプラグインにまとめない。** 見かけ上の重複より、意味の非同一性による誤った共通化の危険が大きい。

再利用の候補になり得るのは、入力型の検査、失敗理由を失わない診断、候補と採用の区別といった、より小さな関心である。ただし、これらについてもTEIの既存DSL演算子、検証結果、権限境界に相当する機構があるため、新しい共通プラグインを作る理由はまだない。次は両実装をTEI側の契約に写せるか、違いを保ったまま検討する。

## 将来、共通化を認める条件

1. 同じ意味契約を満たす処理が両リポジトリに実在し、入力・出力・失敗条件を同じ言葉で説明できる。
2. 各案件の現在の動作について、独立した期待値をもつ正負の回帰例が存在する。生成AIが作った実装と期待値の相互一致だけには依存しない。
3. 共有候補を入れた際に、各案件が必要とする正規化・診断・責任の違いを失わない。
4. 案件固有の設定や実装が減る利益が、共有側の条件分岐・依存・保守負担の増加を上回る。
5. 移植する資産の権利・アクセス範囲が明らかで、各リポジトリの所有者が個別に採用判断できる。
6. 個別の版固定・段階移行・切り戻しに加え、実際の対象環境で回帰確認ができる。

## 次の実証への引継ぎ

最初の合成実証は[同ディレクトリのREADME](README.md)のとおり、共通の入力検証規則を抽出した。ここで比較した二つの実リポジトリは、その合成実証の受注・請求案件とは関係がない。同じ成果であるかのようには扱わない。

次に正の共通化例を扱うなら、まず共通の意味契約を持つ二つの**独立した実Consumer**を特定する。固定したソースと各案件の期待値を読み取り、共有化の候補・非対象・変更影響を提出する。実験では既存のPlugin/Build/Lock契約を利用し、新しい共通Resolverや自動採用機構を先に作らない。

本記録の検証範囲は、上記ファイルのテキストをGitHub経由で読み取ったことに限る。SUI/MMI両リポジトリのテストやTEIとの接続試験は実行していない。
