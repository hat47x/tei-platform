# 共通化の効果測定：二案件だけでは固定費が勝つ

この文書はIssue #1067の「定義量削減の利益を、共有側の複雑性増大と併記する」という受入条件を、現在の合成Referenceで測った記録です。

行数は設計品質そのものではありません。ここでは、共通化の固定費が見えなくなることを防ぐための補助指標として使います。

## 対象

対象は次の生成関数だけです。案件固有の承認条件、テスト、README、Lock接続は含めません。

- `orderChecksBefore`
- `invoiceChecksBefore`
- `orderChecksAfter`
- `invoiceChecksAfter`
- `compileRequiredFields`

2026-10-10時点のDraft PR #1069のSourceを基準に、空行を除いた行数を数えています。

| 対象 | 非空行 | rule宣言 |
| --- | ---: | ---: |
| 受注・抽出前 | 9 | 2 |
| 請求・抽出前 | 9 | 2 |
| 受注・抽出後 | 6 | 0 |
| 請求・抽出後 | 6 | 0 |
| 共有生成器 | 19 | 2 |

二案件の合計は次です。

```text
抽出前   9 + 9         = 18
抽出後   6 + 6 + 19    = 31
差分                     +13
増加率                    約72%
```

一方、同じrule objectの宣言数は、案件側の4個から共有側の2個へ減っています。**重複は減ったが、全体量は増えた**状態です。

## なぜ増えるか

現在の共有生成器は、単なるmaterializerではありません。

- semantic contractの照合
- field名の字句検査
- 二fieldの衝突検査
- 共通planの構築

を一つに持っています。

この固定費は、一案件ごとに3行程度減らす効果より大きくなっています。現在の構造をそのままN案件へ増やす単純モデルでは、

```text
個別実装: 9N
共有化:   6N + 19
```

なので、行数だけで逆転するのは概ね**7案件目**です。

これは「7案件あれば必ず共有化すべき」という閾値ではありません。現在の小さなfixtureに対する観測値にすぎません。

## E4の責務分離を反映した見方

[実行境界の整理](transform-boundary.md)では、現行JSが持つ責務を次へ分ける方針としました。

```text
Semantic / Authoring
  -> contract identity
  -> typed field reference
  -> distinctness

deterministic Transform
  -> derived validation plan materialization
```

この分離が成立すれば、19行の共有生成器に含まれている意味検査の一部はTransform側の固定費ではなくなります。ただし、上位のtyped validation自体はどこかに必要です。単に行が別ファイルへ移っただけなら、製品全体の複雑性削減にはなりません。

したがって次の測定では、Repository全体で次を分けます。

- 案件ごとの記述量
- 共有Semantic contractの記述量
- 共有Transform Sourceの記述量
- 共通contract test
- 案件固有の受入・接続test
- Lock / Build接続に必要な記述
- 変更時にレビューが必要なファイル数
- 一つの意味変更が影響するConsumer数

## 共通化の判断規則

今回の結果から、#1067の昇格条件を「二案件に似たコードがある」より厳しく扱います。

共有Plugin / Transform候補へ昇格するのは、少なくとも次を満たす場合です。

1. 共通する意味契約が安定している。
2. 案件固有の意味を共有側へ押し込まない。
3. 重複削減だけでなく、変更箇所・試験・レビュー負担のどれかが実測で減る。
4. 共有側の固定費とblast radiusを含めても利益がある。
5. 各案件が独立して採用・版固定・切り戻しできる。

二案件しかなく、共通部分が小さい場合は、**重複を許容したまま局所実装を維持することも正常な判断**です。生成AIが将来同じ差分を再び見つけられるなら、早すぎる抽象化を避けるコストは従来より小さくなります。

## 次の測定

TEI Transform版が成立した時点で、同じ二案件について再計測します。

- JS共有候補とTEI TransformのSource量
- 案件側に残る定義量
- 共通testと案件testの総量
- 変更ファイル数
- 版更新・切り戻し時の差分量

その結果、二案件では依然として固定費が勝つなら、#1067の価値は「すぐ共有化する仕組み」ではなく、**必要になった時点で安全に共通化でき、不要なら共通化しない仕組み**として評価します。
