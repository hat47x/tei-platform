# 受注ルールの改訂から業務完了まで

三件の受注について、業務ルールを改訂し、不備を直して確定し、停止した処理を照合してから最終帳票を作る。一つの受注業務の中で、意味の変更、実行許可、永続更新、観測、帳票、失敗時の診断を確かめる参照モデルである。

従来の`postgres-order-execution`と`source-execution-loop`、画面を使わない受注処理の検証を統合した。`fixture.sql`と`change-candidate.json`がこのモデルの入力で、業務定義は引き続き`reference/workspace`を正本とする。整形プラグインと実行ホストは別の実装部品であり、個別の参照モデルとして数えない。

## 一連の作業

1. 三件の未確定受注を受け取る。1002は数量が不正、1003は単価が0である。業務データの準備はここだけで行う。
2. 単価を正値とする変更案を確認し、確認内容と一致する案を既存の共通受理機構へ渡す。確認だけではソースも受注状態も変えない。検証用の複製だけを更新し、ルートの業務定義は変更しない。
3. 受理したR1を再読込みする。旧R0の実行を拒否し、R1のDB実行許可を別に設定する。以後の工程は同じR1を使う。
4. 三件を一括処理する。1001を確定し、1002の数量検証で停止する。ログを読み、記録した結果と現在のDB状態を別々に確認する。
5. 1002の数量を直し、未処理の1002・1003を明示的に選んで実行する。1002を確定し、1003は新たに受理した単価ルールで停止する。
6. 1003の単価を直す。最後の受注の行を別接続でロックし、開始記録の保存とロック待ちを確認してから、検証器が起動したCLIを強制終了する。先に確定した1001・1002はそのまま保つ。
7. ログと新しい読取りで1003が未確定であることを照合する。検証器が停止位置を特定したこの条件で、操作者の明示的な残件処理として1003を確定する。ログからの自動再開はしない。
8. 三件すべての完了を確認し、同じR1でCSVとJSONの最終帳票を作る。両形式を独立して読み直し、訂正済みの四明細と照合する。確定済み受注の再送を拒否する。記録版を旧R0へ変えた診断用ログでは、記録版と現在版の不一致を明示する。

工程間で受注を未確定へ戻さない。各件は独立したトランザクションで、全件の一括原子性はない。入力の数量・単価の訂正は検証用SQLで行っており、製品の編集画面や訂正APIの成立を示すものではない。

## 再現

Go・Python 3・Dockerが使えるLinuxで、変更のない候補版から実行する。出力先は新しいリポジトリ外のディレクトリとする。

```sh
python3 tools/verify-order-workflow.py --output /absolute/new/order-workflow-evidence
```

検証器は所有するPostgreSQL 16コンテナーにだけ`fixture.sql`を適用する。実行ホストは表・許可・参照データを作成しない。終了時にCLI・ロック用接続・コンテナー・接続ファイル・資格情報ファイルを解放する。検証用のソース複製、進行ログと帳票は再確認用に出力先へ残す。

`order-workflow.json`は受理版・工程ごとの状態履歴・最終状態・帳票の照合値を記録する。`evidence.json`は候補コミット、実行物のSHA-256、実DB回帰試験、変更の有無、後片付けを結ぶ。各工程の応答・進行ログ・最終帳票も同じ出力先に保存する。

## 基盤へ返す改善圧力

- 受理版を後続業務へ渡すため、ソース版の同定・明示的な実行許可・古い版の拒否が必要になる。再読込みだけで権限を得たことにしない。
- 一括処理は読取だけでなく永続確定サービスにも依存する。登録簿にこの依存を宣言し、依存先の宣言変更を利用側の選択へ反映する。宣言の現在性と、具体的な世代が稼働していることは別の境界である。
- 保存ログには実行版を残す。診断では記録版と現在版を明示して比較し、指紋や版の一致を承認・認可・確定記録の代わりにしない。
- 資格情報を工程の受領記録やログへ残さず、取消・部分成功・結果不明・一時資源の解放失敗を業務確定と分ける。
- 最終帳票には実出力の行数・バイト予算が必要になる。予算超過で部分帳票を公開しない。

次の改善課題は、診断用SQLに代わる意味に結び付いた訂正操作、永続的な親・子要求ID、現在の認可正本と同じDB内の確定記録、選択済み確定世代を保持した項目実行である。流れの不足として追跡し、技術要素ごとに別の小さなモデルを増やさない。

## 部分工程の診断と互換入口

既存の固定候補を再検証するため、次の部分工程は同じモデルの診断として残す。状態を初期化する旧診断と、初期化せず進む一連の作業を区別する。

```sh
python3 tools/verify-order-workflow.py --diagnostic-slices --source-loop --non-screen --batch-crash --output /absolute/new/diagnostics
python3 tools/verify-order-workflow.py --frozen-api --non-screen --batch-crash --output /absolute/new/frozen-diagnostics
```

旧`tools/verify-postgres-order-execution.py`は旧引数の互換入口だけを残し、同じ検証器へ委譲する。参照用表の所有標識`tei.reference.postgres-order-execution.v1`も、既存の専用DB試験との互換性のため維持する。別のデータ・ソース・実装の正本は残さない。

ホストの起動引数と個別操作は[受注ホスト](../../tools/reference-first-web-target/README.md)、[帳票・一括処理・診断](../../tools/reference-first-web-target/NON_SCREEN.md)を参照する。

## 根拠の限界

実DBエンジン上の合成業務データである。顧客参照と認証・業務認可は模擬実装。機械的なソース受理は人による承認ではなく、DBの許可表は汎用認可の正本ではない。開始記録だけではDB作用の成否を判断できない。停止位置を特定した試験の成功を、一般の結果不明や自動再開の安全性へ拡張しない。

本番データ、実Oracle、本番認可、永続的な要求ID、無停止のモデル交換、全体のメモリ・性能、表示品質、人による利用価値は未検証である。
