# 配備命令と監督ホストの交代(order-rollout-host-continuity)

運用者が受注の新版`order_rollout@2026.8.27`を出すために、最初の配備命令(`sales_core`を4.1.0へ拡張するデータベースの配布)を隔離と資源の貸与つきで実行し、その途中で監督ホストが交代しても命令を正しく継続できるかを確かめる技術検証用サンプルです。受理の通知を到達の証明と取り違えないこと、再接続の結果が不明なら命令を完了にも失敗にもせず未解決のまま保つこと、秘密と具体の参照先を記録に残さないことが焦点です。

- 状態: 設計案は提案段階です。工程1〜5の通しの検証を[`tools/reference-order-rollout-host-continuity`](../../tools/reference-order-rollout-host-continuity/README.md)に実装しました(使い捨てのPostgreSQLと、同じ機械の上の別プロセスのホストと移行ツールの代役による試験。実際の提供元や運用環境での確認ではありません)。各工程の状況は、次の工程表で工程ごとに区別して示します。
- 設計の正本: [技術検証用サンプルの統合設計](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md)の4.6節。技術検証用サンプルの位置づけは同じ文書の1.2節、要件の目録は2章、資産の対応表は6章にあります。
- 先行サンプル`order-workflow`(設計文書の4.1節)の保守停止の運用側として連結するかは、決めていません(設計文書の8章)。
- 各資産の使い方と実装状況は、それぞれのREADMEが正本です。このREADMEは工程との対応を案内するだけで、内容を写しません。

## 工程

「既存資産の現状」は、工程に置いた既存資産の範囲で判断した区分です。「通しの検証」は、`tools/reference-order-rollout-host-continuity`での区分です。工程の間の受け渡しは、通しの検証の中でだけ接続しています。命令の実行に使う`migration.atlas`は隔離が必須ですが、対応する実行ファイルがなく、通しの検証はツールの中の代役を子プロセスとして呼びます。

| 区分 | 意味 |
| --- | --- |
| 実装あり | コードはあるが、資産の中に試験が見当たらない |
| 合成データで試験 | 合成データ、メモリ上の記録、模擬の実行環境を使う試験がある。このREADMEの作成時に試験は実行していない |
| 実環境で確認 | 実際の提供元や運用環境で確かめた記録がある |
| 足場なし | 工程を担う既存資産がない |
| 未確認 | 資産のREADMEから状況を確かめられなかった |
| 実DBで通し試験 | 使い捨てのPostgreSQLと別プロセスのホストで、工程1〜5を一つの記録でつなぐ試験がある。所有記録や貸与の永続実装、移行ツール、隔離のアダプターはサンプル側の実装で、実際の提供元や運用環境ではない |

| 工程 | 内容 | 前工程から受け取るもの | 使う既存資産 | 既存資産の現状 | 通しの検証 |
| --- | --- | --- | --- | --- | --- |
| 1 | 配備前の観測と開始記録の読込、最初の命令の確定 | なし(固定済みの配備前観測と開始記録) | 共有入力の[配備前の観測](../observed/)と[開始記録](../order_rollout.durable-run.m0.21.start.json)(説明は[reference/README.md](../README.md)) | 実装あり | 実DBで通し試験(読込は`reference-deployment-attempt`と同じ。固定物は読むだけ) |
| 2 | 隔離・資源貸与つきの一回の呼出しと、貸与更新・所有の監督 | 工程1の命令と環境計画 | 工程に組み込む資産はない。製品コードの[lease.go](../../internal/plugin/runtime/lease.go)、[supervisor.go](../../internal/plugin/runtime/supervisor.go)、[ownership.go](../../internal/resource/ownership.go)とその試験が足場 | 合成データで試験 | 実DBで通し試験(製品の`Registry`と`HostSandboxLauncher`が貸与の自動更新と所有の心拍を監督する。ブローカーと所有ストアはサンプル側のPostgreSQL実装) |
| 3 | ホストAの停止と、期限切れ後のホストBの引継ぎ | 工程2の貸与の識別、所有者、排他トークン、期限 | 工程2と同じ製品コードの試験(所有ストアはメモリ実装) | 合成データで試験 | 実DBで通し試験(ホストAを`SIGSTOP`で止め、所有が残った状態からホストBが引き継ぐ) |
| 4 | 実行状態への再接続と、未解決の引渡し | 工程3の新しい所有と、工程2の呼出記録から組んだ耐久呼出の記録 | [runtime-reattach](../../examples/runtime-reattach/)(READMEなし) | 実装あり | 実DBで通し試験(製品の`ReconcileDurableInvocation`。再接続先は移行ツールの代役の実行登録で、ホストAの子プロセス) |
| 5 | 命令後の観測との比較と、実行記録への反映 | 工程1の開始時の観測と、工程4の結果 | なし | 足場なし | 実DBで通し試験(サンプル側に最小限で作った再観測と実行記録への反映) |

補足します。

- 工程1の入力は時点固定の記録で、判定段階Bも固定しています。移動、改名、手書きの修正をしません。開始記録を読む[reference-deployment-attempt](../../tools/reference-deployment-attempt/)は部分診断として残します。
- 工程2・3の診断としていた3件のツールは#1197で削除済みです。製品コードの試験は、呼出しが終了時に所有と貸与を必ず返すため、停止したホストの所有が残る状況を作れません。通しの検証は、呼出しの途中でホストAのプロセスごと止めることで、この状況を作っています。
- 既存の`runtime-reattach`の再接続先は手作業で登録した合成の実行環境です。通しの検証の再接続先は、移行ツールの代役が自分で登録する実行登録(対象のDBの表)で、ホストAの子プロセスが動かしています。ホストより長く生きる実行環境ではありません。
- 到達を示す観測(`sales_core` 4.1.0)の置き場は正本にありません。通しの検証は、命令の後に対象のDBから取り直した観測を使い、`reference/observed`には何も加えていません。

## 取り込むピーキーな要件と失敗注入

注入する失敗と合否の観測の詳細は、設計文書の4.6節にあります。要件の内容は2章の要件目録を参照してください。「固有」は目録にない、このサンプル固有の困難です。

| 要件 | 工程 | 注入する失敗(要点) | 観測する合否(要点) |
| --- | --- | --- | --- |
| 固有 | 1・5 | シナリオ時点に固定した観測や受理の通知を、到達の証拠と取り違えやすい | 再観測するまで完了と判定せず、比較できなければ到達未確認とする |
| 固有 | 1〜5 | 資格情報、DBの接続先、作業領域の具体の参照先が記録や出力から漏れる | 全工程の出力を連結しても具体の文字列が現れない |
| 固有 | 2 | 貸与の更新や心拍が失敗しているのに処理を続ける | 呼出し全体を失敗にする |
| P-OPS-01 | 3 | ホストAが止まり、期限切れの後にホストBが引き継ぎ、ホストAが復帰する | 旧ホストの操作をすべて拒否し、新ホストだけが貸与を返却できる |
| 固有 | 3・4 | 交代の間に環境計画が更新される | 古い呼出しの記録を、観測の前に拒否する |
| P-TX-02 | 4・5 | 交代の後、実行環境の状態が不明または行方不明になる | 自動で再実行せず、命令を未解決のまま残す |
| P-OPS-01 | 3 | 二つのホストの時計を数分ずらして期限を切らす | 判定が時計でなく排他トークンで決まる |
| P-MIG-03 | 2・5 | 拡張の適用中と適用後に、`order_entry` 3.7.0が旧い契約で書き込み続ける | 3.7.0の書込みが失敗せず、値を失わない |

## 通しの完了条件

各条件の状況は、`tools/reference-order-rollout-host-continuity`の実DBの試験で確かめた範囲です(試験と観測値は、そのツールのREADMEと検証スクリプトの受領記録にあります)。使い捨てのPostgreSQL、同じ機械の上の別プロセスのホスト、移行ツールの代役での確認で、実際の提供元や運用環境での確認ではありません。

| 条件 | 状況 |
| --- | --- |
| 同じ識別子での追跡 | 成立(試験の範囲)。工程ごとの記録が、その工程が受け取った入力から作った識別(実行、開始記録、計画、命令、冪等キー、呼出し、要求)を持ち、照合値で連鎖する。貸与・所有者・排他トークンは引継ぎの検証で確かめる。再接続先はホストAの子プロセスの代役で、実行が継続した証拠ではない |
| ホストAの停止と、期限切れ後に限った引継ぎ、旧ホストの拒否 | 成立(試験の範囲)。ただし、実行環境の側のトークンは再接続が成功したときしか進まず、状態が不明のときや新しい所有者の再接続が拒否されたときは、旧ホストの実行登録への再接続を実行環境の側では拒否できない(呼出しの再接続としては拒否される) |
| 不明・行方不明で完了にせず、後続を実行可能にせず、再実行しない | 成立(試験の範囲) |
| 再観測で4.1.0と3.7.0だけの稼働を見たときに限り完了、観測できなければ到達未確認 | 成立(試験の範囲) |
| 秘密、接続先、マウント先が現れない | 成立(試験の範囲)。ホストの報告と標準出力・標準エラー、制御用DBと実行登録の全行、工程1と5の出力を連結して検査する |
| 環境計画が変わったら観測や再接続より前に拒否 | 成立(試験の範囲) |
| 時計のずれでもトークンで決まる、拡張の間も3.7.0の書込みが値を失わない | 成立(試験の範囲)。時計のずれは各ホストのプロセスの時計に数分の差を与えて注入し、DBの時計は判定に使わない |

条件の文言は次のとおりです。

- 一つの配備実行が、工程1から5まで同じ識別子(命令、貸与、呼出し、所有者、排他トークン)で追跡できる。再接続先が合成の実行環境である間は、実行が継続した証拠としない。
- ホストAが止まった状況で、所有が期限切れになった後に限ってホストBが引き継ぎ、旧ホストの操作がすべて拒否される。
- 再接続の結果が不明または行方不明のとき、命令は完了にならず、後続の命令は実行可能にならない。自動での再実行もない。
- 命令の後に再取得した観測が`sales_core` 4.1.0(`order_entry`は3.7.0のみ稼働)を示したときに限り、命令が完了する。観測が得られなければ到達未確認とする。
- 実行記録、呼出記録、耐久呼出の記録、標準出力をつなげて検査しても、具体の秘密、DBの接続先、マウント先が現れない。
- 環境計画が途中で変わった場合は、観測や再接続より前に拒否する。
- ホスト間の時計がずれても交代の判定が排他トークンで決まり、拡張の間も3.7.0の書込みが値を失わない。
