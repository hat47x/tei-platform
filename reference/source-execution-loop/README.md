# ソース変更の受理から受注の再実行まで

共通受理機構で業務ルールとアプリケーションの検証対象を同時に追加し、再読込みした版をプラグインの呼出しとPostgreSQLの実行許可へ結ぶ参照例である。保護された`reference/workspace`は変更せず、検証用の複製だけを受理対象にする。

## 再現

Go、Python 3、Dockerが使えるLinux環境で、変更のない候補版から実行する。

```sh
python3 tools/verify-postgres-order-execution.py --source-loop --output /absolute/path/outside-repository
```

既存の[PostgreSQL検証器](../postgres-order-execution/README.md)を再利用し、同じ使い捨てDBで次を追加確認する。

1. `candidate.json`に現在のソース版R0を入れ、既存の共通受理CLIで変更案を確認する。確認はソースを変えず、未受理の単価ルールも実行へ反映されない。
2. 現在のソースへ提案版R1を指定してホストを起動すると、版不一致で拒否する。
3. 確認内容の識別が異なる受理は拒否し、R0を保つ。一致する確認内容で、単価の正値制約とアプリケーションの評価対象を一度にR1へ受理する。
4. R0を基にした古い提案の再受理を拒否し、R1を保つ。旧ホストも新規の確定処理を拒否する。
5. R1を再読込みしてホストを明示的に起動する。再読込みだけではDBの実行許可を得られない。ホスト側でR1の実行を別に許可してから使う。
6. 同じ単価0の明細が、R1では確定前の検証で止まる。正の単価へ直したデータは確定され、別読取りと独立したSQL確認で状態が一致する。投影・読取・確定の記録は同じR1を示す。
7. 受理後にソースを直接変えると、R1のホストは処理を拒否し、DB状態を保つ。

変更案、確認結果、受理決定、実行前後の応答を出力先へ保存する。`source-loop-evidence.json`はR0、R1、候補と確認内容の識別、確認項目を記録し、`evidence.json`は候補コミット・実行物・全体の合否・後片付けと結ぶ。検証用のソース複製は結果を再確認できるように保持する。

## 実行側の境界

`-model-revision sha256:...`は、ホストが実行するソース版を明示的に選ぶための指定である。変更案を受理する指定ではない。管理対象ソースの版計算は、共通受理CLIとウェブ実行側が`sourceindex.Revision`を共有し、従来の版計算を二重実装しない。

ホストは読み込んだ定義を稼働中に書き換えず、ソース版と読み込んだ構成ファイルの内容を照合する。変更があれば新規処理を拒否し、明示的な再読込みと実行許可を要求する。確定処理では読取後にも照合する。DB上の実行許可の`model_revision`も同じ版でなければ使えない。版を選ばないホストは、版に結び付いた許可を利用できない。

管理対象ソースの版は、相対パスと内容の識別から導く。Gitコミット、表示名、業務上の識別子、意味上の同等性とは別の値である。構成ファイルの照合は、読み込み器が実際に解析した内容の識別を使う。業務モデル、プラグイン基盤、決定記録に別の正本を増やさない。

## 確認していないこと

検証用の複製への機械的な受理であり、人が内容を承認した証拠ではない。共通受理機構の決定記録や確認内容の識別も、承認者・実行権限・配布元の署名の証明として扱わない。実行許可は参照ホストのDB表で別に検査する。

ソース照合と任意のファイル書換えを一つの原子的な操作にする保証はない。照合を通った処理も、読み込み済みの版を使い続け、途中で定義をすり替えない。ホストの再起動による再読込みを、無停止のモデル交換とは呼ばない。案件の認可基盤、Studioでの人の編集、表示品質、複数ホストの切替、実際のOracle・認証提供元、本番運用は未検証である。
