# E28：案件構成の作業・AI確認を、実測と未計測を分けて記録する

- **管理**：[Issue #1016](https://github.com/hat47x/tei-platform/issues/1016)。案件の生成AI支援・専用Plugin作成に関する直近の追加要件は[Issue #1016の受入シナリオ](https://github.com/hat47x/tei-platform/issues/1016)を参照する。
- **範囲**：[E27の既存Source観測・残余選択](E27_RESIDUAL_SELECTION_AUDIT.md)に紐づいた作業を読み取り専用で集計する**任意の参照試験**。製品の必須入力項目、構成Profileの新DSL、第二のSource Index、Plugin Lock、実行時Resolverを増やさない。
- **実装**：[集計器](e28_attested_work_measure.mjs)／[Node.js回帰試験](e28_attested_work_measure.test.mjs)。元のApplication／Environment／SUIの正本、認証・書込み先は変更しない。

## なぜ「未測定」を維持するのか

[E26](E26_COMPOSITION_COST_BASELINE.md)では既存Webの設定・案件UIに**5ファイル・非空行67行**、SUIの**試験専用**の接続候補に3ファイル・9行、入力型を記述すると同じ3ファイル・15行を観測した。これらは**実導入に要した人手操作やAIへの追加質問数ではない**。[E27](E27_RESIDUAL_SELECTION_AUDIT.md)で残余選択が3項目と分かったことも、AIに3回質問したという証拠ではない。

E28では「記録が無い」と「記録範囲を閉じた上で、実際に0件だった」を区別する。将来、人間が案件対応を行った際に観測可能な作業を記録するための枠組みだけを追加した。

## 計測対象

| 記録の種類 | どのイベントを数えるか | 計数条件 |
| --- | --- | --- |
| 人手操作 | `manual-action` | 人手操作の記録範囲が`complete`と明示され、セッションが終了している |
| AIへの質問 | `ai-question` | 質問そのものは保存せず、個別の質問イベントだけを記録。範囲が`complete`かつ終了済み |
| 変更ファイル | `source-change` | Gitの変更前・変更後blobとリポジトリ・相対パスの組を持ち、範囲が`complete`。同じファイルを複数回編集しても**変更ファイル数は1** |
| 再検証 | `verification` | 実行イベントと成否(`pass/fail/unknown`)を記録。実行の証拠が無い判定は数えない |

どの指標も`complete`でなければ値は`null`（未計測）とする。見本の`illustrative`イベントは計数方法のテスト用であり、全項目を`complete`にしても**実測値として公表しない**。

入力は短いメタデータ（セッションID、イベント種別、E27の既存判断ID、時点、出典参照）のみ。同じセッションに属さないイベントは拒否する。自然言語の元プロンプト、個人情報、認証情報、顧客データは持ち込まない。出典参照・報告イベントの**真正性は自動検証しない**ため、出力は明示的に`caller-supplied-events-not-independently-verified`と表示する。

## 実際の別作業を参照したファイル差分の観測

[案件固有Go補助処理とLit UIの試作PR #1567](https://github.com/hat47x/tei-platform/pull/1567)は、#1016の追加受入シナリオを具体化する**並行する別作業**である。2026-10-12にGitHubのPR変更ファイル一覧を、固定head `166fce730cbbd5e338f72eab91e3d9343f77840d`で照合したところ、**変更パス18件**だった。

この18件は「作業中のPRに列挙された変更ファイル数」という**単一の観測値**である。対応する実作業セッションがE28形式で継続記録されたわけではなく、人手操作数・AI質問回数・実際の導入時間はすべて**未計測**。PRはその観測時点でDraftであり、製品採用や実Browser・本番Authorityの合格を意味しない。#1567に変更を加えず、差分を別の構成用正本として複製しない。

## 比較の条件

実際に**同じ案件の同じ要求**を、既存ソースを直接選択する方法と、追加Profile候補を使う方法で比較するときは、両記録の`consumer`・`requirementId`・`target`・TEI/SUIの基点コミットを一致させる。片方が未完了・未記録、もしくは任意の計数が未完了なら`not-comparable`。

一致していても結果は`caller-reported-comparison-only`にとどめる。人間の自己申告だけから受理済みの業務意味、提供元適合、現在の操作権限や実Target動作を認定しない。別の正規の実行・受入検証を必要とする。

## 検査する負例

- 同じイベントIDの重複、異なるConsumerのE27判断IDを使った紐付け、時刻の不正を拒否する。
- ファイルの不正な相対パス、変更前後が同じGit blob、偽のblob値を拒否する。
- 生の質問本文・業務データ等、定義外フィールドをイベントに持ち込ませない。
- 未記録のAI質問や作業中セッションを**0件**としない。
- 同じファイルを複数回編集した場合、変更イベント2件と変更ファイル1件を区別する。
- 基点やTargetが異なる2セッションの差を、生産性の比較に使用しない。

### 実行方法

```sh
node --test reference/application-composition/e28_attested_work_measure.test.mjs
```

この試験の成功が示すのは、**計測の取り違えを防ぐ参照処理の正しさ**に限る。生成AIによる案件Plugin作成、実SUIの認証・保存（#993）、正式なTarget選択、組織的な作業計測の運用採用は別の課題である。

## 採否判断

E28時点で第二の構成Profileを製品化する根拠は増えていない。一方、今回の任意の記録方式を使えば、実案件の作業・再試行が発生した段階で**何が観測されたかを残す**ための最低限の器は用意できる。

次の比較では#1567の案件Plugin縦断など実際のConsumerを使い、正本への変更パス、実Targetでの受入・拒否、担当者による選択とAI往復の記録範囲を揃える。定義量だけでPlugin化・独立Profile化を推奨しない。
