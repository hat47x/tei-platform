# E26：二つの利用先における構成記述量の観測基準

- **管理**：[Issue #1016](https://github.com/hat47x/tei-platform/issues/1016)。アプリケーション構成プロファイルを導入すべきか、既存ソースだけで十分かを判断するための**測定の第一段階**。
- **基点**：TEI main `dd7ad1e70599a206524d7e9b72b7f4e83db5e5c1`、SUI `4bd493f9942890d52117461886207d628f3554e2`。E25で固定したSUI側の既存実装・改訂証拠を再利用する。
- **回帰試験**：[E26のGo試験](e26_composition_cost_baseline_test.go)。現在のTEI参照ファイルを読み込み、試験専用の仮作業領域に限って新規定義の行数を観測する。再現可能な数値はGo試験の`E26_OBSERVED_BASELINE`というJSON行へ出力する。

## 何を計測したか

数えたのは、**読取った実ファイルの空白以外を含む行数と、参照に必要なファイル数**である。実際の開発工数、自然言語での追加確認数、動作する完成アプリの構築回数ではない。コメント行も行数に含め、二つのコードベースの規模・言語の生産性比較として使わない。

| 観測対象 | 実際の測定対象 | ファイル数 | 空白以外の行数 | 採用・完成状態 |
| --- | --- | ---: | ---: | --- |
| 受注明細Webの既存設定・画面差分 | Application、送信Command、Go実現宣言、開発環境、案件固有UI差分 | **既存5** | **67**（23＋3＋1＋32＋8） | 参照ソースの既存部分を測っただけ |
| SUI Stage 0 | `tei.workspace.yaml` のみ | **既存1** | **3** | Application未受理 |
| SUIのE22空の操作候補 | Capability、Application、Commandの仮宣言 | **試験中の新規3** | **9**（3＋3＋3） | 保存・入力・権限なし |
| SUIのE24型付き操作候補 | 入力DataとCapability、Application、Commandの仮宣言 | **試験中の新規3** | **15**（9＋3＋3） | SUI正本との自動同期・実復号・保存なし |

E22・E24候補はそれぞれ**同じ3つの試験用ファイルの別状態**であり、6ファイルを累積して追加したわけではない。型付き候補の行数は空候補比で**6行増**となる。E22候補の作業領域はStage 0の`semantic`に`applications`というソースの参照元を**1件増やした**構成を使う。名称も試験用に変更しているため、この「1件」はマニフェスト全体の差分が1行だけという意味ではない。

SUIの既存意味ファイル`semantic/sui/island.tei`は一時的な試験作業領域へバイト一致で複写されるが、それを新たなSUIドメイン実装や受理済みの正本と計上しない。原本はSUI側のRepositoryと既存Stage 0のままである。

## 何を比較でき、何を比較できないか

受注明細の**67行はすでに存在する宣言・案件UI**の合計であり、TEI採用に際して今回新たに手書きした67行ではない。SUI側の**9／15行は仮の接続記述**であり、完成したSUI統合の必要行数ではない。「受注明細は67行、SUIは15行で低コスト」と比較することを禁じる。

それぞれの測定値は以下のように整理する。

| 比較したい指標 | 今回観測できた値 | まだ測れていないもの |
| --- | --- | --- |
| 既存資産の再利用 | 受注明細の既存5ファイル、SUIのStage 0意味ファイルと既存SUI Native実装に変更しない試験 | 実案件での既存資産検索・接続に費やした時間 |
| 新しいTEI宣言 | SUIの試験候補3ファイル・9行。入力型を表現すると同じ3ファイル・15行 | 実SUIで採用する正式契約、必要な成果物・Target選択 |
| 構成の接続箇所 | 候補作業領域に`applications`という参照元を1件追加 | 実Provider・UI Kit・Native Target・リリースへの追加接続数 |
| 重複管理 | 新しい製品Core宣言や第二Lockを作成していない | 異なる製品契約との意味上の重複箇所数 |
| 更新再作業 | [E25](E25_CROSS_REPOSITORY_REQUALIFICATION.md)の実Git更新1回で、SUI実装4ファイル不変／試験4ファイル変更／CI1ファイル新規を確認済み | 実際に必要だった手動修正回数、変更に要した時間 |
| 生成AIへの追加質問 | **未計測** | 質問の定義、回答までの往復数、再質問回数、案件別の分布 |
| 実行先での合格 | **未検証** | 同じ構成をWeb／Nativeの実Targetへ組み込む結合・E2E |

この段階では「完成した二つの実アプリケーションの導入コスト」の比較結果ではなく、**今後の導入作業と変更を比較するための再現可能な数値基準**だけを得た。

## 既存構成機構との結び付き

[E22](E22_NATIVE_APPLICATION_CANDIDATE.md)の隔離作業領域から、実`workspace.Load`と`driver.NewResolver`を使う。受注明細の既存`order_entry.submit_order`とSUI候補の`sui.move`をそれぞれ解決して、数えたファイルが意味なく置かれた断片ではないことだけを確認する。[E24](E24_NATIVE_INPUT_CONTRACT_BOUNDARY.md)の型付き候補についても実際のDriverに通す。

ただし、その結果は**Authority・現行権限・実データ保存・Targetでの動作を証明しない**。SUI側の4つの実装ファイルと最新の動作試験を参照・活用し、TEI側へコピーして測定値を水増ししない。検証と結果を得たコードはReferenceの試験に限定し、プロファイル専用の二重登録簿や独立した依存関係解決器は実装しない。

## 次に測るべき値と判定

既存の構成方式を基準に実受注明細と実SUIの**それぞれ同じ条件の導入手順**を記録する必要がある。各作業について、どの既存Sourceを参照したか、どのSourceを何行変更・追加したか、手動判断を何回求めたか、実Targetで何を確認できたか、同じ更新時に何回再検証したかを別に記録する。

反証可能な採否条件は[E10](E10_COMPOSITION_ADOPTION_DECISION.md#受入判断今は保留)にある。新しい構成Profileを導入した場合の同条件の測定値が存在しないため、現時点では**追加Profileによって生産性が向上した**とも、**不要であることが証明された**とも断定しない。

### 実行

```sh
go test -count=1 ./reference/application-composition -run '^TestE26' -v
```

この測定で成功すれば、試験ログへ実参照Source5ファイルの行数と隔離した3つのNative候補の行数が出力される。個々の計測値はソースと対応するため、将来ソースが更新された場合に意図せず旧値を使い続けることを防ぐ。行数が変わっただけでは、構成の意味が破綻したとは判定しない。その場合はこの基準を再測定し、変更理由を確認する。
