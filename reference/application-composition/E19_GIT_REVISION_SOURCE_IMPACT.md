# E19：Git改訂に固定した意味ソースと変更影響の照合

**目的**：[Issue #1016](https://github.com/hat47x/tei-platform/issues/1016)の構成変更検査について、二つのソース状態を単に比較するだけでなく、**各状態がどのGitコミットのどのファイル内容に由来するか**を確認する。

[前段のE18](E18_TWO_PARSED_SOURCE_STATES.md)では、隔離した作業領域の二状態を用いて意味上の関係の変更と影響候補を確認した。E19は同じ実参照モデルを使い、試験内に**一時的なGitリポジトリを作って、二つの独立したコミットIDを確定**する。

## 検証する連鎖

[E19のGoテスト](e19_git_revision_source_test.go)は次の条件を検査する。

1. `reference/workspace`を安全な一時ディレクトリへ複製し、初期状態をGitコミットへ記録する。
2. `sales.order.customer`から`sales.order.account_contact`への関係名変更と、`order_entry.customer_reference`の参照修正だけを行い、次のコミットを作る。`git diff --name-only`の結果が**意味定義とPatternの2ファイルだけ**であることを検査する。
3. 旧コミットは独立した`git worktree --detach`で復元し、新コミットは元の作業領域で読み取る。両方について`HEAD`と期待したコミットIDの一致、`git status --porcelain`が空であること、`git show <改訂>:<ファイル>`の**Git内部に保存されたバイト列**と作業ファイルの一致を検査する。
4. 旧・新双方の`workspace.Load`とSource Indexから、関係とPatternの定義元が一意であること、出典指紋が`git show`で得られるバイト列のSHA-256と一致することを確認する。
5. 既存の`index.Build`・`derivedbridge.FromIndex`・`modelref.ReviewImpactDiff`を再利用し、関係の削除／追加と、PatternおよびApplicationの再確認候補を検査する。モデルの依存関係を二重に管理しない。
6. 変更後の作業ファイルを**コミットせずに書き換える負例**を実行し、Gitの改訂IDが不変でも「固定したソースの出典としては使えない」と判定する。

この試験は既存のGo通常テストに含める。Gitコマンドが利用できない環境では成功扱いでスキップせず、検証環境の不備として失敗させる。

## 資格の範囲

| 判定 | E19で確認できること |
| --- | --- |
| ソース所在・同一性 | 選択した2ファイルについて、Gitコミット→保存バイト列→Source Index指紋の対応を確認する |
| 意味上の変更と影響候補 | 既存の型付き解析による直接参照の候補を提示する。自動再適用はしない |
| 全体の依存閉包 | **未保証**。既知の未解決参照が残る |
| 業務意味の承認と実行 | **未保証**。Provider適合、権限、SUI Native Actionを判断しない |

**注意：** ここで使うGitコミットは、試験が実参照モデルから生成した**隔離された二つの試験改訂**である。TEI本体の既存main履歴に、同じ意味変更が実際に提出・承認されたという証拠ではない。二つの公開Gitコミットの間で案件が採用した構成を再現する段階は、今後の課題として残る。

E19を構成プロファイルの正式採用条件にすり替えない。既存のソース索引・型付き参照機構がつながることを再現可能に示す、限定した回帰検査である。
