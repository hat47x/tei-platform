# 多言語の業務データ――版と翻訳提案の参照実装

- **状態**：D1の小さな読み取り専用実証。正式な多言語属性型、永続化方式、AI翻訳器、翻訳の承認機構ではない。
- **担当課題**：[Issue #1453](https://github.com/hat47x/tei-platform/issues/1453)
- **設計**：[多言語業務データとAI翻訳支援](../../plan/design/MULTILINGUAL_BUSINESS_DATA_AND_AI_TRANSLATION_2026-10.md)

## 対象とする二つの事例

商品`P-100`の説明では、業務上の商品識別子と属性の意味上の参照を変えずに、日本語の原文、原文の特定版に基づく英語訳、公開されている各言語の版を区別する。原文が改訂されると、既に保存された英語訳は**記録として残る**が、現在の正式な訳文としての読取りは失効する。

独立した二言語の契約の例では、日本語版と英語版を別々に作成・承認できる。日本語版が変更されたからといって英語版を自動的に失効させたり書き換えたりしない。両言語を同時に発行する必要のある正式契約の組の承認は、別途、業務上の契約として検証する。

## 実装上の最小表現

- `Key`：テナント、レコード、既存の`modelref.Key`で示す属性、言語、用途に応じた版区分。業務上の識別と文章の版を分ける。
- `Revision`：言語別の文章、版、起草・翻訳・独立作成の区分、翻訳した原文の厳密な版、候補／確認済みの状態。
- `Publication`：どの文章版を公開するかの明示的な参照。単なる最大版番号では決めない。
- `Snapshot`：前述の情報を固定した読み取り用の入力。この参照実装は実際のデータベースを変更しない。
- `TranslationProposal`：翻訳による変更候補。元の文章版と対象言語の現在の公開版に照らして古い候補を拒否する。

文章の確認状態として与えた`approved`は**合成した試験値**であり、既存のTEIの変更受理手続や人間の承認を実行したことを示さない。また、`Select`は既存の読取権限の検査を代行しない。呼び出し元が対象のデータへアクセスできることを確認した後に、版の選択を検査する参照用の関数である。

## 実行方法

リポジトリのルートから実行する。

```sh
go test -count=1 ./reference/multilingual-business-data
go test -race -count=3 ./reference/multilingual-business-data
go vet ./reference/multilingual-business-data
gofmt -l reference/multilingual-business-data/*.go
```

試験では、次の不変条件を確認する。

1. 同じ商品と属性の値について、言語別の文章が存在しても元の業務上の識別子を保つ。
2. 原文の公開版が変わると、以前の原文に従属する公開翻訳を失効させる。古い記録は自動的に削除しない。
3. 翻訳候補の追加は公開を意味せず、明示的な発行参照によってのみ公開版が選択される。
4. 更新候補が参照した原文の版・翻訳先の既存版が変わった場合、競合を返す。
5. 別テナントの文章を誤って参照する関係は不正とする。
6. 各言語で独立した正式文章は、一方の改訂を他方の自動失効としない。
7. 翻訳済みの言語からさらに翻訳する連鎖はD1の対象外として拒否し、間接的な失効を見落とさない。

## 実証できていないこと

- `internal/semantic.Attribute`への正式な意味拡張や、実データソースの権限を伴う更新。
- SQLite／PostgreSQLにおける言語別の従属表、JSON列、既存SQLとの往復と移行。
- 言語別の全文検索、ソート、言語の代替表示、地域別の数値・日時書式。
- 複数言語が共同で正式な版となる契約の組としての発行・署名。
- 生成AIによる翻訳の生成、用語集・翻訳記憶、承認者の認証、原文の更新を受けた非同期処理。
- 機密区分、外部AIへの情報送信の許可、監査ログ、保持期限を含む本番運用。

この参照実装で得た正負の検証結果を踏まえて、D2の物理保存・検索とD3の生成AI翻訳へ進める。新たな意味モデルや第二の権限管理をコアへ先回りして実装しない。
