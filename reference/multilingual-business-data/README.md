# 多言語の業務データ――版と翻訳提案の参照実装

- **状態**：D1の小さな読み取り専用実証。正式な多言語属性型、永続化方式、AI翻訳器、翻訳の承認機構ではない。
- **担当課題**：[Issue #1453](https://github.com/hat47x/tei-platform/issues/1453)
- **設計**：[多言語業務データとAI翻訳支援](../../plan/design/MULTILINGUAL_BUSINESS_DATA_AND_AI_TRANSLATION_2026-10.md)

## 対象とする二つの事例

商品`P-100`の説明では、業務上の商品識別子と属性の意味上の参照を変えずに、日本語の原文、原文の特定版に基づく英語訳、公開されている各言語の版を区別する。原文が改訂されると、既に保存された英語訳は**記録として残る**が、現在の正式な訳文としての読取りは失効する。

独立した二言語の契約の例では、日本語版と英語版を別々に作成・承認できる。日本語版が変更されたからといって英語版を自動的に失効させたり書き換えたりしない。両言語を同時に発行する必要のある正式契約の組の承認は、別途、業務上の契約として検証する。

## 実装上の最小表現

- `Key`：テナント、レコード、既存の`modelref.Key`で示す属性、言語、用途に応じた版区分。業務上の識別と文章の版を分ける。
- `Revision`：言語別の文章、版、起草・翻訳・独立作成の区分、翻訳した原文の厳密な版、候補／確認済みの状態。
- `Publication`：どの文章版を公開するかの明示的な参照。単なる最大版番号では決めない。
- `Snapshot`：前述の情報を固定した読み取り用の入力。この参照実装は実際のデータベースを変更しない。
- `TranslationProposal`：翻訳による変更候補。元の文章版と対象言語の現在の公開版に照らして古い候補を拒否する。

文章の確認状態として与えた`approved`は**合成した試験値**であり、既存のTEIの変更受理手続や人間の承認を実行したことを示さない。また、`Select`は既存の読取権限の検査を代行しない。呼び出し元が対象のデータへアクセスできることを確認した後に、版の選択を検査する参照用の関数である。

## 実行方法

リポジトリのルートから実行する。

```sh
go test -count=1 ./reference/multilingual-business-data
go test -race -count=3 ./reference/multilingual-business-data
go vet ./reference/multilingual-business-data
gofmt -l reference/multilingual-business-data/*.go
```

試験では、次の不変条件を確認する。

1. 同じ商品と属性の値について、言語別の文章が存在しても元の業務上の識別子を保つ。
2. 原文の公開版が変わると、以前の原文に従属する公開翻訳を失効させる。古い記録は自動的に削除しない。
3. 翻訳候補の追加は公開を意味せず、明示的な発行参照によってのみ公開版が選択される。
4. 更新候補が参照した原文の版・翻訳先の既存版が変わった場合、競合を返す。
5. 別テナントの文章を誤って参照する関係は不正とする。
6. 各言語で独立した正式文章は、一方の改訂を他方の自動失効としない。
7. 翻訳済みの言語からさらに翻訳する連鎖はD1の対象外として拒否し、間接的な失効を見落とさない。

## 実証できていないこと

- `internal/semantic.Attribute`への正式な意味拡張や、実データソースの権限を伴う更新。
- SQLite／PostgreSQLにおける言語別の従属表、JSON列、既存SQLとの往復と移行。
- 言語別の全文検索、ソート、言語の代替表示、地域別の数値・日時書式。
- 複数言語が共同で正式な版となる契約の組としての発行・署名。
- 生成AIによる翻訳の生成、用語集・翻訳記憶、承認者の認証、原文の更新を受けた非同期処理。
- 機密区分、外部AIへの情報送信の許可、監査ログ、保持期限を含む本番運用。

この参照実装で得た正負の検証結果を踏まえて、D2の物理保存・検索とD3の生成AI翻訳へ進める。新たな意味モデルや第二の権限管理をコアへ先回りして実装しない。

## D2：SQLiteとPostgreSQLの実保存を使う追加検証

`testdata/schema.sql`は、SQLiteとPostgreSQLで共通に動かす**参照用の物理構造**である。業務アプリケーションの実スキーマや、新しいTEI標準テーブルを定めるものではない。利用者のデータベースへ適用しない。

言語別の履歴と、現在の公開版への参照を別の表に置く。主キーはテナント、業務レコード、意味上の属性、言語、用途別の版区分、文章版を区別する。外部キーは、存在しない翻訳元と公開先を拒否する。翻訳元の言語と文章版を保持しても、業務レコード自体の同一性は変えない。

`tei_multilingual_current`という読み取り用のビューでは、承認済みの公開版に加え、翻訳元の版が現在の公開原文に一致する場合だけ訳文を返す。原文が改訂されたときも履歴を削除せず、旧版の翻訳は表示対象から除外する。言語の自動代替はしない。

このビューは**利用者やテナントの権限検査を代行しない**。利用側は既存の権限を検証したうえで、`tenant_id`、業務レコード、属性、言語、版区分を明示して検索する。SQLに直接書き込める者が任意に付けた`approved`を、正式な人間の承認とみなしてはならない。実際の書込み・承認・移行は、既存のデータベース契約と受理機構が担当する。

### 実測する処理

- SQLite：メモリ内ではなく一時的なファイルに保存し、別の接続から読み直す。外国キーは**接続ごとに**有効化する。
- PostgreSQL：一時的なCIサービスで同じSQL構造を構築し、言語別の値を保存して読み出す。
- 両方：原文改訂に伴う翻訳の失効、古い訳文の履歴保持、未承認候補の非公開、独立した言語の正式文章、テナント境界、明示された言語での部分文字列検索、存在しない翻訳元の拒否を検査する。
- 更新競合：SQLiteでは書込みトランザクション、PostgreSQLでは翻訳元公開版の行ロックを使い、原文の版確認と翻訳先の条件付き更新を同じ処理として検査する。実際のAIによる翻訳や並行負荷試験ではない。

CIは`tei-multilingual-business-data-ci.yml`を利用する。SQLiteはPython標準の`sqlite3`、PostgreSQLは既存のGo依存`pgx/v5`を使用し、SQLiteドライバーや別のプラグイン解決器を追加しない。

```sh
python3 -m unittest discover -s reference/multilingual-business-data -p test_sqlite.py -v

# PostgreSQLの試験は、専用の一時データベース接続先を明示したときだけ実行。
TEI_MULTILINGUAL_PG_DSN='postgres://tei:tei@127.0.0.1:5432/tei?sslmode=disable' \
  go test -run '^TestPostgresRelationalRoundTrip$' -count=1 ./reference/multilingual-business-data
```

PostgreSQL試験の実行先には既存の同名テーブルがないことが前提。上記のDSNはCIの使い捨てサービスの例であり、実運用の接続情報ではない。

### D2で残る停止線

- 現段階はアプリケーションの意味モデルから物理SQLへの**自動生成**と、SQLから既存の意味モデルへの自動取込を実証していない。
- 共通のSQLで同じ例を試しても、SQLiteとPostgreSQLの全文検索、照合規則、言語ごとの索引の一致は主張しない。今回の検索は部分文字列の一致だけである。
- スキーマの列に保存された言語タグを標準化する処理や、公開者の実際の権限・監査・契約の共同発行は含まない。
- 既存SQLが正本の案件では、そのスキーマをTEIのこの参照用構造へ変換することを必須としない。既存テーブルと意味上の属性との読取り契約は、次の実証で比較する。

## D3a：翻訳候補の準備・文脈制限・再検査

`translation.go`は、生成AIに依頼する前後の手順を**読み取り専用で検証する参照実装**である。実際のLLM接続、翻訳サービスの選択、翻訳の承認やDB書込みはしない。

- `SnapshotReader`で公開版と意味参照を取得し、`CheckProposal`で原文の版と翻訳先の版を照合する。原文が未承認の場合や、翻訳先に独立した正式文がある場合は依頼しない。
- 業務用語集`TranslationTerm`は**テナント・意味上の属性・原文言語・対象言語**が一致し、対象文に現れた用語に限って翻訳器へ渡す。周辺の業務レコードを自動収集しない。
- `TranslationMemory`はテナント・意味参照・用途・言語対・原文の**完全一致**で再利用候補を探す。確認済みの翻訳記憶でも現在の業務レコードには未承認の候補として返す。別テナントからの流用、登録順による曖昧な候補の選択はしない。
- 既に同じ原文版に対応する確認済みの公開訳があれば再生成しない。これにより、必要な文章だけを翻訳する。
- `Translator`は呼び出し元で選定済みの翻訳器を受け取るだけの境界。外部転送には呼び出し元による**明示的な許可**と`public`という分類を必要とし、`restricted`の文面を外部送信しない。実際の利用権限の検証はこの参照実装の責務ではない。
- 変更不可の識別子や数値は、作成者が列挙した文字列`Protected`の出現回数を比較する。原文側にない値、訳文で増減した値を拒否する。用語集で指定した必須訳語の有無も検査する。これは**MessageFormat 2のパーサーでも、自然言語の意味が一致するという保証でもない**。
- 翻訳器が返した後に`SnapshotReader`から現在の原文版と翻訳先の公開版を読み直す。参照版が変わった場合や同じ版番号で原文が変更された場合、競合として候補を拒否する。
- 成功結果は`TranslationProposal`のままであり、確認済みや発行済みに昇格しない。実際の受理処理は、更新トランザクション内で**独立に同じ照合を繰り返す必要がある**。

生成AI向けの実アダプター、翻訳に必要な業務文脈の閉包（属性の周辺の業務規則、確定した用語の版など）、翻訳依頼・応答の追跡記録、文章全体の意味確認と人間によるレビュー、権限を伴う正式な受理操作、翻訳記憶の実保存・保管期間は未実装。機械的な文字列照合だけで、否定表現、数値の単位、法的な同等性、正確な翻訳品質を保証しない。
