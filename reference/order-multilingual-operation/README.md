# 受注業務の英語化運用と原文改訂時の訳の失効(`order-multilingual-operation`)

運用者が、日本語で動いている受注業務を、通常のプラグインにも受注の業務定義にも手を入れずに、後から追加する英語の言語プラグインで英語でも運用できるようにする技術検証用サンプルです。確かめたいのは、日本語の原文を一度改訂したとき、確認メッセージ、画面の表示名、機能名のうち改訂した原文に従属する英訳だけが失効し、他の訳は残るか、という点です。

- 状態: 設計案は提案段階です。このREADMEは入口であり、通しの流れは実装していません。各工程の実装、試験、実環境での確認の状況は、下の工程表で工程ごとに区別して示します。
- 設計の正本: [技術検証用サンプルの統合設計 4.8節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#48-受注業務の英語化運用と原文改訂時の訳の失効order-multilingual-operation)。技術検証用サンプルの位置づけ、物語、受け渡しの詳細はそちらを参照してください。
- 各資産の説明と使い方は、それぞれのREADMEが正本です。この入口は工程との対応だけを示します。

| --- | --- | --- | --- |
| P-MIX-03 | 4 | 原文の改訂直後に旧訳が混在したまま表示される | 同じ対象一覧の突合表で、従属訳だけが失効し、他は残る |

## 通しの完了条件

現在、通しの完了条件はどれも成立していません。所有者、環境、原文言語、項目名の識別子が資産ごとに異なり、一つの原文改訂で通して動く構成がないためです。

必須の条件は次の三つです。

- 同じ環境と固定情報の下で日本語原文を一度改訂すると、確認メッセージ、表示名、機能名の旧英訳が従属訳だけ失効し、独立した文章、他の言語、他の提供元の訳は残る。改訂前後の同じ対象一覧の突合表で確かめ、別々の試験の足し算では満たさない。
- 再生成した配布候補のダイジェストが改訂前と異なり、改訂前のダイジェストに固定した表示は拒否される。
- 許可、受理、固定情報の失効、または言語プラグインの撤去が起きても、日本語の原文で業務が続き、旧訳を黙って使わない。

工程5と6は、前提の接続が成立した場合に限って条件に加えます。それまでは達成済みとして数えません。

## 基盤への改善圧力

見出しだけを示します。現状、求める条件、確認方法は、4.8節の「基盤への改善圧力と現状」を参照してください。

- 固有: 所有プラグイン、環境、原文言語、項目名の識別子が資産ごとに別の合成値である(データ)
- 固有: 原文版の導出規則が資産ごとに異なる(コア)
- 固有: 翻訳の許可と受理の確認口が、表示名とメッセージで別の型と実装になっている(プラグイン)
- 固有: 実際の作業領域に、メッセージ、言語プラグイン、翻訳の宣言がない(データ)
- 固有: メッセージの引数展開と件数書式の接続がない(実行時)
- 固有: 業務データの多言語属性が、意味モデルと受理機構に接続されていない(データ)
- 固有: Goの選択規則とSQLの現在値ビューの直接比較、PostgreSQLでの別接続の読取りと並行更新の検査がない(検証根拠)
- P-MIX-03: 言語別の配布候補の信頼と、表示側での失効の伝播が成立していない(実行時)
- P-TX-02: 翻訳依頼と応答の追跡、受理トランザクション内での再照合が未実装(ツール)
- P-DB-04: 並びと比較の意味を宣言する手段がない(データ)
