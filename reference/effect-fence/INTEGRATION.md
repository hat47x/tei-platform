# 認可と副作用の確定境界を接続する設計メモ

対象：[#1174](https://github.com/hat47x/tei-platform/issues/1174)  
作業場所：`reference/effect-fence/`。現段階では参照実装の記録であり、TEI本体の仕様確定や実装完了を意味しません。

## 既存の実装から確認した事実

- `internal/driver/invocation.go`は、機能と実装の対応を解決し、`capabilityinvoke.Adapter`へ実行を委譲します。アダプターの内部で使う権限情報や保存先のトランザクションには立ち入りません。
- `internal/security/legacyauthorization/authorization.go`の`security.authorize`は、`SubjectID`・`Action`・`Resource`を受け取り、業務上の許可・拒否を返します。許可時の`AuthorizationGrant`はこの三項目を保持していますが、**認可版、主体リンクの版、権限変更を追跡する確定識別子は持ちません**。
- 同ファイルの`Rule.Evaluate`は許可の真偽、拒否理由、実行時エラーを返します。実際の更新処理と同じトランザクションに参加する契約はありません。
- `internal/security/legacyauth/authentication.go`の認証成功結果は主体の識別子です。実行時に提示された秘密情報を副作用の確定記録へ移してはいけません。
- `internal/semantic/capabilityinvoke/invocation.go`は、機能が宣言した結果形式を厳密に確認します。単一出力の機能に、フェンス側の都合で`denied`という未宣言の業務結果を追加することはできません。
- `internal/database/provider/provider.go`の`CapabilityTransaction`は、保存先がトランザクション機能を持つことを示すだけです。**認可の正本まで同じ確定境界にあるという証明にはなりません**。

## 必要な責務の分担

1. **入口（Web、CLI、その他）**：既存の認証経路で本人を確定し、任意の入力値では上書きできない主体を実行文脈へ保持します。入口別の役割規則は作りません。
2. **既存認可機構**：`security.authorize`と既存の認可規則を評価し、主体・操作・対象が一致する許可を返します。通常の事前判定はこれまでどおり利用します。
3. **権限版の提供元**：認可判断を左右する利用者の状態、主体リンク、所属・役割、対象別の許可などを変えた際に版が更新される必要があります。版の粒度はProviderが定義し、古い許可と新しい権限状態を区別できなければなりません。
4. **書込みを実行するアダプター**：操作識別子、対象版、許可の範囲と版を受け取り、保存先の確定処理で権限・対象版を再照合し、実際の更新と確定記録をまとめて確定します。実際にこの条件を満たす保存先だけが、永続的な原子性を申告できます。
5. **呼出結果の投影**：宣言済みの業務結果、無作用の拒否、実行障害、結果不明を分けます。最後の二つを「効果がなかった」と断定してはいけません。

```text
既存の認証 → 検証済み主体
                  │
            security.authorize
                  │
       操作範囲と版条件の固定
                  │
       保存先Adapterの保証を確認
                  │
     ┌────────────┴────────────┐
  原子的に照合可能          一体化できない
     │                          │
  版の照合＋更新＋記録        原子的保証は不成立
  を一つの確定境界で実行      条件付きAPIや補償を別途設計
     │
  成否と確定記録を返す
```

## 今すぐ接続できない理由

現行の`AuthorizationGrant`は権限版を持ちません。既存の認可規則を評価できても、書込み側のトランザクションが**その評価に用いた権限の正本と主体リンクの最新版**を同時に確認できるとは限りません。

権限版を任意の数値で補う、書込み直前に`security.authorize`をもう一度呼ぶ、`CapabilityTransaction`が真だから原子的だとみなす、といった方法では時間差の問題は解消しません。

先に必要なのは、対象となる実際の認可Providerごとに、権限変更の正本と対象データの更新が同一の確定境界を共有できるかを調べることです。共有できない場合は、その構成を原子的として承認しません。

## 今回導入した契約の扱い

`contract.go`の`BoundaryContract`は、実行先に保証を要求する場合の**申告内容の検査器**です。

- メモリ内ロックの証拠は、単一プロセス内の保証としてのみ受け付けます。永続的な原子性は要求できません。
- 実トランザクションまたはProvider側の条件付き更新であっても、権限版、対象版、主体リンクの照合、確定記録が同一境界にないものは拒否します。
- 外部送信が確定境界の外にある構成や、実Providerの証拠がない構成は永続的な原子性を名乗れません。
- 現時点では`ProofReference`は申告された文字列です。文字列があるだけで試験の妥当性を保証するものではありません。永続的な原子性を許可するには、配備側で管理する独立した`EvidenceVerifier`が、その保存先構成と実証済み成果物を確認する必要があります。現在の参照実装では無条件の自己申告は不合格になります。検証器をアダプター自身に供給させたり、無条件で合格させたりしてはいけません。
- 利用する機能が原子的保証を必要とする場合、無条件に低い保証へ格下げしません。

この小さな契約を基に、将来的に実アダプター・プラグインの適合性検査へ接続します。既存の`capabilityinvoke.BusinessResult`、固定のプラグイン種別、Driverの実装選択規則は今回変更しません。

## 実SQLiteに対するGo適合性試験を追加した理由

最初のSQLiteの実証は、Pythonでトランザクション境界を確かめる独立試験でした。Goから同じ条件を確認するため、ビルドタグで明示的に選ぶ試験用のSQLite接続処理を追加しました。Goの共通適合性検査7項目を、この実SQLite接続処理に適用します。

ここで検証するのは、試験用権限表、更新対象、確定記録が**同一のSQLiteファイルにある場合**の確定動作です。外部認可の版や主体リンクの正本を用いた保証は、依然として未成立です。SQLiteを使うという理由だけで、この実装を標準データベースProviderやPluginとして昇格させません。

同一ファイルを扱う二つの接続でも、Prepareで得たトークンは別接続に持ち込めません。これを明示的に拒否する試験を設けました。一方、切断・再起動後の再送には、保存済みの操作識別子と確定記録を使います。別接続で確定済み記録を照会する際も、現在の認可状態を先に照合します。

**次の実装上の判断点**は、実際の`security.authorize`が根拠とした主体リンク・所属・役割の版を、どの保存先が同一トランザクション内で検査できるかです。認可正本と更新対象が別々なら、試験用のSQLite表へ認可版を写すだけで実際の原子的保証は成立しません。版の複製、同期、失効通知には遅延と障害があるため、機能が要求する保証を満たす方式をProviderごとに検証する必要があります。

## 第5段階：既存認可結果の厳密な受渡し

`legacy_authorization.go`に、既存の`legacyauthorization.Adapter`（`security.authorize`）から返る許可結果を、メモリ内の副作用確定試験へ渡す入口を加えました。役割や所属の判定式を複製しません。

- 主体は認証済み実行文脈から引き渡す必要があり、書込み要求の主体をそのまま信用しません。主体の不一致では認可処理を呼ばずに拒否します。
- 既存認可が返す機能ID、結果形式、`AuthorizationGrant`の主体・操作・対象を検査します。別の主体や対象の許可、別の型の成功結果、未定義の結果は契約違反として書込みを進めません。**既存GrantはApplicationとCapabilityも含まない**ため、これらの識別値の真正性は呼出側のBinding解決が担い、今回の接続口だけでは検証できません。
- 既存認可の業務拒否は無作用の拒否に、認可系障害と結果契約違反は実行エラーに分けます。拒否理由の内部情報は、参照実装の戻り値へ転写しません。
- `internal/security/legacyauthorization/authorization.go`でも、`FindBySubject`が返すレコードの主体IDを入力と照合します。不一致・欠落の場合は、誤った利用者レコードで役割判定せず、保存先契約のエラーとして停止します。
- この入口が受け取る`AuthorizationGrant`には**認可版と主体リンク版がありません**。既存認可を呼べることと、失効・保存を同一トランザクションで確定できることは別です。`MemoryStore`内の版は引き続き合成状態であり、外部の役割変更と同期する保証はありません。

対象範囲の実装・試験は、新しい`legacy_authorization_test.go`および既存認可パッケージの回帰試験にあります。権限版を得られない実Providerについては、従来どおり`GuaranteeDurable`の要求を満たしたとみなさず、永続的な原子性を名乗りません。

後続の実装では、認可の正本を変更するすべての経路に対する単調増加の版、主体リンクの版、そして保存先での同一確定境界の検証手段をProvider側に設ける必要があります。その際も`security.authorize`の役割判断を別の場所へ複製しません。

## 第6段階：認証後のアカウント状態変更を認可へ反映する

既存の`security.authenticate`は、無効化、有効開始・終了時刻、ロック解除時刻を検査していました。一方で`security.authorize`は、主体から利用者レコードを再取得してもこれらの項目を検査せず、組織・役割の判断に進んでいました。認証後にアカウントが無効化された場合でも、新たな操作が許可される余地がありました。

`internal/security/legacyauth/account_state.go`に、利用者の利用可能状態を調べる共通関数`User.AccessDenialAt`を追加しました。認証と認可の両アダプターが同じ関数を使い、無効化・開始前・期限切れ・ロック中を通常の業務拒否として扱います。認可側では既存の役割規則を評価する**前**に判定します。時刻境界を明示的に試験し、認証と認可の解釈をそろえます。

副作用フェンスの参照接続口でも、確定した操作の後でアカウントを無効化すると、その後の新しい準備要求が拒否され、保存対象は変化しないことを試験します。

**原子的な失効保証とは異なります。** 認可時点で読み取る利用者レコードが古ければ失効は見えません。また、認可アダプターが利用可能と判定した直後に無効化が起きても、現在の`MemoryStore.Commit`は実アカウントの最新版を再照合しません。従ってこの対応だけで#1174の受入条件である「失効変更と書込みを同一境界に置く」を満たしたことにはなりません。

この残課題を解消する際は、主体リンク・アカウント状態・認可規則が参照する正本を、永続化アダプターが確定時に検査できる版へ接続する必要があります。認可規則の内容を別の場所へ複製せず、実Providerが更新・版管理・確定を一貫して扱えることを検証します。

## 第7段階：実SQLiteで主体リンク・所属・規則版を確定時に再照合

`sqlite_authority_dependencies_cgo.go`に、試験用の認可根拠の版を追加しました。同じSQLiteファイルの`authority_dependencies`表に、主体リンク、所属、認可規則の3種類を独立して記録します。版は各種類・権限範囲ごとに単調増加とし、失効状態も記録します。

`RequireAuthorityDependencies()`を有効にした試験用アダプターは、操作を準備するときに3種類すべての版と利用可能状態を取得します。いずれかが欠けるか失効していれば、準備を拒否します。確定するときには、`BEGIN IMMEDIATE`で開始した**同じSQLiteトランザクション内**でその3種類と操作単位の権限版を照合し、その後に対象データと確定記録を更新します。版または利用可能状態の変更が先に確定していれば、副作用は発生しません。失効後の準備済み再送も拒否し、記録を開示しません。

別のSQLite接続から、主体リンクと所属の失効、許可状態が続く認可規則の改版を行う回帰試験を追加しました。確定処理とリンク失効の同時実行では、先に確定した側が勝つ直列化順序だけを許容します。改版の単調増加、必須版の欠落、失効後の確定記録非開示も確認します。

**保証の範囲は厳格に限定します。** この3種類の表は、役割・所属・主体リンクの実データを格納した正本ではなく、独立した試験用の版情報です。変更経路から版を更新することを試験で模しているだけで、実際の`security.authorize`の判定がそれらの版に結び付いているわけではありません。`RequireAuthorityDependencies()`も試験用の選択肢であり、本番環境で省略可能という意味ではありません。

したがって今回確認できるのは、「**実際のSQLiteで、版条件と書込みを一つのトランザクションに置いた場合の競合・失効検出**」までです。「**実際の認可正本の変更と書込みが必ず同じ版条件を使う**」ことは未実装です。この差を埋めるには、実Providerの変更経路がすべて版を更新し、許可の取得がその正確な版を返し、確定先が同じ正本の版を検査できることが必要です。

GoのSQLite試験は従来どおり`tei_sqlite_reference && cgo`タグ付きで任意実行とし、通常ビルドとTEI製品にSQLite依存は加えません。
