# 副作用確定時の権限検査 — 最小参照実装

対象：Issue [#1174](https://github.com/hat47x/tei-platform/issues/1174)。本資料は最初の実験であり、TEI本体の実行経路へ組み込まれた仕組みではありません。

## 解決したい問題

事前に権限を確認しても、保存処理までの間に権限が失効することがあります。保存対象も別の操作によって変更され得ます。必要なのは、**副作用を確定する境界で、権限の版と保存先の版を同時に照合すること**です。保存先が別のシステムにある場合、認可の再実行だけでは原子的な整合性を保証できません。

この参照実装では、試験用の権限状態と保存先を一つのメモリ内のロックで管理し、版の照合と値の確定を同じ区間で実行します。外部DB、外部API、複数プロセスを跨ぐ原子性は実証していません。

## 操作の流れ

```text
検証済み主体と操作の範囲（模擬）
  → Prepare：現在の許可を照合し、要求を固定
  → [失効・別の書込みが入り得る]
  → Commit：権限版・保存先版を一つのロック内で再照合
    → 合致：保存と確定記録を同時に更新
    → 不一致：無作用の拒否
  → Lookup：権限確認のうえ確定記録を照会
```

- `Scope`はアプリケーション、機能、主体、操作、保存先を一組として照合します。主体をHTTP入力やCLI引数から信用するための仕組みではありません。
- `OperationID`は再送の識別子です。同一操作・同一内容なら、二回目以降の書込みは行いません。識別子だけ一致して内容が異なれば拒否します。
- `Permit`は事前検査の不透明な結果です。呼出元が権限版を自由に差し替えられないよう、参照実装内に情報を保持します。
- `Receipt`には確定識別子と保存先の版だけを含め、保存値や資格情報は含めません。

## 結果の区別

| 状態 | 意味 | 再試行時の扱い |
| --- | --- | --- |
| `prepared` | 事前検査を通過した。副作用はない | 確定処理へ進む前に再照合する |
| `committed` | 同一ロック内で保存と確定記録が成立した | `OperationID`で照会する |
| `replayed` | 既に確定した同一操作。新たな効果はない | 元の確定記録を返す |
| `denied` | 不正な範囲、失効、版の不一致などによる無作用の拒否 | 根拠を再確認し、必要なら新たな操作として開始する |
| `error`（Goエラー） | 中断や内部障害。実行の確定状態は個別に調べる必要がある | 無条件に再送しない |

外部Providerの通信障害では、結果が**不明**な場合があります。この参照実装が持つメモリ内の確定記録を、実Providerでの耐久的な確定記録や結果照会に読み替えてはいけません。

## 既存機構との接続方針

`internal/driver/invocation.go`は、解決済みのBindingから`capabilityinvoke.Adapter`を実行します。`internal/semantic/capabilityinvoke/invocation.go`は業務結果と実行エラーを区別し、未宣言の業務Outcomeを拒否します。ここでは両者を変更しません。

次に実Adapterを接続する際は、既存の`security.authorize`等を認可の正本とし、検証済みの主体と操作範囲を結び付けます。外部認可基盤が返す版・主体リンク版・保存先の版を、Providerが実際の確定操作で原子的に照合できるかを先に判定してください。**参照実装に権限を模した表があるからといって、別のRole判定エンジンを本体へ追加してはいけません。**

Capabilityが`output`だけを定義する場合、失効による拒否を未宣言の名前付きOutcomeとして注入することはできません。実行フェンス共通の「確定しなかった」という区分と、Capabilityが宣言した業務結果、実行エラーの対応は、後続の契約検討で決めます。HTTPやCLIが勝手に成功へ丸めてはいけません。

現在のPlugin契約には刷新計画（[#1223](https://github.com/hat47x/tei-platform/issues/1223)）があります。汎用Plugin型や固定列挙値をここで追加することは避け、実Adapterの原子性確認を先行させます。

## 第2段階：共通の適合性試験

`conformance.go`の`CheckAtomicConformance`は、試験用の隔離された保存先へ適用する**検査器**です。業務用の新たな認可エンジン、TEI標準の実行インターフェース、プラグイン種別ではありません。今後の保存先アダプターが異なる準備トークンを用いても試せるよう、試験用の束縛はトークンの実体を固定しません。

一つの空の保存先を各検査ごとに生成し、次の七つを調べます。

| 検査 | 必要なふるまい |
| --- | --- |
| 確定・観測・再送 | 保存と確定記録が一致し、同一操作の再送で二重更新しない |
| 権限失効 | 事前認可後の失効を、保存確定時に検知する |
| 権限版の更新 | 許可が続く場合でも、古い許可版を使った保存を拒否する |
| 失効後の保留済み再送 | 先に確定した同一操作の記録を、後続Permitから失効後に開示しない |
| 保存先の競合 | 保存先が別途変更されていたら、古い版で上書きしない |
| 並列実行 | 同じ操作識別子による二つの確定を一つの効果にまとめる |
| 操作範囲 | 別の主体への許可の流用を拒否する |

あわせて、権限版の変更を無視する故意に不正なアダプターでは、失効と権限版更新の二検査が不合格になることを確認します。汚染済みの試験用保存先や、試験用保存先が未指定の場合も不合格にします。操作範囲の全項目と操作識別子について、不正な区切り文字や空白だけの値を拒否し、内部連番の桁あふれでは停止します。

実施コマンド：

```bash
GOENV=off GOWORK=off GO111MODULE=off go test -race -count=1 ./reference/effect-fence
GOENV=off GOWORK=off GO111MODULE=off go vet ./reference/effect-fence
```

上記は独立したGo標準ライブラリだけの参照パッケージを検査する入口です。全リポジトリの標準検証は、別途実際のコミットを固定して実行してください。

### 適合性検査が証明しない事項

適合性試験の対象となる認可版、保存先、操作記録が、**実際に同一の確定境界にあること**は、コードレビュー、トランザクション構成、外部Storeを使った割込み試験で別途確かめる必要があります。メモリ内だけで合格しても、別プロセスでの失効、プロセス障害後の確定記録、遠隔サービスへの二重送信は保証されません。

特に認可基盤が別のサービスにあり、保存先側でその認可版を原子的に確認できない場合、直前に認可をやり直す方式は「失効後の効果を完全に防ぐ保証」を満たしません。保証を得られない構成を成功扱いせず、Providerの条件付き更新・サーバ側認可・結果照会などを個別に設計します。

最終結果が不明な障害と、効果が発生しなかったと確認できた拒否は区別します。本参照実装の`Denied`を遠隔Providerの通信障害やタイムアウトに流用してはいけません。

## 実SQLiteによる確定境界の検証（任意の追加試験）

メモリ上の模擬Storeに加え、`sqlite_transaction_test.py`で**実際のSQLiteデータベース**を使った確定操作を検証します。Python標準ライブラリの`sqlite3`のみを使用し、Go本体や通常のビルドに依存を追加しません。リポジトリのルートから次を実行します。

```bash
python3 -m unittest -v reference/effect-fence/sqlite_transaction_test.py
```

一つのSQLiteデータベースに、試験用の権限版、保存対象、操作ごとの確定記録を置きます。`BEGIN IMMEDIATE`で書込みトランザクションを開始し、現在の権限版と保存対象の版を読み取ってから、保存対象の更新と確定記録の追加を同じトランザクションで実行します。`WAL`と`synchronous=FULL`を指定します。

確認する七つの条件は、①権限失効、②権限は有効なまま版のみ変更、③保存先の競合と接続し直した後の再送、④確定記録の保存失敗と保存対象のロールバック、⑤別接続からの同時確定、⑥操作識別子の衝突、⑦権限失効後の再送で確定記録を開示しないことです。

本試験で確かめるのは、**同じSQLiteファイルに権限状態と対象データが含まれる場合の、二つの独立接続間でのトランザクション動作**です。これは実データベースを使った試験ですが、TEIの既存`security.authorize`や`driver.Resolver`へ接続した実装ではありません。Pythonの`repr`による要求の比較も試験上の仮表現であり、正式な操作指紋ではありません。

認可の正本が別サービスに存在する場合、SQLite内の試験用の権限版を照合しても、外部サービスの認可状態との原子的な一致は証明できません。また、二つの接続での競合と再接続は検証しましたが、別プロセス間の障害、電源断、実運用の永続性、遠隔APIでの結果不明は未検証です。

今回の試験は、**通常のGo参照実装の回帰試験とは別の証拠**として扱います。将来、永続的なGo Adapterを実装する際には、型付きの認証済み文脈から権限版を得て、同じ確定境界で照合できるProviderに限って原子的な保証を宣言してください。

## 第3段階：保証要求と実認可機構の接点

詳しい設計上の判断は[認可と副作用の接続メモ](INTEGRATION.md)を参照してください。

`contract.go`で、アダプターが確定境界について申告する内容と、呼出側が要求する保証を比較します。少なくとも次を区別します。

| 必要な保証 | メモリ内の模擬保存先 | 実Providerで確認した一体的な確定 |
| --- | --- | --- |
| 単一プロセス内の原子性 | 参照試験では条件付きで許可 | 必要な条件が確認できれば許可 |
| 永続的な原子性 | **拒否** | 権限・保存先・確定記録が同一境界にあり、実Providerの証拠と照会経路がある場合のみ申告可能 |

この判定は申告内容の整合性を調べるものであり、アダプターの自己申告や証拠の参照文字列だけで、実際の原子性を検証したことにはなりません。**永続的な保証は自己申告だけでは必ず拒否**し、配備側で管理する独立した証拠検証器を指定した場合に限って判定を進めます。検証器が無条件に合格を返す構成は安全な証明になりません。

`gate.go`の`CommitWithRequirement`は、この判定を実際の書込み関数を呼ぶ前に行います。要求を満たせなければ書込み関数は呼ばれず、`GuaranteeUnavailableError`を返します。これは業務上の拒否として未宣言のOutcomeを生成するものではありません。現段階では参照実装の入口であり、TEI本体のDriverや実アダプターへの組込みは未実施です。

今回の既存コード調査で、`security.authorize`が返す`AuthorizationGrant`には主体・操作・対象しかなく、版情報が存在しないことを確認しました。従って、実際の認可正本の版を保存先で照合する連携方式の確立は、引き続き最重要の残課題です。

検証は通常のGo試験に含まれます。

```bash
GOENV=off GOWORK=off GO111MODULE=off go test -race -count=10 ./reference/effect-fence
```

## 第4段階：Goからの実SQLite接続を使った検証（任意実行）

`sqlite_fixture_cgo.go`と`sqlite_integration_test.go`を追加しました。どちらもビルド条件`tei_sqlite_reference && cgo`を指定したときだけ対象になり、**通常のGo実装やTEI本体にはSQLite依存を追加しません**。試験用の接続処理はSQLite C APIを直接呼び、`-lsqlite3`でリンクします。Linuxの場合、SQLiteの開発用ヘッダーと共有ライブラリが必要です。

```bash
# 追加依存がない通常の参照試験
GOENV=off GOWORK=off GO111MODULE=off go test -race -count=10 ./reference/effect-fence

# 任意の実SQLite接続を含むGo競合試験
CGO_ENABLED=1 GOENV=off GOWORK=off GO111MODULE=off \
  go test -race -tags tei_sqlite_reference -count=10 ./reference/effect-fence

# 任意の実SQLite接続を含む静的検査
CGO_ENABLED=1 GOENV=off GOWORK=off GO111MODULE=off \
  go vet -tags tei_sqlite_reference ./reference/effect-fence
```

同じ適合性検査7項目を**Goのメモリ内保存先と、実SQLiteファイルの両方**へ適用します。SQLiteでは、別の接続から権限版を変更して確定時の拒否を確認し、再接続後の保存結果再照会、二接続からの同一操作の同時確定、確定記録の保存失敗による更新全体のロールバックを確認します。追加で、同じ連番の操作トークンを別の接続へ渡しても他の書込みを確定できないことを試験します。

**証明の限界**：`sqliteFixture`が扱う権限状態は、同じSQLiteファイルに試験用として置いた値です。これは実DBでのトランザクション試験であっても、TEIの`security.authorize`や主体リンクの実際の正本を接続した証拠ではありません。また、この接続処理は適合性検査用であり、製品向けのSQLiteプラグインや汎用データベースアダプターではありません。SQLiteの合成権限の検証から、外部認可サービスや他のDBに対する原子的保証を推論してはいけません。

Goの`Permit`は、発行した保存先インスタンスと結び付けました。同じ内部連番が別の保存先で生じても、操作トークンを使い回せません。保存先の再起動後に使う再試行識別子は`OperationID`と確定記録であり、`Permit`を外部へ永続化・転送する設計ではありません。

### 保存先障害の分類

GoからSQLiteへ接続する試験では、操作の事前検査後に**認可表を参照できない状態**を作り、確定処理が業務上の拒否（`denied`）や成功を返さず、実行エラーを返すことを確認します。この障害では更新も確定記録も残りません。表を復旧し、改めて認可版を取得した操作は確定できます。

この試験は模擬認可表が属するSQLiteファイルの障害を扱います。実際の認可サービス停止、ネットワーク分断、外部APIへの送信結果が不明な障害を再現したものではありません。結果が不明な外部副作用を「何も起きなかった」と推定しないことが、別途必要です。

## 既存認可の結果を受け取る参照接続口

`legacy_authorization.go`の`PrepareWithLegacyAuthorization`は、既存の`security.authorize`を再利用し、主体・操作・対象が完全に一致する許可だけを`MemoryStore`の準備処理へ渡します。既存の認可規則は複製しません。入力主体と認証済み主体が異なる場合、認可アダプターを呼ぶ前に拒否します。

既存認可が返す許可の型、機能ID、結果形式、三つの識別値を検査します。認可の拒否を業務上の拒否として扱い、認可サービスの障害や契約違反を実行エラーとして区別します。拒否理由の内部情報は公開しません。

既存の利用者検索が**別の主体のレコードを返す不整合**も防ぐため、`internal/security/legacyauthorization/authorization.go`に主体IDの再照合を追加しました。契約違反の場合は、役割規則へ進まず実行エラーとします。

この接続口は、永続的な原子性の実装ではありません。既存の`AuthorizationGrant`に認可版はなく、メモリ内の模擬権限と実際の認可正本は結び付いていません。永続保証を要求する処理は引き続き`GuaranteeUnavailableError`で停止します。

対象の試験は次のように実行します。いずれも**変更範囲の検証**であり、リポジトリ全体の健全性検証ではありません。

```bash
go test -race -count=10 ./reference/effect-fence ./internal/security/legacyauthorization
go vet ./reference/effect-fence ./internal/security/legacyauthorization
```

[認可結果と確定境界の接続メモ](INTEGRATION.md)に、今回成立した部分と実Providerへ持ち越した条件をまとめています。

### 認証後の無効化・期限切れを、新しい認可判断へ反映する

認証と認可の両アダプターで、`legacyauth.User.AccessDenialAt`によりアカウントの無効化、有効期間、ロック状態を同じ規則で評価します。ログイン後にアカウントが無効化された場合でも、その後の`security.authorize`は役割を評価する前に拒否します。`PrepareWithLegacyAuthorization`を使う新しい操作の準備にも、この拒否が適用されます。

検証対象には`internal/security/legacyauth`も加わります。

```bash
go test -race -count=10 ./internal/security/legacyauth ./internal/security/legacyauthorization ./reference/effect-fence
go vet ./internal/security/legacyauth ./internal/security/legacyauthorization ./reference/effect-fence
```

この確認は**認可時点の状態を再評価する**ものであり、認可後に起きた失効と書込み確定の原子性は実証しません。権限版・主体リンク版を実保存先で同時に照合する条件は引き続き未完成です。

## 任意の実SQLite試験：認可根拠の版変更

実SQLiteの試験に、主体リンク・所属・認可規則の**3種類の版条件**を加えました。

`RequireAuthorityDependencies()`を指定した試験用の接続では、この3種類すべての有効な版がなければ操作を準備できません。`SetAuthorityDependency()`で別接続から版を更新・失効させた場合は、書込み確定のトランザクション内で比較して拒否します。許可が継続する規則の改版も、古い版を使った操作には適用されません。

追加した`sqlite_authority_dependencies_test.go`は、失効・改版・版の欠落・版の単調増加・確定済み操作の再送・別接続の並列競合を扱います。実行コマンドは既存のSQLite連携試験と同じです。

```bash
CGO_ENABLED=1 GOENV=off GOWORK=off GO111MODULE=off \
  go test -race -tags tei_sqlite_reference -count=10 ./reference/effect-fence
```

これは**同一SQLiteファイルに置いた模擬版情報**の実証であり、実認可サービスの正本、役割や主体リンクの実際の更新経路と同期した証拠ではありません。通常ビルドへのSQLite依存はありません。詳細と残る設計条件は[接続メモ](INTEGRATION.md)を参照してください。
