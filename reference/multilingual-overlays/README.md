# 通常プラグインへ後付けする多言語表示オーバーレイ（O1）

- **担当**：[Issue #1551](https://github.com/hat47x/tei-platform/issues/1551)
- **状態**：独立した参照実装。TEI製品のプラグイン契約・Editor・Web／Desktopに接続された機能ではない。
- **利用する既存機構**：`internal/plugin.ResolvedSet`、`internal/modelref.Graph`、[多言語表示資源E1](../multilingual-resources/README.md)。
- **隣接する業務データの多言語化**：[Issue #1453](https://github.com/hat47x/tei-platform/issues/1453)。業務レコードの文章や翻訳・受理の正本は、このオーバーレイの対象外。

## なぜ通常プラグインを修正しなくてもよいか

通常プラグインの機能定義や意味モデルが持つ、**安定した意味参照**と標準の表示名を利用する。環境／アプリケーション側が別ファイルの「表示面の結合定義」を用意すれば、通常プラグイン自身に翻訳用の構文やAPIを追加せずに、日本語の表示名へ英語の表現を重ねられる。

初期段階では既存`modelref.Node.DisplayName`だけを対象とする。任意のHTML、独自UI内部の固定句、意味参照のないリソース、業務レコードの文字列までも完全に自動翻訳することを意味しない。それらは後続の安定したリソース識別子や抽出用アダプターが必要。

## 合成の順序

```text
通常のプラグイン定義 ─┐
                       ├─ 既存Plugin Resolve + Lock ── 選択済みプラグイン集合
多言語プラグイン定義 ─┘                                    │
                                                            ▼
既存の型付き意味モデル ──────── 標準の表示名 ──────── 表示面の結合定義
                                                            │
        多言語資源の候補・確認済み翻訳 ── 適用許可 ────────────┤
                                                            ▼
                                           表示用オーバーレイの合成
                                                            │
                                         既存E1の言語選択・失効検査
                                                            ▼
                                       Web・Desktop等へ表示（今後）
```

**合成と翻訳の適用は、既存プラグインの選択・固定の後**に行う。多言語プラグインだけが任意の既存プラグインを書き換えられるわけではない。今回の`Grant`は、対象となる環境、翻訳の提供元、通常プラグインの正確なID・版、意味参照、表示箇所、言語をすべて指定する。

`Override`は、同じ言語・表示面を複数の多言語プラグインが提供するときだけ使う。置き換える提供元と採用する提供元を個別に指定し、登録順／ファイル読込順／番号による優先順位で暗黙に解決しない。競合する提供元が複数ある場合、**他の全候補を明示的に置き換える設定がなければ失敗**する。

`Grant`と`Override`を作成・採用できる利用者の権限検証は、この参照実装にはない。製品実装では既存の受理・権限境界を通じて確定した宣言だけを受け取る必要がある。プラグイン側が自分に適用許可を与えることはできない。

## 原文と翻訳の版

通常プラグインの意味モデルが持つ表示名を原文の表示資源とする。原文の**表示文字列のSHA-256照合値**を翻訳の`BasedOn`に保存する。これにより、業務意味の版が変わらない場合でも、元の表示名が変更されたときは翻訳を失効させられる。

通常プラグインのID・版も厳密に照合する。表示文字列の照合値だけでは、互換性のない新しいプラグイン版の表示に旧訳を付けてよいとは判断できない。

同じ意味参照でも、原文の言語は別途`SourceLocale`で宣言する。漢字があるから日本語と推測したり、画面利用者の言語が原文の言語だと推測したりしない。

## O1での制限

- オーバーレイは`display-name`のみ。通常プラグインの機能ID、入力・出力、業務規則、権限、DB構造、実行機能の上書きは拒否する。
- 原文と同じ言語の別表現への上書きもO1では拒否する。原文の更新と、翻訳用資源の変更を混同しないため。
- 確認済みではない翻訳、原文の旧版に基づく翻訳を表示しない。重要文言での代替言語は既存E1が禁止する。
- 原文の言語以外を求める場合は、翻訳資源が必要。暗黙の親言語への代替はせず、必要に応じて明示した代替言語のみ評価する。
- 合成した表示文字列をそのままHTMLとして信頼しない。表示時のエスケープや、MessageFormat 2での引数処理は別の責務。
- 現行の`Surface.Critical`は**信頼できる環境側の規則を受け取るだけ**で、その規則が人間に確認済みかは検証しない。任意の外部多言語プラグインから`Surface`を採用してはならない。

## 検証

Goの参照実装は`overlay.go`にあり、通常プラグインが多言語定義を持たない合成の成功、原文改訂、版不一致、適用許可の欠落、重複候補、明示的な上書き、重要文言の保護、参照できない意味対象、入力順に依存しない結果を検査する。

```sh
go test -count=1 ./reference/multilingual-overlays
go test -race -count=3 ./reference/multilingual-overlays
go vet ./reference/multilingual-overlays
gofmt -l reference/multilingual-overlays/*.go
```

この試験は`plugin.ResolvedSet`を合成したテスト入力で与えており、実際の`Lock`生成や環境受理を実施したわけではない。正式な配布では既存のロックと照合した後に合成し、対象言語に必要な資源だけをビルドへ渡す方式をO2／O3で検証する。

## 後続に必要な検証

**O2**：実際のプラグイン・Editor・通常の業務画面が表示面を宣言できるようにする。意味参照のないUI部品、既存の自由形式の帳票などには安定した資源IDを与える。

**O3**：既存Plugin Lockと資源版を固定し、対象ごとの言語資源をビルド時に絞り込む。Web・Desktop・CLIの表示、キャッシュ・差替え・失効、実行先別のメッセージ書式、権限と受理の接続を検証する。

**多言語の業務データ**：商品名・商品説明などを実際に多言語保存することは、表示資源を上書きすることとは異なる。対象となる意味上の属性に多言語性を宣言し、既存のデータベース契約と業務レコードの版・受理を通じて扱う（#1453）。表示オーバーレイが暗黙にDBを変更することはない。

## O2a：Plugin Lockを使用した標準UI表示

`locked_display.go`は既存の`plugin.Catalog.ResolveEnvironmentWithLock`と`EnvironmentLockFingerprint`を使い、固定されたPluginの版・定義を検証してから表示資源を合成する。`order_case.go`と`cmd/render-manifest`は、通常プラグインと独立した多言語プラグインの合成事例をJSONで出力する。

`web/order-form.mjs`は[既存React Starter](../ui-customization/web-react/starter.mjs)のファイルを変更せずに利用する。JSONの環境・Pluginの版・意味参照・言語・原文照合値を確認し、画面のタイトルだけを差し替える。フォームの入力名とActionは変更しない。

`web/order-form.test.mjs`は、Go CLIの実際の出力をNodeで読み、React APIのスタブに渡して日本語と英語の要素構造を検証する。実ブラウザやReactDOMの描画試験ではない。

```sh
go test -race -count=3 ./reference/multilingual-overlays/...
go run ./reference/multilingual-overlays/cmd/render-manifest en-US
node --test reference/multilingual-overlays/web/order-form.test.mjs
```

**現時点の境界**：Pluginの定義とモデルは試験用の合成入力であり、受理済みのEditor定義は取得していない。表示用JSONのロック指紋は来歴情報であって、ブラウザが独力で発行元を認証できる証拠ではない。実製品では既存の受理・権限確認を通じて宣言を取得し、信頼できる配布経路から渡す必要がある。

O2bでは、受理済みの表示面と適用許可をEditor／Runtimeへ接続する。O3では対象言語別の配布、WebView、アクセシビリティ、MF2を検証する。今回のUI連結は**タイトルの表示のみ**であり、画面全体の翻訳を実証したものではない。
