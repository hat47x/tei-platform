## 1. CSW-01（CSW #593）— **決定：残す**

### 問い
型付き受け渡しカード（帰属4値・ハッシュ・順序）を、CSWの公開Skillに**任意の道具として残す**か。

### 決定と理由
**残します。** 任意の道具として、Skill本文を変えずに補足1節だけを置きます。

理由は次の3点です。

1. **型付き境界は、保持すべきものを保持できた。** 帰属4値（`source_material` / `generated_proposal` / `contact_reading` / `author_stated`）が`SKILL.md`「生成過程の由来を保持する」の4区分と1対1で対応することを、anchor試験（`csw/anchor_test.go`）で上流原文と照合済みです。
2. **対価が小さい。** 製品側のコード・Schema・CI・テストは0行のまま。追加は`skills/writing-flow/references/handoff-card.md`への補足1節だけです。
3. **必須条件を満たせる。** 記録は任意、全候補へのラベルは不要、Skill本文の手順は不変——いずれも現行方針と衝突しません。

### 残す場合の対価（これだけ）
- `skills/writing-flow/references/`に、任意の受け渡しカードの雛形として、型の名前と4つの帰与値の対応を1節追加する。既存の受け渡しカードの雛形を**置き換えず**、補足として置く。
- 帰属4値と`SKILL.md`の4区分の対応を1行ずつ書く。

### 残さない場合に起きないこと
- 型の追加、Schema、CI、テスト、配布基盤。CSWの製品側は0行のまま。

### 必須条件（採用の前提。順守すること）
- 「全候補へのラベルや一覧表は要らない」という現行方針を変えない。記録は**任意**で、著者が使うときだけ行う。
- 「仮説」「問い」「比較」を値にしない。
- Skill本文の手順は変えない。

### 判断材料
- **リスク2件**：帰属ラベルが分類表に育つ、ハッシュは本文と照合されない（研究文書§4.5）。
- **probeの成果**：`csw/anchor_test.go` が4区分の一文を逐語で結び、変更があれば検出する。`csw/handoff.go` が厳格な読み取りと参照整合性を実装している。
- **TEIの限界**：現行DSLでは範囲・時間窓を書けない。帰属ラベルは書けるが、「作者の判断」と「接触から生まれた読み」の境界は人間のreviewに残る。

### 実装状況（2026-11-11）

補足1節の**文案は作成済み**で、CSWの作業ツリーにある
`skills/writing-flow/references/handoff-card.md` の末尾に追加してあります（§付録A）。

ただし、**このファイルはCSWのgitで未追跡**です。`skills/writing-flow/references/`
ディレクトリ全体が追跡されておらず、GitHubの`73efa57ef66ae4d53db3ff9bb63c927f624f44a8`
および現在の`main`にも存在しません（`gh api .../contents/...` が404）。
したがって研究文書§9 CSW-01が載せていたGitHubリンクは**リンク切れ**でした。

**未 commit の理由**：未追跡のファイルをcommitすると、著者がまだ公開していない
内容を公開することになります。公開するかどうかは著者の判断に委ねます。

**後続で必要なこと**：著者が `skills/writing-flow/references/` を公開する
タイミングで、§付録Aの文案を置く（または、すでに作業ツリーへ置いてある節を
そのままcommitする）。

### 付録A：補足1節の文案（そのまま置ける形）

```markdown
## 由来の区分を使う場合（任意）

受け渡しカードの各欄に、その内容がどこから来たかを1語だけ添えられます。使うか
どうか、どの欄に添えるかは、渡す側と受け取る側が決めます。全部の欄に添える必要は
ありません。

添える語は、[生成過程の由来を保持する](../../cultural-substrate-weaving/SKILL.md)で
区別している4つに対応します。

- `source_material` — 原稿や資料にすでにあること。
- `generated_proposal` — 体系から生まれた問い・仮説・構成案。
- `contact_reading` — 原稿と体系の接触から新しく生まれた読み。
- `author_stated` — 著者が明示した方針や判断と、生成AIが新しく提示した案。

使うときの注意：

- 区分は由来だけを運びます。何が書いてあるかは欄の本文が持ち、語に内容を含めません。
- 「仮説」「問い」「比較」は値にしません。これらは `generated_proposal` の内容として、欄の本文に書きます。
- 全候補へのラベルや一覧表は要りません。必要な欄にだけ添えます。
- この語は、受け取る側が保存先・権限・記録の形式を決めるときの助けです。共通の記録基盤や必須の書式にはしないでください。
```

## 2. BEAR-01（VSクマ #95, #17）— **決定：保留**

### 問い
契約の写し（TEI 104行）をVSクマに**受け入れる**か。推奨は**保留**。

### 決定と理由
**保留とします。** 受け入れの条件が満たされるまで、VSクマ側の製品コードは変更しません。

理由は次の3点です。

1. **TEIが保持できるのは形状のみ。** `heading_bias_rad`・`persistence_bias` 等の連続値は `clamp` の形で写せますが、範囲・有限性・時間窓は現行DSLの外です（研究文書§5.5）。
2. **二重管理のコストが増える。** 受け入れるとGDScript・TEI・probeの3箇所で同一の列挙・境界値・wire形式を管理することになります。上流が変わったときにprobeは自動追随しません。
3. **状態機械も列挙に留まる。** §5.6とSM-01のreviewで、優先度・global遷移・付随変数の保持が書けないことを確認済みです。受け入れの追加の根拠は出ていません。

### 受け入れる場合に必要な手順（これが対価。保留の間に決めること）
1. 列挙の一致試験に加えて、**境界値・wire形式・fixtureの同期**を確認する手順を決める。
2. 同期手順を、`docs/BEAR_TYPED_COGNITION_BOUNDARY.md`の検証節に1行追加する（専用runnerは作らない）。
3. 上流が変わったときにprobeが追随しないことを、受け入れ側の記録に明記する。

### 受入条件（adoption の判定基準）
1. 上記3点の手順が決まり、実施された証拠があること。
2. 二重管理のコスト（GDScript・TEI・probeの3箇所）が、可読性・review理解の利益を上回らないこと。
3. 判断が`deterministic-baseline`の既定とM5の採否基準を変更しないこと。

### 非目標
GDScript生成、ゲームループへの依存、既定providerの変更。

### 判断材料
- **意味の保持**：形状のみ（§5.5）。
- **実装負荷**：増える（§5.5）。
- **変更容易性**：悪化する（§5.5）。
- **状態機械**：現行DSLでは列挙に留まる（§5.6、SM-01）。
