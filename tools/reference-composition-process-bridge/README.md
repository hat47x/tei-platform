# 合成基盤と既存のプロセスプラグインの接続

[Issue #1251](https://github.com/hat47x/tei-platform/issues/1251)の実証用試験です。製品の新しいプラグイン契約や本番用ホストを定義するものではありません。

## 目的と実行

リポジトリのルートで次を実行します。

```sh
go test -count=1 ./tools/reference-composition-process-bridge
```

試験は、既存の[処理実行プラグイン](../reference-process-plugin/main.go)と、[内部パッケージに依存しない参照プラグイン](../../plugins/reference-process-executor/README.md)をそれぞれ`go build`で一時ディレクトリに構築し、同一のホスト側試験を実際の子プロセスに対して実行します。`internal/composition`のサービス選択・世代保持・権限ガードを通した後で、既存の`internal/plugin/runtime`が提供する実行アダプターを呼び出します。

確認する事項は次のとおりです。

- 合成基盤が選択したサービス契約と、構築した実行ファイルのSHA-256による識別を関連付けられる。
- 実際の子プロセスが既存の呼出し方式で実行結果を返す。実行結果に付属するプラグインの来歴を照合する。
- 提供者の宣言変更時には古い選択による新規呼出しを拒否する。
- 世代を入れ替えても処理中の旧世代を保持し、解放後に一度だけ後始末する。
- ホストが権限を拒否したとき、外部プロセスを呼び出さない。
- 実行ファイルの内容が宣言された指紋と異なるとき、呼出しを拒否する。
- 提供者を撤去した後に、新たな実行が行われない。

## 契約の形と利用範囲に対するホストの承認

[契約変更時の拒否試験](contract_shape_gate_test.go)では、独立して構築したプロセスプラグインを実際に起動し、サービス契約の識別子と版を変えずに要求・応答の形だけを変更します。合成基盤では提供者の宣言として選択できても、利用者側が承認した契約の形とは異なるため、ホストでの事前照合によって子プロセスの起動を拒否します。別の利用範囲にある提供者を同じ権限で呼び出すことも拒否します。

古い選択が失効することと、新たに選択できる契約が利用者に承認済みであることを区別します。利用者が承認した形に戻れば、ホストの現在の権限と実行ファイルの照合を経て、新世代として呼び出せることまで確認します。

**この照合は試験内のホスト側参考処理です。** 契約定義の発行権限、互換性の証拠、署名の検証、正式な公開APIを実装したわけではありません。製品の契約管理機構は[#951](https://github.com/hat47x/tei-platform/issues/951)および[ADR-0032](../../plan/adr/0032-composition-kernel-replacement.md)と整合させ、第二の契約解決機構を増やさない方針です。

## ホストが受理した経路との照合

参考ホストは、合成基盤で取得した現在の世代束縛と、ホストがすでに受理した呼出し用の束縛（契約ID・契約版・提供者ID・成果物指紋・世代）を**全項目で照合**してからプラグインを実行します。成果物の指紋が同じでも、違う契約や提供者へ暗黙に振り替えません。負例試験では、実行ファイルが同一のまま契約・提供者・世代のいずれかが違う場合、子プロセスの起動回数が増えないことを確認します。

この照合用の期待値は、**信頼するホストが受理済みの選択と実行計画から与えるもの**です。要求者やプラグインが自分で提出した期待値を比較しても権限確認にはなりません。参考ホスト自体が契約の正本、署名検証、権限発行、実行隔離を実装したという意味ではなく、正式なホスト入口への移行時に同等の条件を保護するための検査です。

## 限界と移行判断

この試験では、既存の実行アダプターを**そのまま利用**し、既存プラグインと独立参照プラグインの両方を試します。新しい合成基盤と旧プラグイン管理機構を一時的なホスト側試験コードでつないでいるのであり、二つの正本を製品に追加するわけではありません。

この参考実装の検証者はローカルの実行ファイルを読み取ってSHA-256を照合します。署名、来歴の証明、実際の隔離、権限の耐改ざん性は提供しません。子プロセス起動時にもOSの隔離は行いません。

また、実際のプラグインは一回の呼出しごとに子プロセスとして起動されます。世代切替の試験は**論理的な呼出し経路とリソース管理**を確認するもので、異なるバイナリの無停止入替や、処理中のプロセスを跨ぐ更新を証明しません。

処理実行プラグインの応答`accepted`は業務上の処理要求の受領を示すだけで、データベース変更の完了証拠ではありません。

従来のプラグイン実装はGoの`internal/`以下に依存します。一方、新しい参照プラグインは標準ライブラリのみで独立構築できます。ただし、この試験だけで製品の正式なプラグイン契約やすべての既存プラグインの独立性が証明されるわけではありません。次の段階では、言語と実行方式に依存しない呼出し契約とホストの実行権限を分離し、旧実装の段階的な置き換えを検討します。

関連する設計判断は[ADR-0032](../../plan/adr/0032-composition-kernel-replacement.md)と[ADR-0033](../../plan/adr/0033-core-and-plugin-subprojects.md)を参照してください。

## 保護されたWeb入口から実プロセスを呼ぶ追加試験

[Issue #1145](https://github.com/hat47x/tei-platform/issues/1145)の横断検証として、`web_bridge_test.go`を追加しました。既存の[Web保護入口](../../reference/web-composition/go-host/host.go)を経由して、**合成基盤が選択した実装**を既存プロセス実行アダプターへ渡します。プラグイン実行器や認証・認可の共通契約を複製しません。

追加試験は、同じGoパッケージの既存補助関数を再利用し、次の経路を確認します。

```text
合成HTTP要求
 → Web Hostの経路・本人確認・要求元確認・操作認可
 → Hostだけが設定できる検証済み主体
 → Composition CoordinatorのProvider選択・現在権限
 → 実ファイルのSHA-256照合
 → 既存プロセス実行器と子プロセス
 → accepted（永続的な完了は未確認）／監査
```

正常例だけでなく、本人確認・要求元確認・操作認可の拒否、認可先の障害、Host権限の失効、Provider宣言の撤去を試します。これらの拒否では**子プロセスが起動しないこと**を確認します。ブラウザ側が偽の利用者・Providerヘッダーを送っても、実行側が使用する主体はHostから渡されたものだけです。拒否・障害・受領を監査記録でも区別します。

**実証範囲の制約：** この試験のセッション・CSRF・操作認可は、Host側の真偽値による**合成検証器**であり、実際のIDプロバイダー、Cookie、ブラウザ、既存業務の`security.authorize`の一貫した実行を証明しません。また、子プロセスは配備指示を`accepted`として返すだけで、データベース更新を行いません。業務操作の成功や永続的な副作用の確定、プロセス隔離、署名の検証を主張しないため、応答でも`durability=unconfirmed`と記録します。

この追加試験は既存の`go test -count=1 ./tools/reference-composition-process-bridge`から実行できます。実行結果はGitHub Actionsまたは実チェックアウトによる記録を別途確認し、コード追加だけでPASSと判定しません。次の段階では、合成されたOperationではなく、実際のApplication Actionと既存`security.authorize`を同じ契約のまま横断させます。

## 正規の業務認可から独立プロセスの受領まで

[Issue #1145](https://github.com/hat47x/tei-platform/issues/1145)の横断試験として、`canonical_process_test.go`を追加しました。既存の参照Workspaceの`order_entry.submit_order`について、`driver.Resolver`と既存の`security.authorize`を**実際に呼び**、許可された要求だけを、新合成基盤が選択した独立した子プロセスへ渡します。

```text
合成された企業／既存認証セッション
 → 保護されたWeb Hostの本人確認・要求元検査
 → 既存Canonical Bindingとsecurity.authorizeによる操作認可
 → 要求内だけで有効な操作認可の引渡し
 → 合成基盤での提供者選択・現在のHost実行権限
 → 実行ファイルのSHA-256照合と既存プロセス通信
 → 外部プロセスによる受領応答（業務処理は未実行）
```

企業認証と従来認証の二つの合成主体が、既存の規則で同じ利用者に結び付けられる場合の受領を確認します。閲覧者の拒否、主体対応付けの撤去・障害、要求元検査の拒否、セッションの失効、Host権限失効、成果物検証器の欠落、提供者の撤去では、子プロセスが起動しません。HTTP本文・ヘッダーに偽造した主体・権限・提供者・秘密文字列を入れても、プロセス要求のJSONには転送されないことを確認します。

```sh
go test -count=1 -run '^TestCanonicalAuthorizationGatesRealSelectedProcessReceipt$' ./tools/reference-composition-process-bridge
```

**重要な境界**：今回使う独立プラグインは既存の*配備処理の受領器*であり、受注を登録するプラグインではありません。プロセスとの接続は、既存の`DeploymentExecutor`が理解する合成された受領要求を用いているため、`order_entry.submit_order`という業務Actionの**実行契約と一致した物理プロセス実装になったと判定してはいけません**。HTTP 202は受領試験の成功であり、業務操作が完了した証拠ではありません。業務効果もDB変更も行いません。これは、認証・認可・提供者選択・プロセス境界の縦断的な接続と非漏洩を試す限定的な結合試験です。

実際の別プロセスに業務Actionを委譲するには、業務Actionの意味契約・要求／結果形式と、物理的なプロセス呼出し形式を独立させる必要があります。旧式の配備機能分類を汎用業務Actionへ流用することや、HTTPで承認した利用者を外部プロセスにそのまま自称させることは認めません。実IdP、Cookie／CSRF、本番のLease・OS隔離・署名・実行結果の永続確認も対象外です。
