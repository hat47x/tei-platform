# Linuxで実行内容を固定する参照試験（Issue #1370）

この試験は[合成基盤とプロセスプラグインの接続試験](README.md)の補助検証です。製品の実装や正式なプラグイン契約は変更しません。

## 問題と検査方法

従来の成果物検証では、SHA-256を照合してからパスを指定して起動します。この二つの操作の間に、参照先が別のファイルへ置き換わる可能性があります。

Linux向けの`pinned_launch_linux_test.go`では、ホスト専用の一時ディレクトリへ実行ファイルを複製し、複製した内容のSHA-256を検証した後で書込み用ファイル記述子を閉じます。読み取り専用の記述子を開いてファイル名を削除し、子プロセスの起動時にその記述子を渡します。元のファイル名ではなく、保持したファイルを起動する方法です。

独立参照プラグインから内容の異なる実行ファイルを二つ構築して、元ファイルの置換とシンボリックリンクの付け替え後にも、検証済みの内容だけが起動することを確認します。誤ったSHA-256、別パスの指定、保持した記述子の解放後、開始前の中断は拒否します。既存の`DeploymentExecutor`を使い、検証器と起動器の両方に同じ保持済み実行ファイルを与える試験です。

```sh
go test -count=1 -run '^TestLinuxPinnedProcess' ./tools/reference-composition-process-bridge
```

## 保証していないこと

これは**LinuxでネイティブのGo実行ファイルを起動する参考実験**です。署名や来歴の真正性、OSによる隔離、ホスト自身の耐改ざん性を提供しません。ホストと同じ利用者権限で別のプロセスがホストに干渉できる環境での安全性も保証しません。試験用起動器に出力・資源管理等の製品要件が揃っているわけではありません。

通常の製品用プロセス実行器はこの試験で変更していません。Linux以外の実行先へ仕組みを一般化せず、実行先ごとの権限境界と成果物の固定方式を検証する必要があります。正式な契約と実行権限の移行は[ADR-0032](../../plan/adr/0032-composition-kernel-replacement.md)と[Issue #951](https://github.com/hat47x/tei-platform/issues/951)に従い、第二の契約解決機構を作りません。

## 切替中の旧実行ファイルの保持

[世代切替の追加試験](pinned_generation_linux_test.go)では、既存の合成基盤に二世代の参照プラグインを登録し、それぞれの実行内容を独立して固定します。旧世代の処理が参照を保持したまま提供者の宣言を更新し、新世代の準備と確認を終えてから、新しい呼出しを新世代へ切り替えます。

旧世代の参照が残っている間は、その実行ファイルを閉じず、元のファイル名を別の実行ファイルへ置き換えても旧内容を起動できることを確かめます。旧世代の参照を解放した後で後始末を一度だけ実行し、閉じた実行ファイルから新たに起動できないことを確認します。新世代の権限失効と撤去時の拒否、新世代の後始末も対象です。

```sh
go test -count=1 -run '^TestLinuxPinnedGeneration' ./tools/reference-composition-process-bridge
```

この試験の旧世代の処理は、実際に待機している子プロセスではなく、合成基盤の参照保持として模擬します。したがって、**切替時の実行内容の保持と解放を確認する試験**であって、長時間稼働する子プロセスの無停止移行や実業務の処理継続を証明するものではありません。現在の参照起動器をそのまま製品の共通ホストへ採用する判断でもありません。


## Runtimeに追加した選択式のLinux起動器

`internal/plugin/runtime/process_pinned_linux.go`には、`PinLinuxProcess`を追加しました。ホストが事前に許可したプラグインの識別子・実行ファイルのパス・SHA-256を渡すと、実行内容を自分の一時領域に複製して照合し、名前を削除した読み取り専用ファイル記述子を保持します。

戻り値の`PinnedLinuxProcess`は既存の`ArtifactVerifier`と`ProcessLauncher`の両方を実装します。ホストが同じインスタンスを`Registry.Verifier`と`Registry.Processes`に設定すれば、既存の`DeploymentExecutor`が実行前に同じプラグイン識別子・版・成果物指紋を照合し、起動時に保持済みの内容を使います。通常の`StdioProcessLauncher`は引き続き利用できます。どちらを使うかはホストが選びます。

実行内容を固定する段階では、拡張子やファイル名の信用だけで起動せず、複製先の内容をSHA-256で照合します。複製サイズは64 MiB以下とし、開始前の中断、誤った指紋、別のプラグイン識別子、違う実行パス、解放後の呼出しを拒否します。書込み用記述子を閉じてから実行用記述子を開き、呼出しが完了する前には`Close`によって閉じないようにします。入出力の大きさの制限とエラー時の標準エラー出力の扱いには既存の標準入出力処理を共用します。

```sh
go test -count=1 -run '^TestProductPinnedLinuxProcess' ./tools/reference-composition-process-bridge
```

**保証の境界：** これはLinux上の選択式起動器であって、全ホストの既定の起動方式へ適用したものではありません。`ArtifactVerifier`の結果で真になるのは指紋の一致だけで、署名や来歴の真正性は主張しません。必須の隔離実行器がない場合には従来どおり起動を拒否します。Linux以外の実行先、攻撃者と同一権限のホスト保護、長寿命の実行プロセス管理、監査と本番構築・配備への採用は別途検討が必要です。


## 実行器と検証器の結び付けを検査する

ホストが実行内容固定方式を選ぶ場合、検証を担当する部品と起動を担当する部品は**同一の保持済み実行ファイルを持つインスタンス**でなければなりません。両者の片方だけを通常のパス起動方式へ置き換えると、検証した内容とは異なるファイルを実行する危険があります。

Runtimeの`Registry`は、固定した実行内容を使用するときだけ、検証器と起動器が同一のインスタンスであることを、資源使用権限を取得する前に確かめます。誤接続や別世代の固定済みファイルを指定した場合は呼出しを拒否します。隔離用の別起動器へ処理を迂回させた場合も、固定済みの実行内容が渡る保証がないため拒否します。

通常の検証器と起動器には、この限定的な同一インスタンス要件を課しません。ただし、通常のパス起動方式で検証から起動までの内容が固定されることを保証するものでもありません。固定実行方式の利用は引き続きホストが明示的に選択します。
