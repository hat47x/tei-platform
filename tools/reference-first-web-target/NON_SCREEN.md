# 画面を使わない帳票と一括処理

受注の参照ホストに、HTTPを起動せず終了する`-non-screen report`と`-non-screen batch`を追加しています。実PostgreSQL、`-composition-scenarios`、接続ファイル、正の排他トークンが必要です。[既存の起動引数](README.md)に以下を加えます。

```sh
# 帳票。保存先の親ディレクトリはあらかじめ作る。
-non-screen report -from 2026-09-18T00:00:00Z -rows 0,1,2 \
  -report-format csv -artifact-out /secure/output/orders.csv

# 一括確定。資格情報はコマンド引数に直接書かない。
-non-screen batch -from 2026-09-18T00:00:00Z -rows 0,2 \
  -login-id legacy-order-editor -credential-file /secure/editor.private
```

使い捨てDBの[参照データ](../../reference/postgres-order-execution/README.md)は帳票用と一括処理用の実行許可を別々に用意します。実行物の指紋、世代、モデル版、期限、排他トークン、失効を既存の照合処理で確認します。帳票は認証済み利用者用画面ではなく、実行許可を持つ診断ホストの読取例です。認証とOracle顧客参照は引き続き模擬実装です。

帳票は選択した受注の明細を取得し、[整形プラグイン](../../plugins/report-renderer/README.md)へ渡します。CSVからJSONへ変更しても読取処理と契約を共有します。保存先はホストが指定し、モデル作業領域内への保存と既存ファイルの上書きを拒否します。成功時の標準出力は保存先、文書のSHA-256、形式、行数、整形元とサービスの識別を持つ受領記録です。保存直前にも実行許可を確認しますが、DBの失効とファイル保存を原子的には実行しません。複数受注の読取も全体として単一のDBスナップショットではありません。

一括処理は最大100件の対象IDと検証入力を、作用を起こす前に固定します。同じIDの重複を拒否し、各件で既存の認証、業務検証、認可、DB確定、別読取りによる観測を使います。受注版や明細の変化は確定時に再確認します。各件は独立したトランザクションで、全件の一括原子性はありません。

標準エラーへ各件の進行記録、標準出力へ対象集合と処理済みの各件を出します。資格情報は両方に残しません。業務拒否、実行失敗、観測失敗ではそこで停止します。Ctrl+Cによる取消は未開始の後続処理を止めます。確定済みの作用は巻き戻しません。確定結果不明や観測失敗では自動再試行せず、記録とDB状態を照合する必要があります。

`-batch-journal /secure/output/progress.jsonl`を加えると、対象集合、各件の開始、処理結果、終了結果を行単位のJSONへ保存します。対象集合と開始記録は処理前に、結果は処理後に同期保存します。保存先はホストが指定し、モデル作業領域内への保存と既存ファイルの上書きを拒否します。資格情報は保存しません。記録の保存に失敗すると後続処理を停止し、受領結果の`stage`を`journal-failed`にします。確定後の記録失敗では、その確定を巻き戻しません。

記録は参照ホストの進行ログで、DBと同じトランザクションの確定記録ではありません。最後が`starting`で結果がない場合、DB作用の成否は不明です。`ended`の欠落や途中で切れたJSON行を成功とみなさず、保存した対象IDと`batch-observe`の現在状態を照合します。ログから自動再開しません。プロセス強制終了後の同期済み記録の保持を試験しますが、電源断、ストレージ障害、改ざん耐性、本番の監査証跡は未検証です。

同じ対象全体の再実行は、先頭の確定済み受注で拒否されます。残りを再開するには、未処理の対象を明示的に選び直します。これは現在の受注状態による重複遷移の拒否であり、永続的な要求IDによる重複排除や自動再開ではありません。管理操作で状態を戻した場合まで同じ要求を識別する保証はありません。

停止後の受注状態を診断する場合は、処理結果の`planned`にある受注IDを使って次を実行します。行番号の再検索を行わず、指定したIDの現在の状態を一つの読取り専用スナップショットで取得します。

```sh
-non-screen batch-observe -order-ids 1001,1002,1003
```

この操作は最大100件の正のIDを受け付け、重複・不明なIDや許可失効では結果全体を拒否します。受注の更新、未処理行の自動選択、再実行は行いません。`order-batch-observe`の独立したDB実行許可を必要とします。確定処理が許可されていなくても、観測用の許可が有効なら診断できます。帳票と同じく診断ホストの操作で、業務利用者の認証・認可を証明するものではありません。

出力の`observation`は現在の外部状態です。受注が`submitted`でも、どの要求が確定させたかは判断できません。過去の処理結果との一致は、永続的な要求IDによる確定記録や、再開する権限の代わりになりません。読取り後にも現在の実行許可を確認しますが、失効と標準出力への公開は原子的ではありません。

固定した変更のないLinuxチェックアウトで、次の検証を実行できます。自身が作った使い捨てDBを削除し、証拠と帳票はリポジトリ外へ保存します。

```sh
python3 tools/verify-postgres-order-execution.py --non-screen --output /secure/evidence
```

この実行はCSV／JSON出力、帳票許可の取消、一括処理の部分成功、取消、重複確定拒否、明示的な残件処理を検査します。大規模処理、プロセス停止からの永続的な再開、PDF表示、ブラウザー、人による利用価値評価、本番運用の証拠ではありません。

## 受注専用ビルドと固定Worldからの実行

受注専用ビルドでも同じ`-non-screen report`と`-non-screen batch`を指定できます。処理後に終了し、HTTPサーバーを起動しません。選択済みサービスと実PostgreSQLの指定は必須です。修理受付専用ビルドには帳票・一括処理の引数や実装を含めません。

固定Worldの実行物では、`-workspace`に構築器が公開した`api/`ディレクトリを指定します。構築時に固定したWorldから既存の業務処理を解決し、Workspaceや構文解析器は実行物へ取り込みません。帳票の出力先は、この固定Worldのディレクトリの外に置きます。ライブソースの変更・再読込みはできません。

```sh
python3 tools/verify-postgres-order-execution.py --frozen-api --non-screen --output /absolute/new/frozen-non-screen-evidence
```

この指定は、固定WorldのHTTP試験と同じ実行物・使い捨てDBを使い、実プロセスによるCSV／JSONの生成、許可失効、部分成功、重複確定拒否、明示的な残件処理を確かめます。取消は別に実DB回帰試験で調べます。要求IDによる永続的な再開には引き続き対応していません。
