# reference-order-web-delivery-member

技術検証用サンプル[`order-web-delivery`](../../reference/order-web-delivery/README.md)の工程6「会員向けの注文履歴の公開と負荷の分離」を、二つの配備単位(会員向けと社内向けの別プロセス)とPostgreSQLで実行する実装です。設計の正本は[技術検証用サンプルの統合設計 4.4節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#44-未確定の受注の画面での確定から別観測配備単位の分離までorder-web-delivery)です。

この実装はサンプル固有の処理で、`internal/`の基盤には入れていません。利用者の種類ごとの射影、流量制限、表示用キャッシュの鮮度、権限の版と剥奪の伝播は、基盤に宣言の手段がないため、ここで最小限に作りました(後述の「基盤の不足」)。工程1〜5との受け渡し(受理版R1、工程5の成果物)は未接続です。

## 構成

| 配備単位 | 起動 | DBのロール | 担当 |
| --- | --- | --- | --- |
| 会員向け | `serve -unit member` | `owdm_member` | 注文履歴の一覧と1件の照会、配送メモの更新、在庫の表示、同じ内容での再注文 |
| 社内向け | `serve -unit staff` | `owdm_staff` | 受注の確定、受注の追加、会員の権限の剥奪と閲覧範囲の縮小、在庫の調整、社内向けの照会 |

- 二つの配備単位は同じ実行ファイルの別プロセスで、状態を持ちません。セッション(`owdm.session`)、主体と権限(`owdm.principal`、`owdm.principal_scope`)、受注、在庫はPostgreSQLにあります。認証は合成のトークン(`Authorization: Bearer`)で、実際の認証基盤、Cookie、CSRFは扱いません。
- 各配備単位は自分のロールでだけ接続します。会員のロールは接続数の上限(既定16、会員の配備単位を3つまで同時に動かす試験の分)と文の上限時間(2秒)を持ち、受注の列に対する権限は会員の射影から生成した列単位の許可だけです。原価、与信区分、担当者メモの列は、会員のロールでは読めず、状態と金額の列は更新できません。
- 起動時に工程1の読込計画から自分の種類の射影を導き、その照合値が`-expect-projection-digest`と一致しなければ起動しません。起動後は待受けのアドレス、射影の照合値、設定の照合値、DBのロールを`-ready-file`へ書きます。

## 要件ごとの作り

### P-B2C-01 行と項目の認可

- 返す項目は、射影が選んだ列だけを`SELECT`で読みます。全項目の直列化や`SELECT *`はありません。
- 他の会員の注文は404で返します。存在しない注文と本文まで同じにし、注文番号の存在を推測させないためです(403は、その番号の注文が存在することを示してしまいます)。
- 更新は、本文の項目を射影の受け付ける項目と照合してからDBに触れます。許可外の項目を一つでも含めば403で、DBは変わりません。所有していない注文は404、版の食い違いは409、`If-Match`がなければ428です。

### P-B2C-02 流量制限と資源の分離

会員の要求は、次の順で受け付けます。受け付けられない要求は待たせずに429と`Retry-After`(秒、1以上)を返します。

| 段 | 既定値 | 超えたときの`reason` |
| --- | --- | --- |
| 会員ごとのトークンバケット | 毎秒5件、蓄え20件 | `principal-rate` |
| 会員向け全体のトークンバケット | 毎秒50件、蓄え10件 | `tier-rate` |
| DB接続を使う同時実行の枠 | 2件(空きを50ミリ秒まで待つ) | `tier-concurrency` |

資源は、配備単位を別プロセスにし、DBのロールと接続の上限、接続プール(各4)を分けて分離します。会員の配備単位はDBの読取りを再試行しません。

会員向け全体の毎秒50件と同時実行2件は、この機械(WSL2、論理CPU12)で、下流を遅くした会員の照会1件が約20ミリ秒のCPUを使うときに、社内の確定の応答時間を目標内に保つように決めた値です。毎秒100件・同時実行2件では、保護ありの比が3倍を超える回があり(開発中の観測で1.6〜3.3倍)、毎秒50件で1.0〜2.2倍になりました。流量制限の状態はプロセスごとで、会員の配備単位を複数並べると、全体の上限はその台数倍になります。

### P-DB-01 表示用キャッシュの鮮度

- 在庫の表示(`GET /member/items/{code}/stock`)は、配備単位のメモリ上のキャッシュから返します。応答には正本の行を読んだときのDBの時刻(`asOf`)、版、取得元(`cache`/`canonical`)、宣言した上限(`maxStalenessMs`、既定1000)を含めます。
- 宣言する鮮度: キャッシュから返す値は、返す時点から上限以内に正本から読んだ値です。経過時間は、正本を読む前に取った時刻から測ります。格納した時刻から測ると、格納が遅れた古い値が若く見えるためです。
- 在庫の更新は、同じトランザクションで`NOTIFY owdm_stock`(品目と版)を送ります。受け取った版より古い値は格納しません。通知が届かない場合も、上の上限で古い値は消えます。
- 再注文の判断は、正本の在庫の行を`FOR UPDATE`で読んで行い、表示の版は比べて記録するだけです。

### P-OPS-02 権限の剥奪と閲覧範囲の縮小

- 各配備単位は、主体の権限(有効か、版、閲覧できる取引先)を、最大2秒(宣言した上限)保持します。剥奪と縮小は同じトランザクションで`NOTIFY owdm_authz`を送り、受け取った配備単位は保持をやめます。通知が届かない場合も、2秒で読み直します。
- 権限を読むときは、同じ文の中で論理時計(`owdm.clock`、受注の追加と範囲の縮小のたびに同じトランザクションで進める)の値も読みます。受注の行は追加時の論理時計の値(`created_seq`)を持ち、照会は「権限を読んだ時点の論理時計以下の行」だけを返します。保持中の古い権限でも、権限を読んだ後に追加された行は見えません。
- この仕組みのため、まだ見てよい範囲に新しく追加された行も、最大2秒は見えないことがあります。会員自身の再注文の後は、その会員の権限を読み直して、自分の注文が見えるようにしています。

## 失敗注入と負の対照

| フラグ | 種類 | 内容 |
| --- | --- | --- |
| `-member-query-burn N` | 失敗注入 | 会員の照会ごとに、DBで`generate_series`をN行数える。CPUを使う遅い下流(`pg_sleep`は接続を占有するだけでCPUを使わない) |
| `-drop-notify` | 失敗注入 | `NOTIFY`による無効化を捨てる。宣言した上限だけで古さが止まるかを見る |
| `-inject-stock-fill-reorder` | 失敗注入 | 在庫の表示の最初の格納を、正本に新しい版ができてから上限より長く待たせる(キャッシュとDBの更新順の入替え) |
| `-unprotected` | 負の対照 | 流量制限なし。試験では接続プール48、管理者のロール(接続の上限なし)と組み合わせる |
| `-unsafe-ignore-authz-snapshot` | 負の対照 | 論理時計による行の隠蔽をしない |
| `-unsafe-stamp-at-set` | 負の対照 | キャッシュの経過時間を格納した時刻から測り、無効化の版を無視する |

## 実行

単体試験(DB不要):

```sh
go test ./tools/reference-order-web-delivery-member/ -count=1
```

実DBの試験は、`TEI_OWDM_ADMIN_DSN`がなければskipします。skipは合格の証拠になりません。WSL2などGoとDockerがある環境で、リポジトリのルートから次を実行します。

```sh
python3 tools/verify-order-web-delivery-member.py --out /tmp/owdm-receipt
```

スクリプトは、`postgres:16-alpine`のコンテナー(`tei-owdm-<乱数>-pg`)を`track_commit_timestamp=on`で一つ作り、専用のDB`tei_owdm`を作ってから、パッケージの全試験を`go test -json -p 1`で実行します。終了時に、作ったコンテナーだけを削除します。全試験がPASSし、skipが0件で、通しの記録(`chain.json`)がある場合だけ成功です。受領記録(`receipt.json`)には、コミット、作業ツリーが清浄か、Goとサーバーの版、試験ごとの結果、試験が記録した観測値(`observed.jsonl`)、通しの記録の要約を残します。出力先はリポジトリの外に限ります。

試験は、接続先のDB名が`tei_owdm`であることを確かめてから、スキーマ`owdm`と二つのロールを作り直します。配備単位は、試験のバイナリをCLIとして別プロセスで起動します。

CLIを直接使う場合は次のとおりです。DSNは各配備単位のロールのものを渡します。

```sh
CLI="go run ./tools/reference-order-web-delivery-member/cmd/tei-order-web-member"
$CLI projection -unit member -workspace reference/workspace
$CLI serve -unit staff -dsn "$STAFF_DSN" -workspace reference/workspace -ready-file /tmp/staff.json
$CLI serve -unit member -dsn "$MEMBER_DSN" -workspace reference/workspace -ready-file /tmp/member.json \
  -expect-projection-digest sha256:...
```

## 実DBの試験が確かめること

時間の上限は、試験のプロセスの単調時計で測ります。配備単位も同じカーネルの単調時計で経過時間を測るため、宣言と測定が同じ時計になります。DBの時計は壁時計で、WSL2では一つの試験の間に約5秒前後へ跳ぶことを観測したため、上限の測定には使いません。DBの時計と単調時計のずれは`clockDriftMs`として記録します。上限の起点は、剥奪・縮小・在庫の調整の応答を受け取った時刻(確定の後)です。

| 試験 | 要件 | 確かめること |
| --- | --- | --- |
| `TestPostgresPB2C01MemberProjectionAndOwnership` | P-B2C-01 | 会員Aの一覧は自分の20件だけで、項目は会員の射影の中だけ。会員Bの注文の照会は404で、存在しない注文と本文が同じ。番号での絞込みも0件。原価・与信区分・担当者メモの選択、絞込み、並べ替えと`$count`、`$apply`、DBの列名の指定は400。社員の射影との差分はちょうど社内向けの3項目。許可外の項目を含む8種類の更新は403で、自分と他人の注文の行がDBで変わらない。配送メモの更新は`delivery_note`と`version`だけを変える。会員のロールで原価や担当者メモを読む文、状態や金額を書く文はDBが権限エラー(42501)で拒否する。会員への全応答に社内向けの値の目印が一つもない |
| `TestPostgresPOPS02RevocationAcrossUnits` | P-OPS-02 | 社内向けで会員を剥奪し、会員向けの二つの配備単位(通知あり、通知を捨てる)から250ミリ秒ごとに照会する。上限の2秒を過ぎて始めた照会はすべて401。通知を捨てる配備単位が剥奪の後も保持した権限で応答したこと(注入が効いたこと)を確かめる。閲覧範囲の縮小と受注の追加を両方の順で行い、追加した受注はどちらの配備単位からも一度も見えず、外した取引先の行は上限の後に見えない。負の対照(論理時計の隠蔽なし)では、追加した受注が見える |
| `TestPostgresPDB01StockCacheReorderedUpdate` | P-DB-01 | 格納を遅らせた在庫の表示を、通知を捨てる場合、通知がある場合、負の対照(格納時刻で測る)の三つで繰り返す。各応答の版が、要求の開始より上限だけ前に確定していた版以上であることを確かめる。前の二つは違反0件で、負の対照は違反がある。20人の会員が、在庫10の品目を同じ表示の版で同時に再注文し、成功10件、在庫不足の409が10件、在庫0、作られた受注10件で、過剰な引当は0件 |
| `TestPostgresPB2C02SurgeIsolation` | P-B2C-02 | 負荷なし、保護ありの急増、保護なしの急増の三つを、200件の確定ずつ5回交互に繰り返す。社内の確定の応答時間の、回ごとのp99の中央値で比べる。保護ありは負荷なしの3倍以内(分母は5ミリ秒以上)。保護なしは負荷なしの3倍を超え、保護ありの2倍以上。会員側は200と429(`Retry-After`付き)だけで、受け付けた件数は全体の上限以内。会員のロールの接続数はロールの上限以内で、実行中は同時実行の枠+1以内 |
| `TestPostgresThroughStep6` | 通し | 二つの配備単位を起動し、他方の射影の照合値を指定した配備単位が起動を拒否されることを確かめた後、上の四つを同じ配備単位の上で順に行い、全応答の目印の検査で終える。各段の記録は、読込計画、二つの射影の照合値、二つの配備単位の設定の照合値と、配備単位が報告した射影の照合値を持ち、前の記録の照合値で連鎖する。識別を一つ差し替えると連鎖の検証が失敗する |

### 負荷の試験の閾値の根拠

- 急増: 会員の48の作業者が48の取引先で照会を続けます。半数は`Retry-After`に従い(ばらつきを加え、再試行は1回まで)、半数は従わず20ミリ秒後に送り直します。開発中の観測で、試行は毎秒約900〜1,100件、受け付けたのは毎秒約50件でした。社内側は2つの作業者で確定を送ります。
- 比較を相対にしたのは、絶対値がこの機械の状態に左右されるためです。負荷なしのp99は、開発中の実行の間で11〜49ミリ秒の幅がありました。
- 3倍は、負荷なしのp99そのものが実行の間で約3倍揺れたことから決めました。これより狭くすると、分離の効果ではなく機械の揺れを測ることになります。
- 保護なしが同じ測り方で3倍を超えること(開発中の観測で8〜24倍)と、保護ありの2倍以上であること(同3.6〜17倍)を合わせて求め、測り方が干渉を見分けられることを示します。
- 回ごとのp99の中央値を使うのは、負荷なしを含むどの状態でも、機械全体が一時的に止まる200ミリ秒程度の外れ値が出たためです。1回分の外れ値で判定が変わらないようにしました。全件を合わせたp99も記録します。
- 停止した会員の配備単位のDBの照会は、プロセスを止めた後も終わるまで動き続けます。各回の後に、他の照会が動いていないことを`pg_stat_activity`で確かめてから次の回へ進みます。

## 基盤の不足

このサンプルで、基盤にないためサンプル側で作ったものです。4.4節の「基盤への改善圧力と現状」に対応します。

- P-B2C-01: 項目の公開区分と、利用者の種類ごとの返す項目・受け付ける項目を宣言する手段がありません。`catalog.go`の目録、公開区分、射影の照合値、射影から生成する列単位のDB権限はサンプル固有です。正規のデータ定義(`sales.order`)には社内向けの項目がなく、拡張項目は目録にだけあります。
- P-B2C-01: 行スコープを認可の正本から導く手段がありません。閲覧できる取引先は`owdm.principal_scope`に直接持っています。
- P-B2C-02: 利用者の種類ごとの割当量、流量制限、資源の分離を宣言する手段がありません。トークンバケット、同時実行の枠、DBのロールと接続の上限は、コードとスキーマの作成に直接書いています。流量制限の状態を配備単位の間で共有する仕組みもありません。
- P-DB-01: 項目ごとに許容する鮮度を宣言する手段がありません。上限は`-stock-max-age`の値で、応答の`maxStalenessMs`は自己申告です。`tools/reference-derivation-cache`は版の一致だけを扱い、古さの上限を表せません。
- P-OPS-02: 判定に使った権限の時点と、剥奪を伝える経路の契約がありません。権限の版、論理時計、`NOTIFY`、保持の上限はサンプル固有です。上限は各プロセスの単調時計で守っており、別の機械の配備単位の間で上限を測る根拠はありません。
- 配備単位の受入れ: 射影の照合値の一致で起動を判断していますが、工程5の固定した投影やプラグインの固定情報とは接続していません。
- 通しの記録: 段ごとの記録の連鎖(`chain.go`)はサンプル固有で、工程1〜5の記録とは連鎖していません。

## 範囲外
