# reference-ddl-entry（#1803）

一つのデータベースの物理対応から、提供元（Provider）が出力できるDDLを表ごとに取り出す入口です。データベースにも、Workspaceにも書き込みません。

~~~text
go run ./tools/reference-ddl-entry/cmd/tei-ddl-entry -workspace reference/workspace -database sales_core
~~~

## 位置づけ

このツールはSQLの文法を持ちません。物理対応から望ましい物理の形を導き、空の状態との差分にして、提供元のレンダリング（`migration.Render`）へ渡します。SQLの組み立ては提供元の責務のままです（ADR-0015）。

出力は、宣言された物理対応から導いた**新規作成用**のDDLです。既存のデータベースへの移行文ではありません。

## 守っている境界

- 表ごとに提供元へ渡し、出力できた表（`tables`）と、提供元が出力できなかった表（`unresolved`、理由つき）を分けて返します。一つの表の拒否が、他の表を隠しません。
- 提供元が拒否した内容を、このツールで補いません。

## 現在分かっていること

PostgreSQLの提供元は、新規作成する表の**主キー**を、列の追加の後に`ALTER TABLE ... ADD PRIMARY KEY (...)`として出力します。名前は付けず、PostgreSQLが決めます（[設計案](../../plan/design/POSTGRES_CONSTRAINT_RENDERING_DESIGN_2026-10.md)の案C）。`reference/workspace`の`sales_core`は、二つの表とも出力できます。

一意制約と外部キーも、**同じ差分で新規作成する表に限って**出力します。物理対応が名前を持てばその名前を使い、持たなければ名前を付けずPostgreSQLに任せます。順序は、表と列、主キー、一意制約、外部キーです（外部キーは、参照先の表が作られた後に出します）。外部キーの参照先のスキーマが決まっていない場合は、検索パスに任せず、拒否します。

既存の表への一意制約・外部キーの追加と、主キーの変更は、既存データの検査が要るため、提供元が拒否し、`unresolved`に理由つきで出ます。黙って省くことはありません。


## 実データベースでの確認

`TEI_TEST_POSTGRES_DSN`を設定すると、出力した手順（`script`）を実際のPostgreSQLで実行し、観測した構造と宣言の差分が空になるかを確かめる試験が動きます。未設定の場合は skip されます。試験ごとに使い捨てのデータベースを作り、終了時に削除します。

- `reference/workspace`の`sales_core`: 実行後の差分が空。主キーの名前は、PostgreSQLが決めた`order_lines_pkey`、`orders_pkey`として観測された。
- 合成の親子の表（一意制約は名前つきと名前なし、外部キーは名前つき）: 実行後の差分が空。表名の順では子が先になるが、外部キーは最後に作られ、実行できた。
- 実行前の比較が非空であることも確かめ、比較が何も見ていないために空になる事態を避けている。

確認した版は PostgreSQL 16.14（`postgres:16-alpine`）です。他の版・他の提供元、名前の長い制約、既存データを持つ表は未確認です。

## 未実装

- 既存の表への制約の追加と、主キーの変更（設計案のP4・P5。既存データの検査が要る）
- 名前を持たない一意制約・外部キーの名前の決定的な生成
- PostgreSQL以外の提供元
- DDLの書式の差し替え、コメントの付与
- ファイルへの出力
