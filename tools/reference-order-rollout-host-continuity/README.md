# reference-order-rollout-host-continuity

技術検証用サンプル[`order-rollout-host-continuity`](../../reference/order-rollout-host-continuity/README.md)(サンプル6)の工程1〜5を、一つの配備実行の通しの記録としてPostgreSQLで実行する実装です。設計の正本は[技術検証用サンプルの統合設計 4.6節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md)です。

この実装はサンプル固有の処理で、`internal/`の基盤には入れていません。製品コードは、`internal/plugin/runtime`(`Registry.InvokeWithProvenance`、`HostSandboxLauncher`、`StdioProcessLauncher`、`HostProcessEnvironmentProfile`、`ReconcileDurableInvocation`)、`internal/resource`(`SupervisorOwnershipStore`、`Broker`、参照用の資源アダプター)、`internal/deployment/durable`(実行記録)をそのまま呼びます。所有記録・貸与の権限・耐久呼出の記録の永続実装、移行ツールの代役、命令後の観測と実行記録への反映は、基盤にないためサンプル側で最小限に作りました(後述の「基盤の不足」)。

## 構成

| 役 | 実体 | 担当 |
| --- | --- | --- |
| 試験(編成) | `go test`のプロセス | 工程1・5、DBの準備、`order_entry` 3.7.0の書き手、ホストの停止と再開、失敗注入 |
| ホストA | 試験のバイナリを`host -role a`として起動した別プロセス | 工程2。最初の命令を製品の`Registry`で一回呼ぶ。貸与の自動更新と所有の心拍は製品の監督が行う |
| ホストB | 同じく`host -role b`の別プロセス | 工程3・4。ホストAの所有が止まったのを見て引き継ぎ、貸与を新しいトークンで囲い、呼出しを再接続し、最後に貸与を返す |
| 移行ツール | ホストAの子プロセス(試験のバイナリを`atlas`の名前で起動) | `migration.atlas`の代役。実行の登録、ゲートの待機、移行の適用、適用した版の記録 |

DBは一つのコンテナーの中に、シナリオごとに二つ作ります。

- 制御用(`tei_orhc_<シナリオ>_ctl`、スキーマ`orhc`): 所有記録(`supervisor_ownership`、`ownership_seq`、`ownership_event`)、貸与の権限(`resource_lease`、`lease_event`)、耐久呼出の記録(`invocation_handle`、`handle_event`)、呼出しの記録(`call_event`)、稼働中のアプリケーション(`app_instance`)、実行記録(`run_record`)。すべての記録は一つの列番号(`event_seq`)で順序づけ、工程5の「命令の後」の判定にこの論理時計を使います。ホストが停止中にトランザクションを開いたまま行の鍵を持ち続けないように、`idle_in_transaction_session_timeout`を2秒にしています。
- 対象(`tei_orhc_<シナリオ>_sales`): `sales_core`の4.0.0の状態(永続化`sales_core.order`の表`public.orders`。`status`はまだ空を許す)と、移行ツールの実行登録(`tei_atlas.job`、`tei_atlas.revision`)。移行ツールは自分のロール(表の所有者)で、`order_entry` 3.7.0の書き手は別のロール(参照と追加だけ)で接続します。

### 前例の`PgOwnershipStore`を流用しなかった理由

`tools/reference-month-end-close-correction`の`PgOwnershipStore`は、直接importせず、同じインターフェースの実装をこのツールに作りました。理由は三つです。

1. 前例は表を`mecc`スキーマに固定しています。
2. 前例は期限をDBの壁時計(`clock_timestamp()`)で判定します。WSL2では壁時計が数秒単位で跳ぶため、このサンプルでは時刻で引継ぎを決めません。保持者の心拍は版(`heartbeat_seq`)を進めるだけで、引き継ぐ側は「同じ所有者・トークン・心拍の版を、自分の単調時計で期限(3秒)のあいだ見続けたこと」を確かめてから、その三つ組を条件にした比較交換で引き継ぎます。先に心拍が届けば引継ぎは失敗します。心拍・確認・返却の可否は、所有者と排他トークンの比較だけで決まります。
3. 別ツールのパッケージへの依存を作らないためです。

製品の所有ストアの永続実装を`internal/`へ入れることは[#2146](https://github.com/hat47x/tei-platform/issues/2146)の担当で、このサンプルの範囲外です。この実装は、#2146で「期限の判定に壁時計を使わない」案の材料になります。

## 工程の流れ

1. 工程1: 開始記録、プラグインの固定情報、作業領域から環境計画を組み、実行できる唯一の命令`sales_expand/apply`(`sales_core`を4.1.0へ)を取り出します。呼出しと要求の識別は、実行の識別、命令、冪等キーから導きます。移行`20260826_001`の手順(`schema`、`data`、`verify`のPostgreSQL版)を作業領域から読み、マウント元の作業ディレクトリに置きます。
2. 工程2(ホストA): `Registry`が貸与を取得し、所有を取得(トークン1)して貸与を囲い、`HostSandboxLauncher`がネットワーク・ファイルシステム・秘密の注入のアダプターを適用してから実行部を呼びます。実行部は、受け取った要求から耐久呼出の記録を作って保存し、子プロセスの移行ツールを、`HostProcessEnvironmentProfile`の環境と注入した資格情報だけで起動します。移行ツールは実行を登録し(受理の通知)、ゲートが開くまで待ちます。ホストは呼出しの間、計画の`renew-before`(5分)に0.4秒を足した貸与の期限で、0.4秒ごとに貸与を自動更新し、所有の心拍を1秒ごとに送ります。
3. 試験は、受理の通知、貸与の更新、所有の心拍、ホストBの取得の拒否を確かめてから、ホストAを`SIGSTOP`で止めます。
4. 工程3(ホストB): 心拍の版が3秒止まったのを見て引き継ぎ(トークン2)、貸与をトークン2で囲います。
5. 工程4(ホストB): 製品の`ReconcileDurableInvocation`で、実行登録を観測し、動いていれば再接続します(実行登録のトークンを2にする)。
6. 試験はゲートを開き、移行ツールは移行を一つのトランザクションで適用して(スキーマの手順の後に0.6秒保持し、3.7.0の書込みを重ねる)、4.1.0を記録します。
7. ホストAを`SIGCONT`で再開します。ホストAの監督は心拍か貸与の更新で拒否され、呼出しは失敗します。ホストAはさらに、手元の古い写しで所有の心拍・再取得・返却、貸与の更新・返却・囲い、実行登録への再接続、呼出しの再接続を試み、それぞれの結果を記録します。
8. ホストBが貸与と所有を返却します。
9. 工程5: 再接続の結果を実行記録へ受理(観測待ち)または不明として記録し、命令の後に取り直した観測(移行ツールが記録した版、索引の有無、稼働中のアプリケーション)で実行記録を照合します。

## 通しの完了条件

`TestPostgresThroughHostTakeover`は、工程ごとの記録を前の記録の照合値で連鎖させます(`chain.go`)。各記録の識別(実行、開始記録の照合値、計画の照合値、プラグインの固定情報、実行方針、命令、冪等キー、呼出し、要求)は、その工程が実際に受け取ったものから作ります。工程2はホストAの報告、工程3はホストBが読んだ耐久呼出の記録、工程4は再接続の後に保存された耐久呼出の記録、工程5は実行記録に入れた試行から取り、どれか一つでも違えば連鎖の検証が失敗します(工程4の要求の識別を一つ変えると検出することも確かめます)。貸与・所有者・排他トークンは、工程2から4で交代するため、別に引継ぎの検証(`Handover`)で、同じ貸与、前の所有者とトークンの一致、トークンの増加、耐久呼出の記録が新しい所有者とトークンを持つことを確かめます。

## 実行

単体試験(DB不要):

```sh
go test ./tools/reference-order-rollout-host-continuity/ -count=1
```

実DBの試験は、`TEI_ORHC_ADMIN_DSN`がなければskipします。skipは合格の証拠になりません。WSL2などGoとDockerがあるUnix環境で、リポジトリのルートから次を実行します。

```sh
python3 tools/verify-order-rollout-host-continuity.py --out /tmp/orhc-receipt
python3 tools/verify-order-rollout-host-continuity.py --out /tmp/orhc-receipt-race --race
```

スクリプトは、`postgres:16-alpine`のコンテナー(`tei-orhc-<乱数>-pg`)を乱数のパスワードで一つ作り、専用のDB`tei_orhc`を作ってから、パッケージの全試験を`go test -json -p 1`で実行します。終了時に、作ったコンテナーだけを削除します。全試験がPASSし、skipが0件で、通しの記録(`chain.json`)があり、試験の出力と書いたファイルのどれにもパスワードとインスタンスの接続先が現れない場合だけ成功です。受領記録(`receipt.json`)には、コミット、作業ツリーが清浄か、Goとサーバーの版、試験ごとの結果、試験が記録した観測値(`observed.jsonl`)、通しの記録の要約を残します。出力先はリポジトリの外に限ります。

CLIを直接使う場合は次のとおりです。

```sh
CLI="go run ./tools/reference-order-rollout-host-continuity/cmd/tei-order-rollout-host"
$CLI start                       # 工程1の出力(読むだけ)
# ホストは、制御用DBのDSN、秘密の取扱いと値、接続先、マウント元、作業ディレクトリを
# 環境変数(TEI_ORHC_CONTROL_DSN ほか、host.goを参照)で受け取る
$CLI host -role a -owner host-a -bin-dir /abs/bin -out /tmp/a.json -probe-stale
$CLI host -role b -owner host-b -out /tmp/b.json -release-barrier b-release
```

`-bin-dir`には、この実行ファイルを`atlas`の名前で置いたディレクトリを渡します。

## 時間に依存する判定

WSL2では壁時計が数秒単位で跳ぶことがあるため、判定に壁時計を使いません。

- 所有の引継ぎは、引き継ぐ側のプロセスの単調時計と心拍の版、排他トークンで決めます。DBの時計(`clock_timestamp()`)は記録にだけ使います。
- 貸与の更新後の期限は、取得時の時刻に取得からの単調時計の経過と期限の長さを足して求めます。製品の更新の検証は、更新後の期限が前の期限より後であることを求めるため、壁時計の現在時刻から求めると、壁時計が後ろへ跳んだときに更新が拒否され、呼出しが失敗します。
- 実行登録の「不明」は、観測する側の単調時計で1秒のあいだ心拍の版が進まないことで判定します。
- 工程5の「命令の後」は、制御用DBの列番号(論理時計)で比べます。
- 開始記録の照合値は、改行をLFにそろえてから取ります(Windowsの作業ツリーではCRLFになるため)。

## 安定性の記録

- 作業ツリー(`/mnt/c`の上)で全試験を流した1回で、`TestPostgresPlanChangedRejectedBeforeObservation`が失敗しました。失敗の文言は出力の絞込みで失われ、原因は確定していません。診断の記録では、移行ツールの心拍が1回で止まっており、ホストAの呼出しが停止の前に取り消されたと見られます。候補は、貸与の更新後の期限を壁時計から求めていたため、壁時計の後退で製品の更新の検証が拒否したことです。期限を単調時計から求めるように直し、失敗時にホストの報告も記録に残すようにしました。同じ試験を単独で流した1回は合格しました。
- 修正後の版(`3612136`)で、浅いcloneした清浄な複製から検証スクリプトを5回実行し、5回とも合格しました(各回 PASS 10、FAIL 0、SKIP 0、試験時間31〜36秒、出力への漏れ0件)。`--race`での1回も合格し、データ競合の報告は0件でした(試験時間62秒)。
- 5回の観測値: 引継ぎまでの待ち4.0〜4.2秒(所有の期限3秒)、ホストBの拒否された取得32〜37回、引継ぎ後のホストAの拒否された操作8件・受け付けた操作0件、3.7.0の書込み147〜191件(適用中1件、適用後12〜14件、失敗0件、欠落0件、最大の待ち599〜673ミリ秒)、到達は毎回完了。工程2の注入は、更新・心拍とも285〜379ミリ秒で呼出しが失敗しました。

## 基盤の不足

このサンプルで、基盤にないためサンプル側で作ったもの、確かめて見つかった不足です。4.6節の「基盤への改善圧力と現状」に対応します。

- P-OPS-01: 所有記録、貸与の権限、耐久呼出の記録の永続実装がありません(#2146)。`PgOwnershipStore`、`PgBroker`、`PgHandleStore`はサンプル固有です。
- P-OPS-01: 製品の`ReconcileDurableInvocation`は、呼び出し側のトークンを耐久呼出の記録の中のトークンとだけ比べ、所有ストアを確かめません。新しい所有者の再接続が拒否された場合(計画の更新)は記録のトークンが古いままなので、旧ホストが古いトークンで再接続でき、実行登録の観測と再接続まで進みます。このサンプルでは、耐久呼出の記録を保存する側(`PgHandleStore.Save`)で、記録の所有者とトークンが現在の所有と一致しなければ拒否しています(記憶装置の側でのフェンシング)。それでも観測と再接続は保存より前に起きます。
- P-OPS-01・P-TX-02: 実行環境側のトークンは、再接続が成功したときにしか進みません。状態が不明のとき(製品は「実行側の世代は未確定」と記録します)と、新しい所有者の再接続が拒否されたときは、旧ホストの実行登録への再接続が実行環境の側で拒否されません(`runtime-reattach`の探査が通る)。呼出しの再接続としては拒否されます。
- P-TX-02: 実行環境はホストAの子プロセスです。製品の`StdioProcessLauncher`は一回きりの子プロセスで、ホストAの呼出しが取り消されると子プロセスも止めます。ホストAが移行の途中で再開すると、ホストBが再接続した実行を旧ホストが止めてしまいます。試験は、移行が終わってからホストAを再開する順序にしています。ホストより長く生きる実行環境(コンテナーなど)への再接続は成立していません。
- 固有: `migration.atlas`の実行ファイルがありません。代役はこのツールの中にあり、固定情報の成果物の照合値と一致しません。成果物の検証器は照合しない参照実装です(検証器の識別に明記)。
- 固有: 隔離のアダプター(ネットワークの許可、マウント、秘密の注入)は、記録と環境変数の受け渡しだけで、OSの隔離をしません。
- P-TX-02: 再接続の結果を実行記録へ結ぶ配線がありません。サンプル側の`AttemptFromRecovery`で、再接続済み・成功済みを受理(観測待ち)、不明・喪失を不明として`durable.RecordExecutorResult`へ渡しました。実行記録には「不明のまま未解決」という独自の状態はなく、命令の最後の試行が不明で観測待ちに残ることで表しています。
- 固有: 命令後の観測の置き場と、観測の出所・順序の比較がありません。サンプル側の`Observe`は移行ツールが記録した版と索引の有無から版を決め、契約は版の定義から補っています。到達の判定に稼働中のアプリケーション(3.7.0だけ)も含めるため、条件を満たさない観測は実行記録へ渡しません。
- 固有: 秘密と具体の参照先の通しの検査は、このサンプルの試験の中にだけあります。
- P-MIG-03: 拡張の命令の間に旧版の書込みが続くことを、命令の完了条件として宣言する手段がありません。試験の書き手が確かめています。

## 範囲外

- 製品の所有ストア・耐久呼出の記録の永続実装を`internal/`へ入れること(#2146)。
- 後続の命令(`order_app/start`以降の起動、通信量の切替、旧版の停止、縮約)。工程5は後続の命令が実行可能になることまでを確かめます。
- 別の機械のホスト、実際のネットワークでの時計のずれ、実際の秘密の管理基盤、OSの隔離。
- 先行サンプル`order-workflow`との連結(設計文書の8章)。
