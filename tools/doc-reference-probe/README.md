# 文書中のパス参照検査の試作

Issue #2309 の検討用です。任意実行であり、CIや統合条件には使いません。既存の `repository-plan-check` が扱うMarkdownリンクではなく、バッククォートで囲んだリポジトリルート相対パスを試します。Python 3.10以降を使います。

```bash
python3 tools/doc-reference-probe/probe.py docs/README.md
python3 -m unittest discover -s tools/doc-reference-probe -p 'test_*.py'
python3 tools/doc-reference-probe/evaluate.py
python3 tools/doc-reference-probe/sample.py
```

`repo-path-v4` は `cmd/`、`core/`、`docs/`、`internal/`、`plan/`、`plugins/`、`tools/`、`reference/`、`requirements/`、`product/` のいずれかで始まるASCIIパスと、それらのディレクトリ自体を抽出し、ファイルシステム上の存在を厳密に照合します。それ以外の明示宣言は対応外として報告します。3文字以上のバッククォートまたはチルダによる、行頭から3空白以内のコードフェンスは除外します。引用・リスト内のフェンスやインデントコードなど、Markdown構文全体の解析には対応しません。Linuxでの実行を想定し、大文字小文字の区別はファイルシステムに依存します。出力には規則、照合方式、文書、抽出数と行ごとの結果を含めます。結果は人が確認する必要があります。

- `` `ref:docs/example.md` `` は明示参照です。`plan/`以外では未解決をエラー、`plan/`では警告にします。
- `` `planned:docs/example.md` `` は `plan/` 内のみで将来のパスを宣言します。対象が存在するようになれば警告します。
- `` `docs/example.md` `` は暗黙の候補で、未解決でも警告です。記法外の一般語は調べません。
- バッククォートで閉じた `ref:` / `planned:` の宣言が対象外の接頭辞や文字を含む場合は、見逃さずエラーにします。閉じバッククォートのない不完全な記法は検出できません。

明示参照の一時的な例外だけを、任意の `--allowlist path.json` で指定できます。

```json
{"baseline_count": 1, "entries": [{"document": "docs/example.md", "name": "docs/missing.md", "reason": "移行中", "issue": 2309, "expires": "2027-01-01"}]}
```

各項目は文書と名前の完全一致、理由、正のIssue番号または期限（両方も可）を要します。ワイルドカード、重複項目、重複するJSONキー、項目数の `baseline_count` 超過は拒否します。対象文書内の明示未解決のみ警告に下げ、期限切れ・対象の削除や解決済み項目はエラーです。期限は実行環境のローカル日付で判定します。`--audit-allowlist` を併用すると、例外が登録された全対象文書を読み、期限切れ・不要項目をまとめて検査し、文書の消失・読取不能もエラーにします。指定しない場合は選択文書のみを検査します。

`--baseline-allowlist <基準版JSON>` を併用すると、現在の項目数が基準版の実際の項目数を超える場合、上限が基準版より増えた場合、基準版にない文書・名前の組が追加された場合にエラーにします。同数の項目差替えに加え、理由・Issue・期限などの変更も検出します。基準項目の削除は許可しますが、削除済みの基準項目の再追加は防げません。基準版を自動取得・固定する機構はなく、信頼できる版を利用者が選ぶ必要があります。基準版を指定しない実行では、ファイル内の上限だけを検査します。

さらに `--baseline-sha256 <小文字のSHA-256値>` を指定すると、基準JSONの読み取ったバイト列を照合し、不一致なら失敗します。改行や空白も対象です。出力の `baseline_sha256` は実際に読んだ値、`baseline_digest_verified` は期待値を指定して一致したかを示します。期待値を指定しない場合は後者が `false` です。照合は利用者が信頼する値との一致を確認するもので、基準版の署名・正当性・一度限りの凍結を保証しません。

`evaluate.py` は実際の `docs/README.md` の一箇所を明示・暗黙の参照それぞれで改名し、別に架空パスと一般語を追加します。計画中と未宣言の比較は合成文書で行います。基準main `497b63bf` の同文書で実在を確認したファイル6種類・7出現とディレクトリ6種類・9出現を固定した正解集合として、未解決と判定された数も測ります。出現数が変われば正解集合の再確認を要求します。

2026-11-03、v4をUbuntu 22.04からWindows上のworktreeで単回実行した結果、注入した明示パス欠陥2件中2件を検出、暗黙の改名1件を警告、一般語による追加候補は0件、5回の検査は約506msでした。正解集合16出現の偽陽性は、元の暗黙記法で0件、同じ文書をメモリ上で明示記法に置換した場合も0件でした。時間は欠陥注入の5検査のみで、正解集合の2検査は含みません。元文書の全候補17件のうち `docs/audits/` 1件は意図が未判定のため正解集合から除外しています。計画中宣言ありは情報、宣言のない参照は警告でした。少数のパスに限るため、一般的な検出率・偽陽性率や人手の負担を示すものではありません。

`sample.py` は利用者向け4文書の候補と警告をまとめます。2026-11-03、同じ文書に対するv3の候補数は順に8・0・1・12件、v4では `docs/README.md` 17、`docs/architecture.md` 3、`docs/status.md` 2、`docs/getting-started.md` 21件でした。v4の警告は既知の `docs/audits/` 1件のみ。architectureには `.tei` や `tei.workspace.yaml` など引き続き対象外の記述があるため、候補を抽出できたことは文書に誤りがない証拠になりません。v4の単回所要時間はそれぞれ約202、31、28、248msで、WSLからWindows上のworktreeを読んだ参考値です。

この試作には基準版の自動固定、型・関数・コマンドの解決、すべての対象外記法の検出、十分な欠陥注入による検出率と偽陽性率の評価がありません。対象パスが存在しても記述の意味や実装状態の正しさは証明できません。宣言済み参照に偽陽性が残る、または人手の確認が効果を上回る場合は失敗の対象を縮小するか撤回します。
