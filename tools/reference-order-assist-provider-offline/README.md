# reference-order-assist-provider-offline

技術検証用サンプル[`order-assist-provider`](../../reference/order-assist-provider/README.md)の拡張工程7「営業端末でのオフライン見積と同期」と工程8「値引きの承認と外部与信」を、模擬の営業端末、受注側のサーバ、別プロセスの模擬の外部与信、PostgreSQLで実行する実装です。設計の正本は[技術検証用サンプルの統合設計 4.5節](../../plan/design/TECH_VALIDATION_SAMPLES_2026-10.md#45-受注入力の補助機能の提供元導入交換と営業端末からの見積値引き承認order-assist-provider)で、複合シナリオC5(同3.3節)を通しの試験として行います。

この実装はサンプル固有の処理で、`internal/`の基盤には入れていません。規則の実現の版の照合、操作単位の同期、承認対象の版の固定、外部の提供元への冪等キーと補償は、基盤に宣言の手段がないため、ここで最小限に作りました(後述の「基盤の不足」)。工程8は受注の確定サービスへ接続せず、確定へ渡す入力(`oapo.handoff`)までを作ります。工程1〜6の資産と`plugins/`の実装は変更せず、読み込んで呼ぶだけです。

## 構成

| 構成要素 | 実体 | 状態の置き場所 |
| --- | --- | --- |
| 営業端末(模擬) | 試験のプロセス内の`Terminal`。端末ごとに一つの保存領域 | [`tools/reference-offline-storage`](../reference-offline-storage/README.md)の保存領域(価格マスタ、見積の写し、項目の版、未送信の操作) |
| 受注側のサーバ | 試験のプロセス内のHTTPサーバ(`Server`) | スキーマ`oapo`(ロール`oapo_server`) |
| 外部与信(模擬) | 試験のバイナリをCLI(`credit-provider`)として起動した別プロセス | スキーマ`oapo_credit`(ロール`oapo_credit`)。受注側のロールからは読めない |
| 与信と補償の作業者 | `Saga`。P-TX-03では試験のバイナリをCLI(`saga`)として起動した別プロセス | `oapo.credit_step`、`oapo.handoff` |

見積の規則は二つの世代を持ちます。どちらの世代も、既存の運搬形式(`process-stdio-v1`の`generic-dispatch-v0`)で一回ごとに子プロセスとして起動します。

| 世代 | 規則の版 | 実現 | 場所 |
| --- | --- | --- | --- |
| 1 | `reference.order.quote-rule/v1`(契約`reference.order.quote-lines/v1`) | Goの実行体、同じGoソースのWASIモジュール、JavaScript | 既存の[`plugins/reference-order-quote`](../../plugins/reference-order-quote/README.md)と`plugins/reference-order-quote-js`をそのまま使う |
| 2 | `reference.order.quote-rule/v2`(契約`reference.order.quote-lines/v2`、このサンプルの未受理の候補) | 同上の三つ | [`quotev2/`](quotev2/)。第1世代の要求に、任意の`discountRateBp`(整数0〜3000)を加える。値引きは`floor(小計 × 率 / 10000)`。この項目がない要求には第1世代と同じ小計を返す |

実行先は、端末(JavaScript)、受注側のサーバ(Goの実行体)、夜間の一括の見直し(WASI)の三つです。受注側の再検証は、サーバと一括の見直しの二つの実現が同じ版で同じ結果を返したときだけ判定します。

## 要件ごとの作り

### P-MIX-01 同じ規則を三つの実行先で一致させる

- 配布の状態(`Distribution`)は、実行先ごとに、動かしている実現、世代、成果物の照合値を持ちます。判定(`Judge`)は、目標の世代を報告し、成果物の照合値が登録した実現と一致する実行先だけを起動します。旧版の実行先は起動せず、除外の理由(`rule-version-mismatch`)を判定に残します。世代を偽って報告した実行先は`artifact-digest-mismatch`で除外します。
- 使った実現の結果がバイト単位で一致しなければ、判定しません(`ErrDivergence`)。第2世代の結果は、実現自身が規則の版(`ruleVersion`)を報告し、配布した版と違えば失敗にします。第1世代は版を報告しないため、受け付けた運搬の識別から版を補います。

### P-MIX-02 オフライン端末の同期と競合

- 端末の操作(`Op`)が同期の単位です。操作は、項目の経路(`discountRateBp`、`lines/<SKU>/<項目>`)、端末が最後に見た項目の版、根拠(端末の価格マスタの版、端末の実現の世代と照合値、端末での計算結果)を持ちます。サーバは操作IDで重複を除き、同じ要求の再送には最初の結果を返します。
- サーバは項目ごとの版で楽観的に適用します。端末が見た版より新しい版があり、値が違えば、その項目だけを競合として記録します(`oapo.conflict`)。競合した操作の値は捨てず、サーバの値と並べて保存し、人が選ぶまで見積を`conflict`にします。同じ操作の他の項目は適用します。
- 同期のたびに、サーバは現在の価格表と規則で見積を再検証します。旧単価の明細が残れば`stale-price`にし、承認を開けません。再検証の記録には、旧単価の明細(見積の単価、根拠の版、現在の単価と版)と、端末の計算との比較を残します。単価の付け直し(`Reprice`)は人の操作です。

### P-MIX-03 旧世代の端末と新世代のサーバ

- 項目ごとに導入した世代を持ち、旧世代の端末が知らない項目を区別します。保存を壊さない端末は、知らない項目も生のJSONのまま保存領域に残し、明細を丸ごと書き戻すときにそのまま送ります。
- 知らない項目を落とした書き戻しでも、サーバはその端末の世代が知らない項目を保ちます(`preserved-unknown`)。負の対照(`UnsafeDropUnknownOnPutLine`)では消えます。
- サーバは受け付ける世代の範囲(`oapo.accepted_generation`)と、世代ごとの端末の実現の照合値を持ちます。範囲外は409と、どの世代でも読める固定の形(`code`、端末の世代、受け付ける範囲)で拒否し、端末は未送信の操作を消しません。世代を名乗っても実現の照合値が違えば`unknown-realization`で拒否します。

### P-WF-01 承認対象の版、代理、差戻し

- 案件は開始時の見積の照合値に固定します。承認の操作は、承認者が見た照合値(`IfMatch`)を必ず持ち、現在の照合値と違えば拒否します。再検証で見積の照合値が変われば、同じトランザクションで未完了の案件の承認をすべて無効にし、最初の段へ戻します。
- 照合値(`QuoteDigest`)は、知らない項目を含む文書、判定の結果と規則の版、再検証した価格表の版から作ります。
- 代理は、委任者、代理人、役割、期間(業務日付)で記録します。期間は機械の時計ではなく、サーバの業務日付(`oapo.clock`)で判定します。期間外は拒否し、期間内の承認には「誰の代理として」と使った委任を残します。
- 差戻しの先は規程の段ごとに、差戻しで無効にする承認の範囲は規程全体で宣言します(`target-and-later`または`all`)。拒否した操作も、すべて事象(`decision-refused`)として残します。

### P-WF-02 承認規程の改訂と長期の案件

- 規程は版と照合値で保存し、新しい案件に使う版を一つだけ有効にします。案件は開始時の版と照合値に固定し、改訂後も旧版の段で進みます。判断の記録(`oapo.approval_action`)には、規程の版を必ず残します。
- 移行は対応表([`testdata/policy-migration-v1-v2.json`](testdata/policy-migration-v1-v2.json))で、案件を選んで行います。案件は対応表の段に着地し、対応表が引き継ぐ承認だけを着地より前の段の承認として残します。対応の無い段にいる案件の移行は拒否し、案件は旧版のまま残ります。

### P-TX-02 外部与信の結果不明

- 冪等キーは、案件と、承認した見積の照合値から作ります(`CreditKey`)。呼ぶ前に、キーと`reserve-pending`をDBへ書きます。
- 応答が来なければ`unknown`にし、同じキーで自動で一回だけ送り直します。それでも答えがなければ照会(`GET /reservations/{key}`)で確定します。外部与信は、同じキーの要求には最初の結果を返し、枠を二度消費しません。
- HTTPのクライアントは接続の再利用をしません。標準の転送層が自動で送り直すことがなく、送り直しはすべてこのサンプルの判断です。

### P-TX-03 補償の途中で止まる

- 最後の段(部長)は与信の消費の後でだけ判断でき、却下すると戻し(`release`)が要ります。作業者は、`release-pending`をDBへ書いてから戻しを送り、答えを記録します。
- 作業者のプロセスは、どの時点で止まっても、もう一度動かせば続きから進みます。外部与信は戻しを冪等に扱い、二度目の戻しには最初の結果を返します。
- 収束の判定(`Convergence`)は、受注側の案件、作業者の状態、確定への入力、外部与信の記録を合わせて、`all-complete`(承認、消費、確定への入力あり)、`all-compensated`(却下、戻し済み、取下げの記録)、それ以外の`intermediate`に分けます。

## 失敗注入と負の対照

| 注入の手段 | 種類 | 内容 |
| --- | --- | --- |
| `Distribution`で一つの実行先を第1世代のままにする | 失敗注入 | 配布の途中(P-MIX-01) |
| `JudgeOptions.UnsafeIncludeStale` | 負の対照 | 旧版の実行先も判定に使う |
| 2台の端末をオフラインにしたまま同じ項目を更新し、その間に価格表を改訂する | 失敗注入 | P-MIX-02 |
| `Terminal.NaiveDecode` | 負の対照 | 端末が自分の世代の項目だけを読み、他を落とす |
| `ServerOptions.UnsafeDropUnknownOnPutLine` | 負の対照 | サーバが、書き戻しに無い項目を消す |
| `oapo.accepted_generation`の範囲を狭める | 失敗注入 | 旧世代の端末と、未来の世代を名乗る端末 |
| `oapo_credit.fault`(`drop-after-commit`) | 失敗注入 | 外部与信が消費または戻しを確定した後、応答を返さずに接続を閉じる |
| `CreditClient.UnsafeNoIdempotencyKey` | 負の対照 | 冪等キーなしで送り直す |
| `saga -fault exit-after-reserve-response` | 失敗注入 | 作業者が、消費の応答を受け取った後、記録する前に終了する |
| `saga -fault exit-before-release-send` | 失敗注入 | 作業者が、戻しの意図を記録した後、送る前に終了する |
| `saga -fault exit-after-release-response` | 失敗注入 | 作業者が、戻しの応答を受け取った後、記録する前に終了する |

## 実行

DBもNode.jsも不要な単体試験:

```sh
go test ./tools/reference-order-assist-provider-offline/ -count=1 -run 'TestDocument|TestField|TestQuoteRequest|TestPolicies|TestChain|TestCreditKey'
```

P-MIX-01の試験はGoとNode.jsが要り、実DBの試験はさらに`TEI_OAPO_ADMIN_DSN`が要ります。どちらも、なければskipします。skipは合格の証拠になりません。WSL2などGo、Node.js、Dockerがある環境で、リポジトリのルートから次を実行します。

```sh
python3 tools/verify-order-assist-provider-offline.py --out /tmp/oapo-receipt
```

スクリプトは、`postgres:16-alpine`のコンテナー(`tei-oapo-<乱数>-pg`)を一つ作り、専用のDB`tei_oapo`を作ってから、パッケージの全試験を`go test -json -p 1`で実行します。終了時に、作ったコンテナーだけを削除します。全試験がPASSし、skipが0件で、C5の通しの記録(`chain.json`)がある場合だけ成功です。受領記録(`receipt.json`)には、コミット、作業ツリーが清浄か、Go、Node.js、サーバーの版、試験ごとの結果、試験が記録した観測値(`observed.jsonl`)、通しの記録の要約を残します。出力先はリポジトリの外に限ります。

試験は、接続先のDB名が`tei_oapo`であることを確かめてから、二つのスキーマとロールを作り直します。外部与信と作業者は、試験のバイナリをCLIとして別プロセスで起動します。CLIを直接使う場合は次のとおりです。

```sh
CLI="go run ./tools/reference-order-assist-provider-offline/cmd/tei-order-assist-offline"
$CLI realizations -repo . -out /tmp/oapo-realizations
$CLI credit-provider -dsn "$CREDIT_DSN" -ready-file /tmp/credit.json
$CLI saga -dsn "$SERVER_DSN" -credit-url http://127.0.0.1:PORT -case CASE-1
```

## 試験が確かめること

時間に依存する判定はありません。代理の期間はサーバの業務日付で、事象の順序はDBの論理時計(`oapo.clock.seq`)で判定します。外部与信の注入は接続を閉じるだけで、応答を遅らせません。HTTPのクライアントの上限時間(60秒)は、止まった場合の安全のためだけに置いています。

## 基盤の不足

このサンプルで、基盤にないためサンプル側で作ったものです。4.5節の「基盤への改善圧力と現状」に対応します。

- P-MIX-01、P-MIX-03: 規則の実現の版と世代を実行先ごとに宣言し、照合する手段がありません。`Distribution`、実行先ごとの除外の理由、受け付ける端末の世代の範囲と実現の照合値の登録は、サンプル固有です。第1世代の実現は規則の版を自分で報告せず、版は運搬の識別から補っています。成果物の照合値は起動の直前に読み直しますが、読取りと起動の間の競合は残ります。
- P-MIX-02: 操作単位の同期、項目の版、項目単位の競合、同期時の再検証を宣言する手段がありません。項目の経路と版、競合の記録、再検証の記録は、サンプル固有です。
- P-MIX-03: 項目を導入した世代と、壊さない変更・壊す変更の分類を、形式から機械的に導く手段がありません。項目の世代は`document.go`に直接書いています。
- P-WF-01、P-WF-02: 承認対象の照合値への固定、代理の期間、差戻しの範囲、規程の版の固定と移行の対応表を宣言する手段がありません。規程と対応表の形式はサンプル固有の未受理の候補です。
- P-TX-02、P-TX-03: 外部の提供元への冪等キー、結果不明、照会、補償を、提供元の契約として宣言する手段がありません。キーの作り方、送り直しの回数、照会、作業者の状態は、サンプル固有です。外部与信へ要求を送ることと、その答えを受注側のDBへ記録することは原子的でなく、その間の停止はキーと照会で収束させています。
- 通しの記録: 段ごとの記録の連鎖(`chain.go`)はサンプル固有で、工程1〜6の記録とは連鎖していません。

## 範囲外

- 工程1〜6との接続。工程5の世代交換が渡す「世代つきの見積の実現」は受け取らず、このサンプルが同じソースから構築した成果物を使います。
- 受注の確定サービスへの接続。工程8は確定への入力(`oapo.handoff`)までです。
- 実際の営業端末、その保存領域の暗号化とバックアップ、端末の認証。端末は試験のプロセスの中の模擬で、ネットワークの切断は「同期を呼ばない」ことで表します。
- 実際の外部与信、その契約、別の機械での運用。外部与信の模擬は同じ機械の別プロセスで、同じPostgreSQLの別スキーマを使います。
- 承認者の認証と権限の発行元。主体と役割はサンプルの表にあります。
- 同期の後に与信を消費済みの案件の見積が変わる場合の、戻しと再消費。部長の段の承認は、消費した与信の照合値と案件の照合値が一致するときだけ受け付けますが、照合値が変わった後の戻しは作業者が自動では行いません。
- 承認規程の対応表の内容の妥当性。対応表は試験用に置いた例で、`S2-sales-head`を対応させないこと、`S3-director`を`T2-finance`に着地させることは、業務の判断ではありません。
