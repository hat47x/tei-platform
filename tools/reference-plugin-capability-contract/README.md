# Plugin Capability Contract Reference

ISSUE-000080 / GitHub #951 のReferenceです。

productionの`internal/plugin.CapabilityKind`をすぐに変更せず、PluginがCore固定enumを追加しなくても新しいCapability Contractを宣言・解決できる最小境界をpressureします。

最初のcontractはXead / Xeaf Source Adapterです。これはauthoring toolであり、Application Runtime Capabilityではありません。

Capability Contractはrequest / result / failure / unknownの意味を分けて持ちます。unknownをfailureへ畳まず、逆に未対応や実行失敗をunknownとして曖昧にしません。これらの意味はContract fingerprintへ含めます。

このReferenceで確認する境界は次です。

- contract identity / version / fingerprintとprovider packageを分離する
- providerの自己申告だけではConformance済みとしない
- authoring / build / application-runtime / target-localのAuthority scopeを混ぜない
- 同じcontractに複数providerがある場合、load順で選ばない
- 明示wiringが無い曖昧なprovider選択をfail closedにする
- Conformance Evidenceの更新とcontract / provider resolution identityを分離する
- physical artifactを変えてもlogical contractを別概念へ変えない

これはproduction APIではありません。Referenceが成立した後に、既存`CapabilityKind`を標準contract/profileへどう移すかをADR候補として判断します。
## Capability Resolution Lock

fresh resolutionと、採用済みの解決結果を後から再現する処理を分けます。

fresh resolutionは、compatibleなContractとConformance済みProviderを現在のCatalogから探索します。これに対し、Capability Resolution Lockは採用時に選ばれた組合せをexactに固定します。Catalogへ新しいContract versionやProviderが追加されても、Lock replayでは新しい候補へ自動更新しません。

Reference Lockは次を保持します。

- schemaとcanonicalization規則
- resolution policy
- Authority scope
- root Requirement
- 明示wiringの有無と内容
- exact Contractとcontract fingerprint
- ProviderのPlugin ID / version / implementation ID
- exact artifact digest
- resolution fingerprint
- Lock自身のfingerprint

同じversionのContract内容が変わった場合、Provider artifactが差し替わった場合、root Requirementや明示wiringが変わった場合はreplayを拒否します。

Conformance EvidenceはLockの意味identityへ固定しません。Lock replayはContractとProvider declarationの再現を確認し、current Evidenceの確認は別に行います。Evidenceが更新されてもContract / Provider resolution identityは維持し、Evidence側のfingerprintだけを更新できます。

一方、Conformance EvidenceはProviderのPlugin / version / implementation IDだけでなく、exact artifact digestへも結び付けます。同じlogical implementation IDのartifactだけを差し替え、古いConformance Evidenceを再利用することはできません。

同じPlugin / version / implementation IDを複数のartifact digestで同時に宣言することも拒否します。明示wiringはlogical providerを指定するため、この状態を許すとartifactの選択がCatalog列挙順へ依存するためです。

Capability Resolution LockはRuntime Authorityを与えません。ScopeごとのPermission / Resource / execution boundaryを置き換えず、productionのPlugin Lock形式としてもまだ固定しません。

## 既存CapabilityKindからの移行pressure

generic contractへの移行中に、旧`CapabilityKind`と新しいProvider declarationを二つの正本にしません。Referenceでは、現行`plugin.Definition`をAuthorityとして読み、その中の既存CapabilityからProvider候補を一方向に導出するcompatibility projectionを追加しています。

最初の対象は`contract-query-executor`です。Reference Workspaceにある`tei.database.oracle`の`database.query.oracle`と、`tei.database.postgres`の`database.query.postgres`を`application-runtime.contract-query-executor`へ投影します。

projection自体はConformanceを与えません。既存PluginがCapabilityを宣言していても、generic Contractへの適合には別のConformance Evidenceが必要です。旧定義から対象Capabilityを削除するとprojectionも成立しなくなります。

さらに、callable ProviderをConformance済みとして採用するにはexact implementation artifact digestを必須にします。現在のReference WorkspaceにあるOracle / PostgreSQL Pluginは`runtime builtin`でartifact digestを持たないため、legacy declarationからProvider候補へ投影できても、そのままgeneric resolverの採用対象にはできません。実装artifactのidentityを別の信頼できるbuild / provenance経路で確定することがmigration prerequisiteとして残ります。

OracleとPostgresの両方にConformance Evidenceがあっても、generic resolverはPlugin名やCatalog順で一方を選びません。`contract-query-executor`では既存の`ContractQueryExecutorBinding`がEnvironment / Database instance / Contract Query targetごとにexecutorを選ぶAuthorityなので、generic Contract側に第二のRuntime wiringを作りません。既存Bindingで選択済みのProviderだけをgeneric ContractのConformance検証へ渡します。

compatibility projectionは入力された旧Plugin定義を変更しません。移行bridgeが旧Authorityを正規化やsortの副作用で書き換えないこともtestします。

projectionしたProviderには、投影元のlegacy Capability宣言を正規化した`sourceDeclarationFingerprint`も持たせます。配列の列挙順だけが変わってもfingerprintは変えませんが、Capabilityのpayloadが変われば別identityとして扱います。Resolution fingerprintとConformance Evidenceもこのfingerprintへ結び付くため、旧Capability宣言が変わった後に過去のEvidenceをそのまま流用できません。

artifact digestをまだ持たないlegacy ProviderはCatalogから排除しません。移行状況を発見できる候補として残しつつ、Conformance済みのcallable Providerにはしません。この未確定Providerが別scopeや別contractの正常な解決を止めないことも確認します。

ただし、同じPlugin / version / implementation IDを旧projectionと新しいProvider declarationの双方から同時に出すことは許しません。片方のartifactが未確定でも、logical provider identityが重複した時点で二重Authorityとして拒否します。


## Runtime Plugin Lockとの接続

`application-runtime` scopeのCapability Resolution Lockは、それ自体をRuntime Authorityにはしません。Referenceでは、既存Runtime Plugin Lockの対象Plugin entryへ結ぶ`RuntimeCapabilityBinding`を追加しています。

BindingはEnvironment、Capability Lock fingerprint、Plugin ID / version、Plugin definition fingerprint、artifact digestを保持します。Environment Lock全体のfingerprintは固定しません。対象Providerと無関係なPluginが同じEnvironmentへ追加された場合までCapability bindingをstaleにしないためです。

一方、対象PluginがEnvironment Lockから消えた場合、Plugin definition fingerprintが変わった場合、artifact digestが変わった場合はBindingを拒否します。legacy migration pathでは、generic Providerが現在の`plugin.Definition`から一方向に導出されたことも確認します。これにより、新旧のProvider declarationを独立したAuthorityにはしません。

Runtime Plugin Lock format 3の`buildPlanFingerprint`はCapability identityへ取り込みません。同じruntime artifactに対してBuild provenanceだけが更新された場合、Capability resolution identityは維持します。exact Build Planへの追跡は既存Plugin LockとBuildArtifactLockの責務です。

### target-specific Runtime selection

既存Runtimeがすでにtarget-specificなBindingを持つ場合、Capability Contractのgeneric `Wiring`を同じ選択へ重ねません。Referenceでは、productionの`ResolveContractQueryExecutor`が返す選択結果を先に受け取り、そのPlugin / Capabilityだけをgeneric Contractへ投影してConformanceを確認します。

この経路で作るCapability Resolution Lockは`Wiring`を持ちません。代わりに、Environment、Database instance、Contract Query target、executor Capability、Plugin identity、Capability Lock、Runtime Capability Bindingを`RuntimeCapabilitySelectionBinding`で結びます。target-specificな選択を変更した場合はSelection fingerprintが変わります。

同じEnvironmentでOracle targetとPostgreSQL targetが同じgeneric `application-runtime.contract-query-executor`を使っても、それぞれ既存Bindingに従って別Providerを利用できます。generic ContractはProvider選択のAuthorityではなく、選択済みProviderが共通のcallable contractを満たすかを検証する層として働きます。

generic Capability自体が選択Authorityを持つ別scopeでは、曖昧なProviderを明示`Wiring`なしに選ばない従来の規則を維持します。

保存済みのSelection fingerprintだけでは、現在も同じRuntime Authorityが有効だとは判断しません。legacy migration pathでは、current Runtime Plugin Lock、authoritative `plugin.Definition`、Lockに従ったEnvironment Plugin resolution、current `ContractQueryExecutorBinding`を順に再確認します。Plugin definitionやartifactが変わった場合、Bindingが削除・重複・別executorへ変更された場合はstaleとして拒否します。

この再確認はcurrent Conformance Evidenceの再評価とは分けます。Runtime Authorityを再現できることと、現在のEvidenceでもContract適合を確認できることを同じstatusへまとめません。

`RuntimeCapabilitySelectionBinding`は、この既存選択を後からcurrent authorityへ再照合するためのderived bindingです。Environment、Database instance、Contract Query target、executor Capability、Plugin identity、Capability Lock、Runtime Capability Bindingを結びます。productionの`ResolveContractQueryExecutor`で同じ選択を再現できなくなった場合はstaleとして拒否します。

### 現行Lockで表現できないpackaging

現在のRuntime Plugin LockはPluginごとに`artifactDigest`を一つ持ちます。そのため、一つのPluginが同じTargetで複数のCapability implementation artifactへ分かれる構成は、このLockだけではAuthorityを表現できません。

Referenceでは、Capability Providerのartifact digestとPlugin Lockのartifact digestが異なる場合をfail closedにします。別artifactへ暗黙にfallbackしたり、Plugin-level digestで複数artifactを代表したことにはしません。

この不足は、Web向けlazy loading、Wasm分割、Plugin内部の複数artifact化と関係します。Plugin Lockへprovider artifact一覧を直ちに追加するのではなく、ISSUE-000079のBuildArtifactLockとTarget packagingのEvidenceを合わせて、どのidentityをRuntime Authorityへ固定する必要があるかを判断します。


## Targetごとのrealization

Capability Contractの意味と、Targetごとの実行artifactを分けるpressureを追加しています。

同じPlugin / version / implementation IDでも、DesktopとWeb Browserで別artifactを使えます。Providerはrealization対象のTargetを明示し、Conformance Evidenceも同じTargetとexact artifactへ結び付けます。Target差だけでContract fingerprintは変えません。

resolverへTargetを指定した場合、同じTargetのProviderだけを候補にします。Targetが空のProviderを「全Target対応」とは扱わず、別Targetへのfallbackにも使いません。Target contextを指定しない場合も、Target固有Providerを推測して選びません。

明示wiringはlogical Providerを選びます。TargetごとのartifactはTarget contextで絞り込むため、同じlogical Provider identityをWeb / Desktopへ保ったまま物理realizationを変えられます。同じTarget内で同じlogical Providerを複数artifactへ重複宣言した場合は、従来どおりfail closedにします。

Capability Resolution LockはTargetも固定します。Web向けに採用したLockをDesktop contextでreplayすることはできません。Runtime Capability BindingにもTargetを明示し、どのTarget向けRuntime Authorityへ接続しているかを直接読めるようにします。

このcandidateはTarget selectionの境界を示すものであり、browser-compatible Wasm / JavaScript artifactを実際にbuild・loadしたEvidenceではありません。


## Conformance Evidenceの発行Authority

ProviderがConformance Evidenceを持っていることだけでは、適合性のAuthorityとして不十分です。Provider自身が任意のEvidence fingerprintを作れるなら、自己申告を別形式へ移しただけになるためです。

Referenceでは、Capability Resolution Lockとは別に、次の鎖を検証するcandidateを追加しています。

```text
Capability Contract / Conformance profile
  -> Accepted Conformance Authority Grant
  -> issuer
  -> issuer attestation
  -> current Conformance Evidence
  -> exact Provider / artifact
```

Authority Grantは、exact Contract fingerprint、Conformance profile、issuer、Authority Evidence fingerprintを結び付けます。Conformance Evidenceごとのattestationは、そのEvidenceを誰が発行したかと、どのAuthority Evidenceに基づくかを示します。

Authority Grantが無い自己発行Evidenceは受け付けません。一方、Provider自身をissuerとして明示的に許可することは表現できます。その場合も、自己発行だから暗黙に信頼するのではなく、Accepted Authority Grantが必要です。

このAuthority bindingはCapability Resolution Lockのidentityへ混ぜません。Authority Evidenceが更新されてもContract / Provider resolution identityは変えず、Authority binding fingerprintだけを更新します。

このReferenceが確認するのはaccepted issuance bindingまでです。Authority Evidence自体の真正性、署名検証、組織のpublisher trust、証明書や鍵のrotationはまだ扱いません。fingerprintが存在するだけでcryptographic trust済みとはみなしません。

## Build-backed Provider realization

legacy builtinやcoalesced runtimeでは、Plugin source definitionがCapabilityごとのartifact digestを直接持たない場合があります。その状態を仮のdigestで埋めず、exact BuildPlanと既存BuildArtifactLockからphysical artifactを取得するReference経路を追加しました。

`ProviderBuildRealization`はlogical Provider、exact BuildPlan、BuildArtifactLock内のruntime buildを結びます。保持するのはPlugin / version / implementation identity、Source declaration fingerprint、Target、Build profile、BuildPlan fingerprint、artifact digestです。このbindingはderived artifactであり、Runtime AuthorityやConformanceを与えません。

役割は次のように分けます。

```text
logical Provider declaration
  + BuildArtifactLock
      -> ProviderBuildRealization
      -> exact physical artifact

realized Provider
  + Conformance Evidence
      -> callable Contract適合

Capability Resolution Lock
  + Runtime Plugin Lock / existing runtime selection
      -> Runtime Authority
```

BuildPlan fingerprintはbuild provenanceとしてbindingへ残しますが、Provider resolution identityには入れません。同じartifact bytesを別のAccepted BuildPlanから再構築した場合、Build provenanceは変わってもcallable implementation artifact identityは変えません。

legacy projectionでは、BuildPlanのPlugin definition fingerprintも現在のauthoritative `plugin.Definition`へ照合します。Plugin ID / versionだけが一致する古いBuildPlanを、新しいlegacy Capability宣言へ後付けして使うことはできません。

複数のlogical Plugin / Providerが同じartifact digestを参照するcoalescingも許容します。physical artifactを共有してもProvider identityや選択Authorityは統合しません。複数Providerが同じContractを満たす場合は、従来どおり既存Bindingや明示wiringが必要です。

一つのPluginを同じTargetで複数Capability artifactへ分割する構成も、BuildArtifactLockでは別profileのbuildとしてpressureできます。しかし、現行Runtime Plugin LockはPluginごとにartifact digestを一つしか持たないため、複数artifactを同時にRuntime Authorityへ載せられません。このReferenceはそのGapを解消済みとは扱いません。

Build provenanceだけでもConformanceは成立しません。BuildPlanとBuildArtifactLockからartifactを特定できても、exact Provider / Target / artifactへ結び付いたConformance Evidenceが無ければresolverは採用しません。

## Target Capability Packaging Plan

Capability Contractとphysical artifactの対応をTarget単位で確認するため、`TargetCapabilityPackagingPlan` candidateを追加しました。

このPlanはRuntime Authorityではありません。`authority=derived-packaging-not-runtime-authority`を機械可読に持ち、Capability Resolution LockとProviderBuildRealizationから再生成できるderived artifactとして扱います。

Planはartifact digestごとにProvider参照をまとめます。同じartifactを複数のlogical Providerが共有する場合はcoalescingとして数えます。一つのPluginが複数artifactへ分かれる場合はsplit Pluginとして数えます。同じimplementationが複数のCapability Contractを満たす場合は、Contract参照が増えてもlogical Provider数を増やしません。

少なくとも次の値を機械的に取得できます。

- logical Provider数
- physical artifact数
- 複数Providerを含むartifact数
- 複数artifactへ分割されたPlugin数

入力順はPlan identityへ影響しません。同じlogical Providerを同じTargetで複数artifactへ割り当てる状態、異なるTargetやAuthority scopeの混在、同一Provider / Contract参照の重複は拒否します。

保存済みPlanをcurrentとみなす場合は、現在のCapability Resolution LockとProviderBuildRealizationから再構築してfingerprintを照合します。artifact bytesが同じでもBuildPlanだけが変わればProviderBuildRealizationが変わるため、古いPackaging Planはstaleになります。Capability identityまで変えない点が重要です。

このPlanはphysical配置の比較と将来のRQ-024計測に使う候補です。actual artifact size、network transfer、startup、memory、cache footprintはまだ含みません。また、split packagingを現行Runtime Plugin Lockでauthorizeできるようになったことも意味しません。

## Execution Authorityとproduction Runtimeの接続

Capability Resolution LockはProviderを特定しますが、実行許可ではありません。Referenceでは`CapabilityExecutionProfile`でisolation policyとPermission集合を固定し、別のAuthority Grantから`CapabilityExecutionAuthorityBinding`を作ります。

Application Runtimeのlegacy migrationでは、さらに`ProductionExecutionBridge`で既存production `EnvironmentPlan`へ照合します。generic profileがPermissionを追加するのではなく、production側で選択済みCapabilityのgrantとexactに一致する場合だけbridgeが成立します。

host-trusted profileはin-process / host-trusted runtimeへ、host-enforced-sandbox profileはprocess / external-process / sandbox-required runtimeへだけ接続します。sandbox-preferredを「enforced」と読み替えません。

Resource BindingとLease Policyはproduction側に残します。bridgeは選択済みCapabilityRuntimeのfingerprintを保持するため、Resource / Lease policy driftもreplayで検出できます。一方、無関係なPlugin runtime追加はbridgeをstaleにしません。

このbridgeはderived verificationです。Permission Grant、Resource lease、Host Sandbox invocationを実行しません。actual host enforcementのE2Eは今後のEvidenceです。

## Existing Host Sandboxへの実行委譲

Application Runtimeのlegacy migrationでは、`ProductionExecutionBridge`を確認した後、既存`Registry.InvokeWithProvenance`へlegacy Capability kind / IDで委譲できます。generic Capability専用の実行transportは追加しません。

Reference testではprocess / sandbox-requiredのProviderを使い、production `HostSandboxLauncher`まで通します。artifact verifier、deny-by-default Network / Filesystem enforcer、sandboxed runnerが既存順序で使われます。必要なenforcerが無ければHostSandboxLauncherがfail closedになります。

このtestはzero-Permissionです。Resource Broker / Leaseを含む実行は次のpressureとして残します。

## Existing Resource Brokerへの委譲

Permissionを持つApplication Runtime Capabilityでも、generic contract専用のResource Authorityは追加しません。Execution Profileにはlogical Permissionを固定し、Resource ID、mount、secret handle、network endpoint、Lease Policyは既存production Runtimeへ残します。

Reference testではfilesystem read Permissionを使い、production Resource Brokerからleaseを取得し、HostSandboxLauncherへmountを渡し、呼出し後にreleaseするところまで既存`Registry.InvokeWithProvenance`を通します。Resource Brokerが無ければ既存Runtimeがfail closedになります。

このpressureはfilesystem read一件までです。Secret / Network、renew / refresh、ownership / fencingはまだgeneric Capability経由で実行していません。

## Contract definition Authority

Conformance Evidenceを誰が発行できるかと、Capability Contractそのものを誰が定義できるかは別です。

ReferenceではContract namespaceごとにaccepted publisher Authorityを持ち、exact Contract ID / version / fingerprintのpublicationを照合してからresolverへ渡します。unauthorizedなhigher compatible Contractは、適合Providerを伴っていてもcandidate catalogへ入りません。

より具体的なnamespace grantがある場合はそちらをownerとして扱います。これにより、共通root namespaceを保ちながら明示的に子namespaceを委譲できます。`std.*`も通常の同じprimitiveで扱いますが、third partyへ暗黙開放しません。

Contract Authority Evidenceの更新はContract意味そのものを変えません。同じContract bytes / Providerならresolution fingerprintは維持し、Authority binding fingerprintだけを更新します。旧Authority Evidenceを参照するpublicationはstaleとして拒否します。
