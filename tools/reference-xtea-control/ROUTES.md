# X-TEA操作経路の対応表

この表は、`reference-xtea-control`がどの入口を同じ制御面から扱えるかを示します。対象版は[`upstream.json`](upstream.json)のHEADです。画面上の全ボタン・全条件分岐の実行結果を保証する表ではありません。

XeadServerはTEIの参考対象外です。以下のXeadServer節は過去の参考記録であり、新しい比較・受入・検証の対象ではありません。

[#2152](https://github.com/hat47x/tei-platform/issues/2152)の今回の対象は、Driverの各機能タイプの主要操作、続いて参照モデルで使うスクリプトUIです。XeadServerは対象外です。下記の実動試験は配布JARを使うため、取得したソースのHEADとは別に`artifacts/live-driver/run-*/runtime.json`でJARのSHA-256を記録します。実行ごとの`summary.json`で件数・成否・skipを確認します。

## 到達性の定義

次の三つを満たすとき、その入口を「到達可能」と数えます。

1. 実行中のアプリから、役割・表示文字・名前・パスのいずれかでコンポーネントを特定できる。
2. `invoke` / `set` / `select` / `key`のいずれかで、GUIと同じ入力処理を起動できる。
3. 結果を`snapshot`、`/trace`、`screenshot`のいずれかで観察できる。

メニューのように、親メニューを開かなくても`JMenuItem`が存在する入口は、`/menus`で列挙して直接`invoke`できます。モーダルダイアログは`invoke`を非同期にしたうえで`/wait`し、開いたウィンドウを同じ手順で操作します。

長文型の明細列は、行の編集部品にあるボタンから`XFLongTextEditor`を開き、入力・閉じる・行の確定・保存まで確認します。表示専用欄・無効化された部品への`set`は`COMPONENT_NOT_EDITABLE`で拒否します。`table_edit`の`commit`はセル編集の終了であり、DBへの保存は別途Functionの保存ボタンで行います。

XF100 / XF110 / XF200 / XF300 / XF310では、Excel出力も確認します。XF110は選択画面と更新画面の両方を対象とし、選択した1行だけが出力されることも照合します。生成したXLSXを展開してセル値を読み、期待した値と非対象値の有無、DB不変を確認します。ファイルのハッシュ・セル値は操作記録と一緒に保存します。

試験用Sessionは外部ビューアーを開く`browseFile(URI)`だけを抑制し、出力処理の完了を記録します。PDF / Excelの生成処理は元のままですが、帳票内容・レイアウトの完全な一致、外部アプリでの表示・印刷は未確認です。取消時にDBの値が変わらないことは確認しますが、障害や接続断を伴うトランザクション回復は未確認です。

XF000のトランザクション試験は、元の`createTableOperator`で1行を更新し、同じ接続から未確定の新値を読みます。スクリプトの確認ダイアログでYesを選ぶと元の`instance.commit()`、Noを選ぶと元の`instance.rollback()`を実行します。戻り値で更新件数と処理前後の値を照合し、別JDBC接続から確定後の新値・更新カウンター、またはロールバック後のDB全体の不変を確認します。「保存せず閉じる」試験とは別の経路です。合成スクリプトでの確認であり、参照モデルのトランザクション設計や障害回復の受入を示しません。

XF000のコンソールは、開始した場合のDB更新と、実行せず終了した場合のDB不変を照合します。時刻指定は、同じJVMの時計から12時間後を指定して予約し、停止してDB不変を確認します。別試験で「Run right now」から実行してDB更新を照合します。さらに、同じJVMの現在時刻から30〜90秒後となる時刻を設定し、元のタイマーによる自動実行を待ちます。反復なしでは自動停止、反復ありでは次回予約を確認して停止し、どちらも別JDBC接続で更新カウンターが1回分だけ増えることを照合します。指定時刻・待機秒数・コンソール全文を記録します。翌日の2回目の実行、長期反復、休日判定は未確認です。

入力フォームは取消・閉じるの後も値取得APIに編集中の内容が残ります。取消判定は`request`の戻り値で行う必要があり、呼出元を含む試験では戻り値を確認してから検索条件へ反映します。

各試験は別JDBC接続で業務用の合成テーブルが不変であることも確認します。元のSessionはログ等を書き込むため、Session全体の無書込みを示すものではありません。参照モデル本体の実行や業務意味の受入ではありません。

`JList`の観測には、`itemCount`・`selectedIndex`に加え、`items`の各項目の`index`・表示文字`text`を含めます。チェックボックス等を項目として持つ場合は`checked`・`enabled`も返します。`selectedIndex`はカーソル位置で、チェック状態とは別です。項目は先頭200件、表示文字は既存の概要表示上限までを返し、残りがある場合は`itemsTruncated=true`になります。チェックリストの表示順をDBの読取り順と同一と仮定せず、観測した表示名から操作する行を選びます。

合成入力スクリプトでは、Linux上で`XFInputDialog.request`がnullフォントを参照しないよう、ダイアログへフォントを明示しています。元のDriverや参照モデルは修正しません。

入力ダイアログ内の型は、参照モデルで検出した`ALPHA` / `TEXTAREA` / `NUMERIC` / `ZEROFILL` / `CHECKBOX` / `LISTBOX` / `DATE`を確認します。選択リストは表示文字と戻る値を区別し、ゼロ埋めは`12`に対して`00012`が返ることを照合します。日付は表示欄へ直接書かず、元のカレンダーで日を選びます。試験用Sessionのコンストラクタは通常のApplicationのカレンダー初期化を行わないため、合成起動パネルが元の`XFCalendar`を初期化します。カレンダーの選択処理は置き換えません。

呼出し候補の検出は文字列検索であり、コメント内の記述も数えます。別名経由の呼出しや動的に生成される任意のJava/Swing UIまで網羅するものではありません。今回検出しなかったファイル選択UIと、スクリプトによる長文編集の直接呼出しは対象外です。

### Script間のオプション選択・日付範囲入力

`test_script_range_*`の4件は、合成のオプション画面から別XF000の入力画面へ進む経路を確認します。親で閉じる、子で閉じる、期間不正で2回再入力してから閉じる、再表示、元のカレンダーで日付を修正して採用する経路を含みます。採用時だけSessionの値を更新し、合成の後続Functionへ到達した印を返します。別JDBC接続で業務用の合成テーブルが不変であることも照合します。後続Functionは観測用であり、業務更新を代行しません。

| 観測点 | 確認すること |
| --- | --- |
| オプション選択 | 親を閉じると子の入力画面へ進まない |
| 子の取消 | 入力画面を閉じても、採用先のSession値は元の値を保つ |
| 期間不正でOK | 入力画面が再表示され、後続Functionへ進まない |
| 日付修正後にOK | 修正後のISO日付をSessionへ採用し、合成の後続Functionへ渡す |
| 再度の呼出し | 前回の検証メッセージが初期メッセージへ戻る |

### 呼出し連鎖と確定境界

`SNESTED`は合成XF000で主表の1行を未確定で更新し、同じSessionからXF200を呼びます。子画面を保存または閉じた後、親の確認ダイアログからcommitまたはrollbackを選びます。元のDriverと使い捨てH2で、四つの組合せを独立したDBで確認します。

| 子画面 | 親の選択 | 別JDBC接続で観測する最終値と更新カウンター |
| --- | --- | --- |
| 保存 | commit | 子の入力値、2 |
| 保存 | rollback | 子の入力値、2。子で確定した変更は親のrollbackでは戻らない |
| 保存せず閉じる | commit | 親の未確定値、1。子を閉じること自体は親のrollbackではない |
| 保存せず閉じる | rollback | 更新前の値、0 |

カウンター2は、親のUPDATEで1回、子のUPDATEで1回増えた結果です。独立した二つのトランザクションを巻き戻せたという意味ではありません。子の保存は同じ接続の保留中の変更も確定します。確認ダイアログのNoは、ここでは合成Scriptが明示的にrollbackへ対応付けたもので、すべての取消ボタンに共通する仕様ではありません。

同じ四つの組合せを、リファレンスモデルで使われる`instance.callFunction`から呼ぶ経路でも確認します。このAPIは親の戻りMapを子の戻りMapへ置き換えます。合成Scriptがコードを再設定しない場合、子を閉じたコード`21`のまま親がcommitし、DB変更が残る経路もあります。親がrollbackを呼んだことや、戻りコードだけから最終DB状態を判定しません。

一覧・帳票も、呼出し連鎖の中では確定境界になります。合成XF000が1行を未確定で更新し、次の子Functionを`instance.callFunction`で呼んだ後、親の確認でrollbackを選ぶ三つの経路を確認します。

| 子Functionの操作 | 親rollback後の独立したDB観測 | 出力物 |
| --- | --- | --- |
| XF100の選択一覧を、選ばず閉じる | 親の変更値、カウンター1が残る。戻りコードは`01` | なし |
| XF290のPDF出力を完了 | 親の変更値、カウンター1が残る。戻りコードは`00` | PDFの存在・ヘッダー・終端・サイズ・前後のSHA-256一致 |
| XF390のPDF出力を完了 | 親の変更値、カウンター1が残る。戻りコードは`00` | 同上 |

これらは子Functionが業務データのUPDATEを行うという意味ではなく、正常終了が同じ接続のcommitを呼ぶ結果です。通常の単独試験でDB不変を照合するときは、他の未確定変更がない初期DBから開始しています。「読取りの画面」と「接続上の変更を確定しない処理」は区別します。PDFは内容・レイアウトの意味一致を検証していません。

比較に必要なのは画面の種類だけでなく、呼出元・引数・戻り値・呼出順と、確定前後のDB状態です。ダイアログで入力を採用したこと、呼出元へ値を反映したこと、保存先が確定したことを別々に記録します。PDFやExcel等の外部出力について、DBのrollbackで出力物まで取り消せるとは仮定しません。

TEI側では、Dataの値・版、Functionの引数・戻り値・遷移、Businessの確定条件と権限を分けて照合する必要があります。この試験は旧Driverの接続共有と観測結果を示すものです。旧Sessionのトランザクション境界やRETURN_CODEを、そのままTEIの業務Action・Host契約として採用する判断は含みません。
