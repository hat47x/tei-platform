# X-TEA操作経路の対応表

この表は、`reference-xtea-control`がどの入口を同じ制御面から扱えるかを示します。対象版は[`upstream.json`](upstream.json)の四つのHEADです。画面上の全ボタン・全条件分岐の実行結果を保証する表ではありません。

[#2152](https://github.com/hat47x/tei-platform/issues/2152)の今回の対象は、Driverの各機能タイプの主要操作、続いて参照モデルで使うスクリプトUIです。XeadServerは対象外です。下記の実動試験は配布JARを使うため、取得したソースのHEADとは別に`artifacts/live-driver/run-*/runtime.json`でJARのSHA-256を記録します。実行ごとの`summary.json`で件数・成否・skipを確認します。

## 到達性の定義

次の三つを満たすとき、その入口を「到達可能」と数えます。

1. 実行中のアプリから、役割・表示文字・名前・パスのいずれかでコンポーネントを特定できる。
2. `invoke` / `set` / `select` / `key`のいずれかで、GUIと同じ入力処理を起動できる。
3. 結果を`snapshot`、`/trace`、`screenshot`のいずれかで観察できる。

メニューのように、親メニューを開かなくても`JMenuItem`が存在する入口は、`/menus`で列挙して直接`invoke`できます。モーダルダイアログは`invoke`を非同期にしたうえで`/wait`し、開いたウィンドウを同じ手順で操作します。

### 各機能タイプの実動試験

`tests/test_live_driver.py`は、元の`xteadrv.jar`の`Session.executeFunction` / FunctionLauncherを、独自に作った合成起動パネルから呼びます。各試験で合成XEAFと使い捨てH2を新しく作り、入力はHTTP制御面から行います。元のX-TEAクラスを変更・再コンパイルしません。本来のApplicationのログイン画面・メニューを再試験するものではありません。

| タイプ | 確認する主要経路 | 結果の照合 |
| --- | --- | --- |
| XF000 | Functionのスクリプトを起動し復帰、更新後の確認ダイアログからcommit / rollback | 戻り値のマーカー、同一トランザクション内の更新値、別JDBC接続で確定・取消後の値を照合 |
| XF100 | 2行の一覧→検索で1行→選択・Enter→XF200→閉じる | 件数、詳細値、DB不変 |
| XF110 | 行をSpaceでチェック→次画面→表の実編集部品→確定→一括更新、編集後に閉じて取消 | 編集直後の行、別JDBC接続で変更行と非対象行を比較 |
| XF200 | 更新・保存、編集後に閉じて取消、新規追加、既存行のコピー、削除確認 | 別JDBC接続で値・更新カウンター・行の有無を比較 |
| XF290 | 1レコードのPDF出力 | 正常復帰、PDFヘッダー・終端・サイズ・SHA-256、DB不変 |
| XF300 | 見出しと2行の関連明細→閉じる | 見出し値、明細値・件数、DB不変 |
| XF310 | 明細編集・保存、行追加・保存、行削除・保存、編集後に閉じて取消 | 編集直後の行と別JDBC接続の前後比較 |
| XF390 | 見出しと明細のPDF出力 | 正常復帰、PDFヘッダー・終端・サイズ・SHA-256、DB不変 |

長文型の明細列は、行の編集部品にあるボタンから`XFLongTextEditor`を開き、入力・閉じる・行の確定・保存まで確認します。表示専用欄への`set`は`COMPONENT_NOT_EDITABLE`で拒否します。`table_edit`の`commit`はセル編集の終了であり、DBへの保存は別途Functionの保存ボタンで行います。

XF100 / XF110 / XF200 / XF300 / XF310では、Excel出力も確認します。XF110は選択画面と更新画面の両方を対象とし、選択した1行だけが出力されることも照合します。生成したXLSXを展開してセル値を読み、期待した値と非対象値の有無、DB不変を確認します。ファイルのハッシュ・セル値は操作記録と一緒に保存します。

試験用Sessionは外部ビューアーを開く`browseFile(URI)`だけを抑制し、出力処理の完了を記録します。PDF / Excelの生成処理は元のままですが、帳票内容・レイアウトの完全な一致、外部アプリでの表示・印刷は未確認です。取消時にDBの値が変わらないことは確認しますが、障害や接続断を伴うトランザクション回復は未確認です。

XF000のトランザクション試験は、元の`createTableOperator`で1行を更新し、同じ接続から未確定の新値を読みます。スクリプトの確認ダイアログでYesを選ぶと元の`instance.commit()`、Noを選ぶと元の`instance.rollback()`を実行します。戻り値で更新件数と処理前後の値を照合し、別JDBC接続から確定後の新値・更新カウンター、またはロールバック後のDB全体の不変を確認します。「保存せず閉じる」試験とは別の経路です。合成スクリプトでの確認であり、参照モデルのトランザクション設計や障害回復の受入を示しません。

### スクリプトUI

`inventory_xtea.py`で手元の参照モデルZIPを調べると、13のXEAF（バックアップ版を含む）に8タイプすべてが存在します。版を自動選択せず、メンバーごとの指紋と件数をローカルに記録します。`buttonActions`には標準操作の件数を記録し、任意の呼出し式は`OTHER`へまとめて内容を出力しません。これは静的な使用箇所の調査で、各参照モデルの実行結果ではありません。XEAFがない3アーカイブは`uninspectedInputs`に`NO_XEAF`として残します。

| 検出した呼出し候補 | 合成XF000のスクリプトから確認する操作 |
| --- | --- |
| `getInputDialog` | 入力、OKで返す値、閉じて取消 |
| `getOptionDialog` | 選択肢を変更しEnter、選択番号を照合 |
| `getCheckListDialog` | 行選択・Space・OK、選択キーを照合 |
| `showMessageDialog` | メッセージを閉じてスクリプトへ復帰 |
| `showConfirmDialog` | Yesを押し戻り値を照合 |
| `showInputDialog` | 文字入力・OK、戻り値を照合 |
| `showOptionDialog` | 動的な選択ボタンを押し戻り値を照合 |

合成入力スクリプトでは、Linux上で`XFInputDialog.request`がnullフォントを参照しないよう、ダイアログへフォントを明示しています。元のDriverや参照モデルは修正しません。

入力ダイアログ内の型は、参照モデルで検出した`ALPHA` / `TEXTAREA` / `NUMERIC` / `ZEROFILL` / `CHECKBOX` / `LISTBOX` / `DATE`を確認します。選択リストは表示文字と戻る値を区別し、ゼロ埋めは`12`に対して`00012`が返ることを照合します。日付は表示欄へ直接書かず、元のカレンダーで日を選びます。試験用Sessionのコンストラクタは通常のApplicationのカレンダー初期化を行わないため、合成起動パネルが元の`XFCalendar`を初期化します。カレンダーの選択処理は置き換えません。

呼出し候補の検出は文字列検索であり、コメント内の記述も数えます。別名経由の呼出しや動的に生成される任意のJava/Swing UIまで網羅するものではありません。今回検出しなかったファイル選択UIと、スクリプトによる長文編集の直接呼出しは対象外です。

## XeadServer（今回の対象外）

`web.xml`のサーブレットマッピングと`DBMethod` / `Service`の分岐に基づきます。

| サーブレット | 経路 | 分岐 |
| --- | --- | --- |
| `DBMethod` | `GET /DBMethod` | 接続プール、セッション別接続、最終コマンドの状態表示 |
| `DBMethod` | `POST /DBMethod` | `SELECT`（`Relation`のJava直列化） |
| `DBMethod` | `POST /DBMethod` | `SELECT COUNT(...)`（件数文字列） |
| `DBMethod` | `POST /DBMethod` | `INSERT` / `UPDATE` / `DELETE`（更新件数） |
| `DBMethod` | `POST /DBMethod` | `COMMIT` / `ROLLBACK` |
| `DBMethod` | `POST /DBMethod` | `CALL ...` |
| `DBMethod` | `POST /DBMethod` | `IP` |
| `Service` | `GET /Service` | セッション開始状況、拒否・成功・中断件数 |
| `Service` | `POST /Service` | `FUNCTION`と任意パラメータ。応答はJSON/XML/テキスト |

確認済み: 上記`DBMethod`分岐を、元の`DBMethod`を埋め込みJettyで起動し、使い捨てH2の合成テーブルに対してHTTPで実行。`GET`の状態表示、SELECTのJava直列化、COUNT、INSERT、UPDATE、DELETE、COMMIT、ROLLBACK、CALL、IPを確認。`CALL SQUARE(9)`は「procedure was executed」を返す。

`Service`の`GET`はセッション状態を返すことを確認。`POST`は、Skeletonの一時複製に対して`FUNCTION=AF200J`、`REQUEST_TYPE=ListSections`を送り、2件の部門データがJSONで返ることを確認。ただしハーネスは、上流の認証前`userID`検査を引数`user`へ置き換えるビルド時差分を適用している。この成功は認証バグを補った状態でのFunction実行経路の確認であり、上流認証の正しさの証明ではない。

`WEB-INF/web.xml`付きのWARディレクトリを作り、埋め込みTomcat 9.0へ配備した状態でも、`DBMethod`の状態取得と`Service`の`AF200J`をHTTPで確認。外部Tomcat 9.0.89へWARを配備した状態でも同じ2経路を確認。WAR内の`JdbcBootstrap`がDerbyドライバを`DriverManager`へ登録する。

## 未確認の経路

- Modeler / Editorの全ダイアログを開いた実行。表の全セル、全ての検査エラー、全てのインポート分岐は未実行。
- 各参照モデル本体とその業務DBでの全経路、XF000のタイマー、一覧の全ソート・ページ移動・出力の全分岐、別機能への全呼出し、検出対象外の入力型・全検査エラー、メール、HTTP。
- 元の`jdbc:derby://localhost/...`接続、Derby Network Server。今回の更新試験は使い捨てH2のみ。
- XeadServerのJNDI DataSource、本番Tomcat設定、実デプロイ環境、DB製品別ドライバ、認可・本番運用。
- `Service`の認証条件の正しさ、実ユーザー、認可。ハーネスでは認証前の`userID`検査を引数`user`へ置き換えている。
- WindowsのDPI・Look and Feel・ロケール別の表示差。セレクタは表示文字に依存できるが、文字列が変わればシナリオ側の更新が要る。
- Java 8実機。クラスファイルはJava 8（major 52）だが、実行確認はJDK 11。
